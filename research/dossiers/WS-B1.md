## 1. Scope & boundary

This workstream decides the **shape and contract of the run ledger**: (i) the typed, append-only event log that is the authoritative record of what a run decided, did, and observed; (ii) the ID model (run / turn / model-call / tool-call / effect / artifact / subagent / configuration) and its invariants; (iii) the ordering and causality model within a run and across subagent runs; (iv) the boundary between the authoritative log and derived (materialized) views — OQ-003 / OQ-042, doc 2 §11 "event sourcing selectively, not dogmatically"; (v) content-addressed artifact references in place of embedded payloads; (vi) retention and redaction; (vii) the storage-property requirements WS-L1 needs, stated without naming any technology; (viii) acceptance criteria (crash consistency, rebuildability, replay determinism where it is possible); and (ix) how audit (WS-H6), replay/branching (WS-B4), context views (WS-D1), telemetry (WS-I1) and the results store (WS-J5) consume the ledger.

It explicitly leaves to neighbours: the *semantics* of effects, idempotency keys, leases and compensation (WS-B2 — B1 only fixes the event classes and required fields that B2's state machine must emit); checkpoint/wakeup/restart policy (WS-B3); fork/branch/speculative execution semantics and nondeterminism boundaries (WS-B4 — B1 fixes the identity of a fork and the immutability of the source); the provenance/authority label scheme carried on content-bearing events (WS-L3); artifact identity beyond "content-addressed bytes" (WS-L4); the tamper-evidence attestation protocol (WS-H6 — B1 supplies the hash chain it attests); the reference-monitor events' authority semantics (WS-H1); the context-builder's view policy (WS-D1 — B1 supplies the derived-view contract and invariants); metric definitions (WS-I2); the interchange mapping (WS-J6/I3, OQ-030); and every language/runtime/storage-technology choice (WS-L1).

6. (added) What do at least three mature harnesses actually persist, in what unit, with what ordering and crash semantics — and where do they diverge?
7. (added) What must *not* be event-sourced (environment state, secrets, streaming deltas, large payloads) and how is the boundary drawn so the transcript does not become the database?

## 4. Findings

### 4a. Mechanism evidence (a failure mode exists / an architecture is implementable)

**F1 — Every mature harness read here converges on an append-only record as the durable unit, but three different *units* are in use.** (i) *Event per record*: OpenHands writes one JSON file per event (`event-{idx:05d}-{id}.json`, `persistence_const.py`) and validates duplicate ids and parent existence on append (`event_store.py: EventLog.append`). (ii) *Transaction per line*: Pi writes one JSONL line per commit containing one or more `CommittedWrite`s (`jsonl/io.ts: serializeJsonlTransaction`), validates strictly monotonic `seq` (`commit.ts: validateCommittedWrites` — "Non-monotonic storage sequence"), and reads to the last *complete* line (`jsonl/fork.ts: highestCompleteSeq`). (iii) *Item per line with a persistence policy*: Codex writes `{timestamp, ordinal?, type, payload}` lines (`recorder.rs: RolloutLineRef`) and decides per item type whether it is persisted at all (`policy.rs: should_persist_event_msg` — streaming deltas, `ExecCommandBegin`, `ExecApprovalRequest`, `RequestPermissions` are *not* persisted; `TurnStarted/TurnComplete/TurnAborted`, `ContextCompacted`, `ThreadRolledBack`, `ThreadSettingsApplied`, `TokenCount`, `*End` events are). Logos (S-073, provisional) states the same discipline as invariants I1–I4. **Implication:** the reference runtime's unit should be an *atomic multi-event append* (Pi's transaction) with an explicit per-class persistence policy (Codex) — never "log everything the UI saw".

**F2 — The derived view is *always* a projection with enforced invariants, never the log itself.** OpenHands' `ConversationState.view` is `View.from_events(path_to_root(leaf))` with property enforcement on rebuild (`tool_call_matching.py`: "exactly one observation-like event for each action tool_call_id"; `tool_loop_atomicity`, `batch_atomicity`, `observation_uniqueness`), and the docstring is explicit that "linear append replays only the new tail — O(k)". Logos I4 ("the rebuilt projection equals the messages the session showed") and its pruning rule ("long tool results are pruned in the projection while the full text remains in the file, and nothing is removed from the file itself") are the same mechanism. Codex reconstructs history by scanning the rollout *in reverse* until it finds a surviving compaction checkpoint (`rollout_reconstruction.rs: reconstruct_history_from_rollout`), and interprets `ThreadRolledBack{num_turns}` as "skip the next N user-turn segments" — rollback is an *appended event*, not a truncation. goose's `MessageMetadata{agent_visible, user_visible}` is a degenerate projection hint stored on the row. **Implication:** the context view (WS-D1) is a materialized view whose *invariants* (tool-call pairing, batch atomicity, forgotten-range exclusion) are part of the ledger contract, and navigation/rollback/compaction are events that the projection interprets.

**F3 — Crash consistency is achieved by (a) durable-before-visible, (b) a single writer per run, and (c) persisting the *operation state machine*, not only messages.** OpenHands takes a lock file plus a length marker whose *deletion precedes* its rewrite so an interrupted update "leaves no marker rather than a stale one" (`event_store.py: _advance_length_marker`). Codex holds a per-thread writer lock (`writer_lock.rs: "Acquires exclusive writer ownership, returning WouldBlock for an active writer"`) and a background writer whose `pending_items` are removed "only after it is written successfully" so I/O failure keeps the unwritten suffix for retry (`recorder.rs: RolloutWriterState`). Pi goes furthest: the lane's operation state (`starting → checkpoint → assistant.ready → assistant.effect_pending → tools → …`) is itself persisted, each tool call carries `planned → effect_pending{replay: "never"|"safe"} → outcome_ready → completed` (`session/types.ts`), and on restart an orphaned `effect_pending` assistant call is *synthetically settled* with an explicit warning ("the external outcome is unknown") and `recovery: true` on the emitted events (`runtime/drive/recovery.ts`). Logos (provisional) reports zero repeated effects at four kill points (during execution; after return before persistence; after persistence before announcement; after announcement) using the same durable-before-visible rule. **Implication:** the ledger must record effect *phases* as first-class events (doc 2 §5.5 "intent, prepared action, commit, observed result"; Shepherd's intent/outcome pair), and resume semantics are a function of which phase was last durable. B2 owns the phase semantics and has since refined the four doc-2 phases into a ten-state lifecycle (`intended → authorized|refused → prepared → committing → observed | unknown → probed → compensated|reverted|abandoned`, WS-B2 §6.1, with `committing` written durably *before* dispatch); B1 adopts B2's state names verbatim as the `action.effect.*` event classes and owns only the envelope facts: each phase is a separately durable event carrying the same `effect_id`, every post-`prepared` event carries the writer's `lease_generation`, and exactly one terminal event closes each `effect_id` (Logos I3 generalized from tool results to effects).

**F4 — Branching/forking is universal, and two designs exist: copy-the-prefix vs. reference-the-prefix.** OpenHands `fork()` deep-copies events into a new conversation ("Events are copied so the source remains immutable"); Pi's `runJsonlFork` copies the surviving prefix into an atomically published destination, preserving original `seq`s and `nextSeq`; Codex instead records `forked_from_id`, `forked_from_ordinal_exclusive` and a `history_base` reference ("Revert may replace the physical history base while retaining this fork boundary", `protocol.rs: SessionMeta`). Both preserve source immutability; reference-forks avoid duplication but require lineage resolution at read time. opencode's revert is the negative case: `SessionRevert` *removes* messages (`revert.ts: removeMessage/removePart`) and repairs the workspace from a separate git snapshot store — history is lost. goose's `replace_conversation` does `DELETE FROM messages` (session_manager.rs). **Implication:** the ledger forbids destructive rewrite; forks are new runs with a lineage reference; the *bundle* (WS-I3) materializes lineage on export.

**F5 — Identity: time-ordered allocated ids for runs/threads/entries, content addresses for artifacts and environment state, provider ids demoted to surfaces.** Codex `ThreadId::new()` is `Uuid::now_v7()` with the comment "some use cases rely on that"; Pi's `idGenerator` defaults to `uuidv7`; OpenHands uses UUID4 event ids plus a dense index; opencode prefixes ids (`msg`, `prt`) for type-safety. Shepherd addresses forks and filesystem layers by content hash ("two siblings … share their entire prefix by content hash"); opencode's `Snapshot` stores workspace state as git objects in a separate gitdir; Codex `WorldStateItem{full, state}` records baseline + patches. OTel fixes the shape of a causal identity model (one parent, many links, immutable context); CloudEvents fixes the uniqueness rule (`source + id`). Provider-issued ids (`llm_response_id`, `compaction_response_id`, tool-call ids that "reset each session" per OpenHands' `resume_transcript.py` docstring) are recorded but are *not* the ledger's identity. **Implication:** allocated, time-ordered, opaque ids for the things the runtime creates; content addresses for immutable values; provider/surface ids stored as aliases — consistent with T-LCD-10 (names are surfaces, identities are semantic).

**F6 — Large payloads and environment state are kept out of the event stream in every system that has scaled.** Codex persists a `Compacted` item whose `replacement_history` *is* the new baseline and whose `compaction_response_id` lets `thread/resume` restore usage "without scanning arbitrarily far back"; it compresses rollouts at rest (`compression.rs`) and reads them with a reverse scanner. Logos prunes long tool results in the projection only. Shepherd snapshots environments as CoW layers, not events. opencode stores workspace snapshots as git objects. Managed Agents call the container "the way it called any other tool" and keep the session log outside the harness. This is doc 2 §11's rule ("store content-addressed artifact references instead") observed in the wild. **Implication:** a size threshold above which observation/request/response payloads are stored as content-addressed blobs and referenced; environment state is *never* event-sourced — the ledger records handles, snapshot references and world-state patches.

**F7 — Schema evolution is treated as a hard compatibility contract, with two mechanisms.** OpenHands' AGENTS.md: "Old events should ALWAYS load without error… Never use `extra='forbid'` without a deprecation handler"; golden fixtures per last-known version; `schema_version` bump on incompatible change. Pi versions the file format (`JSONL_FORMAT_VERSION = 4`, `legacy-v3.ts` normalizer) and the coding-agent runs in-memory migrations v1→v2→v3 (`session-manager.ts: migrateSessionEntries`). Codex rejects unknown history modes and strips legacy "ghost snapshot" lines on load (`recorder.rs: reject_unknown_thread_history_mode`, `strip_legacy_ghost_snapshot_rollout_line`). Kiehl's counter-evidence is exactly this cost. **Implication:** every event carries `schema_version`; evolution is additive with recorded deprecations; a loader must accept every historical version (acceptance criterion, §6.4).

**F8 — Deterministic replay is a property of the *control loop*, not of the log, and it has a known price.** Temporal's model: workflow code must make "the same Workflow API calls in the same sequence, given the same input"; nondeterminism arises from code change or intrinsic randomness; everything effectful routes through activities; code changes require versioning/patching. Cursor reports adopting this model for its loop and shortening workflows "which makes version upgrades easier". No coding harness read here replays the control loop deterministically; all of them *reconstruct state from events* and continue live (Codex reconstruction, OpenHands `rebuild_view`, Pi `checkpoint` continuation, Logos cold switching). Shepherd replays "the suffix with the edited workflow" — i.e., re-executes with fresh model samples, exploiting byte-identical prefixes for KV-cache reuse, and does not claim deterministic resampling. **Implication (answers the OQ-042 replay question):** durability at Stage 0–1 requires *event reconstruction* only; deterministic control-loop replay is a declared capability of a control-strategy variant that (a) consumes recorded model I/O (`observability_level ⊇ model_io`) and (b) confines nondeterminism to events (Temporal-style), and it is an acceptance test at Stage 3 for those variants, not a Core invariant.

**F9 — External protocols already define the *minimum* event vocabulary and cursor semantics the ledger must be able to lower to and lift from.** ACP v2's `SessionUpdate` union, `tool_call_update` as an upsert keyed by `toolCallId` with a four-state status, `state_update{idle, stopReason}`, `usage_update`, and `session/resume{replayFrom}` with inclusive cursors; MCP's `_meta` and `progressToken`. Omnigent's executor vocabulary (WS-A1 F2) is the same shape. **Implication:** the native ledger stays typed and richer (ADR-0005), but each native event class declares its lowering to the ACP/Omnigent-style vocabulary, and the ledger's read API offers an inclusive `(run_id, seq)` cursor so a hosted or embedding surface can `replayFrom`.

### 4b. Performance evidence (benchmark lifts) — each tagged `provisional` if 2026 single-team/preprint

- Logos (S-073, `provisional`): under one injected fault on 200 BFCL tasks the single-process baseline scored 1.5% and lost all sessions; Logos preserved all sessions with zero wasted calls and 120 successes; bus overhead ≈ 1 token per 823 first tokens. **Use:** mechanism-level corroboration that durable-before-visible + rebuildable projection yields exactly-once redo; the numbers are not load-bearing.
- Shepherd (S-078, `provisional`): fork 134–143 ms independent of image size vs 53.5 s for full rootfs copy; ≈10 KB metadata per fork. **Use:** feasibility of content-addressed environment snapshots referenced from the ledger (B4/B5); not a design constant.
- Cursor (S-052, production, single team): reliability "one 9 → two 9s" after moving the loop onto a durable-execution engine; 50M actions/day. **Use:** engineering evidence that persisted operation state plus retries is worth its cost at scale; product-specific.
- No benchmark measures "event log vs snapshot store" for agents; doc 2 §6 rates "cross-process/event-sourced harnesses are the right default runtime" a *strong systems hypothesis* with early academic evidence. This dossier's C0 recommendation therefore rests on mechanism convergence across five Tier-B codebases and Tier-B production reports, not on any 2026 performance number.

## 5. Disconfirming evidence & negative results

**Against "the event log is authoritative; everything else is derived" (ADR-0026).** Kiehl's retrospective (S-195) is the sharpest: projections multiply code paths ("adding one projection doubles the amount of code that touches your event stream"), schema evolution forces a choice between casting old events (fidelity loss) and rewriting the ledger (temporal-query loss), materialization lag creates 404/duplicate anomalies, and "a history table gets you 80% of the value of a ledger with essentially none of the cost". Fowler names the external-gateway problem and the code-versioning problem. LangGraph (S-143), a widely used runtime, chose *snapshots with history* rather than an event log and offers time travel. **Why it does not overturn the decision:** (a) the projections here are few and fixed by contract (context view, run summary, index, results row) — not an open ecosystem of subscribers; (b) HarnessHarness's purpose is instrument validity: attribution, ablation and audit *require* the fine-grained decision/effect record that a history table of messages cannot supply (T-LCD-13 needs `delivered/activated/followed`, H6 needs a chain, B2 needs effect phases); (c) the "selective" qualifier is applied literally — environment state, secrets, deltas and large payloads are excluded, so the transcript does not become the database; (d) the "history table" alternative is *exactly* what goose/opencode built, and both had to add destructive rewrite paths that lose the audit record. The cost is real and is carried as a consequence (schema-evolution discipline, acceptance tests for rebuild).

**Against deterministic replay as a Core requirement.** Temporal's documentation shows deterministic replay imposes coding constraints (no reordering of command-producing calls, versioning on every change) that a research runtime meant to *vary* control strategies would find hostile; Shepherd, the strongest replay-oriented research system, re-executes rather than deterministically replays model sampling. Hence the recommendation limits Core to reconstruction and makes deterministic replay a declared variant capability (§6.3 AC-B1-4). The disconfirming risk on the *other* side — that without deterministic replay, counterfactual attribution (WS-I7) is invalid — is real and is recorded as an open question for B4/I7 (OQ-082).

**Against a per-run hash chain / canonical encoding at Stage 1.** Cost: every event must be serialized canonically twice (once to hash, once to store) unless the stored form *is* canonical; JCS forces I-JSON number limits (big integers as strings); chains complicate forks (a forked run's chain must anchor to the source's hash at the fork point). Counter-consideration: none of the audited harnesses chain their logs, and they are widely used. **Why it does not overturn:** the sponsor's "deep audit trails at all levels" (R-2.8.6, C0/Must) and WS-H6 need a tamper-evident substrate that cannot be retrofitted cheaply; the hash is over the canonical form only, so the stored encoding is free to differ; the design is staged (chain at Stage 1, attestation at H6). The encoding *class* choice is left to WS-A3/L1 (ADR-0029 states the properties, not the format).

**Against time-ordered allocated ids.** UUIDv7-class ids leak creation time and are guessable across a millisecond window; content-addressed ids are stable across re-runs, allocated ids are not, so a re-executed run cannot be matched by id. **Why it does not overturn:** runs are *supposed* to be distinct experimental observations; matching across re-runs is by `configuration_id` (content-addressed) + `seed`, not by run id; time-leak is acceptable inside a research instrument and can be replaced by an opaque generator without changing the contract (ids are opaque to consumers).

**Against reference-forks (vs copy).** A referenced fork is not self-contained; deleting or GC-ing the source breaks lineage; read paths must resolve chains. Pi and OpenHands copy for this reason. **Mitigation:** lineage references are content-hashed at the fork event (`source_head_hash`), GC of a referenced prefix is forbidden by the retention policy (§6.5), and the bundle export (I3) materializes lineage, which is where self-containment matters.

**Negative results recorded:** no audited system carries authority/provenance labels on events beyond `source ∈ {agent, user, environment, hook}` (OpenHands) or `SessionSource` (Codex) — the L3 labels are `no-precedent` as event fields; no audited system stamps an observability level on events — `no-precedent` (needed for T-LCD-15); no audited system records artifact `activated/followed` — `no-precedent` (T-LCD-13).

## 6. Recommendation for the spec

### 6.1 Position (answers OQ-003 / OQ-042)

1. **The run ledger is the sole authoritative record of a run's decisions, effects and observations.** Authoritative = (a) the typed append-only event log, (b) the content-addressed artifact/blob store the log references, (c) the immutable run manifest (the payload of the first event). Everything else — context view, run summary, HEAD, indexes, results rows, leaderboard rows, cost totals, audit tree heads — is a **materialized view**: derived, rebuildable from (a)+(b) alone, stamped with the `(run_id, seq)` watermark it was derived from, and never written to except by projection.
2. **Selective, not dogmatic.** Not event-sourced: environment state (filesystem, container, browser — recorded as handles, snapshot refs and world-state patches); secrets (references only, never values); streaming deltas (ephemeral; final message persisted); large payloads (offloaded as blobs above a threshold); UI-only presentation facts (Codex `RealtimeItem` class — ephemeral unless a consumer declares need).
3. **Write path:** one writer per run holding a **lease whose `lease_generation` is the fencing token** (WS-B2 §6.3); appends are atomic multi-event units assigned a dense, strictly increasing per-run `seq`; an event is *visible* (to views, streams, subagents, the reference monitor) only after it is *durable*; readers stop at the last complete record. Storage class at Stage 0–1: a local, ordered, append-only record store plus a local content-addressed blob store (properties in §6.6; no technology named).
4. **Replay:** Core guarantees **event reconstruction** (rebuild any view; resume from the last durable effect phase). **Deterministic control-loop replay** is a *declared capability* of control-strategy variants that consume recorded model I/O and confine nondeterminism to events; it is tested at Stage 3, not assumed at Stage 1.

### 6.2 Interface-contract sketch (language-agnostic)

Operations (inputs → outputs; invariants; failure modes):

- `open_run(manifest: RunManifest) → RunId` — allocates a fresh time-ordered RunId, appends `run.created` as seq 0 with the manifest, acquires the writer lease. *Invariants:* manifest immutable thereafter; `participant_class`, `observability_level`, `configuration_id` present. *Failures:* `ManifestInvalid`, `ConfigurationUnresolvable`.
- `acquire_writer(run, holder, ttl) → Lease{lease_id, lease_generation, expires}` / `renew` / `release` — *Invariant:* at most one valid lease per run; `lease_generation` strictly increases on every takeover (the fencing token; same field WS-B2 §6.3 puts on every post-`prepared` effect event and OpenHands `agent_server/conversation_lease.py` implements); every append carries it; a stale generation is refused (`Fenced` = WS-B2's `StaleLease`). *Failures:* `WouldBlock(active_holder)`, `Fenced`. Lease *policy* (ttl, renewal cadence, takeover) is WS-B2/B3's; B1 fixes only that the generation is a ledger-level field and the ledger is the fencing point.
- `append(run, lease, events: [Event]) → SeqRange` — atomic; assigns contiguous seqs; validates each event: schema, unique `event_id` in run, `parent_event_id` exists (or is the reserved root), scope ids (`turn_id`, `model_call_id`, `tool_call_id`, `effect_id`) refer to opened scopes, `lease_generation` is current, `prev_hash` continuity. *Invariants:* durable-before-visible; no partial batch. *Failures:* `SchemaViolation`, `UnknownParent`, `DuplicateEventId`, `ScopeNotOpen`, `Fenced`, `Durability(io)` (batch not visible; retry safe).
- `read(run, cursor: {from_seq | from_event_id, inclusive: true}, filter?: {plane, class, scope}, direction: fwd|rev, limit) → Page{events, next_cursor}` — *Invariant:* returns only durable events; reverse scan supported (Codex precedent) so reconstruction is O(tail). *Failures:* `UnknownRun`, `UnknownCursor`.
- `head(run) → {seq, event_id, hash}`; `lineage(run) → [{run_id, up_to_seq, head_hash}]` (fork chain, root first).
- `fork(run, at: EventId|Seq, manifest_delta) → RunId` — appends `run.forked` to the *new* run with `forked_from{run_id, at_seq, source_head_hash}`; source untouched. *Failures:* `UnknownForkPoint`, `SourceIncomplete` (fork point beyond durable head).
- `navigate(run, lease, to: EventId|null)` — appends `head.moved`; subsequent appends carry `parent_event_id = to`. Never deletes.
- `put_blob(bytes, media_type) → ContentAddress`; `get_blob(addr) → bytes|Missing` — *Invariants:* address = hash over bytes (domain-separated); idempotent; dedup. *Failures:* `TooLarge(policy)`, `Missing` (GC'd; hash still verifiable).
- `project(run, view_kind, until?: Seq) → View{payload, derived_from: (run_id, seq), view_hash}` — deterministic function of the durable prefix. View kinds at C0: `context_view` (D1 policy applied), `run_summary`, `effect_ledger` (B2), `audit_chain` (H6), `results_row` (J5). *Invariant:* `project(run, k, s)` is pure in `(events ≤ s, view policy version)`; two rebuilds yield equal `view_hash`.
- `verify(run, from?, to?) → {ok | Tampered(at_seq)}` — recomputes the hash chain over the canonical form.
- `redact(run, lease, target: EventId|ContentAddress, reason, authority) → SeqRange` — appends `ledger.redacted` tombstone; deletes blob bytes only; the event's canonical hash stays verifiable. *Failure:* `NotRedactable(class)` for events whose payload carries no redactable content.
- `subscribe(run, from: Cursor) → Stream<Event>` — live tail after durability; used by surfaces, the reference monitor, telemetry, and hosted-participant adapters; supports `replayFrom` semantics identical to ACP.

Hosted participants (ADR-0005): the hosting adapter is the *producer* of events for that run; it calls `append` with `participant_class = hosted`, `observability_level` per its capability declaration, and stores the participant's native transcript as a blob referenced by `hosted.native_record{addr, format}`; interchange import is `open_run` + one `append` batch with `provenance = imported{format, source}`.

### 6.3 Data-model sketch

**Envelope (every event):**
`Event{ event_id, run_id, seq, ts (RFC 3339 UTC, ms), hlc? (optional hybrid logical clock for cross-run ordering), plane ∈ {lifecycle, context, model, action, control, verification, security, measurement}, class: "plane.noun.verb" , schema_version, producer{ component_class, component_variant_ref, participant_ref }, participant_class ∈ {native, hosted}, observability_level ⊆ {events, model_io, end_state, ledger}, durability ∈ {ledger, ephemeral} (class-level constant), scope{ turn_id?, model_call_id?, tool_call_id?, effect_id?, child_run_id? }, lease_generation (of the writer that appended it), parent_event_id (branch tree; reserved root sentinel), causes: [EventRef] (non-tree causal links, OTel-style; may cross runs), refs: [ContentAddress] (payload offloads, artifacts, snapshots), ir_refs: [{semantic_id, version_id}] (the HIR entities the event is about — capability, procedure, rule, validator — per WS-A3 §6.7 "WS-B1 stamps semantic_id/version_id"), provenance? (L3 label; mandatory on content-bearing classes), payload: typed per class, prev_hash, hash }`.
`EventRef = (run_id, event_id | seq)`; `ContentAddress = (hash_algorithm, digest, media_type, size)`.

**Observation payloads (answers WS-A3's OQ-057 and CF-036).** The HIR `Observation` entity is the *payload type*; the ledger never stores observations as nodes of a definition document. `context.observation.recorded` carries the `Observation` value by value when its canonical size is ≤ the offload threshold and by `ContentAddress` otherwise; in both cases the event stamps `version_id = H(canonical(observation))`, so an observation is addressable from definitions, validators and later runs by content. The `produced-by` edge (observation → effect/tool call) therefore lives in the ledger as `scope.effect_id` + `causes`, not in any definition. Observations that a harness *edit* wants to reference (e.g., a counterexample set for WS-I5) are pinned by the bundle (WS-I3), never copied into the IR.

**Canonical numbers (answers WS-A3's OQ-060 for the ledger side).** The canonical form used for `hash`, `version_id` and `ContentAddress` admits integers (arbitrary precision, no exponent) and *decimal strings* only; IEEE-754 doubles are not admitted because two implementations need not print them identically and JCS's I-JSON limits exclude 64-bit counters. Ledger fields that are naturally fractional (scores, ratios, seconds) are declared as decimal strings or scaled integers (`latency_ms`, `tokens`) in their payload schema. This is the same rule WS-A3 §6.1 proposes for IR documents, so one canonicalizer serves both (OQ-041).

**ID model and invariants:**
- `RunId`: allocated once at `open_run`; opaque, globally unique, time-ordered class (UUIDv7-class semantics: creation-time-sortable; RFC 9562 monotonicity method required within a generator). Never reused; child runs carry `parent_run_id` and `spawn_event: EventRef`.
- `seq`: per-run, dense (0..n), strictly increasing, assigned only at durable append; `(run_id, seq)` totally orders one run. Forks do not renumber: a forked run starts at its own seq 0 with `forked_from{run_id, at_seq}`.
- `EventId`: allocated (time-ordered class), unique within a run; the *hash* is derived and separate (`hash = H(canonical(envelope − {hash}) ∥ prev_hash)`), so an event can be referenced before it is hashed but audited after.
- `TurnId`, `ModelCallId`, `ToolCallId`, `PermissionId`: allocated by the runtime at the scope's opening event and closed by exactly one terminal event; provider-issued ids (response ids, provider tool-call ids) are recorded as `surface_ids{}` aliases, never as identity (T-LCD-10 applied to the ledger). Nesting is `run_id ⊃ turn_id ⊃ model_call_id ⊃ tool_call_id` — the same structural chain WS-B2 §6.4 writes as `run_id ⊃ turn_id ⊃ step_id ⊃ call_id`; B1 proposes `model_call_id`/`tool_call_id` as the canonical spellings (a "step" in every audited harness is exactly one model call; "call" is ambiguous between model and tool) and lists the pair as an alias conflict for synthesis (CF-060).
- `EffectId`: the semantic identity of one intended side effect across attempts, resumes and hosting; minted by the runtime, never by the model or the tool. Per WS-B2 §6.1 it is derived deterministically from `(run_id, model_call_id, tool_call_id, ordinal)` so that a re-parsed model response after a crash yields the same `effect_id` and no duplicate intent is recorded — B1 accepts this derivation (it is the one place an allocated-class id is replaced by a derived one, and the reason is exactly-once accounting). `effect_id` is the join key across every `action.effect.*` phase event; B2 owns idempotency-key derivation from it.
- `ArtifactId` = `ContentAddress`; a *named, versioned* artifact (plan.md v3) is `ArtifactName → [ContentAddress]` in L4's registry; the ledger stores addresses only.
- `ConfigurationId`, `HarnessDefinitionRef`, `ModelProfileRef`, `ComponentVariantRef`: content addresses over canonical IR (A3/L4); stored in the manifest so every event is attributable to the exact definition that produced it.
- `ContextItemId`: content address over `(item bytes, provenance)` (D1/L3), so identical text from different authorities is a different item.
- Cross-run references are `EventRef`s; no global sequence is claimed; cross-run order is partial (spawn/result/link edges) with optional HLC timestamps for consistent-snapshot queries.
- Uniqueness rule (CloudEvents-shaped): `(run_id, event_id)` is unique; `(producer.participant_ref, surface_id)` is an alias index only.

### 6.4 Acceptance-criteria sketch

- **AC-B1-1 Append-only.** No operation mutates or removes a durable event; `verify` detects any byte change; `redact` leaves the chain valid.
- **AC-B1-2 Crash consistency (with B2/B3).** Kill the runtime at each of the four tool-cycle points (during execution; after outcome before persistence; after persistence before visibility; after visibility) and at mid-batch append: on resume, `project(context_view)` equals the pre-crash view hash for every durable prefix, no committed effect is re-executed, and every open `effect_pending` scope is closed by an explicit recovery event.
- **AC-B1-3 Rebuildability.** Delete every materialized view and index; rebuild from log + blobs; each view's `view_hash` and the results rows are identical.
- **AC-B1-4 Replay determinism (where possible).** For a control-strategy variant declaring `deterministic_replay`, re-driving it against recorded `model_io` and recorded effect outcomes reproduces the same `control.decision` sequence and `view_hash` sequence; for other variants the test is *not applicable*, reported as `n/a` (never 0).
- **AC-B1-5 Stamping.** 100% of events carry `participant_class`, `observability_level`, `schema_version`, `producer`; a metric registry check can resolve `requires_observability` against them (T-LCD-15).
- **AC-B1-6 Compliance observability (T-LCD-13).** For every `measurement.artifact.delivered` there is a computable compliance metric from `activated/followed` events (with `detector` provenance) per Model Profile; the reference harness at Stage 3 emits all three classes.
- **AC-B1-7 Payload offload.** No durable event exceeds the size threshold; payloads above it are blobs with dedup verified (same bytes → same address).
- **AC-B1-8 Schema evolution.** Golden fixtures from every prior schema version load under the current loader; removing a field requires a recorded deprecation; the readiness report lists supported versions.
- **AC-B1-9 Fork immutability.** After `fork`, the source's head hash is unchanged; the fork's projected view up to the fork point equals the source's.
- **AC-B1-10 Ordering.** `seq` is dense and strictly increasing per run; `parent_event_id` graph is acyclic; every cross-run `EventRef` resolves; a subagent's `run.created` causally follows its `control.subagent.spawned`.
- **AC-B1-11 Single writer.** Two writers with valid-looking tokens cannot both append; the fenced writer receives `Fenced` and the event is absent.
- **AC-B1-12 Ephemeral discipline.** Streaming deltas and permission *requests* appear on `subscribe` but never in `read`; the persistence policy is a declared table, not code scattered across producers.
- **AC-B1-13 Interchange identifiability (phase-0 §5.5).** Imported rows carry `provenance = imported{format, source}` and `participant_class = hosted`; exported runs round-trip their `RunId`, `configuration_id`, lineage and `observability_level`.

### 6.5 Retention and redaction

Tiered by *experiment membership*, not by age alone: (hot) active runs — full log + blobs; (warm) runs bound to an experiment/bundle (I3/J5) — full log + blobs, immutable until the experiment is retired; (cold) unbound runs — log retained, blobs garbage-collectable by policy with the invariant *hashes survive, bytes may not* (a `Missing` blob is distinguishable from a tampered one). Referenced fork prefixes are pinned while any fork is retained. Redaction (secrets accidentally logged, personal data) is a tombstone event plus blob deletion; canonical hashes remain verifiable because the hash covers the redacted content's address, not the bytes. Compression at rest is permitted; it must not change canonical hashes.

### 6.6 Storage-property requirements for WS-L1 (no technology named)

1. Ordered, append-only record store with atomic multi-record append and an acknowledged durable flush.
2. Exclusive-writer primitive (lease/lock with stale-holder detection) usable across processes on one host at Stage 0–1.
3. Forward and reverse sequential scan; random access by `seq` and by `event_id` through a rebuildable index.
4. Content-addressed blob store with dedup, size limits and delete-by-address (for redaction/GC).
5. A canonical serialization of the event envelope + payload stable across versions and implementations (sorted keys, fixed number and string forms, no whitespace, UTF-8) so hashes agree across ecosystem boundaries (WS-L1 §6.5 "byte-identical events").
6. Schema-versioned decoding that accepts every historical version (additive evolution + deprecation handlers).
7. A streaming tail (subscribe) with inclusive cursors.
8. Hashing with domain separation (leaf/node prefixes as in RFC 6962) and optional signatures (H6).
9. Compression at rest that preserves canonical bytes on decode.
10. Reasonable throughput target for Stage 1: tens of events per second per run, event size ≤ 64 KiB, blob sizes up to environment-snapshot scale — no exotic storage requirement.

## 10. Confidence

**High** for the authoritative-log-with-derived-views boundary, the single-writer/durable-before-visible write path, non-destructive rollback/compaction/fork-as-events, and payload offload: five Tier-B codebases at pinned commits and two Tier-B production reports converge, and the one preprint (Logos) only corroborates. **High** for the ID model's *shape* (time-ordered allocated ids + content addresses + surface aliases): direct precedent in Codex/Pi/Shepherd and standards (RFC 9562, OTel, CloudEvents). **Medium** for the event taxonomy's completeness across the security/verification/measurement planes: those classes have partial or no precedent and depend on H1/G2/I2 designs landing in Phase 2. **Medium** for the hash chain at Stage 1: standards precedent is strong (RFC 6962/8785) but no audited harness does it, so the cost is estimated, not measured. **Low-to-medium** on anything quantitative from 2026 preprints; none is load-bearing.
