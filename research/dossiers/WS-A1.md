## 1. Scope & boundary

This workstream decides **how MetaHarness is positioned relative to what already exists**: which of the doc 3 §2 capability planes are already delivered by orchestration libraries, agent SDKs, harness hosts, cloud harness products, and evaluation harnesses; which of the program's novelty claims (doc 3 §3.4) survive contact with that landscape; and what CF-009 (mature coding harnesses avoid general frameworks for their core loop) implies for positioning. It **confirms or refutes** the `novel` flag ADR-0001 places on the two-participant-class comparison plane.

It explicitly leaves to neighbours: the ontology itself (WS-A2), the IR's typed vocabulary (WS-A3), the compiler (WS-A4), the depth of the thin observational ABI (WS-J6, OQ-004), the naming/differentiation thesis as a marketing artifact (WS-L7, which consumes this dossier), and every language/runtime question (WS-L1). Nothing here recommends a programming language, runtime, or package ecosystem; contracts are stated as operations/inputs/outputs/invariants.

## 4. Findings

### 4a. Mechanism evidence (a failure mode exists / an architecture is implementable)

**F1 — A black-box "comparison plane" over heterogeneous harnesses already exists in at least four independent implementations.** Harbor (S-132/S-133) wraps 47 external agents as `BaseAgent` subclasses run inside a task container, shares environment, verifier, metrics and cost fields across them, and emits a common trajectory format (ATIF). HAL (S-134/S-135) does the same with a `module.run(input) -> {task_id: {history, cost}}` contract across 30 scaffolds and 9 benchmarks, cost-controlled by default. Inspect AI (S-136/S-137) hosts black-box agents by intercepting their model-API calls (in-process or through a sandbox proxy) and logs them into the same transcript format as native Inspect agents. Omnigent (S-118) hosts 12+ coding harnesses behind one `Executor` interface and runs a conformance bench across them. Harness-Bench (S-062) itself runs "representative harness configurations across multiple model backends" while "keeping each harness's native execution behavior". **Mechanism status: mature (multiple independent implementations, one Tier-A venue).** This is the principal evidence bearing on ADR-0001's `novel` flag (§4c, §6).

**F2 — Three distinct hosting mechanisms exist, each with a different observability envelope.** (i) *Session-ABI hosting*: ACP (S-035) and Omnigent's `Executor` (`omnigent/inner/executor.py:611–690`) expose start/resume/cancel/prompt/steer, stream typed events (`TextChunk, ReasoningChunk, ToolCallRequest, ToolCallComplete, CompactionStarted/Complete, SubAgent*`), and surface permission requests; Codex's app-server (`codex-rs/app-server-protocol/src/protocol/v2/thread.rs, turn.rs`) adds `thread/fork`, `thread/rollback`, `turn/steer`, `thread_usage`. (ii) *Model-boundary interception*: Inspect's `agent_bridge()`/`sandbox_agent_bridge()` and ClawGym II's serving proxy (S-140) see every model call and tool schema but nothing about the harness's internal state machine. (iii) *Container-installed CLI*: Harbor installs the vendor CLI in the task container, drives it by prompt, and reconstructs a trajectory from the vendor's native log (`agents/installed/claude_code.py:573 _convert_event_to_step`). Each mechanism yields a different *observable*: (i) events + permission requests; (ii) complete model I/O; (iii) native transcript + end state. No existing system combines all three behind one participant contract. **Implication for WS-J6:** the thin observational ABI must be specified as a *minimum observable set* that each mechanism can satisfy, plus optional richer capabilities declared per participant (as Omnigent `HarnessCapabilities` and Harbor `AgentCapabilities` already do).

**F3 — Declared-vs-observed capability conformance is a proven mechanism.** Omnigent's bench reconciles a harness's declared `HarnessCapabilities` (`omnigent/harness_capabilities.py`) against live probes and emits a `DRIFT` verdict (`tests/harness_bench/verdict.py:112 reconcile`); its design doc states the bench is "not a performance/latency benchmark" — it is a *conformance* instrument. Harbor's `AgentCapabilities` (`src/harbor/agents/capabilities.py`) is declared-only (no drift check). This is directly reusable for the black-box participant class: a participant's *declaration* becomes an experimental factor that the comparison engine can verify.

**F4 — A framework-neutral declarative agent IR with multi-runtime compilation exists (Open Agent Spec), but its coverage stops at the control/tool/flow planes.** `pyagentspec` (S-138/S-139) defines versioned `Component`s (`versioning.py`: 25.3.0 → 26.3.0), `Agent{llm_config, system_prompt, tools, toolboxes, human_in_the_loop, transforms}`, a node catalog (`flows/nodes/`: agent, llm, tool, branching, map, parallel, catch-exception…), adapters to LangGraph, AutoGen, CrewAI, OpenAI Agents, WayFlow and Microsoft Agent Framework, and an `evaluation/` package. A grep for permission/provenance/event-log/checkpoint concepts finds them only inside runtime adapters, never as spec entities. AutoGen's `ComponentModel` (`_component_config.py`: provider, component_type, version, component_version, config) is a second, narrower precedent for versioned declarative component assembly. DSPy's `Module.dump_state/load_state` (`dspy/primitives/base_module.py:156–171`) is a third: the *learned* parameters of an LM program are a serializable artifact separate from code. **Implication:** the doc 3 §3.4 novelty claim (i) "comparison-first ontology + IR" must be narrowed (see CF-011): what has no precedent is an IR whose typed entities include `Permission, Effect, Validator, Budget, Memory-with-validity, HarnessRule` with provenance on every entity and *model-conditioned* compilation — not the idea of a declarative cross-runtime agent representation per se.

**F5 — CF-009 is corroborated by the audit, and it cuts in a specific direction.** Every mature coding harness read here hand-rolls its loop: OpenHands' `AgentBase` is a frozen config object driving its own `step`; Pi's `Harness` (`packages/agent/src/harness/runtime/harness.ts`) manages lanes and operations itself; Codex, Claude Code, Cursor, goose and opencode are hosted by Omnigent/Harbor precisely *because* they will not be re-expressed in someone else's framework. S-074 reports the same for all 11 systems. At the same time these systems converge on **external** contracts: ACP (6 of 11 per S-074), MCP, skills, hooks with typed inputs (`claude_agent_sdk/types.py: PreToolUseHookInput … PermissionRequestHookInput`), and declarative config (Omnigent agent YAML; OpenHands `AgentProfile`; AgentCore/Agent Framework "define an agent in configuration"). **Implication:** a general orchestration framework aimed at owning others' core loops has no adoption path; a *reference runtime* plus a *representation and comparison instrument* that speaks the converged external contracts does.

**F6 — No existing system is simultaneously event-sourced, capability-kernelled, provenance-labeled, and factorial-experimental.** Event sourcing: OpenHands `EventLog` (append-only, file-locked) with a conversation *tree* (`event/base.py: parent_id`, `state.py: leaf_event_id` HEAD) is the closest; LangGraph persists *snapshots* (`Checkpoint{channel_values, channel_versions, versions_seen}`) with time travel by checkpoint id, not an event log; Pi persists `Entry{seq,timestamp}` records with `CheckpointData`. Capability kernel: no audited system confers authority out-of-band from model text — OpenHands `SecurityAnalyzerBase.security_risk(ActionEvent) -> SecurityRisk` is risk classification (with LLM-based analyzers) feeding a confirmation policy; Omnigent policies gate tool calls (fail-closed for `PHASE_TOOL_CALL`/`PHASE_REQUEST`) but operate on names/content; Claude SDK has permission rules and modes; Pi and Prime Agent explicitly disclaim any permission system. Provenance labels on context items: OpenHands events carry `source: SourceType`; ATIF steps carry `source ∈ {system,user,agent}`; nothing carries authority class/validity on retrieved memory. Factorial experiments: Harbor `JobConfig{agents[], tasks[], n_attempts}` and HAL are agent × task × attempt; Pi's `evalHarnessTable(baseline, candidates, repetitions)` is configuration × repetition within one runtime; none expresses model × harness-component × environment × budget × seed with component-level attribution.

**F7 — Model-conditioned compilation exists only as scattered heuristics.** OpenHands `get_model_prompt_spec` maps model-name patterns to a `family/variant` used by prompt presets, and ships `examples/04_llm_specific_tools/` (GPT-5 apply-patch preset, Gemini file tools); Omnigent `models/model_override.py` validates harness/model family compatibility and maps reasoning-effort vocabularies per harness (`EffortFamily`); DSPy `Adapter` subclasses (chat/json/xml/two-step) format the same signature differently per LM capability; Pi's `pi-ai` normalizes providers. No system treats the profile as an independently testable, expirable artifact (doc 3 §2.3 C1 ⊕ NEW) — this remains whitespace.

**F8 — Evolution pipelines with governance gates have no integrated precedent; optimizers exist.** DSPy `Teleprompter.compile` (with GEPA, MIPROv2, SIMBA…), Meta-Harness (S-080, harness-as-source-code with a filesystem of prior candidates), PRISM (S-093, edits confined to prompts + tool-boundary middleware, reliability metric `RelLift95`), Prime Agent's `/refine` (supplemental state only; immutable base prompt; snapshot rollback). None implements propose → counterexample set → matched-budget eval → held-out regression → cross-model compat → security-invariant check → canary → retirement test as one governed pipeline. Consistent with ADR-0002 (b).

### 4b. Performance evidence (benchmark lifts) — each tagged `provisional` if 2026 single-team/preprint

- Harness effects are large and model-conditioned: Harness-Bench (S-062, `provisional`, 5,194 trajectories) recommends reporting capability at the model–harness configuration level; Same-Model-Different-Harness (S-072, `provisional`) reports SWE-bench Verified fail-to-pass rising 28%→49% under a 20k-token window for a context-management treatment, with minimal difference at wide windows. HAL (S-135, Tier A) reports higher reasoning effort *reducing* accuracy in the majority of runs across 21,730 rollouts. **Use:** mechanism-level justification for the comparison instrument; effect sizes not to be reused as design constants.
- Harness-of-Harness (S-079, `provisional`): +52% relative over standalone harnesses after three iterations — budget-unmatched (iterations add compute); discounted per §3.1.
- Meta-Harness (S-080, `provisional`): 4.7-pt average across five held-out models on math; TerminalBench-2 harnesses surpass hand-engineered baselines — unmatched against test-time search per S-083.
- Rethinking Harness Evolution (S-083, `provisional (counter)`): under matched feedback/inference budgets automatic evolution does not consistently beat simple test-time scaling and generalizes weakly (Terminal-Bench 2.1, GPT-5.4 and Claude Opus 4.6).
- Harbor-Index (S-133, `provisional`): strongest black-box pair (GPT-5.5 + Codex) 28.0% pass — illustrates that black-box comparison at product granularity is routine and that headroom is large.
- ClawGym II (S-140, `provisional`): +9.98/+14.81 Pass@1 via OpenClaw/Claude Code with a model-boundary proxy — mechanism evidence that model-boundary interception yields trajectories complete enough for RL; performance not load-bearing.

## 5. Disconfirming evidence & negative results

**Against "the two-participant-class comparison plane is novel" (ADR-0001 (b)).** Harbor already runs *native* agents (`terminus_2`, `dspy_rlm`, `oracle`) and *installed/external* black-box agents on one job/trial/verifier/cost plane; HAL runs scaffolds it does not control on a cost-controlled plane; Inspect hosts bridged agents next to native solvers in one log format; Harness-Bench keeps each harness's native execution while fixing task/sandbox/budget/evaluator. The *plane with two kinds of participant* therefore has precedent (four independent implementations, one Tier-A). The recommendation in §6 amends ADR-0001's evidence field rather than its decision: the decision (native-primary, hosting-as-participant, thin observational ABI) stands; the `novel` flag must be narrowed to what none of these systems has — a white-box class that is *component-decomposable through a typed IR* so that component-level attribution, ablation and evolution apply to it, with every metric declaring its class applicability.

**Against "comparison-first ontology + IR" (doc 3 §3.4 (i)).** Open Agent Spec is a versioned, framework-neutral declarative IR with six runtime adapters and a standardized evaluation harness whose paper explicitly targets "reproducible, cross-platform comparisons of agent quality, safety, robustness, and efficiency". If MetaHarness's IR were only "agents, tools, flows, LLM config, compile to runtimes", it would be a rename. The claim survives only in its narrowed form (F4): typed `Permission/Effect/Validator/Budget/Memory-validity/HarnessRule` entities with provenance edges, a behavioral (not framework) `ToolCapability`, and model-conditioned compilation — none of which Agent Spec, AutoGen `ComponentModel`, or DSPy state carries.

**Against "instrument + reference runtime" positioning.** (a) A reference runtime that nobody else adopts risks the same fate CF-009 predicts for frameworks: the audited systems will not migrate their loops into it. The mitigation is that the runtime's purpose is *internal validity of the instrument* (white-box participants that can be ablated), not adoption by Codex/Claude Code; adoption pressure is placed on the IR's external edges (ACP/MCP/ATIF/Agent-Spec export), not on the loop. (b) Harbor/HAL show that "compare everyone's" is *already* served; MetaHarness must therefore either interoperate with them (import ATIF, act as a Harbor/Inspect agent) or explain why a fifth black-box plane is needed. The recommendation adopts interoperation (§6, ADR-3) and confines the new value to component-level science on the white-box side plus cross-class joint analysis. (c) Omnigent already uses the name "meta-harness" for a hosting product; naming collision is real (R-2.12.5; flagged to WS-L7).

**Against the value of white-box component decomposition.** S-083 shows that under matched budgets, harness *evolution* does not reliably beat test-time search; S-092 (doc 2) suggests gains localize to a few components; S-072 shows effects vanish at wide context windows. If most harness benefit is model- and budget-conditional and localized, the marginal scientific value of a fully decomposed white-box runtime could be smaller than its cost. This does not overturn the positioning (the instrument is *how* one would find out) but it is the strongest reason to keep the C0 core minimal and evaluation-first (Stage 3 before Stage 4–6), as doc 2 §11 already insists.

**Against reading hosted-system source as authority.** All three vendor harness products (S-058/S-059/S-056) were read via vendor pages; their internal boundaries are marketing-level and were used only for mechanism (config-declared harness; runtime/harness split), never for performance.

## 6. Recommendation for the spec

### 6.1 Positioning statement for Spec §1 (vision / thesis / non-goals)

**MetaHarness is a research instrument and reference runtime for harness engineering, not a general-purpose orchestration framework.** Its load-bearing capability is *comparability under a portable behavioral representation*: harnesses expressed in the IR (white-box) can be swapped, ablated, attributed and evolved component-by-component; harnesses that cannot be so expressed (black-box) join the same experiments through a thin observational ABI. The reference runtime exists to make white-box participants real; it is opinionated, minimal and event-sourced, and it does **not** aim to host other products' core loops.

**Non-goals (explicit, ADR-linked):** (N1) not a general agent-building framework competing with LangGraph/AutoGen/Agent Framework for application developers; (N2) not a universal Harness ABI that pretends black-box participants are decomposable (ADR-0001); (N3) not a fifth black-box leaderboard — black-box hosting exists to make *joint* white-box/black-box science possible and to import/export existing evaluation-plane artifacts, not to replace Harbor/HAL/Inspect; (N4) not a managed hosting product (sessions-follow-you, collaboration, multi-device) — that is Omnigent's/cloud vendors' plane; (N5) not a benchmark author — benchmarks/environments are integrated (WS-I4), not invented.

### 6.2 What is genuinely novel (defensible list)

1. **A behavioral harness IR whose entity set spans all seven planes** — `Permission`, `Effect`, `Validator`, `Budget`, `Memory` with validity/authority, `HarnessRule` with assumption-debt fields — with provenance edges on every entity, versioned and diffable. Precedent covers only agent/tool/flow/LLM-config entities (Agent Spec, AutoGen `ComponentModel`, DSPy state). *Novel as a set; each entity individually has partial precedent.*
2. **Model-conditioned compilation as a first-class, testable, expirable artifact** (profile compiler + tool-interface compiler). Precedent is heuristics scattered in OpenHands/Omnigent/DSPy adapters; no system versions, tests, or retires profiles.
3. **Component-level comparison plane for white-box participants, joined to a configuration-level plane for black-box participants, with per-metric class applicability.** The two-class *plane* has precedent (Harbor/HAL/Inspect/Harness-Bench); the *component-level axis with causal attribution over an event-sourced trace* on one side of the same plane does not.
4. **Declared-capability ⇄ observed-conformance as an experimental factor** — reusing Omnigent's DRIFT mechanism but feeding it into the analysis engine (a participant's declaration is data, its conformance is measured).
5. **The governed evolution pipeline with retirement tests and security-invariant gates outside the editable surface** (per ADR-0002; F8).
6. **Reference-monitor capability kernel inside the harness runtime** — conferring authority out-of-band from model text (CaMeL/Fides lineage, S-099/S-101); absent in every audited runtime (F6).
7. **Assumption-debt manager** — no precedent found in any audited system.

### 6.3 What is merely renamed (say so in the spec)

- "Harness assembly / declarative definition" ≈ Omnigent agent YAML/agent image, OpenHands `AgentProfile`, AutoGen `ComponentModel`, AgentCore/Agent Framework config, Agent Spec. Novel only insofar as the assembly targets IR component *variants* with typed parameters.
- "External-harness hosting / thin observational ABI" ≈ ACP + Omnigent `Executor` + Codex app-server + Harbor installed agents + Inspect bridge. Not novel; the spec should *cite and conform*.
- "Event store / run ledger" ≈ OpenHands `EventLog`/conversation tree; Pi entries; LangGraph checkpoints (snapshot flavour). Novel only in what is typed on the events (effects, provenance, authority).
- "Experiment & sweep engine" ≈ Harbor `JobConfig`, HAL runner, Pi `evalHarnessTable`, agbench. Novel only in the factor set (component variants, budgets, seeds) and cross-class joins.
- "Results store / leaderboard" ≈ Harbor Hub, HAL leaderboard, OpenHands eval CDN.
- "Reproducible harness bundle" ≈ Harbor trial dir + ATIF + job config; Omnigent agent image tarball. Novel only in bundling model profile + permissions + policies + provenance.
- "Compaction strategy family" ≈ OpenHands condensers (`no_op`, `llm_summarizing`, `pipeline`), Inspect `CompactionStrategy`, Pi compaction/branch summarization.
- "Critic / verification fabric" ≈ OpenHands `CriticBase` + iterative refinement; Harbor verifier; Inspect scorers.
- "Control strategies" ≈ ReAct (DSPy `ReAct`, LangGraph prebuilt), FSM/workflow (LangGraph Pregel, Agent Spec flows), Prime Agent RLM REPL.
- "Sub-agent orchestrator" ≈ Omnigent sub-agents, Claude SDK `AgentDefinition`, Prime `rlm(...)`, AutoGen teams.

### 6.4 Interface-contract sketch — Participant (language-agnostic)

Feeds WS-A2 (ontology) and WS-J6 (ABI depth). Operations, inputs/outputs, invariants, failure modes:

- `describe() -> ParticipantDescriptor{class ∈ {ir-native, hosted-external}, hosting_mechanism ∈ {session-abi, model-boundary-intercept, container-installed} | none, declared_capabilities: CapabilityDeclaration, version_identity: ContentAddress, model_binding: ModelRef|self-selected}` — invariant: descriptor is immutable for the life of a run and stored in the run ledger.
- `start(task: TaskRef, env: EnvironmentHandle, budget: Budget, context: ContextSupply, tools: ToolSupply, policy: PermissionPolicy) -> RunId` — failure: `UnsupportedCapability` if a required supply is not declared; `BudgetRejected`.
- `resume(run: RunId, input: Input)`, `steer(run, input)` (optional capability), `cancel(run) -> Cancelled|Timeout`.
- `events(run) -> Stream<ObservedEvent>` — minimum observable set every mechanism must produce: `turn.started/ended`, `model.call{model_ref, usage}` (interception and session-ABI) **or** `model.usage.summary` (container-installed), `tool.call.requested/completed{name, effect-class if known}`, `permission.requested/decided`, `compaction.occurred`, `subagent.started/ended`, `terminal{status}`; richer events are declared, not assumed. Invariant: events are appended to the same run ledger schema as IR-native runs (WS-B1) with `participant_class` and `observability_level` stamped on each.
- `account(run) -> ResourceAccount{tokens in/out/cache, model calls, wall-clock, env-minutes, approvals}` — invariant: every metric the analysis engine computes declares which `observability_level` it requires; metrics that need model I/O are `n/a` (not zero) for participants that cannot supply it.
- `export(run, format ∈ {native-ledger, ATIF-like interchange}) -> Artifact` / `import(artifact) -> Run` — obligation from ADR-3 (interoperate with existing planes).
- **Conformance**: `probe(participant, dimension) -> SUPPORTED|UNSUPPORTED|PARTIAL|NA|UNKNOWN|SKIPPED|DRIFT` reconciling `declared_capabilities` with observed behaviour (Omnigent precedent). DRIFT is recorded as a fact about the participant version and blocks that version from being labelled as declared in comparisons.

### 6.5 Data-model sketch

- `ParticipantDescriptor` (above) — one per participant version; content-addressed.
- `ComparisonGranularity ∈ {component, configuration, product}` on every experiment factor; IR-native participants admit all three, hosted-external only `configuration` (what the ABI lets us vary: model, context supply, tool supply, permission policy, budget) and `product`.
- `MetricDeclaration{name, requires_observability ⊆ {events, model_io, end_state, ledger}, applies_to_classes}` — enforces ADR-0001's consequence for WS-J4.
- `CapabilityDeclaration` — a typed record modelled on Omnigent `HarnessCapabilities` ∪ Harbor `AgentCapabilities`: `integration/hosting mechanism, streaming, interrupt, steer, live_queue, resume{none|warm|cold}, fork, compaction, images, subagents, permission_surface{none|hook|jsonrpc|mirror|sse}, instruction_delivery, model_family, effort_vocabulary, trajectory_export{native|interchange}, native_config`.
- `ConformanceRecord{participant_version, dimension, declared, observed, verdict, probe_run_id}`.

### 6.6 Acceptance-criteria sketch (for Spec §1 and the hosting subsection of §6)

- AC-1: The spec's non-goals N1–N5 appear verbatim in §1 with ADR links; every §2 item marked ↑ EXT or ⊕ NEW carries a one-line "precedent / renamed / novel" annotation sourced from §4c–§6.3 of this dossier.
- AC-2: The ontology (WS-A2) defines `participant class`, `hosting mechanism`, `comparison granularity`, `observability level`, and `declared vs observed capability` (terms proposed in §9).
- AC-3: Every analysis-engine metric (WS-J4) carries a `MetricDeclaration`; an experiment mixing classes reports component-level results only for IR-native rows and renders `n/a` (never 0) elsewhere.
- AC-4: A hosted-external participant can be attached through at least two of the three hosting mechanisms without changing the analysis engine (proves the ABI is mechanism-neutral).
- AC-5: A run of any class can be exported to an interchange trajectory (ATIF-compatible or documented mapping) and a Harbor/HAL/Inspect-produced trajectory can be imported as a `product`-granularity row (ADR-3).
- AC-6: A conformance probe suite exists for the black-box class and DRIFT verdicts are visible in comparisons.

### 6.7 Build-stage suggestion

- Positioning/non-goals: program artifact, Phase 0 → Spec §1 (no build stage).
- Participant descriptor + metric declarations: **C0, Stage 1** (they are needed for the eval backbone at Stage 3 and are cheap to carry from the start).
- Interchange export/import and the conformance probe suite: **C2, Stage 3–4** (with WS-J6 hosting).
- Hosting mechanisms: session-ABI (ACP) first (C2, Stage 4); model-boundary interception second (C2); container-installed third (C2/C3) — ordering by observability richness and by how many external harnesses each reaches.
