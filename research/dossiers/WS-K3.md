## 1. Scope & boundary

This workstream decides what HarnessHarness looks like **from the outside, to a caller that speaks only MCP**: which capabilities are exposed as tools and resources, under what identity and authority an external caller acts, how its consumption is accounted, and how the served documents are produced by the compiler rather than hand-written. The MCP *edge contract* — statelessness, the canonical catalogue per bundle, dual-era negotiation, hints as claims, `input_required` as a paused effect when HarnessHarness is the *client* — is ratified (ADR-0096/0097/0099) and is consumed here verbatim. This dossier adds the three things ADR-0097 explicitly left to WS-K3: (i) the **Lab operations as handle-carrying tools** ("K3 exposes Lab operations as handle-carrying tools"), (ii) the **authorization of external callers** (H1 authority handles; H5 trust posture applied in the reverse direction — the peer is now the *client*), and (iii) **cost accounting for external use** (L2). It also answers OQ-241 (which edge exposes a run) and the K3 half of OQ-247 (view handles).

It **does not decide** (neighbours named): the MCP client and transports (WS-E4, ratified); the tool-surface lowering itself and the minimum carried set (ADR-0021); the reference monitor's decision function and handle table (ADR-0051/0052/0053 — applied, not extended); the Hosting ABI verbs and the `HostedEvent` set (WS-J6 — this dossier supplies only the *supply surface* a hosted participant receives, which J6 §6.1 already names as "the Lab's sealed MCP surface"); the assembly, experiment, results and comparison operations that the Lab tools wrap (WS-J1/J3/J5/J4 — their operation records are consumed by identity; nothing is re-decided); the SDK/embedding boundary and the ACP interactive run edge (WS-K4 — its dossier was **not available at writing**; assumptions are flagged in §8); OAuth token custody and issuer keying (WS-H3); the `_meta` prefix and URI scheme (WS-L6, OQ-068); the approval UX (WS-H7).

3. (verbatim) Cost accounting for external use (L2).
4. (verbatim) Mapping to the compiler's protocol target (A4/E4).

6. (added) What is an external caller *in the ontology* — an AgentProcess, a principal, or something new — and which authority class does it act at?

## 4. Findings

### 4a. Mechanism evidence (a failure mode exists / an architecture is implementable)

**F1 — Every audited product that exposes its own capabilities over MCP does so through a hand-written tool router, and none derives the served catalogue from the same artefact its model-facing surfaces come from.** goose's built-in servers are separate crates with their own routers (S-112 `goose-mcp/src/*`); the Claude SDK's in-process server takes decorated functions (S-109 `__init__.py` L491); Inspect's bridge wraps `Tool` objects per spec (S-136 `bridge.py`); Codex's app server is a bespoke JSON-RPC protocol with 150+ methods, not MCP at all (S-107 `common.rs`). *Failure mode:* two definitions of "what this tool is" — one for the model, one for the wire — with the name as the only identity (T-LCD-10 signature; WS-E4 negative result iv) and no loss report between them (T-LCD-11). *Implementable alternative:* HarnessHarness already compiles one tool-document kind (`lower_target(bundle, mcp)`, ADR-0021/0097) for every bundle; the Lab's operations can be declared as `ToolCapability` entities in a sealed Harness Definition — an **exposure definition** — and served by the very same `serve(bundle)` path. Nothing new is compiled; the Lab catalogue *is* a bundle. (§6.1, ADR-0173.)

**F2 — MCP's own guidance makes the handle model of ADR-0051 the *only* admissible cross-call state model for a server.** The 2026-07-28 revision has no session; "Stateful Tools" (S-153 `tools.mdx` L683–737) says cross-call state is an explicit handle returned by a creation tool, that "for authenticated servers, a handle is a name, not a capability", that "the server should validate the caller's authorization against the handle on every call", that handles should be opaque and bounded in lifetime, and that an expired handle should yield a tool execution error. The tasks extension repeats it: task ids may serve as bearer tokens only when unguessable, and "servers MUST perform authentication and authorization checks on each task-related request" (S-554 L902–903). *Implication:* run/experiment/session handles returned by Lab tools are **surface aliases of allocated ids** (ADR-0027 `surface_ids`), the *authority* to act on them is a kernel-table `AuthorityHandle` held by the caller's AgentProcess (never in the result — H-1), and every call resolves `(caller, capability, canonical params incl. the handle) → covering handles` (H-5). A stdio server with no authentication is the "unauthenticated server" case: its handles must be high-entropy and short-lived, and the caller binding comes from the launch context (§6.2).

**F3 — Caller context in `_meta` is precedented only under four simultaneous restrictions, and the spec forbids trusting anything a peer self-reports.** Codex injects an entitlement context into a tool call's `_meta` only when the server is the host-owned stdio server, the tool was selected by an installed plugin, the call has zero arguments, and the tool declares `read_only_hint` (S-107 `trusted_access.rs` L26–62); it projects only known extension namespaces downstream and strips `userVerification` for non-host-owned servers (`client_capabilities.rs` L11–31). The spec says `serverInfo`/`clientInfo` are display-only and annotations are untrusted (S-153 `discover.mdx` note; `tools.mdx` L305). *Implication for K3 as a server:* nothing a caller puts in `_meta` (client info, capabilities, foreign keys, even a HarnessHarness-prefixed key) decides authority; caller identity comes from the transport binding (token via H3, or the stdio launch record) and the `ProtocolBinding.capabilities_declared` of the caller is a claim reconciled by probing (ADR-0099 N3). The one thing `_meta` *does* legitimately carry inbound is propagation context (`traceparent`/`tracestate`, ADR-0042) and the client's declared capabilities that gate result *shapes* (`elicitation.form` → MRTR allowed; tasks extension → task results), per S-554 L61.

**F4 — Long-running work over MCP has exactly three admissible shapes, and they map onto three tiers.** (i) Create-then-poll with ordinary handles (spec "Stateful Tools"; no capability needed); (ii) resources with `subscriptions/listen` and `notifications/resources/updated` (S-153 `resources.mdx` L244–268; Codex's event catalogue over resources, S-107 `resource_client.rs` L46–60, is a production instance); (iii) the tasks extension with durable `taskId`, `input_required` + `tasks/update`, cooperative cancel and `notifications/tasks` (S-554). The tasks extension's invariants are the ledger's: "MUST NOT return `CreateTaskResult` until the task is durably created" (L300) ⇔ durable-before-visible (ADR-0026); `failed` only for JSON-RPC faults and `completed` for `isError` results (L837–892) ⇔ ADR-0097 decision 4's protocol-error/result split; cancel "MAY ultimately reach a terminal status other than `cancelled`" (L404) ⇔ ADR-0030's `unknown → probe` for open effects; `input_required` ⇔ `security.permission.pending` (ADR-0070). *Implication (OQ-241):* a run is exposed through K3 at C1 as a handle-carrying tool set (launch/read/cancel/respond), at C2 additionally as an MCP task and as a subscribable ledger resource; ACP (K4) remains the primary *interactive* edge because it carries turn-structured updates and typed permission options natively (ADR-0098). All three are lowerings of the run envelope with loss reports; none introduces a run concept the ledger lacks.

**F5 — Statelessness plus caching rules force "one server instance ↔ one catalogue" and forbid per-caller narrowing, but not per-caller *authorization*.** `tools/list` and `resources/list` MUST NOT vary per connection (S-153 `tools.mdx` L62–71, `resources.mdx` L74–83); `cacheScope: "public"` results may be shared across authorization contexts and servers "MUST NOT rely on `cacheScope` alone to prevent unauthorized access to primitives" (`caching.mdx` L173–179). *Implication:* the catalogue is public-by-construction (identical bytes for everyone — AC-E4-2), so **listing is never an authorization decision**; authorization happens at `tools/call` and `resources/read` through the reference monitor (a caller may *see* `launch_run` and be refused `NoCoveringGrant`). A server that must serve two catalogues (a harness bundle's supply surface and the Lab catalogue) runs two instances, or one instance whose *single* bundle is a composition sealed at assembly time — never a per-connection union (§6.1 D3). This closes the K3 half of OQ-247: no server-minted view handles; deferred loading is client-side (`select_surfaces`, CF-206), and the Lab catalogue offers the ADR-0094 discovery capability as an ordinary tool for callers whose context cannot hold the full list.

**F6 — Machine callers exist and are never principals.** The client-credentials extension exists precisely for callers with "no user present" (S-555); Inspect lets a *model provider* be the MCP client (S-136 `server.py` `execution = "remote"`); ADR-0033 mints `principal` "only for the run's human principal" and `delegate` "for every AgentProcess output". *Implication:* an external agent calling K3 is an AgentProcess at the boundary — by default **`delegate`** even when it presents the principal's OAuth token, because the *content it authors* is model output (the token authenticates the account, not the authorship). Consequently, per ADR-0035 rule 1 and ADR-0070 decision 3, a default caller can launch, read, cancel and supply input, but **cannot approve** a pending `ask` of a run it launched — approvals go to the run's human principal through H7, or to a caller whose sealed `CallerBinding` declares `caller_kind = human_principal` (a human-operated client) or holds an `ApproverGrant`. Auto-approval by the external agent is the OpenHands failure mode (WS-E4 F5) in the reverse direction.

**F7 — Read surfaces are exfiltration gadget sets unless reads are labelled, accounted and redacted.** S-371 (peer-reviewed) shows agents assembling legitimate read tools into disclosure chains, attributing it to missing context-tool isolation and least privilege; the spec requires access controls on resources and output sanitisation (S-153 `resources.mdx` L428–434; `tools.mdx` L789–793). HarnessHarness already has the machinery: `readers` labels on every provenance record (ADR-0033), `SinkPolicy{content_classes, redaction, requires_consent}` and "every delivery is `measurement.export.delivered`" (ADR-0044), `PublicationPolicy` with L0/L1 defaults and L2 by readers (ADR-0141 decision 4), tombstones over redaction (ADR-0068). *Implication:* every K3 read tool is a **sink** under an `ExposurePolicy` (a `PublicationPolicy`-shaped MUST-data record sealed in the exposure definition); L3 diagnostic content is never served (ephemeral by definition); an item whose `readers` excludes the caller's `PrincipalRef` is withheld with a typed reason, and every served page appends `measurement.export.delivered` to the cited run (§6.4).

**F8 — Every Lab operation this surface wraps already exists as a language-neutral operation record with typed refusals.** J1 `assemble/plan/apply/validate_batch/explain`, J3 `register/open_experiment/next/claim/launch/settle/pause/resume/close` with the refusal table (`MissingMatchSpec`, `UnbudgetedArm`, `UnmatchedBudget`, …), J5 `get_row/query_rows/cells/distribution/leaderboard/verify_row/export_rows`, J4 `summarize/compare/interaction/frontier/…`, J2 `resolve/query/catalog/slot_choices/publish`, B1/B3 `open_run/read/subscribe/restore`, H7 `respond`. *Implication:* K3 introduces **no operation**; each Lab tool is a `ToolCapability` whose `semantic.purpose` names one of these operations by identity, whose `EffectClass` is derived from what the operation does, and whose surface schema is the operation's input record lowered to JSON Schema by the tool-interface compiler (ADR-0090) under the exposure definition's profile binding. Refusals lift as `isError` results with a typed `structuredContent.refusal` (ADR-0092 `ResultRenderSpec`), never as protocol errors (ADR-0097 decision 4).

### 4b. Performance evidence (benchmark lifts) — each tagged `provisional` if 2026 single-team/preprint

None is load-bearing. S-370's attack-success rates (36.5 % mean; 72.8 % max; `provisional`) and S-302's prevalence rates (5.5 % tool poisoning; `provisional`) inform the *direction* of the text-authority rule only; ADR-0097 decision 5 and ADR-0034 already fix the mechanism on Tier-A/B grounds. No source reports a performance effect of exposing a harness over MCP versus a bespoke RPC; the MCP changelog's prompt-cache rationale for deterministic catalogues (WS-E4 4b) applies unchanged to the Lab catalogue.

Precedent status: application-capabilities-as-MCP-server, host-tools-into-sandbox, run handles with approval requests, and event resources with subscriptions are **precedented**. The exposure definition (Lab operations as compiled `ToolCapability` entities served by the same `serve(bundle)` path), the caller model (`CallerBinding` → AgentProcess at `delegate` with kernel-held handles, human-principal callers distinguished by sealed binding), and the surface-session ledger with `charged_to` split are `no-precedent / novel` as an integrated contract.

## 5. Disconfirming evidence & negative results

**Against "the Lab catalogue is a compiled bundle" (ADR-0173).** Every product hand-writes its capability server; a compiled route adds the E1–E7 equivalence obligations (ADR-0022), a profile binding and a `SurfaceArgMap` to operations that have no model-conditioned surface. *Why this does not overturn:* the equivalence evidence for Lab tools is trivial and mechanical (E1–E3/E7 on record-shaped inputs; E4 `n/a` for pure reads), and it is exactly what guarantees that a renamed or re-described Lab tool is a profile edit (T-LCD-10) and that the wire catalogue's losses are declared (T-LCD-11). The alternative reintroduces the second tool-definition path that ADR-0096 decision 1 removed for foreign tools. The cost is one small exposure definition per release, versioned with the `InstrumentRecord` (ADR-0038).

**Against "external callers are `delegate` and cannot approve".** Human-operated MCP clients (IDEs, chat UIs) exist; the caller's OAuth token *is* the principal's; refusing approvals over MCP forces a second channel for every `ask`. *Why this does not overturn:* the rule is per **binding**, not per protocol: a sealed `CallerBinding{caller_kind: human_principal}` raises the caller to `principal` and makes MRTR elicitation an approval channel (ADR-0070 lowering, mirrored); the default is `delegate` because the audited population of MCP clients is agents, and because "the model may propose, only the runtime confers" (doc 2 §5.6; ADR-0053 decision 5) must survive the agent holding the human's token. The counter-examples — OpenHands auto-approve (S-110 `acp_agent.py` L1579–1596) and S-104's "automatic review approved 13/13" — are what the default prevents.

**Against "one server instance ↔ one catalogue".** A single multiplexing server (many bundles, namespaced tool names) is operationally simpler and is what goose's `owner__name` prefixing and gemini-cli's `mcp_<server>_<tool>` naming effectively do on the client side. *Why this does not overturn:* namespacing is exactly the name-as-identity mechanism WS-E4 rejected (F4c negative precedent), a union catalogue is no longer a pure function of one `bundle_id` (AC-E4-2 breaks), and cache scope becomes ambiguous when one caller may see bundle A's tools but not B's — which `cacheScope: private` cannot express safely per `caching.mdx` L173–179. A *sealed composition* (an exposure definition that references several bundles' surfaces as slots) keeps one `bundle_id` per server and is the sanctioned way to serve "Lab + this harness" together.

**Against exposing runs through MCP at all (OQ-241).** ACP already carries the run envelope with typed updates and permission options; a second run edge doubles the lowering tables and loss reports. *Why this does not overturn:* the callers K3 serves (agents, schedulers, CI, model providers as MCP clients — F6) speak MCP and not ACP; the run lowering reuses ADR-0098's projection tables (`StopReason`, outcome classes) with a different carrier; and the tasks extension gives exactly the durable-handle semantics a non-interactive caller needs while ACP stays primary for interactive hosts (ADR-0098). Both are lowerings of one envelope; the loss report of each is what makes the choice honest (T-LCD-11).

**Against per-page `measurement.export.delivered` events for pull reads.** A chatty agent paging a ledger would inflate the surface-session ledger. *Why this does not overturn:* the event is L0/L1 (ids and counts, not content), export accounting is the only thing that makes "who read what" auditable across the S-371 disclosure chain, and payload offload above the class threshold (ADR-0029) bounds the cost; batching granularity is OQ-396, not a reason to drop the rule.

**Negative results from the audit.** (i) No audited MCP *server* records who called it or what it served; Codex records origin for *resources it consumes* (`resource_origin.rs`), never for what it exposes. (ii) No audited server rate-limits tool invocations despite the spec's MUST; rate limits appear only as client-side timeouts. (iii) No audited product derives its exposed catalogue from its model-facing tool definitions; all four (goose, Claude SDK, Inspect, Codex) keep two definitions. (iv) The tasks extension is not implemented by any audited server or client at the pinned commits (Codex's `_task_compat` in S-109 is unrelated SDK task plumbing) — its adoption is C2 and carries an assumption-debt record.

## 6. Recommendation for the spec

### 6.1 Structural decisions (ADR-0173)

- **D1 — One serving path.** `serve(bundle_ref, transport, caller_binding_source) → ServerHandle` serves `target_artefacts[mcp]` of exactly one `CompiledBundle` (ADR-0019/0021/0097): `DiscoverResult` and `ListToolsResult` bytes are a pure function of `bundle_id`; `listChanged` fires only when the served bundle is replaced; resources (C2) are listed from the same bundle. There is no other way to put a tool on the wire.
- **D2 — Two kinds of bundle are served, by the same path.** (a) A **harness bundle's supply surface**: the compiled tool surfaces of a sealed Harness Definition, served to a hosted participant (WS-J6 `HostedRunSpec.supplies.tools`) or to any external agent that should act *inside* a HarnessHarness-owned environment; every `tools/call` is a native effect in the run that the caller binding names, executed through E5 under the reference monitor with the caller as proposer. (b) The **Lab catalogue**: the MCP artefact of an **exposure definition** — a sealed Harness Definition whose `ToolCapability` entities wrap Lab operations (§6.3) — versioned with the `InstrumentRecord`. Both are `lower_target(…, mcp)`; the exposure definition differs only in what its capabilities *do*.
- **D3 — Exposure definitions are data.** `ExposureDefinition = Assembly{dialect, profile_binding (null profile by default — OQ-393), slots{lab_operations: [ToolCapability ref], supply_surfaces?: [bundle_ref]}, entities{Permission[], Budget[], HarnessRule[]}, policy: ExposurePolicy, caller_bindings: [CallerBinding], ext}` sealed through `compose → resolve → validate_assembly → seal` (ADR-0025). Composition with harness bundles is a slot, never a per-connection union (F5). `ExposurePolicy` and `CallerBinding`s are MUST-data under `authority_cap`; the server transport, catalogue serving, caller resolution and monitor interposition are MUST-code (ADR-0024).
- **D4 — Dependency direction.** The K3 server imports the compiled documents and the protocol schema; no HIR entity, ledger class or Lab operation record references the server (T-LCD-06/-12; ADR-0096 decision 5). Lab operations are wrapped by *identity*, never re-implemented (F8).
- **D5 — Placement across the ADR-0050 layers (by ADR id and layer only).** The server transport, caller resolution, catalogue serving and the monitor interposition for supply surfaces live in the ADR-0050 **kernel layer** (they sit on the effect path; an MCP server-role SDK exists there per ADR-0050 §8(b), S-155); the Lab-operation handlers live where the operations live — assembly/registry/experiment/results in the ADR-0050 **lab layer** — and are reached over the D2 boundary as records (a `tools/call` crosses as the operation's input record and returns its output record). The late-bound surface layer is not involved (K3 is not a UI). CF-017 exposure honoured: no language, package or API is named.

### 6.2 Caller model and authorization (ADR-0174)

**Records.** `CallerBinding{binding_id, credential: {stdio_launch(launched_by: PrincipalRef, launch_event: EventRef) | oauth(issuer_ref, subject_kind ∈ {user, client}, audience = canonical server uri) | mtls(cert_ref)} (values never stored — H3 `SecretRef` only), principal_ref: PrincipalRef (OQ-139 form), caller_kind ∈ {agent (default), human_principal, provider_client, service}, authority_cap: AuthorityClass ≤ principal, permissions: [Permission ref] (⊆ exposure definition's), budget_node: Ref<BudgetNode>, readers_identity: PrincipalRef, rate_policy?: HarnessRule ref, expires_at?}` — sealed in the exposure definition or minted at `seal` from a `TrustRootPolicy` row for OAuth issuers (H3/H5). `CallerProcess = AgentProcess.hosted = OpaqueProcess{participant_ref: binding_id, hosting_mechanism: session_abi, declared_capabilities ← ProtocolBinding.capabilities_declared (tri-state), observability_levels: {events}, supplies: ∅, budget: binding.budget_node, permissions: binding.permissions}` — the caller is an **opaque AgentProcess at the boundary**, exactly ADR-0053 D-4's hosted child, created on first call and referenced by every proposal it makes.

**Rules.**
- **R-1 Identity from the binding, never from the request.** stdio: the caller is the process that launched the server, identified by the `stdio_launch` record the spawner (the CLI surface, the J6 adapter, or a kernel `spawn_process` effect) writes before the server accepts a request; OAuth SHOULD NOT be used on stdio (S-153 `authorization/index.mdx` L21). HTTP: per request, the bearer token is validated by the H3 broker (issuer keyed, audience = this server's canonical URI per RFC 8707, no passthrough, `insufficient_scope` step-up answered per spec) and mapped to a `CallerBinding`; the mapping is cached by token digest for ≤ token lifetime and re-derived per request otherwise (no session, SEP-2567). A token of a `subject_kind = client` issuer (client credentials, S-555) can bind only `caller_kind ∈ {service, provider_client}`.
- **R-2 Authority class.** `authority(caller) = min(binding.authority_cap, kind_ceiling)` with `kind_ceiling(agent | provider_client | service) = delegate`, `kind_ceiling(human_principal) = principal`; content the caller authors enters as `Text{authority ≤ external}` for `delegate` callers (ADR-0033: free text from a delegate is `external`) and as `principal`-authored content only for `human_principal` bindings. A caller at `delegate` never endorses: `respond_approval` from such a caller is `IllegitimateEndorsement` (ADR-0035 rule 1; ADR-0070 decision 3), even for a run it launched; approvals route to the run's principal through H7 or to a caller holding an `ApproverGrant` (ADR-0070 decision 6).
- **R-3 Claims never decide.** Inbound `_meta` is read for `io.modelcontextprotocol/protocolVersion` and `clientCapabilities` (result-shape gating: MRTR only with `elicitation.form`; task results only with the tasks extension — S-554 L61), and for `traceparent/tracestate/baggage` (ADR-0042 lifting into `causes[]`); every other key is preserved in `ext` and carries no authority (ADR-0099 N4/T2). `clientInfo` is display-only. The codex ceiling (F3) is the outer bound: no caller-supplied entitlement context exists in K3.
- **R-4 Handles are names; authority is the kernel's.** Lab tools return `surface handles` (`run_handle`, `experiment_handle`, `session_handle`, `plan_handle`, `page_cursor`) that are `surface_ids` aliases of allocated ids (ADR-0027) — opaque, high-entropy on unauthenticated stdio, bounded by the surface session's lifetime or the run's retention floor. A call carrying a handle is authorized by `authorize(proposal)` (ADR-0052) with the handle resolved to its allocated id and matched by `ResourcePattern` over canonical parameters (H-5): a caller holds a covering `AuthorityHandle{scope: run(run_id) | experiment(id) | …}` only for objects its own CallerProcess created (minted at creation with `origin_basis = delegation`, `parent_handle` = the binding's root handle, `delegable = false`) or that a sealed `Permission` grants (`scope: all_runs_of(principal_ref)`, `readers`-checked). An unknown or expired handle is a tool execution error (`isError`, `structuredContent.refusal = UnknownHandle | HandleExpired`), never a protocol error (spec L735). `HandleId`s of authority handles never appear in any result (H-1; `HandleLeak` static check on the exposure definition's `model_surface` and on every rendered result).
- **R-5 Effect classes of Lab tools** (derived per ADR-0031, declared in the exposure definition): `launch_run`, `open_experiment`, `serve_bundle` → `{spawn_process, spend}` (`compensable`, `external` when environments are remote); `submit_input`, `cancel_run`, `steer` → `{message_human? no: control input}` modelled as `spawn_process`-scoped control effects with `repeat_safety = idempotent` under the D3 `idempotency_key`; `respond_approval` → `permission_request` domain (never `allow` from Π — ADR-0052; only R-2 principals reach it); `read_ledger`, `query_rows`, `get_row`, `distribution`, `leaderboard`, `catalog`, `explain`, `get_trace`, `get_bundle` → `fs_read{scope: ledger | results | registry}` with `mutability = read_only, world = closed`; `assemble`, `plan`, `validate_batch`, `compile`, `summarize`, `compare`, `frontier`, `interaction` → `fs_read` on the registry plus `model_call`/`evaluator_calls` only where the operation itself spends (compile is pure; judged comparisons charge `instrument`); `apply`, `publish`, `register`, `record_conformance`, `define_leaderboard` → `memory_write{scope: project | organisation}` (persistence ceiling, ADR-0035; `who_may_publish`, WS-J2 §6.5) — refused for `delegate` callers unless a sealed `Permission` covers the namespace. Π rows for the exposure definition follow ADR-0052's defaults; `unattended` mode applies to `service` callers (every `ask → deny`, AT-H1-08).
- **R-6 Supply surfaces.** For a harness bundle served to a hosted participant, the caller binding is written by the J6 adapter at `open` (`launched_by = the hosted run's OpaqueProcess`), the proposer of every `tools/call` is that OpaqueProcess, its handles are the ones ADR-0053 D-4 says the kernel holds at the boundary, results are rendered by the bundle's `ResultRenderSpec` (ADR-0092) under the profile the supply surface was compiled with, and `callable ⇔ revealed` is trivially satisfied because the served catalogue is the whole compiled surface minus `hidden` (ADR-0093 decision 1; exposure modes are the *caller's* concern — OQ-247 closed for K3).
- **R-7 Rate limiting is budgeting.** The spec's "rate limit tool invocations" MUST (S-153 `tools.mdx` L792) is met by the binding's `BudgetNode` (`tool_calls`, `time.wall_ms`, `spend`, `approvals.requested` — ADR-0039/0040) with `reserve` before dispatch; exhaustion is `InsufficientBudget` rendered as an `isError` result with `structuredContent.refusal = budget_exhausted{dimension}` and `stop_reason` semantics per ADR-0040; a windowed request gauge, if needed, is OQ-399.

### 6.4 Cost accounting for external use and the read-side obligations (ADR-0174, decisions 6–8)

- **The surface session is a run.** On a caller's first call the server opens a ledger `kind: surface` (the J3 "the experiment is a run" shape): manifest `{binding_id, bundle_id, catalogue_hash, protocol_bindings[] (ADR-0099), caller_process: OpaqueProcess}`; each `tools/call` is a turn; the K3 server holds no state that is not a projection of this ledger (S-1 of WS-J3 restated). Runs and experiments launched from it record `causes[] ∋ EventRef(surface session, the launching effect)` on their `lifecycle.run.created` (ADR-0027 cross-run links; no new event class).
- **Charges.** Every accountable event in a surface-session turn posts `control.budget.consumed` against the binding's `BudgetNode` (ADR-0039 R-ACC-2 "nothing is unaccounted"): the server's own processing (catalogue serving, assembly/validation, query, comparison, judged analyses) is `charged_to = instrument`; a launched run's root `BudgetNode` is `allocate(parent = binding.budget_node, mode = slice, spec = launch_run.budget)` (ADR-0040) and its consumption is `charged_to = subject` on the child run — the binding's pool sees it by containment, never by double posting. `InsufficientBudget` at `allocate` refuses the launch before any environment is provisioned (J3 `launch` step 1 verbatim). Spend is derived per ADR-0039 decision 4 with `CostProvenance` from the child run's own measurement (`measured` for native children; `reported`/`reconstructed` for hosted ones).
- **What the caller sees.** `structuredContent.account = ResourceAccount{consumed per dimension (integers), remaining per hard dimension, spend{Money{micro_units, currency}, confidence}}` on every result of a spending tool and on `run_status`; the MCP target has no usage slot, so this is the declared `narrowed` lowering (`_meta["<hh-prefix>/account"]` mirrors it for clients that strip `structuredContent`). `NoPrice` renders as `spend: n/a{reason}`, never 0 (ADR-0039).
- **Reads are sinks.** `ExposurePolicy = PublicationPolicy{readers, content_classes ⊆ {accounting, structural, content} (default L0/L1; `content` by `readers` only; `diagnostic` never), redaction, requires_consent (hosted L2, OQ-116), page_limit, max_field_bytes}` (ADR-0141 decision 4 shape; ADR-0044 `SinkPolicy` fields). Every `read_ledger`/`query_rows`/`get_trace`/`export_rows` page: (a) filters items whose `readers ∌ binding.readers_identity` and reports them as `withheld[{ref, reason ∈ {readers, content_class, consent, redacted}}]` in `structuredContent` (never silently — T-LCD-15 pattern; and never an empty page for a non-existent run — spec `resources.mdx` L410); (b) serves redacted items as tombstones (ADR-0068); (c) appends `measurement.export.delivered{sink: mcp_surface(binding_id), items, content_classes, loss_report_ref}` to every cited run (ADR-0044) — granularity per page (OQ-396). The K3 server is therefore a `SinkPolicy`-declared exporter, a *subscriber* of the ledger, never a store (ADR-0042).
- **Descriptions and instructions.** `DiscoverResult.instructions` and every tool `description` are `Text` leaves of the exposure definition at `definition` authority (own export; ADR-0097 decision 5 applies to *consumers*, who lift them at ≤ `external`). Nothing in the served catalogue is model- or caller-authored (S-302/-08 mechanism).

### 6.5 Data-model sketch

`ExposureDefinition` (§6.1 D3) · `ExposurePolicy` (§6.4) · `CallerBinding` (§6.2) · `CallerProcess = OpaqueProcess` (ADR-0018 shape; no new entity) · surface handles = `surface_ids` aliases (ADR-0027) · `SurfaceSession` manifest (`kind: surface`; a `run_kind` discriminator value proposed to WS-B1 alongside J3's `experiment` — CF-367) · `RunStatusView{status, pending_approvals[], account, head_seq}` and `LedgerPage{events[], next_seq, withheld[], watermark}` as `project(run, view_kind, until_seq)` views (ADR-0026) · `ServerHandle{bundle_id, catalogue_hash, transport, protocol_binding, opened_at}` · `TaskProjection{taskId ↔ run_handle, status, inputRequests}` (C2; a view, not a store) · ledger classes reused with no new class: `lifecycle.run.*`, `lifecycle.turn.*`, `action.tool.*`, `action.effect.*`, `security.permission.*`, `control.budget.consumed`, `measurement.cost.attributed`, `measurement.export.delivered`, `security.extension.*` (for the served bundle's pins), `lifecycle.hosted.attached/detached` (for supply-surface callers, ADR-0053 D6).

### 6.6 Acceptance-criteria sketch (conformance suite; the goose `mcp-probe` shape as a Lab recipe)

- **AC-K3-1 Statelessness and identity (T-LCD-10/-11; extends AC-E4-2).** Two independent clients with different bindings receive byte-identical `server/discover` and `tools/list` for `hh-lab/1`, in canonical order, with `ttlMs`/`cacheScope`; every tool carries `_meta["<hh-prefix>/hir"].semantic_id`; renaming a tool in the exposure definition's profile changes the bytes and `listChanged` fires but no `semantic_id` changes; `lift(lower(exposure_def, mcp)) ∪ loss_report = exposure_def`.
- **AC-K3-2 Handles are names (H-1/H-5).** Caller A launches a run; caller B presents A's `run_handle` to `read_ledger`/`cancel_run` → `isError{refusal: NoCoveringGrant}` and `action.effect.refused` in B's surface session; no `HandleId` string appears in any result (static + runtime `HandleLeak` checks); an expired handle → `HandleExpired`, never a protocol error.
- **AC-K3-3 Delegates never endorse (R-2).** A default (`agent`) binding calling `respond_approval` on its own run's pending `ask` → `IllegitimateEndorsement`; the same call from a `human_principal` binding decides it; under the tasks extension the agent binding never observes `input_required` for an approval, the human binding does.
- **AC-K3-4 No unbudgeted launch (T-LCD-14).** `launch_run` without `budget` → `MissingBudget`; with a budget exceeding the binding's pool → `InsufficientBudget` before any `environment.*` event; the child run's root budget equals the request dimension-wise (J3 S-3 mirror).
- **AC-K3-5 Nothing unaccounted (ADR-0039).** For the Stage-4 conformance script, every surface-session turn has a charge per accountable event; `cost_totals` rebuilt from charges equals the live view; `charged_to` is `instrument` for server work and `subject` on launched runs; `structuredContent.account` equals the projection.
- **AC-K3-6 Claims never decide (R-3).** Property test: decisions for a scripted call sequence are byte-identical with and without arbitrary caller `_meta` (including a forged `<hh-prefix>/*` key, forged `clientInfo`, and a forged declared capability); unknown keys survive in `ext`.
- **AC-K3-7 Readers and redaction (§6.4).** An L2 item whose `readers` excludes the caller is `withheld{readers}`; a redacted item is served as a tombstone; a non-existent run → `UnknownHandle`, never an empty page; each served page appends `measurement.export.delivered` to the cited run with matching item counts.
- **AC-K3-8 Durable-before-visible.** Fault injection: crash between `lifecycle.run.created` durability and the `launch_run` response → the retry with the same `idempotency_key` returns the recorded `run_handle`; crash before durability → the retry launches once and no orphan run exists without a `causes[]` link.
- **AC-K3-9 Supply surface mediation (R-6; AC-J6-4 mirror).** A hosted participant's `tools/call` on a served harness bundle with a `deny` Π row never executes and the participant observes `isError{refusal}`; with `ask`, the call returns `pending` and the run shows `security.permission.pending`; `callable ⇔ revealed` holds for every listed tool.
- **AC-K3-10 Task lowering (C2).** The `TaskState`-style mapping of §6.3 is exhaustive over `StopReason` and outcome classes; `CreateTaskResult` is never returned to a client without the extension capability (`-32021`); `tasks/get` after `finished{refused}` is `completed` with the typed result; `failed` occurs only for an injected JSON-RPC fault.
- **AC-K3-11 Out-of-process and probe (T-LCD-12).** The conformance script (list, discover, call, handle misuse, budget exhaustion, elicitation policy, version pin, OAuth parameters) runs against the server as a separate process over stdio and over Streamable HTTP with a fixture authorization server; results are identical; a modern-era and a legacy-era client both pass through ADR-0097's dual-era rule.
- **AC-K3-12 Reflexive debt (T-LCD-05).** The tasks-extension carrier, the legacy-era projection and every `CallerBinding` kind carry assumption-debt records with removal tests; `link` refuses an exposure definition missing one.
