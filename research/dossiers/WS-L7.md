## 4. Findings

### 4a. Mechanism evidence

**F1. The LCD trap is a specific, recognisable failure mechanism, not a vague worry.** Across three unrelated domains the pattern is identical: a portability layer defines its surface as the *intersection* of what all targets support, so target-specific features that drive quality become unreachable through the portable surface, and users route around it with escape hatches until the portable layer is vestigial. AWT's peer model was "limited … to a lowest common denominator approach" because X11/Motif lacked widgets that Windows/Mac had, and WORA decayed into per-platform testing (S-154). LSP avoided the trap by *not* intersecting: each side announces capabilities, unknown properties are ignored, `experimental` and `$/` carve out non-standard space (S-152). ACP v2 copies this exactly ("all capabilities … OPTIONAL"; omitted = UNSUPPORTED; `_meta` on every type; `_`-prefixed methods) (S-035). MCP reserves prefixed `_meta` keys for the same purpose (S-153). The mechanism therefore has a known antidote — **capability declaration + verified probing + typed extension slots** — and a known failure signature — **feature intersection + untyped escape hatches**.

**F2. In agent harnesses the "target-specific features that drive quality" are model-conditioned surfaces, and mature systems already store them as data.** Codex keeps `apply_patch_tool_type`, `shell_type`, `truncation_policy`, reasoning levels and the context-window reminder prose *per model slug* in `models.json`, and the tool planner registers the apply-patch tool only when the model's profile says so (`spec_plan.rs` L1255). OpenHands renders an `<IMPORTANT>` block keyed by `model_family`/`model_variant` behind a guard (`static.py` L480–500). AutoGen's `ModelInfo` is a typed capability record (`_model_client.py` L164–183). Cursor states the underlying reason: OpenAI models are trained on patch-format edits, Anthropic models on string replacement, and forcing the wrong shape "costs extra reasoning tokens and increases mistakes" (S-049). This is the exact content a "generic" IR is tempted to hide. The design implication (doc 3 §1.2 stance) is validated at the mechanism level: *keep one semantic capability, compile per profile, and make the profile a first-class, versioned, expirable object.*

**F3. Assumption debt is observed in production, which makes "expiry" a required field, not a nicety.** Anthropic's context resets for Sonnet 4.5 "had become dead weight" on Opus 4.5 (S-047); Cursor documents "knocking down guardrails" as models improve (S-049). Neither system reports an automated retirement test; both discovered the debt by inspection. The mechanism (a model-specific rule outliving its motivating deficiency) is Tier-B production evidence.

**F4. Harness effects are large enough to be worth an instrument, and the field's own evidence says the unit of measurement is the configuration.** Harness-Bench (5,194 trajectories) concludes capability "should be reported at the model-harness configuration level" (S-062); Same-Model-Different-Harness moves a fixed model from 28% to 49% fail-to-pass with one context-policy change (S-072); the belief-divergence study shows harness variants change *beliefs* even when terminal success is unchanged (S-148); Harness-Updating-Is-Not-Harness-Benefit shows benefit is non-monotonic across model tiers (S-088). All four are 2026 preprints and `provisional` as performance claims, but they *independently* establish the same mechanism: harness is a policy intervention with model-conditioned effect size. That is the premise of a comparison-first instrument.

**F5. The comparison plane has real prior art, and it is black-box.** HAL (ICLR 2026, accepted) runs 21,730 rollouts across 9 models × 9 benchmarks behind a `run(input) → dict` interface, instruments cost, and analyses logs with a model (S-135). Inspect AI bridges external agents by *intercepting model API calls* in-process or through a sandbox proxy, controlling model choice and generation parameters while the agent keeps its loop (S-137). Omnigent hosts 23 harnesses behind declared, probe-verified capabilities (S-118). None of the three decomposes a participant into components; none has a behavioral IR; none can hold a context policy fixed across participants. This is precisely the ADR-0001 split: the comparison plane is not novel, the *white-box participant class inside it* is.

**F6. The behavioral-IR idea has partial priors, each confined to one plane.** DSPy: one `Signature`, many `Adapter`s (prompt/IO plane). AgentSquare: four modules with "uniform IO interface" plus recombination search (control/memory plane, coarse). LangGraph: graph-of-nodes control representation, no model conditioning, no comparison surface. HarnessFix's HTIR: a *trace* IR aligned to harness artefacts (measurement plane). PRISM: a three-surface edit taxonomy (prompt / tool-boundary / joint). No source found expresses **all seven planes** (context, tools, control, verification, state, security, measurement) **with provenance/authority on every entity and a profile-compiled lowering** — which is where the novelty claim must be pinned (see §6.1).

**F7. Naming collision is real.** "MetaHarness"/"meta-harness" is used by (i) the Stanford Meta-Harness paper and its reference repo (S-080, S-151), (ii) ruvnet/metaharness, a harness *generator* CLI (S-149), (iii) SuperagenticAI/metaharness, an unofficial Meta-Harness implementation (S-150), (iv) Omnigent's self-description as "the open-source meta-harness" (S-118 README), and (v) "Harness-of-Harness" (S-079) in the adjacent sense of orchestrating existing harnesses. The product name may stay per the brief, but sub-concept names must not lean on "meta-", and public materials need a disambiguating qualifier.

## 5. Disconfirming evidence & negative results

**Against "a comparison-first instrument is the differentiator".** HAL already exists, is accepted at ICLR 2026, is framework-agnostic, cost-instrumented and runs at 21k-rollout scale (S-135); Inspect AI already bridges external agents and controls the model plane (S-137); Harness-Bench already provides the factorial dataset (S-062). If the lab's value were "run many agents on many benchmarks and plot cost/accuracy", it would be redundant. *Why this does not overturn:* all three treat participants as opaque; none can vary one component while holding the rest fixed, attribute credit to a component, or express two harnesses in a common representation. The differentiator is therefore **not** the comparison plane; it is the **white-box participant class** and the representation that makes it decomposable. The thesis in §6.1 is worded accordingly, and the ADR narrows the novelty claim to what HAL/Inspect/Harness-Bench cannot do.

**Against "a behavioral Harness IR is novel".** DSPy Signatures+Adapters (S-144), AgentSquare's uniform-IO modules (S-024), GPTSwarm/ADAS graph search spaces (S-020, S-023), HTIR (S-146), PRISM's edit surfaces (S-093) and LangGraph's `StateGraph` (S-143) each represent part of a harness portably. *Why this does not overturn:* each covers one or two planes and none carries provenance/authority, permission, effect, validator and budget entities with a profile-compiled lowering. The honest claim is "first IR spanning all seven planes with provenance and profile compilation, designed for comparison" — and even that claim is an *engineering* novelty, to be demonstrated by the two-target compile test (T-LCD-04), not asserted.

**Against the whole enterprise: mature harnesses don't use frameworks (CF-009).** S-074 finds that none of eleven production coding harnesses imports a general-purpose agent framework for its core loop. If the best teams hand-roll loops, a framework aimed at them will not be adopted. *Why this does not overturn:* MetaHarness is not positioned as the core loop of others' products (non-goal N1). Its adopters are people who need to *measure* harnesses — including those eleven teams, who run their own A/B loops (S-049) and discover assumption debt by hand (S-047). The same study also reports policy migrating "from prompt prose to configuration" and ACP creating a "harness hosting" role — both moves *toward* a portable representation and a hosting boundary.

**Against the LCD-trap battery: "you cannot test for the absence of an abstraction failure".** Some LCD failures show up only after years (AWT). *Why this does not overturn:* the battery does not claim completeness; it converts the three historical failure signatures (feature intersection, untyped escape hatches, loss on lowering) into positive checks and adds a behavioural round-trip. It is a floor, and it is cheap. The residual risk is recorded in RK-02 as "open, mitigated by battery + Phase 2 validation".

**Against "model-conditioned compilation" itself.** If frontier models converge on identical tool conventions, profiles collapse to one and the compiler is dead weight — the same assumption-debt trap applied to our own design. *Why this does not overturn:* Cursor (S-049), Codex (`models.json`), OpenHands (`ModelSpecificSection`) and AutoGen (`ModelInfo`) all still ship per-family conditioning as of this audit; the design carries its own expiry (T-LCD-05 applies to the compiler's existence, not just to rules), so if profiles converge the lab will show it and the tier can be descoped by ADR.

**Against automated instruments generally: "The Last Harness You'll Ever Build" (S-147).** If a meta-evolution blueprint converges on any task without human engineering, the hand-designed IR is moot. *Why this does not overturn:* the claim is `provisional`, single-team, and contradicted at matched budget by S-083, S-075 and S-091 (see CF-004); moreover such a system would *need* a portable representation and matched-budget instrument to demonstrate its own claim — it is a customer of the lab, not a replacement.

**Negative result from the audit.** Grepping nine repositories for ablation/factorial/leaderboard/scorecard signals found zero hits in LangGraph, AIOS, OpenHarness and pi-mono core; hits in opencode/goose/dspy are unrelated (UI "leaderboard" strings, optimizer internals). No framework in the atlas ships a comparison plane. This supports the differentiation claim but also warns that *nobody has shipped one on top of a framework* — possibly because it is hard, not because nobody thought of it.

## 6. Recommendation for the spec

### 6.1 The differentiation thesis (one paragraph, for Spec §1)

> **MetaHarness is a research instrument and reference runtime for harness engineering, not another agent framework.** Its load-bearing capability is that any harness expressed in its behavioral Harness IR — a typed, provenance-bearing representation of all seven harness planes — can be assembled from swappable component variants, compiled per model profile and protocol target without loss of model-specific behaviour, executed on a deterministic runtime, and compared against any other harness (native or hosted) as an explicit model × harness × environment × budget configuration under shared evals. The instrument is what is new: existing frameworks give you *a* harness; existing leaderboards compare *opaque* harnesses; MetaHarness makes the harness itself the decomposable, attributable, evolvable experimental variable, and proves the representation is real by running a reference harness on it.

**Longer defence.** The claim decomposes into three parts, each with a test rather than an assertion. (1) *Comparison-first representation*: the IR is judged by whether two materially different profiles/targets compile from one definition with semantics preserved (T-LCD-04) and whether a reference harness round-trips behaviourally (T-LCD-03) — the doc 2 §12 "first paper". (2) *Integrated instrument*: the lab is judged by whether it can hold one component fixed and vary another across participants, report model × harness interaction effects (T-LCD-09), and refuse un-budgeted comparisons (T-LCD-14) — things HAL, Inspect and Harness-Bench cannot do because their participants are opaque. (3) *The §12 mechanisms* (IR+compiler, assumption-debt manager, safe adaptive optimizer, execution-alignment layer, trust-aware memory, capability kernel, benchmark science) are each partially preceded (DSPy adapters, AutoGen `ModelInfo`, CaMeL/Fides, HAL's Pareto analysis) and are claimed as *integrated contracts with provenance and expiry*, not as inventions. The novelty is in the coupling — which is exactly what doc 2 §9 says is new about the field.

### 6.3 The LCD-trap test battery (to be carried into acceptance criteria)

Conventions: each test names the owning workstream(s), the checkable criterion, the check method, and the failure signature. "Profile" = model profile (WS-C3); "target" = protocol/runtime lowering target (WS-A4); "surface" = anything a model or external system actually sees.

| id | criterion (must hold) | owner | check method | failure signature |
|---|---|---|---|---|
| **T-LCD-01 Model-specific tool shape without escape hatch** | The IR can express one `ToolCapability` (e.g., *edit file*) whose compiled surfaces differ by profile (patch-format for one family, string-replacement for another — S-049; `apply_patch` freeform vs absent — codex `models.json`) with **zero** per-model branches in the IR entity and all divergence in profile-owned fields. | A3, C3, E2 | Compile the same IR entity under ≥2 profiles; diff must touch only fields the profile schema owns; a semantic-equivalence validator (same effect on the workspace) passes on both. | An `if model == X` in IR, or a `raw_schema_override` field that bypasses the profile. |
| **T-LCD-02 Opacity budget** | Every model-facing surface is typed; free text is admitted only as a typed `Text` leaf carrying provenance, owner and authority class. Each harness definition reports an **opacity ratio** (tokens of untyped text ÷ total compiled surface tokens) and the lab can ablate opaque leaves individually. | A3, D1, I2 | Static check on the IR schema; opacity ratio computed at compile time and stored in the bundle. | "System prompt: string" as an IR entity; behaviour that cannot be ablated because it is one blob. |
| **T-LCD-03 Behavioural round-trip of a reference harness** | A minimal reference harness (Stage 0 baseline, mini-SWE-agent-class) expressed in the IR and compiled to the native runtime reproduces the original's behaviour within statistical equivalence on the Stage 3 suite (paired runs, fixed model/seed/budget). | A3, A4, I2 | Paired comparison; pre-registered equivalence margin; report distributions (doc 2 §8). | Systematic loss on any scorecard dimension attributable to a construct the IR could not express. |
| **T-LCD-04 Two-targets, two-profiles compile** | One IR definition compiles to ≥2 materially different profiles and ≥2 targets (e.g., native function calling and MCP) preserving policy and task semantics, verified by executable validators. | A4, C3, E4 | Same validators pass on all four compilations; permission/effect/budget invariants identical across targets. | Passing only on the "home" profile; validators skipped on a target. |
| **T-LCD-05 Every conditioned rule expires** | Every profile-owned rule carries hypothesis, evidence, owner, expiry condition and removal test (assumption-debt record). The compiler refuses a rule with none, warns on expired rules, and the lab can run a "delete this rule" experiment on demand. (Applies reflexively: the profile compiler itself carries an expiry and a removal test.) | C3, I6, A4 | Schema-level requirement; compiler diagnostics; a lab recipe "retire rule R". | Rules with `evidence: none`; "dead weight" discovered by inspection (S-047) instead of by test. |
| **T-LCD-06 Hosted participants never weaken native contracts** | Adding a hosted participant requires no change to any native (IR/runtime) contract. Hosting is removable: with hosting disabled the native acceptance suite is unchanged. No dependency edge points from IR entity definitions to the Hosting ABI. | J6, A3, L5 | Dependency-graph check in the spec's DAG; build with hosting tier absent. | An IR entity gaining a field "so that hosted participants can fill it". |
| **T-LCD-07 Declare, verify, stratify — never intersect** | The Hosting ABI defines participant capabilities as a declared vector (interrupt, streaming, resume, context-supply, tool-supply, permission-elicitation, cost-accounting, model-override…) verified by probes; undeclared = UNKNOWN, not unsupported; features are never removed from the ABI because some participant lacks them; comparisons stratify by capability. | J6, J4 | ABI schema mirrors ACP/LSP capability negotiation (S-035, S-152) and Omnigent's declared-vs-probed layers (S-118 `designs/harness-capabilities-bench-seam.md`). | A single "common subset" feature list; a probe result silently coerced to "unsupported". |
| **T-LCD-08 Component contracts see the profile** | Every component-class contract (compaction, context builder, control strategy, validator, router…) receives the model profile and resource accounting as inputs, so model-conditioned variants are expressible inside the contract rather than around it. | A5, J2, D2, F1 | Contract signature review; a model-conditioned variant (e.g., compaction that differs by context-window reminder policy, as in codex `models.json`) is implementable without touching Core. | A variant that must read a global or patch Core to learn which model it serves. |
| **T-LCD-09 Interaction effects are representable** | The experiment/results data model represents model × harness × environment × budget × seed as explicit factors and can report interaction effects and per-configuration distributions, never a single "harness score" or "model score". | I2, J3, J4, J5 | Schema check; a canned analysis "does compaction variant V help model M more than model N?" is executable. | Results keyed by harness alone, or by model alone. |
| **T-LCD-10 Names are surfaces, identities are semantic** | The identity of a capability/procedure/rule is content-addressed semantics; the model-facing name/description is a versioned, profile-owned surface. Renaming a compiled tool never changes IR identity; it is recorded as a profile edit with its own experiment (doc 2 §9: "a language-model tool often can [change behaviour when renamed]"). | A3, C3, L4 | Identity derivation excludes surface fields; rename produces a profile diff, not an IR diff. | Tool identity == tool name string. |
| **T-LCD-11 Lowering is lossless-or-declared-lossy** | Compiling to a protocol target (MCP/A2A/ACP/provider tool API) carries risk, permission, effect, cost and provenance metadata through typed extension slots (`_meta` prefixed keys) and the compiler emits a **loss report** for anything the target cannot carry; lifting back recovers everything not declared lost. | A4, E4, K3 | Round-trip lower→lift test per target; loss report is part of the bundle. | Silent dropping of permission or effect metadata at the MCP boundary. |
| **T-LCD-12 Contracts are operations, not inheritance** | No Core contract requires a component to subclass or import a framework object; every contract is specified as operations/inputs/outputs/invariants/failure modes (language-neutral). | A5, L5, L1 | Spec review; the contract can be implemented out-of-process. | "Implement interface X from package Y". |
| **T-LCD-13 Compliance is observable separately from validity** | The event taxonomy records, for every artefact delivered to a model, *delivered / activated / followed* events so the lab can measure harness compliance independently of harness validity (S-088 mechanism; ontology `validity vs compliance`). | B1, I1, I2, A2 | Event schema includes artefact-delivery events with artefact ids; a compliance metric is computable per profile. | Only "prompt sent" is logged. |
| **T-LCD-14 No un-budgeted comparison** | The experiment engine refuses to run or report a comparison whose arms lack an explicit, matched resource budget (tokens, calls, wall-clock, approvals); search-time and artefact benefit are separated in the results schema. | J3, J4, I5 | Engine-level precondition; results schema has `search_budget` and `eval_budget` fields per arm. | "Evolved harness after N attempts vs baseline with one" (S-083 critique). |
| **T-LCD-15 Class-scoped metrics** | Every scorecard metric declares which participant classes it applies to; component-level metrics on hosted participants are reported as N/A, never as 0 or as a configuration-level proxy. | J4, I2, A2 | Metric registry has an `applies_to` field; report generator enforces. | A hosted participant "scoring 0" on attribution quality. |

**Carrying into acceptance criteria.** Each test maps to a spec §7.2 #5 acceptance-criterion line in the owning subsystem. Tests T-LCD-01/-02/-06/-10/-12 are *schema/static* checks (C0, Stage 1); T-LCD-03/-04/-11/-13 are *executable* (Stage 3 evaluation-first, since they need the suite and event ledger); T-LCD-05/-08/-09/-14/-15 are *contract* checks enforced by the compiler/engine (Stages 1–3); T-LCD-07 lands with hosting (C2, Phase 3 / later stage). The readiness report should carry a 15-row LCD matrix with a status per test.

### 6.5 The strongest counter-argument and the response

**Counter-argument ("just another agent framework").** Every capability in doc 3 §2 already ships somewhere: loops, tools, compaction, memory, sandboxes, approvals and telemetry are in Microsoft's Harness ("batteries-included … individually customizable or removable", S-059), AWS AgentCore (declarative config + export-to-code, S-058), Cloudflare's runtime/harness split (S-056), LangGraph/deepagents (S-045), OpenHands SDK (S-110), goose, pi. Optimization lives in DSPy, GEPA, AFlow, Meta-Harness. Hosting lives in Omnigent. Leaderboards live in HAL. Security kernels live in CaMeL/Fides. The best teams hand-roll their loops anyway (S-074). A "meta-harness framework" that abstracts over all of this is either an LCD wrapper nobody adopts or a re-implementation of what each of those does better in its niche. The word "meta" is a tell: three other projects already use it for three different things.

**Response.** The objection is correct about *components* and wrong about the *object*. (1) None of the cited systems makes the harness a decomposable experimental variable: HAL and Inspect accept `run(input)` and intercepted model calls — opaque participants (S-135, S-137); Microsoft/AWS/Cloudflare give you *a* harness with swappable parts but no representation in which two harnesses are comparable, no profile compilation, no interaction-effect reporting, no assumption-debt records; DSPy's Signature/Adapter pair is the right idea confined to the prompt/IO plane; Omnigent declares and probes capabilities — the right hosting pattern — but explicitly cannot decompose what it hosts. The differentiator is the pairing of a **seven-plane, provenance-bearing IR with profile compilation** and a **lab that can vary one component under matched budget across participants**. (2) The S-074 finding is evidence *for* the positioning, not against it: those teams run bespoke A/B loops (S-049) and find dead-weight rules by hand (S-047); they are the instrument's users, not its replacement — and their migration of policy "from prompt prose to configuration" is movement toward exactly the representation we propose. (3) The claim is falsifiable on our own terms: if T-LCD-03 (round-trip) and T-LCD-04 (two profiles × two targets) cannot be passed, the IR *is* an LCD wrapper and the thesis fails — that is the doc 2 §12 "first paper" and it is scheduled before any evolution work. (4) The "meta" tell is acknowledged: sub-concepts avoid it, and the sponsor is asked (OQ) whether to qualify the product name.

### 6.6 Interface-contract sketch (language-agnostic) — the LCD gate

The battery implies one small contract that the compiler and lab must expose (WS-A4/J3 own the full versions):

- **`lcd_report(harness_def, profiles[], targets[]) → LcdReport`** — inputs: a harness definition, ≥2 profiles, ≥2 targets. Output: `{opacity_ratio, per_profile_diff_fields[], lowering_loss[target][], conditioned_rules[{id, evidence?, expiry?, removal_test?}], identity_stability: bool, hosting_edges: []}`. Invariants: `per_profile_diff_fields ⊆ profile_schema.owned_fields` (T-01); every `conditioned_rule` has all three evidence fields or the report is `FAIL` (T-05); `hosting_edges` is empty (T-06); `identity_stability` true under rename (T-10). Failure modes: `UnexpressibleSurface(entity, profile)` when the IR cannot express a required profile difference — this is the LCD signal and must be a first-class error, never a warning.
- **`equivalence_run(reference_participant, native_harness_def, suite, budget, seeds[]) → EquivalenceReport`** — paired runs; output: per-dimension distributions and an equivalence verdict against a pre-registered margin (T-03/T-04). Invariant: both arms carry identical `budget`; refuses otherwise (T-14).
- **`capability_vector(participant) → {declared: map, probed: map, unknown: set}`** — for hosted participants (T-07). Invariant: `unknown` is never coerced; comparisons consuming it must stratify.

### 6.7 Data-model sketch

- `LcdReport` (above) is stored in the reproducible harness bundle (WS-I3) next to the compile outputs, so every bundle carries its opacity ratio, lowering loss and conditioned-rule ledger.
- `AssumptionDebtRecord {rule_id, hypothesis, evidence_refs[], owner, expiry_condition, removal_test_ref, status}` — the schema WS-I6 will own; the *requirement that it exists on every conditioned rule* is a C0/Stage-1 schema constraint, even though the manager that acts on it is C4.
- `MetricDescriptor.applies_to ⊆ {native, hosted}` (T-15) in the scorecard registry (WS-I2/J4).
