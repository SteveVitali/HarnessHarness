## 1. Scope & boundary

This workstream decides **"version everything"** as one identity model: (i) the **identity scheme** — which of *content address*, *version id*, *semantic id*, *allocated id* and *logical name* applies to each kind of thing the instrument handles (HIR nodes, sealed definitions, component variants, Model Profiles, tools/ToolCapabilities, skills/Procedures, environment images, permission policies, budgets, graders/Validators, task data, run ledgers, bundles), with the invariants that tie the five together and the **provenance link** every reference carries; (ii) the **hash-algorithm and canonical-form pinning and rotation** procedure — the half of OQ-041 that WS-A3 and WS-B1 explicitly left to WS-L4 (OQ-056, OQ-083); (iii) the **immutability, supersession and revocation rules** over versioned things (the *artifact lifecycle* half of OQ-020 that is identity-shaped; WS-D4 owns memory-retrieval semantics, WS-H6 what audit must retain); (iv) **what counts as "the same harness" across edits** — the mapping between `HirDiff` classification and version/lineage identity; (v) **reproducibility levels** (recorded / bit-exact / semantic / statistical) with what each requires and what each participant class can claim; (vi) how identity feeds the reproducible harness bundle (WS-I3), the component registry (WS-J2), the results store (WS-J5) and audit (WS-H6); (vii) the host-ecosystem requirements WS-L1 must weigh, stated without naming technologies.

It explicitly leaves to neighbours: the canonical form's *definition* and the two-id derivation for HIR nodes (WS-A3 — adopted verbatim); the event envelope, `prev_hash` chain and payload offload (WS-B1 — adopted verbatim); the assembly grammar, `resolve`/`seal` pipeline and `ConfigurationId` composition (WS-A5 — adopted, one conflict flagged); the bundle *format* and export/import (WS-I3 — this dossier fixes the bundle's identity and completeness contract); registry *service*/discovery (WS-J2 — this dossier fixes the name-index record and resolution semantics); memory retrieval filtering by validity/authority (WS-D4 — this dossier fixes the version/supersession/revocation records D4 filters on); attestation/signature protocol (WS-H6 — this dossier fixes what a rotation checkpoint must contain); extension trust records and signing (WS-H5/L5 — this dossier fixes only that executables are referenced by content address plus a trust record); the provenance/authority label values (WS-L3, CF-006); and every language/runtime/storage-technology choice (WS-L1). Naming a *cryptographic standard* (a hash algorithm) is not a language or ecosystem commitment and is done below where the evidence demands it; naming a serializer, library or storage engine would be, and is not done.

## 4. Findings

### 4a. Mechanism evidence (a failure mode exists / an architecture is implementable)

**F1 — Every mature content-addressing system uses the same three-part construction: a domain tag, a canonical byte form, and a self-identified hash — and the systems that skipped one of the three paid for it later.** git prefixes content with `"<type> <size>\0"` before hashing so a blob and a tree with equal bytes cannot share an id (S-224); Nix builds an explicit `type:sha256:inner:store:name` fingerprint (S-225); RFC 6962 separates leaf and node hashes with `0x00`/`0x01` prefixes (S-190); OCI and multihash carry the algorithm inside the digest string (`sha256:…`; varint code) so a consumer can verify or pass through an unfamiliar algorithm (S-187, S-226). git, which fixed SHA-1 without an algorithm tag in 2005, has needed a multi-year, still-incomplete object-format transition once SHA-1 collisions became practical — the cost of omitting agility. **Consequence:** every HarnessHarness identifier is `(identity_profile, domain_tag, digest)` where the identity profile names the hash algorithm and canonical-form version; agility is designed in at Stage 1, not retrofitted (§6.2).

**F2 — Names are a separate axis from identity, and the two mature systems disagree on whether the name enters the hash; the disagreement is resolvable by *layer*.** Unison excludes names entirely ("names are just separately stored metadata that don't affect the function's hash", S-171 via WS-A3); git excludes them from blobs/commits but a *tree* entry binds a name to a hash; Nix *includes* the name in the store-path digest so identical bytes under two names are two paths. SemVer treats a version *label* as a claim about compatibility, not an identity, and forbids modifying released contents (S-227). Harbor records `AgentInfo.version` as a free string and keys lock equality by digest, not by name or path (`TaskLock._equality_key = (digest,)`, S-132); goose hashes the *path* of a recipe (S-112 via WS-A5) — the anti-pattern. **Consequence:** the IR layer follows Unison (T-LCD-10: surface names excluded from `semantic_id`); the *registry* layer follows git refs/Nix: a `(namespace, logical_name)` is a mutable, append-only pointer whose *history* is a first-class record and whose *binding* to a version is itself hashed into the bundle (so "which name resolved to which version at resolution time" is reproducible). Version labels (SemVer-class) are metadata on a name-history entry, never identity.

**F3 — The two evaluation harnesses that ship "lock files" independently converged on the same record shape: per-input content digests, a schema version on the lock itself, the harness's own version and source commit, and a lineage pointer for derived runs.** Harbor's `TrialLock{schema_version: 2, task{digest, git_commit_id}, agent (config), skills[{name, digest, git_commit_id}], extra_instructions[{digest}], environment, extra_docker_compose[{digest}], verifier, source_trial{action: regrade, trial_id, task}}` inside `JobLock{schema_version: 3, harbor{version, git_commit_hash, is_editable}, trials[]}`; digests are `sha256:`-prefixed, validated to 64 lowercase hex chars, and equality is content-anchored ("Equality is content-anchored: the trial UUID … and the source task digest. `path` is otherwise recorded for humans", S-132 `lock.py` L91–121). Inspect's `EvalSpec` records `revision{origin, commit, dirty}`, `packages{name: version}`, the full model generate config and `task_args` (S-136). Both also show the *unpinned* remainder: Harbor's `docker_image` is a mutable tag string and `AgentInfo.version` a claim; Inspect's `task_version` is an integer claim and its sandbox spec a name plus config file; neither can pin the provider-side model snapshot. Harbor is *migrating* from a directory-hash property (`Task.checksum`, deprecated) to lock digests — evidence that "compute the hash on demand" loses to "record the digest at resolution time". **Consequence:** the reproducible bundle (WS-I3) is a *lock manifest* of this shape (§6.5) and the reproducibility levels (§6.6) are defined by which members are pinned by digest vs recorded as claims.

**F4 — Production harnesses pin mutable references at the moment of use and store the pinned form; the unpinned form is kept only for display.** OpenHands resolves a plugin `ref` (branch) to a commit SHA and persists `ResolvedPluginSource{resolved_ref, original_ref}` "to ensure deterministic behavior across pause/resume … prevents drift when branches are updated between pause and resume", redacting credentials from the recorded URL (S-110 `plugin/types.py`); Codex writes `cli_version`, workspace `GitInfo{commit_hash, branch, repository_url}` and a per-turn `TurnContextItem{model, sandbox_policy, permission_profile, approval_policy}` into the rollout (S-107); Inspect redacts credentials from the recorded origin (S-136 `git.py`). **Consequence:** `resolve` (WS-A5) is where selectors become `version_id`s and where a `registry_snapshot_id` is minted; the sealed definition and the run manifest carry only pinned ids; selectors and display names live in `assembly` residue and name-history entries; recorded locators are credential-free.

**F5 — Supersession and revocation must be *records enforced by the resolver/retrieval layer*, not labels the consumer is trusted to read.** Invalidation Contracts attaches version stamps and cacheability hints so stale cross-episode memories are evicted deterministically and reports zero contract failures for validity while compliance varies by model 100% → ≤11% (S-077, `provisional (mech)`); "Revoked but Still Authoritative" finds that in five memory systems a soft-revoked fact "is returned wherever the revocation label is visible to the retrieval layer, outranks its replacement, and leads agents to the unsafe action", and that a guard between agent and backend fixes it (S-106, `provisional (mech)`). The two papers are fresh and single-team, but they instantiate a mature systems principle (cache invalidation and truth maintenance; doc 2 §5.1 Tier-B synthesis), and the audited code agrees: OpenHands' `Condensation` supersedes events by naming forgotten ids and the *projection* enforces it; Codex's rollback is an appended event the reconstruction interprets (WS-B1 F2). **Consequence:** a `supersedes` edge with `reason` and a `validity` interval is the only revocation mechanism; the superseded version is never deleted; `resolve` and D4 retrieval return the superseded version only when explicitly asked for a pinned id or an audit view (§6.3 rules S1–S8). D4 owns the retrieval filter; this dossier owns the record it filters on.

**F6 — "Bit-exact" is a property of *derivations from recorded inputs*, not of stochastic re-execution, and the systems that promise reproducibility say so.** Reproducible-builds defines reproducibility as bit-identical artifacts "given the same source code, build environment and build instructions" with the environment's relevant attributes recorded and minimized (S-181); SLSA records `resolvedDependencies` by digest separately from the parameters that named them (S-223); Nix distinguishes *input-addressed* outputs (identity = hash of the derivation) from *content-addressed* ones (identity = hash of what came out), precisely because a build need not be deterministic (S-225). WS-B1 established that no audited harness replays the control loop deterministically; all reconstruct state from events, and deterministic replay is a declared variant capability (WS-B1 F8, adr-3). **Consequence:** four reproducibility levels (§6.6): *recorded* (all inputs pinned — SLSA/Harbor lock completeness), *bit-exact* (derived views and, for declared variants, control decisions re-derive to equal hashes — Nix input-addressing applied to projections), *semantic* (re-execution satisfies the same validators/end-state class — Nix content-addressing applied to outcomes), *statistical* (distributions equivalent within a pre-registered margin across seeds under matched budget — doc 2 §8). A bundle *declares* the level it supports and the lab reports `n/a` above it.

**F7 — Provider-side model identity is the one input that cannot be content-addressed by us, and the audited systems record it as a claim.** Codex `model: String` / `models.json` `slug` + opaque `comp_hash`; Harbor `ModelInfo`; Inspect `model` + `model_args`; Anthropic and Cursor both report harness behaviour changing under model updates (S-047, S-049). **Consequence:** a `ModelSnapshotRecord{provider, model_id, snapshot_id?, pinned: bool, observed_fingerprint?}` with `provenance = reported` — never `measured` — and a rule that a bundle whose model record is `pinned = false` can claim at most the *statistical* level; a cheap deterministic probe fingerprint (fixed prompt, temperature 0, hash of output) is recorded as *evidence of drift*, never as identity (OQ-111).

**F8 — Directory-shaped artifacts (task data, skills, environment build contexts) need a *tree hash* with fixed rules, and three independent implementations chose subtly different rules.** git trees hash `mode name\0sha` entries; Harbor's `compute_skill_digest` hashes `relpath\0sha256(content)\0` over sorted files, `Packager.compute_content_hash` hashes `rel\0file_hash\n`, and the dataset manifest hashes a comma-joined sorted digest list (S-132) — three formats in one repository, none capturing file mode or symlinks. Nix's NAR serialization fixes ordering, modes and no timestamps. **Consequence:** the identity profile must fix *one* tree-serialization rule (sorted byte-order paths, mode class, symlink target, no timestamps/ownership) and every directory-shaped member of a bundle is addressed through it (§6.2 T-rule); a bundle must never contain two tree-hash conventions.

## 5. Disconfirming evidence & negative results

**Against content addressing everything (the "version everything is bookkeeping nobody keeps" objection).** Harbor is the field's most careful evaluation harness and still leaves the container image as a mutable tag, the agent version as a free string, and the model as a name; Inspect records a `dirty` flag rather than refusing dirty runs; Kiehl's ledger critique (S-195, via WS-B1) argues that record-keeping machinery rarely pays for itself. *Why this does not overturn:* the sponsor's brief makes reproducibility and audit C0/Must (R-2.12.1, R-2.8.6) and the *purpose* of the instrument is attribution — an unpinned input is an uncontrolled experimental factor, which is exactly the "model name absorbs the harness effect" failure doc 2 §8 warns about. The cost is bounded by design: digests are computed once at `resolve`/`put_blob` time (Harbor's own migration away from on-demand `checksum`), and the levels in §6.6 make partial pinning *legal and visible* rather than forbidden — a bundle with an unpinned image simply cannot claim more than the statistical level.

**Against excluding names from identity (Nix includes the name).** Nix's argument is real: identical bytes under two names may be two *different things* (two packages that happen to share a tarball), and collapsing them loses meaning. *Why this does not overturn:* the disagreement is about layers. In the IR, T-LCD-10 requires that renaming a compiled tool not change identity, and DSPy's `Signature.equals` including wording is the documented anti-pattern (CF-039). At the *registry* layer this dossier adopts Nix's concern in a different place: the **name binding** `(namespace, name) → version_id` is itself a hashed, provenance-bearing record that enters the bundle, so "the same bytes published under two names" are one `version_id` and two name-history entries, and the bundle records which one resolved. Nothing is collapsed; nothing is duplicated.

**Against hash-algorithm agility at Stage 1 (git ran fifteen years on one algorithm).** Agility adds a prefix to every id, a profile record to every manifest, and a rotation procedure nobody may ever run. *Why this does not overturn:* git's SHA-1→SHA-256 transition — forced by the 2017 collision — has been a multi-year, still-incomplete object-format migration precisely because ids carried no algorithm tag; OCI and multihash, designed after that lesson, both self-describe; the cost here is ~7 bytes per id and one record per manifest, and the rotation procedure (§6.2) reuses RFC 6962's consistency-proof shape that WS-H6 needs anyway. The design keeps *one* mandatory algorithm at any time so the day-to-day cost is nil.

**Against "semantic reproducibility" as a level (it is not reproducibility, it is agreement).** Two runs that satisfy the same validators can differ in every byte and in behaviour the validators do not observe; calling that "reproducible" invites the same over-attribution the level is meant to prevent. *Why this does not overturn:* the level is named for what it *checks* (validator/end-state equivalence) and is subordinate to the bit-exact level in the ordering; every semantic-level claim must name the validator set it was checked against (`ReproReport.validators[]`), so the reader sees what was and was not observed. Nix's content-addressed outputs are the precedent for "identity by what came out, verified by a fixed check", and doc 2 §8's insistence on distributions places the statistical level as the honest default for stochastic re-execution.

**Against deterministic revocation records (S-077/S-106 are fresh preprints).** Both mechanism papers are 2026 single-team; the revocation study's numeric findings may not replicate. *Why this does not overturn:* the recommendation rests on the *record shape* (a `supersedes` edge with reason and validity; superseded versions never deleted; resolvers default to the head), which is standard truth-maintenance/cache-invalidation practice and is what OpenHands' `Condensation`, Codex's rollback-as-event and git's refs already do; the preprints supply only the failure signature that motivates enforcing the record at the resolver rather than trusting the model to read a label. No C0 element depends on their numbers.

**Against a single tree-hash rule (git modes, NAR, Harbor's three formats all "work").** A fixed rule can be wrong for some artifact kind (e.g., a symlink-heavy workspace, a large binary corpus) and forcing one rule may make importing third-party digests impossible. *Why this does not overturn:* foreign digests are admitted as *recorded claims* (`foreign_digest{scheme, value}`) alongside the instrument's own tree hash, never as identity, exactly as OCI passes unrecognized algorithms through; the instrument's own hash must be one rule so that two bundles built on two machines agree.

**Negative results from the audit.** No audited harness (Harbor, Inspect, OpenHands, Codex) carries: an algorithm-agile identity profile; a content digest for the environment image (all use tags); a content-addressed configuration identity shared between the run record and the results store (Harbor has `concurrency_key`, not persisted as identity; Inspect derives `eval_id` from allocated ids); a supersession/revocation record on published component versions (SemVer's "MUST NOT modify" is a norm, not a record); or a declared reproducibility level. These are the `novel`-as-integration parts of §6, each with the partial precedent named above.

## 6. Recommendation for the spec

### 6.1 The unified identity model (Spec §8; ADR-0036)

Five identity kinds, each with a fixed domain of application. All hashed identities share one **identity profile** (§6.2).

| kind | form | applies to | derived how | mutable? |
|---|---|---|---|---|
| **content address** | `ContentAddress{idp, algorithm, digest, media_type, size}` (WS-B1 shape + `idp`) | raw bytes: artifacts, offloaded payloads, `CompiledPayload` bodies, environment snapshots/images (via their own manifest digest), task-data files, skill files, trajectories, native records of hosted participants | `H(idp ∥ "blob" ∥ bytes)`; directories through the **tree rule** (`"tree"` domain over sorted `(path, mode_class, entry_address)` entries; symlinks by target; no timestamps/ownership) | never |
| **version id** | `version_id = H(idp ∥ domain_tag(kind) ∥ canonical(record))` | every typed record the instrument authors: HIR nodes and sealed definitions (WS-A3), variant records (WS-A5/J2), Model Profile versions (WS-C3), permission policies (WS-H1), budgets (WS-L2), Validators/graders (WS-G1), task-data manifests, capability declarations (WS-J6), run manifests (WS-B1), bundle manifests (WS-I3), name-binding records (this dossier), identity-profile records | WS-A3 `identity()` generalized: same canonicalizer, kind-specific domain tag | never |
| **semantic id** | `semantic_id = H(idp ∥ domain_tag ∥ canonical(semantic projection))` | HIR nodes and definitions only (surface, provenance, ext, version excluded; refs by semantic id) — WS-A3 §6.1 verbatim | WS-A3 | never |
| **allocated id** | opaque, time-ordered (WS-B1: RunId, EventId, TurnId …) | things the runtime *creates as observations* rather than authors | WS-B1 | never reused |
| **logical name** | `(namespace, name)` + append-only **name history** | published things people refer to: harness definitions, variants, profiles, policies, validators, task sets, bundles | `publish` (§6.4) | pointer moves; history append-only |

**Versioned reference** — the one reference type every consumer uses (Spec §8 "versioned references"):
`VersionedRef{kind: RecordKind, version_id, semantic_id?, name?: {namespace, name, label?}, resolved_from?: NameSelector, supersedes?: version_id, provenance: ProvenanceRecord (WS-A3 shape), idp}`.

**Invariants (N-rules):**
- **N1 Full digests only.** Ids are never truncated or abbreviated in any stored record (OpenHands' 8-hex filenames are a display convenience, not identity); display forms are derived.
- **N2 Self-describing.** Every content address and version id carries `idp` (and the algorithm within it); a consumer that does not know `idp` may pass the id through (OCI rule) but must never *verify* it silently as OK.
- **N3 Domain separation.** Two records of different kinds with equal canonical bytes have different ids; two blobs vs a node never collide (git header / RFC 6962 rule).
- **N4 Identity compares by digest, never by name or path.** Equality of any versioned thing is `version_id` equality; `name`, `label`, `path`, `resolved_from` are for humans and for reproduction of resolution (Harbor `SourceTrialLock` rule).
- **N5 Pinned in sealed and executed forms.** A sealed definition, a run manifest, a bundle manifest and a registry record contain only `version_id`/`ContentAddress` references; a selector anywhere in them is `UnresolvedRef` (WS-A3/A5 rule, restated as an identity invariant; T-LCD-10 test: rename ⇒ `semantic_id` unchanged, `version_id` changed, name history extended).
- **N6 Semantic ids are the comparison coordinate, version ids the execution coordinate.** Results aggregate by `semantic_id`-based coordinates; runs, ledgers and bundles pin `version_id`s. (Resolves CF-083 between WS-A5 `ConfigurationId` and WS-A3/B1 "manifest ids are `version_id`s": *both exist* — `configuration_id` = `H(idp ∥ "configuration" ∥ canonical{model_ref, harness_def.semantic_id, profile.semantic_id, environment_ref, budget.semantic_id})` as the factor coordinate (seed excluded so seeds are replicates of one arm), and `configuration_version_id` = the same over `version_id`s plus `seed` as the manifest's exact-bytes key. The run manifest carries both.)
- **N7 Provider ids are surfaces.** Model snapshot ids, provider tool-call ids, container tags are `surface_ids{}`/claims with `provenance = reported`, never identity (T-LCD-10 applied to the run record; WS-B1 F5).
- **N8 One tree rule.** All directory-shaped members use the identity profile's tree rule; foreign digests are recorded as claims (`foreign_digest{scheme, value, source}`), never as identity.

### 6.2 Identity profile: hash pinning and rotation (answers OQ-056 / OQ-083; closes OQ-041 — ADR-0036)

`IdentityProfile{idp_id: "idp/1", hash_algorithm, digest_length, canonical_form_version (WS-A3/B1 rule set: sorted keys by code point, UTF-8, no whitespace, no Unicode normalization, integers or decimal strings, explicit null), domain_tags: map<RecordKind, bytes>, tree_rule_version, id_text_form: "<algorithm>:<hex>"}` — itself a record with a `version_id` under the *previous* profile (bootstrapping: `idp/1` is hashed under itself and its bytes are also published verbatim).

- **Pinning.** Every HIR dialect declares the `idp_id` it uses (WS-A3 §6.1 "pinned per HIR dialect"); every run manifest and bundle manifest carries `idp_id`; every id carries the algorithm text prefix. At any time exactly **one** `idp` is *mandatory-writable*; older ones are *readable*; there is no "default" algorithm for a consumer to assume.
- **`idp/1` requirements (properties, then the one standard they select).** A 256-bit, collision-resistant, standardized cryptographic hash with streaming (chunked) computation over multi-gigabyte blobs, second-preimage resistance, and ubiquitous independent implementations so the two-implementation byte-equality test (WS-A3 AC-6) is cheap. The hash OCI mandates and git chose for its transition satisfies these; naming a cryptographic standard is not an ecosystem commitment. Digest text form: lowercase hex, `algorithm:` prefixed (OCI grammar), so Harbor/OCI/SLSA digests interoperate textually.
- **Rotation procedure (Phase 2 detail, contract fixed now).** (1) Publish `idp/2` as a record hashed under `idp/1` (the *bridge record*), recording the reason. (2) **Ids are never rewritten.** Existing `version_id`s, `semantic_id`s, content addresses and hash chains remain valid *under their recorded idp*; `verify` recomputes with the id's own algorithm. (3) A **rotation checkpoint** event (`security.audit.checkpoint{seq_range, chain_hash (idp/1), tree_head (idp/1), rehash{idp/2, chain_hash', tree_head'}, bridge_record_ref, attestation_ref}`) is appended to every live run and to every bundle manifest, signing the old head under the new algorithm (RFC 6962 consistency-proof shape). (4) New records are written under `idp/2`; a record referencing an `idp/1` id references it as-is (mixed-idp graphs are legal; N2). (5) **Identity migration map** `IdMigration{from: (idp/1, id), to: (idp/2, id'), method ∈ {recanonicalized, rehashed_bytes}, attested_by}` is produced *on demand* by re-canonicalizing stored canonical bytes (records) or re-hashing stored bytes (blobs); the map is itself a versioned record; `semantic_id` equality across idps is asserted only through the map, never by string comparison. (6) Canonical-form changes are handled identically (a new `idp` with the same algorithm and a new `canonical_form_version`); the WS-A3/B1 golden corpus gains the new form. (7) Dual-write period: during rotation a writer may emit both ids in `alt_ids[]` — `alt_ids` are never identity.
- **Failure modes:** `UnknownIdentityProfile(idp)`, `AlgorithmMismatch(expected, found)`, `DigestLengthInvalid`, `TruncatedId`, `IdpNotWritable(idp)` (writing under a retired profile), `BridgeMissing` (an `idp/2` record with no bridge to `idp/1`).

### 6.3 Immutability, supersession and revocation (Spec §8 "artifact lifecycle"; feeds D4, H6, H5, J2 — ADR-0037)

**Immutability rules (I-rules).**
- **I1** Anything with a `version_id` or `ContentAddress` is immutable: bytes never change; a changed record is a new record with a new id (SemVer "MUST NOT be modified"; OCI "MUST NOT modify content in ways that change identifiers").
- **I2** A logical name is a mutable pointer with an **append-only history**: `NameHistoryEntry{namespace, name, version_id, semantic_id, label? (SemVer-class), published_at, publisher (provenance/authority), status ∈ {active, deprecated, yanked}, supersedes_entry?, display_selector?}`; moving a name is appending an entry; `yanked` hides the entry from default resolution and never deletes the version (registry precedent: Harbor/OpenHands keep pinned refs; SemVer norm).
- **I3** Deletion of bytes is only ever **redaction** (WS-B1 tombstone): the hash survives, the bytes may not; a `Missing` blob is distinguishable from a tampered one.
- **I4** Sealed definitions, run manifests, bundle manifests, registry records and name-history entries are immutable; only the *authored* assembly and the name pointer are mutable.
- **I5** Run manifests reference only `version_id`s/`ContentAddress`es (N5); a run's identity of inputs is therefore fixed at `open_run` (Codex/Inspect/Harbor "record at moment of use").

**Supersession rules (S-rules) — the `supersedes` edge (WS-A3 edge kind, `reason ∈ {edit, revocation, expiry, migration}`) generalized to every versioned record kind.**
- **S1** Supersession is an edge between two immutable versions, carried on the *newer* record (`supersedes: version_id`) and mirrored in the name history; it is never an in-place flag on the older record (which cannot change, I1). Revocation *without replacement* is a **revocation record** — a new version of the same kind whose `validity.until` is set and whose body is empty/tombstoned — so "revoked" is itself a versioned, provenance-bearing, hash-chained fact (S-106 mechanism: the revocation must be a first-class record the guard can act on).
- **S2** The supersession graph is acyclic; per `(namespace, name)` it is a DAG (forks allowed: two successors of one version are *branches*, each a name-history entry; the head a name resolves to is chosen by the entry's `status` and publisher authority, never by timestamp alone).
- **S3** `resolve(name | selector)` returns only `active` heads by default; a pinned `version_id` always resolves (audit and reproduction path) but the result carries `superseded_by[]`/`revoked: bool`; consumers that *execute* (run, retrieval into context, tool binding) must refuse a revoked version unless the request is explicitly `mode = audit | reproduce` — the guard sits in the resolver, not in the model (S-106; D4 applies the same filter to memories: validity and authority before relevance, CF-008).
- **S4** Downstream inheritance of invalidation (OQ-020): every sealed definition/bundle carries the closure of its pinned `version_id`s; a `supersedes{reason: revocation}` on any member marks every dependant *stale-by-dependency* — a derived, rebuildable index (`StaleIndex{version_id → [revoked member, reason, since]}`), never a mutation of the dependant. A stale definition still resolves by `version_id` (reproduction) but `resolve` by name refuses it and the lab labels its results `depends_on_revoked = true` (a class-scoped annotation, never silent exclusion — OQ-034's shape).
- **S5** Memory versions (WS-D4): a corrected or contradicted memory is a new `Memory` version with `supersedes{reason}` and the old version's `validity.until` recorded *on the new record* (the old record cannot change); the retrieval guard withholds superseded/revoked versions and their conflict set (S-106 guard; S-077 version stamps are the `version_id`/`validity` pair).
- **S6** Conditioned rules (T-LCD-05): assumption-debt expiry is `supersedes{reason: expiry}` produced by the "retire rule R" recipe; the retired rule stays readable.
- **S7** Migration (`migrate(doc, from, to)`, WS-A3) yields `supersedes{reason: migration}` with `MigrationLoss` recorded on the new record; identity migration across idps (§6.2) is *not* supersession — the record is the same record under two ids.
- **S8** Audit retention (WS-H6): every version that was ever *executed* (referenced by any run manifest) or *published* (has a name-history entry) is retained at least as its canonical bytes; blob GC follows WS-B1 §6.5 tiers; the name history and supersession edges are never GC'd.

### 6.4 "The same harness" across edits — typed diff ↔ version (answers key question 4; ADR-0037)

Sameness is a *ladder*, computed from WS-A3's `HirDiff.classification` and this dossier's records — never from names or text similarity:

| level | test | meaning for the lab (J4/J5) |
|---|---|---|
| **L0 identical** | equal `version_id` | same arm bytes; replicates differ only by seed |
| **L1 semantically identical** | equal `semantic_id` (diff has only `SurfaceEdit`/`ExtEdit`/provenance ops) | same harness under a different profile rendering or provenance; T-LCD-10; results pool by `configuration_id`, and the surface diff is a **profile-version** experiment (WS-C3) |
| **L2 same lineage, compatible** | `semantic_ops ≠ ∅`, `authority_delta ∈ {none, narrowing}`, `budget_delta ∈ {none, tightening}`, connected by `supersedes{edit}` under one name | "the same harness, a new version": `verify_resume` may accept mid-run (WS-A5 rule); results are *not* pooled — they are adjacent points on one lineage and J4 reports the per-version distribution and the `HirDiff` between them |
| **L3 same lineage, incompatible** | `authority_delta = widening` or `budget_delta = loosening` or dialect change | requires `provenance.origin = human` with attestation (ADR-0002 iii); a new name-history entry with `label` MAJOR bump (SemVer-class); never resumable mid-run |
| **L4 different harness** | no `supersedes` path under any name | a different lineage; comparisons are cross-harness |

Rules: (a) the registry (J2) stores a lineage as *sealed snapshots plus `HirDiff`s between consecutive versions*, each diff's `version_id` recorded on the successor's name-history entry (`diff_ref`), so "what changed" is a lookup, not a recomputation (answers the storage-form question ADR-0017 left to WS-L4: **snapshots are authoritative, diffs are derived and cached** — `apply(base, diff) = target` must hold byte-for-byte, and a diff that fails this check is regenerated, never trusted); (b) an `ablate`d definition (WS-A3) is an L2 successor with `derived-from{hypothesis: "ablation"}` and is filed under an experiment-scoped namespace so ablation arms never pollute a product lineage; (c) hosted participants (`OpaqueProcess`) have only L0/L4: their `version_identity = H(capability declaration ∥ participant_version)` (WS-A3 §6.5) is a `version_id`, their "same harness" is their declared `participant_version` string recorded as a *claim*, and DRIFT (ontology) is the observation that the claim failed.

### 6.5 Identity in the bundle (I3), registry (J2), results store (J5) and audit (H6)

**Reproducible harness bundle = a lock manifest (`BundleManifest`), itself a versioned record whose `version_id` is the bundle id.** Sections mirror SLSA's statement and Harbor's lock (S-223, S-132):

```
BundleManifest{
  idp, schema_version, created_at, bundle_kind ∈ {run, experiment, arm, lineage},
  subject:            { run_ids[], run_head_hashes[] (WS-B1 head), lineage[] (forked_from chain) }
  definition:         { sealed_definition: version_id (+ semantic_id), hir_dialect, validation_report: ContentAddress,
                        lcd_report: ContentAddress, opacity_report: ContentAddress }
  configuration:      { configuration_id, configuration_version_id, seed, budget: version_id, profile: version_id (+ semantic_id),
                        environment: EnvironmentRecord{image: ContentAddress | foreign_digest, build_context: tree address?, snapshot_refs[]},
                        permissions: version_id, policies[]: version_id }
  resolved_dependencies: { variant_records[]: version_id (the transitive closure actually bound — see OQ-074 answer),
                        registry_snapshot_id, name_bindings[]: NameHistoryEntry.version_id (which name resolved to which version),
                        tools[]: {capability semantic_id, version_id, surface_hash per profile}, skills/procedures[]: version_id,
                        text_leaves[]: semantic_id, compiled_payloads[]: ContentAddress + trust_record_ref (WS-H5),
                        validators/graders[]: version_id, task_data: TaskDataRecord{manifest: version_id, tree: ContentAddress, foreign_digest?},
                        extensions[]: {ContentAddress, signature_ref?} }
  model:              ModelSnapshotRecord{provider, model_id, snapshot_id?, pinned: bool, provenance: reported, observed_fingerprint?: ContentAddress}
  instrument:         InstrumentRecord{harnessharness_version, source_commit, dirty: bool, component_versions{…}, idp}
  traces:             { ledger_export: ContentAddress (canonical events), blobs[]: ContentAddress, audit_tree_head, attestation_ref? }
  results:            { results_rows[]: version_id (J5), metric_declarations[]: version_id }
  reproducibility:    { claimed_level ∈ {recorded, bit_exact, semantic, statistical}, evidence: ReproReport?, unpinned[]: [member, reason] }
  ext:                ExtensionSlots
}
```
Invariants: every member is a `version_id`/`ContentAddress` (N5) or an explicitly listed `unpinned` claim; `registry_snapshot_id` = `H(idp ∥ "registry_snapshot" ∥ canonical(sorted[(namespace, name, resolved version_id)] over the transitive closure actually referenced))` — the **closure, not the catalog** (answer to OQ-074: the closure is what reproduction needs and is machine-independent; a `catalog_id` may be recorded additionally as a claim for "what could have been chosen"); a bundle that omits any `resolved_dependencies` member that a run manifest references fails `check_completeness`. Export materializes fork lineage (WS-B1 F4) and is a Merkle tree over member addresses so partial verification is possible.

**Registry (J2).** Stores immutable `VariantRecord`s, sealed definitions, profiles, validators and policies by `version_id`; the **name index** is the append-only name history of §6.3 I2; `resolve(NameSelector{namespace, name, selector ∈ {label_range (SemVer-class), pinned version_id, head, deny_list}}, registry_snapshot_id?) → version_id | Unresolved | Ambiguous | Revoked` is deterministic given a snapshot id and never returns a `yanked`/revoked head by default. Registry records carry `dialect_range`, `capability_declaration`, `conditioned_rules[]` (WS-A5) and a `trust_record` (WS-H5/L5) — all inside the hashed record.

**Results store (J5).** Row key `(configuration_version_id, run_id)`; aggregation keys `configuration_id` (semantic coordinate) and the factor tuple `(model_ref, harness_def.semantic_id, profile.semantic_id, environment_ref, budget.semantic_id)` (T-LCD-09); every row carries `bundle_ref` and `reproducibility.claimed_level`; rows for `depends_on_revoked = true` bundles are annotated, never hidden (S4). Leaderboard rows are results rows plus a name-history entry — a leaderboard never keys by name alone.

**Audit (H6).** Every ledger event's `ir_refs[]` (WS-B1) carries `{semantic_id, version_id}`; `security.audit.checkpoint` includes `idp` and, on rotation, the bridge record (§6.2 step 3); the attestation subject is the bundle manifest `version_id` (SLSA `subject.digest`); redaction and yank are events, so the audit trail of *why* a version disappeared from default resolution is itself hash-chained.

### 6.6 Reproducibility levels (Spec §10; ADR-0038)

| level | claim | requires (all pinned in the bundle) | verified by | who can claim it |
|---|---|---|---|---|
| **R0 recorded** | every input the run consumed is identified by content (or listed as an explicit unpinned claim) and the raw traces are present | `check_completeness(bundle) = ok`; `InstrumentRecord.dirty = false` for anything above R0 | manifest completeness + hash verification of every member | native and hosted participants (hosted: at least `events`) |
| **R1 bit-exact (derivation)** | every *derived* object — context views, run summary, effect ledger, results rows, opacity/LCD reports, bundle manifest — re-derives from the recorded ledger to equal `view_hash`/`version_id`; for a control-strategy variant declaring `deterministic_replay`, the `control.decision` sequence re-derives too (WS-B1 AC-B1-3/-4) | canonical form + `idp` pinned; `observability_level ⊇ model_io` for replay of decisions; no re-sampling of the model; recorded effect outcomes | `reproduce(bundle, bit_exact)` recomputes and compares hashes | native participants; hosted only for derived views over their recorded events |
| **R2 semantic (re-execution)** | re-executing the pinned configuration (same `configuration_version_id`, same seed) yields runs whose validator verdicts and end-state class equal the recorded run's | `ModelSnapshotRecord.pinned = true`; environment image by digest; tool/skill/validator versions pinned; seed recorded; `NondeterminismDeclaration[]` (which sources of nondeterminism remain: provider sampling, wall clock, network) | `reproduce(bundle, semantic, n)` paired re-runs; `ReproReport{validators[], agreement per validator, end_state_match}`; verdict against a pre-registered margin | native participants; hosted participants whose mechanism supplies `end_state` |
| **R3 statistical** | the distribution of each scorecard metric over `n ≥ k` seeds is equivalent within a pre-registered margin to the recorded distribution, under matched budget | everything in R0; matched `search_budget`/`eval_budget` (T-LCD-14); seeds recorded; model may be unpinned but must be *named* with `observed_fingerprint` recorded before and after | `reproduce(bundle, statistical, seeds[])`; distributions, not means (doc 2 §8) | all participants; the only level available when the provider changes the model silently |

Rules: levels are ordered R0 < R1 < R2 < R3 in *strength of claim about re-execution* but R1 is the strongest claim about *derivation*; a bundle declares `claimed_level` and lists `unpinned[]`; a claim above what the pins allow is a `ReproClaimUnsupported` error at `check_completeness`; the lab reports a level as `n/a` (never 0) when the participant class cannot supply it (T-LCD-15); `ModelSnapshotRecord.pinned = false ⇒ claimed_level ∈ {R0, R1, R3}` (F7). "Bit-exact" is therefore precisely the reproducible-builds sense applied to derivations (S-181) and Nix input-addressing (S-225); "semantic" is Nix content-addressing applied to outcomes; "statistical" is doc 2 §8.

### 6.7 Interface-contract sketch (language-agnostic; operations · inputs → outputs · invariants · failure modes)

- `address(bytes | tree, media_type, idp?) → ContentAddress` — streaming; tree rule for directories; idempotent. *Failures:* `IdpNotWritable`, `TreeRuleViolation(path)` (e.g. unsupported entry kind).
- `identify(record, kind, idp?) → {version_id, semantic_id?}` — delegates to WS-A3 `identity` for HIR kinds; applies the kind's domain tag; `semantic_id` only for kinds with a declared semantic projection. *Failures:* `NonCanonicalInput`, `UnknownRecordKind`, `UnresolvedRef` (a selector inside a record to be sealed).
- `verify(id, bytes | record) → ok | Mismatch{expected, computed} | UnknownIdentityProfile` — recomputes under the id's own idp; never coerces.
- `publish(namespace, name, version_id, label?, supersedes?: version_id, status = active, provenance) → NameHistoryEntry` — *Invariants:* append-only; `label` unique per name (SemVer "MUST NOT be modified"); `supersedes` must name a version of the same kind; publishing a version whose `HirDiff` vs `supersedes` has `authority_delta = widening` requires `provenance.origin = human` + attestation. *Failures:* `LabelReused`, `KindMismatch`, `AuthorityWideningRequiresHuman`, `NamespaceForbidden(authority)`.
- `resolve(NameSelector, registry_snapshot_id?, mode ∈ {execute, audit, reproduce}) → VersionedRef | Unresolved | Ambiguous{candidates} | Revoked{version_id, superseded_by[], reason}` — *Invariants:* deterministic given a snapshot id; `mode = execute` never returns yanked/revoked/stale-by-dependency heads; pinned `version_id` resolves in every mode with its status attached.
- `supersede(new: version_id, old: version_id, reason, provenance)` / `revoke(old: version_id, reason, authority, replacement?: version_id) → RevocationRecord` — emits the edge, extends name history, updates the derived `StaleIndex`; never touches `old`. *Failures:* `CycleDetected`, `NotAncestorOrSibling` (allowed with `reason = fork` only), `AuthorityInsufficient`.
- `lineage(version_id | name) → DAG{versions, supersedes edges, diff_refs, name_entries}`; `sameness(a: version_id, b: version_id) → {level: L0..L4, evidence: HirDiff.classification | none}`.
- `snapshot_registry(refs[]) → registry_snapshot_id` — closure over the referenced names (§6.5).
- `bundle(scope: run_ids[] | experiment_id | arm | lineage, policy) → BundleManifest` (WS-I3 owns format; this fixes members); `check_completeness(bundle) → ok | Incomplete{missing[]} | ReproClaimUnsupported{claimed, max_supported, unpinned[]}`; `reproduce(bundle, level, seeds?) → ReproReport{level, verdict, per_member_hash_checks, validators[], distributions?, nondeterminism_sources[]}` — refuses unmatched budgets (T-LCD-14).
- `rotate(from_idp, to_idp, reason, authority) → RotationPlan{bridge_record, checkpoints_to_emit[], migration_map_ref}`; `migrate_id((idp, id)) → (idp', id') | NoBridge`.

Every operation is implementable out-of-process over the canonical encoding (T-LCD-12); failure modes are typed errors, never warnings, except `ReproReport` verdicts, which are declared outcomes.

### 6.8 Data-model sketch

`IdentityProfile` (§6.2) · `ContentAddress{idp, algorithm, digest, media_type, size}` · `VersionedRef` (§6.1) · `NameHistoryEntry` (§6.3 I2; `diff_ref?`, `display_selector?`) · `RevocationRecord{kind, revokes: version_id, reason, validity.until, replacement?, authority, provenance}` · `StaleIndex` (derived) · `IdMigration` · `ModelSnapshotRecord` · `EnvironmentRecord` · `TaskDataRecord` · `InstrumentRecord` · `BundleManifest` (§6.5) · `ReproReport` · `NondeterminismDeclaration{source ∈ {provider_sampling, wall_clock, network, filesystem_order, concurrency}, confined_to_events: bool}` (WS-B1 F8) · `configuration_id` / `configuration_version_id` (N6).

### 6.9 Acceptance-criteria sketch

- **AC-L4-1 Self-describing ids.** 100% of stored ids parse as `<algorithm>:<hex>` with full digest length; a truncated or untagged id is rejected at `verify` with `TruncatedId`/`AlgorithmMismatch`.
- **AC-L4-2 Domain separation.** A corpus containing a blob, a Text leaf and a node with identical canonical bytes yields three distinct ids.
- **AC-L4-3 Rename stability (T-LCD-10).** Renaming a compiled tool under a profile yields: `semantic_id` unchanged, `version_id` changed, a new name-history entry, `sameness = L1`.
- **AC-L4-4 Pinned forms.** A sealed definition, run manifest, bundle manifest or registry record containing any selector or display name as a reference fails `identify` with `UnresolvedRef`.
- **AC-L4-5 Cross-implementation agreement.** Two independent implementations of `address`/`identify` agree byte-for-byte on the WS-A3/B1 golden corpus extended with ≥20 directory trees (symlinks, executables, empty dirs, non-ASCII names).
- **AC-L4-6 Rotation.** After `rotate(idp/1 → idp/2)` on a corpus with chained runs: every `idp/1` id still verifies; every live run has a rotation checkpoint whose `rehash` verifies under `idp/2`; `migrate_id` round-trips for every record in the corpus; no stored id was rewritten.
- **AC-L4-7 Revocation enforcement.** After `revoke(v)`, `resolve(name, mode = execute)` never returns `v` or any definition in `StaleIndex[v]`; `resolve(v, mode = audit)` returns `v` with `revoked = true`; the ledger carries the revocation as an event; a retrieval test in D4's suite shows the revoked memory withheld and its replacement returned (S-106 scenario as a regression test).
- **AC-L4-8 Bundle completeness and levels.** `check_completeness` fails when any run-manifest reference is absent from `resolved_dependencies`; a bundle with `ModelSnapshotRecord.pinned = false` claiming R2 is `ReproClaimUnsupported`; hosted participants' bundles report R1/R2 as `n/a`, never 0.
- **AC-L4-9 Bit-exact derivation.** For the Stage-1 reference run, deleting every view and re-deriving from the bundle's ledger export yields equal `view_hash`es and an equal bundle `version_id` (WS-B1 AC-B1-3 lifted to the bundle).
- **AC-L4-10 Lineage storage.** For every consecutive pair in a registry lineage, `apply(base, diff_ref) = target` byte-for-byte; a diff failing the check is regenerated and the discrepancy logged.
- **AC-L4-11 Yank ≠ delete.** After `status = yanked`, the version's bytes and its name-history entry remain retrievable by `version_id`; the results store rows referencing it are annotated, not removed.

### 6.10 Build-stage suggestion

- **C0 / Stage 1:** `IdentityProfile idp/1`; `address` (blob + tree rule), `identify`, `verify` sharing WS-A3's canonicalizer; `VersionedRef`; `configuration_id` + `configuration_version_id` in the run manifest (with WS-B1/A5); name index with `publish`/`resolve` (local, single-namespace); `supersede`/`revoke` records and edges; `InstrumentRecord`; golden corpus + AC-L4-1…5.
- **C0 / Stage 2:** `StaleIndex`, `lineage`/`sameness`, `snapshot_registry`, revocation enforcement in `resolve` and D4 retrieval (AC-L4-7), `EnvironmentRecord` with image digests (with WS-B5), `ModelSnapshotRecord` with fingerprint probe (with WS-C1).
- **C0 / Stage 3 (evaluation-first):** `BundleManifest` members and `check_completeness` (with WS-I3), `reproduce` at R0/R1/R3 with `ReproReport` (with WS-I2/J3), results-store keys (with WS-J5), AC-L4-8…10.
- **C1 / Stage 4:** hosted-participant bundle rows (`participant_version` claim, DRIFT annotation), lineage-aware export, multi-namespace registry (WS-J2 service), `rotate`/`migrate_id` end-to-end (AC-L4-6) with WS-H6 attestation.
- **C2 / Stage 5–6:** R2 semantic reproduction gated on profile pinning (WS-C3); evolution lineages (`derived-from`, ablation namespaces) with WS-I5/I7.

### 6.11 Host-ecosystem requirements for WS-L1 (properties; no technology named)

H1 **One canonicalizer** for records (WS-A3 P4) usable for identity, ledger hashing and bundle manifests — the same implementation, byte-tested. H2 **Cryptographic hashing with algorithm agility**: at least two standardized 256-bit-class algorithms available, streaming over arbitrarily large inputs, constant memory. H3 **Deterministic tree serialization** of directories (sorted byte-order names, mode class, symlink targets, no timestamps/ownership) implementable in a few hundred lines. H4 **Content-addressed blob store** with dedup and delete-by-address (WS-B1 property 4). H5 **Arbitrary-precision integers and decimal strings** in the canonical form (WS-B1). H6 **Unicode-preserving strings** (no implicit normalization). H7 **Ability to read a container/VM image digest and a source-control commit id** from the host environment at resolution time (Inspect/Codex/Harbor all shell out; a boundary is acceptable). H8 **Credential redaction** helpers for recorded locators. H9 **Out-of-process implementability** of every §6.7 operation over the canonical encoding (T-LCD-12). H10 **Append-only name history** with atomic append (WS-B1 property 1 reused). None of these fires an ADR-0009 hard gate; H1–H3 are weighted criteria under C3/C6.

## 10. Confidence

**High** for the identity model's shape (five kinds, domain separation, self-describing agile digests, names as append-only pointers over immutable versions): every element has a Tier-A/B precedent read in a standard or in source (git, Nix, OCI, multihash, RFC 6962/8785, SLSA, SemVer; Harbor, Inspect, OpenHands, Codex at pinned commits) and composes with the WS-A3/B1/A5 contracts read in full. **High** for the immutability and pinned-form rules (universal in the audited systems). **Medium** for the supersession/revocation *enforcement* placement (resolver guard): the record shape is mature practice, but the motivating failure evidence (S-077, S-106) is `provisional (mech)` and the guard's cost in retrieval latency is unmeasured. **Medium** for the reproducibility levels: the definitions rest on Tier-A/B standards, but the R2 margin design and the model-fingerprint probe are proposals to be validated at Stage 3. **Medium-low** for the rotation procedure's operational details (no audited harness has rotated an algorithm; the design borrows from RFC 6962 and OCI and is exercised only by AC-L4-6). No C0 element rests on a 2026 performance number.
