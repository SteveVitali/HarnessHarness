## 1. Scope & boundary

This workstream decides how **behaviour-changing dependencies** — skills (SKILL.md bundles with scripts/references/assets), hooks (commands or in-process callbacks bound to lifecycle events), plugins (bundles of skills/hooks/MCP servers/commands/policies), MCP servers (local processes or remote endpoints that supply tools, resources, prompts and `instructions`), repository instruction files (AGENTS.md/CLAUDE.md/GEMINI.md-class), fetched web content that carries instructions, and extensions the agent installs for itself — acquire **identity**, **integrity**, **attestation**, a **provenance class on injection**, **execution isolation**, and an **install → update → revoke → audit** lifecycle inside HarnessHarness. It fixes one invariant the whole design turns on: **no automatic elevation by configuration location** — the directory, marketplace, settings scope or "trusted folder" an extension was found in never mints authority; only a verified origin plus a legitimate endorsement event does (ADR-0033 rule 6, ADR-0035 basis list). It confirms the **trust-record shape** CF-055 asked WS-H5/L5 to confirm, and answers OQ-022 and the WS-H5 half of OQ-107.

It explicitly leaves to neighbours: **WS-L5** — the component-class contract, plugin packaging and the kernel↔extension boundary protocol (this dossier fixes what a plugin *record* must carry and how its executables are isolated, not the ABI); **WS-D5** — the Procedure/skill IR and progressive-disclosure semantics (this dossier fixes the provenance class and pin of a skill, not its representation); **WS-E4** — MCP/ACP/A2A transports (this dossier fixes the *surface pin* and lifting class of an MCP server, not the client); **WS-H1** — the reference monitor and Π (this dossier supplies the `pin` endorsement, the extension taint tag and the install-effect classification as inputs); **WS-H3/H4** — credential mediation and egress policy (this dossier states which env/secret/network defaults an extension process receives and delegates their mechanism); **WS-B5/E5** — the sandbox helper (this dossier declares isolation classes; the helper implements them); **WS-H6** — attestation of chain heads and retention (this dossier fixes which extension events exist and what the bundle carries); **WS-H7** — approval UX and fatigue (this dossier fixes *what* an install/trust approval endorses); **WS-F1** — hooks as control-boundary guards (this dossier fixes hook trust and isolation, not hook semantics — OQ-165); **WS-G1** — advisory scanners as Validators. Nothing here names a language, runtime, package ecosystem or framework.

## 4. Findings

### 4a. Mechanism evidence (a failure mode exists / an architecture is implementable)

**F1 — An extension is three things at once, and every precedent that secured only one of them was compromised through another.** A skill/plugin is (i) *text the model reads* (SKILL.md body, tool descriptions, MCP `instructions`, AGENTS.md), (ii) *code a machine runs* (scripts, hooks, MCP server processes, in-process plugin modules), and (iii) *a claim about what it may do* (frontmatter `allowed-tools`, MCP `ToolAnnotations`, plugin `permissions`). The Agent Skills specification (S-309) defines (i) and (ii) and is silent on trust; MCP says (iii) are "hints" never to be trusted from untrusted servers (S-153 L1903–1910). The attack literature attacks each leg: tool poisoning and cross-server shadowing attack (i) (S-310); ClawHavoc's infostealers attack (ii) through (i) — the SKILL.md tells the agent to run the installer (S-311/16); registry-level squatting attacks the *name* (S-303); semantic registry attacks manipulate *which* skill is selected through its description alone (S-301). Unit 42's diagnosis is the program's: "no isolation between skill logic and agent authority" (S-311); the skills taxonomy paper names "absence of a data-instruction boundary" and a "single-approval persistent trust model" as the structural causes (S-300). **Consequence (§6.1):** an extension record must carry a *separate* label, pin and grant for each leg — text authority (ADR-0033 class), code identity + isolation class, and a Permission the kernel confers — and no leg may be raised by another (a signed script does not make its SKILL.md `definition`; an approved install does not make its descriptions trusted).

**F2 — In source, every audited harness elevates extension content by location and inherits ambient authority into extension code; none records provenance on the injected text.** goose renders each MCP server's `instructions` into the **system prompt** after Unicode-tag sanitization (`agents/prompt_manager.rs` L109–127) and lists discovered skills in the system prompt via `SkillsClient::get_instructions` (`skills/client.rs` L246–266); opencode renders `<available_skills>` from `~/.claude/skills`, `~/.agents/skills`, every `.claude/.agents` directory walking up from cwd, config dirs, `skills.paths` and remote `skills.urls` (`skill/index.ts` L176–232, L307–330) with the only gate being a name-pattern permission rule; gemini-cli's own consent text admits "Agent skills inject specialized instructions … into the agent's system prompt" (`consent.ts` L26). Extension *code* runs with the host's authority: opencode `import()`s npm/file plugins **in-process** (`plugin/loader.ts` L128–137) and auto-loads any `{plugin,plugins}/*.{ts,js}` under a config dir (`config/plugin.ts` L20–31); pi-mono loads extensions in-process through a module loader with the full extension API (`core/extensions/loader.ts`); goose spawns stdio MCP servers on the host with the merged environment including keyring-resolved `env_keys` (`extension_manager.rs` L1609–1650) and runs plugin hooks as `sh -c <command>` with `PLUGIN_ROOT` (`hooks/mod.rs` L1111–1130); opencode passes `...process.env` to every local MCP server (`mcp/index.ts` L352–355); OpenHands and codex run hooks as host shell subprocesses. This is the source-level form of S-103's "skill discovery into high-privilege roles" and S-104's assembly bug, corroborated independently of their `provisional` attack rates. **Consequence (§6.2, invariant L1):** location is a *scope fact*; authority is minted only by ADR-0033 defaults and ADR-0035 endorsements; extension-provided free text is `external` (rule R-TEXT) unless sealed or pinned; extension code never runs in the kernel process and never inherits the ambient environment.

**F3 — The maturing harnesses have independently added *location-trust gates* and *admin allowlists*, but none has *content-anchored identity with authority derived from a verified signer*.** Codex skips AGENTS.md entirely for untrusted projects (`agents_md.rs` L61–62), records a `HookSource ∈ {System, User, Project, Mdm, SessionFlags, Plugin, CloudRequirements, CloudManagedConfig, …}` on every hook run (`hook_runtime.rs` L983–995), scopes skills `User | Repo | System | Admin` (`protocol.rs` L3801), and lets a managed requirements layer restrict plugin marketplaces to allowed git URLs/host patterns/local paths (`marketplace_policy.rs` L35–80). pi-mono prompts "Trust project folder? … load settings and resources, install missing project packages, and execute project extensions" and defaults to untrusted without a UI (`project-trust.ts` L24–95). gemini-cli tiers policy by source (default < extension < workspace < user < admin, `policy/config.ts` L133), refuses ALLOW and YOLO rules contributed by extensions ("Ignoring this rule for security", L244–252), keeps a per-project trusted-hooks list keyed `name:command` (`trustedHooks.ts`), and has an *integrity store* — but it is an HMAC over the extension's **install metadata** under a machine-local secret (`integrity.ts` L190–320): it detects local tampering with the record, not who published the content. Claude Code ships admin controls (`strictKnownMarketplaces`, `blockedMarketplaces`, `disableCommandPluginSources`, `allowManagedHooksOnly`) and documents "no built-in signing/verification … trust is social/organizational" (S-313). Two useful precedents survive: the **monotone authority layering** these systems converge on (extension < workspace < user < admin; extensions may narrow, never widen — exactly WS-A5's `authority_cap`, ADR-0024) and the **SEP-1024 transparency rule** (exact command and arguments, untruncated, before execution). **Consequence:** location-trust and admin allowlists are kept as *scope facts and source policy* (`TrustRootPolicy.allowed_sources`, §6.3); authority still derives from signer/hash + endorsement (S-222/S-223 rule).

**F4 — Pinning is universally partial and default-unpinned, which is precisely the rug-pull and freeze/rollback surface TUF exists to close.** opencode resolves a bare plugin name to `name@latest` (`plugin/shared.ts` L207–210) and refreshes remote skills by comparing a version *string* with no digest (`skill/discovery.ts`); goose installs plugins by cloning a git URL and auto-updates every N hours by re-pulling (`plugins/mod.rs` L153–260) while OSV malware checks only fire for two package ecosystems and *fail open* on unknown commands or network failure (`extension_malware_check.rs` L46, L425); pi-mono distinguishes `pinned` npm versions (exact semver) from ranges that update to `@latest` (`package-manager.ts` L139–144, L1101–1105, L1173); codex packs npm plugins with an optional version and hardens tar extraction (size cap, no links, path-escape check — `plugin_bundle_archive.rs` L127–235) but verifies no signature; Claude marketplaces support `sha`/`sha256` pins but refresh daily in the background and default to `ref` (S-313); OpenHands persists the resolved commit SHA for resume determinism (`extensions/fetch.py` L170–284) — the one precedent that matches ADR-0036 F4. MCP has no pin at all: the server may change any tool's description after approval (S-310; ETDI's motivation, S-304). TUF names the attacks this enables — freeze, rollback, mix-and-match, key compromise — and the remedies: content hashes in signed targets metadata, a snapshot of consistent versions, expiring timestamps, delegations with thresholds, revocation through root (S-306). **Consequence (§6.4):** every extension member of a sealed definition is a `ContentAddress` (tree rule) or `version_id`; selectors resolve only at `resolve`; an MCP server's *lifted surface* (tool names, schemas, descriptions, `instructions`) is content-addressed at resolution and re-checked at connection (`surface pin`); background updates never touch a sealed definition — they create a new version and a supersession; freshness is a *policy* (`max_age`) checked at `resolve`, never an in-run mutation.

**F5 — Scanners are advisory and evadable; they can refuse but never confer.** The registry that integrated two scanners after ClawHavoc still shipped infostealers hidden by base64 droppers, 22 MB README padding above scanner size limits, and paste-site redirects that swap the payload *after* publication (S-311); the formal-analysis paper reports that information-flow analysis "adds no detections over pattern matching on this corpus" (S-305); registry descriptions alone evade governance blocking in 36.5–100% of trials (S-301); goose's own OSV check fails open. Meanwhile 73.5% of credential leaks in skills come from debug output "because agent frameworks feed stdout into the LLM context window" (S-279) — a *harness* property, not a scanner miss. **Consequence (§6.3, §6.5):** advisory scans (malware advisories, secret patterns, invisible-Unicode/bidi detection, description–code mismatch) are `Validator{kind: advisory}` outputs recorded on the trust record and may *deny* under policy; they never raise a class (ADR-0035 `validator` basis is restricted to closed-schema shape endorsement). Extension stdout/stderr enters the ledger as `external` tool output with the extension's taint tag and is subject to WS-H3 redaction before delivery — the leak channel is closed by provenance, not by scanning.

**F6 — Agent-initiated installation is already a product feature and the only governed precedent gates it on a human elicitation and a first-party originator.** Codex prompts "Install / Continue anyway" when a mentioned skill declares an MCP dependency, only for first-party clients behind a feature flag (`mcp_skill_dependencies.rs` L1–60); goose's `summon` extension and sub-recipes, opencode's `skills.urls`, and every SKILL.md that says "run `npx …`" are ungoverned versions of the same path; ClawHavoc *is* this path weaponized (S-311/16). ADR-0035 already gives the type-level rule: a `delegate` origin can never endorse; approval endorses **one effect** with canonical arguments, never content or a class. **Consequence (§6.6, ADR-0065):** a model-install is a governed `Procedure` whose effects are ordinary ledgered effects (`net_egress`, `fs_write`, `exec`, `spawn_process`), whose result is an extension record at `origin = model`, content authority ≤ `external` with taint `{model, source}`, Permission ⊆ the proposer's own grants (attenuation, ADR-0034 P2), isolation ≥ `subprocess_confined`, activation as a `HirDiff` with `authority_delta ∈ {none, narrowing}` (widening from a non-human origin is refused, ADR-0017); a human `approval` of the install effect does not raise its content; only a later `pin` (verified signer) or `promotion` (human review) does.

**F7 — Hooks are the extension kind with the highest authority-to-scrutiny ratio, and the precedents that noticed treat them as code with a per-project trust decision.** Hooks fire on lifecycle events with the tool input/output and can *block* or *modify* decisions (goose `HookDecision`, codex `Blocked`, gemini `HookCheckerRule`, OpenHands `should_continue`); they run as host shell commands with the user's PATH (`goose/hooks/mod.rs` L1075–1130); gemini keeps an explicit trusted-hooks list and codex records hook provenance per run. Under ADR-0016 a hook that can block is a guard at a `DecisionPoint` (control boundary β) and therefore *definition*-plane behaviour: it must be a sealed member with a `CompiledPayload` or code pointer, a declared interface, an isolation class and its own Permission. A hook contributed by a project directory or plugin can attenuate (deny/ask) but never allow — gemini's rule (`policy/config.ts` L244) is the precedent for "extensions narrow, never widen" applied to hooks. Hook semantics as HIR entities are OQ-165 (WS-F1/A3).

## 5. Disconfirming evidence & negative results

**Against pinning everything: catalogs drift and users want updates.** OpenHands' authors chose deny-lists over pins because skill catalogs change (ADR-0024 (c)); Claude marketplaces refresh daily and pi/goose auto-update; a pinned SKILL.md misses upstream fixes. *Why this does not overturn:* ADR-0025 already separates *authored selectors* (ranges, branches, deny-lists — legal) from the *sealed* form (pins only); updates are supersessions that produce a new definition version with a classified `HirDiff` (L2 if grants/authority do not widen), and `resolve` may declare `max_age`/`freshness` policy so stale pins are *refused at resolve*, not silently replaced mid-run. The cost is one re-seal per update — which is exactly the moment a human should see the diff of grants and hooks.

**Against signatures: no ecosystem signs skills; the trust roots do not exist yet.** The Agent Skills spec has no signing field; Claude Code documents "no built-in signing"; ClawHub, SkillsMP and the MCP registries verify at most namespace ownership (S-303). Demanding signatures would make the C1 feature unusable in 2026. *Why this does not overturn:* the design makes **hash pins mandatory and signatures optional**: an unsigned extension is content-addressed, sandboxed and delivered as `external` text — usable, honest and cheap; a signature verified against a `TrustRootPolicy` is the only thing that can raise text to `definition` (`pin` basis). Trusted publishing with keyless signing already exists for the two package ecosystems every harness shells out to (S-249), and in-toto/SLSA fix the envelope; adoption is a policy knob per definition, not a prerequisite.

**Against sandboxing extension processes: it breaks the tools people install extensions for.** Local MCP servers exist to reach the filesystem, browsers, and cloud APIs; hooks exist to run formatters and tests in the workspace; a confined default will fail many of them on first use. gemini-cli's SDK-side `excludedCommands`/`allowUnsandboxedCommands` and Anthropic's ~93% approval rate (S-053) show the pressure toward escape hatches. *Why this does not overturn:* the isolation class is *declared per extension* with its Permission (fs allowlist, network egress list, declared env keys) and reviewed at `seal` — the same declaration MCP's own best-practices text asks for ("provide mechanisms for users to explicitly grant additional privileges", S-308); an extension that needs the whole host declares `host_unconfined` and the definition's `authority_cap` decides whether that is admissible. What is refused is *silent* ambient authority, not capability. The utility cost is a Stage-4 Lab measurement (AC-H5-9), not an assumption.

**Against `external` for skill text: it makes skills useless.** If a skill's instructions are `external`, the per-call context label drops to `external` whenever a skill is activated (ADR-0034 P3) and every open-world effect goes through Π. That would make skills — the field's main procedural-memory mechanism (S-039, S-074) — a liability. *Why this does not overturn:* (i) skills placed in the Harness Definition by the author are sealed (`definition`) and skills from a signed source are pinned (`definition`) — the common cases for a *research instrument* whose definitions are authored; (ii) only *discovered, unsigned* third-party skills are `external`, which is exactly the ClawHavoc population; (iii) the S-103 skill-directory vector shows the alternative is the bug; (iv) the Lab can measure the cost (AC-H5-9). WS-D5 may additionally let a skill declare a *typed* interface (arguments, effects) so that the parts that matter to the monitor are structured, not free text.

**Against forbidding run-time discovery: every audited harness discovers skills at run time, and users expect `~/.agents/skills` to just work.** *Why this does not overturn:* the closed-world rule (ADR-0019) already forbids any run-time surface without a compiled identity; discovery therefore moves to `compose → resolve`, where a *declared source* (`kind = directory_scan{root, scope}`) enumerates candidates and pins them. The user experience is preserved (the directory is scanned) while the *result* is a sealed member with provenance — and hosted participants keep their own run-time discovery (T-LCD-06, `n/a` for the relevant metrics). Recorded as CF-143 because a Lab arm "run-time discovery on/off" is not natively expressible.

**Against a content-addressed surface pin for MCP servers: benign servers change descriptions constantly.** Description edits, added optional parameters and reordered tools will trip `ExtensionSurfaceDrift` and force re-resolution. *Why this does not overturn:* drift is the *definition* of a rug pull (S-310, S-304) and there is no way to distinguish benign from malicious description changes without reading them; the pin makes the change *visible and reviewable* as a `HirDiff` on the lifted `ToolCapability` surfaces rather than silently effective; the tolerance policy (`drift_policy ∈ {refuse, quarantine_changed, accept_schema_only}`) is per definition and is OQ-164 with WS-E2/E4.

**Against the model-install path: the safest answer is "the agent never installs anything".** *Why this does not overturn:* the sponsor scope names "the agent installing its own extensions" as in-scope; codex ships it; an ungoverned version (SKILL.md saying "run the installer") exists in every harness anyway. Governing it — as ordinary effects, attenuated grants, `external` text and a human approval of one effect — is strictly safer than pretending it does not happen, and the definition's `authority_cap` may set `model_install = deny`.

**Negative results from the audit.** (i) No audited harness content-addresses an MCP server's tool surface; (ii) none attaches an authority class to extension-provided text or a taint tag to extension output; (iii) none verifies a publisher signature on a skill, hook or plugin (gemini's store is machine-local HMAC; codex hardens archives without signatures); (iv) all four run third-party hooks on the host shell with the user's environment; (v) all default-unpinned resolutions are silent (no event); (vi) the Agent Skills spec and the MCP registry carry no signing or provenance field at all.

## 6. Recommendation for the spec

### 6.1 Extension kinds and the three-leg trust record (confirms CF-055; ADR-0063)

`ExtensionKind ∈ {skill, hook, plugin, mcp_server, instruction_file, fetched_instruction, component_variant (WS-L5), other(ext)}` — closed per HIR dialect. An **extension record** is a registry-layer versioned record (ADR-0036 "version id" domain; a new `RecordKind` and domain tag), not a new HIR entity: it *references* the HIR nodes it contributes (`Procedure` for skills, `ToolCapability` for MCP tools, `HarnessRule`/guard for hooks, `Text` leaves for instruction files, `CompiledPayload` for scripts and servers).

```
ExtensionRecord{
  extension_id: version_id,                       // over this record's canonical form
  kind: ExtensionKind, name: {namespace, name},   // display; name history per ADR-0037
  content: ContentAddress,                        // tree rule over the extension directory / lifted surface document
  manifest: TypedValue,                           // parsed SKILL.md frontmatter, plugin manifest, MCP initialize+tools/list document
  contributes: [VersionedRef],                    // HIR nodes minted from this extension (all with provenance)
  locator: SourceLocator{scheme, credential_free_uri, selector?, resolved{commit|digest|registry_version}, fetched_at},
  trust: ExtensionTrustRecord, provenance: ProvenanceRecord, ext }
ExtensionTrustRecord{
  text_authority: AuthorityClass,                 // leg (i): class of the free text it contributes (default per §6.2 table)
  code_identity: [ContentAddress],                // leg (ii): every executable body (scripts, server binary/package digest, hook command)
  isolation: IsolationClass,                      // leg (ii): where the code may run (§6.5)
  grants: VersionedRef<Permission>,               // leg (iii): what its code/tools may effect (domain + scope; attributes narrow only)
  declared_claims: TypedValue,                    // leg (iii) as *claims*: allowed-tools, MCP annotations, plugin permissions — never inputs to decisions
  attestations: [Attestation],                    // ADR-0033 shape; kind ∈ {pin, signature, hash_chain, seal}; verified_by = kernel
  attestation_status: {none_required | verified(signer_ref, predicate_types[]) | failed(reason) | missing},
  scans: [AdvisoryResult{validator_ref, status ∈ {clean, flagged, unavailable}, findings[]}],   // advisory only
  text_hygiene: TextHygieneReport{invisible_or_bidi: [(path, offset, codepoint)], description_code_mismatch?: ref},
  installed_by: Origin, installed_at, scope: PersistenceScope,
  status ∈ {resolved, sealed, quarantined, revoked}, review_ref?: EventRef }
```

**Invariants.** L1 (*location neutrality*) `text_authority ≤ default_text_authority(kind, origin, attestation_status)` (table §6.2) — never a function of `locator`, `scope`, directory, marketplace or a "trusted folder" fact; violations are `LocationElevation` validation errors. L2 (*leg independence*) no field of one leg raises another: a verified `signature` raises `text_authority` only through a `pin` endorsement event that names the signer under the definition's `TrustRootPolicy`; it never widens `grants` (grants are conferred only by a `Permission` whose `issuer.authority ≥ principal`, ADR-0035 check 1). L3 (*claims are not grants*) `declared_claims` never reach the monitor (MCP hints rule; `allowed-tools` is a request the author may accept at `seal`). L4 (*pinned in sealed form*) a sealed definition references extensions only by `extension_id` whose `locator.resolved` and `content` are pins (ADR-0036 N5) — `UnpinnedInSealedForm` otherwise. L5 (*out-of-process*) `isolation ≠ in_process` for every extension whose `provenance.origin ∉ {kernel}`; third-party code never loads into the kernel process (T-LCD-12; ADR-0050 boundary). L6 (*taint tag*) every item an extension contributes or emits carries `taint ∋ extension_id` unless the extension is sealed/pinned at `definition` and its tool is closed-world (ADR-0033 I3 keeps such items ≤ `external`).

### 6.3 Attestation, trust roots and the `pin` endorsement (answers OQ-107, WS-H5 half)

`TrustRootPolicy` is a `definition`-plane record (a `HarnessRule` artifact with `authority_cap`, layered per ADR-0024: organisation > user > project may only narrow): `{allowed_sources: [SourcePattern{scheme, host_pattern | url, ref_pattern?}], accepted_signers: [SignerRef{identity_kind ∈ {key, keyless_issuer+subject, marketplace_signing_key}, trust_root_ref}], required_predicates: [PredicateType] (e.g. SLSA-provenance-class), require_signature_for: set<ExtensionKind>, hash_only_ceiling: AuthorityClass (default external), max_age?: Duration, drift_policy, scanner_policy{flagged ⇒ deny|quarantine|warn, unavailable ⇒ deny|warn}, model_install: deny|ask|allow_attenuated, archive_policy{max_bytes, links_allowed: false}}`.

- **Attestation kinds** (ADR-0033 `Attestation.kind`): `pin` = kernel-verified equality of fetched bytes with the recorded `ContentAddress` (integrity, cheap: one tree hash per load, amortised by the content store); `signature` = a signed statement (in-toto/DSSE-class envelope) whose `subject.digest` equals `content` and whose signer resolves under `accepted_signers` (authenticity; one signature verification plus a trust-root lookup per resolve, cached by `(extension_id, policy version_id)`); `hash_chain` = presence in a ledger the kernel already attested (WS-H6; free); `seal` = the author's own sealing act.
- **Rule.** `verify_attestation` never reads a class from the extension's own manifest (in-toto/SLSA signer–builder rule, MCP hints rule). `pin` **endorsement** (ADR-0035 basis `pin`, endorser = the definition's policy at class `definition`) is emitted only when `attestation_status = verified` under the *current* `TrustRootPolicy`; hash-only pins yield integrity and `hash_only_ceiling` (default `external`), never `definition` — this refines ADR-0035's "`pin` → definition or principal per policy" wording (CF-142). A failed verification yields `unverified` and `status = quarantined`.
- **Trust roots** live outside the editable surface (ADR-0024 MUST-code: extension trust); the accepted-signer list is data but its `authority_cap` makes model/evolution edits `AuthorityWidening`. Key rotation/revocation of a signer is a supersession of the policy record; a revoked signer marks every extension it vouched for `stale-by-dependency` (`StaleIndex`, ADR-0037 S4) — the TUF root-revocation shape without a TUF repository.
- **Freshness** (TUF freeze/rollback): `resolve` records `fetched_at`, `registry_version`/`commit` and the source's *snapshot* (`registry_snapshot_id` over the closure, ADR-0036); `max_age` refuses stale pins at resolve; rollback is visible as a supersession whose `version_label` regresses (`LabelRegression` warning at `review`).

### 6.4 Lifecycle: `discover → resolve → review → seal → activate → update → revoke → audit` (ADR-0064)

- `discover(sources: [DeclaredSource], policy) → [Candidate{locator, kind, manifest_preview}]` — sources are *declared in the Assembly* (`directory_scan{root, scope}`, `marketplace{catalog_ref}`, `registry{name}`, `git{url, ref}`, `archive{url}`, `mcp_endpoint{uri}`, `instruction_files{roots}`); scanning `~/…` implicitly is not a source. Run-time discovery does not exist (closed-world rule). Failure: `SourceNotAllowed(policy)`.
- `resolve(candidate, policy) → ExtensionRecord` — fetch through the credential-free locator with WS-H4 egress policy; unpack under `archive_policy`; compute `content` (tree rule) and `code_identity`; for `mcp_server`, connect in the declared isolation class and lift `initialize` + `tools/list` + `resources/list` + `prompts/list` into a *surface document* whose `ContentAddress` is the **surface pin** (descriptions, schemas, annotations, `instructions`, server name/version) — lifted `ToolCapability` nodes carry `authority = unverified` (ADR-0034 P7); run advisory validators (malware advisories with `unavailable` recorded, secret patterns, `TextHygieneReport`, description–code mismatch); verify attestations; fill defaults from §6.2; mint `contributes` nodes with provenance. Failures (typed, never warnings): `UnpinnedInSealedForm`, `AttestationRequired`, `AttestationFailed`, `ArchivePolicyViolation`, `NameCollision`, `ScanDenied`, `SourceNotAllowed`, `IsolationUnavailable(class)`.
- `review(record) → ReviewRequest` — renders, untruncated (SEP-1024): the canonical exec/install plan (command, arguments, env keys, isolation class, fs/network grants), the surface document diff vs the previous version, the `TextHygieneReport`, advisory findings, attestation status and the resulting `text_authority`. A human decision here is an `approval` of the **seal diff** (`HirDiff` adding this extension) — one endorsement of one edit, never of the content (S-053 bound). Unattended definitions configure `review = policy_only`.
- `seal` (ADR-0025) — refuses any extension whose `status ∉ {resolved}` or whose `grants ⊄ authority_cap`; records `security.extension.sealed{extension_id, trust_snapshot}`.
- `activate` (run time) — hook registration, MCP connection, skill listing: emits `security.extension.loaded{extension_id, isolation, pin_check ∈ {ok, drift}}` (ADR-0035 mandatory-provenance table already names this class); at MCP connection the live surface is re-lifted and compared with the surface pin — on mismatch `ExtensionSurfaceDrift` is raised, the changed tools are **not delivered** (closed-world), `security.extension.drift{diff_ref}` is appended and the run proceeds per `drift_policy`. Skill delivery/activation/following are `context.artefact.delivered/activated` + `verification.artefact.followed` (T-LCD-13) with the extension's `delivery_id`.
- `update` — never in place: `resolve` a new candidate → new `ExtensionRecord` with `supersedes{edit}` → new definition version via `HirDiff`; `authority_delta = widening` (new grants, higher class, hooks gaining block power) requires `human` origin (ADR-0017/0037 L3); background refresh may *prefetch and pre-resolve* but never re-seal; a running run keeps its pins until `verify_resume`.
- `revoke(extension_id, reason, authority)` — `RevocationRecord` (ADR-0037 S1); `StaleIndex` marks dependants; `resolve(mode = execute)` refuses; live runs receive `security.extension.revoked` and the kernel (a) removes the extension's surfaces from subsequent `context_assembly` (closed-world), (b) converts its `grants` to deny in Π, (c) terminates its processes, (d) emits `action.effect.unknown` for any in-flight effect of that extension (B3 rule); results rows are annotated `depends_on_revoked`. Propagation latency into live runs is OQ-166.
- `audit` — every operation above is a ledger event with provenance; the bundle's `resolved_dependencies` carries `extensions[]: {extension_id, content, trust_record version_id, attestation refs, surface pin}` (ADR-0038 member list, refining "extensions + signatures") and H6 attests chain heads; `audit_view` can answer "which extension delivered the text that preceded effect E" through `taint` and `derived_from`.

### 6.5 Execution isolation (declares classes; WS-B5/E5/H3/H4 implement)

`IsolationClass ∈ {in_process (kernel only), subprocess_confined (helper-binary sandbox: fs allowlist = declared roots, no network unless `net_egress` granted with destination list, cleared environment + declared env keys, no ambient credentials — secrets by WS-H3 handle, resource limits, kill-on-timeout), container (session/environment container, image by digest — B5), remote (network endpoint; H4 egress policy; OAuth per MCP best practices — no token passthrough), host_unconfined (admissible only under `authority_cap` and always reviewed)}`. Defaults: hooks and skill scripts `subprocess_confined`; local MCP servers `subprocess_confined` with declared egress; remote MCP `remote`; plugins inherit the max of their members; instruction files and fetched content have no code leg. Every process start is an effect (`spawn_process`/`exec`) with the extension's Permission as the grant source and `charged_to = subject` unless the extension is an instrument (grader, probe). Extension stdout/stderr is `external` tool output with `taint ∋ extension_id` (F5).

### 6.6 The model-install path (ADR-0065)

A run-time request by the model (or by content it read) to add an extension is a `Procedure` `install_extension(candidate)` provided by the kernel (MUST-code) and admitted only if `TrustRootPolicy.model_install ≠ deny`. Its steps are ordinary effects: `net_egress` (fetch), `fs_write` (cache), `exec`/`spawn_process` (unpack/probe) — each authorized by H1 through Π at the proposer's effective authority (`≤ delegate`, typically `external` after reading the instructing content), so Π's default row for `spawn_process`/`net_egress` at `external` is `ask`; the human `approval` endorses **that install effect** (`effect_id` + canonical args = locator + expected digest), nothing else. The resulting record has `installed_by = model(run_ref)`, `text_authority ≤ external`, `taint ⊇ {model, source}`, `grants ⊆ Permission(proposer)` (attenuation, ADR-0034 P2 applied to the extension as a delegate), `isolation ≥ subprocess_confined`, and enters the definition only through a `HirDiff` whose `authority_delta ∈ {none, narrowing}` and `budget_delta ∈ {none, tightening}` — so it is at most an L2 successor and never widens (ADR-0017 refuses widening from non-human origins). The run continues on the new version through `verify_resume` (ADR-0025). `pin`/`promotion` may raise it later; nothing in the run can. Unattended runs (no `ask`) get `model_install ∈ {deny, allow_attenuated}` only.

### 6.7 Interface-contract sketch (language-agnostic; operations · inputs → outputs · invariants · failure modes)

- `discover(sources, policy) → [Candidate]` — pure over declared sources; `SourceNotAllowed`.
- `resolve(candidate, policy, mode) → ExtensionRecord | Quarantined{record, reason}` — deterministic given `(candidate.locator, fetched bytes, policy version_id)`; produces pins only; failures §6.4.
- `verify_attestation(record, policy) → verified(signer, predicates) | failed(reason) | missing` — anchors on signer/trust root, never on the manifest; cacheable by `(content, policy version_id)`.
- `default_text_authority(kind, origin, attestation_status) → AuthorityClass` — the §6.2 table; total; independent of locator/scope (property-tested, AC-H5-2).
- `lift_surface(mcp_endpoint, isolation) → SurfaceDocument{content, tools[], resources[], prompts[], instructions?, server_info}` and `check_surface(record, live: SurfaceDocument) → ok | Drift{HirDiff over lifted ToolCapability surfaces}`.
- `review(record, previous?) → ReviewRequest{canonical_plan, grants, isolation, surface_diff, hygiene, scans, attestation, resulting_class}`; `approve_seal_diff(diff, principal) → EndorsementEvent{basis: approval, subject: HirDiff}`.
- `activate(record, run) → ActivationHandle` — emits `security.extension.loaded`; `IsolationUnavailable`, `PinMismatch`, `Revoked`.
- `install_extension(candidate, proposer_ctx) → ExtensionRecord` — the §6.6 procedure; every step an effect; `ModelInstallDenied`, `AuthorityWidening`, `InsufficientBudget`.
- `revoke(extension_id, reason, authority) → RevocationRecord`; `propagate_revocation(run_id) → [EventRef]`.
- `trust_snapshot(definition) → {extensions[], policy version_id, registry_snapshot_id}` for the bundle.
All operations are records-in/records-out and implementable out-of-process (T-LCD-12); a hosted participant's extensions are invisible to them (T-LCD-06) and the metrics below render `n/a`.

### 6.8 Data-model sketch

`ExtensionKind` · `ExtensionRecord` · `ExtensionTrustRecord` · `SourceLocator` · `DeclaredSource` · `TrustRootPolicy` (HarnessRule artifact, layered) · `SurfaceDocument` / surface pin · `IsolationClass` · `AdvisoryResult` · `TextHygieneReport` · ledger event classes `security.extension.{resolved, quarantined, sealed, loaded, drift, install_requested, install_completed, revoked}` (all carry provenance; `loaded` already mandatory per ADR-0035); bundle member `resolved_dependencies.extensions[]` (refines ADR-0038). Ledger `Origin.tool(extension_ref, inner_source?)` is reused; `TaintTag = extension_id` is a valid tag under ADR-0033 (origin ref at class ≤ `external`).

### 6.9 Acceptance-criteria sketch

- **AC-H5-1 Pinned forms.** A sealed definition, run manifest or bundle containing an extension reference whose `locator.resolved` is a selector (branch, `latest`, range) or whose `content` is absent fails `seal`/`check_completeness` with `UnpinnedInSealedForm`. (C0/Stage 1)
- **AC-H5-2 Location neutrality (property test).** For every `(kind, origin, attestation_status)` and every locator/scope/"trusted folder" fact, `default_text_authority` is invariant; the M-CPE fixture extended with a skill discovered from a project directory renders its text only in roles ≤ `role_map(external)`; `context_label = external` while it is delivered. (C0/Stage 1–2)
- **AC-H5-3 Leg independence.** A signed skill with a malicious `allowed-tools` claim gains `definition` text authority and **no** grants; an approved install of an unsigned plugin gains no text authority; a validator endorsement of a closed-schema tool result never touches the extension's class. (C0/Stage 2)
- **AC-H5-4 Surface pin / rug pull.** Connect to an MCP server, seal; change one tool description on the server; the next connection emits `security.extension.drift`, the changed tool is not delivered, the run proceeds per `drift_policy`, and the diff is a `HirDiff` over the lifted surface. (C1/Stage 4)
- **AC-H5-5 Isolation.** A hook, a skill script and a local MCP server each attempt an undeclared file read, an undeclared network egress and a read of an ambient credential; all three are refused by the helper with a ledgered effect refusal; declared equivalents succeed. (C0/Stage 2 with B5/E5/H3/H4)
- **AC-H5-6 Attestation.** With `require_signature_for ∋ skill`: an unsigned skill resolves `quarantined`/`unverified` and its scripts never run; a skill signed by an accepted signer receives a `pin` endorsement to `definition`; the same skill after the signer is revoked is `stale-by-dependency` and refused at `resolve(mode = execute)`. (C1/Stage 4)
- **AC-H5-7 Model-install.** A SKILL.md instructing "install X" leads to an `install_requested` event; without approval nothing is fetched; with approval of the one install effect the extension is `external`, tainted `{model, source}`, its grants ⊆ the proposer's, the definition edit is L2 with `authority_delta = none|narrowing`; an install that would add a `net_egress` grant the proposer lacks is `AuthorityWidening`. (C1/Stage 4)
- **AC-H5-8 Revocation propagation.** Revoking a plugin mid-run terminates its server, removes its tools from the next `context.assembled`, converts its grants to deny, emits `action.effect.unknown` for its in-flight effect and annotates the results row `depends_on_revoked`. (C1/Stage 4 with B3/H6)
- **AC-H5-9 Utility measurement.** The Lab runs "same task, matched budget: extension text `external` vs sealed; confined vs host_unconfined" and reports success, approvals, cost and Π-denials (T-LCD-14). (C1/Stage 4)
- **AC-H5-10 Audit.** For every effect in a run, `audit_view` lists the extensions whose text was in the proposing call's context (via `context_label.taint`) and whose code produced the effect; the bundle's `extensions[]` verify by digest and the trust snapshot re-derives (R1). (C0/Stage 3)
- **AC-H5-11 Hygiene.** A SKILL.md with invisible Unicode/bidi controls resolves with a non-empty `TextHygieneReport` shown at `review`; bytes are preserved in the `Text` leaf; the report is advisory. (C0/Stage 1)

## 10. Confidence

**High** for the invariants (location neutrality, pinned sealed forms, leg independence, out-of-process isolation, claims ≠ grants): each follows from ratified ADRs (0019/0024/0025/0033–0037) and from Tier-A/B standards and protocol text (TUF, in-toto/SLSA, MCP hints rule, SEP-1024), and every audited harness's failure mode is the negation of one of them. **Medium-high** for the default authority table: it is the ADR-0033 minting rule applied kind-by-kind, but `external`-for-unsigned-skills has an unmeasured utility cost (AC-H5-9) and WS-D5 may add a typed skill interface. **Medium** for the surface pin and `drift_policy`: the mechanism is ETDI/Invariant's recommendation and WS-A4's surface hashes make it cheap, but benign churn rates are unknown (OQ-164). **Medium** for the model-install path: it composes ratified rules (attenuation, approval-of-one-effect, no widening from non-human origins), and codex's elicitation is the only governed precedent. **Medium-low** for attestation operations: no skill ecosystem signs today; the design is usable without signatures and the signing infrastructure choice is OQ-162. No C0 element rests on a `provisional` number; S-299…S-305/15/16 supply existence and shape only.
