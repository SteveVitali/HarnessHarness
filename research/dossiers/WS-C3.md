## 1. Scope & boundary

This workstream decides **how one semantic meaning in a sealed Harness Definition becomes the model-specific surfaces a particular model snapshot sees, as data that can be diffed, tested in isolation, probed against the live model, expired and deleted** — and what the compiler, the registry and the Lab owe each other so that a rule that exists because of a hypothesised model deficiency can be shown to still earn its place. Concretely it fixes: (a) the **rule inventory** `ProfileRuleInventory/1` — for each of the twelve ADR-0020 kinds, the typed parameter shape, the surface fields it owns, what it may reference (an E2 `SurfaceFamily` variant, a D1 `Layout`, a `Text` leaf), its application point (compile time vs run time under the closed-world rule) and its removal-test shape; (b) the **Profile Compiler** contract — `resolve_profile`, `lower_profile` (ADR-0019 stage 3 made concrete), `diff_profiles`, `probe_profile`, `test_profile`, `evaluate_expiry` — as one component class with `home = model_boundary` (Ontology v1 *boundary component*); (c) **profile chains and selection** — declarative selector matching, precedence, refusal on ambiguity, `successor_ref`/`retirement_at` as the data form of a model upgrade, no silent fallback profile; (d) the **profile test contract** that separates *validity* (the profile is well-formed, owned-field-disciplined, capability-consistent, deterministic, equivalence-evidenced) from *compliance* (the served model actually follows what the rule renders) and from *conformance* (the model actually has the declared capability); (e) the **expiry/revalidation contract** — trigger evaluation, the status state machine as ledger events, the removal test as a matched-budget `ComparisonReport`, and the reflexive expiry of the Profile Compiler and of every profile; (f) the `profile_prose` bucket of the opacity report; (g) the answers to OQ-064, OQ-067 (profile side), OQ-071, OQ-104 (profile side), OQ-122 (profile side), OQ-293, OQ-294 and the reconciliation of CF-199, CF-166, CF-106.

It explicitly leaves to neighbours: the compilation pipeline, purity, trace map, `relower`, bundle identity (**WS-A4**, ADR-0019 — consumed); the equivalence obligations E1–E7 and the composite/synthesized surfaces (**WS-A4/WS-E2**, ADR-0022 — a `tool_shape` rule *points at* an E2 `SurfaceFamily` variant and ships its evidence; it never inlines a surface); the `Layout`/slot admission invariants, `render` execution and the demotion-wrapper *mechanics* (**WS-D1** — the profile *owns* the layout data and `role_map`; D1 *executes* them); compaction operations, triggers and summariser variants (**WS-D2** — the profile owns only the reminder surface and the summary's rendered role via `role_map`); the wire codec, `WireDialect` documents, retries, usage emission (**WS-C1** — the gateway is model-blind; dialect-side textual rules are not profile rules, CF-251 accepted); routing, fallback and the compatibility guard (**WS-C2** — it *reads* `selector`, `capabilities`, `expiry.status`, `successor_ref`); the assumption-debt *manager* — dashboards, owner nudging, fleet-level expiry policy (**WS-I6**, C4 — this dossier fixes the records, events and operations the manager consumes); judge-validator profiles for oracle roles (**WS-G3/I2**, OQ-059); the Hosting ABI's capability declaration for hosted participants (**WS-J6** — the same declare/probe/DRIFT shape, different object); every language, runtime or library choice (ADR-0050 §8).

## 2. Key questions

1. (doc 3 §5, verbatim) Design model profiles as first-class, versioned, testable, expirable components that the A4 compiler consumes: profile contents (prompt layout, tool shape preferences, error formats, compaction preferences, interaction modes, context limits, caching hints), profile tests (compliance measurement, I2), expiry/revalidation (assumption debt, I6), profile discovery/selection (C2), and the LCD-trap tests.

3. (phase-1 §6.9, binding) C3 designs the rule inventory *inside* ADR-0020; every conditioned rule carries an assumption-debt record; every "X beats baseline" is a `ComparisonReport` with `benefit_kind` and `budget_match.status`.
4. (OQ-071, inherited) Who runs `probe_profile`, when, where `ConformanceRecord`s live, and does DRIFT block compilation or annotate it?
5. (OQ-064, inherited) How are profile-owned prompt templates counted in the opacity report?
6. (OQ-104, inherited, profile side) What does `role_map` look like for providers with two to five roles; are demotion wrappers profile-owned `Text` leaves with expiry?
7. (added) What is the *minimal* signal that a profile's assumptions have been invalidated by a model change when providers change behaviour behind a stable id — and can the runtime observe it at all?
8. (added) How does a rule prove it still earns its place — what is the shape of a removal test that does not fall into the unmatched-budget trap?
9. (added) When more than one model serves a run (summariser, judge, subagent, router fallback), how many profiles are bound and how are they keyed?
10. (added) What must never be resolvable "by default" — when the registry has no profile for a served model, what happens?

## 4. Findings

### 4a. Mechanism evidence (a failure mode exists / an architecture is implementable)

**F1 — The same per-model knowledge exists in three maturity forms across the audit, and the migration direction is uniformly toward data with a declared selector.** codex keeps it as per-slug rows (`models.json`) but still has a literal `match slug` in `model_info.rs` L188 and a `starts_with` in the TUI; gemini-cli keeps per-family full manifests as data and resolves family by a regex in code *while* a flag-gated path already reads `family` from a data record (`config/models.ts` L440–447); OpenHands keeps selectors as ordered substring lists in code; opencode keeps everything as branches. **Implication:** ADR-0020's option 4 (profile = data with a declared selector) is where the field is heading; the design question left is *the selector grammar* — every audited selector is a substring/regex over an id string, which is exactly what T-LCD-01 forbids in the IR and what §6.3 replaces with a closed pattern grammar evaluated by the compiler, not by code that can grow another `includes`.

**F2 — Profile rules are non-monotone across models, so a rule is never a default; it is a hypothesis with a scope.** Tier A: format performance "only weakly correlates between models" (S-459); tool names cut misalignment on small models by 80% (S-177); namespacing effects "varied by model" (S-037). Source: gemini-cli ships two full manifests that differ only in descriptions (S-119 `model-family-sets`); codex's reminder threshold and templates are per slug. **Implication (§6.2):** every rule carries a *scope* (`selector` of the profile that owns it) and a *hypothesis*; a rule copied from one family to another is a new rule with a new debt record, and the Lab metric of interest is the model × rule interaction (T-LCD-09), which is why removal tests are paired per model (§6.6).

**F3 — A profile's assumptions are invalidated by changes the runtime cannot see in the model id; the only honest expiry signals are observables.** Behaviour of the "same" service changed substantially within three months, including formatting compliance (S-460); production teams report the inverse — the model improved and the workaround became dead weight (S-047, S-049). codex's answer is a provider-supplied `comp_hash` whose change forces compaction under the previous model *before* the new one samples (`turn.rs` L1278–1300) — the only audited system that treats "the model changed under me" as an event with a handler. WS-C1 supplies `served_model`, `snapshot_id?`, discovery claims and a *distributional* fingerprint (ADR-WS-C1-3 proposed). **Implication (§6.5):** `expiry_condition = model_version_change` is evaluated over four observables — selector no longer matching any listed model, `served_model ≠ requested`, a changed provider compatibility token, a fingerprint DRIFT — never over a hand-edited version string; and a compatibility-token change is a *re-lowering trigger*, not only an expiry trigger (codex precedent; CF sidecar to WS-C1/A4).

**F4 — Validity, conformance and compliance are three different failures of one rule, and the audit tests at most the first.** gemini-cli's snapshot matrix (S-119) tests that the *compiled surface* is what the author intended per model — validity; codex validates reminder parameters (`TokenBudgetConfig::validate`) — validity; no audited system probes whether the served model *has* the capability a rule assumes (conformance: does a dotted name round-trip, does strict mode accept `anyOf`, is the reasoning signature replayable), and none measures whether the model *followed* the rendered rule (compliance: did the reminder cause a `notes` write before `new_context`?). S-088 (`provisional (mech)`) supplies the vocabulary; ADR-0014 fixes the chain `delivered → activated → followed`. **Implication (§6.4):** the four ADR-0020 suites are concretised as three questions with three owners: *is the profile well-formed and does it compile to what its author meant* (static + golden, compiler, C0/Stage 3); *does the model have what the profile declares* (probes, gateway-executed, charged `instrument`, C0/Stage 3 minimal, C1 full); *does the model do what the rule renders* (compliance metrics per rule, Lab, class-scoped, native only). A rule that is valid, conforms and is not followed is *exactly* the dead weight T-LCD-05 is for.

**F5 — Removal tests are the point of the whole discipline and they are budget-sensitive in a way naive keep-rate testing is not.** Cursor evaluates by keep-rate on whole harness variants (S-049); item-level regressions hide inside aggregate gains (S-461, `provisional`): a rule's removal may improve the mean while breaking a reliable subset. ADR-0046 already requires paired, matched-budget comparison with `benefit_kind`; ADR-0045 requires distributions and per-task `(c, n)`. **Implication (§6.6):** the removal test of rule R is a pre-registered two-arm `Design` — profile P vs `P − R` (one `relower` away, ADR-0020 §4) — under `MatchSpec{mode: matched_cap}` on the same model snapshot and seeds, with an *equivalence* verdict (pre-registered margin, two one-sided tests) reported as `ComparisonReport{benefit_kind: artifact_benefit, budget_match.status}` and a per-item reliability table; "retire" requires no reliable regression on any headline dimension, not merely a non-negative mean.

**F6 — Profiles are bound per model role, not per run.** D2 binds a `summarizer_profile`; G3 judges carry a `ProfileRef` (ADR-0047); F3 subagents may bind a different model; C2 fallback re-lowers; ADR-0045 keys results by "model snapshot(s) with roles"; gemini-cli binds a per-model compression alias (`chat-compression-*`). **Implication (§6.3):** a run manifest carries a `profile_binding: map<ModelRole, ProfileRef>` and every `model.call.requested` carries the `profile_ref` for *its* role (WS-B1 payload already has `model_ref.profile_ref`); `configuration_id` includes the primary role's profile `semantic_id` and the other roles' profiles are recorded coordinates (proposal to WS-A5/J3, §8).

**F7 — Transcript-rendering knowledge is capability-shaped, not rule-shaped, when it is a constraint of the model/API; it is rule-shaped only when the harness *chooses*.** pi declares `requiresToolResultName`, `requiresAssistantAfterToolResult`, `requiresThinkingAsText`, `allowEmptySignature` as `compat` flags (S-113); opencode implements the same as branches inside `normalizeMessages`. **Implication (§6.2):** the `transcript_render` kind carries only *choices* (image-downgrade placeholder text, stale-signature policy `drop | placeholder`, tool-result naming template, reasoning-summary inclusion); hard provider requirements live in `capabilities` and the compiler derives the mandatory renderer steps from them with `deriver = kernel` and *no debt record needed* — a constraint is not a hypothesis. This keeps the debt ledger honest (a record per real assumption) and answers the "bureaucracy" objection in §5.

## 5. Disconfirming evidence & negative results

**Against a closed rule inventory (R1).** pi's flag set is ~45 and growing; opencode's `transform.ts` has 83 substring tests; a twelve-kind enum will meet a thirteenth need within a model generation and the `ext` block becomes the new `transform.ts`. *Why this does not overturn:* F7 shows that a large share of what looks like "rules" in the audit are *capability constraints* (`requiresAssistantAfterToolResult`) that belong in `capabilities` and are derived by the kernel without a debt record; the rule kinds are the *choices*, and twelve kinds cover every choice in the 48 codex keys and both gemini manifests (§6.2 cross-check). The `ext` block is typed, owner-prefixed, debt-recorded and *metered* (`profile.ext_field_count` class-scoped metric), and its growth is a scheduled input to the next `ProfileRuleInventory/2` ADR — exactly the "observable escape hatch" ADR-0020 §5 ratified. Residual risk recorded (RK-02 lineage), re-checked at Phase 3 by WS-J2.

**Against probes at all (R2).** Probes cost money, are noisy (80 distinct temperature-0 outputs in 1,000 samples — S-441), and cannot prevent a provider change mid-experiment; a `DRIFT` verdict is information, not protection. *Why this does not overturn:* the probe suite is scoped to *capability* questions with deterministic detectors (does a strict schema with `anyOf` get rejected; does a namespaced name round-trip; does a replayed signature get accepted) — not to behaviour — so the noise argument applies only to the fingerprint probe, which WS-C1 already made distributional; probes run at registry publish and experiment boundaries, charged `instrument`, never per call; and DRIFT *does* protect in one place: a required-capability DRIFT refuses compilation without recorded intent (§6.5, answering OQ-071/OQ-293), so a run cannot silently assume a capability the model just lost.

**Against per-rule compliance measurement (R3).** Most rules have no deterministic `followed` detector (a description template "followed"?), so compliance collapses to judged metrics with all of ADR-0047's costs; and rules interact — removing one changes compliance of others. *Why this does not overturn:* ADR-0014 already types compliance per artifact kind with `activation_observable` and `detector ∈ {deterministic, judged}`; this dossier declares, per rule kind, which detector class is *admissible* (§6.4 table) and reports `n/a{no_detector}` otherwise — never a proxy; interaction is handled the way the Lab handles every factor (T-LCD-09): removal tests are single-rule arms, and profile-level tests compare whole chains. The alternative — no compliance measurement — is the status quo where "dead weight" is found by reading (S-047).

**Against expiry automation (R4).** Expiry conditions will fire constantly under monthly provider churn; an `expiring` profile that blocks nothing is a warning nobody reads, and one that blocks everything stops the Lab. *Why this does not overturn:* the state machine (§6.5) makes only two transitions consequential — `expired` requires recorded intent to compile, `retired` requires a passed removal test — and both are ledger events with `causes[]`, so the Lab can stratify runs by profile status like any other DRIFT (ADR-0013 semantics); `expiring` is a scheduling signal for WS-I6, not a gate. The honest failure mode is the *opposite* one: without automation, codex's `retirement_at` is enforced by hand and Cursor's guardrails are "mostly long gone" by memory.

**Against refusing unknown models (R5).** codex, opencode, goose and OpenHands all *default* when the model is unknown; refusing makes the runtime unusable on day one of a new release. *Why this does not overturn:* the refusal is at `link`, where a definition may bind an explicit `fallback_profile` whose own debt record says "this model is unprofiled" — codex's `used_fallback_model_metadata: true` made explicit and expiring; what is forbidden is a *silent* default that lets an unprofiled model inherit another model's rules and then attributes the run to a profile it never had (ADR-0036 `configuration_id` would lie).

**Against the `profile_prose` bucket (R6).** Counting profile templates as opacity punishes the most faithful profiles (a Codex-class profile carries a 21,261-character template) and will push authors to hide prose in `description_template` slots. *Why this does not overturn:* the bucket is *reported*, not gated (ADR-0019 AC-12 already says "reported, not rejected"); its purpose is to keep the harness-opacity number honest by separating it from profile opacity, and to make template decomposition into typed sections a measurable improvement. Slot-hiding is caught because every `Text` leaf is counted wherever it lives.

**Negative results (audit).** (N1) No audited system probes; (N2) none records profile status; (N3) OpenHarness has no per-model branches at all — single-family harnesses do not need this component, which bounds conditionality; (N4) the WS-C1 dossier lists three proposed ADR files and a sidecar that are not present in the tree at the time of writing — this dossier consumes WS-C1's *dossier text* (`seed_honoured`, `substitution_allowed`, `usage_mapping` custody, `served_model`, fingerprint) and flags the persistence gap for synthesis (§8).

### 6.3 Profile chains, selection and binding (for WS-C2, WS-A5, WS-J3)

- **Chain resolution.** `resolve_profile` evaluates every registered profile's `Selector` against `model_ref{provider_api_family, model_family, provider_model_id, served_model?}`; matches are ordered by `(precedence, specificity of Pattern: exact > range > prefix > any)`; ties → `AmbiguousSelector` (refusal, never "last wins" as in OpenHands). The chain is the `extends` path from the leaf upward; a leaf may not skip a base its `extends` names. Per-field merge policy across the chain follows ADR-0024's layered composition: `override` (default for rule params), `append` (`reserved_names`, `recovery_table`, `positions`), `forbid_override` (`capabilities.context_window` below a base's declared value is `capability_contradiction`).
- **No silent default.** `NoProfile` at `link` is an error unless the definition's `profile_binding` names a `fallback_profile` (a real profile whose debt record's hypothesis is "unprofiled model"; `status` may never be `active` beyond `expiry_condition = date`); the run manifest then records `profile_binding.fallback_used = true` and the Lab stratifies on it.
- **Per-role binding (F6).** `AgentProcess.native.profile` (ADR-0016) is read as the *primary* role's binding; the run manifest carries `profile_binding: map<ModelRole ∈ {primary, summarizer, judge, subagent(class), shim_interpreter}, ProfileRef>`; every `model.call.requested` stamps its role's `profile_ref`; `configuration_id` takes the primary profile's `semantic_id` and records the others as coordinates (proposal to WS-A5/J3, §8).
- **Retirement and succession.** When `retirement_at` passes, the profile transitions to `expiring` (§6.5); C2's compatibility guard may reroute to `successor_ref` only if the successor is `active | expiring` and the transcript re-lowers within the declared loss bound (C2 G-3); the reroute is `model.rerouted{reason: policy}` plus `model.surface.relowered`.

### 6.4 Profile test contract: validity · conformance · compliance

`ProfileTestReport{profile_hash, schema_version, validity: {V1..V9: pass | fail{diagnostics[]}}, golden: {surfaces: map<(capability semantic_id, surface_id) → ContentAddress>, layout_hash, renderer_spec_hash}, equivalence: map<surface_id → EquivalenceEvidence>, probes: ConformanceRecord[], compliance: [{rule_id, metric_ref, design_ref, last_report_ref?}], produced_at, producer_version}` — stored in the registry beside the profile (WS-J2), referenced from every bundle compiled under the profile (`CompiledBundle.diagnostics` carries `profile_test_report_ref`).

**Validity suite (compiler-only; C0/Stage 3 for V1–V6, V9; V7/V8 with E2 at Stage 3):** V1 schema validity incl. per-kind constraints (table §6.2); V2 owned-field discipline — compile the Stage-0 fixture definition under the profile and under the **null profile** (kernel-defined: reserved slots only, `native_fc`, identity naming, no templates); `diff ⊆ owned_fields` (T-LCD-01); V3 debt completeness on every rule and on the profile; V4 capability consistency — no rule assumes a capability declared `unsupported` (e.g. `caching_markers` with `cache_control_convention = none`); V5 **golden surfaces** — every compiled tool surface, the layout and the renderer spec match the content addresses recorded at profile publish (gemini-cli snapshot precedent; a mismatch after a compiler upgrade is a compiler regression, after a profile edit a review item); V6 determinism — two compiler implementations/hosts agree on `profile_hash` and on every golden address; V7 equivalence linkage — every `tool_shape` variant carries E1–E3/E7 `pass` (E4 for `edit_file`/`execute`/`read_file`); V8 error-format E5 — surjective and pairwise-distinguishable renderings over capability and surface failure classes; V9 role placement — `role_map` monotone, wrappers never promote, reserved slots present.

**Conformance suite (`probe_profile`; executed by the gateway `probe` operation, charged `instrument`; C0/Stage 3 minimal set, C1/Stage 5 full):** `ProbeSpec{capability, kind ∈ {schema_accept, name_roundtrip, id_roundtrip, signature_replay, parallel_calls, developer_role, image_input, context_window_edge, max_output_edge, strict_keyword(kw), cache_marker_accept, seed_repeat}, fixture_ref, samples, budget, verdict_rule}`; each yields `ConformanceRecord{profile_version, capability, declared, probed, verdict ∈ {SUPPORTED, UNSUPPORTED, PARTIAL, NOT_APPLICABLE, UNKNOWN, SKIPPED, DRIFT}, probe_run_id}` (ontology *observed conformance*). Detectors are deterministic (accepted/rejected, round-tripped/not) except `seed_repeat`, which is the C1 distributional fingerprint. Cadence and ownership (OQ-071 answer): at profile publish (registry, C3), at every experiment open/close (Lab, J3, alongside the fingerprint), and on any `model_version_change` observable (I6 scheduler). Storage: records are registry rows keyed by `(profile_hash, ModelSnapshotRecord)` and every probe call is an ordinary ledger run.

**Compliance suite (Lab; class-scoped `applies_to_classes = {native}`, `requires_observability ⊇ {ledger}`; `n/a` for hosted):** per rule with `compliance.detector_class ≠ none`, a `MetricDeclaration` `profile.rule.followed_rate{rule_id}` computed over `context.artefact.delivered → activated → verification.artefact.followed` (ADR-0014) with the rule's `followed_predicate_ref`; rules without a detector report `n/a{no_detector}`; judged detectors are `Validator{kind: judge}` with calibration and `charged_to = instrument` (ADR-0047). Every compliance claim is evaluated on a **held-out** task split not used when the rule was authored (S-037's warning against overfitting descriptions), pre-registered in the rule's `compliance_design_refs`.

### 6.5 Expiry and revalidation contract (for WS-I6, WS-C2, WS-J3)

- **Status state machine (per rule and per profile; ADR-0020 §7 made operational):** `active → expiring` on any trigger; `expiring → active` on `revalidated{evidence_ref}` (a passed probe/compliance report newer than the trigger); `expiring | active → expired` on `probe_failure` for a capability the rule depends on, on selector matching no listed model for `grace_period`, or on `retirement_at` passing; `expired → retired` only by ADR after a passed removal test; `expired → active` only by a new evidence refresh **and** a probe pass. A profile's status is the *worst* of its rules' (`active` while all rules `active`), as ratified.
- **Triggers are observables.** `model_version_change` ⇐ (i) `served_model ≠ requested` on ≥ 1 call for this binding (C1), (ii) `capabilities.compatibility_token` differs from the discovery claim (C1 `discover`), (iii) fingerprint DRIFT (C1), (iv) `resolve_profile` matches no model in the listing; `date` ⇐ `now ≥ expiry.until`; `probe_failure` ⇐ a `ConformanceRecord{verdict: DRIFT | UNSUPPORTED}` for a capability in the rule's dependency set; `evidence_refresh_due` ⇐ `max(age(evidence_refs)) > evidence_max_age`; `experiment_ref` ⇐ a `ComparisonReport` for the rule's design shows the removal arm non-inferior. A compatibility-token change is additionally a **re-lowering trigger**: the runtime treats the next call as `relower(bundle, same_profile)` with `model.surface.relowered{reason: compatibility_token_changed}` (codex `comp_hash_changed` precedent, generalised) — proposed to WS-A4/B1 (§8).
- **Events (WS-B1 payload proposal, `model` category):** `model.profile.status.changed{profile_ref, rule_id?, from, to, trigger, evidence_ref, causes[]}`; `model.profile.probed{profile_ref, probe_run_id, records[]}`; compile under `expired` appends `model.profile.expired_used{profile_ref, intent_ref}` to the run.
- **DRIFT policy (OQ-071; OQ-293):** DRIFT/UNSUPPORTED on a capability in the *dependency set of any rule in the bound chain* ⇒ `link` refuses without recorded intent (same mechanism as `expired`); DRIFT elsewhere ⇒ annotate the run/arm (ADR-0013 stratification), never refuse. C2's guard uses the same predicate.
- **Removal test (T-LCD-05 "retire rule R"; F5):** `RemovalTest{rule_id, design_ref}` where the `Design` is two arms `P` and `P − R` (via `retire_rule`), same model snapshot, same seeds, `MatchSpec{mode: matched_cap}`, `eval_budget` equal; verdict = non-inferiority of `P − R` on every headline metric within a pre-registered margin (two one-sided tests on the paired distribution) **and** no reliable per-item regression class above a pre-registered share (S-461 mechanism); reported as `ComparisonReport{benefit_kind: artifact_benefit, budget_match.status}`. Passing ⇒ `retired` by ADR; failing ⇒ `revalidated` with the report as new evidence.
- **Reflexivity.** The Profile Compiler, every `WireDialect` (C1) and the null profile's kernel derivations carry records; the compiler's own removal test is "compile everything under the null profile and pass Stage 3" — if it passes, the component has no reason to exist, which is the honest end state ADR-0020 §(d) anticipates.

### 6.6 Opacity accounting (OQ-064 answer)

`OpacityReport` gains a third bucket: `profile_prose = tokens(Text leaves owned by the bound profile chain rendered into the surface: description templates, section templates, demotion wrappers, placeholder texts, reminder/guidance/fallback templates)`; `opacity_ratio` (harness) excludes it; `profile_opacity_ratio = profile_prose / tokens(surface)` is reported per profile in the bundle and as a registry metric per profile hash. Leaves are individually ablatable (WS-I2 `ablate`), so a profile author can measure each template's compliance benefit.

### 6.7 Acceptance-criteria sketch

- **AC-C3-1 No model literal (T-LCD-01).** A static gate over the compiler and runtime sources finds no model-family/version literal and no string test on a model id outside the selector-grammar evaluator; the Stage-0 fixture under the two ADR-0020 minimal profiles differs only in owned fields (V2); opencode's `provider(model)` shape is a failing fixture. (C0/Stage 1)
- **AC-C3-2 Selector grammar.** `resolve_profile` over a fixture registry yields the expected chain for exact/prefix/range patterns, refuses `AmbiguousSelector` on equal precedence, refuses `NoProfile` without a fallback binding, and records `fallback_used`. (C0/Stage 3)
- **AC-C3-3 Golden surfaces (V5).** Every compiled tool surface/layout/renderer spec for each registered profile matches its recorded content address; a description edit changes the profile hash and the golden address and *no* HIR `semantic_id` (T-LCD-10). (C0/Stage 3)
- **AC-C3-4 Capability consistency (V4) and derived constraints.** A rule assuming an `unsupported` capability fails `link`; a `*_required` capability yields a kernel-derived renderer step without a debt record; changing the capability changes the rendered transcript. (C0/Stage 3)
- **AC-C3-5 Probe suite.** On a fake gateway with scripted acceptance/rejection, each `ProbeSpec` kind yields the expected verdict; DRIFT on a dependency capability makes `link` refuse without intent and pass with intent; every probe call is charged `instrument`. (C0/Stage 3 minimal; C1/Stage 5 full)
- **AC-C3-6 Compliance metrics (T-LCD-13/-15).** For the reference harness under both minimal profiles, `profile.rule.followed_rate` is computed per rule with a detector, `n/a{no_detector}` otherwise, `n/a{class}` for hosted rows. (C0/Stage 3)
- **AC-C3-7 Expiry state machine.** Injected observables (served-model drift, token change, date, probe DRIFT) produce exactly the transitions of §6.5 as ledger events; compiling under `expired` without intent is refused; with intent it is recorded. (C1/Stage 5; event schema C0/Stage 1)
- **AC-C3-8 Removal test (T-LCD-05/-14).** `retire_rule` yields a valid arm; the engine refuses the design without `MatchSpec`; a scripted fixture in which removal regresses a reliable subset while improving the mean yields *fail*. (C1/Stage 5; contract Stage 3)
- **AC-C3-9 Re-lowering on token change.** A discovery claim with a changed compatibility token yields `model.surface.relowered{reason: compatibility_token_changed}` before the next call. (C1/Stage 5)
- **AC-C3-10 Opacity buckets.** The bundle reports `profile_prose` separately; a profile whose layout is one opaque template is reported, not rejected; ablating one template leaf changes only that bucket. (C0/Stage 3)
- **AC-C3-11 Per-role binding.** A run with a summariser profile different from the primary records both in the manifest, stamps each call's `profile_ref`, and the results row carries the primary in `configuration_id` and the rest as coordinates. (C1/Stage 5)
- **AC-C3-12 Out-of-process (T-LCD-12).** The Profile Compiler runs as a separate process exchanging canonical documents and the suite is unchanged. (C0/Stage 3)

## 10. Confidence

**High** for the rule inventory's *coverage* and for the compiler contract: the twelve kinds absorb every model-facing key in codex's 48-key rows and both gemini manifests, the capability/rule split (F7) is read directly from pi's typed flags, and the contract composes with ADR-0019/0020/0022 without amendment. **High** for the validity suite: every check has a production precedent (gemini snapshots, codex validation) or is a ratified invariant restated executably. **Medium** for the conformance/probe suite and the expiry state machine: the mechanism (behaviour changes under a stable id; compatibility token as an event) is Tier A/B plus one production precedent, but probe parameters and trigger thresholds are unvalidated (OQ-300/-06) and no audited system runs anything like it (`novel as integrated`). **Medium** for compliance-per-rule: the chain is ratified (ADR-0014) but detectors exist only for a subset of kinds and judged detectors inherit ADR-0047's costs. **Low-to-medium** for anything quantitative from 2026 preprints (S-461/-04 — `provisional`, mechanism only).
