# WS-E4 — Protocol edges: MCP (client + server), A2A, ACP — where each boundary belongs

**Track:** E · **Phase:** 2 · **Tier(s) fed:** C1 (with a C0/Stage-3 MCP slice per ADR-0021/ADR-0048 and C2 A2A/hosting slices) · **Status:** dossier-written
**Owner agent:** WS-E4 research subagent (Fable 5.1) · **Date:** 2026-09-10
**Feeds spec section(s):** §7.2 #5 (tools & action plane: R-2.5.4), #7 (surfaces: MCP server R-2.11.3, SDK R-2.11.4), #6 (hosting), #8 (cross-cutting: versioning/extensibility) · **Scope register items:** R-2.5.4 (primary); touches R-2.11.3, R-2.11.4, R-2.10.6

## 1. Scope & boundary

This workstream decides **where the three standardized edges of a harness attach to the HarnessHarness architecture** — which Harness IR (HIR) entity, which run-ledger event family and which component owns each protocol concept — and what the compiler must emit so that a native participant can *speak* each protocol without any protocol type leaking into the IR (T-LCD-06). It covers: the MCP edge in both directions (HarnessHarness as MCP **client** consuming foreign tool servers; HarnessHarness as MCP **server** exposing compiled tool surfaces and Lab operations — the WS-K3 surface); the ACP edge in both directions (a native harness exposed as an ACP **agent** — the ADR-0005 "act as a participant" obligation; foreign ACP agents attached as hosted participants through the session-ABI hosting mechanism); the A2A edge (agent-to-agent tasks as delegation to a remote `OpaqueProcess`, and HarnessHarness as an A2A server); protocol **version and capability negotiation** across all three; and the **trust posture** at every edge, applied from ADR-0033/0034/0035 and the WS-H5 extension-trust record.

It **does not decide** (neighbours named): the lowering/lifting *mechanism* and the minimum carried set (ratified ADR-0021 — consumed and extended here, one amendment proposed); the tool registry and typed capability metadata (WS-E1 — its dossier was not yet available at writing; assumptions are flagged in §8); the tool-interface compiler and composite surfaces (WS-E2, ADR-0022); tool discovery and deferred loading (WS-E3 — this dossier fixes only what MCP's statelessness forces on it); sandboxed execution of MCP server processes (WS-E5/B5 — this dossier declares isolation classes only by reference to WS-H5 §6.5); the Hosting ABI's full depth (WS-J6, Phase 3 — this dossier supplies the *first proposal* of the ACP verb reuse it asked for); the MCP-server product surface (WS-K3) and SDK (WS-K4), for which this dossier supplies the documents they consume; credentials and OAuth token custody (WS-H3); the `_meta` prefix and A2A extension URI (WS-L6, OQ-068).

## 4. Findings

### 4a. Mechanism evidence (a failure mode exists / an architecture is implementable)

**F1 — There is exactly one tool-supply channel across all three edges, and it is MCP.** ACP v2 removed the client-side `fs/*` and `terminal/*` methods and its migration guide instructs clients to "expose Client-side tools through MCP servers passed in `mcpServers`" (S-035 `docs/protocol/v2/migration.mdx` L611–616, L741). Omnigent already does this for ACP v1 agents: it injects the Lab's own tools into a hosted goose/qwen session by adding a localhost MCP relay to `session/new.mcpServers` (S-118 `inner/_acp_omnigent_mcp.py` L1–20). A2A has no tool concept at all (S-180 `a2a.proto` — no message mentions tools; `docs/topics/a2a-and-mcp.md` L7–45 assigns tools to MCP by design). Every audited harness consumes tools through an MCP client (8/11 per S-166) and none through a second protocol. *Implication:* the compiler needs exactly **one** tool-document kind (the MCP tool surface, already C0/Stage 3 per ADR-0021) and the tool registry exactly **one** foreign-tool lifter; the ACP and A2A edges *reference* tool documents rather than define tools (§6.1 decision D1).

**F2 — MCP 2026-07-28 is stateless and session-less, which changes what a server can do per run.** The revision removes protocol-level sessions and the `initialize` handshake; every request carries `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` in `_meta`; servers "MUST NOT infer capabilities from prior requests" (S-153 `schema.ts` L63–118); list endpoints "no longer vary per-connection" and cross-call state must use "explicit, server-minted handles passed as ordinary tool arguments" (changelog §1, SEP-2567); `tools/list` SHOULD be deterministically ordered and MUST carry `ttlMs`/`cacheScope` (SEP-2549). *Failure mode:* a K3 server that narrows its tool list per run (deferred loading, WS-E3) or per client identity violates SEP-2567 and breaks client-side caching; ADR-0021 decision 5's phrase "`listChanged` when run-time selection changes" cannot be implemented as written under this revision (CF-206). *Implementable alternative:* publish the full compiled catalogue per bundle (identical across connections), fire `listChanged` only on bundle change, and carry run identity as a server-minted handle argument.

**F3 — Server-initiated requests are gone from MCP; the human-in-the-loop points are now typed results.** Elicitation, sampling and roots became multi-round-trip results: a `tools/call` may return `resultType: "input_required"` with `inputRequests` and an opaque `requestState` the client MUST echo unmodified; servers MUST treat `requestState` as attacker-controlled and integrity-protect it if it influences authorization (S-153 `patterns/mrtr.mdx` L130, L232–257). Sampling and roots are deprecated (SEP-2577) with a twelve-month window. *Implication for the effect lifecycle:* an `input_required` result is neither `observed` nor `failed`; it is a **paused effect awaiting a human/kernel decision** — the same shape as ADR-0030's `prepared` → decision gap and ACP's `requires_action`. The mapping (§6.2) routes it to `control.decision{kind: ask}` plus a `message_human` effect, never to a permission grant (an elicited answer is `principal`-authored content, not an endorsement).

**F4 — Every protocol carries capability declarations with "omitted = unsupported" wire semantics, and every audited host re-interprets that at its own layer.** ACP: "MUST treat all capabilities omitted … as UNSUPPORTED" (S-035 `initialization.mdx` L80); MCP: per-request `clientCapabilities`, `MissingRequiredClientCapabilityError` −32021 (S-153 L513); A2A: `AgentCapabilities{streaming?, push_notifications?, extensions[]}` with `AgentExtension.required` (S-180 L412–435). Hosts then *probe or override*: OpenHands checks `agent_name_patterns` and tolerates rejected `set_session_model` calls (S-110 `acp_agent.py` L550–660, L800–885); Omnigent keeps a per-harness capability table and a DRIFT verdict (WS-A1 F3); goose gates behaviour on `_meta`-advertised client capabilities (`extract_client_capabilities_meta`, S-112 `server.rs` L466). CF-027's ruling (wire UNSUPPORTED → analysis `unknown`) is therefore the right general rule for all three protocols and is applied uniformly in §6.4.

**F5 — Trust never flows through protocol metadata in any audited implementation, but each draws the line differently.** MCP says annotations "are hints … Clients should never make tool use decisions based on `ToolAnnotations` received from untrusted servers" and that a human SHOULD always be able to deny (S-153 L1912–1920; `server/tools.mdx` L30–45, L305). Codex uses `destructive_hint`/`open_world_hint` for policy only on its first-party apps server and uses `read_only_hint` only to *add* a host-owned context (S-107 `mcp_tool_call.rs` L204–222; `trusted_access.rs` L55–62); gemini-cli reads `readOnlyHint` but its confirmation short-circuit is `trustedFolder ∧ server.trust`, a *location + configuration* fact (S-119 `mcp-tool.ts` L207–216) — the pattern WS-H5 L1 forbids; goose strips server-supplied `_meta` before re-attaching a trusted key (S-112 `extension_manager.rs` L349–392); OpenHands auto-approves every ACP permission request (S-110 L1579–1596); Omnigent routes ACP permission requests through its own policy plus consent (S-118 `acp_executor.py` L775–800, L874–950). *Implication:* the kernel-side reference monitor is the only consistent place for the decision at every edge; protocol hints, ACP option kinds, A2A `required` flags and OAuth scopes are **claims** (`declared_claims` in WS-H5's trust record), and the ADR-0031 rule `effective_risk_class = max_by_danger(kernel_assessed, projected(declared))` already gives them the only influence they may have (raising, never lowering).

**F6 — The implementation population lags the specifications by one major version on both protocols.** Every audited ACP implementation is v1 (goose `ProtocolVersion::V1`, gemini `protocolVersion: acp.PROTOCOL_VERSION` with `session/set_mode`, opencode `protocolVersion: 1`, Omnigent/OpenHands drive v1 methods), while the spec repository serves v2 (2.0.0-alpha.3, 2026-08-20) with removals (`session/load`, modes, `tool_call`, client fs/terminal). MCP clients carry an explicit era switch: goose `preferred_versions: [V_2026_07_28], legacy_version: V_2025_11_25` (S-112 `mcp_client.rs` L706–722); codex `McpProtocolMode::{Legacy (2025-06-18), V20260728}` with an opt-in marker for stdio (S-107 `protocol_mode.rs` L9–47); the spec itself documents a compatibility matrix where modern-client/legacy-server "fails" unless `server/discover` is sent first (S-153 `versioning.mdx` L136–167). *Implication:* version negotiation is not a Stage-4 nicety; the ACP session artefact must ship a **v1 compatibility profile** with a declared loss report or it cannot be driven by any host that exists today (CF-207), and the MCP client must implement both eras with a deterministic probe (§6.4).

**F7 — ACP is the closest analogue of the session-ABI hosting mechanism, and its stable v2 surface is *smaller* than the verb set CF-023 assumed.** ACP v2 has no `steer` (goose supplies `_goose/unstable/session/steer`), no `account` request (`usage_update` is a notification with `used/size/cost`), `fork` and `compaction_update` are unstable, and there are no subagent or model-call events at all (S-035 schema unions; S-118's `SubAgent*` events come from Omnigent's own executor, not ACP). Conversely ACP v2 provides things the WS-A1 §6.4 minimum set lacks: `plan_update`, `config_option_update` (model/mode/thought-level as *configuration-level* coordinates the Lab can set), inclusive replay cursors, and `session/request_permission` with typed option kinds. *Implication:* the Hosting ABI's session-ABI mechanism should adopt ACP v2's core verbs and update kinds verbatim as its **baseline**, mark `steer/account/fork/compaction/subagents` as capability-declared, and document that session-ABI hosting yields `observability_level = {events, end_state}` — `model_io` requires interception (OQ-038) — see §6.5.

**F8 — A2A maps to the delegation edge and only to product granularity, but it carries one thing the others do not: a signed, versioned self-description.** `AgentCard{version, capabilities.extensions[], skills[], security_schemes, signatures[JWS]}` plus `AgentInterface{protocol_binding, protocol_version}` (S-180 L336–470); tasks are immutable once terminal and follow-ups open new tasks in the same `contextId` (`life-of-a-task.md` L85–103). The one A2A server in the audit (gemini-cli `packages/a2a-server`) maps tool confirmations to `input-required` and smuggles its typed agent events through `status-update.metadata.coderAgent` (S-119 `agent/task.ts` L279–325, L560–580) — exactly the "profile extension" pattern A2A's own docs describe. *Implication:* export = card from the sealed definition with `version ← bundle_id` and `signatures` as an `Attestation{kind: signature}`; import = `OpaqueProcess` reached over A2A at `product` granularity with the card's signature verified under `TrustRootPolicy` (WS-H5 §6.3); the run-envelope-to-task-state mapping is exhaustive (§6.2).

**F9 — Protocols carry propagation context, not provenance.** MCP reserves unprefixed `traceparent/tracestate/baggage` in `_meta` (S-153 `basic/index.mdx` L421–441); ACP reserves the same three root keys (S-035 `extensibility.mdx`); A2A has `metadata` Structs and a traceability sample extension. None carries authority, validity, effect class or budget natively — which is why ADR-0021's minimum carried set travels in `_meta`/`AgentExtension` and lifts to `unverified` when it comes from a foreign peer. Codex's `ResourceOrigin` checkpoints (S-107 `resource_origin.rs` L24–99) are the only audited case of a harness *recording* per-item origin for tool-supplied content across resume; the ledger's `Origin.tool(server_ref, inner_source?)` (WS-H5 §6.2) generalises it.

### 4b. Performance evidence (benchmark lifts) — each tagged `provisional` if 2026 single-team/preprint

None is load-bearing. S-074/S-166 adoption counts (MCP 8/11, ACP 6/11, skills 9/11) are `provisional (mech)` and internally inconsistent in places (CF-018); they are used only to rank which edge to build first (MCP, then ACP), a decision ADR-0021 already made on other grounds. No source reports a performance effect of protocol choice; the A2A docs' claims about complementarity are positioning, not evidence. MCP's own changelog gives a mechanism rationale (prompt-cache hit rates from deterministic tool order, SEP-2549/changelog minor §3) that is consistent with WS-A4 §5's observation that byte-stable prefixes are performance-relevant; no number is attached.

## 5. Disconfirming evidence & negative results

**Against "MCP is the only tool-supply channel".** Provider tool APIs (native function calling, per profile) are a second, non-protocol channel; codex's app-server and goose's `_goose/unstable/tools/{list,call}` expose tools over a session protocol; A2A "extended skills" can add RPC methods. *Why this does not overturn:* the provider tool API is a *model-facing surface* consumed by the model, not a supply channel between processes (ADR-0021 decision 5 separates it); vendor `_`-methods are per-vendor extensions with no interop and ACP's own migration guide routes tool supply to MCP; A2A extended skills are RPC methods, not callable tools with schemas. The decision is scoped to *standardized cross-process tool supply* and is `high` reversibility (a second lifter can be added by ADR).

**Against building on MCP 2026-07-28 now.** The revision is weeks old at the audit commit; zero audited *servers* were confirmed to serve it; goose and codex clients keep legacy fallbacks; SEP-2567 statelessness is contested precisely by harnesses that want per-session tool lists (deferred loading). *Why this does not overturn:* ADR-0021 already pins target-spec versions into the derivation key so a bump is a recompile plus a loss-report diff; the dual-era client is mandatory (§6.4) so nothing depends on modern servers existing; and statelessness *helps* the instrument — a bundle's tool catalogue becomes content-addressable and identical for every client, which is what T-LCD-10/-11 and prompt-cache determinism want. The residual risk (E3's deferred loading cannot use per-session `tools/list`) is recorded as CF-206 with a mitigation that needs no protocol change.

**Against reusing ACP verbs for the Hosting ABI.** ACP is v2-alpha and in flux (three removals in one major); its stable surface omits steer, subagents, model calls and accounting; every host in the audit runs v1; Zed-centric UX concepts (`plan_update`, `available_commands_update`, terminal display) do not concern a lab. *Why this does not overturn:* ADR-0005 already fixed session-ABI as the first mechanism and CF-023 fixed "same verb shape"; adopting the *stable v2 core* (nine methods, seven update kinds) as the baseline and everything else as declared capabilities is exactly T-LCD-07's "declare, verify, stratify — never intersect"; the observability gap (`model_io`) is documented, not hidden, and interception is the declared upgrade (OQ-038). The alternative — an HarnessHarness-specific session RPC — is non-goal N5 (ADR-0006).

**Against exhaustive lowering tables.** Lowering ledger events to `session/update` is lossy by construction (effect phases → five `ToolCallStatus` values; `stop_reason` → five values; budgets → nothing), and ACP's `_meta` can carry anything, so "loss report" risks being satisfied trivially by stuffing `_meta`. *Why this does not overturn:* the loss report's purpose is to make the *granularity ceiling* computable (ADR-0021 decision 4, T-LCD-15), not to prove losslessness; the table in §6.2 states per event class whether the ACP form is `exact`, `narrowed`, `hint_only` (`_meta` only) or `no_slot`, and the ACP artefact's granularity ceiling is `configuration` (never `component`), which is what ADR-0013 predicts for a hosted view of a native run.

**Against kernel-side decisions at every edge.** Human-in-the-loop UX lives on the *client* side of ACP (the editor renders `request_permission`) and on the *server* side of MCP (`input_required` elicitation), so the kernel is not always where the human is. *Why this does not overturn:* the reference monitor *decides*; the protocol only *transports* the question and the answer. When HarnessHarness is the ACP agent, `request_permission` is the transport for `decider = human`; when it is the ACP client (hosting), the hosted agent's request is a *proposal* evaluated by the kernel's Π before any human is asked (Omnigent precedent); when it is an MCP client, an `input_required` result is a paused effect whose continuation is a kernel decision. In no configuration does a peer's option kind or hint decide.

**Negative results from the audit.** (i) No audited implementation records the negotiated protocol version or the peer's declared capabilities in a durable per-run record; OpenHands comes closest with pinned provider binaries. (ii) No audited ACP host verifies that `state_update{idle}` follows durable persistence — an ACP agent can say "idle" before its own transcript is saved (goose's `ActiveRunDropGuard` cancels on drop but does not sequence durability). (iii) No audited MCP client distinguishes `isError` tool results from protocol errors *in the ledger*; gemini-cli parses `isError` as a string-or-boolean (S-119 `mcp-tool.ts` L249–265), i.e. wire looseness leaks into the observation. (iv) Names remain identity everywhere: every client derives the model-facing name from server + tool name and at least two truncate or mangle it — the T-LCD-10 failure signature.

## 6. Recommendation for the spec

### 6.1 Boundary placement decisions (ADR-0096)

- **D1 — One tool-supply channel.** MCP is the sole standardized channel through which tools cross a process boundary: inbound (foreign MCP servers → `ToolCapability` via the WS-H5 `lift_surface` lifter into the WS-E1 registry, executed by WS-E5 through the reference monitor) and outbound (compiled tool surfaces → the MCP tool-surface document of ADR-0021, served by WS-K3). The ACP edge supplies tools only by *reference* (`session/new.mcpServers[]` ↔ `OpaqueProcess.supplies.tools`); the A2A edge supplies none. The compiler emits one tool-document kind; the registry has one foreign lifter.
- **D2 — ACP is the session boundary (the run-envelope seam).** Outbound: a native harness is exposed as an ACP agent by rendering `proj_ABI(native ledger)` into `session/update` (ADR-0005, ADR-0013 total projection). Inbound: a foreign ACP agent is a hosted participant under `hosting_mechanism = session_abi` (ADR-0018). The WS-L1 §6.5 internal boundary shares the verb *shape* (CF-023) but is a **different binding**: it carries IR-typed events byte-identical to the ledger with unknown fields rejected; the ACP edge carries lowered events with preserved unknowns and a loss report (CF-209).
- **D3 — A2A is the delegation edge.** An A2A peer is an `OpaqueProcess{hosting_mechanism: session_abi, binding: a2a}` reached by `delegated-to` from a native process at `product` granularity; a task is a child run (`control.subagent.spawned{child_run_id}`); permission and budget are enforced kernel-side and only the dimensions the kernel can observe (`spend` where priced, `time.wall_ms`, `network.calls`) are hard; tokens are `reported`-provenance or `n/a`. Inbound A2A (HarnessHarness as A2A server) is the C2 lowering of the run envelope to `TaskState`.
- **D4 — What no protocol covers stays kernel-side, by construction.** Orchestration (control boundary β, WS-F1/F3): no protocol has a decision-point concept; ACP `plan_update` is *observational*. Safety (WS-H1): the reference monitor decides on the kernel side of every edge; hints, option kinds, `required` flags and OAuth scopes are claims that may only raise risk (ADR-0031). Memory (WS-D3/D4): no protocol carries validity/authority; ACP's unstable `compaction_update` is an observation. Budgets (WS-L2/F2): only ACP reports usage; no protocol enforces. Provenance: only via `_meta`/`AgentExtension`, `unverified` from foreign peers (ADR-0021 decision 3, CF-082).
- **D5 — Dependency direction.** Protocol schemas are inputs to `lower_target`/`lift` and to the transport implementations; no HIR entity, ledger event class or component-class contract references a protocol type (T-LCD-06). `ToolKind`, `TaskState`, `StopReason`, `PermissionOptionKind` and `ToolAnnotations` are *projections* of `EffectDomain`, run status, ledger `stop_reason`, kernel decision and `EffectAttributes` respectively; the projection tables live in the compiler's target module, versioned with the target-spec pin.

- **Per-edge `ProtocolBinding` record (all targets, C0/Stage 3 schema):** see §6.4; emitted as a bundle member so the derivation key changes when a target-spec pin changes (ADR-0021 (d)).

### 6.4 Version and capability negotiation; trust at the edges (ADR-0098)

`ProtocolBinding{protocol ∈ {mcp, acp, a2a}, role ∈ {client, server, agent, peer}, spec_pin: {version_label, schema_content_hash}, era ∈ {modern, legacy}, negotiated_version, peer_info: Implementation (claim), capabilities_declared: TypedValue (wire form, preserved), capabilities_observed: map<field, {supported, unsupported, unknown}>, extensions: [prefixed id], transport ∈ {stdio, streamable_http, jsonrpc_http, grpc, custom(uri)}, negotiated_at: EventRef}` — a **runtime record** (not an IR entity) stored in the run manifest and referenced by `lifecycle.run.created`.

Rules: (N1) **probe first, then pin** — MCP clients send `server/discover` before any other request on stdio and select from `supportedVersions`; on `UnsupportedProtocolVersionError`/legacy-era silence the client retries once in legacy mode; ACP clients send `initialize` with the latest supported version and accept a lower one only if it is in the pinned support set; A2A clients read the card's `supported_interfaces` and pick the first interface whose `protocol_version` is pinned. (N2) **No silent fallback:** a version outside the pinned set raises `ProtocolVersionMismatch{requested, supported}` — a typed error, never a warning (the T-LCD-11 stance for wire versions). (N3) **Omitted = unknown at analysis** (CF-027) for all three protocols; wire semantics stay as specified. (N4) **Unknown preservation:** unknown `_meta` keys, `_`-prefixed values and unknown extension ids survive lower→lift byte-for-byte in `ext` (ADR-0015) — the opposite default from the internal boundary contract (CF-209). (N5) **Pins are inputs:** `spec_pin.schema_content_hash` enters the bundle derivation key; bindings are generated from the three schema sources with CI drift checks (ADR-0021 decision 1; OpenHands `check-acp-drift.py` shape). (N6) **Eras expire:** the legacy-era MCP projection and the ACP v1 compatibility profile carry assumption-debt records (T-LCD-05, reflexive) with removal tests keyed to the spec's deprecation windows.

Trust (applies ADR-0033/0034/0035 and WS-H5; no second scheme): (T1) every peer is `unverified` until an attestation verifies under `TrustRootPolicy`; a foreign MCP server is an `ExtensionRecord{kind: mcp_server}` whose surface is pinned and reviewed before any tool is callable; an A2A card's JWS signature is `Attestation{kind: signature}`; an ACP agent binary is pinned by `content` (OpenHands pinned-binary precedent). (T2) `ToolAnnotations`, ACP option kinds, A2A `required`, OAuth scopes and `serverInfo/clientInfo` are `declared_claims`; the reference monitor never reads them, ADR-0031's `projected(declared)` may only raise risk. (T3) Text from any peer (`instructions`, descriptions, `plan_update` content, agent messages, task messages) is `external` at best and renders only under `role_map(external)` (ADR-0034 RP; WS-H5 §6.2). (T4) Approval is per `effect_id` (ADR-0035): an ACP `allow_always` selection or an MCP client-side allowlist is a **policy amendment** that must be ledgered with `approval` basis and is scoped ≤ run unless a principal seals it (OQ-246); adapter-level auto-approve (OpenHands) is inadmissible. (T5) Secrets never cross an edge in payloads: OAuth tokens are mediated by H3; MRTR `requestState` is stored as an opaque blob and echoed, never inspected; `x-mcp-header` mirroring is disabled unless sealed. (T6) Taint: everything a foreign peer contributes carries `taint ∋ extension_id` (WS-H5 L6); an A2A child run's outputs re-enter at `≤ delegate`.

### 6.6 Interface-contract sketch (operations · inputs/outputs · invariants · failure modes; language-neutral)

- `negotiate(edge_spec, peer_locator) → ProtocolBinding | ProtocolVersionMismatch | PeerUnreachable` — probe-first (N1); invariant: `negotiated_version ∈ spec_pin.support_set`; never downgrades below the pinned set.
- `open_edge(binding, isolation: IsolationClass) → EdgeHandle` — for MCP servers and ACP agents spawns the peer under the WS-H5 isolation class (never `in_process` for non-kernel origins); failure: `IsolationUnavailable`, `PinMismatch`, `AttestationRequired`.
- `lift_surface(handle) → SurfaceDocument` (WS-H5 owns) and `check_surface(record, live) → ok | Drift` — invariant: lifted items are `unverified`; names never parsed.
- `call_tool(handle, tool_ref: (server_ref, semantic_id), args, effect_id, attempt_no, idempotency_key) → ToolOutcome{observed(result) | paused(input_required{inputRequests, requestState: blob}) | failed(isError result) | protocol_error | unknown}` — invariants: dispatched only after `action.effect.committed` for non-`read_only` classes (ADR-0030); `paused` never retried without a kernel decision; `protocol_error` and `failed` are distinct ledger outcomes; cancellation of a non-`read_only` call yields `unknown` then `probe`.
- `serve_tools(bundle, transport) → ServerHandle` — invariant: `tools/list` bytes are a pure function of `bundle_id` (SEP-2567 statelessness; AC-E4-2); every `tools/call` becomes a native run step with the caller as `principal`-class only when authenticated as the run's principal, else `delegate`.
- `render_session(run, binding{acp, version}) → stream<session/update> | stream<v1 update>` — total over the ledger classes with a declared lowering; invariant: `idle` after durability; every emitted update carries `_meta.hh.event_id` so `trace_map` is total over emitted updates (T-LCD-11 for events).
- `attach_session(binding{acp}, participant_ref, supplies, budget, policy) → RunId` (hosting, C2) — invariant: the hosted agent's `request_permission` is a proposal evaluated by Π before any human; supplied tools are the Lab's sealed MCP surface.
- `delegate_task(binding{a2a}, goal, budget_slice, permission_attenuated) → child RunId` (C2) — invariant: child budget contained; outputs re-enter at `≤ delegate`; task terminal ⇒ child run finished with the mapped outcome class.
- `edge_loss_report(binding) → LoweringLossReport` — per §6.2 tables; part of the bundle.

### 6.7 Data-model sketch

`ProtocolBinding` (§6.4) · `EdgeHandle{binding, isolation, extension_ref?, opened_at}` · `SurfaceDocument` (WS-H5) · `ToolOutcome` (above) · `EventClassLowering{ledger_class, acp_update_kind | none, loss_class ∈ {exact, narrowed, hint_only, no_slot}, projection_ref}` (the concrete form of WS-B1's "every class declares its lowering") · `ToolKindProjection`, `TaskStateProjection`, `StopReasonProjection` (versioned tables in the target module) · ledger event classes reused (no new classes): `lifecycle.run.*`, `security.permission.*`, `action.tool.*`, `action.effect.*`, `control.decision`, `security.extension.{resolved, loaded, drift}`, `measurement.cost.attributed`; one new payload field proposed on `lifecycle.run.created.manifest`: `protocol_bindings: [ProtocolBinding]` (WS-B1 amendment log).

### 6.8 Acceptance-criteria sketch

- **AC-E4-1 Round trip (T-LCD-11).** For the Stage-0 reference harness under both minimal profiles, `lift(lower(x, mcp)) ∪ loss_report = x`; the MCP loss report lists exactly `{permission enforcement location: no_slot, budgets: no_slot, validators: no_slot}` and nothing else.
- **AC-E4-2 Statelessness (K3).** Two independent MCP clients receive byte-identical `tools/list` for one bundle, in canonical order, with `ttlMs`/`cacheScope` present; a second bundle changes the bytes and fires `listChanged`.
- **AC-E4-3 Hints never decide.** A fixture server declaring `readOnlyHint: true` on a tool that writes a file: the kernel's `effective_risk_class` is `{irreversible, non_idempotent, external}` until sealed; the ledger records `declared ≠ effective`; the lifted description carries `authority = unverified`; the monitor's decision is unchanged when annotations are removed (property test).
- **AC-E4-4 Negotiation.** A modern-era and a legacy-era MCP server both connect through the probe-first rule; the `ProtocolBinding` records differ in `era`/`negotiated_version`; an unsupported version yields `ProtocolVersionMismatch` with no silent fallback; an ACP v1 host drives the native agent through the compatibility profile with the profile's loss report attached to the run.
- **AC-E4-5 ACP agent conformance (T-LCD-04 for events).** A generic ACP v2 client fixture completes `initialize → session/new → session/prompt → updates → state_update{idle}`; every emitted update resolves through `trace_map` to a ledger event; `idle` is never observed before `lifecycle.turn.finished` is durable (fault-injection test: crash between finish and emit ⇒ no `idle` was sent).
- **AC-E4-6 Permission transport.** `request_permission` is emitted iff `security.permission.requested{decider: human}`; `cancelled` outcome ⇒ `action.effect.refused`; no effect dispatches before `security.permission.decided`; an `allow_always` selection produces a ledgered policy amendment or is downgraded to `allow_once` (per OQ-246).
- **AC-E4-7 Hosted ACP participant (T-LCD-07/-15).** Driving goose, gemini-cli and opencode (v1) through `attach_session` yields descriptors with `observability_level = {events, end_state}`, `ledger ∉`, `unknown` for `steer/fork/compaction/subagents`, component metrics `n/a`; a hosted agent's auto-approvable request is still evaluated by Π (a fixture with `deny` policy never executes).
- **AC-E4-8 Dependency direction (T-LCD-06).** The spec DAG check finds no edge from any HIR entity, ledger event class or component-class contract to a protocol schema; only `lower_target`, `lift`, `negotiate`, `render_session` import them.
- **AC-E4-9 Unknown preservation (T-LCD-11).** An unknown `_meta` key and an unknown `_`-prefixed `ToolKind`/`StopReason` survive `lift ∘ lower` byte-for-byte in `ext`.
- **AC-E4-10 A2A (C2).** `TaskState` mapping is exhaustive over outcome classes; an `INPUT_REQUIRED` round trip resumes the child run; card `version = bundle_id`; the card's signature verifies under a fixture trust root and fails closed under a wrong one.
- **AC-E4-11 Out-of-process (T-LCD-12).** All edge operations run as a separate process exchanging typed documents; the acceptance suite is unchanged.
