## 1. Scope & boundary

This workstream decides **how a HarnessHarness harness is assembled declaratively**: the grammar by which a *Harness Definition* names component variants, parameters, bindings and constraints; **what must be runtime code versus what must be data** (the code-vs-config boundary) and the migration path between them; the **assembly validation contract** (operations, diagnostics, invariants); how a definition references component implementations by **versioned identity** (hooks to WS-L4); and how the composition model exposes **parameter spaces** the Harness Lab can sweep (WS-J3). It answers OQ-044 (is a Harness Definition a data document any runtime can load; may variants be out-of-process) language-neutrally, and states which LCD-trap tests it satisfies (T-LCD-08, T-LCD-12 are owned here; T-02/-05/-06/-10/-14 are touched).

It explicitly leaves to neighbours: the typed entity/edge vocabulary and identity derivation of the Harness IR (WS-A3 — this dossier consumes entity *references*, it does not type entities); lowering to runtime/profile/protocol targets (WS-A4); the profile schema (WS-C3); the registry *service* and its discovery/UI (WS-J2/J1 — this dossier fixes the registry *records* those services store); the plugin packaging/trust/signing model for third-party variants (WS-L5/H5 — this dossier fixes only what a definition may point to); content-addressing and canonical byte encoding (WS-L4 with OQ-041 — this dossier states requirements on them); the experiment engine (WS-J3 — this dossier fixes what a parameter space *is*, not how it is scheduled); every language/runtime/package question (WS-L1). Nothing here names a language, runtime or ecosystem; every precedent is cited by file path only.

## 4. Findings

### 4a. Mechanism evidence

**F1. Every audited harness converged, independently, on the same configuration shape: a typed document whose plug points are tagged unions of `{variant tag, typed parameters}`, whose cross-references are names resolved through a registry, and whose free text enters through a small number of named text fields.** OpenHands `kind`/`agent_kind`/`condenser_kind`; goose `type ∈ {stdio, builtin, platform, streamable_http}`; opencode MCP `type ∈ {local, remote}` and agent `mode`; Claude SDK `{type: preset|file}` prompts and `type: stdio|sse|http|sdk` MCP servers; AutoGen `provider`+`component_type`; Agent Spec `component_type`; Omnigent `executor.harness`. None of the seven uses inheritance, host-language object graphs, or serialized closures as the *persisted* form; where code is loaded (Pi extensions, opencode plugins, DSPy `save_program`, AutoGen `provider` import) the document carries a *pointer* (path, package name, module path) and the loader treats it as the untrusted path (DSPy warns; AutoGen checks a trusted namespace; Pi gates on project trust; Claude Code applies `permissions.allow` only after folder trust). This is Tier-B mechanism evidence from seven independent code bases plus S-074's population-level finding ("policy migrated out of prose"; skills 9/11, MCP 8/11). It licenses fixing the *shape* of the Harness Definition at C0 without an LCD risk: the shape is the intersection of nothing — it is what each system built for itself.

**F2. The reference-versus-inline distinction is load-bearing, and the mature systems make it explicit.** OpenHands separates the *profile* (references: `llm_profile_ref`, `mcp_server_refs`, deny-listed skills; secret-free at rest; stable UUID + renameable name + revision) from the *resolved settings* (embedded, secrets decrypted by the caller) and provides a side-effect-free `resolve_agent_profile_dry_run` that reports `DanglingMcpServerRef` and `ProfileNotFound`. Its authors chose a deny-list for skills precisely because an allow-list "would dangle whenever the authoring catalog differs from the launch catalog". goose recipes *embed* extension configs so a recipe is self-contained, while the global config *keys* extensions by name. OpenHands plugins pin `ref` to a commit SHA in `ResolvedPluginSource` "so that a resumed conversation gets exactly the same plugin version". Mechanism: a definition that references by *mutable name* is not reproducible; one that embeds everything is not shareable or secret-free. The composition model therefore needs both forms and a **resolution** step that turns references into pinned identities, with dangling references as first-class errors.

**F3. Layered configuration with provenance is the norm, and authority layers are monotone.** Codex materialises every layer with `{name: ConfigLayerSource, version, config, disabled_reason}` and a numeric precedence; "requirements" from managed layers are `Sourced<T>` values enforced through `Constrained<T>` validators whose errors name the `requirement_source`; a disablement from any layer wins. Claude Code documents the same stack (managed > CLI > project-local > project > user), takes ordered lists whole from the winning layer, merges `permissions.allow` across scopes, and honours a *stricter* value from a lower scope for security keys. opencode records `plugin_origins {spec, source, scope}` so "later runtime code can make location-sensitive decisions", and MDM preferences "override everything". Pi gates project settings on trust. Mechanism (Tier B, four systems): the merge is *typed per field* (replace / append-set / stricter-wins), never a generic deep-merge; and the layers that carry authority (organisation, security) can only *narrow* what lower layers may set. For a comparison instrument this matters twice: the experiment override is itself a layer (with provenance `experiment`), and the reference monitor (WS-H1) needs the same monotone-narrowing property that Codex's `Constrained` implements.

**F4. The persisted configuration is part of the run record, and resume is a compatibility check, not a merge.** OpenHands persists the *agent configuration* in `base_state.json` as "the single source of truth", and on resume `verify()` requires the same agent class and that tools were only added, never removed — "the LLM may have already been told about them". goose restarts an extension only when the unresolved *or* resolved configuration changed. DSPy stores `dependency_versions` with the state and warns on mismatch; AutoGen stores `component_version` and dispatches to a migration hook. Mechanism: the object the lab must key results by is the **resolved, pinned definition** — not the authored file — and a runtime must expose a `verify_resume` operation with typed incompatibility reasons. This is exactly the reproducible-bundle requirement of doc 2 §8 seen from the configuration side (feeds WS-I3, WS-J5, WS-L4).

**F5. Schema is a derived artifact, validation is diagnostic-bearing, and unknown fields are a policy decision.** Codex generates and commits `config.schema.json` from its config type; opencode and Claude Code publish `$schema` URLs; opencode's compatibility lowering emits `Diagnostic{kind ∈ {invalid, unsupported, conflict}, path, message}`; goose validates recipe templates structurally (declared parameters must equal the template's variables in both directions; optional parameters must have defaults; JSON schemas are compiled). Unknown-field policy diverges: OpenHands profiles use `extra="forbid"` to prevent "mongrel" records across union variants; Claude Code ignores unknown top-level manifest fields (dual-purpose manifests) but `validate --strict` warns; MCP/ACP/LSP reserve prefixed `_meta`/`_` slots. Mechanism: strict schemas at union boundaries + one typed extension slot is the combination that avoids both mongrels and the LCD escape hatch (WS-L7 F1).

**F6. Where control lives today: the loop, tool executors, provider clients, compaction algorithms, permission evaluation and persistence are code in every system; which of them is active, with what parameters, under which policy, for which model, is data.** The boundary is visible in the same files: OpenHands `CondenserBase.condense()` is the algorithm, `LLMSummarizingCondenserSettings{max_size, keep_first, max_tokens}` is the data; opencode `ToolRegistry.tools(model, agent, permission)` computes the tool set from three data inputs; goose's `add_extension` dispatches on the config tag to a client *factory*. Three hybrids sit on the boundary and are instructive: (i) *prose with frontmatter* (opencode `agent/*.md`, Claude agents, Pi/OpenHands AGENTS.md, Omnigent `instructions: AGENTS.md`) — the body is text, the frontmatter is typed config; (ii) *policy DSLs* — Codex execpolicy "Starlark, not TOML" (S-166 §10.2.1) and hook commands (Claude Code, Pi, opencode) — data that names or contains something an interpreter runs; (iii) *in-process versus out-of-process under one tag set* — goose `platform` extensions "run in the agent process" beside `stdio` servers; OpenHands `ACPAgent` beside the native `Agent` under one `agent_kind`. AgentCore states the vendor rule explicitly: configuration first, "export to code when configuration isn't enough" (S-058, vendor).

**F7. The optimization literature, as mechanism only, agrees that the editable surface is a small set of named slots with typed knobs, and that value is unevenly distributed across them.** MemoHarness names six dimensions (context assembly, tool interaction, generation control, orchestration, memory management, output processing); S-092 names four slots and finds value localized to reflection/control on its tasks, with the warning that spreading a fixed search budget uniformly across slots starves every slot; AHE attributes gains to tools, middleware and long-term memory rather than the system prompt. All three are `provisional` and single-team; none is load-bearing here. What they *jointly* support at mechanism level is that a factorial parameter space must (a) be slot-scoped so budget can be concentrated per slot, and (b) record `search_budget` per slot/arm (T-LCD-14), which the grammar below provides.

## 5. Disconfirming evidence & negative results

**Against "a Harness Definition can be pure data" (ADR-1).** Every audited product keeps an escape hatch to code: OpenHands `system_prompt_filename` "falls through to the Jinja escape hatch" and `AgentBase` subclasses may ship their own `prompt_dir`; Codex execution policy is Starlark; hooks are shell commands; Pi extensions are code modules; DSPy needs `save_program=True` to round-trip a custom module; AutoGen imports a provider class. If the best systems cannot avoid code in their definitions, a pure-data definition may be an LCD abstraction (RK-02). *Why this does not overturn:* the escape hatches are of two kinds and both are representable as data without loss. (i) *Code pointers* (package, path, module, command) — the definition names a versioned, content-addressed, trust-recorded *variant* and never embeds code; the loader is the untrusted path in every precedent already. (ii) *Interpreted policy leaves* (templates, execpolicy rules, JSON-schema constraints) — these are data for a Core interpreter with a declared effect class; they are admitted only as *typed leaves of declared kind* (the same discipline T-LCD-02 applies to text). What is *not* admitted — a serialized closure or an inline host-language body — is exactly what DSPy and AutoGen flag as the dangerous path. The residual risk is a behaviour that no registered variant expresses and that the author cannot add as a variant; that is a T-LCD-03 round-trip failure and is reported as such, not hidden (OQ-A5-05 on interpreted leaves at C0).

**Against typed slot grammars: AgentSquare/ADAS-style search spaces have been criticised as too coarse, and S-092 shows value concentrates in one slot on its tasks.** If nearly all optimization value lives in "reflection/control", a rich slot grammar over seven planes is over-engineering. *Why this does not overturn:* S-092 is provisional, single-model (7B), two-benchmark, and task-contingent (WebShop "freezes empty" for all methods); AHE reaches the opposite attribution (tools/middleware/memory) on Terminal-Bench. The disagreement between two provisional papers is *the* argument for an instrument whose parameter space is slot-scoped and budget-aware rather than for fixing the answer — the grammar must let a lab concentrate budget on any slot (T-LCD-14) and report per-slot effects (T-LCD-09).

**Against reference resolution and pinning: the OpenHands authors deliberately chose a deny-list for skills because catalogs drift — strict pinning may make definitions unusable across machines.** *Why this does not overturn:* the grammar separates *authoring* references (may be names, deny-lists, version ranges) from the *resolved* definition (fully pinned). Reproducibility is required of the resolved artifact that the lab keys results by; portability of the authored artifact is preserved. The cost is that resolution is environment-dependent and must be recorded as provenance in the run bundle (WS-I3).

**Against layered configuration in a research instrument: layers are a product concern (organisations, MDM); a laboratory could key everything by one flat resolved document and avoid merge semantics entirely.** *Why this does not overturn:* the lab itself needs at least three layers — baseline definition, experiment override, and security/budget caps that an experiment may not widen (T-LCD-14, ADR-0002 governance) — and the results ledger must know which layer set which field to attribute effects. Flat resolution is what `resolve()` produces; layering is how it is authored. The cost accepted: per-field merge policy must be declared in the schema (F3), which is more design than a generic deep-merge.

**Against out-of-process variants (OQ-044 second half): every hot-path component (context builder, control step) in the audited systems is in-process; goose's `platform` extensions exist precisely because some extensions "have direct access to the agent".** Out-of-process hot-path variants add serialization per step and could distort latency/cost metrics the lab is trying to measure. *Why this does not overturn:* the contract admits both localities (T-LCD-12 requires implementability out-of-process), the *default* locality for Stage 0–2 Core variants is in-process, and out-of-process binding is a declared property of the variant with its own cost attribution (WS-L2) so that the lab can stratify on it rather than pretend it is free. The residual open question (OQ-A5-03) is the per-class performance budget above which out-of-process binding is refused for a hot-path class.

**Against "policy migrated out of prose" as a design trend (S-074): the same study finds none of eleven systems imports a framework, i.e. their configuration schemas are bespoke and mutually incompatible.** A shared Harness Definition might be the framework nobody adopts (CF-009). *Why this does not overturn:* ADR-0003 already positions HarnessHarness as an instrument; the definition format is for *native participants*; hosted participants keep their own configuration and join at `product`/`configuration` granularity (ADR-0004), where Omnigent's agent YAML shows the same grammar suffices at that granularity. The definition needs no third-party adoption to do its job.

**Negative result from the audit.** No audited system computes a *content identity* for its resolved configuration (goose recipe ids hash the *path*; OpenHands profile ids are UUIDs; Claude/opencode key by file); none records which *layer* set which field in the run record (Codex records the layer stack in memory but not in a run artifact we found); none validates that a configuration's declared parameter space matches what the runtime actually reads. These are the gaps the instrument must fill and are the `novel`-as-integration parts of §6 (each with partial precedent named).

## 6. Recommendation for the spec

### 6.1 The composition grammar (abstract; Spec §3 "Harness Definition document")

A **Harness Definition** is the root document of a Harness IR dialect (`hir/<n>`), a data document with no host-language content, containing:

```
HarnessDefinition
  dialect          : "hir/1"                              # apiVersion/kind analogue; refused if unknown
  identity         : { name, version, digest?, provenance }   # digest computed over the *resolved* form (§6.3)
  profile_binding  : "unbound" | ProfileRef | ProfileConstraint   # default unbound (T-LCD-04): one definition, ≥2 profiles
  slots            : { <class_id> : SlotBinding | [SlotBinding] }  # one entry per Core component class used
  parameters       : { <param_id> : ParameterSpec }        # the declared parameter space (§6.5)
  values           : { <param_id> : Value }                # this definition's point in the space (may be partial → defaults)
  entities         : { <entity_id> : EntityRef | Entity }  # HIR entities owned by WS-A3 (ToolCapability, Permission, Budget, Validator,
                                                           #   HarnessRule, Procedure, ContextItem/Text leaf …); referenced by slots and values
  constraints      : [ Constraint ]                        # requires / conflicts / implies / range / authority-cap
  layers?          : [ LayerProvenance ]                   # present only on composed documents: which layer set which path
  ext              : { "<namespace>/<key>" : TypedValue }  # the single typed extension slot (MCP/ACP `_meta` discipline); no other unknown keys

SlotBinding
  variant   : VariantRef { class_id, variant_id, version | digest }   # authored: version range or name allowed; resolved: digest required
  params    : { <name> : Value | "$param:<param_id>" | "$entity:<entity_id>" }   # validated against VariantRecord.param_schema
  enabled   : bool (default true)                          # ablation switch; disabled bindings still count toward identity
  locality? : "in-process" | "out-of-process" | "inherit"  # a *hint* — the contract is locality-neutral (T-LCD-12)

ComponentClass (registered by Core; the *contract*)
  class_id, contract { operations[{name, inputs, outputs, invariants, failure_modes}] }, cardinality ∈ { exactly-one, optional, ordered-many }
  required_inputs ⊇ { ModelProfile, ResourceAccount }      # T-LCD-08: every class receives the profile and accounting
  base_param_schema                                        # parameters every variant of the class must accept (e.g. budget share)

VariantRecord (stored by the registry, WS-J2; the *implementation identity*)
  variant_id, class_id, version, digest, param_schema, binding { locality ∈ {in-process, out-of-process, remote}, entrypoint_identity },
  capability_declaration, conditioned_rules[ AssumptionDebtRecord ] (T-LCD-05), provenance/trust (WS-L5/H5), dialect_range { min, max }

ParameterSpec
  id, type ∈ { int, real, bool, enum, string, duration, token_count, ref<class_id>, ref<entity_kind> }, domain (range | set | pattern),
  default?, required ∈ { required, optional, prompt }, unit?, sweepable: bool, affects: [ slot/entity paths ], budget_relevant: bool

Constraint
  kind ∈ { requires, conflicts, implies, range, authority_cap }, subject paths, source: LayerProvenance
  # authority_cap is monotone: a layer may only *narrow* a permission/budget/effect set, never widen it (Codex `Constrained`, Claude "stricter wins")
```

Rules: (1) a definition contains **references** to code, never code — a `VariantRef` and, for hooks/skills/extensions, an entity whose *executable* is itself a registered variant or a content-addressed artifact with a trust record; (2) all free text is a typed `Text` leaf with provenance/owner/authority (WS-A3; T-LCD-02) — prose files such as AGENTS.md-class instructions enter as `ContextItem` entities, their frontmatter as typed fields (opencode/Claude precedent); (3) `profile_binding` is unbound by default — profile is a *configuration* coordinate (ontology v0.1), so one definition compiles under ≥2 profiles; (4) `slots` are keyed by class, not by plane, so the seven planes are covered by whichever classes WS-A3/Phase 2 register (context builder, compaction, control strategy, control envelope, validator, router, memory, tool registry policy, permission policy evaluator …); (5) the `ext` slot is the only place unknown keys may live; anything else unknown is an error (F5).

### 6.2 The code-vs-config decision rule (Spec §3 and §8)

**MUST be code (Core or variant implementation; never editable by an optimizer):** the loader/validator/resolver/assembler of definitions; the event ledger and effect model (WS-B1/B2); the reference monitor, credential mediation, egress and sandbox boundaries (ADR-0002 (iii)); budget enforcement; component-class *contracts* and variant *algorithms*; the interpreters of any admitted policy leaf. Rationale: doc 2 §4 design principle (hard invariants in deterministic software) and ADR-0002 governance.

**MUST be data (in the Harness Definition):** which variant fills each slot and whether it is enabled; every parameter value and the declared parameter space; every reference to model profile, entities, environments, budgets; permission/effect/validator *declarations*; prompts and instructions as typed text leaves; tool/skill/procedure inventories; conditioned rules with their assumption-debt records; experiment overrides. Rationale: only data can be diffed structurally, content-addressed, swept, ablated, versioned, attributed and edited under governance (doc 2 §11 "expose enough of the harness as data/configuration that an optimizer can later edit it safely"; T-LCD-02/-10; ADR-0002).

**MAY be either, decided by the ladder:** a behaviour moves *up* the ladder only when it earns it and *down* when it stops earning it —
`prose (opaque) → typed Text leaf with provenance → typed parameter or entity → registered variant → Core invariant (by ADR only)`.
Promotion criteria: a text rule becomes a parameter when it can be stated as a value in a typed domain (e.g. "keep the last 20k tokens" → `keep_recent_tokens`); a parameterised behaviour becomes a variant when it is an algorithm with its own failure modes; a variant becomes Core only when it is a hard invariant every harness must satisfy. Demotion/retirement: a conditioned rule whose assumption-debt record expires is deleted by the lab's "retire rule R" recipe (T-LCD-05); a Core invariant is never demoted without an ADR. Every promotion is a lab experiment (paired runs, matched budget) and lowers the definition's opacity ratio (T-LCD-02) — the migration finding of S-074 becomes a measurable quantity per definition.

**Pointer rule for hybrids (F6):** hooks, skills, extensions and plugins are *data records naming executables by versioned identity* (path/package → content digest + trust record at resolution), executed only through a Core-declared effect class and permission (WS-H5/L5). Interpreted policy leaves (templates, exec-policy rules, JSON-schema constraints) are admitted as `TypedValue` leaves of a declared kind whose interpreter is a Core component with no ambient authority; whether any such leaf is admitted at C0 is OQ-A5-05.

### 6.3 Interface-contract sketch (language-agnostic)

- `load(bytes, expected_dialect?) → Definition | ParseError{path, reason} | UnknownDialect{found}` — canonical decoding (WS-A3/B1 OQ-041); unknown non-`ext` keys → error; invariant: `load(encode(d)) = d`.
- `compose(layers: [ {definition_fragment, provenance: LayerProvenance{source_kind ∈ {packaged-default, organisation, user, project, experiment, session}, id, version, precedence}} ], merge_policy: from schema) → Definition` — per-field policy `replace | append-set | stricter-wins | forbidden-below(precedence)`; output carries `layers[]` with the winning source per path; failure `AuthorityViolation{path, attempted, cap, source}` when a lower layer widens an `authority_cap`. Invariant: composition is deterministic and order-defined; the experiment layer can never satisfy `forbidden-below` for security/budget caps (T-LCD-14, ADR-0002).
- `resolve(definition, registry_view, environment) → ResolvedDefinition | UnresolvedReference{path, ref} | AmbiguousVersion{path, candidates} | DialectIncompatible{variant, range}` — every `VariantRef` pinned to a digest; every entity reference pinned; every `$param` substituted; secrets replaced by *channel names* (never values); `registry_view` is the snapshot used (recorded). Invariants: the result is *closed* (no environment lookups remain), *secret-free*, and *idempotent* (`resolve(r) = r`).
- `validate(resolved, class_catalog, profiles?: [ProfileRef]) → ValidationReport{ status ∈ {ok, error}, diagnostics[ Diagnostic{code, severity, path, source_layer?, detail} ], derived{ opacity_ratio, identity_stability, hosting_edges: [] } }` — stages, in order, all reported (never fail-fast on the first): (1) schema; (2) class conformance — `variant.class_id = slot.class_id`, cardinality, `params` against `base_param_schema ∪ variant.param_schema`, unknown param → error; (3) parameter space — every `values` key declared, every `sweepable` parameter has a domain, every `$param` used is declared and every declared parameter is used (goose bidirectional rule); (4) constraints; (5) IR validation delegated to WS-A3 (entity typing, provenance on every `Text` leaf, assumption-debt record on every conditioned rule); (6) profile compatibility — each variant's `capability_declaration` and `dialect_range` against each named profile, propagating `UnexpressibleSurface` from WS-A4 as an error; (7) LCD static checks T-02 (opacity computed), T-06 (`hosting_edges = []`), T-10 (identity excludes surface fields), T-12 (no contract in `class_catalog` requires inheritance). Invariant: `validate` is pure and deterministic over its inputs.
- `identity(resolved) → Digest` — digest over the canonical encoding of the resolved definition *excluding* surface fields owned by profiles (T-LCD-10) and excluding `layers[]` provenance (two authoring paths that resolve identically are the same configuration coordinate); this digest is the `harness_definition` coordinate of a `configuration` id (ontology v0.1) and the key WS-J5 stores results under and WS-I3 bundles. Handoff to WS-L4: the encoding must be deterministic (OQ-041) and the digest algorithm/`mediaType` follow an OCI-descriptor-style record `{kind, dialect, digest, size}`.
- `instantiate(resolved, runtime, profile, accounting) → HarnessInstance | BindFailure{slot, variant, reason ∈ {not-installed, trust-denied, locality-unsupported, contract-mismatch}}` — the Core assembler binds each slot to its variant in-process or through the variant-host boundary; every class receives `(profile, accounting)` (T-LCD-08); binding order and results are emitted as ledger events (WS-B1) so the run record shows the exact instance graph.
- `diff(resolved_a, resolved_b) → StructuralDiff{ changed: [ {path, kind ∈ {slot-variant, param, entity, constraint, enabled}, before, after} ] }` — structural, never textual; the unit the evolution service edits and the attribution engine reasons over (ADR-0002; feeds WS-I5/I7).
- `verify_resume(persisted: ResolvedDefinition, current: ResolvedDefinition, ledger_view) → Compatible | Incompatible{reasons[ {path, rule} ]}` — Core rules: dialect equal; every slot's `class_id` equal; tool/capability inventory add-only if the ledger shows any delivered surface referencing removed items (OpenHands rule generalised through T-LCD-13 events); budgets may only decrease mid-run if the accounting allows; other changes allowed and recorded as a `definition-changed` event.
- `space(resolved) → ParameterSpace{ params: [ParameterSpec], slot_choices: { class_id: [VariantRef] }, constraints }` and `enumerate(space, design: FullFactorial | Fractional{...} | OverrideList[Override]) → [ ResolvedDefinition ]` — `Override` uses the Hydra-style grammar (`path=v`, `+path=v`, `++path=v`, `~path`, `path=v1,v2` choice sweeps, slot overrides `class_id=variant`); every enumerated definition passes `validate`; the engine (WS-J3) attaches `search_budget`/`eval_budget` per arm (T-LCD-14) and the identity of each point is `identity()`.
- `export(resolved, target) → Lowering` — delegated to WS-A4; the definition is the input to `lcd_report`.

### 6.4 Data-model sketch

`HarnessDefinition` (§6.1) · `ResolvedDefinition` = `HarnessDefinition` with all refs pinned, `values` complete, `layers[]` provenance, `registry_snapshot_id`, `resolved_at` · `VariantRecord` (§6.1; the registry row, WS-J2) · `ClassRecord{class_id, contract, cardinality, required_inputs, base_param_schema, dialect_introduced}` · `LayerProvenance{source_kind, id, version, precedence}` · `Diagnostic{code, severity ∈ {error, warning, info}, path, source_layer?, detail}` · `ParameterSpace` / `Override` · `StructuralDiff` · `ConfigurationId = digest(model_ref, harness_definition_digest, profile_digest, environment_digest, budget, seed)` (ontology `configuration`; the lab keys by it) · `AssemblyEvent{run_id, slot, variant_digest, locality, bind_result}` (WS-B1 event; makes the instance graph observable).

### 6.5 Parameter spaces for the laboratory (Spec §6)

A parameter space is *declared in the definition*, not inferred from code: `parameters` plus the set of registered variants per slot. Consequences the lab relies on: (i) every sweepable axis has a typed domain, so `enumerate` can refuse an ill-typed sweep before spending budget; (ii) `affects` links each parameter to the slot(s) it touches, so a factorial can be slot-scoped and budget concentrated per slot (the S-092/AHE disagreement is testable, not assumed); (iii) `budget_relevant` parameters (context window share, max turns, tool-call caps) are recognised so T-LCD-14 can check that arms are matched on them; (iv) `enabled` on a `SlotBinding` is the canonical ablation switch, so "delete component X" is an override, not a code change; (v) hosted participants declare their `params` in the same grammar (Omnigent precedent) but only at `configuration`/`product` granularity (ADR-0004), so cross-class factorials share one override vocabulary and class-scoped metrics remain `n/a` where they must (T-LCD-15).

### 6.6 Answer to OQ-044 (for WS-L1; no ecosystem named)

(a) **A Harness Definition is a data document loadable by any conformant runtime.** Composition (compose/resolve/validate/instantiate) requires runtime code, but only the Core assembler's; no host-language code appears in, or is required to author, a definition. Precedent: a complete harness configuration already crosses a process boundary as data in the Claude Agent SDK; OpenHands/goose/opencode persist their configurations as data and reload them; AgentCore runs harnesses from configuration. (b) **Component variants may be in-process or out-of-process.** Class contracts are operation-shaped (T-LCD-12), so both bind; `locality` is a property of the *variant registration*, not the class. Default for Core variants at Stage 0–2 is in-process; out-of-process support is mandatory for third-party variants (WS-L5) through a *variant-host boundary* that reuses the WS-L1 §6.5 verb discipline (single source of truth, generated bindings, byte-identical events, no authority widening — CF-023) and declares its operations, schemas and change signals the way MCP declares tools. (c) Implication for the language criteria: the definition format imposes only "deterministic canonical encoding + schema validation + content digest" on the ecosystem; it does not require closed sum types (variant tags are open, registry-validated) — that answer belongs to WS-A3 for the IR entities (OQ-040).

### 6.7 Acceptance-criteria sketch (Spec §3/§6)

- AC-1 (T-LCD-12): every registered `ClassRecord.contract` is expressed as operations/inputs/outputs/invariants/failure modes; a conformance harness binds a stub variant to each Core class *out-of-process* and passes the class's contract tests.
- AC-2 (T-LCD-08): every `ClassRecord.required_inputs ⊇ {ModelProfile, ResourceAccount}`; a model-conditioned compaction variant is implementable without touching Core (the codex `models.json` reminder-policy example).
- AC-3: `resolve` produces a closed, secret-free document; `identity(resolve(d))` is stable across machines given the same registry snapshot; two authoring paths with identical resolved content yield one identity.
- AC-4: `validate` reports all diagnostics with paths and layer provenance; the Stage-0 reference harness definition validates with zero errors and computes an opacity ratio (OQ-036 definition).
- AC-5: `compose` rejects an experiment-layer attempt to widen a permission/budget cap with `AuthorityViolation` naming the capping layer.
- AC-6: `diff` of two definitions that differ only in a compiled tool name under a profile is empty (T-LCD-10); `diff` of an `enabled=false` ablation is exactly one change.
- AC-7: `verify_resume` refuses removal of a tool whose delivery event exists in the ledger and accepts additions (OpenHands rule).
- AC-8 (T-LCD-14 hook): `enumerate` output carries per-arm `search_budget`/`eval_budget` placeholders that WS-J3 must fill before a run is admitted.
- AC-9: the code-vs-config ladder is documented in Spec §8 with the promotion/retirement criteria and a worked example (a reminder rule migrating from prose → text leaf → parameter → conditioned rule with expiry).

### 6.8 Build-stage suggestion

C0 · **Stage 1**: dialect + grammar, `load/validate/resolve/identity/diff`, in-process `instantiate`, `AssemblyEvent`, the class catalog for Stage-0/1 classes, `verify_resume`. C0 · **Stage 2**: out-of-process variant host + `locality` binding (with WS-L5 preview), text-leaf and skill/procedure entities. C0 · **Stage 3**: `compose` with layers and `authority_cap`, `space/enumerate` with override grammar (with WS-J3), opacity ratio in the bundle. C1 · **Stage 5**: `profile_binding` constraints and profile-compatibility validation stage (6) with WS-C3. Organisation-level layers (MDM/managed analogues) are C2 and never on the critical path.

## 10. Confidence

**High** for the grammar shape, the reference/resolution/pinning model, layered provenance and resume verification: each rests on Tier-B source read at pinned commits in ≥3 independent systems and on Tier-A/B specifications (Kubernetes conventions, OCI descriptors, MCP/ACP), with no reliance on 2026 performance claims. **Medium** for the code-vs-config ladder's *promotion criteria* (the direction is Tier-B production evidence — S-074 population trend corroborated by direct reading — but the criteria are a design proposal to be validated by Stage-3 opacity-ratio and ablation experiments) and for the out-of-process default policy (cost data does not yet exist; OQ-A5-03). **Medium-low** for anything that depends on where optimization value lives (S-061/S-066/S-092 disagree and are all provisional); the grammar is deliberately neutral on that question.
