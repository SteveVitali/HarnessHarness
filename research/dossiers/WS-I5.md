## 1. Scope & boundary

This workstream decides the **evolution service**: the C4 subsystem that turns execution evidence into candidate harness edits and drives each candidate through a governed pipeline — candidate generation → explicit failure hypothesis → targeted counterexample set → matched-budget evaluation → held-out regression → cross-model compatibility → security-invariant check → canary → rollout → retirement test (ADR-0002; doc 2 §11 "treat evolution as a deployment pipeline"). Concretely it fixes: (i) the **stage contracts** — for each of the ten stages the inputs, outputs, gates, refusal codes and which ratified operation realises it, with the matched-budget gate normative (ADR-0041 M3, ADR-0046 §7); (ii) the **candidate data model** — a candidate is a `HirDiff` (ADR-0017) between sealed definitions carrying a `FailureHypothesis`, a `PredictedEffect` and a `CounterexampleSet`, with a closed candidate state machine whose transitions are ledger events; (iii) the **governance invariants** — proposal ≠ deployment, no self-authorization, reversibility, expiry, no self-reference, no held-out reading, never-delete lineage; (iv) the **evidence corpus** the proposer reads and the **proposer-adapter contract** that lets the AHE / RHO / Meta-Harness / Harness-R1 / MemoHarness / DGM / AFlow / GEPA families plug in as component variants under one gate set; (v) the **taxonomy** of self-improving harnesses (offline search, continual compilation, test-time adaptation, learned editing, co-evolution, meta-harnessing) mapped to which tier, which gates and which maturity flag each admits; (vi) the **seven-point evidence standard** (doc 2 §5.8; ADR-0002) as the acceptance report every accepted candidate carries; (vii) **canary, rollout and retirement** semantics over the registry lineage, the experiment engine and the assumption-debt record; (viii) answers to OQ-008 and partial answers to OQ-025, OQ-061, OQ-127, OQ-147, OQ-216, OQ-280, OQ-350, OQ-382.

It explicitly leaves to neighbours: the `HirDiff` format, classification and `apply/invert` (**WS-A3**, ADR-0017 — consumed verbatim); the matched-budget protocol, the three benefit kinds and the C4 admissibility gates (**WS-I2**, ADR-0046 §7 — this dossier *applies* them, it adds no estimator); `MatchSpec` modes and refusal semantics (**WS-L2**, ADR-0041); the experiment definition, scheduler, `adaptive_search` and `retirement` kinds (**WS-J3**, ADR-0154…0156 — the pipeline *authors* `ExperimentSpec`s and never runs an arm outside one); transfer profiles, search-time baselines and the realized-benefit decomposition (**WS-J4**, ADR-0159); the registry, its `exp/<experiment_id>/` namespace and R-NM (**WS-J2**, ADR-0151…0153); the assembly service's `apply(base, diff)` and `AssemblyDiff` (**WS-J1**, ADR-0147/0149); the kernel's D-5 handle set and AT-H1-05 (**WS-H1**, ADR-0053); counterfactual branches and the intervention record (**WS-B4**, ADR-0133…0135; attribution statistics **WS-I7**); the removal test and expiry triggers (**WS-C3**, ADR-0126; the *manager* **WS-I6**); the procedure lifecycle and promotion policy for induced procedures (**WS-D5**, ADR-0086); co-evolution with weights and consolidation (**WS-I8**); value-of-compute allocation across candidates (**WS-F4** — this dossier supplies the per-slot history F4 reads); judge calibration and untrusted-monitor protocols (**WS-G3**); every ecosystem choice (**ADR-0050**).

## 4. Findings

### 4a. Mechanism evidence (a failure mode exists / an architecture is implementable)

**F1 — Every open-source search loop has the same skeleton, and the skeleton is exactly the first half of the doc 2 pipeline: archive → select parent → diagnose → propose → compile-gate → evaluate → archive-append.** DGM keeps an archive of run ids with a parent pointer and reconstructs any candidate as an ordered chain of patches over `initial` (`evo_utils.py` L28–41) — a *diff lineage*, not a snapshot store; it chooses a parent by score with a children-count penalty (`DGM_outer.py` L91–100) and an *entry* (a failing task) from that parent's unresolved set; a separate diagnosis model turns the failing trajectory into a structured problem statement (`self_improvement_prompt.py` L114–118: summary → potential improvements → one proposal → implementation suggestion → issue text); the coding agent then edits its own source in a container; a compile gate (`is_compiled_self_improve`) refuses candidates that produced no patch or did not finish evaluation; the archive is appended, by default keeping everything (`update_archive` `keep_all`). AFlow does the same with rounds as directories: sample a parent from the top rounds with an exploration mixture (`data_utils.py` L61–95), render experience and operator descriptions into the proposer prompt, regenerate while the `modification` string repeats a past one (`check_modification`), write `graph.py`/`prompt.py`, evaluate, append `experience.json`. ADAS appends `{thought, name, code, fitness, generation}` after a compile-and-debug loop and a bootstrap-CI fitness. **Implication:** the pipeline's S0–S4 (observe, propose, hypothesize, screen, search-evaluate) are precedented in shape; what is precedented *nowhere* is S5–S10 (held-out regression as a gate, cross-model transfer as a gate, security invariance, canary, rollout under separate authority, retirement) — confirming ADR-0002 (b) "novel as an integrated contract" at source.

**F2 — Explicit failure hypotheses and predictions are already produced by the strongest loops, but never verified as contracts.** DGM's diagnosis JSON is a failure hypothesis in all but name (a problem statement derived from one trajectory); AHE goes one step further and attaches a *self-declared prediction* to every edit, verified against outcomes in the next iteration, calling the result "falsifiable contracts" (S-061). HarnessEvolve computes credit by aligning failed executions against *reference trajectories* generated with the answer (S-090); RHO selects "difficult" past trajectories and re-solves them (S-063); PRISM clusters failures and routes each cluster to an edit surface (S-093). None of the three source loops *checks* the hypothesis: DGM's post-hoc `diagnose_improvement` produces a judged score in [−2, 2] but the score is not a gate (`self_improve_step.py` L400–415 stores it as metadata), AFlow records only `succeed = avg_score > before`. **Implication (§6.2 S2):** a candidate is refused unless its `FailureHypothesis` names the evidence it explains (`RunRef`/`EventRef`s), the metric(s) it predicts to move, the direction, and the task set on which the prediction should be visible; the prediction is verified at S3–S5 and the verdict is stored on the candidate — AHE's mechanism made a typed gate, with DGM's five-field diagnosis as the shape of the hypothesis text.

**F3 — The three loops evaluate on the set they search, and the one that separates a test split evaluates it only once, at the end.** DGM selects entries from the parent's unresolved SWE-bench instances and evaluates children on the same small/medium/big subsets (`DGM_outer.py` L245–250; `get_full_eval_threshold`); its evaluation of "improvement" is `accuracy_score` on those subsets with `num_swe_evals = 1`; a candidate that beats the archive's second-best score is promoted to a bigger *subset of the same benchmark*, never to a held-out one. AFlow's `validation_rounds = 5` averages five runs of one validation set and decides `succeed` by a bare comparison; the test split (`workflows_test`) is run in a separate mode. ADAS keeps `SEARCHING_MODE` val/test apart and re-scores the whole archive on test at the end — the only held-out discipline in the three, and it is a *report*, not a gate. S-083's finding that evolution "exhibits limited generalization" and HarnessBank's "task-specific overfitting" (S-087) are the predictable consequence. **Implication (§6.2 S3–S5):** the counterexample set and every search-time evaluation are confined to `search`/`dev` split labels registered *before* search (ADR-0143 L3; `SplitAssignmentRecord`); the held-out split is never delivered to any candidate or proposer (L1); `artifact_benefit` is a `full_set` experiment on `held_out` with a pre-search `task_split_hash` (ADR-0046 decision 4; ADR-0156 decision 4) — the gate ADAS reports and none of the three enforce.

**F4 — No loop compares against a matched test-time baseline, and each records a different fraction of its search spend.** DGM's only baselines are `no_selfimprove` (initial agent) and `no_darwin` (chain without archive) — neither is best-of-N with equal rollouts; AFlow records `avg_cost`/`total_cost` per evaluation (`data_utils.py` `create_result_data`) but never the optimizer-model spend; ADAS records nothing about cost; RHO's abstract reports no budget; Meta-Harness's proposer reads "scores and traces of all prior candidates" — the search spend is the whole archive's. S-083 shows that supplying the same feedback and inference budget to parallel sampling or sequential refinement removes the consistent advantage. **Implication (§6.2 S4):** the pipeline's search stage is an `ExperimentSpec{kind: adaptive_search}` whose arms carry a complete `SearchBudgetRecord` (rollouts, model calls, tokens, feedback labels, judge calls, wall-clock, per-slot allocation — ADR-0046 decision 1) and a `MatchSpec{mode: matched_total}` (ADR-0041 M3) against the ADR-0159 `oracle_best_of_n`/`selected_best_of_n` baseline at equal rollouts; a candidate whose `search_budget` is incomplete cannot be *accepted* (ADR-0046 §7), only reported at product level.

**F5 — Gates that read a judge, or that let the judge see the oracle, are the reward-hacking surface.** DGM's improvement judge is handed SWE-bench's official test patch and answer patch (`diagnose_improvement_prompt.py`: "SWE-bench's official private tests", "official answer patch") — defensible for a post-mortem, indefensible for a gate, because the same channel would let a proposer read the held-out oracle; RHO's acceptance is pairwise *self*-preference "without any external grading" (S-063); S-068 finds peer-judge signal between similarly powered models "yields no usable signal"; S-104 shows automatic reviewers approving 13/13 attacks. ADR-0047 already fixes headline capability to deterministic oracle classes and makes judges labelled, calibrated, independent and instrument-charged; ADR-0143 L1 makes held-out delivery a veto. **Implication (§6.4 G7–G8):** judges (including self-preference and teacher-relative oracles) are admissible *inside* the search budget as selectors and never as the S5 gate; the target set of a candidate excludes every `Validator` the suite uses, every oracle declaration and every grader executable (a candidate may not edit what scores it); the proposer's evidence corpus is a projection that carries no held-out surface (L1 applied to the evolution AgentProcess as a model-facing surface).

**F6 — Retention and adaptation pull apart, and value concentrates in one slot; both are visible only if the pipeline records per-task and per-slot outcomes.** EVOHARNESSBENCH's "harness-induced forgetting" (S-091) is the reason the S5 gate carries a `retention` row (paired Δ on previously-passing tasks ≥ −margin; ADR-0046 §7) beside `artifact_benefit`; HarnessEvolve's performance gate ("improve current batch without degrading recent batches", S-090) is the same rule at batch granularity. S-092's leave-one-in/out shows the budget-splitting trap: a uniform split starves every slot. ADR-0045 already stores per-task (c, n); ADR-0046 stores `allocation` per slot in the search record. **Implication (§6.6, §6.7):** `ProposalConstraints.target_classes` is chosen by a `SlotAllocationPolicy` (MUST-data) with a per-slot floor and a default of *concentrate*; the campaign exposes a per-slot `search_time_benefit` history to WS-F4 (OQ-025); and "no addressable failure in any slot" (WebShop in S-092) is a declared stop reason, not an infinite loop.

**F7 — Separation of proposal from deployment exists in three shapes, and only one is safe: a separate evolver agent (HarnessBank, DGM's diagnosis model, Harness-R1's engineer), a regression gate before acceptance (Self-Harness, HarnessEvolve), and a human/definition-class seal.** The first two separate *roles*; only the third separates *authority*. ADR-0053 D-5 fixes the third: the evolution AgentProcess holds a root handle set frozen at `seal` (`fs_read` on ledger views, `memory_write` at scope `run` to the candidate store, `model_call`, `exec` in a network-less sandbox), no `permission_request` grant that could auto-resolve, no `delegable` grant, no scope over the definition, Π, the handle table or MUST-code pointers; its outputs are `HirDiff`s refused on `authority_delta = widening`, `budget_delta = loosening`, `validity_delta = loosening` or any op on a MUST-code leaf; deployment is a `seal` endorsement by a `definition`-class human (ADR-0035 basis list). ADR-0177/0181 add that guards and hooks the service authors can only `narrow`/`annotate`/`propose_replacement`, never `allow`. **Implication (§6.4):** the pipeline has exactly one non-automatable transition — `security_checked → sealed_candidate` — and exactly one class of *automatic* transition toward less exposure: revert to an ancestor that a human already sealed. Everything else is an experiment the engine runs under the D-5 handles.

**F8 — Reversibility is cheap when the candidate is an invertible typed diff over sealed definitions, and impossible when it is an in-place edit of source.** DGM's self-edit mutates `coding_agent.py` inside a container and reconstructs versions by replaying patch chains; AFlow writes new round directories; both can *reconstruct* a prior version but neither can *revert a live deployment* because there is no deployed object separate from the search artefact. ADR-0017 gives `invert(diff)` with `apply(target, invert(diff)) = base` byte-for-byte; ADR-0037 makes every sealed version immutable and every supersession an edge; ADR-0147 M-2 makes every Lab change an `apply(base, diff)`; ADR-0149 T-3 fixes `freeze` as the only drift default. **Implication (§6.4 G3, §6.9):** rollback = `apply(head, invert(candidate.diff))` = the already-sealed ancestor; the rollback record is `supersedes{reason: revocation}` on the lineage plus `lifecycle.run.rolled_back` on any live run (WS-B4) — never a deletion; and because the ancestor was human-sealed, an *automatic* revert on canary abort mints no authority (G3).

**F9 — Accepted evolution edits are conditioned rules, so T-LCD-05 applies reflexively and the retirement test already exists.** Doc 2 §5.9's assumption-debt thesis ("every special rule is a hypothesis about a failure mode that should have evidence, ownership, an expiry condition, and a regression test") describes an accepted candidate exactly: hypothesis = the `FailureHypothesis`; evidence = the S4–S6 `ComparisonReport`s; owner = the campaign's principal; expiry = model drift / evidence age / transfer sign flip; removal test = ADR-0126's matched-budget non-inferiority `retirement` experiment (ADR-0156 decision 3). S-096 (a policy change invalidating the harness tuned around the old policy) and S-087 ("model-specific self-evolving process") are the mechanism behind the expiry trigger `model_version_change`. **Implication (§6.2 S10, §6.5):** every accepted candidate carries an `AssumptionDebtRecord` and `HarnessRule.conditioned_on` when its transfer profile is model-conditioned; the pipeline's last stage *is* the assumption-debt manager's first record (WS-I6); nothing the service accepts is permanent by construction.

**F10 — Certification, not generation, is the bottleneck, so the pipeline needs a stop rule and a value-of-information front.** S-094 proves (under its model) that more candidates do not raise the probability of a certified improvement when evaluation is fixed, that stagnation occurs with headroom remaining, and that certification cost diverges near the ceiling; HarnessLens (S-089) and Task-CoEvolve (S-082) attack the same bottleneck by spending evaluation where candidates *disagree* or where the edit is *behaviour-relevant*; ADR-0156 admits `disagreement_weighted`/`successive_halving` only inside search, rank-labelled. **Implication (§6.2 S3–S4, §6.11):** the counterexample set is the behaviour-relevant screen (cheap, `estimated`), the search experiment may use adaptive validation, the held-out stage is always `full_set`, and the campaign declares `CampaignStopRule{max_candidates, max_search_budget, max_consecutive_rejections, no_addressable_failure}` — a `research-grade` VOI scheduler (WS-F4) may replace the fixed rule later.

**F11 — Test-time adaptation and continual compilation are not pipeline stages; they are component variants whose *persistent* outputs the pipeline governs.** MemoHarness adapts the harness per test case from retrieved experience without labels or search (S-066); JIT-Agent synthesizes a task-conditioned harness on demand (S-071); Evo-Harness compiles skills from single-shot executions (S-588); Procedural Graphs commit edits only under held-out validation (S-095). In HarnessHarness terms the per-run adaptation is a registered component (procedure selector, retrieval ranker, context policy — WS-D3/D5) acting on `Memory`/`Procedure` entities with `origin ∈ {model, evolution}`, validity `unknown`, authority `≤ delegate` (ADR-0086 lifecycle; "induced procedure"); what persists across runs is a candidate for *this* pipeline when it seeks `principal`/`definition` authority (ADR-0086 promotion policy `require_transfer_test`). **Implication (§6.7 taxonomy):** two of the six classes route through the pipeline only at promotion; the pipeline governs persistence, not per-run selection.

**F12 — Hosted participants can be searched only along enforced, SUPPORTED coordinates, and the answer is already implied by ratified refusals.** ADR-0041's Phase 3 amendment refuses `matched_total` when any arm has an unenforceable dimension; ADR-0013/0154 admit hosted levels only at configuration/product granularity; ADR-0149 T-4 restricts hosted diffs to `value_change` on declared coordinates. **Implication (OQ-382, §6.10):** the service may search a hosted participant's SUPPORTED configuration-level coordinates only where `budget_enforcement = enforced` on every matched dimension; the result is a product/configuration-granularity claim with component attribution `n/a{class}`; it never enters a component-level `artifact_benefit` row.

## 5. Disconfirming evidence & negative results

**Against building an evolution service at all ("under matched budgets it does not consistently win").** S-083 is the strongest single source: with two frontier models on Terminal-Bench 2.1, automatic evolution did not consistently beat parallel sampling or sequential refinement given the same feedback and inference budget, and transferred weakly; HarnessDev (S-075) finds generated harnesses behind mature human references in code and research, with unstable, model-dependent evolution gains; S-094 proves stagnation and diverging certification cost. *Why it does not overturn:* ADR-0002 settled scope and made these findings the governance, not the argument; the pipeline is designed so that the S-083 comparison is *the* S4 gate (`matched_total` against `oracle_best_of_n`), so a family that cannot beat test-time search at equal budget produces no accepted candidate — the instrument then *reports* that, which is the research result doc 2 §8 asks for. What is conceded: the first Stage-6 slice is the human-proposed pipeline (§6.13), and every automated family carries a `research-grade` maturity flag until it has passed the gates on the Stage-3 suite.

**Against a ten-stage pipeline ("too expensive to ever accept anything").** Ten gates, each a matched-budget experiment with replicates, multiply cost; DGM ran with one replicate and AFlow with five averaged runs precisely because full evaluation is unaffordable; S-094 says certification cost diverges. *Why it does not overturn:* the stages are ordered cheap-to-expensive with typed early exits (S1 static; S2 static; S3 `estimated` on a small counterexample set; S4 adaptive inside the search budget; S5–S6 `full_set` only for survivors); HarnessLens and Task-CoEvolve are admitted exactly where they are admissible (ADR-0156 decision 4); the campaign has a declared stop rule; and the *search* spend is `charged_to = instrument` and reported, so cost is a measured quantity rather than a hidden one. The concession is real: the pipeline accepts fewer candidates than any published loop, by design.

**Against separating proposal from deployment ("RHO deploys by self-preference and gains 19 points; a human in the loop kills the loop").** *Why it does not overturn:* ADR-0002 (ii)/(iii) and ADR-0053 D-5 are ratified and constitutional; S-104's 13/13 and S-068's "no usable signal" are the mechanism evidence that a model-origin gate is not a gate. The design keeps the loop fast where it is safe — everything up to `security_checked` is automatic; the human act is one `seal` per accepted candidate, and canary/rollout/revert are automatic under a sealed `RolloutPolicy`.

**Against typed diffs as the candidate representation ("Meta-Harness, DGM and AFlow search whole code; a typed diff forbids the winning designs").** *Why it does not overturn:* ADR-0015/0017 already admit `CompiledPayload` replacements (`ReplaceLeaf` on a body with a declared interface) as diff ops, so whole-component code candidates are expressible; what is excluded is an opaque candidate with undeclared effects or one that edits a MUST-code leaf — the S-104/S-476 attack surface. The cost is attribution granularity (a `ReplaceLeaf` candidate is attributable only to the leaf), which the acceptance report states honestly (`attribution_quality` at leaf granularity) rather than hides.

**Against "an accepted edit is a conditioned rule" (reflexive T-LCD-05).** A transfer-tested edit that helps every model family is not model-conditioned; forcing a debt record and an expiry on it adds ceremony. *Why it does not overturn:* the record is cheap (hypothesis and evidence already exist as pipeline outputs), `conditioned_on` is set only when the transfer profile shows a model-conditioned effect, and the expiry triggers are the observable ones ADR-0126 already fires (served-model drift, evidence age, removal-test report) — the alternative is doc 2 §5.9's "fossil record of old model deficiencies".

**Against the held-out-never-delivered rule for the proposer ("Meta-Harness needs scores and traces to propose").** *Why it does not overturn:* the proposer receives *search/dev* scores and traces in full (the evidence corpus is a projection of those runs); only `held_out`/`private` surfaces are withheld (ADR-0143 L1), which is what ADAS already does with `SEARCHING_MODE`. DGM's judge reading the answer patch is the counter-example that shows why the rule must be a kernel predicate rather than a convention.

**Against automatic revert on canary abort ("rollback is a deployment decision").** *Why it does not overturn:* revert applies `invert(diff)` and lands on an ancestor a human sealed; it mints no authority and widens nothing (`authority_delta` of an inverse of a narrowing diff is at most `widening` *back to the human-sealed base*, which is admissible because the target is already sealed); it is the canary's *purpose*. The concession: a revert is ledgered as a supersession with `reason: revocation` and escalated to the principal, never silent (ADR-0032's "abandoned is always escalated" pattern).

**Negative results from the audit.** (N1) No audited loop enforces a held-out split as a per-candidate gate; (N2) none compares against a matched test-time baseline; (N3) none records complete search spend; (N4) none separates the deploying authority from the proposing agent; (N5) none has a retirement test or expiry on an accepted edit; (N6) none can revert a live deployment as a first-class operation; (N7) two of three execute generated code in-process; (N8) one hands its judge the held-out oracle. Every one of these is a rule in §6.

## 6. Recommendation for the spec

### 6.1 Position

1. **The evolution service is a Lab client, not a runtime authority.** It is a native `AgentProcess{origin = evolution, class = delegate}` with the ADR-0053 D-5 root handle set, driving the instrument only through `hh-embed/1` (phase-3 §6.2), authoring `ExperimentSpec`s (ADR-0154) and `HirDiff`s (ADR-0017) applied through `apply(base, diff)` (ADR-0147 M-2), publishing only into `exp/<experiment_id>/` (ADR-0153). It runs no arm itself and decides nothing about authority.
2. **A candidate is a typed diff plus a falsifiable hypothesis plus its own evidence trail**, moving through a closed state machine whose every transition is a ledger event; rejected candidates are retained (never-delete lineage).
3. **The ten doc 2 stages are ten typed gates over ratified operations** — six are experiments of ratified kinds, two are static checks, one is a human endorsement, one is a supersession — with the matched-budget gate (S4, `matched_total`) normative for every accepted candidate (ADR-0002 (d); ADR-0041 M3; T-LCD-14).
4. **Deployment is one human `seal`; exposure is staged data.** The only non-automatable transition is `security_checked → sealed_candidate`; canary share, rollout and revert are `RolloutPolicy` (MUST-data) executed by the engine; the only automatic transition toward *more* exposure is a canary advancing under its pre-registered rule, and the only automatic transition toward *less* is revert to a human-sealed ancestor.
5. **An accepted edit is a conditioned rule** carrying an `AssumptionDebtRecord` whose removal test is the ADR-0156 `retirement` experiment (T-LCD-05 applied reflexively). The pipeline's last stage is WS-I6's first record.
6. **Families are component variants behind one proposer contract**, each with a maturity flag; the taxonomy decides which tier and which gates apply, never whether the gates apply.

**Ordering invariants.** P-1 no stage runs before its predecessor's gate passed (the state machine refuses skips); P-2 S5–S7 run on the *same* sealed `exp/` version that S8 seals (content identity; a re-proposal restarts at S1); P-3 every experiment the pipeline authors names the campaign (`subject.experiment{experiment_id, arm_id}`), pins one `registry_snapshot_id` and one `SplitAssignmentRecord`; P-4 search spend is `charged_to = instrument`, evaluated arms `subject` (phase-3 §6.2); P-5 the human `seal` sees the full `EvolutionAcceptanceReport` and the `AssemblyDiff` rendering (ADR-0149) — never a raw diff.

### 6.3 Candidate data model and state machine

- `CandidateProposal{candidate_id: ContentAddress = H(idp ∥ "candidate" ∥ canonical(base ∥ diff)), base: DefinitionVersionRef, diff: HirDiff, family: ProposerFamily, proposer_run_id: RunId, target_classes[], search_spend: SearchBudgetRecord (fragment), provenance: ProvenanceRecord{origin: evolution(candidate_id, hypothesis_ref), authority: delegate}}`.
- `FailureHypothesis{hypothesis_id: ContentAddress, statement: Text{authority ≤ external}, failure_class: metric_ref | veto_ref | outcome_class | Text, evidence_refs: [RunRef | EventRef | ResultsRowRef], affected_task_ids[] (⊆ search ∪ dev), reference_trajectories?: [RunRef] (S-090/S-586), model_scope: {families[], profiles[]}, predicted: PredictedEffect}`; `PredictedEffect{deltas: [{metric_ref, direction ∈ {up, down}, magnitude?: interval}], expected_flips: [task_id], cost_delta?: direction}`. The `statement` is what `derived-from.hypothesis: Text` carries (ADR-0016); the structured record is referenced through the reserved `ext` key `hh.evolution/hypothesis_ref` until HIR/2 adds `hypothesis_ref` (CF-416); `ext` never decides validity — the S2 gate reads the record, not the edge.
- `CounterexampleSet{set_id, candidate_id, tasks[], selection_rule, inclusion_probabilities_ref?, replicates, split_labels ⊆ {search, dev}}`.
- `EvolutionAcceptanceReport` (§6.8) — one per candidate at S8; content-addressed; a bundle member of the campaign's `experiment` bundle (WS-I3).
- **Candidate state** (closed sum; growth = dialect bump): `proposed → classified → hypothesized → screened → searched → validated → transferred → security_checked → sealed_candidate → canary → active → expiring → {retired | revalidated}`; terminal failures `rejected{stage, code, report_ref}`, `withdrawn{by}`, `reverted{from ∈ {canary, active}, reason}`; `reverted` and `rejected` candidates stay in the lineage. Each transition is a ledger event `measurement.evolution.candidate.transitioned{candidate_id, from, to, stage, report_ref?, causes[]}` on the **campaign run** (a `run_kind = experiment` ledger; ADR-0155/0183 — no new run kind), plus `measurement.evolution.campaign.{opened, stopped{reason}, closed}`; the candidate view is `project(campaign_run, candidate_view, until_seq)` (CF-415 for WS-B1).
- **Lineage:** every sealed candidate is a `sealed_definition` record in `exp/<experiment_id>/` with a `NameHistoryEntry` per candidate id and a cached `diff_ref` (ADR-0037 (4)); the archive is the name history; `keep_all` is the only policy (never-delete); `ParentSelectionPolicy ∈ {best, score_proportional{alpha, uniform_mix}, score_child_proportional{alpha, children_penalty}, pareto_per_task}` is campaign data (DGM/AFlow/GEPA precedents).
- **Campaign:** `EvolutionCampaignSpec{campaign_id, base: DefinitionVersionRef, family, proposal_constraints, slot_allocation: SlotAllocationPolicy{floors: map<class_id, min_rollouts>, mode ∈ {concentrate, uniform, voi(F4)}}, suite_binding + split_assignment_ref, search_budget: BudgetSpec (instrument), eval_budget per stage, match_specs per stage, model_levels (held-out families for S6), rollout_policy, stop_rule: CampaignStopRule{max_candidates, max_search_budget, max_consecutive_rejections, stop_on_no_addressable_failure: true}, pre_registration}` — MUST-data; content-addressed; the campaign's `ExperimentSpec`s are derived from it and registered through ADR-0154 `register` (all refusals inherited).

### 6.4 Governance invariants (kernel-checked; errors, never warnings)

- **G1 Proposal ≠ deployment.** No transition into `sealed_candidate` without a `seal` endorsement whose `origin ∈ {human}` with `authority = definition` (ADR-0035 basis `seal`; ADR-0053 D-5); the proposer's `AgentProcess` cannot append `security.label.endorsed`; `SealRefused{not_human}` otherwise. AT-H1-05 (iv) is the fixture.
- **G2 No self-authorization.** `classify(diff)` refuses `authority_delta = widening`, `budget_delta = loosening`, `validity_delta = loosening`, any op on a MUST-code leaf, any op on Π, `authority_cap`, pre-authorization rules, the handle table, `Permission` grants (except narrowing), or `Budget.hard` (except tightening) — all at S1 *and again* at S7 on the re-sealed version. A candidate-authored guard is a `GuardVerdict` that can only `narrow`/`annotate`/`propose_replacement` (ADR-0181). `permission_request` by the evolution process is `deny` in unattended mode and `ask` to the principal otherwise, never auto-resolved (AT-H1-05 (ii)).
- **G3 Reversibility.** Every accepted candidate has `invert(diff)` verified at S1 (`apply(target, invert(diff)) = base`); the lineage records `rollback_ref = base` on the head; `revert(head) = apply(head, invert(diff))` targets a human-sealed ancestor and is admissible **automatically** on canary abort or an expiry veto, ledgered as `supersedes{reason: revocation}` and escalated to the principal — never silent, never a deletion; live runs receive `lifecycle.run.rolled_back` per WS-B4 with a rewind note.
- **G4 Expiry.** Every accepted edit carries `AssumptionDebtRecord{rule_id = candidate_id, hypothesis = hypothesis_ref, evidence_refs = [S3–S7 report refs], owner = campaign principal, expiry_condition ∈ ADR-0126 triggers ∪ {transfer_sign_flip}, removal_test_ref = the S10 retirement design, status}`; `publish` at S9 refuses `ConditionedRuleIncomplete`; `conditioned_on` is set iff the S6 transfer profile is model-conditioned.
- **G5 Target-set exclusion (no self-reference, no editing the scorer).** The fixed exclusion set is: every `Validator` bound by the campaign's suites and every `OracleDeclaration`/grader executable; every `Permission`, `Budget.hard`, Π/policy leaf, pre-authorization `HarnessRule`, `TrustRootPolicy`, `ContainmentPolicy`, `SinkPolicy`; every MUST-code pointer; **the evolution service's own definition and its proposer variants** (`SelfModificationRefused` — the service may evolve itself only through a human-origin diff in a separate campaign, CF-419); `ext` cannot widen the target set.
- **G6 Split discipline.** `SplitAssignmentRecord` precedes S0 (ADR-0143 L3); `held_out`/`private` surfaces are never delivered to the proposer, a diagnoser, a self-preference judge or any candidate run (`HeldOutLeak` veto, L1); `artifact_benefit` rows only from `held_out`/`private`; a candidate that sealed under one split hash is re-validated under a new one, never grandfathered.
- **G7 Judges never gate.** Any `Validator{kind: judge}` (self-preference, self-validation, teacher-relative, agentic critic) is admissible only as a *selector* inside S3–S4 (`selected_best_of_n`, `charged_to = instrument`, calibration record mandatory, independence from the beneficiary snapshot — ADR-0047/0117) and never decides S5–S7; a judge-only acceptance is `AcceptanceIncomplete{item 1}`.
- **G8 Complete search accounting.** `SearchBudgetRecord` covers the proposer's model calls, diagnosers, judges, screens and search arms since S0; `search_budget = unknown` makes the candidate reportable only at product level and never acceptable (ADR-0046 §7); the leaderboard form is `selection{n_candidates_registered, rule, search_budget_ref}` (ADR-0163 L4).
- **G9 Never delete; always attribute.** Rejected, reverted and withdrawn candidates remain in `exp/` lineage with their reports; a re-attempt is a new candidate id; every candidate names its `proposer_run_id` so the proposer's own trajectory is auditable (the evolution process is a ledgered run like any other).
- **G10 Candidate text is external.** Every `Text` leaf a candidate introduces enters at `authority ≤ external` (ADR-0177 injection table) and reaches `definition` only through the S8 `seal`; the role-placement invariant applies to canary runs, so a candidate-authored instruction cannot render into a role above `role_map(external)` until sealed.

### 6.5 Edit representation

Candidates are `HirDiff`s and nothing else (ADR-0017; ADR-0147 M-2). Admissible op classes by family (§6.7): `ReplaceLeaf` on `Text` (prompt/instruction families), `ReplaceLeaf`/`AddNode` on `CompiledPayload` with declared interface and `placement ≠ in_process` (code-search families), `Rebind`/`ReplaceField` on `SlotBinding` and parameters (configuration search), `AddNode`/`AddEdge` of `Procedure`/`HarnessRule`/`Memory` with `origin = evolution` (continual compilation), `SurfaceEdit` only as a *profile* candidate (T-LCD-10 — filed against the Model Profile version with its own arm, ADR-0017). The `AssemblyDiff` projection (ADR-0149) is the human-review rendering at S8 and the leaderboard `sameness` source. `rebase` (OQ-061): a candidate targets a named `base`; if the lineage head moved before S8, the pipeline re-proposes (`StaleBase`) at Stage 6a/6b and admits `rebase(d, head')` (GumTree-class, C1 extension) at Stage 6c for parallel campaigns; a rebased candidate re-enters at S5 (P-2).

### 6.6 The evidence corpus (S0) and evidence-to-candidate

`EvidenceCorpus{corpus_id: ContentAddress, campaign_id, watermarks[run], layers: {outcomes: results rows (outcome class, per-task (c, n), veto trips, budget utilisation), ledger_views: [{run, effect_ledger, context_view, claim_ledger, guard_fired, compaction events, compliance chain}], model_io?: by address under readers policy, artifacts?: by address, prior_candidates: [{candidate_id, diff_ref, hypothesis_ref, state, report_refs}], reference_trajectories?: [RunRef] (human demonstrations or answer-conditioned reference runs, S-090/S-586), slot_history: map<class_id, [search_time_benefit refs]>}, excluded: {held_out surfaces, validators, secrets, kernel notices above external}}` — a projection (`project(...)`, ADR-0026 rebuild-equality) delivered to the proposer as a read-only content-addressed tree through the D-5 `fs_read` handle (Meta-Harness/AHE "filesystem of prior candidates, scores and traces" — S-080/S-061 — made a kernel-owned projection). The corpus is *layered and drill-down* (AHE experience observability): the outcome layer is small and always present; ledger views expand by address; `model_io` only with `readers` and consent (WS-I3 §6.9). Evidence-to-candidate routing (PRISM failure clustering; S-093) is the proposer's business, but the pipeline records which `failure_class` each candidate claims so that WS-F4 can learn where addressable failures live (OQ-025).

### 6.8 The seven-point standard as the acceptance report

`EvolutionAcceptanceReport{candidate_id, items: [{n ∈ 1..7, status ∈ {pass, fail, n/a{reason}}, evidence_ref}], comparisons: [ComparisonReport refs], portability_label ∈ {reported, portable, model_conditioned}, attribution_granularity ∈ {component, slot, leaf, configuration}, human_review: {reviewer, seal_ref}}` — a candidate reaches S8 only with items 1–3, 5 and 6 `pass`, item 4 `pass` or declared granularity, item 7 `pass` or `n/a{observability}` with the reason shown:

1. **Matched total compute** — S4 `matched_total`; `SearchBudgetRecord` complete; `search_time_benefit` reported (ADR-0046 §7 "search_budget complete", "search_time_benefit reported").
2. **Held-out tasks and, ideally, held-out model families** — S5 `artifact_benefit` on `held_out`; S6 `transfer` on ≥ 1 family (gate), ≥ 2 families + 1 held-out level for the `portable` label (AC-I2-10; CF-417).
3. **Persistent artifact separated from search-time computation** — three benefit rows; frozen `exp/` version; `selection` record at S9.
4. **Component-level attribution** — the diff's targets are registry slots/nodes; `attribution_quality` from WS-I7 LOI/LOO or counterfactual arms when `semantic_ops > 1` (`research-grade` until I7 lands; declared granularity otherwise).
5. **Forgetting/regression** — S5 `retention` row ≥ −margin; vetoes unchanged.
6. **Security-policy invariance** — S7 static + dynamic.
7. **Beneficiary compliance** — S6 activation/following rates and `Pass-When-Activated` for every new artefact (S-088 mechanism; T-LCD-13).

### 6.9 Canary, rollout, revert, retirement

- `RolloutPolicy` (MUST-data, sealed with the campaign): `mode` — `shadow` = every live goal forks a WS-B4 counterfactual branch with `InterventionRecord{kind: definition_diff, payload_ref: diff}`, `n ≥ k` factual re-executions per ADR-0135, irreversible/external effects `deferred` and *never released* (the branch is always discarded), cost `instrument`; `split` = the sealed candidate serves `share` of incoming goals chosen by a recorded assignment seed, under the principal's authority and the live `Budget`, paired only where the same goal is re-run (otherwise an unpaired design — CF-421); `advance_rule` = pre-registered non-inferiority on primary metrics after `min_runs` with `budget_match ∈ {matched, imbalanced}`; `abort_on` = any veto trip, primary-metric regression beyond `margin`, cost ceiling.
- **Revert** (G3): `revert(head) → apply(head, invert(diff))`; appends `supersedes{reason: revocation}` mirrored in name history; every live run on the candidate gets `rollback` (WS-B4) or finishes under the candidate and is annotated; escalation event to the principal; candidate state `reverted{from, reason}`. Automatic on `abort_on`; also available to the principal at any time.
- **Rollout** (S9): `publish` of the head under the target namespace's `who_may_publish`; `promotion` endorsement required when leaving `exp/`; leaderboards admit the entry only with `selection` and M3 (ADR-0163 L4).
- **Retirement** (S10): triggers per ADR-0126 plus `transfer_sign_flip` (a later `TransferProfile` on a new family shows the opposite sign) and `superseding_candidate` (a newer candidate on the same targets passes S8); the `retirement` experiment is `head` vs `apply(head, invert(diff))`; `retired` is a supersession, never a deletion; a *profile* candidate retires through ADR-0126 decision 5 unchanged.

### 6.10 Answers to assigned open questions

- **OQ-008 (safe self-modification):** reward hacking → deterministic-only gates (G7), scorer exclusion (G5), held-out never delivered (G6), proposer trajectories ledgered (G9); disabling safeguards → G2 refusals + S7 + AT-H1-05 as the Stage-6 precondition; overfitting a local suite → S3 `estimated` only, S5 `full_set` held-out + retention, S6 transfer, S10 retirement; silent widening → `classify` at S1 and S7, `AuthorityViolation`, X6 (ADR-0182). Answered.
- **OQ-025 (which component deserves compute; with WS-F4):** the pipeline records `SearchBudgetRecord.allocation` per slot and a per-slot `search_time_benefit` history in the corpus; `SlotAllocationPolicy` defaults to `concentrate` with floors (S-092); `mode = voi` is F4's scheduler over that history. Partial; F4 owns the estimator.
- **OQ-216 (transfer test before promoting an induced procedure):** `require_transfer_test = {profiles: ≥ 2 families} ∨ {1 family ∧ ≥ 1 held-out environment}` for promotion to `definition`; a single-profile pass promotes to `principal` only, with `conditioned_on` and a debt record whose removal test is S10; `charged_to = instrument`. Answered (WS-D4/I2 to confirm).
- **OQ-280 (untrusted-monitor critics gating evolution arms):** never a gate (G7); as a selector inside S3–S4 only with: a `CalibrationRecord` against a deterministic reference on a pre-split labelled subset; honeypot items in the counterexample set; a fixed human audit budget per campaign (`instrument`), with the audited share reported; evidence paraphrased where the critic shares the beneficiary's family. ### 6.11 Acceptance-criteria sketch (Stage 6; executable fixtures unless marked static)

- **AC-I5-1 (G1, static + fixture).** A campaign whose S7 survivor is sealed by the evolution process's own endorsement is refused `SealRefused{not_human}`; sealed by a `definition`-class human it transitions to `sealed_candidate`; AT-H1-05 (i)–(iv) pass on the fixture campaign.
- **AC-I5-2 (G2/S1).** Fixture candidates that (a) widen a grant, (b) loosen a hard budget, (c) loosen a `validity_policy`, (d) edit Π, (e) edit a MUST-code pointer, (f) edit a suite validator, (g) edit the evolution service's definition are each refused with the named code at S1 and again at S7 after re-seal.
- **AC-I5-3 (S2).** A candidate without evidence refs, without a predicted metric, or naming a `held_out` task is `HypothesisUnfalsifiable`/`LeakedSplit`; a valid hypothesis stores `derived-from{hypothesis, trajectories, candidate_id}` on every changed node (ADR-0016 AC-7 shape).
- **AC-I5-4 (S3).** On a fixture where the prediction is wrong, `PredictionFalsified` rejects before any S4 spend; screen rows carry `estimated{…}`; the set ⊆ `search ∪ dev`.
- **AC-I5-5 (S4, T-LCD-14 gate).** A campaign arm without `MatchSpec{matched_total}` or with `search_budget = unknown` cannot transition past `searched`; `search_time_benefit` is computed against `oracle_best_of_n` with N = the arm's rollouts; a fixture with equal search spend but a negative `search_time_benefit` still proceeds (label, not gate) and the report says so.
- **AC-I5-6 (S5).** `artifact_benefit` is `full_set` on `held_out` with `task_split_hash` older than the campaign's first event (else `LeakedSplit`); a fixture that regresses two previously-passing tasks beyond margin is `RetentionRegressed{tasks}`; a fixture that trips `false_completion_rate` is `VetoRegressed`.
- **AC-I5-7 (S6).** `transfer` on one held-out family yields a `TransferProfile`; with one family the acceptance report's `portability_label = reported`; with two families + one held-out level it may be `portable`; a model-conditioned profile forces `conditioned_on` + debt record; activation/following rates are computed for every new `ContextItem`/`Procedure`/`HarnessRule` (deterministic detectors) or rendered `n/a{observability}`.
- **AC-I5-8 (S7).** `classify_policy_edit = widening` on any policy leaf, an opaque body without interface, or `placement = in_process` on a candidate payload is refused; the LT-01…12 battery and the security vetoes are byte-equal or better vs base on the Stage-3 security suite.
- **AC-I5-9 (S8 canary; G3).** In `shadow` mode the candidate branch defers every irreversible effect and never releases it (AC-B4-5 joined); in `split` mode an injected veto trip triggers automatic `revert` within one settlement, the lineage shows `supersedes{reason: revocation}`, live runs show `lifecycle.run.rolled_back`, the principal receives an escalation, and nothing is deleted.
- **AC-I5-10 (S9/S10; G4, T-LCD-05).** `publish` of an accepted edit without a complete `AssumptionDebtRecord` is `ConditionedRuleIncomplete`; a forced `model_version_change` trigger moves the edit to `expiring`; the `retirement` experiment on `head` vs `apply(head, invert(diff))` returns a `ComparisonReport{benefit_kind: artifact_benefit}` and a non-inferior removal yields `retired` as a supersession.
- **AC-I5-11 (G9, never delete; T-LCD-10).** After a campaign with three rejected, one reverted and one active candidate, `lineage(exp/<id>/)` lists all five with reports; candidate identity is content-derived (`candidate_id` stable under re-registration); renaming a compiled surface in a candidate produces a profile-version diff, not a candidate.
- **AC-I5-12 (G8; ADR-0163 L4).** The leaderboard entry of an accepted candidate carries `selection{n_candidates_registered, rule, search_budget_ref}`; `n_candidates_registered` equals the campaign ledger's `candidate.transitioned{to: proposed}` count (rejected included).
- **AC-I5-13 (stop rule; S-094).** A fixture proposer returning `NoAddressableFailure` stops the campaign with `stopped{no_addressable_failure}`; `max_consecutive_rejections` reached stops with `stopped{stagnation}`; both are ledgered and the corpus's `slot_history` is exported for WS-F4.
- **AC-I5-14 (proposer conformance; T-LCD-07/12).** Every registered `evolution_proposer` variant passes its `ConformanceSuite` out of process: isolation probes (no read outside the corpus; no held-out path; no network), the property "never emits an excluded target", and the executable "≥ 1 S2-valid hypothesis on the golden corpus"; a variant declaring `uses_judge = false` that calls a judge is `DRIFT`.
- **AC-I5-15 (hosted; OQ-382).** A campaign over a hosted participant's SUPPORTED coordinates with one `reported`-only budget dimension is refused `IncommensurableMatch` at `register`; with enforced dimensions it runs and every component-level cell is `n/a{class}`.
