## 1. Scope & boundary

This workstream decides **the mechanism that makes "modular/extensible" true**: (i) the **plugin contract model** — what a third-party *package* is (identity, manifest, the contributions it may carry, the Core contract versions it requires, the grants it *requests*, the isolation it *declares*), and how a package becomes registry records (WS-J2) and extension records (WS-H5) at `resolve`; (ii) the **loading / isolation contract** — the *variant-host boundary* (the kernel↔extension ABI) through which every non-kernel component variant, hook, and executable contribution is driven: its verbs, placements, version negotiation, what crosses it, what never crosses it, and how every crossing is ledgered and charged; (iii) the **conformance-testing contract** for plugins — the suites a package must pass before it is admitted at a given `require_conformance` floor, layered over WS-J2's per-class suites; (iv) **versioning and compatibility** of plugins against Core contract versions (over WS-L4's identity model); (v) the doc 3 §1.3 rule — *no extension reaches another extension's internals except through Core-defined contracts* — stated as **enforceable invariants** the build ladder, the readiness gate and the runtime each check; and (vi) the **C0 / C1–C4 extension DAG** as a declared, checkable structure rather than a diagram.

It explicitly leaves to neighbours: registry semantics — record kinds, envelope, `register/publish/resolve/query`, per-class `ConformanceSuite`/`ConformanceReport`, namespaces and foreign import (**WS-J2**; adopted verbatim — this dossier fixes what a *package* contributes and how it is *driven*, J2 fixes what a *record* says); the three-leg trust record, provenance class on injection, attestation/`pin`, isolation classes and the model-install path (**WS-H5**; adopted verbatim — this dossier fixes the ABI those isolated processes speak, not their trust); the assembly grammar, `ClassRecord`/`VariantRecord` base shapes, `compose → resolve → validate_assembly → seal`, `instantiate` and `lifecycle.component.bound` (**WS-A5**; adopted — this dossier fixes what `instantiate` does across a process boundary); identity, supersession, name histories and reproducibility levels (**WS-L4**; adopted); the ecosystem-boundary contract's *surface* side — SDK/embedding API, generated clients (**WS-K4**, which co-owns the WS-L1 §6.5 contract with this dossier per ADR-0050 D3; this dossier owns the *kernel↔extension* binding of that contract, K4 the *kernel↔surfaces* binding); the sandbox helper protocol and effect execution stages (**WS-E5/B5**, ADR-0100/0136 — the variant host is a *client* of the helper's placements, never a second sandbox); hook *semantics* as HIR guards (**WS-F1/A3**, OQ-165 — this dossier fixes what a hook contribution may return across the boundary); every per-class contract (Phase 2 owners); packaging formats, licensing and distribution channels (**WS-L6**); every ecosystem question (**WS-L1**, ADR-0050).

## 4. Findings

### 4a. Mechanism evidence (a failure mode exists / an architecture is implementable)

**F1 — Every audited plugin manifest is an *inventory of contributions by kind* plus store metadata; none is a program.** Pi's manifest is four lists of entry points (`extensions, skills, prompts, themes`, S-113 `pi-manifest.ts`); gemini's is `mcpServers, contextFileName, excludeTools, settings, themes, plan` with hooks, skills, agents, policy rules and checkers loaded from conventional subdirectories (S-119 `extension.ts` L24–50; `config.ts` L396–448; `extension-manager.ts` L870–935); codex's is `paths{skills[], mcp_servers?, apps?, hooks?}` plus an `interface` block of store fields (S-107 `plugin/src/manifest.rs` L8–57), generic over the resource locator so one shape is validated locally and remotely; Claude Code's `plugin.json` is the same with `dependencies` and typed `userConfig` (S-184); goose accepts two foreign manifest formats and lowers both into one install record (S-112 `plugins/mod.rs` L18–60). The only non-inventory fields are *claims* (codex `interface.capabilities: Vec<String>`; Agent Skills `allowed-tools`; MCP annotations — ADR-0063 L3 already says claims never reach the monitor). **Consequence (§6.1):** `PluginManifest/1` is an inventory whose entries are exactly the WS-J2 `RecordKind`s a package may contribute (`variant`, `capability`/`mcp_server`, `procedure_profile`/skill, hook, `validator`, `model_profile`, `benchmark_adapter`, `environment_family`, `metric_declaration`, instruction files) — each entry resolving to a registry record with its own identity and trust legs — plus the *requirements* block no audited manifest has (Core contract versions), plus requested grants as claims. Nothing in a manifest is executable; every executable is a `code_identity` leg of a trust record (ADR-0063).

**F2 — One operation-shaped contract can drive in-process, subprocess, container-placed and remote implementations, and the placement is a data tag on the registration — goose proves it; the component model and the editor extension host generalise it.** goose drives *every* extension through `McpClientTrait` (`list_tools/call_tool/get_info/get_instructions/list_resources/read_resource`, S-112 `mcp_client.rs` L108–142) regardless of whether the tag was `platform` (in-process factory), `builtin` (in-process MCP over an in-memory duplex, or `docker exec -i <container> goose mcp <name>` when a session container exists), `stdio` (child process) or `streamable_http` (remote) (`extension_manager.rs` L1474–1610). VS Code declares the same principle at product scale: extensions run in a separate host process so that they cannot impact startup, slow the UI or modify it, with three host kinds selected against the extension's declared `extensionKind` (S-562). The component model makes the contract the *only* channel ("a component may not export a memory"; composition = exports satisfying imports; S-560). ADR-0023 decision 5 already fixed "locality is a property of the variant registration, never of the class contract" (T-LCD-12). **Consequence (§6.2):** the variant host is one protocol with a closed placement sum `{in_process (kernel-ecosystem first-party only), subprocess_confined, container, remote}` mapped one-to-one onto ADR-0063's `IsolationClass` (minus `host_unconfined`, which is admissible for tool executables under `authority_cap` but never for a *component variant* that the kernel invokes on the hot path — see §5). `component_model` is a declared *future* placement (C2) gated on WASI 1.0 (S-165, S-165; ADR-0050 revalidation trigger 3).

**F3 — The extension surfaces that matter are *closed, named lifecycle points with typed input and output*, and the two failure modes are (a) a mutable shared output that the last plugin silently wins, and (b) an output that can raise authority.** opencode's `Hooks` is a closed map of ~20 named points (S-111 `packages/plugin/src/index.ts` L222–335) and `trigger` iterates plugins **sequentially mutating one `output`** (L284–297): `permission.ask` may set `status = allow`, `tool.execute.before` rewrites `args`, `tool.definition` rewrites a tool's description and parameters. Pi's `on(event)` covers ~40 events; `emitToolCall` short-circuits on the first `block` but does not catch handler exceptions, while `emit` does (S-113 `runner.ts` L851–882 vs L982–1004) — error isolation differs per event. Claude Code's hook protocol is records-in/records-out over a process boundary, with parallel execution and typed outputs — but `permissionDecision: allow` and `updatedInput` are in the vocabulary, and "Exit 2 blocks whether or not JSON is printed" while other non-zero codes do not (S-563). gemini admits `rules` and `checkers` from an extension's `policies/` directory but refuses `ALLOW`/`YOLO` rules contributed by extensions (WS-H5 F3; `policy/config.ts` L244–252). ADR-0053 D-5/decision 5 and ADR-0100 I-3 already fix the type-level answer for our kernel: *executors report, never decide*; a classifier or reviewer "may withdraw a pre-authorization … and may feed Π as a raise-only input; it can never create authority". **Consequence (§6.3):** every extension-facing operation is a **guard-shaped** operation — records in, a *verdict-or-proposal* record out, where the verdict sum is `{pass, annotate(Text ≤ external), narrow(deny | ask | attenuate), propose_replacement(Proposal at ≤ hook authority)}` and never `allow`, never a label, never a mutated proposal; multiple guards compose by **meet** (the most restrictive wins, order-independent), never by last-wins; a throwing or timed-out guard yields `no_decision` — never `allow`, and for a guard that a definition marks `required`, `no_decision ⇒ deny`. This is the same shape as ADR-0110's validator ("annotate-or-reject, never rewrite") applied at the control boundary β.

**F4 — In-process extension APIs hand the extension the host's internals, and that is exactly what "no extension reaches another extension's internals" must forbid.** goose's in-process `PlatformExtensionContext` contains a weak reference to the `ExtensionManager` (i.e., every *other* extension), the session store and the scheduler (S-112 `platform_extensions/mod.rs` L230–237); Pi's `ExtensionAPI` exposes `exec`, `setModel`, `setActiveTools`, `sendUserMessage`, `getSessionManager`-class accessors and a `VIRTUAL_MODULES` table of the host's own packages (S-113 `types.ts` L1252–1400; `loader.ts` L48–60); opencode's `PluginInput` carries an authenticated client to the host's own HTTP surface, a shell and `experimental_workspace.register` (S-111 `packages/plugin/src/index.ts` L60–86); gemini loads a `trajectoryProviderModule` in process (S-119 `config.ts` L437). In each system an extension can therefore (i) act on the agent (send messages, switch models, run commands) outside any contract, (ii) reach other extensions through the shared process, and (iii) inherit the process's ambient authority — the S-103/S-104 escalation vector and CF-141's rejected precedent. Logos states the opposite architecture: "a plugin is a process", the router keeps only a rebuildable routing table, and recovery state lives "in an append-only transcript owned by no process" (S-073, `provisional`) — which is precisely ADR-0026's ledger plus ADR-0053's kernel. **Consequence (§6.4):** the reach of an extension is *defined by the manifest's declared dependencies on Core contracts and nothing else*; the variant host gives each plugin its own process, a cleared environment, an fs allowlist that excludes every other plugin's root, and a host-callback set whose members are all Core operations over records (`propose_effect`, `read_view`, `emit_diagnostic`, `request_budget`) — there is no callback that names another extension. Inter-extension effects happen only through kernel-visible objects (ledger records, HIR entities, effects) that the *other* extension observes through its own contract.

**F5 — A pre-load compatibility gate against the *host's* declared contract version is the only compatibility mechanism found, it is applied inconsistently, and no system versions the contract the plugin *implements*.** opencode checks `engines.opencode` only for npm plugins and imports file plugins without any gate (S-111 `loader.ts` L118–127; `shared.ts` L194–204); Pi has no compatibility field (its manifest is four path lists); gemini and codex carry `version` on the manifest but no host-range field; goose's `platform` extensions are compiled in; VS Code's `engines.vscode` and activation events are the mature form. None declares which *hook surface version* or *tool contract version* the plugin implements — the shape WS-J2 fixed as `VariantRecord.contract_range` against `ClassRecord.contract_version`. **Consequence (§6.5):** `PluginManifest/1.requires` is a typed record of ranges over **Core contract versions** — `hir_dialect`, `registry_dialect`, `plugin_abi` (the variant-host protocol version), and per contribution `contract_range` — checked at `resolve` (`ContractIncompatible` before any load, opencode's stage order generalised) and re-negotiated at `hello` (probe-first, ADR-0099); the Core publishes a `ContractVersionPolicy` (supported ranges, sunset dates) as MUST-data so that deprecation is a record, not a release note.

**F6 — Atomic registration and typed load failure are precedented and cheap.** Pi queues an extension's registrations while its factory runs and applies them on `commit()`, discarding them on failure (S-113 `loader.ts` L247–300); opencode's loader returns a typed stage on failure (`install | entry | compatibility | load`; L15–60); Omnigent records failed contributions in `load_errors` and continues (WS-J2 F4); ADR-0025's `instantiate` already returns `BindFailure{slot, variant, reason ∈ {not-installed, trust-denied, locality-unsupported, contract-mismatch}}`. **Consequence (§6.2):** `bind` is atomic per slot — a plugin whose `hello` succeeds but whose contribution fails to bind leaves no partial registration; the ledger's `lifecycle.component.bound{…, bind_result}` (ADR-0025) records the outcome; a failed plugin is a `RegistryDiagnostic` (WS-J2 R10) and never a startup failure.

**F7 — Deny-by-default resource declarations in the plugin manifest are precedented outside the agent field and absent inside it.** Extism's manifest grants no network host and no filesystem path unless listed, caps memory, and pins code by hash (S-561); the component model's imports are the complete list of what a component can call (S-560). In the agent corpus goose's `env_keys`/`available_tools` (S-112 `extension.rs` L183–199) and Agent Skills `allowed-tools` are the only analogues, and they are claims read by the host with ambient authority intact (WS-H5 F2). ADR-0063 fixed the trust-record legs and isolation classes. **Consequence (§6.1):** the manifest's `requests` block (grants *asked for*: effect domains, fs roots, egress destinations, env keys, budget share, `hot_path` operations) is lowered at `seal` into a `Permission` the author accepts or narrows — deny-by-default like Extism, conferred like ADR-0035 (only an issuer ≥ `principal`), and enforced by the helper's `ContainmentPolicy` (ADR-0060) on the plugin's process.

**F8 — The extension DAG is checkable with three existing tests plus one new one.** T-LCD-06 already requires a dependency-graph check ("no dependency edge points from IR entity definitions to the Hosting ABI") and a *removability* build ("with hosting disabled the native acceptance suite is unchanged"); WS-A5's `validate_assembly` stage 7 computes `hosting_edges = []`; ADR-0025 records the instance graph per run through `lifecycle.component.bound`. What is missing is a declaration on every spec item of its **tier** and its **contract dependencies**, and a rule for what counts as an *internal*. **Consequence (§6.4):** every Spec §7.2 #5 subsystem section and every `ClassRecord`/`PluginManifest` carries `tier ∈ {C0, C1, C2, C3, C4}` and `depends_on: [ContractRef{kind ∈ {class_contract, record_kind, dialect, protocol_binding}, id, version_range}]`; an *internal* is anything not reachable by a `ContractRef`; the spec DAG check (readiness gate) verifies acyclicity, tier monotonicity (an item depends only on tiers ≤ its own) and contract-only edges; the build ladder verifies removability per tier (build with C(n+1…4) absent; the C(n) acceptance suite is unchanged); the runtime verifies the same property by construction (F4).

## 5. Disconfirming evidence & negative results

**Against out-of-process for every third-party variant ("goose keeps `platform` extensions in process because some need direct access; the per-call serialisation distorts the hot-path latency the Lab measures; Pi's readability comes from in-process code").** *Why this does not overturn:* CF-141 and ADR-0063 L5 decided it; the *reason* the in-process precedents are readable is the reason they are unsafe — the API hands the extension the agent (F4). The cost is real and is treated as a measured factor, not denied: the variant host stamps every invocation with a `boundary_overhead` span (§6.6, M-point proposal), OQ-075 fixes the per-class ceiling from Stage-2 data, and `hot_path` classes admit out-of-process variants only under that ceiling. First-party kernel-ecosystem variants remain in process (ADR-0050 D1), so Stage 0–2 pays nothing. Logos' 1/823-of-first-token figure (S-073) suggests the cost is small but is `provisional` and is not relied on.

**Against a narrow-only guard contract ("every hook system in production lets hooks allow, rewrite input, or transform messages; opencode's `tool.definition` and `experimental.chat.system.transform` are how plugins fix model-specific behaviour; forbidding them makes plugins toothless").** *Why this does not overturn:* the three things those hooks do have homes that keep authority and identity intact — (i) rewriting a tool's *surface* (description, parameters) is a Model Profile rule or a `SurfaceFamily` variant (ADR-0090/0124), which a plugin may contribute *as records* with assumption-debt (T-LCD-05); (ii) rewriting a *proposal's* arguments is `propose_replacement`, which re-enters `resolve → authorize` as a new proposal at the hook's authority (ADR-0100 stage order) — nothing is lost except silence; (iii) transforming the system text is a `context_policy` variant or a `Text` leaf contribution under the role-placement invariant (ADR-0034 RP). What is refused is only the *silent* form and the `allow` verdict, which every audited compromise used (WS-H5 F1). The utility cost is measurable by the Lab under matched budget (AC-L5-9), not assumed.

**Against a `requires` block over Core contract versions ("no plugin ecosystem versions its hook surface; contract versions will churn every release and every plugin will be `ContractIncompatible` on day one").** *Why this does not overturn:* opencode's `engines` gate and VS Code's `engines.vscode` show plugin authors already declare host ranges; WS-J2 already fixed `contract_range` on variants and `contract_version` on classes; the churn risk is handled by a `ContractVersionPolicy` with **sunset windows** (a class contract version stays supported for a declared window after its successor is published; refusal is typed and dated), by the rule that additive changes never bump `contract_version` (a new optional operation or field is a *capability* declared tri-state, T-LCD-07), and by `hello` negotiation which lets a plugin implementing several ranges pick one. The alternative — untyped "works with latest" — is CF-330's rejected precedent.

**Against a single variant-host protocol for hooks, variants and tool executables ("hooks want a stdin/stdout one-shot; variants want a persistent session; MCP servers already have a protocol; one protocol is the LCD trap").** *Why this does not overturn:* the protocol is a *session* with a verb set, and the three kinds differ only in which verbs they implement, declared at `hello` (T-LCD-07: undeclared = `unknown`, never intersection): a hook implements `invoke` for one guard operation and may declare `one_shot: true` (the host spawns per invocation — Claude Code's shape); a variant implements `bind`/`invoke`/`stream`; an MCP server is *not* driven by this protocol at all — MCP is the sole standardized tool-supply channel (ADR-0096) and the extension record's isolation class places the server process; the variant host only *launches* it under the same placement and containment. The transport discipline (protocol-only channel, diagnostics channel, negotiation) is shared because MCP stdio already fixed it (S-153 stdio.mdx).

**Against the extension DAG as an enforceable structure ("tiers are a planning fiction; real dependencies cross tiers — the C2 IFC monitor is called by the C0 kernel; the C1 router is invoked by the C0 control loop — and a strict DAG will force awkward indirection").** *Why this does not overturn:* the rule is about *direction of knowledge*, not call direction — a C0 kernel may *invoke* a C1/C2 component only through a C0-defined class contract whose Stage-1 variant is the trivial one (doc 3 §1.3 rule 3: "every subsystem ships behind a stable contract before its rich variant"); the H2 monitor check 3 is a C0 contract (`flow`) with a C0 no-op implementation and a C2 rich variant (ADR-0054 "one lattice, two enforcement depths"); the router is a C0 `router` class contract with a C0 pass-through variant (ADR-0121). The DAG check therefore tests exactly what §1.3 promises: *removing* C(n+1…4) leaves a buildable, acceptance-passing C(n). Where a genuine upward edge exists, it is a spec defect the gate should find — that is the purpose of the check.

**Against deferring Wasm/component-model placement ("the component model is the only design that makes contract-only reach *provable* rather than policed; deferring it means policing").** *Why this does not overturn:* WASI 1.0 is targeted for late 2026/early 2027 (S-165, S-165); the ADR-0050 kernel ecosystem hosts a runtime natively (S-247) and revalidation trigger 3 exists precisely for this; process isolation + helper containment (ADR-0060/0100) *is* the policed form and is the same mechanism the kernel already relies on for tools. The placement sum is closed-but-growable by dialect bump, the manifest's `requests` block is already component-shaped (declared imports), and a Wasm host is a drop-in placement behind the same verbs. Recorded as OQ-410.

**Negative results from the audit.** (i) No audited harness versions the *contract* a plugin implements (only, at best, the host it runs on); (ii) none composes multiple hooks order-independently (all are sequential and last-wins or first-block); (iii) none gives hooks a `no_decision` outcome distinct from `allow` on error/timeout except Claude Code (timeout renders no decision) — and there other non-zero exit codes let the action proceed; (iv) none records which extension's code produced which effect *and* which extension's text was in the proposing context (WS-H5 AC-H5-10 is the first); (v) none declares the resources a plugin may use in the manifest with deny-by-default semantics (Extism does, outside the field); (vi) none has a spec-level or build-level check that an extension cannot depend on another's internals — in every audited system it can, by import.

## 6. Recommendation for the spec

### 6.1 The plugin contract model (Spec §8; ADR-0180)

A **plugin** is the packaging unit for third-party contributions (ADR-0008: "plugin" = third-party packaging). It is an `ExtensionRecord{kind: plugin}` (ADR-0063) whose `manifest` conforms to `PluginManifest/1` and whose `contributes[]` are registry records under `registry/1` (WS-J2). A plugin has no behaviour of its own: it is the closure of its contributions plus the trust record that covers them.

```
PluginManifest/1 (data document; canonical form idp/1; content-addressed by the tree rule over the package)
  identity        : { namespace, name, version_label? }            # ADR-0037: label is a claim; identity is content
  requires        : { hir_dialect: Range, registry_dialect: Range, plugin_abi: Range,   # Core contract versions (F5)
                      contracts: [ ContractRef{ kind ∈ {class_contract, record_kind, protocol_binding}, id, version_range } ],
                      records:   [ VersionedRef ] }                # pinned dependencies on other published records (variants, profiles…)
  contributions   : [ Contribution{ kind: RecordKind ∈ {variant, capability, mcp_server, procedure_profile (skill), hook,
                                      validator, model_profile, surface_family, benchmark_adapter, environment_family,
                                      metric_declaration, instruction_file, harness_rule},
                                    path_or_locator, declaration: TypedValue,          # the record's authored form (J2 schemas)
                                    executable?: { code_pointer, isolation: IsolationClass, placement_preference?,
                                                   one_shot?: bool, host_requirements: TypedValue },   # per executable (H5 leg ii)
                                    contract_range? } ]            # for variant/hook/validator: which ClassRecord.contract_version(s)
  requests        : { effects: [ {domain: EffectDomain, scope} ], fs_roots: [], egress: [ Destination ], env_keys: [],
                      budget_share?: BudgetSpec, hot_path_operations: [] }             # CLAIMS (ADR-0063 L3); lowered to a Permission at seal
  claims          : TypedValue                                     # allowed-tools, annotations, "capabilities" strings — never inputs to decisions
  conformance_claims : [ ConformanceReport{produced_by = publisher_claim} ]           # displayed at review; never satisfy `probed` (J2)
  parameters?     : { <param_id>: ParameterSpec }                  # plugin-level userConfig (ADR-0023 grammar; `sensitive` ⇒ SecretRef)
  summary         : Text{authority ≤ external}                     # human surface; never model-facing (J2 R-NM)
  ext             : ExtensionSlots                                  # ADR-0015 rules; never decides admission, authority or compatibility
```

**Rules.** (P1) *Inventory only:* every `contribution` becomes one registry record with its own `version_id`, envelope and — when it has an executable — its own trust legs; the manifest carries no code, no closures, no host-language content (ADR-0023 decision 1; the pointer rule ADR-0024). (P2) *Requests are claims:* `requests` is lowered at `seal` into one `Permission` issued by the sealing principal (ADR-0035 check 1) after the author accepts or narrows it at `review` (ADR-0064); the helper enforces it as the plugin process's `ContainmentPolicy` (ADR-0060); the default when the author accepts nothing is **deny everything** (Extism rule). (P3) *Pinned in sealed form:* `requires.records[]` and every `code_pointer` are `version_id`/`ContentAddress` after `resolve` (ADR-0036 N5; `UnpinnedInSealedForm`). (P4) *Unknown contribution kinds are errors* (`UnknownRecordKind`, J2 AC-J2-2); unknown non-`ext` manifest keys are errors (ADR-0023 rule 5). (P5) *Foreign manifests* (Claude Code `plugin.json`, gemini `gemini-extension.json`, codex `agent-plugin`, Pi `package.json#pi`, Agent Skills trees, MCP `server.json`) are `import`ed with a `LossReport` (J2 §6.6; T-LCD-11) — every audited format lacks `requires`, `requests` and per-executable isolation, which the report names; `export` lowers a first-party plugin to those formats with the same report. (P6) *Namespaces:* a plugin publishes only into a namespace its publisher owns (J2 `NamespaceRecord`); third-party plugins can never publish into `hh/`.

**Resolution pipeline** (composes ADR-0064 and ADR-0025; one resolver): `discover(declared sources) → resolve(candidate) → check_compatibility(manifest.requires, ContractVersionPolicy, class_catalog) → review → seal → bind` with typed failures `SourceNotAllowed | UnpinnedInSealedForm | AttestationRequired | ContractIncompatible{ref, offered_range, supported_range, sunset?} | UnknownRecordKind | LocalityInadmissible | RequestsExceedCap{authority_cap}` — all before any executable is launched (opencode stage order, generalised to every source kind).

### 6.2 The loading / isolation contract — the variant-host boundary (Spec §8; ADR-0181)

The **variant host** is the kernel component (MUST-code, ADR-0024) that drives every non-kernel executable contribution — component variants, hooks/guards, validators, benchmark adapters — over one protocol, `plugin_abi/1`, which is the kernel↔extension binding of the WS-L1 §6.5 ecosystem-boundary contract (ADR-0050 D3/D4; CF-023). It is *not* the Hosting ABI (ADR-0005/0098; CF-208): a hosted participant is an `OpaqueProcess` with no slots (T-LCD-06); a plugin is a set of slot-fillers with declared contracts.

**Placements** (closed sum; one-to-one with ADR-0063 `IsolationClass` less `host_unconfined`): `in_process` — first-party variants of the ADR-0050 kernel ecosystem only (`hh/` namespace; the assembler binds them directly, ADR-0025 `instantiate`); `subprocess_confined` — the default for third-party variants and hooks: the helper (ADR-0100) launches the plugin's process with the plugin's `ContainmentPolicy` (cleared environment + declared env keys, fs allowlist = the plugin's own root + declared roots — **never another plugin's root**, no network unless `egress` was granted, resource limits, kill-on-timeout); `container` — the session/environment container (ADR-0136) for variants that must see the workspace; `remote` — a network endpoint under H4 egress policy with `ProtocolBinding` (ADR-0099). `component_model` is reserved (dialect bump) pending WASI 1.0 (OQ-410). `host_unconfined` is inadmissible for anything the kernel invokes on a decision path (variants, hooks, validators); it remains admissible only for tool executables under `authority_cap` (ADR-0063).

**Verbs** (records-in/records-out; canonical `idp/1` encoding; every message carries `protocol_version`, `schema_hash`, `seq`; WS-L1 §6.5 I1–I5):
- `hello(plugin_abi_version, plugin: {version_id, content}, contract_versions_offered: [ContractRef], capabilities: TriState) → {host_id, negotiated: {plugin_abi_version, contract_versions_chosen}, registry_snapshot_id, kernel_capabilities}` — probe-first (ADR-0099); unknown fields rejected (Pi protocol precedent, I2); `ProtocolVersionMismatch` refuses; the plugin's `version_id` must equal the sealed definition's pinned reference (`PinMismatch`), J2's requirement that `hello` carries `contract_version`, `variant version_id` and `registry_snapshot_id` is satisfied here.
- `bind(slot, class_id, contract_version, variant: VersionedRef, params, profile: ModelProfileRef, account: ResourceAccountRef, budget: BudgetNodeRef) → binding_id | BindFailure{reason}` — atomic per slot (F6); T-LCD-08 satisfied by construction (profile and account are inputs); emits `lifecycle.component.bound{…, locality = placement, bind_result}` (ADR-0025).
- `invoke(binding_id, operation, inputs: [canonical document], reservation: BudgetReservationRef, deadline) → outputs: [canonical document] | TypedFailure` — `operation` is one of the class contract's operations; inputs/outputs are the class's declared documents (`Cue`/`ControlDecision`, `ContextView`/`ContextPlan`, evidence bundles…); every invocation opens a ledger scope (§6.6) and consumes the reservation (ADR-0040 reserve-before-spend; `InsufficientBudget` is a pre-dispatch refusal).
- `stream(binding_id, operation, …) → stream<document>` with `seq`-based resume; `cancel(invocation_id)`; `unbind(binding_id)`; `close(host_id)`.
- **Host callbacks (plugin → kernel), closed:** `propose_effect(Proposal) → EffectRef` (the *only* way plugin code causes a world effect — it enters ADR-0100 `resolve → authorize → …` under the plugin's Permission; the plugin never executes effects itself and never receives a `KernelDecision`); `read_view(view_kind, until_seq) → projection` (ADR-0026 views the plugin's grants cover; never raw handles, never Π, never other plugins' records except through public registry `query` under the snapshot); `request_budget(amount) → reservation | InsufficientBudget`; `emit_diagnostic(record)` (ephemeral, L3 — never an authoritative event: plugins **propose**, the kernel **appends**). There is no callback that names another extension, the agent loop, the model gateway, the session store or the reference monitor (F4).
- **Invariants.** V1 *no authority crosses inward*: no message from a plugin carries a `Permission`, a label, a `KernelDecision`, a risk class that lowers, or a retryability that raises (ADR-0100 I-3, ADR-0053); outputs are stamped `origin = tool(extension_ref)`, `authority ≤ delegate` for model-derived content and `≤ external` for free text, `taint ∋ extension_id` (ADR-0063 L6). V2 *byte-identical documents*: what the ledger records is what crossed (WS-L1 I4; CF-058). V3 *one plugin, one process, one policy*: a placement never hosts two plugins' code in one process; a plugin process never sees another plugin's root, socket or environment. V4 *no ambient channel*: `net.mode ∈ {none, mediated}`; secrets only as `SecretRef` (ADR-0057); the attribution token is not a credential (ADR-0100 I-2). V5 *exact pinning both ways*: the kernel refuses a plugin whose `version_id` differs from the sealed pin; the plugin refuses a host whose `plugin_abi` is outside its declared range (WS-L1 I3). V6 *single source of truth*: the class contracts' document schemas and the `plugin_abi/1` schema are exported from the kernel's schema source; every plugin-side binding is generated and CI-checked (ADR-0050 D3 I1); a schema drift is a build failure, never a runtime negotiation.
- **Failure modes.** `ProtocolVersionMismatch`, `PinMismatch`, `ContractIncompatible`, `BindFailure{not-installed | trust-denied | locality-unsupported | contract-mismatch | isolation-unavailable}`, `InvocationTimeout` (→ `no_decision` for guards; a typed failure for variants that the class's fallback ladder handles, e.g. ADR-0075's compaction fallback), `PluginCrashed` (session `detached`; the kernel re-`hello`s from the ledger — Managed-Agents `wake` shape; open effects proposed by the plugin follow ADR-0030 `unknown → probe`), `UnhandledOperation`, `SchemaViolation`, `AuthorityCrossing` (V1 violated — the message is refused and `security.extension.violation` appended).

**Hooks as guards (closes the L5 half of OQ-165).** A hook contribution is a `HarnessRule` whose `action` is a `CompiledPayload`/code pointer bound at a `DecisionPoint` (ADR-0016 β) and driven through `invoke(binding, guard, {decision_point, proposal | cue | context_plan, ledger_cursor})`. Its output sum is `GuardVerdict ∈ {pass, annotate(Text{authority ≤ external}), narrow(deny(reason) | ask(reason) | attenuate(scope ⊂ requested)), propose_replacement(Proposal at ≤ hook authority), no_decision}` — never `allow`, never a mutated input, never a label. Multiple guards at one point compose by **meet** (`deny > ask > attenuate > annotate > pass`; `propose_replacement` is ordered before the original and re-enters `resolve → authorize` as a new proposal with `derived_from` the hook; `no_decision` is the identity unless the rule is `required`, where it is `deny`) — order-independent, so parallel execution (Claude Code) and sequential execution (opencode/Pi) yield the same verdict. A guard's `Permission` bounds what it may read (`read_view`) and it may never `propose_effect` inside a guard invocation (guards observe; effects are proposals of the agent process). This is F1's "hooks narrow, never widen" (WS-H5 F7) made into a type.

**OQ-258 answer.** A `control_strategy` variant may live out of process **through the variant host** (`invoke(step)` per control step with the `Cue`/`ControlDecision` documents F1 fixed), never through the per-run lab boundary (`submit`/`stream_events` are per-run verbs, ADR-0050 D2); admissibility at C1 is subject to the OQ-075 ceiling on `hot_path` classes; the lab-ecosystem variant is then just an out-of-process variant with a stratified `boundary_overhead`.

**OQ-353/-03 answers.** Registry operations that cross the kernel↔lab boundary are `resolve`, `query`, `catalog`, `slot_choices`, `snapshot`, `record_conformance` (records in/out, per design or per publish — never per model call); `register`/`publish`/`revoke` cross only as *requests* that the kernel's registry executes under `NamespaceRecord.policy`. The out-of-process conformance driver is the **variant host itself** in a `registry_ci` session: the same `hello/bind/invoke` verbs drive the suite's fixtures, under `subprocess_confined` by default (or the placement the variant declares), charged `instrument` (ADR-0039); no second driver exists.

### 6.3 The conformance-testing contract for plugins (Spec §8; ADR-0181)

A plugin is admitted at floor `require_conformance ∈ {none, declared, probed}` (J2 `RegistryPolicy`). Conformance has four layers, each a `ConformanceSuite` record pinned to the contract version it tests (J2 §6.3 form), run by the variant host as `registry_ci`:

1. **Protocol conformance (`plugin_abi/1` suite; C0/Stage 2)** — `hello` handshake with version negotiation, refusal of unknown fields, canonical-encoding round trip (byte equality across two implementations, AC-L4-5 shape), `seq`/resume on `stream`, `cancel` honoured within the deadline, crash recovery (`detached → hello(resume)`), every closed-sum input handled (`UnhandledOperation` only for undeclared operations).
2. **Isolation conformance (H5 AC-H5-5 shape; C0/Stage 2)** — probes: undeclared fs read, undeclared egress, ambient-credential read, another plugin's root, the kernel's socket — each refused by the helper with a ledgered refusal; declared equivalents succeed; `host_requirements` honoured.
3. **Contract conformance per contribution (J2 suites; Stage per class)** — the class's `static/contract/executable/property` tests driven out of process; a hook's suite additionally checks the **guard property**: every output parses as `GuardVerdict`, never `allow`, never a mutated proposal (a fixture that returns a rewritten `args` is `AuthorityCrossing`).
4. **Reach conformance (this dossier; C0/Stage 1 static + Stage 2 runtime)** — static: `manifest.requires` names only `ContractRef`s and pinned records; no path or locator inside a contribution points outside the package root; runtime: the *hostile-plugin fixture* (a plugin that attempts to import the host, open another plugin's root, connect to the helper's socket, spawn a process without `spawn_process`, and return `allow`) fails every probe with a typed refusal and the run proceeds.

**Plugin conformance kit (deliverable of Stage 3):** one **null plugin** per Stage-1–3 class (passes every layer; the reference for authors), the **hostile plugin** fixture, and a **golden manifest corpus** (valid, `ContractIncompatible`, `UnknownRecordKind`, `UnpinnedInSealedForm`, `RequestsExceedCap`). Reports are `ConformanceReport{produced_by = registry_ci}` and feed `variant_conformance_vector` (J2 R4); `publisher_claim` reports are shown at `review` and never count.

### 6.4 The extension-DAG rule as enforceable invariants (Spec §4, §9; ADR-0182)

Doc 3 §1.3: "Extension tiers (C1–C4) depend only on the Core and on each other along a declared DAG. No extension may reach into another extension's internals except through Core-defined contracts." Stated as invariants with their checks:

- **X1 Contract-only reach (spec + load).** A dependency is expressible **only** as a `ContractRef{class_contract | record_kind | dialect | protocol_binding, id, version_range}` or a pinned `VersionedRef` to a published record. An *internal* is anything not reachable through a `ContractRef`: another variant's implementation, process, files, private records, the kernel's internal projections beyond the views a Permission covers. There is no manifest field, assembly field or host callback in which an internal can be named — X1 holds by construction of `PluginManifest/1`, `Assembly` (ADR-0023) and `plugin_abi/1`.
- **X2 Tier monotonicity and acyclicity (spec).** Every Spec §7.2 #5 subsystem section, every `ClassRecord` and every plugin carries `tier ∈ {C0, C1, C2, C3, C4}` and `depends_on: [ContractRef]`; a C(n) item depends only on contracts whose *defining* tier is ≤ n; the graph over items is acyclic. Check: the readiness gate's spec-DAG check (extends T-LCD-06's dependency-graph check; `hosting_edges = []` becomes one row of a general `tier_violations = []`).
- **X3 Kernel-mediated interaction (run time).** Two extensions interact only through kernel-visible objects — ledger records, HIR entities, effects, registry records — each observed through the observer's own contract; the variant host's placement rules (V3) and closed callbacks make direct interaction physically unavailable. Check: isolation and reach conformance (§6.3 layers 2 and 4).
- **X4 Removability (build).** For every tier n, the build ladder must produce a working system with C(n+1…4) absent, and the C(n) acceptance suite must be unchanged (T-LCD-06's rule generalised from hosting to every tier). Every C0 class contract ships its trivial Stage-1 variant in C0 (doc 3 §1.3 rule 3) so that the removal of a rich C1/C2 variant never removes the *slot*. Check: `orchestrate-build` stage gate — a per-tier "build with higher tiers absent" job.
- **X5 Substitution without ripple (spec + registry).** Replacing a variant of class C with any `substitutable` variant (J2 `substitutable(a, b)`) changes no other item's `depends_on`; a change to a class contract is a new `contract_version` with a `ContractVersionPolicy` sunset, never an in-place edit. Check: `HirDiff` over the sealed definition after a `Rebind` touches only that slot (ADR-0025 AC-6 shape); a class-contract bump is a registry event.
- **X6 Authority never flows up the DAG.** An extension's `Permission` is issued at `seal` by the principal (ADR-0035) and attenuates through delegation (ADR-0053); an extension contributes `HarnessRule`s with `authority_cap` narrowing only; the evolution service (C4) edits only `HirDiff`s with `authority_delta ∈ {none, narrowing}` (ADR-0053 D-5). Check: `validate_assembly` (`AuthorityViolation`), `HirDiff.classification`, guard property tests.

**Tier assignment table for the extensibility mechanism itself** (feeds Spec §9): `PluginManifest/1`, `ContractRef`, `tier`/`depends_on` on class records and spec items, the spec-DAG check, `ContractVersionPolicy` — **C0/Stage 1**; the variant host with `subprocess_confined` placement, host callbacks, the guard verdict sum, `lifecycle.component.bound`/invocation scopes, isolation + protocol conformance — **C0/Stage 2** (the first out-of-process first-party variant, aligned with WS-J2 §6.7 and WS-A5 §6.8); the plugin conformance kit, reach conformance, `boundary_overhead` metrics and the OQ-075 measurement — **C0/Stage 3**; third-party publish/install/import/export, `TrustRootPolicy`-gated attestation, `remote` placement — **C1/Stage 4** (with WS-J2/H5); `container` placement for workspace-seeing variants — **C1/Stage 4** (with WS-B5); `component_model` placement and cross-plugin flow checks — **C2**; evolution-service plugins (`exp/` namespace, C4) inherit the same ABI with the ADR-0053 D-5 handle set — **C4/Stage 6**.

### 6.5 Versioning and compatibility (Spec §8; ADR-0180)

- **Identity** is WS-L4's: plugin `content` by the tree rule, manifest `version_id`, each contribution's `version_id`; `version_label` is a claim on a name-history entry (ADR-0037 I2); sameness across plugin versions is the L0–L4 ladder over the `HirDiff` of the contributions (ADR-0037 §6.4).
- **Compatibility** is declared as ranges over **Core contract versions**: `hir_dialect`, `registry_dialect`, `plugin_abi`, per-contribution `contract_range` (J2). The Core publishes `ContractVersionPolicy{contract: ContractRef, supported: [version], sunset: map<version, date | stage>, additive_only: bool}` as a `hh/`-namespace registry record (MUST-data). Rules: additive changes (a new optional operation, field or capability) never bump a `contract_version` — they are tri-state capabilities negotiated at `hello` (T-LCD-07); a breaking change is a new `contract_version` published with a sunset window during which both are supported; refusal is `ContractIncompatible{…, sunset?}`; `hello` negotiates the highest common version.
- **Updates** are supersessions (ADR-0064): a new plugin version is a new `ExtensionRecord` with `supersedes{edit}`; the definition moves by `HirDiff`; `authority_delta = widening` (new `requests`, higher text class, a hook gaining `required`) needs `human` origin (ADR-0017/0037 L3); running runs keep their pins until `verify_resume` (ADR-0025). The variant host **never** auto-updates a bound plugin (CF-330: every audited plugin system does; rejected).
- **Deprecation** of a plugin, a contribution or a contract version is a name-history status (`deprecated | yanked`) or a `ContractVersionPolicy` sunset — never deletion (ADR-0037 I1–I4); `resolve(mode = execute)` refuses past the sunset with a dated reason.

### 6.6 Data-model sketch

`PluginManifest/1` (§6.1) · `Contribution` · `ContractRef{kind, id, version_range}` · `ContractVersionPolicy` · `PluginRequests` (lowered to `Permission` + `ContainmentPolicy`) · `Placement ∈ {in_process, subprocess_confined, container, remote}` (+ reserved `component_model`) with the ADR-0063 mapping · `plugin_abi/1` message envelope `{protocol_version, schema_hash, seq, payload}` · `BindingRecord{binding_id, slot, class_id, contract_version, variant: VersionedRef, placement, host_id, permission: VersionedRef, budget: BudgetNodeRef}` · `GuardVerdict` (§6.2) · `HostCallback ∈ {propose_effect, read_view, request_budget, emit_diagnostic}` · ledger: `lifecycle.component.bound` (ADR-0025) gains `placement` and `host_id`; **proposed** `lifecycle.component.invoked{binding_id, operation, inputs_digest, outputs_digest | failure, boundary_overhead_ms, charged_to}` as the terminal event of a **proposed scope kind `component_call`** (ADR-0042's `scope_kind` sum is closed — CF-376 asks WS-I1/B1 to add it by dialect bump or to rule that the existing per-class scopes `context_assembly | compaction | validation | …` are the invocation scopes and only classes without one need the new kind); `security.extension.violation{extension_id, kind ∈ {authority_crossing, reach, isolation}, refused_message_digest}` (proposed to the ADR-0064 event family); metrics (class-scoped, ADR-0045): `boundary_overhead_ms` per `(class_id, placement)` at a new measurement point on the M1–M18 list (**proposed M19: variant-host invocation, kernel side, both edges**; CF-377 for WS-I1/L2), `guard_verdict_rate{verdict}`, `plugin_crash_rate`, `no_decision_rate` — all `n/a` for hosted participants (T-LCD-15).

### 6.7 Acceptance-criteria sketch

- **AC-L5-1 Manifest is inventory (C0/Stage 1).** A manifest with an inline body, a serialized closure, a path outside the package root, an unknown contribution kind or an unknown non-`ext` key fails `resolve` with the named typed error; the golden manifest corpus passes/fails byte-identically on two implementations.
- **AC-L5-2 Compatibility before load (C0/Stage 1).** A plugin whose `requires.plugin_abi` or any `contract_range` misses the `ContractVersionPolicy` is refused with `ContractIncompatible{…, sunset?}` and no process is ever launched (helper ledger shows no `spawn_process`); a plugin offering two contract versions negotiates the highest common one at `hello`.
- **AC-L5-3 Requests are claims (C0/Stage 2).** A manifest requesting `net_egress` to a destination confers nothing until `seal`; after `seal` with the author narrowing to one destination, the plugin process reaches that destination and is refused elsewhere with a ledgered `security.egress.*` refusal (ADR-0061); a plugin claiming `capabilities: ["admin"]` gains no grant (AC-H5-3 shape).
- **AC-L5-4 No authority crosses inward (C0/Stage 2).** A hostile variant returning a `Permission`, a label, a lowered risk class or a raised retryability is refused with `AuthorityCrossing`; `security.extension.violation` is appended; the run proceeds with the class's fallback.
- **AC-L5-5 Guard meet-composition (C0/Stage 2).** Three hooks at one `DecisionPoint` returning `{pass, ask, annotate}` in any order and under parallel or sequential execution yield `ask` with the annotation attached; a hook returning `allow` or a rewritten proposal is `AuthorityCrossing`; a timed-out `required` hook yields `deny`, a timed-out optional hook `no_decision → pass`; a `propose_replacement` re-enters authorization as a new `effect_id` with `derived_from` the hook.
- **AC-L5-6 One plugin, one process, no reach (C0/Stage 2).** The hostile plugin's probes (another plugin's root, the helper socket, ambient env, host import, undeclared spawn) are each refused by the helper with a ledgered refusal; two plugins bound in one run never share a process (`host_id` distinct; OS-level check in the suite).
- **AC-L5-7 Atomic bind and crash recovery (C0/Stage 2).** A plugin whose second contribution fails `bind` leaves no `lifecycle.component.bound{bind_result: ok}` for its first; killing a plugin process mid-invocation yields `PluginCrashed`, a `detached` session, a re-`hello` from the ledger, and `action.effect.unknown` for any effect it had proposed and the kernel had committed (ADR-0030/B3 rule).
- **AC-L5-8 Extension DAG (C0/Stage 1 spec; every stage build).** The spec-DAG check over all §7.2 #5 sections, `ClassRecord`s and the two Stage-1 plugins reports `tier_violations = []` and acyclicity; for each tier n ∈ {0..3} the build with tiers > n absent passes the tier-n acceptance suite unchanged (X4).
- **AC-L5-9 Cost is measured, not assumed (C0/Stage 3; T-LCD-14).** The same `compaction_strategy` variant bound `in_process` (first-party) and `subprocess_confined` (packaged as a plugin) under matched budget reports `boundary_overhead_ms` distributions per invocation and an unchanged headline metric within the pre-registered margin; the OQ-075 ceiling per `hot_path` class is set from this data and recorded as an assumption-debt record.
- **AC-L5-10 Plugin conformance kit (C0/Stage 3).** Every null plugin passes all four layers; the hostile plugin fails layers 2 and 4 with typed refusals; a third-party plugin at `require_conformance = declared` resolves with `probed = UNKNOWN` fields and at `probed` is refused until a `registry_ci` report exists (AC-J2-9 shape).
- **AC-L5-11 Foreign formats round-trip with declared loss (C1/Stage 4; T-LCD-11).** Importing a Claude Code `plugin.json`, a gemini `gemini-extension.json` and a codex agent-plugin manifest yields quarantined plugins whose `LossReport` lists at least `{requires, requests, per-executable isolation, contract_range}`; exporting a first-party plugin to each format and re-importing recovers every field not declared lost.
- **AC-L5-12 T-LCD-06 preserved (C0/Stage 1).** No `PluginManifest/1`, `plugin_abi/1` or `ContractRef` schema references the Hosting ABI or `OpaqueProcess`; with the hosting tier absent every plugin test above passes unchanged.

## 10. Confidence

**High** for the loading/isolation contract's invariants (out-of-process third-party code, closed host callbacks, no authority crossing, one plugin per process, pinned both ways): each follows from ratified ADRs (0023/0050/0053/0063/0100) and from Tier-A/B protocol text (MCP stdio, component model, Extism), and every audited in-process precedent exhibits the failure the invariants close. **High** for the manifest shape (inventory of registry kinds + `requires` + `requests`): five independent manifests converge on the inventory, J2/H5 fix the record and trust shapes, and the two additions have precedents outside the field (Extism, VS Code `engines`). **Medium-high** for the guard verdict sum and meet composition: the narrow-only rule is ratified (ADR-0053, gemini precedent), but the *replacement re-entry* and `no_decision` semantics are new and their utility cost is a Stage-2/3 measurement (AC-L5-5/-9); WS-F1/A3 still own the HIR placement (OQ-165). **Medium** for the extension DAG as a gate: X1/X3 hold by construction, X2/X4 are checkable but no audited project runs a per-tier removability build, so the cost of maintaining it is unmeasured. **Medium** for versioning/compatibility policy details (sunset windows, additive-only rule): precedented in shape (SemVer, `engines`), untested for a contract catalogue of this size (OQ-411). **Medium-low** for boundary cost on hot-path classes: no data yet (OQ-075/AC-L5-9); Logos' number is `provisional` and not used.
