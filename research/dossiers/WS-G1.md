## 1. Scope & boundary

This workstream decides the **verification fabric**: (i) the **task contract** — how a `Goal` states what counts as acceptance evidence, which criteria the subject harness may see and which are held out, and what the run must have proven before it may claim completion; (ii) the **Validator component contract** — the operations, inputs (authoritative evidence handles, never model prose), outputs (typed verdicts with provenance and an inputs digest), invariants and failure modes of every validator, deterministic or judged, subject-bound or instrument-bound; (iii) the **placement of checks** — *local* checks that run immediately after an effect reaches a terminal phase (schema conformance, exit status, diff sanity, scope containment, declared postconditions) and *global* checks that evaluate task-level invariants and completion evidence at decision points and at the completion gate; (iv) **evidence requirements** — authority floor, freshness and integrity of the evidence a verdict may rest on, including the anti-tampering rule for pinned validators; (v) how verdicts are recorded in the ledger and how they feed the scorecard (WS-I2) and the control loop (WS-F1/F2); (vi) the deterministic `followed` detectors per artifact kind that Phase 1 left to G1 (OQ-049).

It explicitly leaves to neighbours: **WS-G2** — belief-state reconciliation (claims vs authoritative state; `verification.claim.*` events; whether an `abandoned`/`unknown` effect blocks completion, OQ-092); **WS-G3** — judge rubrics, calibration (OQ-123), independence, critic ensembles (G1 fixes only that a judge is a `Validator{kind: judge}` consuming the same evidence handles); **WS-I2/I4** — the oracle taxonomy (ADR-0047, consumed unchanged), per-suite oracle implementations, headline/veto reporting; **WS-F1/F2** — what to *do* with a verdict (retry, stop, escalate, revert), bounded reflection counts, `DecisionPoint.verify` guards; **WS-B2/B4/B5** — effect phases, `probe`, revert/baseline mechanics, environment handles (G1 consumes `env_handle`, `baseline_ref`, `snapshot_ref`); **WS-E1/E5** — `ToolCapability.output_schema`/`preconditions` and the sandboxed executor that captures effects (G1 reads what E5 captured); **WS-H1** — the reference monitor (a verdict never confers authority; endorsement by `validator` basis is ADR-0035's and is only *invoked* here); **WS-D1/D4** — how verdict Observations are rendered into context and memory-validity checks. Nothing here names a language, runtime, package or framework; every contract is operations/inputs/outputs/invariants/failure modes (T-LCD-12; ADR-0050 §8).

## 4. Findings

### 4a. Mechanism evidence (a failure mode exists / an architecture is implementable)

**F1 — The post-tool-use seam exists in every audited harness, with four vocabularies and three incompatible semantics.** Codex `PostToolUse` (`should_block`, `feedback_message`, `additional_contexts`), Claude SDK `PostToolUse` (`additionalContext`, `updatedToolOutput`), Gemini CLI `AfterTool` (`decision ∈ {block, deny, ask}`, `additionalContext`, `systemMessage`), opencode `tool.execute.after`, aider's `auto_lint`/`auto_test` after every edit, SWE-agent's lint-in-the-edit-tool, OpenHands' critic in `all_actions` mode. The semantics diverge on one axis that matters to the ledger: **what a failing check may do to the observation.** (a) *Annotate*: Codex wraps the original output — `PostToolUseFeedbackOutput{original, model_visible}` — and records hook contexts as developer messages (`registry.rs` L732–738; `hook_runtime.rs` L833–840); aider appends lint/test output as a new user message. (b) *Reject*: Codex `should_block` turns the result into `FunctionCallError::RespondToModel(message)` while the code comment states the rule exactly — "A PostToolUse block rejects the result, not the already-completed tool execution" (`registry.rs` L707). (c) *Rewrite*: Claude SDK `updatedToolOutput` "Replaces the tool output before it is sent to the model" (`types.py` L433–439). (d) *Revert*: SWE-agent's edit tool undoes the edit itself when new lint errors appear (`bin/edit` L109–116) — the check is fused into the effect. **Implication:** the fabric needs one typed seam with the *annotate* semantics as the only C0 behaviour (a verdict is a new Observation with `source = validator`, never a mutation of the original — ADR-0026 immutability), *reject* expressed as a verdict the control envelope consumes, *revert* delegated to B4's `revert(effect_id)` on a `fail` verdict rather than fused into tools, and *rewrite* excluded (§5, CF-231): a rewritten observation launders provenance and breaks E6's "result renderer preserves every field a bound Validator reads" (ADR-0022).

**F2 — Local checks after effects are cheap, deterministic and already standard; the only unresolved design point is what evidence they read.** Aider lints the *edited files* (`lint_edited(fnames)` → `linter.lint(abs_path)`), i.e. post-effect end state on the touched scope, and runs `test_cmd` on non-zero exit adding output to chat (`cmd_test` → `cmd_run(add_on_nonzero_exit=True)`). SWE-agent diffs *pre-edit vs post-edit* lint output so only *new* errors count (`bin/edit` L94–108) — a **freshness/baseline** rule. ToolGate (S-411) formalizes the same thing as a Hoare postcondition that gates *commit* of a result into symbolic state; S-204 adds postcondition verification before retry. WS-B2 already reserved `postcondition_results[]` on the `Effect` record and a `probe` verb; WS-A3's `ToolCapability` carries `output_schema` and `preconditions` but **no postcondition slot**, and the `validates` edge does not target `ToolCapability` or `Effect` (ADR-0016). Implication: local checks bind either through a `HarnessRule{trigger: effect terminal event, action: require Validator}` (no dialect change) or through a kernel built-in over `output_schema`/exit status/diff sanity; their evidence is `{effect record, output artifacts, end-state on the effect's `resource_keys[]`, baseline_ref}` — never the model's own description of what it did.

**F3 — Global checks are runtime-verification monitors over the ledger and the end state, and two production harnesses already gate completion on them.** HAL's `ComplianceMonitor` evaluates constraints over traces and produces `ComplianceViolation` records with a score over opportunities (S-134); AgentDojo's `security_from_traces` and OpenHands' stuck detector are the same shape (trace predicates). Anthropic's evaluator (S-046) reads the *running application* through a browser, grades against criteria with **hard per-criterion thresholds**, and a sprint fails if any threshold is missed; Symphony ends a run at a *workflow-defined handoff state*, never at the agent's say-so (S-108). Leucker & Schallhart (S-410) give the theory: a monitor decides a property over a finite trace prefix, with a three-valued answer when the prefix is inconclusive — which is exactly ADR-0014's `{valid, invalid, unknown}` and ADR-0047's `reference_relative` `{equivalent, not_equivalent, inconclusive}`. Implication: global checks are `trace_predicate`/`end_state` validators evaluated at `DecisionPoint.verify` and at the **completion gate**; their verdict type is three-valued at minimum; an inconclusive verdict is *not* a pass.

**F4 — Completion claims are the failure locus, and every production report names it.** S-041: later sessions "look around, see that progress had been made, and declare the job done"; S-046: agents "respond by confidently praising the work — even when … the quality is obviously mediocre", and the evaluator itself needed "several rounds" before it stopped approving problematic work; Harness-Bench names execution-alignment failures "decoupled from … verifiable output contracts" (S-062). OpenHands' deterministic `AgentFinishedCritic` encodes the minimal gate — a `FinishAction` *and* a non-empty patch — and `IterativeRefinementConfig` re-prompts up to `max_iterations` when a critic score is below threshold. Implication (§6.3): a run's terminal `lifecycle.run.finished` carries a `verification_summary` computed by the kernel from verdict events, and a `status = succeeded` claim is admissible only when every `required` acceptance criterion has a `pass` verdict whose evidence post-dates the last effect terminal event on the contract's scope. The model may *propose* completion (a `stop` decision at `DecisionPoint.stop`); the fabric *decides* it.

**F5 — Reward hacking is a property of the visible verification surface, and the countermeasures are structural, not prose.** SpecBench (S-412): "oversight collapses onto a single surface: the automated test suite"; the visible-vs-held-out pass-rate gap is the hacking measure and grows with task size. RHB (S-413): shortcuts are "skipping verification steps, inferring answers from task-adjacent metadata, or tampering with evaluation-relevant functions", and "simple environmental hardening reduces exploitation". Harbor's verifier uploads tests only at verify time and protects reward files (S-132) — the tests are not in the agent's environment during the run. Anthropic's countermeasure is prose — "It is unacceptable to remove or edit tests" (S-041) — which under ADR-0014 is a *compliance* fact (delivered → followed) to be measured, not a guarantee. Implication: the task contract separates **visible** criteria (delivered to the subject as `ContextItem`s; may be run by the subject) from **held-out** criteria (never delivered; executed by the instrument from a pinned `CompiledPayload`); validators and their fixtures are content-addressed and pinned in the sealed definition or experiment; a workspace copy of a pinned validator that no longer matches its hash is a veto predicate (`EvidenceTampered`), and the visible/held-out gap is a class-scoped metric.

**F6 — A verdict is not a score, and deterministic and judged verdicts must never share a slot.** OpenHands collapses both into `CriticResult.score ∈ [0,1]` with `success = score ≥ 0.5`, and a `predicted probability of success` from an API judge drives the same retry loop as the deterministic "non-empty patch" check (S-110 `result.py` L9–30, `base.py` L114). ADR-0047 rejected exactly this ("a judged 0.8 and a test-derived 0.8 become indistinguishable"). Doc 2 §5.3's rule — critics "should consume the same authoritative external evidence rather than simply critique another model's prose" — is satisfied in S-046 (the evaluator drives the browser) and violated whenever a judge reads only the transcript. Implication: the verdict record carries `detector ∈ {deterministic, judged, human}`, `evidence_refs[]` and an `inputs_digest`; a judge that consumed no evidence handle beyond the transcript has `evidence_class = claimed` (ontology term from CF-080) and is inadmissible as a `followed` detector for any artifact with an executable check.

**F7 — Verdict consumption belongs to the control envelope, with bounded reflection.** Aider re-prompts with lint/test errors as a `reflected_message`; SWE-agent's error template forbids re-running the same edit; OpenHands bounds refinement by `max_iterations`; Codex's block becomes a model-visible error. Every precedent converges on: the verdict is rendered back to the model as an observation, and a *deterministic* policy bounds how many times. Implication: G1 emits verdicts; F2 owns `retry`/`stop`/`escalate` policy keyed on `verdict.value` and `phase`; the verdict's rendering is a profile surface (D1/C3), never an IR field (T-LCD-10).

**F8 — Making evidence legible is harness work, not tooling.** S-044 wires the browser protocol and a per-worktree observability stack into the agent runtime so that "logs, metrics, and traces" and DOM snapshots are queryable evidence; custom linters "inject remediation instructions into agent context"; layering rules are "enforced mechanically". This is the environment-boundary half of the fabric: a validator can only be deterministic if the environment exposes an **evidence handle** (log query, DOM snapshot, exit status, database state) the kernel can read without the model in the loop. WS-B5/E5 own the handles; G1 fixes the handle *kinds* a validator may declare as inputs.

## 5. Disconfirming evidence & negative results

**Against a typed verification fabric at all ("tests are enough; keep it in the environment").** SWE-bench, Terminal-Bench and Harbor get by with a test script and a reward file; S-044 shows an entire codebase governed by linters and CI without any harness-level validator abstraction. *Why it does not overturn:* those are *instrument-side* oracles run once at the end; the failure modes in F4 (false completion) and F5 (hacking of the visible surface) arise *during* the run and are invisible to an end-of-run test. Harbor's own design (tests uploaded only at verify time) is the held-out half of this fabric done by convention; the fabric makes the convention a typed, auditable rule and lets the same validator kind serve local, global and instrument roles with one verdict record. The cost — a verdict event per check — is bounded by the persistence policy (ADR-0026) and by the validator's own budget accounting.

**Against deterministic-first ("the Verification Horizon says nothing fixed survives").** S-415 argues that "no fixed reward function can remain effective as policy capability continues to grow" and that verification must co-evolve; S-046 needed several rounds to tune its judged evaluator; S-412 shows frontier agents saturate visible test suites. *Why it does not overturn:* the argument is about *reward functions used for training* and about a fixed *visible* surface. The fabric's answer is structural: held-out criteria, content-addressed pinning, veto predicates over the ledger for the known shortcut classes, and the visible/held-out gap as a reported metric — none of which is a fixed reward. Where deterministic oracles do not exist, ADR-0047 already admits judges under obligations; G1 adds only that judges must consume evidence handles. Co-evolution of oracles is WS-I5/I8's (C4) with `provisional` labelling. Recorded as the standing risk that any *particular* held-out suite ages (assumption-debt record on every suite, T-LCD-05).

**Against local checks on every effect (cost and fatigue).** A verdict per effect adds a ledger event and a validator run per tool call; aider makes auto-test opt-in (`auto_test = False`) and asks before fixing; S-053's 93 % approval rate shows that any check that becomes a prompt is ignored. *Accepted and scoped:* kernel local checks are limited to what the runtime already has in hand (schema conformance of the result, exit status class, patch application status, scope containment against `resource_keys[]`); declared postconditions are opt-in per `ToolCapability`/`HarnessRule`; a verdict never becomes an approval prompt by itself — routing to a human is H7's decision on `veto`/`escalate`.

**Against a kernel-enforced completion gate (autonomy and undecidability).** Many tasks have no executable acceptance criterion (research, writing); a gate that refuses `succeeded` would render every such run "unverified" and could be gamed by declaring no criteria. Symphony and Managed Agents let the environment or the human decide. *Why it does not overturn:* the gate is honest rather than strict — `Goal.success_criteria` non-empty *or* `unverifiable_reason` (ADR-0016) is already an HIR/1 invariant; a run whose contract has no executable criteria finishes `succeeded_unverified` with the reason, which the scorecard reports as `n/a{no_detector}` for headline capability (ADR-0045), never as success. Judged criteria may satisfy the gate only for metrics that admit judged detectors. The gate cannot be gamed by the subject because the contract is sealed before the run and held-out criteria are instrument-bound.

**Against rejecting `updatedToolOutput`-style rewrites.** Rewriting is useful: truncating huge outputs, redacting secrets, normalizing formats for a model family. *Why it does not overturn:* all three are *rendering* concerns the profile-owned transcript renderer and D1's offload already own (ADR-0019 item 6; WS-D1), applied to a ledger record that stays intact. A validator that changed the bytes a later validator reads would violate E6 and make `inputs_digest` unreproducible. The fabric therefore admits *annotate* and *reject* only (CF-231).

**Against `followed` being deterministic for anything but tool surfaces.** ADR-0014 (b) records that every following signal in the literature is judged; S-088's HFR is LLM-judged. *Accepted with a narrower claim:* §6.6 lists the kinds where a deterministic detector is a *trace predicate the artifact itself defines* (a procedure's typed steps, a tool surface's schema, a soft-budget rule's counter, a memory whose value is a closed-schema datum that reappears in an effect's canonical args); prose instructions stay judged-only unless they carry a `validates` edge. The honest number will be the share of delivered artifacts with `detector = deterministic`, reported per profile (AC-G1-9).

**Negative results.** (N1) The scalar critic score (OpenHands) cannot be lifted into the fabric without losing ADR-0047's deterministic/judged separation; (N2) no audited hook system records *which evidence* a hook read, so none can be replayed or audited — this is the gap `inputs_digest` closes; (N3) S-044 could not be fetched from its origin in this environment (HTTP 403); the proxy copy was used and the quotes should be re-verified at synthesis.

## 6. Recommendation for the spec

### 6.1 Position

1. **One Validator component class, three bindings.** Every check — kernel local check, declared postcondition, task acceptance criterion, invariant monitor, judge — is a HIR/1 `Validator` (ADR-0016 entity 10) exercised through one operation-shaped contract (§6.4). What differs is the **binding**: *subject-bound* (referenced from the sealed Harness Definition; part of θ; `charged_to = subject`; visible to the model as a `ContextItem` if delivered), *contract-bound* (referenced from the `Goal`'s task contract; may be `visible` or `held_out`), or *instrument-bound* (a Lab oracle per ADR-0047; `charged_to = instrument`; never in θ). The scorecard's headline reads only contract-`held_out` and instrument oracles of deterministic class.
2. **Verdicts are Observations, never mutations.** A verdict is appended as `verification.validator.verdict` and rendered as an `Observation{source = validator}`; the original observation is never rewritten (ADR-0026, E6). A `fail` verdict does not undo an effect; it is consumed by F2 (retry/stop/escalate) or B4 (revert).
3. **Local checks read the effect; global checks read the run.** Local = evaluated once per effect terminal event over `{Effect record, output artifacts, end state on `resource_keys[]`, `baseline_ref`}`; global = evaluated at `DecisionPoint.verify`, at `stop`, and at the completion gate over `{ledger cursor, end-state handle, artifacts}`.
4. **Evidence beats claims.** A validator's inputs are typed evidence handles with authority ≥ `environment` (ADR-0033); `model_claim` observations never satisfy a validator alone (ADR-0016 invariant, restated as an operation-level failure `ClaimOnlyEvidence`); every verdict carries an `inputs_digest` so it is reproducible at R1 (ADR-0038).
5. **Held-out criteria and pinned validators are the anti-hacking floor.** A task contract's held-out criteria are never delivered; validators and fixtures are content-addressed and pinned; the known shortcut classes are veto predicates.

### 6.2 Task-contract data model (C1 / Stage 3; schema C0 / Stage 1)

The task contract is **not a new entity**. It is the typed projection `project(sealed ∪ experiment, task_contract)` over `Goal`, its `success_criteria: [Ref<Validator>]`, the `validates` edges that point at the Goal, and the experiment's instrument oracles — the same construction WS-A2 used for `HarnessArtifact` (ADR-0016 §"neighbour reconciliation"). Its load-bearing fields live on the **`validates` edge record**, which HIR/1 currently leaves without typed fields; this dossier proposes the additive record (ADR-0109; OQ-266 asks synthesis whether this is an HIR/1 amendment or an HIR/2 item — it cannot live in `ext` because `ext` never decides validity, ADR-0015):

`ValidatesRecord{role ∈ {acceptance, invariant, precondition, postcondition}, phase ∈ {local, global, completion}, required: bool, visibility ∈ {visible, held_out}, veto: bool = false, evidence_requirements: [EvidenceRequirement], window?: {after: EffectScopeSelector | run_start, until: completion | decision_point}, weight?: decimal-string}`

`TaskContract{contract_id (= H(canonical(goal.semantic_id ∥ sorted criterion refs ∥ records))), goal_ref, criteria: [AcceptanceCriterion{criterion_id (= edge id), validator_ref: VersionedRef, record: ValidatesRecord}], invariants: [criterion_id where role = invariant], completion_policy ∈ {all_required, weighted_threshold(t), unverifiable(reason: Text)}, evidence_kinds_required: set<EvidenceKind>, budget_ref: Ref<Budget> (verification spend is metered under the run's budget with `attribution.charged_to` per binding), provenance, sealed: bool}`

`EvidenceRequirement{kind: EvidenceKind, min_authority: AuthorityClass ≥ environment, freshness ∈ {any, after_last_effect_on_scope, after_seq(n)}, integrity ∈ {content_addressed, chain_verified}, scope?: ResourcePattern}`

`EvidenceKind = {end_state(env_handle), snapshot(ContentAddress), artifact(ContentAddress), effect_record(effect_id), observation(EventRef), ledger_range(run_id, from_seq, to_seq), world_state_patch(ContentAddress), external_probe(ToolCapability ref, read_only), model_io(EventRef) — judges only, human_attestation(attestation)}`

Invariants: (I1) `contract_id` is computed before the first `lifecycle.turn.started` and stamped into the run manifest (`lifecycle.run.created.manifest.task_contract_id`), so the contract is immutable per run and a coordinate of `configuration_version_id` when it is part of the task (WS-I2 factor "task with split label"); (I2) a criterion with `visibility = held_out` is never the payload of `context.artefact.delivered` (kernel check at `deliver`: `HeldOutLeak` — error, and a veto predicate over the ledger); (I3) every `required` criterion references a validator whose `kind ≠ judge` **or** the metric that consumes it declares `detector_classes_allowed ∋ judged`; (I4) `completion_policy = unverifiable` requires `Goal.unverifiable_reason` (ADR-0016) and forces `status = succeeded_unverified`; (I5) validators referenced by `held_out` criteria are pinned by `version_id` and their `CompiledPayload.bytes_hash` and fixture `ContentAddress`es are recorded in the bundle (ADR-0038 lock manifest); (I6) `phase = local` criteria must name an `EffectScopeSelector` (capability semantic ids and/or `resource_keys` patterns) — they are evaluated per matching effect, never at completion only. Precedent: Meyer's precondition/postcondition/invariant triad (S-409); S-046's negotiated "sprint contract"; SpecBench's visible/held-out split; Harbor's verify-time upload.

**Visible vs held-out, concretely.** A coding task ships `visible` criteria (a test command the subject may run; compiled into a `ContextItem` with `authority = definition` at `seal`) and `held_out` criteria (composition tests, invariants, the tamper check) executed by the instrument over the end-state handle after the run. The reported pair (`visible_pass_rate`, `held_out_pass_rate`) and their gap is the `reward_hacking_gap` metric (class-scoped; `requires_observability ⊇ {end_state}`; applies to hosted participants too — this is the comparison plane's common floor).

### 6.3 Placement: local checks, global checks, completion gate

**Kernel local checks (MUST-code, C0 / Stage 1).** After every effect terminal event (`action.effect.observed`, `probed → observed`), the `verify` plane operator (WS-A2 harness step) runs the built-in validators the runtime has evidence for without any declaration: (a) `schema_conformance` — the observation payload against `ToolCapability.output_schema` (E6 guarantees the fields survive lowering); (b) `exit_status_class` — for `exec` effects, `{success, failure(code), timeout, signal}` from the executor's captured status (B2/E5); (c) `patch_application` — for `fs_write` effects with a patch shape, `{applied, rejected(hunks), partial}` and `touched_paths ⊆ effect.resource_keys[]` (scope containment; Codex `assess_patch_safety` precedent — here read-side, after the fact); (d) `diff_sanity` — bounded size/line/file-count thresholds and no writes outside the sealed `Permission` scope (a conditioned rule with an assumption-debt record, since thresholds are model/task-dependent — T-LCD-05; defaults OQ-270). Each yields one `verification.validator.verdict` with `phase = local`, `validator_ref = hir/kernel/<check>` (kernel-owned Validator nodes in the reference dialect), `detector = deterministic`, `charged_to = subject`. Their cost is metered as `harness_overhead.verification` (ADR-0044).

**Declared local checks (MUST-data, C0 schema / C1 use).** A `ToolCapability` may carry `postconditions: [Ref<Validator>]` (proposed HIR/1 field beside `preconditions`, ADR-0111; fallback if refused: a `HarnessRule{trigger: action.effect.observed{capability_id ∈ S}, action: require Validator(v)}`, which needs no dialect change) and a `Procedure` may carry `Verify(Ref<Validator>)` steps (already HIR/1). Evidence: the effect record, its `output_artifact_ids[]`, end state on `resource_keys[]`, `baseline_ref` for before/after predicates (SWE-agent "only new errors" rule: `new_findings = findings(after) − findings(baseline)`). WS-B2's `Effect.postcondition_results[]` becomes the list of these verdicts' `EventRef`s (CF-233: one declaration, by reference).

**Global checks (C1 / Stage 3).** `role ∈ {invariant, acceptance}` with `phase ∈ {global, completion}`: evaluated (a) at `DecisionPoint.verify` whenever the control strategy asks (F1 declares its cadence; default: before each `stop` proposal and every N turns as a conditioned rule), (b) at every `stop` proposal, (c) at the completion gate. Invariants are runtime-verification monitors (S-410) over the ledger cursor `(run_id, 0..head)` and the end-state handle: e.g. "no `fs_write` outside `src/`", "every `compensable` effect terminal", "held-out validator files unchanged (`EvidenceTampered`)", "no `context.artefact.delivered` of a `held_out` criterion (`HeldOutLeak`)". Verdict values are three-valued at minimum (`pass | fail | inconclusive`).

**Completion gate (C1 / Stage 3; kernel-enforced).** When the control strategy proposes `stop{reason = completed}`, the kernel computes `VerificationSummary{contract_id, required: {pass, fail, inconclusive, not_run}, invariants_tripped[], evidence_head_seq, freshness_ok, held_out_status ∈ {run, deferred_to_instrument}}` and decides `status`:
- `succeeded` iff every `required` `visible`/subject criterion is `pass` with `freshness_ok` and no `veto` tripped — *and* held-out criteria are `deferred_to_instrument` (the instrument's later verdicts can only lower the outcome to success-with-veto or `scored = fail`, never raise it);
- `succeeded_unverified` iff `completion_policy = unverifiable`;
- otherwise the proposal is refused with `CompletionRefused{summary}` rendered to the model as an Observation (F2 decides how many refusals are allowed — bounded reflection; the run then ends `stop_reason = verification_failed` or `budget_exhausted`).
OQ-092 (open `unknown`/`abandoned` effects) is G2/F1's; the gate exposes it as the invariant "all effects terminal" with `inconclusive` when violated, so whichever policy G2 chooses is a one-line change.

**Hosted participants (T-LCD-06/-15).** Local checks are `n/a{observability}` unless the hosting mechanism yields `events` with effect terminal records; global held-out criteria apply to every participant through `end_state` — no native contract changes, and no field exists "so that hosted participants can fill it".

### 6.4 Validator component contract (language-agnostic; C0 / Stage 1)

`Validator` is a registered component class (`ClassRecord{class_id = validator, cardinality = ordered-many on the `validators` slot, required_inputs ⊇ {ModelProfile, ResourceAccount}}`, ADR-0023; OQ-073's `ordered-many` shape applies — a validator chain is one ordered list, per-element `enabled` is the ablation switch). Operations:

- `declare(validator: Ref<Validator>) → ValidatorDeclaration{validator_ref: VersionedRef, kind ∈ {executable, schema, predicate, judge, human} (ADR-0016), oracle_class (ADR-0047), deterministic: bool, evidence_inputs: [EvidenceKind] (what it will read), evidence_out: ArtifactKind, verdict_type ∈ {bool, graded(decimal-string), lattice{C,I,P,N}, three_valued{pass,fail,inconclusive}, vector}, requires_observability, cost_model, isolation ∈ {kernel, sandbox(env_handle), external}, side_effects: set<EffectClass> (must be ⊆ read-only domains or the validator is an effect and goes through B2), profile_ref? (judges), calibration_ref? (judges), charged_to, assumption_debt?: AssumptionDebtRecord (mandatory for judges and for any threshold-conditioned validator — T-LCD-05)}` — invariant: `evidence_inputs ≠ ∅`; `kind = judge ⇒ deterministic = false ∧ profile_ref ∧ charged_to`; failure `IncompleteDeclaration`.
- `bind(validator_ref, sealed | contract, profile, account) → BoundValidator` — resolves the `CompiledPayload`/schema/predicate by content address; refuses `PayloadHashMismatch`, `UnboundFixture`; records `lifecycle.component.bound` (OQ-079).
- `collect(bound, target: TargetRef, cursor: LedgerCursor, env: EnvHandle?) → EvidenceBundle{handles: [EvidenceHandle{kind, ref, authority, provenance, produced_at_seq}], inputs_digest = H(canonical(sorted resolved content addresses ∥ target ∥ validator version_id))}` — the kernel resolves handles and stamps authority from the ledger's provenance records; the validator body never fetches evidence on its own (this is what makes `isolation = sandbox` safe). Failures: `EvidenceMissing(kind)`, `EvidenceStale` (freshness), `EvidenceUnauthoritative` (authority < requirement), `ClaimOnlyEvidence` (only `model_claim` observations present), `EvidenceTampered` (content address mismatch against the pinned fixture/validator).
- `check(bound, bundle) → Verdict` — pure in `(bundle.inputs_digest, validator version_id)` for deterministic validators (acceptance test AC-G1-4); for judges, `Verdict.detector = judged` and `model_call_id`s are recorded with `charged_to`. Failures: `OracleFailure{cause ∈ {crash, timeout, unparseable, non_finite, refused}}` (ADR-0047 item 4 — outcome class, never a score), `BudgetExhausted` (reserve-before-spend, ADR-0040).
- `emit(verdict) → EventRef` — appends `verification.validator.invoked` (at `collect`) and `verification.validator.verdict`; a verdict is rendered into context by D1 as an `Observation{source = validator, authority = kernel (deterministic) | delegate (judge) | principal (human)}`.
- `explain(verdict) → Text` — human/model-facing rendering, profile-owned surface (T-LCD-10); never stored as the verdict.

**Verdict record (data model).** `Verdict{verdict_id (EventId), validator_ref: VersionedRef, oracle_class, target: TargetRef (Goal | Artifact | Effect | Procedure | Memory | HarnessRule | Run), criterion_ref? (edge id), contract_id?, phase ∈ {local, global, completion, instrument}, role, value: VerdictValue, status ∈ {decided, inconclusive, oracle_failure}, detector ∈ {deterministic, judged, human}, evidence_refs: [EvidenceHandle], inputs_digest, evidence_head_seq, freshness_ok: bool, findings?: [Finding{code, severity, location?, message: Text}] (lint/compliance detail, e.g. HAL `ComplianceViolation`), cost: ResourceVector + attribution{charged_to}, veto_tripped?: [invariant_id], provenance: ProvenanceRecord{origin = kernel(validator_ref) | model(judge profile, model_call_id) | human(rater, role = reviewer), authority}, measured_at}` — invariants: `status = decided ⇒ value present`; `detector = judged ⇒ requires_observability ∋ model_io ∧ profile_ref ∧ calibration_ref?`; `authority(verdict) ≤ kernel` and a verdict **never** changes any item's label except through ADR-0035's `validator` endorsement basis (closed schema only); `inputs_digest` recomputed at replay equals the stored one (R1). The verdict is the `Observation` payload type WS-A3 named for `source = validator`; the event envelope is WS-B1's.

**Ledger events (WS-B1 taxonomy; payload extensions proposed).** `verification.validator.invoked{validator_ref, target, phase, criterion_ref?, contract_id?, evidence_refs[], inputs_digest, isolation}` and `verification.validator.verdict{… Verdict fields …}` (B1 has `{validator_ref, target, verdict, score, evidence_ref}`; this dossier extends with `status, detector, phase, role, criterion_ref, contract_id, inputs_digest, evidence_refs[], freshness_ok, findings?, veto_tripped?, cost`). New classes: `verification.contract.sealed{contract_id, goal_ref, criteria[], completion_policy}` (durability = ledger; Stage 3), `verification.completion.proposed{by, decision_point}`, `verification.completion.decided{status, summary}` (or, if WS-B1 prefers, a `verification_summary` payload on `lifecycle.run.finished` — CF-235 lets synthesis choose one). `verification.artefact.followed` is emitted by `emit` when the verdict's target carries `delivery_id` (ADR-0014).

### 6.5 Feeding the scorecard (I2) and the control loop (F1/F2)

- **Scorecard.** Every `Verdict` maps to a `MetricValue` under the `OracleDeclaration` its validator declares (ADR-0047 item 1). Rules: headline capability reads only `phase = instrument` or `visibility = held_out` verdicts of deterministic class; subject-bound and `visible` verdicts feed *process* metrics only (`validator_pass_rate`, `local_check_fail_rate_per_effect`, `completion_refusals`, `verification_ms`, `verification_share_of_spend` — ADR-0044 catalogue, grounding row); `reward_hacking_gap = visible_pass − held_out_pass` per configuration; `deterministic_followed_share` per profile (AC-G1-9); veto predicates `EvidenceTampered`, `HeldOutLeak`, `VerificationSkipped` (a `required` `visible` criterion never invoked before a `stop` proposal), `MetadataShortcut` (read of a declared task-metadata scope — RHB class 2, I4 declares the scope) join ADR-0047 item 5's list. `oracle_failure` and `inconclusive` are outcome-class/`n/a` facts, never 0 (CF-097).
- **Control loop.** Verdicts are the typed input of `DecisionPoint.verify` guards (`ControlBoundary.guards`, ADR-0016; OQ-062's open half — guards *may* reference Validators, this dossier recommends yes, as `Predicate over VerificationSummary`). F2 consumes `Verdict.value/phase/role` for `retry` (bounded reflections; aider/OpenHands precedent), `stop` (completion gate), `escalate` (veto or `inconclusive` on a `required` criterion), and B4 `revert(effect_id)` on a local `fail` when `baseline_ref` exists. G1 fixes only the *inputs* to those decisions and the invariant that a `fail` never mutates history.
- **Compliance chain.** `verification.artefact.followed{detector, detector_ref = validator_ref, verdict, confidence, evidence_ref}` is emitted by `emit` for targets with a `delivery_id`; deterministic when the validator is deterministic (§6.6).

### 6.6 Deterministic `followed` detectors per artifact kind (OQ-049 proposal; with WS-B1/D4, judged half WS-G3)

| artifact kind (WS-A2 `HarnessArtifact`) | activation signal (`activated`, existing) | deterministic `followed` detector (a `trace_predicate`/`schema` Validator the artifact references) | judged-only when |
|---|---|---|---|
| `tool_surface` | `tool_used` naming the surface | args conform to the surface's compiled schema and `SurfaceArgMap` narrowings; effect class equals declared (E1) — `schema` validator | never (always deterministic) |
| `procedure` (typed steps) | `procedure_invoked` | ordered `control.decision`/`action.tool.proposed` subsequence matches the Procedure's `Invoke`/`Verify`/`Branch` steps within the window; each `Verify` step has a verdict — `trace_predicate` | steps are `Instruction(Text)` only |
| `rule` (`HarnessRule`, kernel-executed action) | rule-fired event | the action's postcondition (tool set restricted ⇒ no proposal outside it; validator required ⇒ verdict present; approval required ⇒ `security.permission.decided`) — `trace_predicate` | the rule is a delivered instruction with no `validates` edge |
| `rule` (soft budget threshold, ADR-0040) | delivered | `control.budget.consumed` running totals stay under the soft threshold, or the rule's declared reaction appears — `trace_predicate` | never |
| `memory` (closed-schema value: path, id, version) | `context.memory.read` | the value reappears in a later effect's `args_canonical_hash` pre-image or `resource_keys[]` (citation-in-action) — `trace_predicate` over canonical args | the memory is prose (`Text`) without a `validates` edge |
| `instruction` (Text in system material) | not observable (`activation_observable = false`) | only if the instruction carries a `validates` edge to a `trace_predicate`/`schema` validator (e.g. "always run tests before finishing" ⇒ `VerificationSkipped` never trips) | otherwise (most prose) — WS-G3 |
| `observation` | n/a | n/a | n/a |

The share of delivered artifacts with a deterministic detector is reported per profile (AC-G1-9); the judged remainder is G3's with ADR-0047 obligations. This answers OQ-049's G1 half; D4 supplies memory validity checks and B1 the event payloads.

### 6.7 Acceptance-criteria sketch

- **AC-G1-1 (Stage 1, kernel local checks).** For every effect terminal event in the Stage-0/1 reference harness, exactly the kernel local verdicts (a)–(d) applicable to its domain are appended, each with `detector = deterministic`, `inputs_digest`, and `charged_to = subject`; the original observation event is byte-identical before and after.
- **AC-G1-2 (Stage 1, no rewrite).** No operation of the fabric mutates a durable observation; a validator declared with non-read-only `side_effects` is refused at `bind` (`ValidatorHasEffects`).
- **AC-G1-3 (Stage 1, claims are not evidence).** A validator whose bundle contains only `model_claim` observations returns `ClaimOnlyEvidence`; a corpus of transcript-only "I ran the tests and they passed" runs yields zero `pass` verdicts for any executable criterion.
- **AC-G1-4 (Stage 1, reproducibility).** For deterministic validators, re-running `check` on the same `EvidenceBundle` (same content addresses) yields a verdict with equal `value` and `inputs_digest` across two independent runs and across a process restart (R1); changing one evidence byte changes `inputs_digest`.
- **AC-G1-5 (Stage 3, held-out).** No `context.artefact.delivered` event references a `held_out` criterion in any Stage-3 run (`HeldOutLeak` never trips on the reference harness; a deliberately leaky definition trips it and is refused at `seal`).
- **AC-G1-6 (Stage 3, tamper).** A fault-injection arm that edits a pinned test file or the verifier payload in the workspace yields `EvidenceTampered` on the instrument's verdict and success-with-veto in the scorecard; the untampered arm does not.
- **AC-G1-7 (Stage 3, completion gate).** A run whose model proposes `stop{completed}` with a `required` criterion `fail`/`not_run` ends with `CompletionRefused` rendered to the model and never `status = succeeded`; a run with all `required` `pass` and fresh evidence ends `succeeded`; a run with `completion_policy = unverifiable` ends `succeeded_unverified` and renders `n/a{no_detector}` for headline capability.
- **AC-G1-8 (Stage 3, scorecard separation).** In the results store, no headline value is derived from a `charged_to = subject` or `visibility = visible` verdict; `reward_hacking_gap` is computable per configuration; `oracle_failure` runs are excluded from the denominator and counted beside.
- **AC-G1-9 (Stage 3, T-LCD-13).** For the reference harness under two profiles, `verification.artefact.followed` events with `detector = deterministic` exist for every delivered `tool_surface`, typed `procedure`, kernel `rule` and soft-budget rule; the deterministic share is reported per profile; prose instructions render `n/a{no_detector}` unless a `validates` edge exists.
- **AC-G1-10 (Stage 3, hosted).** A hosted participant run with `observability_level = {end_state}` receives the same held-out verdicts as native runs and `n/a{observability}` for every local metric; no native schema field was added to make this true (T-LCD-06).
- **AC-G1-11 (Stage 1, T-LCD-08/-12).** The `Validator` `ClassRecord` contract carries `required_inputs ⊇ {ModelProfile, ResourceAccount}`; a validator variant is implementable out-of-process over the canonical encoding, exchanging `EvidenceBundle` and `Verdict` documents only.

## 10. Confidence

**High** for the Validator contract's shape (evidence in, typed verdict out, annotate-not-rewrite, claims never evidence): four hook systems and three post-edit loops at pinned commits converge on the seam, the classic contract/RV theory fixes the semantics, and every rule restates a ratified ADR (0016, 0026, 0035, 0047) at the operation level. **High** that held-out criteria plus pinned, content-addressed validators are necessary: Harbor already does it by convention and three 2026 benchmarks (`provisional`) independently describe the failure it prevents. **Medium** for the placement details (which kernel local checks are always-on; the completion gate's refusal semantics) — precedents are heterogeneous and the cost is estimated, not measured; F2 may relax the gate by policy. **Medium** for the deterministic `followed` table: tool surfaces and typed procedures are certain; memory citation-in-action and rule postconditions are plausible trace predicates with no source precedent. **Low-to-medium** on anything quantitative from SpecBench/RHB/ToolGate/S-046 — all `provisional` or vendor-reported, none load-bearing.
