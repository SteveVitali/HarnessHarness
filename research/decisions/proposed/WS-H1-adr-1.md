# ADR-NNNN — Authority handles: kernel-table object-capabilities derived from the sealed definition and the principal, never present in model context; conferral rule, scope over capability parameters, and the `permission_request` domain

**Status:** proposed
**Owner workstream(s):** WS-H1 (consumers: WS-H3, WS-H4, WS-H5, WS-H6, WS-H7, WS-E1, WS-E5, WS-F3, WS-I5, WS-J6, WS-K4, WS-B1, WS-A3) · **Phase:** 2 · **Related:** ADR-0002 (iii), ADR-0016 (`Permission`, `authorizes`, `delegated-to`, `Permission.issuer.authority ≠ model_claim`), ADR-0017 (`authority_delta`), ADR-0022 (E2 `SurfaceArgMap`), ADR-0024 (MUST-code; `authority_cap`), ADR-0026/0027 (allocated ids; views are projections), ADR-0033 (`AuthorityClass`; `Permission.holder`), ADR-0034 (P2), ADR-0035 (endorsement bases; check 1–2, 7), ADR-0050 §8; CF-037 (`authority handle` term), CF-WS-H1-03; OQ-014, OQ-021, OQ-091, OQ-WS-H1-01/-03/-04; R-2.8.1

## Context

HIR/1 declares `Permission` (grants by effect domain + scope, attenuating delegation, issuer never a model claim) and reserves the runtime object-capability under the name *authority handle* (CF-037), leaving WS-H1 to define it. Doc 2 §5.6 fixes the principle — "the model may propose an action, only the runtime confers authority" — and CapScope (S-105, `provisional`) restates for coding agents what capability security has held since Dennis & Van Horn (S-WS-H1-03) and Miller (S-WS-H1-04): authority is an unforgeable kernel-held record referenced by the acting subject's identity, never by a name or a string. The source audit found no runtime that holds authority this way: Codex keys approvals on command prefixes and cache keys (`execpolicy`, `approvals.rs`), the Claude SDK on tool-name rules writable to settings scopes (`types.py` L109–140), OpenHands on a model-supplied risk value (`agent.py` L1068–1092); the escalation studies (S-103/S-104, `provisional (mech)`) show that where authority is inferred from text location or persistence, low-privilege content acquires it. Codex's `request_permissions` tool (`handlers/request_permissions.rs`; `session/mod.rs` L2845–2905) and ACP's `RequestPermissionRequest` (S-035) show the model *requesting* authority is a real operation that needs first-class semantics; HIR/1 already reserves the `permission_request` effect domain.

## Options considered

1. **Permissions as tool-name rules in configuration (Claude SDK / Codex execpolicy shape).** *Rejected:* identity == tool name string (T-LCD-10 failure); no delegation attenuation; rules persisted to settings scopes are the X-CPE write target (S-103).
2. **Permissions as strings/banners in the model context ("you may use tools A, B").** *Rejected:* authority is not a string (S-105; Hardy's confused deputy S-WS-H1-05); the model can be induced to believe it holds authority it does not.
3. **Per-value capabilities on every datum (CaMeL interpreter).** *Rejected for C0 (kept as C2 via H2):* requires a model-programmed interpreter; utility/authoring cost (S-099); ADR-0033 option 4.
4. **Handles keyed by tool call id, minted per call by the runtime.** *Rejected:* a per-call handle cannot express lifetime, delegation chains or count constraints; the Codex approval cache keyed on call ids is exactly what ADR-0031 forbids.
5. **A kernel-owned handle table keyed by AgentProcess identity, minted from the sealed definition's `Permission`s at run start (capped by `authority_cap`), extended only by legitimate endorsement events, referenced by opaque allocated ids that never enter model-facing surfaces; scope matched over canonical capability parameters via `SurfaceArgMap`; `permission_request` as an ordinary effect that policy never auto-allows (chosen).**

## Decision

1. **Record.** `AuthorityHandle = {handle_id: HandleId (allocated, opaque, time-ordered), permission_ref: VersionedRef<Permission>, holder: Ref<AgentProcess>, issuer: ProvenanceRecord, grants: [Grant], ceiling: AuthorityClass, validity: {issued_at: EventRef, expires_at?: {effect_id | turn_id | run_id | session_ref}, revoked_by?: EventRef}, parent_handle?: HandleId, delegable: bool, origin_basis ∈ {seal, approval, policy_rule, delegation, pin}, budget_ref?}`; `Grant` is ADR-0016's `Permission.grants[]` element unchanged. The **handle table** is `project(run, handle_table, until_seq)` over `security.permission.granted/revoked` events; rebuild equality is an acceptance test (ADR-0026).
2. **Out-of-band (H-1).** A `HandleId` never appears in a model-facing surface, a `Text` leaf, a tool result or a `CompiledPayload`; the model addresses tools by compiled surface name; the kernel resolves `(holder, capability, canonical params) → covering handles`. `HandleLeak` is a static error on the compiled `model_surface` and a runtime error on outgoing context.
3. **Conferral (H-2).** `issuer.authority ≥ principal ∧ issuer.origin ∉ {model, evolution, participant}`; `kernel`-issued handles only for kernel-internal effects. `IllegitimateIssuer` otherwise.
4. **Derivation (H-3).** At run start the kernel mints the root handle set from the sealed definition's `Permission` entities (`origin_basis = seal`, issuer `definition`), intersected with every `authority_cap` constraint (ADR-0024) — **before** any tool output, repository content or memory is read. The principal's task adds no authority unless a `principal`-issued grant is explicit. Every later handle has `origin_basis ∈ {approval, policy_rule, delegation, pin}` and a `basis_ref` to its endorsement event.
5. **Attenuation chain (H-4) and cascade (H-6).** `parent_handle ≠ null ⇒ grants ⊆ parent.grants (domain-wise; scope-wise subset; attributes narrowing; constraints tightening) ∧ ceiling ≤ parent.ceiling ∧ parent.delegable`; violation `AuthorityWidening` / `NotDelegable`. Revocation cascades to descendants in one ledger transaction.
6. **Scope over parameters (H-5).** `ResourcePattern` matches canonical capability parameters obtained through `SurfaceArgMap` (ADR-0022 E2), never surface fields; an unmapped argument is `UnmappedArgument` (deny). The pattern grammar is closed (OQ-WS-H1-01).
7. **Lifetimes (H-7).** `approval`-basis handles expire with their single `effect_id` by default; `turn`/`run`/`session` lifetimes only through an H7-declared canonical action pattern (OQ-091); persistence to `user`/`project` scope is an effect under ADR-0035 ceilings, never a handle property.
8. **`permission_request` domain.** A proposal `{domain: permission_request, requested: [Grant], lifetime, justification: Text(external)}` is authorized like any effect; the policy table never returns `allow` for it (ADR WS-H1-adr-2); an `approval` mints a handle with `issuer = principal`, `grants = requested ⊓ authority_cap`, `origin_basis = approval`, `delegable = false` by default, lifetime as requested (default `turn` — Codex `PermissionGrantScope` precedent); in unattended mode the request is denied and recorded. A `definition` pre-authorization (ADR WS-H1-adr-3) may pre-answer a request class only within `authority_cap`. The justification is evidence for the human, never a monitor input.
9. **Events.** `security.permission.granted{handle_id, holder, issuer, grants, ceiling, validity, parent_handle?, origin_basis, basis_ref}` and `security.permission.revoked{handle_id, cascade: [HandleId], reason, revoker}` carry mandatory provenance (ADR-0035 table); `Effect.permission_id?` becomes `handle_ids: [HandleId]` (CF-WS-H1-03).

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-10 (handles attach to `semantic_id`-identified capabilities and canonical parameters; renaming a surface changes no handle), T-LCD-12 (table and operations are records, out-of-process implementable), T-LCD-06/-07/-15 (hosted participants' handles are held by the kernel at the boundary; undeclared hosted capabilities are `unknown`, never granted), T-LCD-14 (count/budget constraints on grants are budget dimensions), T-LCD-02 (no handle in any `Text` leaf). Does not itself satisfy T-LCD-11 (handle metadata through protocol targets) — mitigated by ADR-0021/ADR-0034 P7 loss reporting. Rung on the ADR-0024 ladder: MUST-code (table, minting, resolution); `Permission` entities and `authority_cap`s are MUST-data.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** capabilities as unforgeable kernel-table rights referenced by the subject, not by name — Dennis & Van Horn (S-WS-H1-03, Tier A); object-capability discipline, no ambient authority, attenuation by wrapping — Miller (S-WS-H1-04, Tier A); confused deputy as the failure of name-based authority — Hardy (S-WS-H1-05, Tier A); least privilege and fail-safe defaults — Saltzer & Schroeder (S-WS-H1-02, Tier A); delegable, attenuating rights in a practical sandbox — Capsicum (S-WS-H1-06, Tier A); typed capabilities outside context, ceiling derived before untrusted reads, per-issuer checks — CapScope (S-105, `provisional`, corroborating only); authority inferred from location is the harness bug — S-103/S-104 (`provisional (mech)`, corroborated by the Codex/Claude SDK source cited); the model may propose, only the runtime confers — doc 2 §5.6 (S-130); `Permission` shape and issuer rule — ADR-0016; endorsement bases — ADR-0035.
- **(b) Source-code precedent:** `codex/codex-rs/core/src/tools/handlers/request_permissions.rs` + `core/src/session/mod.rs` L2845–2905 + `protocol/src/request_permissions.rs` L12–23 (model-requested permissions answered by policy first; turn/session grant scope); `codex/codex-rs/protocol/src/protocol.rs` L1103–1130 (`WritableRoot` protected subpaths — attenuation inside a root); `claude-agent-sdk-python/src/claude_agent_sdk/types.py` L109–140, L238–257 (`PermissionBehavior`, `updated_permissions`, destinations — the counter-example H-7 governs); `agent-client-protocol/schema/v2/schema.json` L487–545, L2031–2052 (elicitation verb and option kinds); `camel-prompt-injection/src/camel/capabilities/capabilities.py` L23–38 (capabilities as metadata on values, not text). The kernel-table handle keyed by AgentProcess identity with an attenuation chain is **`no-precedent / novel`** among audited agent runtimes (WS-A3 §5 negative result reconfirmed); precedented in OS capability systems.
- **(c) Disconfirming evidence considered:** tool-name rules are what every shipping product uses and users understand (Codex, Claude SDK) — the compiled surface name remains the user-facing label; only the *identity* the kernel checks changes; per-value capabilities give finer guarantees (CaMeL) — deferred to C2 under the same lattice at documented utility cost; a handle table is a single point of failure — accepted as the reference-monitor bargain with containment (H4) below it; CapScope's numbers are single-team — not load-bearing. None overturns.
- **(d) Conditionality:** independent of model tier and task class; assumes a sealed definition with `Permission` entities (ADR-0025) and a `SurfaceArgMap` for every admitted surface (ADR-0022); assumes a reachable principal for `approval`-basis handles (unattended runs use `seal`/`policy_rule` bases only); the volume of `permission_request` proposals is model- and task-dependent and is a Stage 3 metric, not an assumption.
- **(e) Build-stage assignment:** **C0 / Stage 1** (record, table projection, root minting with `authority_cap`, H-1/H-2/H-5 checks, `security.permission.granted/revoked`); **C0 / Stage 2** (`approval`-basis handles, `permission_request`, lifetimes, H-7); **C1 / Stage 4** (H-4/H-6 with subagents and hosted participants); **C2** (per-value extension via WS-H2).

## Consequences

- WS-B1 adds `handle_ids[]`, `origin_basis`, `parent_handle?`, `cascade[]` to the `security.permission.*` payloads; WS-A3/B2 replace `Effect.permission_id?` with `handle_ids[]` (CF-WS-H1-03).
- WS-E1 declares `EffectAttributes` per capability and the canonical parameter domains `SurfaceArgMap` maps into; WS-E5 executors receive `(effect_id, attempt_no, idempotency_key)` and never a handle.
- WS-F3 obtains child handles only via `delegate` (ADR WS-H1-adr-3); WS-J6/K4 lower `security.permission.requested` to the ABI's permission verb and lift `allow_always` only to an H7 pattern cache.
- WS-H7 designs the `ask` UX and cache lifetimes within H-7; WS-H5's `pin` mints `definition`-issued handles for verified extensions; WS-H6 attests the handle-table projection.
- Every later dossier that says a component "has permission" names the handle's `origin_basis`.

## Reversibility

**Medium.** Adding handle fields or bases is a dialect bump. Replacing the table with tool-name rules after Stage 2 would invalidate the complete-mediation invariant, the delegation tests and the X-CPE acceptance tests simultaneously; H-1/H-2 are constitutional with ADR-0035 rule 1.
