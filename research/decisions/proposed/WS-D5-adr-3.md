# ADR-NNNN — Skills are lifted Procedures: the Agent Skills file-tree mapping in both directions with a loss report, render purity, claims-to-grants only at `seal`, the procedure lifecycle and promotion policy, hooks as triggers with procedure bodies, and a C0/Stage-2 slice of R-2.4.5

**Status:** proposed
**Owner workstream(s):** WS-D5 (consumers: WS-H5, WS-D1, WS-D4, WS-F1, WS-H1, WS-H7, WS-I5, WS-E4, WS-K3, WS-L6, WS-A5) · **Phase:** 2 · **Related:** ADR-0007 (T-LCD-02/-05/-10/-11/-13), ADR-0017 (`derived-from`; widening rules), ADR-0019 (purity; closed-world rule), ADR-0021 (protocol targets; minimum carried set; loss classes), ADR-0024 (pointer rule; ladder), ADR-0025 (`resolve`/`seal`), ADR-0033 (R-TEXT; rule 6), ADR-0034 (RP; P2), ADR-0035 (`promotion`, `pin`, `approval` bases), ADR-0037 (name histories; `RevocationRecord`), ADR-0038 (bundle members); WS-H5 ADR-1/-2/-3 (extension record, lifecycle, model-install); CF-WS-D5-02/-03/-04/-05; OQ-020 (procedure half), OQ-H5-04 (input), OQ-WS-D5-04/-06; R-2.4.5, R-2.8.5, R-2.12.2

## Context

Doc 2 §5.6 requires skills to be "treated like supply-chain dependencies with version/pinning and provenance, not automatically elevated because they appear in a configuration directory"; §5.12 asks that procedures be "evolved independently of the entire runtime"; OQ-020 asks what happens when "a skill … is superseded or revoked". WS-H5 fixed the extension record and trust legs and named `Procedure` as what a `skill` contributes. The Agent Skills specification (S-WS-H5-13) fixes `name`/`description`/`license`/`compatibility`/`metadata`/experimental `allowed-tools` and `scripts/`/`references/`/`assets/` with three disclosure levels — and has no version, provenance, precondition, effect or test field. The audit found: activation *widening scope* (gemini `activate-skill.ts` adds the skill directory to the workspace); verified skill *paths* rendered at a privileged role (codex `guardian-context/src/trusted_skills.rs`); render-time shell execution inside skill bodies (OpenHands `skills/execute.py`, "full process privileges"); last-wins name shadowing across locations (opencode `skill/index.ts`; OpenHands "project skill overrides"); a per-skill model binding without a debt record (OpenHarness `SkillDefinition.model`); and, positively, explicit/implicit activation telemetry (codex `core/src/skills.rs`), skill enablement as "a context filter, not a sandbox" (Claude SDK `types.py`), and hooks whose outputs are `permissionDecision`/`updatedInput`/`additionalContext` (Claude SDK). Induction of procedures from trajectories is precedented (S-WS-D5-05 AWM; S-011 Voyager; S-095, `provisional`) and its transfer is fragile (S-WS-D5-03, `provisional`).

## Options considered

1. **A separate `Skill` entity beside `Procedure`.** *Rejected:* two homes for one thing; HIR/1 is closed at 13 entities; H5 already maps `skill → Procedure`.
2. **Skills stay foreign artifacts (files) that the context builder reads on demand, never lifted into HIR.** *Rejected:* no identity, provenance, V-EFF or tests; the S-103 skill-elevation vector stays open; T-LCD-13 events cannot name the artifact.
3. **Lift skills to HIR but keep the industry semantics** (activation widens scope; `allowed-tools` grants; location decides precedence; render-time exec allowed). *Rejected:* each contradicts a ratified rule (ADR-0033 rule 6, H5 L3, ADR-0037, ADR-0019 purity).
4. **`lift_skill` / `export(skill_tree)` as a declared-lossy target pair; render purity; claims become grants only at `seal`; the procedure lifecycle under D4/L4 with a promotion policy gated on validity and transfer; hooks as triggers whose actions are `workflow_node` procedures; a C0/Stage-2 stage note on R-2.4.5 (chosen).**

## Decision

1. **Lift.** `lift_skill(ExtensionRecord{kind: skill}) → {Procedure, Text[], Artifact[], CompiledPayload[], LoweringLossReport}` per the dossier §6.5 table: `name` → name-history entry + surface (identity = `semantic_id`; `NameCollision` at `resolve`, never last-wins); `description` → `index.description` `Text` at the extension's `text_authority` (default `external`); body → one `Instruction(Text)` step at C0; `allowed-tools` → `declared_claims` only; `compatibility` → applicability note (+ `env_requires` predicate if the author types it); `metadata.version` → `version_label` claim (CF-087), other keys preserved in `ext`; `scripts/*` → `CompiledPayload{format_tag, declared_interface{inputs: argv, outputs?, effects: {exec}}}` behind `Opaque` steps, executed only as `exec` effects in `subprocess_confined` (H5 §6.5); `references/*`/`assets/*` → content-addressed `Artifact`s read through `fs_read` scoped to the extension's content — **never a workspace widening**; vendor fields (path triggers, inputs, arguments, dependencies, invocation policy) lifted where typed. **Render purity:** a body containing a render-time execution marker fails `validate` with `RenderTimeExecution`; dynamic content is a declared `filling` slot bound to a capability invocation with its own effect record.
2. **Claims → grants at `seal`.** `allowed_capabilities` and the `authorizes` edges V-EFF requires are minted only when the author accepts the claim at `seal` or a principal `approval` endorses the seal diff (one edit, never content); until then a lifted procedure invoking a capability is `EffectUncovered` and cannot seal. Loading, listing, activation and enablement are *delivery*; none confers authority or scope (ADR-0033 rule 6; RP invariant: an `external` body renders only into slots with `min_authority ≤ external`).
3. **Export as a target (ADR-0021 shape).** `export(P, skill_tree)` emits a spec-conformant tree; the minimum carried set travels only as string pairs in `metadata` (prefix per OQ-WS-D5-06/OQ-068), so exports are admitted at `configuration` granularity at best; `preconditions`, `expected_evidence`, tests, handlers, `outputs` are `no_slot` losses; `allowed_capabilities` → `allowed-tools` (a claim). `export(P, mcp_prompt)` (parameterised `instruction` target → MCP `Prompt{arguments}`) and `export(P, a2a_skill)` (`subagent_task` index → `AgentSkill{id, tags, examples}`) are the same mechanism. Round trip `lift(export(P)) ∪ loss_report = P` is the T-LCD-11 test.
4. **Lifecycle (D4/L4 semantics).** Origin classes: `human(author)` sealed → `definition`; `import` (lifted) → `external` unless `pin`; `model`/`evolution` (induced) → `≤ delegate`, taint ∋ `{model}`, mandatory `derived-from{hypothesis, trajectories[], candidate_id}`. States `proposed → tested → sealed | pinned | promoted → active → expiring → superseded | revoked`. **Promotion policy:** `promotion` (ADR-0035) to `principal`/`definition` requires a human reviewer and `PromotionPolicy{require_validity = valid, require_transfer_test?: [profile_scope]}`; `PromotionRefused{reason}` is ledgered. Supersession/revocation per ADR-0037 (`supersedes{reason}`, `RevocationRecord`, `StaleIndex` for procedures whose `depends-on` capability/extension/fixture is revoked; `resolve(mode = execute)` and retrieval exclude them). Expiry: `validity.until | condition`; profile-conditioned targets expire through their debt records; tests last run under a retired profile make validity `unknown`, not `invalid`. A per-skill model binding is refused (`ConditionedRuleIncomplete` unless expressed as a `procedure_target` profile rule with a debt record).
5. **Hooks (input to WS-F1, OQ-H5-04).** A hook is a trigger — a `ControlBoundary.guard` at a `DecisionPoint` or a `HarnessRule` with a decision-point trigger — whose action is a `Procedure` with `compile_hint = workflow_node`. Guard outputs: `{narrow: deny | ask | none, additional_context?: ContextItem at ≤ definition, replacement_proposal?: Effect intent}`; a replacement proposal re-enters `authorize` as a new proposal at the guard's authority; `allow` is never a guard output. Hook bodies are therefore versioned, tested, revocable procedures.
6. **Stage note (scope register, no tier change).** R-2.4.5 stays C2/Could; a C0/Stage-2 slice is recorded: `ProcedureProfile/1`, `lift_skill`, `instruction` target, index/body candidates, deterministic detectors, `RenderTimeExecution`, claims→grants at seal. C1/Stage 3–4: `workflow_node`, tests, exports, promotion policy. C2: `subagent_task`, induction/transfer gate, relations.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: skills elevated by location/role are the S-103/S-104 escalation vector (`provisional (mech)`, corroborated by direct reading of codex `trusted_skills.rs` and OpenHands `agent_context.py` via WS-L3/D1); activation is an observable event with explicit/implicit forms (S-107 `core/src/skills.rs`); render-time execution exists in production (S-110 `skills/execute.py`); the spec carries no provenance/version/test (S-WS-H5-13; S-039 "no mention of versioning"); induced procedures transfer unevenly (S-WS-D5-03, `provisional`; S-WS-D5-05) — hence a transfer gate before promotion; "installing skills only from trusted sources" is the industry's whole model (S-039, Tier B); doc 2 §5.6/§5.12 (Tier B synthesis); ADR-0033/0035/0037 ratified rules.
- (b) Source-code precedent: `gemini-cli/packages/core/src/tools/activate-skill.ts` L100–150 (activation with confirmation; scope widening — rejected part) (S-119 @ed2ac40); `codex-rs/core/src/skills.rs` L38–209, `guardian-context/src/trusted_skills.rs` L1–60, `config/src/skills_config.rs` L20–90 (S-107 @0735c51); `openhands-sdk/openhands/sdk/skills/execute.py` L1–119 and `tool/builtins/invoke_skill.py` L60–140 (S-110 @3fc7b22); `opencode/packages/opencode/src/skill/index.ts` L120–135, L290–330 and `tool/skill.ts` (S-111 @9f8db11); `OpenHarness/src/openharness/skills/types.py` (S-117 @9b2efd7); `claude-agent-sdk-python/src/claude_agent_sdk/types.py` L263–540, L2230–2250 (S-109 @ad77094); `pi-mono/packages/coding-agent/src/core/skills.ts` L280–350 (S-113 @400d690); `modelcontextprotocol/schema/2026-07-28/schema.ts` L1659–1687 and `a2a/specification/a2a.proto` L436–450 (export targets, S-153 @aa8ce04, S-180 @98853be). The lift/export pair with a loss report, render purity, claims→grants at seal and the promotion policy are `no-precedent / novel` as an integrated contract.
- (c) Disconfirming evidence considered: (i) making activation confer read scope is what lets skills use bundled files at all — answered: the same reads happen through an `fs_read` capability scoped to the extension's content address, ledgered, without touching workspace scope; (ii) forbidding render-time exec breaks "dynamic context" skills — answered: the `filling` slot bound to a capability gives the same content with an effect record and Π in the loop; (iii) the promotion gate slows adoption of induced procedures — answered: induced procedures remain deliverable at their honest class into `admit_unknown_validity` slots; the gate governs *authority*, not availability, and the AFTER/AWM evidence is why; (iv) export loses almost everything, so T-LCD-11 is satisfied trivially — answered: the loss report is the honest artifact and the `metadata` string pairs keep round-trip identity; the ecosystem's spec is the constraint, not the design. None overturns.
- (d) Conditionality: assumes the Agent Skills spec keeps `metadata` as string→string and no typed slot (a future typed slot shrinks the loss report); assumes WS-H5's extension record ratifies as proposed; independent of model tier; the C0 slice assumes coding/computer-use environments.
- (e) Build-stage assignment: **C0 / Stage 2** (lift; render purity; claims→grants; detectors); **C1 / Stage 3–4** (exports with round-trip test; promotion policy; hook bodies as procedures with F1); **C2 / Stage 6** (induction and transfer gate with I5).

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-02 (lifted bodies are `Text` leaves counted by opacity), T-LCD-05 (per-skill model bindings become debt-recorded profile rules), T-LCD-10 (skill name is a surface; identity is semantic), T-LCD-11 (declared-lossy export with round trip), T-LCD-12 (operations), T-LCD-13 (delivered/activated/followed for lifted skills), T-LCD-06 (no IR dependence on any skill store or ABI). Does not by itself satisfy T-LCD-01/-04/-09 (ADR WS-D5-adr-2). **ADR-0024 rung:** prose → `Text` leaf → entity, with the pointer rule for scripts.

## Consequences

- WS-H5: `contributes` for `kind: skill` is exactly the lift output; `declared_claims.allowed_tools` reaches `allowed_capabilities` only through `seal`; OQ-H5-07 answered by ADR WS-D5-adr-1.
- WS-D1: bundled artifacts are handle-only `artifact_excerpt` candidates; the `procedures` slot never exceeds `external` for lifted bodies unless pinned.
- WS-F1: receives the hooks position as input to OQ-H5-04; WS-H7: activation confirmations are `approval`s of delivery, counted against the approvals budget.
- WS-E4/K3: `mcp_prompt` and `a2a_skill` exports join the target list (C1/C2); WS-L6: prefix keys for `metadata` (OQ-WS-D5-06).
- WS-I5: `induce` output must satisfy the promotion policy before any authority change; WS-J3: "skill on/off", "target", and "selector" are Lab factors.
- Scope register: stage note on R-2.4.5 (CF-WS-D5-04).

## Reversibility

**High** for the export mapping and stage note; **medium** for the promotion policy (a `PromotionPolicy` edit re-gates existing induced procedures); **low** for render purity and claims→grants-at-seal — relaxing either reopens the S-103 skill-elevation and render-time-execution vectors and would require superseding ADR-0019/ADR-0033.
