# ADR-NNNN — The model-install path: agent-initiated extension installation as a kernel Procedure of ordinary effects, approval of one install effect, attenuated and tainted results, and a non-widening definition edit

**Status:** proposed
**Owner workstream(s):** WS-H5 (consumers: WS-H1, WS-H7, WS-B2, WS-F3, WS-D5, WS-I5, WS-B3) · **Phase:** 2 · **Related:** ADR WS-H5-adr-1/-2, ADR-0002 (iii: no self-widening), ADR-0016 (delegation attenuates), ADR-0017 (`authority_delta = widening` refused from non-human origins), ADR-0025 (`verify_resume`), ADR-0030/0031 (effect lifecycle; risk class), ADR-0034 (P2 delegation, P3 effective authority), ADR-0035 (approval endorses one effect; `delegate` never endorses); OQ-022 ("especially when the agent itself can install new extensions"), OQ-101 (Π rows), OQ-H5-02; R-2.8.5, R-2.6.x

## Context

The sponsor scope names "the agent installing its own extensions" as in-scope (doc 3 §5 WS-H5 row; OQ-022). It already happens ungoverned in every audited harness: SKILL.md bodies instruct the agent to run installers, opencode pulls `skills.urls`, goose's `summon` extension adds sub-recipes, and ClawHavoc's infostealers were delivered exactly this way (S-WS-H5-15/16). The one governed precedent — codex's skill MCP-dependency install — gates on a human elicitation ("Install / Continue anyway"), a first-party originator and a feature flag (`codex-rs/core/src/mcp_skill_dependencies.rs` L1–60). Doc 2 §5.6 and §11 fix the principle: the model may propose but never confer; "the evolution service may propose a narrower permission or a new request for approval, but it should not be able to silently enlarge its own authority." ADR-0035 gives the type-level rules (a `delegate` origin never endorses; approval endorses one `effect_id` with canonical arguments; never content, never a class) and ADR-0017/0037 refuse widening diffs from non-human origins. What remains is to compose them into a path that is *usable* — so that self-extension is possible under attenuation — rather than pretending it does not occur.

## Options considered

1. **Forbid agent-initiated installation.** *Rejected:* out of scope with the brief; the ungoverned path (instructions telling the agent to run installers) exists regardless and would remain invisible to the ledger; the safe form of "forbid" is the `model_install = deny` policy value.
2. **Allow with a human approval that trusts the result** (the "single-approval persistent trust model" S-WS-H5-03 criticises; codex "Install" as the only gate). *Rejected:* approval fatigue (S-053) launders injected instructions into trusted extensions; ADR-0035 already scopes approval to one effect.
3. **Allow only pre-approved catalog entries** (org allowlist; Claude `pluginSuggestionMarketplaces`). *Rejected as the sole path:* it is a `TrustRootPolicy.allowed_sources` setting, orthogonal to who initiates; it does not answer what authority the installed extension gets.
4. **A kernel Procedure whose steps are ordinary ledgered effects, whose approval endorses only the install effect, whose result enters at ≤ `external` with taint and attenuated grants, and whose activation is a non-widening definition edit (chosen).**

## Decision

1. **The path.** `install_extension(candidate, proposer_ctx)` is a kernel-provided `Procedure` (MUST-code, ADR-0024) admitted only when the definition's `TrustRootPolicy.model_install ∈ {ask, allow_attenuated}`; `deny` makes any such proposal `ModelInstallDenied` (a ledgered refusal, not silence). Its steps are ordinary effects — `net_egress` (fetch from a declared or policy-allowed source only), `fs_write` (cache), `exec`/`spawn_process` (unpack, probe, resolve) — each authorized by WS-H1 through Π at the proposer's **effective authority** (`min(delegate, context_label)`; after reading instructing content this is ≤ `external`, ADR-0034 P3) with the proposal's taint including the instructing content. Whether install needs its own `EffectDomain` is OQ-H5-02 (WS-H1 dialect bump); until then Π's rows for `spawn_process`/`net_egress` at `external` apply (default `ask`).
2. **Approval scope.** The human `approval` endorses **the install effect** — `(effect_id, canonical args = {locator, expected content digest, isolation, requested grants})` — and nothing else (ADR-0035 basis `approval`). Unattended runs (no `ask`) may use `model_install = allow_attenuated` only, which admits installs that need no new grants and no network beyond declared sources, or `deny`.
3. **What the result is.** The `ExtensionRecord` has `installed_by = model(run_ref)`, `text_authority ≤ external`, `taint ⊇ {model, source, instructing_content}`, `grants ⊆ Permission(proposer)` (the extension is a delegate of the proposer: attenuation per ADR-0016/0034 P2 — child grants ⊆ parent's, child budget ≤ parent's), `isolation ≥ subprocess_confined`, `attestation_status` as verified; a signature verified under the trust-root policy may still yield a `pin` endorsement (the policy, not the model, is the endorser), which is the only way a model-installed extension's text can reach `definition`.
4. **Activation is a non-widening edit.** The extension enters the running definition only through a `HirDiff` with `origin = model`, `authority_delta ∈ {none, narrowing}` and `budget_delta ∈ {none, tightening}` (ADR-0017 refuses `widening` from non-human origins) — at most an L2 successor (ADR-0037); the run continues on the new version via `verify_resume` (ADR-0025) with `security.extension.install_completed{extension_id, diff_ref}`. Any install that would add a domain/scope the proposer lacks is `AuthorityWidening` and is *not* rescued by approval (approval endorses the effect of fetching, not a grant). `promotion` by a human reviewer (ADR-0035) after the run is the route to higher authority.
5. **Evolution and hosted participants.** Evolution candidates (`origin = evolution`, class `delegate`) use the same path with `model_install` read from the experiment's `authority_cap`; hosted participants' internal installs are invisible (`n/a`) and their outputs remain `participant`/`unverified` (ADR-0034 P2).
6. **Ledger.** `security.extension.install_requested{candidate, proposer_ctx, effective_authority, taint}` precedes any effect; `install_completed` or a typed refusal follows; approvals are counted (T-LCD-14; WS-H7 budgets them).

**T-LCD statement.** Satisfies T-LCD-12 (a Procedure over records; helper-executed), T-LCD-13 (the installed skill's later delivery/activation is observable with its `delivery_id`), T-LCD-14 (installs and approvals are budgeted and counted per arm), T-LCD-06 (hosted installs are `n/a`; nothing native changes for them). Not applicable: T-LCD-01…05/-07…11/-15. **ADR-0024 rung:** the Procedure is MUST-code; `model_install` is MUST-data (a `TrustRootPolicy` field under `authority_cap`).

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** instruction-driven installs as the delivery vector of a registry compromise — S-WS-H5-15/16 (Tier B); "single-approval persistent trust model" as a structural flaw — S-WS-H5-03 (`provisional`); approval fatigue bounds approval's meaning — S-053 (Tier B); model may propose, never confer; no self-widening — doc 2 §5.6/§11 (S-130), ADR-0002 (iii), ADR-0035; delegation attenuates — ADR-0016/0034, CapScope per-issuer checks S-105 (`provisional`, corroboration only); widening diffs refused from non-human origins — ADR-0017/0037; effective authority after reading external content — ADR-0034 P3 (Fides/Biba, Tier A via ADR-0033).
- **(b) Source-code precedent:** codex `codex-rs/core/src/mcp_skill_dependencies.rs` L1–60 @0735c51 (elicitation "Install"/"Continue anyway"; first-party-only; feature flag); goose `crates/goose/src/recipe/mod.rs` L254–271 (`summon` auto-added for sub-recipes — ungoverned counter-example) @fae91d0; opencode `packages/opencode/src/skill/index.ts` L226–231, `skill/discovery.ts` (remote pull without pin — counter-example) @9f8db11; Claude Code `pluginSuggestionMarketplaces` / `--yes` non-interactive install (S-WS-H5-17). **`no-precedent / novel`** for the composition: ordinary effects + approval-of-one-effect + attenuated tainted result + non-widening diff + `verify_resume`.
- **(c) Disconfirming evidence considered:** "the agent should never install anything" is simpler and safer — available as `model_install = deny`, but the ungoverned path exists in every harness and would stay unledgered; attenuated installs are useless because most extensions need new grants — accepted: those installs are refused with `AuthorityWidening` and surface as a human review item after the run (`promotion`), which is the intended friction for widening; per-install `ask` adds approval load — counted and budgeted (T-LCD-14) and reducible by `allowed_sources` + `allow_attenuated`; CapScope's numbers are five-task `provisional` — used as corroboration only. None overturns.
- **(d) Conditionality:** assumes a human principal is reachable for `ask` (unattended: `deny`/`allow_attenuated`); assumes Π rows for `spawn_process`/`net_egress` at `external` default to `ask` (OQ-101, WS-H1/H7); assumes `verify_resume` admits L2 successors mid-run (ADR-0025); independent of model tier and task class; the utility of attenuated self-installation is a Stage-4 Lab measurement.
- **(e) Build-stage assignment:** **C1 / Stage 4** (the Procedure, `model_install`, `install_requested/completed` events, AC-H5-7) after WS-H1's Π and WS-B5/E5 confinement exist; **C2 / Stage 6** for evolution candidates using the path under experiment `authority_cap`.

## Consequences

- WS-H1 treats install steps as ordinary proposals; `install_extension` never bypasses Π. WS-H7 renders the install approval with the SEP-1024 canonical plan and counts it.
- WS-F3 applies P2 attenuation to the installed extension as a delegate of the proposer; WS-B2 classifies install effects (fetch = `external` scope; cache = `workspace_local`).
- WS-D5 skills that reference dependencies (codex `SkillToolDependency` shape) declare them as candidates for this path rather than embedding installer commands in prose.
- WS-I5 evolution may propose extensions but can never widen (ADR-0002 iii restated for extensions).

## Reversibility

**Low** for "approval endorses the install effect, never the content or a grant" and "non-widening from non-human origins" (constitutional per ADR-0035/0017); **medium** for the `model_install` policy values and unattended defaults; **high** for the Procedure's internal step order.
