# ADR-NNNN — The extension lifecycle: declared sources instead of run-time discovery, pinning and surface pins at `resolve`, transparent `review`, update as supersession, revocation with propagation into live runs, and the extension audit trail

**Status:** proposed
**Owner workstream(s):** WS-H5 (consumers: WS-A5, WS-B1, WS-B3, WS-D1, WS-D5, WS-E2, WS-E4, WS-G1, WS-H1, WS-H6, WS-H7, WS-I3, WS-J2, WS-L5) · **Phase:** 2 · **Related:** ADR WS-H5-adr-1 (the trust model), ADR-0019 (closed-world rule; `relower`), ADR-0017/0037 (classified diffs; supersession; `RevocationRecord`; `StaleIndex`), ADR-0025 (`compose → resolve → validate_assembly → seal`; `verify_resume`), ADR-0026/0030 (ledger events; `action.effect.unknown`), ADR-0035 (mandatory provenance on `security.extension.loaded`; approval endorses one effect), ADR-0036/0038 (tree rule; bundle members); CF-H5-04/-05/-06; OQ-020, OQ-H5-03/-05/-06; R-2.8.5, R-2.10.2, R-2.9.3

## Context

Every audited harness discovers skills, plugins and instruction files at run time from a fixed list of locations, resolves names to `@latest` or a branch by default, refreshes in the background, and has no notion of "the tool surface I approved" for an MCP server (dossier F2–F4). MCP explicitly allows a server to change tool descriptions after approval; Invariant Labs and ETDI both recommend pinning "the version of the MCP server and its tools" (S-WS-H5-14, S-WS-H5-08). TUF names the update-channel attacks (freeze, rollback, mix-and-match, key compromise) and the remedies. HarnessHarness already has the pieces: the closed-world rule (no run-time surface without a compiled identity, ADR-0019), a single `compose → resolve → validate_assembly → seal` path (ADR-0025), supersession edges and `RevocationRecord`/`StaleIndex` enforced in the resolver (ADR-0037), a mandatory-provenance `security.extension.loaded` event (ADR-0035) and a bundle member "extensions + signatures" (ADR-0038). What is missing is the lifecycle that connects them for extensions, and the rule that an approval at install time endorses an *edit*, not content.

## Options considered

1. **Run-time discovery with a cache** (all audited harnesses). *Rejected:* violates the closed-world rule; the discovered item has no compiled identity, no provenance and no review; it is the S-103 vector.
2. **Pin the server/package but not its surface** (Claude marketplaces `sha`, OpenHands resolved commit). *Rejected as sufficient:* an MCP server at a fixed version can still return different descriptions per session (rug pull); the surface is what the model reads.
3. **In-place auto-update of sealed definitions** (goose auto-pull, Claude daily refresh, opencode `@latest`). *Rejected:* sealed definitions are immutable (ADR-0037 I4); silent updates make results unattributable and let a benign extension turn malicious between runs.
4. **Soft revocation** (a `disabled` flag; deny-lists). *Rejected:* the S-106 failure shape; ADR-0037 requires records enforced by the resolver.
5. **Declared sources enumerated at `resolve`; content + surface pins; transparent review whose approval endorses the seal diff; updates as supersessions with classified diffs; revocation records propagated into live runs; every step a ledger event and a bundle member (chosen).**

## Decision

1. **Discovery is declaration.** `DeclaredSource ∈ {directory_scan{root, scope}, marketplace{catalog_ref}, registry{name}, git{url, ref}, archive{url, sha?}, mcp_endpoint{uri}, instruction_files{roots}}` lives in the Assembly (ADR-0023 `slots`/`values`); `discover(sources, policy) → [Candidate]` is the only enumeration; implicit scanning of home or project directories does not exist. A "trusted folder" fact is a scope condition on a `directory_scan` source, never an authority input (ADR WS-H5-adr-1 L1).
2. **`resolve` pins.** For each candidate: fetch through a credential-free locator under WS-H4 egress policy; unpack under `archive_policy` (size cap, no links, no path escape); compute `content` (tree rule) and `code_identity[]`; for `mcp_server` connect in the declared isolation class and **lift a surface document** (`initialize` result incl. `instructions`, `tools/list`, `resources/list`, `prompts/list`) whose `ContentAddress` is the **surface pin**, minting `ToolCapability` nodes at `unverified` (ADR-0034 P7); run advisory validators; verify attestations; fill defaults; record `fetched_at`, resolved commit/digest/registry version and the source snapshot (ADR-0036 `registry_snapshot_id` over the closure). Typed failures: `UnpinnedInSealedForm`, `AttestationRequired`, `AttestationFailed`, `ArchivePolicyViolation`, `NameCollision` (never silent last-wins), `ScanDenied`, `SourceNotAllowed`, `IsolationUnavailable`, `StalePin` (`max_age`).
3. **`review` is transparent and endorses an edit.** `review(record, previous?)` renders untruncated (SEP-1024 shape): the canonical install/exec plan (command, arguments, declared env keys, isolation class, fs/network grants), the surface-document diff, `TextHygieneReport`, advisory findings, attestation status and the resulting `text_authority`. The human decision is an `approval` (ADR-0035 basis) whose subject is the `HirDiff` that adds/updates the extension — one endorsement of one edit; it never raises `text_authority` and never confers grants beyond the diff's declared `Permission`, which the definition's `authority_cap` bounds. Unattended definitions set `review = policy_only`.
4. **`seal` and `activate`.** `seal` refuses `status ≠ resolved` or `grants ⊄ authority_cap` and emits `security.extension.sealed{extension_id, trust_snapshot_ref}`. At run time `activate` emits `security.extension.loaded{extension_id, isolation, pin_check}`; for MCP servers the live surface is re-lifted and compared with the surface pin: on mismatch `ExtensionSurfaceDrift` — the changed/added tools are **not delivered** (closed-world), `security.extension.drift{diff_ref}` is appended, and the run proceeds per `drift_policy ∈ {refuse, quarantine_changed, accept_schema_only}` (default `quarantine_changed`; granularity OQ-H5-03). Skill delivery/activation/following emit the T-LCD-13 chain with the extension's `delivery_id`.
5. **`update` is supersession.** A new candidate resolves to a new `ExtensionRecord` with `supersedes{edit}`; the definition changes only through a `HirDiff` classified per ADR-0017 — `authority_delta = widening` (new grants, higher text class, hooks gaining block power) requires `human` origin with attestation (ADR-0037 L3); otherwise L2. Background refresh may prefetch and pre-resolve candidates and raise `UpdateAvailable`, but never re-seals; a run keeps its pins until `verify_resume` (ADR-0025). Version-label regressions are `LabelRegression` warnings at `review` (TUF rollback).
6. **`revoke` propagates.** `revoke(extension_id, reason, authority) → RevocationRecord` (ADR-0037 S1) marks dependants in `StaleIndex`; `resolve(mode = execute)` refuses them; live runs receive `security.extension.revoked{extension_id, reason}` and the kernel (a) drops the extension's surfaces from the next `context_assembly`, (b) converts its grants to `deny` in Π, (c) terminates its processes, (d) emits `action.effect.unknown` for its in-flight effects (ADR-0030; B3 rule), (e) annotates results `depends_on_revoked = true`. Signer revocation (ADR WS-H5-adr-1 §4) revokes transitively through `StaleIndex`. Propagation latency and quarantine-vs-terminate are OQ-H5-05.
7. **Audit.** Event classes `security.extension.{resolved, quarantined, sealed, loaded, drift, install_requested, install_completed, revoked}` all carry provenance (extending ADR-0035's mandatory table); the bundle member is `resolved_dependencies.extensions[]: {extension_id, content, trust_record: version_id, attestation_refs[], surface_pin?}` (refines ADR-0038 — CF-H5-06); `audit_view` answers "which extensions' text was in the proposing context of effect E, and whose code produced it" via `context_label.taint` and `Origin.tool(extension_ref)`. Advisory scanners are `Validator{kind: advisory}` registered with WS-G1; `scanner_policy` decides deny/quarantine/warn; `unavailable` is recorded, never treated as `clean`.

**T-LCD statement.** Satisfies T-LCD-10 (surface pins are content addresses over a typed document; renames are surface edits), T-LCD-11 (surface document is the lifted MCP form; drift is a typed `HirDiff`, never silent loss), T-LCD-12 (operations over records; implementable out of process), T-LCD-13 (activation chain with `delivery_id`), T-LCD-14 (approvals per update/install are counted). Not applicable: T-LCD-01/-02/-03/-04/-05/-06/-07/-08/-09/-15. **ADR-0024 rung:** the lifecycle operations are MUST-code; declared sources and policies are MUST-data.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** rug pulls and post-approval description changes — S-WS-H5-14 (Tier B), S-WS-H5-08 (Tier D, mechanism); update-channel attacks and their remedies (hashes in signed metadata, consistent snapshots, expiry, revocation via root) — TUF S-WS-H5-10 (Tier A); payload swapped after publication and scanner evasion — S-WS-H5-15 (Tier B); registry ownership weakness — S-WS-H5-07 (Tier C, DSN 2026); pin at moment of use — ADR-0036 F4 (OpenHands, Codex, Harbor); revocation must be a resolver-enforced record — ADR-0037 (S-106 `provisional (mech)` corroborated by OpenHands `Condensation`/Codex rollback); consent transparency — SEP-1024 (S-WS-H5-11); closed-world rule — ADR-0019.
- **(b) Source-code precedent:** software-agent-sdk `openhands-sdk/openhands/sdk/extensions/fetch.py` L170–284 (resolved SHA persisted), `plugin/loader.py` L30–60 (merge semantics, `max_skills`) @3fc7b22; pi-mono `packages/coding-agent/src/core/package-manager.ts` L139–144, L1101–1105, L1173 (pinned vs `@latest`) @400d690; codex `codex-rs/core-plugins/src/plugin_bundle_archive.rs` L127–235 (archive hardening), `core-plugins/src/marketplace_policy.rs` L35–80 (source allowlist), `core/src/hook_runtime.rs` L983–995 (per-run hook provenance) @0735c51; gemini-cli `packages/cli/src/config/extensions/update.ts` L57–63 (refuse update on integrity failure), `packages/core/src/hooks/trustedHooks.ts` @ed2ac40; goose `crates/goose/src/plugins/mod.rs` L153–260 (auto-update counter-example), `agents/extension_malware_check.rs` L425 (fail-open counter-example) @fae91d0; opencode `packages/opencode/src/plugin/shared.ts` L207–210, `skill/discovery.ts` (unpinned counter-examples) @9f8db11; Claude Code marketplaces (`sha`/`sha256` pins; daily refresh; command-source consent) S-WS-H5-17. **`no-precedent / novel`** for: the surface pin over a lifted MCP surface with drift as a `HirDiff`; approval-of-the-seal-diff; revocation propagation into live runs through `StaleIndex` and `action.effect.unknown`.
- **(c) Disconfirming evidence considered:** catalogs drift and users want updates (OpenHands deny-lists; daily marketplace refresh) — absorbed by selector-vs-pin (authored selectors stay legal; only the sealed form pins) and by prefetch + `UpdateAvailable`; benign description churn will trip drift — accepted as the definition of a rug pull, made reviewable rather than silent, tolerance is policy (OQ-H5-03); one re-seal per update is friction — that is the moment grants and hooks should be seen, and the diff is classified so L1/L2 updates need no human; run-time discovery is what users expect — preserved as a `directory_scan` source at `resolve` (CF-H5-04). None overturns.
- **(d) Conditionality:** model- and task-independent; assumes the resolver can fetch and hash directories (ADR-0036 H3/H7 host requirements) and that MCP servers expose their surface at `initialize`/`tools/list` (protocol-guaranteed); assumes B3's resume semantics for in-flight effects of a revoked extension; drift tolerance depends on the server population (measured at Stage 4).
- **(e) Build-stage assignment:** **C0 / Stage 1** (declared sources; `resolve` pins; `UnpinnedInSealedForm`; event classes); **C0 / Stage 2** (`activate` with `pin_check`; instruction-file sources); **C0 / Stage 3** (bundle member, `audit_view`); **C1 / Stage 4** (surface pin + drift for MCP with WS-E4; `review` UX with WS-H7; update/supersession flow; revocation propagation with B3/H6; advisory validators with G1); **C2** (organisation-layer policies; cross-extension flow).

## Consequences

- WS-A5's `resolve` gains extension resolution and the `trust_snapshot`; WS-J2 stores extension records and name histories; WS-I3 carries `extensions[]` per the refined member list.
- WS-E4 implements `lift_surface`/`check_surface`; WS-E2 treats surface-document fields as compiled surfaces subject to the closed-world rule.
- WS-B1 adds the `security.extension.*` classes to the mandatory-provenance table; WS-H6 attests them; WS-B3 handles `action.effect.unknown` on revocation.
- WS-H7 renders `review` and counts install/update approvals; WS-G1 registers advisory validators.
- WS-D5's skills and WS-F1's hooks are extension kinds that enter only through this lifecycle.

## Reversibility

**Low** for "discovery is declaration", pinned sealed forms and resolver-enforced revocation (they are restatements of ADR-0019/0036/0037 for extensions); **medium** for the surface-pin granularity and `drift_policy` defaults (policy data); **high** for the review rendering and prefetch behaviour (product surface).
