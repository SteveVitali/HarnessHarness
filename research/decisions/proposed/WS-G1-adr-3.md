# ADR-NNNN — Check placement: kernel local checks after every effect terminal event, declared postconditions bound to capabilities or rules, global monitors at `verify`/`stop`; and the deterministic `followed` detector table per artifact kind

**Status:** proposed
**Owner workstream(s):** WS-G1 (consumers: WS-A2, WS-A3, WS-B1, WS-B2, WS-B4, WS-D4, WS-E1, WS-E5, WS-F1, WS-F2, WS-G3, WS-I1, WS-I2, WS-C3) · **Phase:** 2 · **Related:** ADR-0012 (harness step `execute → verify → persist → decide`; `DecisionPoint`), ADR-0016 (`ToolCapability.output_schema/preconditions`; `Procedure.Verify` step; `HarnessRule.action = require Validator`; `validates` targets), ADR-0030/0031 (effect terminal events; `resource_keys[]`; `probe`), ADR-0022 (E1 effect equality; E6), ADR-0014 (compliance chain; `activation_observable`), ADR-0040 (soft budgets as `HarnessRule`s), ADR-0044 (M11; grounding metrics), ADR-0047 (`trace_predicate`, `schema` oracle classes), ADR-0007 (T-LCD-05/-08/-13/-15); OQ-049 (blocking), OQ-062, OQ-WS-G1-01/-02; CF-WS-G1-04/-05; R-2.7.1, R-2.4.4

## Context

Doc 2 §5.3: "local checks run immediately after side effects (schema validation, exit codes, diff sanity, permissions, postconditions); global checks evaluate task-level invariants and evidence of completion." Phase 1 placed `verify` as the P4 plane operator after `execute` (ADR-0012), reserved `postcondition_results[]` on the `Effect` record (ADR-0030), typed `Procedure.Verify` steps and `HarnessRule{action: require Validator}` (ADR-0016), and left OQ-049 — which artifact kinds get deterministic `followed` detectors — **blocking** T-LCD-13 at Stage 3 with G1 among the owners. The audit shows local checks are cheap and universal (aider lints edited files and runs tests after every edit; SWE-agent lints inside the edit with a pre-edit baseline so only *new* errors count; Codex/Claude SDK/Gemini/opencode expose a post-tool seam; OpenHands' critic has an `all_actions` mode), that global checks are trace/end-state monitors (HAL compliance checkers, OpenHands stuck detector, Anthropic's browser-driving evaluator), and that no runtime records a deterministic `followed` event (ADR-0014 (b)).

## Options considered

1. **All checks at the end (verifier-only).** *Rejected:* the model iterates on wrong state for many turns (aider/SWE-agent exist precisely to avoid this); false completion is detected too late.
2. **All checks fused into tools (SWE-agent edit-and-undo).** *Rejected:* not ablatable or attributable per check (T-LCD-02/-08); revert belongs to B4.
3. **Local checks only by declared hooks (Codex/Claude SDK style; nothing built in).** *Rejected:* schema conformance, exit status and patch status are already in the kernel's hands after E5 captures the effect; leaving them undeclared makes the Stage-0/1 baseline unverifiable and the grounding metrics uncomputable.
4. **Kernel built-in local checks + declared postconditions + global monitors at decision points, with a per-kind deterministic detector table (chosen).**

## Decision

1. **Kernel local checks (MUST-code, always-on for native runs).** After each effect terminal event (`action.effect.observed`, or `probed → observed`), the `verify` operator appends one `verification.validator.verdict{phase = local, detector = deterministic, charged_to = subject}` per applicable built-in: (a) `schema_conformance` — observation payload vs `ToolCapability.output_schema` (E6 guarantees the fields survive lowering); (b) `exit_status_class ∈ {success, failure(code), timeout, signal}` for `exec` domains, from the executor's captured status; (c) `patch_application ∈ {applied, rejected(hunks), partial}` and `touched_paths ⊆ resource_keys[]` for `fs_write` domains; (d) `diff_sanity` — size/line/file-count bounds and no path outside the sealed `Permission` scope — a **conditioned rule** with an assumption-debt record (thresholds are model/task-dependent; defaults OQ-WS-G1-02). Built-ins are kernel-owned `Validator` nodes in the reference dialect (`hir/kernel/<check>`) so they appear in `lcd_report.conditioned_rules` and can be ablated in the Lab. Their cost is metered as `harness_overhead.verification` (M11).
2. **Declared local checks (MUST-data).** `ToolCapability.postconditions: [Ref<Validator>]` (proposed HIR/1 field beside `preconditions`; if WS-A3 rules it an HIR/2 item, the equivalent binding is `HarnessRule{trigger: action.effect.observed{capability_id ∈ S}, action: require Validator(v)}`, which needs no dialect change — OQ-WS-G1-01, CF-WS-G1-05) and `Procedure.Verify(Ref<Validator>)` steps. Evidence: the effect record, `output_artifact_ids[]`, end state on `resource_keys[]`, and `baseline_ref` for before/after predicates (`new_findings = findings(after) − findings(baseline)` — the SWE-agent rule generalized). `Effect.postcondition_results[]` is the list of these verdicts' `EventRef`s (CF-WS-G1-04).
3. **Global checks.** Contract criteria with `role ∈ {invariant, acceptance}` and `phase ∈ {global, completion}` are evaluated (a) at `DecisionPoint.verify` on the control strategy's declared cadence (default conditioned rule: before every `stop` proposal and every N turns), (b) at every `stop` proposal, (c) at the completion gate (ADR-1). Invariants are `trace_predicate`/`end_state` monitors over `(run_id, 0..head)` and the end-state handle with three-valued verdicts; `inconclusive` is never a pass. The `probe` verb (ADR-0030) is a read-only validator invocation and shares the verdict record.
4. **Consequences of a `fail` are not G1's.** F2 keys `retry`/`stop`/`escalate` on `Verdict.value/phase/role` with bounded reflection; B4 may `revert(effect_id)` on a local `fail` when `baseline_ref` exists; no local `fail` mutates history or un-executes an effect (ADR-2 item 4).
5. **Deterministic `followed` detectors (answer to OQ-049, G1 half).** A `followed` event is deterministic iff the artifact references (via `validates`) a `schema` or `trace_predicate` validator the kernel can evaluate from `events`/`end_state` alone: `tool_surface` → args conform to the compiled surface schema and narrowings, effect class equals declared (always deterministic); typed `procedure` → the ordered `control.decision`/`action.tool.proposed` subsequence matches its `Invoke/Verify/Branch` steps in the window and every `Verify` step has a verdict; kernel-executed `rule` → the action's postcondition holds in the ledger (tool set restriction, validator required, approval required); soft-budget `rule` (ADR-0040) → `control.budget.consumed` totals stay under threshold or the declared reaction appears; closed-schema `memory` → the value reappears in a later effect's canonical-args pre-image or `resource_keys[]` (citation-in-action); `instruction` → only when it carries a `validates` edge to such a validator (e.g. "run tests before finishing" ⇔ `VerificationSkipped` never trips). Prose instructions, `Instruction`-only procedures and prose memories stay judged-only (WS-G3, ADR-0047 obligations). The per-profile share of delivered artifacts with `detector = deterministic` is a reported metric (AC-G1-9); `activation_observable` semantics are unchanged (ADR-0014).
6. **Hosted participants.** Local checks render `n/a{observability}` unless the hosting mechanism yields effect terminal records with `events`; global end-state criteria apply to all classes; no native field is added (T-LCD-06/-15).

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-13 (deterministic `followed` detectors named per kind; judged remainder labelled), T-LCD-05 (`diff_sanity` and cadence rules are conditioned rules with debt records), T-LCD-08 (built-ins and declared validators receive profile and account; a family-specific tolerance is a profile-conditioned validator, not a kernel branch — T-LCD-01), T-LCD-15 (class-scoped `n/a`), T-LCD-02 (built-ins are ablatable nodes), T-LCD-12 (operations). Not applicable: T-LCD-03/-04/-06/-07/-09/-10/-11/-14 (T-14 via ADR-2's metering). **ADR-0024 ladder rung:** built-in checks and the `verify` operator's placement = MUST-code; postcondition refs, cadence, thresholds, detector bindings = MUST-data (references, parameters, conditioned rules).

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: post-effect local feedback converts hidden mistakes into observations — doc 2 §5.3 (Tier B synthesis), S-014/S-114 (SWE-agent ACI, Tier A paper + source), S-121 (aider, Tier B source); postconditions gate commit — S-WS-G1-03 (ToolGate; mechanism admissible), S-204 (`provisional`); runtime verification as trace monitoring with inconclusive verdicts — S-WS-G1-02 (Tier A); activation is deterministic for skills/retrievals/tool calls and following is judged in the literature — S-088, S-077 via ADR-0014 (`provisional (mech)`, ratified use); soft-budget compliance measured via the chain — ADR-0040 (ratified). No `provisional` number is load-bearing; C0 items rest on Tier A/B source and ratified ADRs.
- (b) Source-code precedent: `aider/aider/coders/base_coder.py` L1599–1618 (`auto_lint`/`auto_test` after edits; `lint_outcome`/`test_outcome`), `aider/aider/linter.py` L82–135, L177–232 (syntax/compile/flake8 checks on edited files with tree context), `SWE-agent/tools/windowed_edit_linting/bin/edit` L94–116 (pre/post lint baseline; only new errors), `software-agent-sdk/openhands-sdk/openhands/sdk/agent/critic_mixin.py` L34–76 (`all_actions` vs `finish_and_message` modes), `software-agent-sdk/.../conversation/stuck_detector.py` L104–160 (trace-predicate monitors), `hal-harness/hal/utils/compliance_checkers.py` (trace constraints with opportunities), `codex/codex-rs/core/src/tools/registry.rs` L698–745 (post-tool seam placement after the effect completes), `software-agent-sdk/.../event/llm_convertible/message.py` `activated_skills` (deterministic activation, via ADR-0014). Deterministic `followed` detectors and kernel built-ins as ablatable `Validator` nodes: `no-precedent / novel`.
- (c) Disconfirming evidence considered: (i) always-on local checks cost a validator run and an event per effect — bounded to what the kernel already holds (a)–(d), with declared postconditions opt-in; (ii) aider makes auto-test opt-in and asks before fixing — the *reaction* is F2's policy and may be opt-in; the *verdict* is cheap and always recorded; (iii) `followed` detectors for memories via citation-in-action can produce false positives (a value reappearing by coincidence) — the metric carries `detector_ref` and the predicate's specificity is part of its debt record; (iv) fusing lint into the edit tool (SWE-agent) is simpler — but not ablatable or attributable. None overturns.
- (d) Conditionality: built-ins (b)/(c) assume `exec`/`fs_write` domains (coding/terminal environments) — other domains contribute only (a) until their executors capture equivalents; detector coverage depends on the share of typed artifacts in a definition (reported, not assumed); judged detectors assume `model_io`.
- (e) Build-stage assignment: C0 / Stage 1 — `verify` placement, built-ins (a)–(c), verdict events, AC-G1-1; C0 / Stage 2 — built-in (d) with debt record, `postconditions`/`HarnessRule` binding, `baseline_ref` predicates (B4), `Procedure.Verify`; C1 / Stage 3 (evaluation-first) — global monitors at `verify`/`stop`, detector table wired for the reference harness under two profiles (AC-G1-9), grounding metrics; C2 / Stage 4 — judged detectors (G3), hosted `n/a` rendering (J6).

## Consequences

- WS-A3 decides `ToolCapability.postconditions` vs the `HarnessRule` binding (OQ-WS-G1-01/CF-WS-G1-05) and whether `validates` gains `ToolCapability`/`Effect` targets; WS-B2 references verdicts from `postcondition_results[]`; WS-E5 exposes captured exit status, patch status and touched paths on the effect terminal event; WS-B4 exposes `baseline_ref` and `revert`; WS-F1 declares its verification cadence and whether `verify` guards reference Validators (OQ-WS-G1-04); WS-F2 owns bounded reflection; WS-D4 supplies memory validity checks as validators and the closed-schema marking that enables citation-in-action; WS-B1 records `followed` with `detector_ref = validator_ref`; WS-I1/I2 compute `validator_pass_rate`, `local_check_fail_rate_per_effect` and the deterministic-`followed` share; WS-G3 owns everything in the judged column; WS-C3 may condition built-in thresholds per profile through conditioned rules only.
- OQ-049 is answered for the G1 half; it stays open for D4 (memory validity checks) and B1 (payload confirmation) until Phase 2 synthesis.

## Reversibility

**High.** Built-ins are ablatable nodes; disabling one is a definition parameter; moving a check from kernel to declared (or back) is a migration-ladder move (ADR-0024) with no data loss because every verdict already records its `validator_ref` and `phase`.
