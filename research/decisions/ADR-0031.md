# ADR-0031 — Effect risk class (reversibility × repeat-safety × scope), per-class delivery semantics, idempotency-key derivation, and monotone consumption by the kernel and approval policy (OQ-015)

**Status:** **ratified, amended** (Phase 2 synthesis, 2026-09-10); previously: **ratified, amended** (Phase 1 synthesis, 2026-09-10)
**Owner workstream(s):** WS-B2 (consumers: WS-H1, WS-H7, WS-E1, WS-E5, WS-F2, WS-A3, WS-A4/E4, WS-J6) · **Phase:** 1 · **Related:** ADR-0001, ADR-0002 (security kernel outside the editable policy surface), ADR-0007 (T-LCD-07/-11/-12), ADR-0011; ADR-0030, ADR-0032; ADR-0015 (`EffectClass` kind sum); CF-061, CF-062, CF-063, CF-065; OQ-015, OQ-041, OQ-055, OQ-086, OQ-087, OQ-091; R-2.2.2, R-2.6.2, R-2.8.1, R-2.8.7

## Context

Doc 2 §10 asks for "the right idempotency, checkpoint, transaction, and exactly-once/at-least-once semantics for real-world agent actions" (OQ-015) and §5.5 names the hard boundary: irreversible external action "requires explicit transaction semantics rather than assuming a filesystem-style undo exists". The audit (dossier §4a M2, M5) shows: exactly-once effect is not a transport property (Helland S-199); production APIs achieve effectively-once by client-minted keys and server-side replay (Stripe S-200; Temporal S-201); no audited harness passes a key to a tool executor; two harnesses already key approval on a risk class but source it heterogeneously — Codex from deterministic patch/command analysis (`safety.rs`), OpenHands from a model-supplied `security_risk` argument (`agent.py` `_extract_security_risk`) — and MCP declares its annotations untrusted (S-153). WS-A3 has fixed `EffectClass` as the closed sum of effect *kinds*; this ADR names the orthogonal risk triple and its consumption so the security kernel (WS-H1) acts on one deterministic input.

## Options considered

1. **Single scalar risk level (LOW/MEDIUM/HIGH), model-predicted** (OpenHands). *Rejected:* conflates reversibility, repeat-safety and scope; self-report is gameable by injection; cannot drive delivery semantics.
2. **Trust tool-declared hints (MCP annotations) as the class.** *Rejected:* the MCP spec itself forbids decisions on annotations from untrusted servers; misdeclaration is undetectable statically.
3. **Uniform at-least-once with mandatory idempotent tools** (Temporal default). *Rejected:* shell and browser effects have no target to honour a key; would silently duplicate non-idempotent effects.
4. **Uniform at-most-once, no retries.** *Rejected:* throws away cheap, safe retries for read-only and reversible effects, which dominate coding workloads.
5. **Three-attribute effect risk class, kernel-assessed and monotone (`max_by_danger`), with per-class delivery semantics and a ledger-derived idempotency key (chosen).**

## Decision

1. **Effect risk class** = `{reversibility ∈ {read_only, reversible, compensable, irreversible}, repeat_safety ∈ {idempotent, non_idempotent}, scope ∈ {workspace_local, external}}`, **derived** from the capability's declared `EffectClass.attributes` (CF-104: `reversibility' = read_only if mutability = read_only else reversibility`; `scope = workspace_local if world = closed else external`; `repeat_safety` verbatim) — never a second declaration on `ToolCapability` — and re-assessed per effect by the kernel. Name fixed as *effect risk class* to avoid collision with `EffectClass` (CF-065).
2. **Monotone effective class.** `effective_risk_class = max_by_danger(kernel_assessed, declared)`; `unknown` ⇒ `{irreversible, non_idempotent, external}`. Sources for `kernel_assessed`, in precedence: static capability metadata → deterministic argument analysis (path/writable-root containment, parsed command classes, network host policy) → hooks → model self-report, which may only *raise* the class. Untrusted server hints never lower it.
3. **Delivery semantics per effective reversibility** (dispatch / on `unknown` / approval default / undo): `read_only` — at-least-once, free retry, no write-ahead / redispatch / auto / none. `reversible` (workspace_local) — at-least-once; effectively-once by revert-and-redo from `baseline_ref` or by dedup key / probe by diff, else revert + redispatch / auto inside sandbox with writable-root containment, ask outside / mechanical revert (WS-B4/B5). `compensable` — at-most-once dispatch per attempt with mandatory idempotency key; effectively-once iff `dedup_support ≠ none` / probe first; `not_applied` → retry same key; `undeterminable` → escalate after `max_probes` / auto iff a compensation plan is registered and the grant covers it, else ask / compensator (ADR-3). `irreversible` — at-most-once, **no automatic retry ever** / never redispatched automatically; escalated with evidence / **ask**, per-effect approval record with approver identity; session cache only on a canonical action pattern (Codex `ApprovedForSession` precedent), never a bare call id / none — `abandoned` or human resolution. `idempotent` repeat-safety permits redispatch from `unknown` without a probe; `external` scope raises the approval default one step.
4. **The spec never claims "exactly-once effect".** It promises *effectively-once* where `dedup_support ∈ {executor, target}` and *at-most-once dispatch* where `dedup_support = none` and the class is not repeat-safe.
5. **Idempotency key** `= H(run_id, effect_id, canonical(args), capability_version)` over the WS-A3/B1 canonical form (OQ-041); stable across attempts and restarts; executors declare `dedup_support ∈ {none, executor, target}` and `dedup_window`; with `executor` the executor stores `(key → Observation)` and replays; with `target` the key is forwarded in the target's idempotency slot via typed extension slots (T-LCD-11). Invariant: one key never yields two `applied` observations with different outputs when `dedup_support ≠ none`. Key derivation is the effect model's; retry counts/backoff/budget are the control envelope's (CF-061).
6. **Kernel/approval interface (OQ-015 answer).** Input `{declared_risk_class, kernel_assessed_class, effect_kind, scope, resource_keys, capability_grant, approval_cache}`; output `KernelDecision{effective_risk_class, allow | ask | deny, reason, cache_key?}`; cache key `H(canonical action pattern, scope)` with run/session lifetime, recorded as `decider = cache` with the originating `permission_id` (WS-H6 audit). Approval fatigue mitigation (scope narrowing, caches) is WS-H7's; the class defaults above are the floor it narrows from.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: exactly-once is not achievable by transport; dedup is the receiver's obligation — S-199 (Tier A/B), S-200, S-201 (Tier B); classification is a property of the action space, irreversible conflicts are unrecoverable by any algorithm — S-205 (`provisional (mech)`, theorem used, corroborated by Sagas S-197 "acceptable approximation"); class-keyed confirmation with an incomparable `UNKNOWN` — S-110 `security/{risk,confirmation_policy}.py`; deterministic containment-based safety assessment and session-scoped approval cache — S-107 `safety.rs`, `sandboxing.rs`; annotations are untrusted hints — S-153; adapters own idempotency — S-108 §10.5; approval fatigue is real (~93 % approve) — S-053 (Tier B). Verify-before-retry with keys reduces duplicates — S-204 (`provisional`, simulated; not load-bearing).
- (b) Source-code precedent: `codex/codex-rs/core/src/safety.rs` L11–29 (`assess_patch_safety` → `AutoApprove | AskUser | Reject`), `codex-rs/core/src/tools/sandboxing.rs` L70–111 (`with_cached_approval`, `ApprovedForSession`), `codex-rs/core/src/turn_diff_tracker.rs` L52–127 (per-path baseline); `software-agent-sdk/openhands-sdk/openhands/sdk/security/risk.py`, `security/confirmation_policy.py` L43–55 (`ConfirmRisky`, `confirm_unknown`), `agent/agent.py` L1068–1090 (`_extract_security_risk`), `tool/tool.py` L215–260, L704–709 (`ToolAnnotations`, `DeclaredResources`, readOnly suppression); `modelcontextprotocol/schema/2026-07-28/schema.ts` L1903–1954. The *integrated* three-attribute class with per-class delivery semantics and a ledger-derived key presented to executors is `no-precedent / novel` relative to Stripe/Temporal API-layer keys and the two harness classifiers.
- (c) Disconfirming evidence considered: reversibility of arbitrary shell commands is undecidable and every production classifier is heuristic (S-107, S-110) — does not overturn: the class is the only input a deterministic kernel can act on; the `unknown ⇒ irreversible` default plus scope narrowing (sandbox + writable roots) keeps most coding effects `reversible`; the residual is approval volume, owned by WS-H7 with S-053 in view. Keys are useless for targets that cannot honour them — accepted and made explicit (`dedup_support = none` ⇒ at-most-once). Managed Agents lets the model decide retries (S-047) — holds for `read_only`/`reversible`, which is all that system operates on (CF-062). OpenHands honours model self-report (S-110) — adopted only upward (CF-063).
- (d) Conditionality: independent of model tier; the *approval defaults* are a floor that policy may narrow per task class and trust level (a sandboxed benchmark run may auto-approve `compensable`; a production deployment may not). Assumes a sandbox with declared writable roots exists (WS-B5/E5) so `reversible` is common; without it most effects degrade to `compensable`/`irreversible` and approval volume rises. Assumes executors can declare `dedup_support`; where they cannot, the class is honest about at-most-once.
- (e) Build-stage assignment: **C0 / Stage 1** — risk-class attributes on `ToolCapability`, `effective_risk_class` in the kernel decision, key derivation, per-class dispatch table, static checks AC-B2-05/-07; **C1 / Stage 2** — executor-side dedup store; **Stage 3** — AC-B2-01 duplicate-after-retry battery; **Stage 4 (WS-E4)** — target-side key forwarding.

**T-LCD statement (ADR-0007 decision 5).** Satisfies: T-LCD-07 (undeclared ⇒ `unknown`, never coerced to `read_only`), T-LCD-12 (contract is operations, implementable out-of-process), T-LCD-10 (class attaches to the semantic capability, not its surface name). Does not by itself satisfy T-LCD-11 (class/key survival through MCP/A2A/ACP lowering) — mitigated by the mandatory lowering loss report (WS-A4) and AC-B2-09; T-LCD-04 (identical effect invariants across targets) is an executable Stage-3 obligation shared with WS-A4.

## Consequences

- WS-E1's `ToolCapability` gains no new field: the risk class is projected from `EffectAttributes` (CF-104); the `Effect` record carries `declared: EffectClass` and `effective_risk_class`.
- WS-H1's reference monitor consumes `effective_risk_class` as a required input; model self-report enters last and only upward. WS-H7 designs approval UX from the per-class floor; caches key on canonical action patterns (OQ-091).
- WS-F2 keys retry/backoff policy on the class and never redispatches `irreversible` automatically; WS-E5 executors accept the key and declare `dedup_support`.
- WS-I2 gains class-scoped process metrics (duplicate-effect count, `abandoned` count, approval count per class).

## Reversibility

**Medium.** Adding attributes or values to the risk class is additive; loosening the `irreversible` no-auto-retry rule later is a policy change. Collapsing the triple to a scalar after WS-H1/H7/F2 consume its axes would lose the ability to express "idempotent but irreversible" (safe to redispatch, never safe to auto-approve) — the case that motivates the split.
