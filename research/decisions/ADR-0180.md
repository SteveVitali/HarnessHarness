# ADR-0180 — The plugin contract model: `PluginManifest/1` as an inventory of registry-kind contributions with `requires` over Core contract versions, `requests` as deny-by-default claims, pinned dependencies, a pre-load compatibility gate, and `ContractVersionPolicy` sunsets

**Status:** ratified
**Owner workstream(s):** WS-L5 (consumers: WS-J2, WS-H5, WS-A5, WS-K4, WS-L6, WS-I3, WS-J1, WS-J3) · **Phase:** 3 · **Related:** ADR-0008 ("plugin" = third-party packaging), ADR-0015 (`ext` rules), ADR-0023/0024/0025 (data document; pointer rule; `resolve`/`seal`/`instantiate`), ADR-0033/0035 (no widening; issuer ≥ `principal`), ADR-0036/0037/0038 (identity, supersession, bundle), ADR-0050 §8 (language-use), ADR-0060 (`ContainmentPolicy`), ADR-0063/0064 (extension record, trust legs, lifecycle), ADR-0099 (probe-first negotiation), ADR-0151/-3 (record kinds, envelope, `contract_range`, namespaces, import/export); CF-055, CF-141, CF-330, CF-378, CF-381; OQ-411, OQ-412; R-2.12.2, R-2.10.2, R-2.8.5

## Context

Doc 3 §2.12 makes "extensibility / plugin architecture & third-party component contracts" a C0 Must and §1.3 requires that extensions reach each other only through Core-defined contracts. Phase 1–2 fixed the pieces a plugin decomposes into — component variants and their registry records (ADR-0023, WS-J2), extension records with three-leg trust (ADR-0063), skills as lifted Procedures (ADR-0086), lifted MCP surfaces (ADR-0088), validators (ADR-0110), profiles (ADR-0124) — but not the *package* that carries several of them, what it declares about the Core versions it needs, or how compatibility is checked before anything is loaded. The audit of five plugin architectures at pinned commits (dossier §3–§4) found that every manifest is already an inventory of contributions by kind (Pi `package.json#pi` lists; gemini `gemini-extension.json`; codex `PluginManifest{paths{skills, mcp_servers, apps, hooks}}`; Claude Code `plugin.json`; goose lowering two foreign formats to one install record), that none versions the contract a plugin *implements*, that only one gates on the host version and only for one source kind (opencode `engines.opencode`, npm plugins only), that all resolve unpinned by default, and that none declares plugin resources deny-by-default — a property found outside the field in Extism's manifest (`allowed_hosts`/`allowed_paths` empty ⇒ none; hash-pinned sources).

## Options considered

1. **Plugin = one variant** (a package is exactly one `VariantRecord`; skills/hooks/servers are separate installs). *Rejected:* every audited ecosystem ships multi-kind packages; forcing one kind per package moves the composition problem into the user's configuration and loses the shared trust record.
2. **Plugin = code module with a registration API** (Pi/opencode shape: the package exports a factory that registers whatever it likes). *Rejected:* the contribution set is then discoverable only by executing the code, which violates WS-J2's no-load-on-read (R3), ADR-0063 L5 (no in-process third-party code) and X1 (reach defined by declaration).
3. **Plugin = inventory manifest with host-version range only** (VS Code/opencode `engines` shape). *Rejected as insufficient:* it says which *host* the plugin runs on, not which class contracts it implements; a contract bump would silently break variants (WS-J2 fixed `contract_range` for exactly this).
4. **Plugin = inventory manifest whose contributions are registry records, with `requires` over Core contract versions, `requests` as deny-by-default claims lowered to a Permission at `seal`, per-executable isolation, pinned dependencies, a pre-load compatibility gate and a published `ContractVersionPolicy` (chosen).**

## Decision

1. **A plugin is an `ExtensionRecord{kind: plugin}` whose `manifest` conforms to `PluginManifest/1`** — `{identity{namespace, name, version_label?}, requires{hir_dialect, registry_dialect, plugin_abi: Range; contracts: [ContractRef{kind ∈ {class_contract, record_kind, protocol_binding}, id, version_range}]; records: [VersionedRef]}, contributions: [Contribution{kind: RecordKind, path_or_locator, declaration, executable?{code_pointer, isolation, placement_preference?, one_shot?, host_requirements}, contract_range?}], requests{effects[], fs_roots[], egress[], env_keys[], budget_share?, hot_path_operations[]}, claims, conformance_claims[], parameters?, summary: Text, ext}`. Every contribution resolves to one `registry/1` record (WS-J2) with its own `version_id`, envelope and, where executable, its own trust legs (ADR-0063); a plugin has no behaviour beyond the closure of its contributions. The manifest carries no code (ADR-0023 decision 1; ADR-0024 pointer rule); unknown contribution kinds and unknown non-`ext` keys are errors.
2. **Requests are claims; grants are conferred at `seal`.** `requests` is lowered by `review → seal` into one `Permission` issued by the sealing principal (ADR-0035 check 1) after the author accepts or narrows it; the helper enforces it as the plugin's `ContainmentPolicy` (ADR-0060). The default is deny everything (Extism rule). `claims` (`allowed-tools`, `capabilities` strings, annotations) never reach the monitor (ADR-0063 L3). A `requests` entry exceeding the definition's `authority_cap` is `RequestsExceedCap` at `validate_assembly` (ADR-0024).
3. **Compatibility is declared over Core contract versions and checked before load.** `check_compatibility(manifest.requires, ContractVersionPolicy, class_catalog)` runs inside `resolve`, before any executable is fetched, unpacked or launched, for every source kind (file, package, git, archive, marketplace); failure is `ContractIncompatible{ref, offered_range, supported_range, sunset?}`. `hello` (ADR-0181) re-negotiates the highest common version at bind time (probe-first, ADR-0099). **`ContractVersionPolicy{contract: ContractRef, supported: [version], sunset: map<version, date | stage>, additive_only: bool}`** is a `hh/`-namespace registry record (MUST-data). Additive changes (a new optional operation, field or capability) never bump a `contract_version` — they are tri-state capabilities negotiated at `hello` (T-LCD-07); a breaking change is a new `contract_version` with a sunset window during which both are supported; `resolve(mode = execute)` refuses past the sunset with a dated reason.
4. **Pinned in sealed form; updates are supersessions; never auto-update.** After `resolve`, every `requires.records[]` entry and every `code_pointer` is a `version_id`/`ContentAddress` (ADR-0036 N5; `UnpinnedInSealedForm`). A new plugin version is a new `ExtensionRecord` with `supersedes{edit}` and a classified `HirDiff` over its contributions; `authority_delta = widening` (new `requests`, a higher text class, a hook gaining `required`) requires `human` origin (ADR-0017/0037 L3); bound plugins keep their pins until `verify_resume` (ADR-0025). The variant host never advances a bound plugin (CF-330 rejected precedent).
5. **Foreign formats are imported and exported with loss reports** (WS-J2 `import`/`export`; T-LCD-11): Claude Code `plugin.json`, gemini `gemini-extension.json`, codex agent-plugin manifests, Pi `package.json#pi`, Agent Skills trees and MCP `server.json` lift to quarantined plugins whose `LossReport` names at least `{requires, requests, per-executable isolation, contract_range}`; a first-party plugin lowers to each with the same report.
6. **Namespaces and publish authority** are ADR-0153's: a third-party plugin never publishes into `hh/`; its contributions' text legs default per the ADR-0063 table; `admission` of the plugin is the minimum over its contributions' admissions (proposed; OQ-412).

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-10 (identity is content and `version_id`; labels are histories), T-LCD-11 (foreign formats with loss reports), T-LCD-07 (additive capabilities tri-state, negotiated, never intersected), T-LCD-05 (sunsets are dated; a plugin's conditioned rules carry debt records via its variants), T-LCD-06 (no manifest field references the Hosting ABI), T-LCD-02 (`summary` and descriptions are `Text` ≤ `external`), T-LCD-12 (the manifest is data; nothing requires a host-language object). Not applicable: T-LCD-01/-03/-04/-08/-09/-13/-14/-15 (no model-facing surface; T-LCD-08/-14 are satisfied at bind, ADR-0181). **ADR-0024 rung:** manifest schema validation, the compatibility gate and the lowering of `requests` are MUST-code; manifests, `ContractRef`s, `ContractVersionPolicy` and requests are MUST-data.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** manifests as inventories (S-113 `pi-manifest.ts`; S-119 `packages/cli/src/config/extension.ts` L24–50, `packages/core/src/config/config.ts` L396–448; S-107 `codex-rs/plugin/src/manifest.rs` L8–57, `core-plugins/src/manifest.rs` L1–120; S-184; S-112 `plugins/mod.rs` L18–60 — five independent code bases, Tier B); pre-load compatibility gate and its inconsistency (S-111 `packages/opencode/src/plugin/loader.ts` L86–135, `plugin/shared.ts` L194–210); deny-by-default resource manifests and hash pins (Extism manifest, S-561; VS Code `engines`/`extensionKind`, S-562 — Tier B, outside the field); requests never grants (ADR-0063 L3; MCP hints rule S-153); unpinned-by-default as the rug-pull surface (WS-H5 F4; CF-330); population trend toward platforms with extension surfaces (S-074/S-166, `provisional (mech)`, corroborated by direct reading).
- **(b) Source-code precedent:** manifest shape — codex `codex-rs/plugin/src/manifest.rs` L8–57 @0735c51 (generic over resource locator; `paths{skills, mcp_servers, apps, hooks}`), gemini `packages/cli/src/config/extension.ts` L24–50 @ed2ac40, pi `packages/coding-agent/src/core/pi-manifest.ts` @400d690; staged resolution with a compatibility stage — opencode `packages/opencode/src/plugin/loader.ts` L15–60, L86–135 @9f8db11; pinned resolution — software-agent-sdk `openhands-sdk/openhands/sdk/plugin/types.py` L118–197 @3fc7b22; foreign-format lowering — goose `crates/goose/src/plugins/mod.rs` L18–60, `plugins/formats/*` @fae91d0. The integrated `requires`/`requests`/`ContractVersionPolicy` design is `no-precedent / novel` as an integration.
- **(c) Disconfirming evidence considered:** (i) no plugin ecosystem versions its hook/contract surface and a contract catalogue will churn — absorbed by the additive-only rule, sunset windows and `hello` negotiation (dossier §5); (ii) deny-by-default resources break the tools people install plugins for (gemini `excludedCommands`; ~93% approvals, S-053) — absorbed by author acceptance at `review` and `host_unconfined` remaining admissible for tool executables under `authority_cap` (ADR-0063), with cost measured (AC-L5-9); (iii) catalogs drift and users want updates (OpenHands deny-lists; daily marketplace refresh, S-313) — absorbed by supersession + re-seal (ADR-0064) and `max_age` at `resolve`; (iv) foreign formats lose fields — declared, never silent (T-LCD-11). None overturns.
- **(d) Conditionality:** model- and task-independent. Assumes WS-J2's record kinds and `contract_range` (proposed, same phase) and ADR-0063's trust legs; assumes the helper enforces `ContainmentPolicy` per process (ADR-0100/0060). Sunset-window defaults are OQ-411. If a future dialect admits in-process third-party code (it must not — CF-141), `requests` lowering would need a second enforcement path.
- **(e) Build-stage assignment:** **C0 / Stage 1** — `PluginManifest/1` schema, `ContractRef`, `ContractVersionPolicy`, `check_compatibility` inside `resolve`, golden manifest corpus (AC-L5-1/-2); **C0 / Stage 2** — `requests` lowered to `Permission` + `ContainmentPolicy` (AC-L5-3) with the variant host; **C1 / Stage 4** — third-party publish/install, foreign import/export (AC-L5-11) with WS-J2/H5; **C2** — organisation-level `ContractVersionPolicy` layers.

## Consequences

- WS-J2 stores plugin manifests as `extension` records of kind `plugin` and their contributions as ordinary records; `resolve` composes `check_compatibility`; `import`/`export` gain the plugin formats above.
- WS-H5's trust legs apply per contribution; `review` renders `requests` beside the canonical exec plan (SEP-1024 shape).
- WS-A5's `instantiate` receives pinned contributions only; `verify_resume` treats a plugin update as a definition edit.
- WS-K4/L6 package the manifest schema with the generated bindings; WS-I3 adds plugin `version_id`s and the negotiated `plugin_abi` version to `extensions[]` (CF-381).
- The evolution service may publish plugins only into `exp/<id>/` at `origin = model` with non-widening `requests` (ADR-0053 D-5).

## Reversibility

**Low** for decisions 1, 2 and 4 (inventory-only, claims-not-grants, pinned-and-superseded — reverting reopens the audited compromise paths and breaks reproducibility) · **medium** for decision 3's policy details (sunset defaults, additive-only rule — policy data amendable by ADR) · **high** for decision 5's format list (adding a foreign format is a registry `import` variant).
