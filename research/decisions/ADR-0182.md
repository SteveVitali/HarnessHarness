# ADR-0182 — The extension DAG as enforceable invariants X1–X6: tier and contract-dependency declarations on every spec item, class record and plugin; contract-only reach; per-tier removability builds; kernel-mediated interaction; and the tier/stage placement of the extensibility mechanism itself

**Status:** ratified
**Owner workstream(s):** WS-L5 (consumers: Phase 5 synthesis / readiness report, `decompose-spec`/`orchestrate-build` hand-off, WS-J2, WS-A5, WS-H1, WS-I5, every Phase 2–4 class owner) · **Phase:** 3 · **Related:** doc 3 §1.3 (core/extension layering; staged build ladder; "every subsystem ships behind a stable contract before its rich variant"), §7.2 #4/#9, §7.3 (Decompose-Readiness Gate: "valid DAG with no cross-extension internal coupling"), ADR-0007 (T-LCD-06 dependency-graph check and removability build), ADR-0017 (`HirDiff.classification`), ADR-0023/0025 (class records; `Rebind`; `validate_assembly` `hosting_edges`), ADR-0035/0053 (no widening; evolution service as threat actor), ADR-0054 (one lattice, two enforcement depths — the pattern for C0 contract / C2 rich variant), ADR-0121 (router as C0 contract with pass-through), ADR-0151 (`ClassRecord`, `substitutable`), ADR-0180/-2; R-2.12.2; risks RK-01 (integration risk of a single full-vision spec)

## Context

Doc 3 §1.3 discharges the integration risk of one full-vision spec by requiring that "Extension tiers (C1–C4) depend only on the Core and on each other along a declared DAG" and that "no extension may reach into another extension's internals except through Core-defined contracts"; §7.3 makes "the build ladder forms a valid DAG with no cross-extension internal coupling" a gate criterion. Phase 0–2 gave the rule two partial checks — T-LCD-06's dependency-graph and removability tests for the hosting tier, and `validate_assembly`'s `hosting_edges = []` — but no general declaration of tier and dependencies on spec items, no definition of "internal", no per-tier build check, and no runtime guarantee. The audit (dossier §4 F4) found that in every in-process plugin architecture an extension *can* reach another's internals (by import, shared process or handed-in manager handles), so the rule cannot be inherited from precedent; the component model states the target property ("a component may not export a memory"; composition = exports satisfying imports) and Logos (S-073, `provisional`) shows a harness whose plugins are processes with state owned by none of them.

## Options considered

1. **Leave the DAG as a diagram in Spec §4 reviewed by humans at the gate.** *Rejected:* §7.3 requires a valid DAG "with no cross-extension internal coupling" — unverifiable without declared edges and a definition of internal.
2. **Enforce only at run time** (process isolation makes reach impossible; no spec/build checks). *Rejected as incomplete:* run-time isolation cannot detect a spec item whose *contract* was defined in a higher tier, and cannot prove removability of a tier — the property `decompose-spec` inherits.
3. **Enforce only at spec time** (tier tags + DAG check; trust implementations). *Rejected as incomplete:* first-party in-process variants could still couple by import; the build ladder needs an executable check.
4. **Declared tier + contract dependencies on every item; contract-only reach by construction; DAG check at the gate; per-tier removability builds on the ladder; kernel-mediated interaction at run time (chosen).**

## Decision

1. **Declarations.** Every Spec §7.2 #5 subsystem section, every `ClassRecord` (WS-J2) and every plugin manifest (ADR-0180) carries `tier ∈ {C0, C1, C2, C3, C4}` and `depends_on: [ContractRef{kind ∈ {class_contract, record_kind, dialect, protocol_binding}, id, version_range}]`. A `ClassRecord`'s tier is the tier that *defines the contract*; a variant's tier may be higher (a C0 `router` contract with a C0 pass-through variant and a C1 rich variant — ADR-0121; a C0 `flow` check with a C2 enforcement depth — ADR-0054).
2. **X1 Contract-only reach.** A dependency is expressible only as a `ContractRef` or a pinned `VersionedRef` to a published registry record. An *internal* is anything not reachable through a `ContractRef`: another variant's implementation, process, files or private records; kernel projections beyond the views a `Permission` covers; Π; the handle table. No manifest field, assembly field or host callback can name an internal (ADR-0180 §1, ADR-0181 §3), so X1 holds by construction for third-party code; for first-party in-process variants it is a build-time lint over the kernel ecosystem's module graph (variants import only the class-contract interfaces and the kernel's public record types).
3. **X2 Tier monotonicity and acyclicity.** A C(n) item's `depends_on` names only contracts whose defining tier is ≤ n, and the graph over items is acyclic. Check: the readiness gate's **spec-DAG check** — generalising T-LCD-06's `hosting_edges = []` to `tier_violations = []` and `cycles = []` — run over all sections, class records and Stage-1–3 plugins; a violation blocks the gate (doc 3 §7.3).
4. **X3 Kernel-mediated interaction.** Two extensions interact only through kernel-visible objects (ledger records, HIR entities, effects, registry records), each observed through the observer's own contract; the variant host's placement rules (ADR-0181 V3) and closed callbacks make direct interaction physically unavailable. Check: isolation and reach conformance (ADR-0181 §7 layers 2 and 4).
5. **X4 Removability per tier.** For every n ∈ {0..3}, the build ladder must produce a working system with tiers > n absent, and the tier-n acceptance suite must be unchanged. Every C0 class contract ships its trivial Stage-1 variant in C0 (doc 3 §1.3 rule 3), so removing a rich variant never removes the slot. Check: an `orchestrate-build` stage-gate job per tier ("build with higher tiers absent"), recorded in the readiness report.
6. **X5 Substitution without ripple.** Replacing a variant of class C with any `substitutable` variant (WS-J2) changes no other item's `depends_on`; the `HirDiff` after a `Rebind` touches only that slot (ADR-0025 AC-6 shape). A class-contract change is a new `contract_version` under `ContractVersionPolicy` (ADR-0180), never an in-place edit.
7. **X6 Authority never flows up the DAG.** An extension's `Permission` is issued at `seal` by the principal and attenuates downward (ADR-0035/0053); extension-contributed `HarnessRule`s carry `authority_cap` narrowing only (ADR-0024); the evolution service (C4) edits only `HirDiff`s with `authority_delta ∈ {none, narrowing}` (ADR-0053 D-5). Check: `validate_assembly` (`AuthorityViolation`), `HirDiff.classification`, the guard property test.
8. **Tier/stage placement of the extensibility mechanism** (feeds Spec §9): `PluginManifest/1`, `ContractRef`, tier/`depends_on` declarations, the spec-DAG check, `ContractVersionPolicy` — **C0/Stage 1**; the variant host with `subprocess_confined`, host callbacks, `GuardVerdict`, invocation scopes, protocol + isolation conformance — **C0/Stage 2**; conformance kit, reach conformance, boundary-overhead metrics, OQ-075 measurement — **C0/Stage 3**; third-party publish/install/import/export, attestation-gated admission, `remote`/`container` placements — **C1/Stage 4** (with WS-J2/H5/B5); `component_model` placement, cross-plugin flow checks — **C2**; evolution-service plugins in `exp/` — **C4/Stage 6**. The mechanism itself obeys X4: with C1–C4 absent, Stage 1–3 still binds first-party variants and runs the conformance kit.

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-06 (its dependency-graph and removability tests are the n = hosting instance of X2/X4; no IR edge to the Hosting ABI), T-LCD-12 (dependencies are contract references, never inheritance or imports), T-LCD-10 (dependencies pin `version_id`s; names are histories), T-LCD-05 (a tier violation accepted temporarily must carry an assumption-debt record with a removal test — the only admissible exception), T-LCD-14 (the removability build is budget-neutral: it removes code, not arms). Not applicable: T-LCD-01/-02/-03/-04/-07/-08/-09/-11/-13/-15. **ADR-0024 rung:** the DAG check, the module-graph lint and the removability job are MUST-code (tooling); tier and `depends_on` declarations are MUST-data.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** in-process extensions reach internals by construction — goose `PlatformExtensionContext` (S-112), Pi `ExtensionAPI` and `VIRTUAL_MODULES` (S-113), opencode `PluginInput` (S-111), gemini `trajectoryProviderModule` (S-119) — Tier B, four systems; contract-only reach as a design property — Component Model (S-560, "a component may not export a memory"; exports satisfy imports); process-per-plugin with state owned by no process — Logos (S-073, `provisional`, mechanism only); removability as an existing gate test — ADR-0007 T-LCD-06; C0 contract / higher-tier rich variant already practised — ADR-0054, ADR-0121, ADR-0075 (fallback ladder to the C0 variant); doc 2 §11 staged build sequence and §1.3's three rules.
- **(b) Source-code precedent:** dependency direction enforced by package/module boundaries — codex `codex-rs/*` crate layout with `app-server-protocol/src/export.rs` as the single schema source (S-107 @0735c51, via ADR-0050); goose `crates/*` split (S-112 @fae91d0); omnigent `_validate_community_contribution` refusing overrides of core keys (S-118 `omnigent/harness_plugins.py` L932–990 @6a069da, via WS-J2); tier-removability builds and a spec-level DAG check over contract references are `no-precedent / novel` (no audited project builds with tiers absent; VS Code's extension host and the component model enforce reach, not tiers).
- **(c) Disconfirming evidence considered:** (i) real dependencies cross tiers (the C0 kernel calls the C2 IFC monitor and the C1 router) — resolved by the direction-of-knowledge reading: the kernel invokes higher-tier *variants* only through C0-defined contracts with C0 trivial variants (ADR-0054/0121), which is exactly what X4 tests; a genuine upward edge is a spec defect the gate should find; (ii) per-tier builds are expensive ceremony — four extra build jobs at stage gates on a system whose tiers are already the decomposition unit; the cost is bounded and the property is the one `decompose-spec` inherits (doc 3 §7.4); (iii) first-party in-process code cannot be physically prevented from importing internals — accepted; the module-graph lint is the check, and the number of in-process first-party variants is small by ADR-0050 D1; (iv) the component model would prove X1/X3 rather than police them — deferred placement (OQ-410). None overturns.
- **(d) Conditionality:** independent of model and task. Assumes WS-J2's `ClassRecord` (proposed, same phase) carries `contract_version` and that Phase 5 authors `tier`/`depends_on` on every §7.2 #5 section (a synthesis obligation); assumes the build ladder retains doc 2 §11's stage shape. If a tier boundary is re-cut at Phase 5 (e.g. hosting C2 → C1), declarations change, the invariants do not.
- **(e) Build-stage assignment:** **C0 / Stage 1** — declarations on the Stage-1 classes and plugins, the spec-DAG check as a readiness-report tool, the module-graph lint; **every stage gate** — the tier-n removability build (X4) from Stage 2 onward; **C0 / Stage 2–3** — X3 through the variant host's isolation and reach suites; **Phase 5** — the spec-DAG check over the assembled spec is a §7.3 gate criterion.

## Consequences

- Phase 5 synthesis must stamp `tier` and `depends_on` on every subsystem section and run the spec-DAG check before the Decompose-Readiness Gate; `READINESS_REPORT.md` gains rows `tier_violations`, `cycles`, `removability(n)` for n ∈ {0..3}.
- `decompose-spec` inherits `depends_on` edges directly as ticket ordering; `orchestrate-build` gains a per-tier removal job at stage boundaries.
- WS-J2's `ClassRecord` gains `tier`; `substitutable` is the X5 test; WS-A5's `validate_assembly` generalises `hosting_edges` to `tier_violations`.
- Any temporary upward edge accepted during the build carries an assumption-debt record with a removal test (T-LCD-05) and appears in the readiness report.
- WS-I5's evolution service is bound by X6 and publishes only into `exp/`.

## Reversibility

**Low** for X1/X3/X6 (they restate ratified authority and isolation rules; reverting reopens CF-141 and the S-103/S-104 vector) · **medium** for X2/X4 as gate criteria (the checks are tooling; relaxing them is an ADR that weakens §7.3 and RK-01's mitigation) · **high** for the tier/stage table in decision 8 (a Phase 5 re-cut moves rows, not invariants).
