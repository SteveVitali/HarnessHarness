# ADR-0148 — The assembly validation contract: the `AssemblyDiagnostic` record, a closed per-dialect diagnostic code taxonomy across every pipeline stage, severity and completeness rules, `n/a` stage outcomes, and one fixture per code as the acceptance rule

**Status:** ratified
**Owner workstream(s):** WS-J1 (consumers: WS-J3, WS-K1, WS-K4, WS-I5, WS-J6, WS-L5; rule owners cited per code: WS-A3, WS-A4, WS-A5, WS-C3, WS-H3, WS-H5, WS-L3) · **Phase:** 3 · **Related:** ADR-0007 (T-LCD-02/-05/-06/-08/-10/-12/-14/-15), ADR-0015 (closed sums per dialect; error set), ADR-0016 (kernel invariants), ADR-0019 (`LinkError`, `PlanError`, `UnexpressibleSurface`), ADR-0023, ADR-0024 (`AuthorityViolation`, merge policy), ADR-0025 (seven-stage complete report; `Diagnostic`), ADR-0037 (`Revoked`), ADR-0045 (`n/a{reason}`), ADR-0057, ADR-0063/0064 (trust failures), ADR-0126 (expiry); CF-323; OQ-075, OQ-078, OQ-351; R-2.10.1

## Context

ADR-0025 fixed that `validate_assembly` runs seven stages, reports every diagnostic with a path and a source layer, and never silently corrects. The brief's acceptance criterion — *invalid assemblies rejected with reasons* — is not yet testable: the ratified ADRs name typed errors per stage (`ParseError`, `UnresolvedRef`, `AuthorityViolation`, the ADR-0016 kernel set, `LinkError`, `PlanError`, `BindFailure`, `Incompatible`) but no shared record, no severity rule, no rule for stages that do not apply to a participant class, and no way for a sweep engine to assert "point P was rejected for R at path Q". The audit shows the state of practice: opencode accumulates `Diagnostic{kind ∈ {invalid, unsupported, conflict}, path, message}` and throws one `InvalidError{issues[]}` for hard incompatibilities (`config/v2-compat.ts` L10–18, L100–116); goose names two error classes for undeclared/unused parameters in one message (`validate_recipe.rs` L156–181); OpenHands returns an `AgentProfileDiagnostics` object listing every dangling reference and secret channel (`resolver.py` L64–100). None uses stable codes across stages; all identify a diagnostic by its message string. Kubernetes server-side apply names a *conflict* when two managers claim one field (S-500) — the one compose-time condition ADR-0024 does not name.

## Options considered

1. **Per-stage error bags with message strings** (state of practice). *Rejected:* untestable across hundreds of enumerated points; messages drift; no severity or `n/a` semantics.
2. **An open code registry (any component may mint codes).** *Rejected:* the ADR-0015 escape-hatch signature — unknown codes fail late; consumers cannot be exhaustive; invites a catch-all.
3. **Fail-fast first error with a code.** *Rejected:* ADR-0025 requires a complete report; a sweep must see every path at once.
4. **A closed per-dialect code list over a fixed `AssemblyDiagnostic` record, severity/completeness/`n/a` rules, `LayerConflict` added, no catch-all, and one fixture per code (chosen).**

## Decision

1. **Record.** `AssemblyDiagnostic{code, class ∈ {syntax, dialect, reference, class_conformance, parameter_space, constraint, kernel_invariant, authority, budget, profile_compat, lcd, locality, trust, resume, internal}, severity ∈ {error, warning, info}, path (JSON pointer), source_layer?: LayerProvenance, subject{node_id?, slot?, ref?, param?}, stage ∈ {desugar, compose, resolve, validate:1..7, link, lower, instantiate, resume}, detail: Text{owner = kernel}, remedy ∈ {edit_path, choose_variant, pin_version, narrow_cap, add_debt_record, add_param, remove_param, declare_capability, human_attestation, none}, owner_adr}`. The `code` is the identity of a diagnostic; `detail` is never matched on.
2. **Code list (HIR/1)** as tabulated in the dossier §6.3: `C-LOAD-1…4`, `C-COMP-1…4`, `C-REF-1…6`, `C-CLASS-1…6`, `C-PARAM-1…5`, `C-CONS-1`, `C-KERN-*` (the ADR-0016/0033 error set mirrored one-to-one), `C-PROF-1…3`, `C-LCD-1…4`, `C-LOC-1`, `C-TRUST-1`, `C-SEC-1`, `C-LINK-1`, `C-PLAN-1`, `C-RES-1`, `C-INT-1`. Each row records the stage, the condition, the severity and the owning ADR; this ADR *owns* only `C-COMP-3 LayerConflict` (two layers of equal precedence setting one path to different values — never silent last-wins), `C-REF-5 DenyListNoop` (info), `C-REF-6 SnapshotDrift` (ADR-0149), `C-PARAM-5 DefaultedBudgetRelevant` (warning), `C-CLASS-6 SlotsOnHosted` (ADR-0150) and `C-INT-1 UncodedRejection`; every other code is a ratified rule given a stable name.
3. **Rules.** V-1 every rejection returned to any caller is an `AssemblyDiagnostic` with a registered code; a string-only rejection is `C-INT-1` and is a defect. V-2 `path` is mandatory and resolves in the document the stage saw; `source_layer` is mandatory whenever `layers[]` attributes the path. V-3 `status = error ⇔ ∃ severity = error`; warnings and info never block; a report is complete (all stages run, ADR-0025). V-4 `n/a{reason ∈ {class, observability, not_run}}` is a first-class stage outcome (ADR-0045 vocabulary): for `AgentProcess.hosted` stages 2, 6 and 7-opacity return `n/a{class}`, never pass, never 0 (T-LCD-15). V-5 the list is closed per dialect: adding a code is a dialect bump with a fixture; removing one is a supersession recorded by its owner; there is no `Other`. V-6 the schema the `C-LOAD-*` stage validates against is the derived `hir/1` schema artifact, never hand-maintained (ADR-0025 decision 3). V-7 defaulting never adds a slot (`C-CLASS-2 SlotUnbound` for an empty `exactly-one` slot) and every defaulted path is reported (ADR-0147 S-8).
4. **Acceptance.** One invalid fixture per code, rejected with exactly that code, a resolving path and the correct `source_layer`; a planted multi-error fixture returns every diagnostic; a fuzzed corpus over valid fixtures yields no `C-INT-1` (dossier AC-J1-3/-4). The corpus is a Stage-3 gate for the sweep engine (it runs `validate_batch` before spending budget).

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: typed diagnostics with kind/path and hard rejection with an issues list (S-111 `config/v2-compat.ts` L10–18, L100–116); complete parameter reports naming both missing and unnecessary definitions (S-112 `recipe/validate_recipe.rs` L156–181); side-effect-free diagnostics objects with resolved/dangling partitions (S-110 `profiles/resolver.py` L64–100); `extra="forbid"` refusing cross-variant fields rather than dropping them (S-110 `agent_profile.py` L67–76); schema migrations refusing newer-than-supported documents (S-110 L318–365); conflicts as first-class outcomes when two managers set one field, with explicit force to override (S-500); validation errors, never silent correction (S-186); constraint errors naming the `requirement_source` (S-107 via ADR-0025); closed sums per dialect with growth by bump, never `ext` (ADR-0015); `n/a` never 0 (ADR-0045, T-LCD-15).
- (b) Source-code precedent: `packages/opencode/src/config/v2-compat.ts` L10–18, L100–116 (S-111 @9f8db11); `crates/goose/src/recipe/validate_recipe.rs` L113–203 and `recipe/build_recipe/mod.rs` L11–17 (S-112 @fae91d0); `openhands-sdk/openhands/sdk/profiles/resolver.py` L50–100 and `profiles/agent_profile.py` L67–76, L318–365 (S-110 @3fc7b22). A closed, cross-stage, per-dialect code taxonomy with a no-catch-all rule and fixture-per-code acceptance is `no-precedent / novel`; each component (typed kinds, paths, complete reports, conflicts) is precedented.
- (c) Disconfirming evidence considered: (i) closed code lists ossify and invite `Other` — answered by V-5 (dialect bump with fixture) and the `C-INT-1` defect rule that makes gaps visible; (ii) `LayerConflict` may be too strict where products intend last-wins (opencode plugins dedupe by identity keeping the winning source, `config.ts` L355–362) — answered: last-wins remains available as a *declared* per-field merge policy (`replace`, ADR-0024 (5)); the conflict fires only when the schema declares no order between equal-precedence layers, which is exactly the case that hides "who set it"; (iii) complete reports cost more than fail-fast — accepted per ADR-0025 (small documents; hundreds of points). None overturns.
- (d) Conditionality: independent of model tier and task class; the initial code list assumes HIR/1 and the Phase 1/2 error sets; `C-PROF-3` is conditional on OQ-078; `C-LOC-1` thresholds on OQ-075; `C-LCD-1` assumes a tokenizer or declared proxy per profile (ADR-0015 (9)).
- (e) Build-stage assignment: **C1 / Stage 3** (record, code list, V-1…V-7, fixture corpus, `validate_batch` gate); **C1 / Stage 5** (`C-PROF-2` propagation at plan time; `C-PROF-3`); **C2 / Stage 4** (hosted `n/a` rows exercised with WS-J6). The `C-KERN-*` mirror is C0/Stage 1 by ownership (ADR-0016) and only *named* here.

**T-LCD statement (ADR-0007 decision 5).** Satisfies: T-LCD-15 (`n/a{class}` stage outcomes; never 0), T-LCD-06 (`C-LCD-2 HostingEdge`; `C-CLASS-6`), T-LCD-10 (`C-LCD-3`), T-LCD-05 (`C-LCD-4`, `C-KERN ConditionedRuleIncomplete`), T-LCD-08 (`C-CLASS-5`), T-LCD-12 (`C-CLASS-4`; the validator is a pure operation), T-LCD-14 (`C-COMP-1`, `C-PARAM-5`), T-LCD-02 (`C-KERN TextAboveExternal`, opacity or `n/a`). Does not address T-LCD-03/-04/-11/-13 (executable). **ADR-0024 rung:** the taxonomy and validator are MUST-code; fixtures are test data; no MUST-data surface is added.

## Consequences

- Spec §5 "failure modes" for the assembly subsystem *is* the code table; every later assembly-adjacent dossier that adds a check registers a code with a fixture rather than a message.
- WS-K1/K4 render diagnostics by `code` and `remedy` (localisable `detail`); WS-J3 refuses to spend on any point whose report has `status = error` and records `C-PARAM-5` warnings beside the arm's `MatchSpec`; WS-I5 treats a candidate `HirDiff` whose result validates with errors as a rejected candidate with the codes as its rationale.
- WS-A3/A4/A5/H5/L5 keep ownership of the rules behind their codes; this ADR only names them.

## Reversibility

**High.** Codes are names over ratified rules; the record is derivable from existing error types; changing it regenerates fixtures, not stored definitions. Removing the no-catch-all rule would be the only costly reversal (it silently re-admits untyped rejection) and needs a superseding ADR.
