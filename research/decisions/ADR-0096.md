# ADR-0096 — Boundary placement for the protocol edges: MCP is the sole standardized tool-supply channel, ACP is the session boundary, A2A is the delegation edge; orchestration, safety, memory, budgets and provenance stay kernel-side

**Status:** **ratified** (Phase 2 synthesis, 2026-09-10)
**Owner workstream(s):** WS-E4 (consumers: WS-E1, WS-E3, WS-E5, WS-K3, WS-K4, WS-J6, WS-F3, WS-H1, WS-H5) · **Phase:** 2 · **Related:** ADR-0005 (interoperate; act as a participant), ADR-0006 (N5 no new protocol), ADR-0007 (T-LCD-06/-11/-12/-15), ADR-0013 (participant descriptor; total ABI projection), ADR-0018 (`OpaqueProcess`), ADR-0021 (protocol targets — consumed), ADR-0031 (`projected(declared)` raises only), ADR-0033/0034/0035, ADR-0050 §8; CF-023, CF-027, CF-045, CF-051; CF-209, CF-210; OQ-004, OQ-038, OQ-247, OQ-248; R-2.5.4, R-2.11.3, R-2.11.4, R-2.10.6

## Context

ADR-0021 fixed *how* HIR lowers to MCP/ACP/A2A documents and which tier each target has. It did not fix *where each protocol attaches* to the architecture — which IR entity, ledger seam and component owns each protocol concept — nor whether more than one protocol supplies tools. Reading the three specifications at pinned commits and eight implementations shows: ACP v2 removed its own client-side `fs/*` and `terminal/*` methods and routes client-supplied tools to MCP servers passed in `session/new.mcpServers` (S-035 `docs/protocol/v2/migration.mdx` L611–616, L741); Omnigent already injects Lab tools into hosted ACP v1 agents through an MCP relay in `mcpServers` (S-118 `inner/_acp_omnigent_mcp.py`); A2A has no tool concept and assigns tools to MCP in its own documentation (S-180 `docs/topics/a2a-and-mcp.md`); 8/11 audited harnesses consume tools only through MCP clients (S-166). No protocol carries decision points, authority, validity, effect classes or budget enforcement; every audited host makes the permission decision on its own side of the edge, with the exceptions (OpenHands auto-approve, gemini-cli location-trust short-circuit) being exactly the failure modes ADR-0035 and WS-H5 L1 forbid.

## Options considered

1. **Per-protocol tool definitions** (ACP `_`-methods, A2A extended skills and MCP each define callable tools; the registry has three lifters). *Rejected:* vendor `_`-methods have no interop; A2A extended skills are RPC methods without schemas; ACP's own migration routes tools to MCP; three lifters triple the surface for T-LCD-11 round trips.
2. **A HarnessHarness session protocol** with its own tool, permission and budget verbs, bridged to MCP/ACP/A2A. *Rejected:* non-goal N5 (ADR-0006); the WS-L1 §6.5 internal boundary already exists for internal seams and CF-023 fixed that the external edge shares its *shape*, not a new wire protocol.
3. **Protocol types as IR fields** (e.g. `ToolCapability.mcp_annotations`, `AgentProcess.acp_capabilities`). *Rejected:* T-LCD-06 failure signature; ties C0 to protocol revisions that change yearly.
4. **Chosen:** one tool-supply channel (MCP), ACP as the session boundary, A2A as the delegation edge, every non-covered concern kernel-side, protocol schemas as inputs to lowering/lifting/transport only, with fixed projection tables from IR sums to protocol enums.

## Decision

1. **Tool supply.** MCP is the only standardized channel through which tools cross a process boundary. Inbound: foreign MCP servers become `ExtensionRecord{kind: mcp_server}` (WS-H5) whose lifted surface yields `ToolCapability` nodes with `origin = tool(server_ref)`, `authority = unverified`, `effects = unknown` until the author declares them at `seal`; execution goes through the reference monitor and WS-E5. Outbound: the compiler's MCP tool-surface document (ADR-0021) is what WS-K3 serves and what an ACP `mcpServers[]` entry or a hosted participant's `OpaqueProcess.supplies.tools` references. The compiler emits one tool-document kind; the registry has one foreign-tool lifter.
2. **Session boundary.** ACP is the run-envelope seam. Outbound, a native harness is exposed as an ACP agent by rendering the total projection `proj_ABI(native ledger)` into `session/update` (ADR-0005/0013); inbound, a foreign ACP agent is `AgentProcess.hosted = OpaqueProcess{hosting_mechanism: session_abi}` (ADR-0018). The WS-L1 §6.5 internal boundary and the ACP edge are distinct bindings with the same verb shape (CF-023): the internal one carries IR-typed, byte-identical ledger events and rejects unknown fields; the ACP edge carries lowered events, preserves unknowns, and ships a `LoweringLossReport{granularity_ceiling: configuration}` (CF-209).
3. **Delegation edge.** An A2A peer is an `OpaqueProcess{hosting_mechanism: session_abi}` with a `ProtocolBinding{protocol: a2a}`, reached by a `delegated-to` edge at `product` granularity; an A2A task is a child run (`control.subagent.spawned{child_run_id}`, `delegated-to` with attenuated `Permission` and contained `Budget`); only kernel-observable budget dimensions are hard (wall-clock, priced spend, network calls); token usage is `reported` or `n/a`; outputs re-enter at `≤ delegate`. HarnessHarness as an A2A server is the C2 lowering of the run envelope to `TaskState` (table in WS-E4 §6.2).
4. **Kernel-side by construction.** Orchestration (control boundary β; ACP `plan_update` is observational), safety (the reference monitor decides on the kernel side of every edge; `ToolAnnotations`, ACP `PermissionOptionKind`, A2A `required`, OAuth scopes, `clientInfo/serverInfo` are `declared_claims` that may only raise risk per ADR-0031), memory (no protocol carries validity/authority; ACP `compaction_update` is observational), budgets (only ACP `usage_update` reports; nothing enforces), provenance (carried only in `_meta`/`AgentExtension`; `unverified` from foreign peers, ADR-0021 decision 3).
5. **Dependency direction and projections.** No HIR entity, ledger event class or component-class contract references a protocol type; protocol schemas are inputs to `lower_target`, `lift`, `negotiate`, `render_session` and the transports only. `ToolKind`, `ToolCallStatus`, `StopReason`, `TaskState`, `PermissionOptionKind` and `ToolAnnotations` are fixed, versioned **projections** of `EffectDomain`, the tool/effect lifecycle, ledger `stop_reason`, run outcome classes, the kernel decision and `EffectAttributes`, living in the compiler's target module and versioned with the spec pin; each projection declares its loss class.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: ACP v2 removes client tool execution and routes tool supply to MCP (S-035 migration guide; `schema/v2/schema.json` method union has no `fs/*`/`terminal/*`); MCP-inside-ACP tool supply in production hosting (S-118 `_acp_omnigent_mcp.py`); A2A's tool-less data model and its own MCP-complementarity statement (S-180 `a2a.proto` L143–470; `docs/topics/a2a-and-mcp.md`); adoption direction MCP 8/11, ACP 6/11 (S-166, `provisional (mech)`, ordering only); hints are untrusted by specification (S-153 `schema.ts` L1912–1920; `server/tools.mdx` L305); hosts decide permissions on their own side (S-118 `acp_executor.py` L775–950; S-107 `mcp_tool_call.rs` L204–222) and the counter-examples are the failure modes (S-110 `acp_agent.py` L1579–1596 auto-approve; S-119 `mcp-tool.ts` L207–216 location trust).
- (b) Source-code precedent: omnigent `omnigent/inner/_acp_omnigent_mcp.py` L1–60 @6a069da (MCP as the tool channel inside an ACP session); goose `crates/goose/src/acp/server.rs` L503–560 (`mcp_server_to_extension_config`: ACP `mcpServers` → the agent's MCP extension manager) @fae91d0; software-agent-sdk `openhands-sdk/openhands/sdk/agent/acp_agent.py` L1404–1530 @3fc7b22 (ACP updates → native events; hosting); gemini-cli `packages/a2a-server/src/agent/task.ts` L279–325, L560–580 @ed2ac40 (run envelope → `TaskState`, confirmations → `input-required`); codex `codex-rs/codex-mcp/src/resource_origin.rs` @0735c51 (per-item origin for tool-supplied content). The single-channel invariant and the "projections, never fields" rule as an integrated contract are `no-precedent / novel`.
- (c) Disconfirming evidence considered: (i) provider tool APIs and vendor `_`-methods are additional tool paths — answered: provider APIs are model-facing surfaces (ADR-0021 decision 5), vendor methods have no interop; the decision is scoped to standardized cross-process supply and is cheap to widen by ADR. (ii) ACP is alpha and the internal boundary might as well *be* ACP — answered: the internal boundary needs byte-identical ledger events and strict unknown rejection (WS-L1 §6.5 I2/I4) which ACP forbids; sharing the shape but not the binding is CF-023's ruling. (iii) A2A may grow tool/permission concepts — answered: the mapping is a projection table versioned with the pin; a richer A2A shrinks the loss list without moving the edge. None overturns.
- (d) Conditionality: independent of model tier; assumes MCP 2026-07-28, ACP v2 and A2A 1.0 remain the served majors through Stage 4 (pins in the derivation key; a major bump is a recompile plus loss-report diff); assumes WS-E1 admits lifted `ToolCapability` with `effects = unknown` (CF-210); assumes the reference monitor's Π exists at C0 (ADR-0035 monitor set).
- (e) Build-stage assignment: **C0 / Stage 3** — decisions 1 and 5 (MCP client/server pair, projection tables, dependency-direction check); **C1 / Stage 4** — decision 2 outbound (ACP agent artefact + transport); **C2 / Stage 4–5** — decision 2 inbound (hosting adapter) and decision 3 (A2A).

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-04 (MCP target executed end-to-end), T-LCD-06 (decision 5; AC-E4-8 DAG check), T-LCD-10 (identity travels in `_meta`, names never parsed), T-LCD-11 (every projection declares its loss class), T-LCD-12 (edge operations are out-of-process records-in/records-out), T-LCD-15 (granularity ceilings `configuration` for ACP, `product` for A2A). Does not by itself satisfy T-LCD-03 or T-LCD-13 (whole-harness round trip and compliance events are ADR-0019/ADR-0026 obligations; edges carry `delivery_id` only as `hint_only`). **ADR-0024 rung:** transports, projections and monitor interposition are MUST-code; target documents and edge policy rows are MUST-data with `authority_cap`.

## Consequences

- WS-E1 needs one foreign lifter (MCP) and a registry state for `effects = unknown` tools; WS-E3's discovery/deferred loading operates on the compiled catalogue client-side (CF-206).
- WS-K3 serves `lower_target(…, mcp)` statelessly; its Lab operations are ordinary tools with server-minted run handles.
- WS-K4/WS-J6 adopt the ACP session boundary and the WS-E4 §6.5 verb proposal; WS-F3 gains `delegate_task` over A2A at C2.
- WS-H1 evaluates every edge proposal on capability parameters through `SurfaceArgMap` (ADR-0022) and ignores wire claims; WS-H5's `ExtensionRecord{kind: mcp_server}` is the only admission path for foreign tools.
- ADR-0021 stands; one clause (decision 5, `listChanged`) is amended by ADR-0097.

## Reversibility

**High** for adding a second tool-supply channel (a new lifter + loss report by ADR); **medium** for moving A2A from delegation to session (re-labels stored child-run rows); **low** for "protocol types never in the IR" (shared with ADR-0016/0021 and T-LCD-06).
