# ADR-0024 — The code-vs-config boundary: what must be code, what must be data, the migration ladder (prose → `Text` leaf → parameter/entity → variant → Core), the pointer rule for executables, and monotone authority layering with per-field merge policy

**Status:** **ratified** (Phase 1 synthesis, 2026-09-10)
**Owner workstream(s):** WS-A5 (consumers: WS-A3, WS-A4, WS-H1, WS-H5, WS-L3, WS-L5, WS-I2, WS-I5, WS-I6, WS-I7, WS-J3, WS-K1, WS-K4) · **Phase:** 1 · **Related:** ADR-0002 (governance (iii); evidence standard), ADR-0006 (N1, N12), ADR-0007 (T-LCD-01/-02/-05/-14), ADR-0008, ADR-0011; ADR-0023 (grammar), ADR-0025 (`compose`, `validate_assembly`); ADR-0015 (`Text`/`CompiledPayload`; `ext` never decides authority/budget/validity), ADR-0016 (Budget monotone containment; `delegated-to` attenuation), ADR-0017 (`HirDiff.classification.authority_delta`), ADR-0019 (`PlanError`; closed-world rule), ADR-0020 (assumption-debt record on every profile rule); CF-055, CF-006, CF-009; OQ-036, OQ-076, OQ-077; R-2.1.4, R-2.12.2

## Context

Doc 2 §4 states the design principle that hard invariants live in deterministic software, §7 records that mature harnesses moved policy out of prose into structured configuration, and §11 asks that the harness be exposed as data an optimizer can edit safely. ADR-0002 fixes the governance side: the security kernel, credential mediation, egress policy, sandbox boundaries, extension trust and audit are *outside* the editable policy surface, and an evolution service may narrow its own authority but never widen it. T-LCD-02 requires an opacity ratio per definition and individually ablatable text leaves; T-LCD-05 requires every conditioned rule to expire; T-LCD-14 forbids un-budgeted comparisons. What Phase 0 did not fix is the *rule* that places a given behaviour in Core code, in a variant, in a typed parameter, or in a text leaf — nor the reverse path by which scaffolding is retired — nor how layered configuration sources (organisation, user, project, experiment) combine in an instrument whose results are keyed by configuration identity.

The audit located the boundary in source (dossier F3, F6). In every system the loop, tool executors, provider clients, compaction algorithms, permission evaluation and persistence are code, while *which* of them is active, with what parameters, under which policy, for which model, is data (OpenHands `CondenserBase.condense()` versus `LLMSummarizingCondenserSettings{max_size, keep_first, max_tokens}`; goose `add_extension` dispatching on a config tag to a client factory). Three hybrids sit on the line: prose with typed frontmatter (opencode `agent/*.md`, Claude agents, AGENTS.md imports); policy DSLs and hook commands (Codex "Execution Policy (Starlark, not TOML)", S-166 §10.2; Claude/Pi/opencode hooks); and in-process versus out-of-process components under one tag set. One counter-example was found in code where data belongs: opencode's `ToolRegistry.tools()` selects `apply_patch` versus `edit`/`write` by a model-id string match (`usePatch`) — the per-model branch a Model Profile relocates into data (T-LCD-01). Layering is the norm and authority layers are monotone: Codex materialises every layer as `ConfigLayer{name, version, config, disabled_reason}` with numeric precedence and enforces managed requirements through `Constrained<T>` values whose errors name the `requirement_source`; Claude Code merges list keys across scopes but honours a *stricter* lower-scope value for security keys; opencode records `plugin_origins{spec, source, scope}`; Pi gates project settings on trust.

## Options considered

1. **Everything configurable is data, including executable policy bodies** (hooks, templates, rule programs inline in the definition). *Rejected:* re-opens the "load arbitrary code" path DSPy and AutoGen flag as dangerous; an inline body has no declared interface and cannot be content-addressed as a variant; contradicts ADR-0002 (iii).
2. **Everything behavioural is code; the definition only names a top-level "agent class"** (subclass-per-harness, as in early OpenHands agents). *Rejected:* nothing is ablatable or diffable below the whole harness; fails T-LCD-02/-10 and doc 2 §11's editability requirement.
3. **A fixed two-level split (Core code vs one flat configuration file) with generic deep-merge of layers.** *Rejected:* deep-merge cannot express "stricter wins", "lists merge", or "taken whole from the winning layer", all of which the audited products needed; it lets an experiment layer widen a security cap by accident; no provenance survives the merge, so attribution cannot name the layer that set a field.
4. **Explicit MUST-code / MUST-data lists, a ladder with promotion and retirement criteria for everything in between, a pointer rule for executables, and layered composition with per-field merge policy and monotone authority caps recorded as provenance (chosen).**

## Decision

1. **MUST be code** (Core or a variant implementation; never on the optimizer's editable surface): the loader/validator/resolver/assembler of definitions; the event ledger and effect model (WS-B1/B2); the reference monitor, credential mediation, egress and sandbox boundaries, extension trust and audit (ADR-0002 iii); budget enforcement; component-class *contracts* and variant *algorithms* (the `CompiledPayload` bodies behind Core contracts, ADR-0015); the interpreter of any admitted policy leaf. Rationale: doc 2 §4 (hard invariants in deterministic software).
2. **MUST be data** (in the Harness Definition, ADR-0023): which variant fills each slot and whether it is `enabled`; every parameter value and the declared parameter space; every reference to profile constraints, entities, environments and budgets; permission/effect/validator *declarations*; prompts and instructions as typed `Text` leaves; tool/skill/procedure inventories; conditioned rules with their assumption-debt records; experiment overrides. Rationale: only data can be diffed structurally, content-addressed, swept, ablated, versioned, attributed and edited under governance (doc 2 §11; T-LCD-02/-10; ADR-0002).
3. **The migration ladder** governs everything in between. A behaviour moves *up* only when it earns it and *down* when it stops earning it: `prose (opaque) → typed Text leaf with provenance/owner/authority → typed parameter or entity → registered variant → Core invariant (by ADR only)`. Promotion criteria: a text rule becomes a **parameter** when it can be stated as a value in a typed domain ("keep the last 20k tokens" → `keep_recent_tokens: token_count`); a parameterised behaviour becomes a **variant** when it is an algorithm with its own failure modes and contract tests; a variant becomes **Core** only when it is a hard invariant every harness must satisfy, and only by ADR. Retirement: a conditioned rule whose assumption-debt record expires is removed by the Lab's "retire rule R" recipe (T-LCD-05); a Core invariant is never demoted without an ADR. Every promotion is a Lab experiment (paired runs, matched budget — ADR-0002 evidence standard) and lowers the definition's **opacity ratio** (T-LCD-02, OQ-036), so S-074's migration finding becomes a per-definition measurement rather than a slogan. Spec §8 documents the ladder with a worked example (a reminder rule migrating prose → `Text` leaf → parameter → conditioned rule with expiry).
4. **The pointer rule for hybrids.** Hooks, skills, extensions and plugins are data records that name executables **only by versioned identity** (package, path, module, command → content address + trust record at `resolve`, WS-L5/H5) or as a WS-A3 `CompiledPayload` leaf with a declared interface; they execute only through a Core-declared effect class and permission. Interpreted policy leaves (templates with variables, exec-policy rule languages, JSON-schema constraint leaves) are admissible only as `TypedValue` leaves of a declared kind whose interpreter is a Core component with no ambient authority; at C0 only `Text` and `CompiledPayload` are admitted and interpreted leaves are deferred pending OQ-077. A per-model branch in code (`if model == X`) is a defect: it is relocated into a profile-owned field (T-LCD-01) or, if it is behavioural, into a variant whose `capability_declaration` names the condition.
5. **Layered composition with per-field merge policy.** A definition may be authored as layers `{fragment, provenance: LayerProvenance{source_kind ∈ {packaged-default, organisation, user, project, experiment, session}, id, version, precedence}}`; `compose` (ADR-0025) merges them by a **merge policy declared in the schema per field** — `replace | append-set | stricter-wins | forbidden-below(precedence)` — never by generic deep-merge; the composed document carries `layers[]` recording the winning source per path; defaulting fills only unset fields and never rewrites a user-set value (S-186). The **experiment layer** is an ordinary layer with `source_kind = experiment` so attribution can name the override (OQ-076).
6. **Authority caps are monotone.** `Constraint{kind: authority_cap, subject, source}` from any layer bounds a permission, budget or effect set; lower-precedence layers — the experiment layer included — may only **narrow** it, never widen it (`AuthorityViolation{path, attempted, cap, source}`); a disablement from any layer wins. This is the same property ADR-0016 imposes on `Budget` (monotone containment) and `delegated-to` (attenuating `Permission`) and that ADR-0017 checks as `authority_delta = widening` on diffs; authority layers use the one label scheme of CF-006 (WS-H1/L3). Organisation-level layers are C2 and never on the critical path; the Lab itself needs three layers at Stage 3 (baseline, experiment override, security/budget caps).

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: the boundary is visible in source in every audited system — algorithm in code, activation/parameters/policy in data (S-110, S-112, S-111, S-107; Tier B); policy migrated out of prose across the 2026 population (S-074/S-166 §14.5, `provisional (mech)`, corroborated by direct reading); prose-with-frontmatter as the on-ramp from text to typed configuration (S-111 `config/agent.ts`; S-184 Claude agents/skills); layered configuration with provenance and monotone managed constraints (S-107 `ConfigLayer`/`Constrained`/`Sourced`; S-183 "stricter value from a lower level over a managed value"; S-111 `plugin_origins`, MDM "override everything"; S-113 `projectTrusted`); defaulting that never overrides user values and validation that never silently corrects (S-186); ablation-by-file as the granularity that makes attribution possible (S-061, `provisional`, mechanism only); value unevenly distributed across slots so promotion must be experiment-gated, not assumed (S-092 vs S-061/S-066 disagreement, all `provisional`); vendor statement of the same rule (S-058 "config change, not a code rewrite … export to code when configuration isn't enough", vendor). Governance requirements are ADR-0002 (ratified).
- (b) Source-code precedent: `openhands-sdk/openhands/sdk/context/condenser/base.py` L16–79 and `settings/model.py` L194/301/323–330 (algorithm vs settings record); `agent/base.py` L207–262, L327–346 (typed prompt fields; the Jinja escape hatch as the boundary case) (S-110 @3fc7b22); `crates/goose/src/agents/extension_manager.rs` L1444–1606, `config/base.rs` L11–19, L49–50 (S-112 @fae91d0); `packages/opencode/src/config/config.ts` L46, L113, L374–539, `config/agent.ts` L13, `tool/registry.ts` L291–305 (`usePatch` model branch — the counter-example) (S-111 @9f8db11); `codex-rs/config/src/config_layer_source.rs` L8–75, `config_requirements.rs` L44, L162–178, `constraint.rs` L10–16, L59–65 (S-107 @0735c51); `packages/coding-agent/src/core/extensions/loader.ts` L763–800, `settings-manager.ts` L363–365, `pi-manifest.ts` (S-113 @400d690); `src/claude_agent_sdk/types.py` L1806–1879 (`allowed_tools` shadowing `can_use_tool` — a two-mechanism boundary warning) (S-109 @ad77094); `dspy/primitives/base_module.py` L156–205 and `dspy/predict/predict.py` L25–34 (state/program split; unsafe-state sanitisation) (S-144 @ca54a85); `autogen_core/_component_config.py` L47, L65 (trusted provider namespaces) (S-145 @027ecf0). The ladder with promotion/retirement criteria tied to the opacity ratio and assumption-debt expiry, and authority caps recorded as layer provenance in a run record, are `no-precedent / novel` as integrated contracts; each mechanism is precedented.
- (c) Disconfirming evidence considered: (i) the best systems cannot avoid code in their definitions (Starlark policy, Jinja templates, hooks, extensions) — answered by the pointer rule: pointers and interpreted leaves of declared kind are data; inline bodies are the one thing refused, and that is the path the precedents themselves mark unsafe. (ii) Layering is a product concern; a laboratory could key everything by one flat sealed document — answered: the Lab needs baseline/experiment/cap layers at Stage 3 and must attribute effects to the layer that set a field; the flat document is what `resolve` produces, layering is how it is authored; the accepted cost is per-field merge policy in the schema. (iii) If optimisation value lives almost entirely in one slot (S-092, `provisional`), the ladder is over-engineering — answered: AHE (S-061, `provisional`) attributes value elsewhere; the disagreement is why promotion is experiment-gated per slot rather than fixed. (iv) Deny-listing beats pinning when catalogs drift (OpenHands authors) — answered in ADR-0025: authored references may be selectors; only the sealed artifact is pinned. None overturns.
- (d) Conditionality: independent of model tier and task class; the promotion criteria are a design proposal validated by Stage-3 opacity-ratio and ablation experiments (medium confidence); interpreted leaves at C0 are conditional on OQ-077 (default: deferred); the layer set assumes at most one experiment layer per configuration (OQ-076); organisation/MDM-class layers are C2.
- (e) Build-stage assignment: **C0 / Stage 1** (MUST-code/MUST-data lists in Spec §3/§8; `Text`/`CompiledPayload`/code-pointer leaf kinds; per-field merge policy declared in the `hir/1` schema); **C0 / Stage 3** (`compose` with layers and `authority_cap`; opacity ratio in the bundle; first promotion experiment and the "retire rule R" recipe with WS-I2/I6); **C2** (organisation-level layers).

**T-LCD statement (ADR-0007 decision 5).** Satisfies: T-LCD-02 (free text only as `Text` leaves; opacity ratio is the ladder's progress metric), T-LCD-01 (per-model branches in code are defects relocated to profile-owned fields or declared variants), T-LCD-05 (retirement path via assumption-debt expiry; conditioned rules cannot be promoted without a record), T-LCD-14 (budget caps are `authority_cap`s the experiment layer cannot widen), T-LCD-10 (layer provenance is excluded from `semantic_id`, per ADR-0025). Does not address T-LCD-03/-04/-11 (executable/compiler; WS-A4) — no mitigating test needed from this ADR beyond the sealed definition being `lcd_report`'s input.

## Consequences

- Spec §3 carries the MUST-code and MUST-data lists; Spec §8 carries the ladder, its criteria and the worked example; every later dossier that proposes a behaviour states its rung on the ladder.
- WS-H1/L3 provide the one label scheme (CF-006) that `authority_cap` constraints and the reference monitor share; WS-H5/L5 confirm the trust-record shape a code-pointer leaf resolves to (CF-055).
- WS-I2 computes the opacity ratio per sealed definition per profile (OQ-036) and reports it alongside promotion experiments; WS-I5/I7 treat a promotion as a `HirDiff` with `derived-from` provenance; WS-I6's assumption-debt manager owns the retirement recipe.
- WS-J3 materialises overrides as an `experiment` layer (OQ-076) and inherits `AuthorityViolation` as a precondition failure alongside T-LCD-14's budget check.
- WS-C3 receives the `usePatch`-class model branches found in code as candidate profile-owned rules with assumption-debt records.

## Reversibility

**High for the ladder's criteria** (they are Spec prose validated by Stage-3 experiments and can be amended by ADR without touching stored documents). **Medium for the merge policy and authority caps** (changing a field's merge policy changes what `compose` produces for existing layered sources; a migration re-composes and re-seals). **Low for the MUST-code list**: moving a security or budget mechanism onto the editable surface contradicts ratified ADR-0002 and would require superseding it.
