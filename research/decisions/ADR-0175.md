# ADR-0175 — Run exposure over MCP (answers OQ-241): handle-carrying run tools at C1/Stage 4; ledger resources with subscriptions and the `io.modelcontextprotocol/tasks` carrier at C2 with an exhaustive status mapping and durable-before-respond; ACP stays the primary interactive run edge; every carrier is a lowering of the run envelope with a loss report

**Status:** ratified
**Owner workstream(s):** WS-K3 (consumers: WS-K4, WS-E4, WS-J6, WS-B1, WS-B3, WS-H7, WS-F2, WS-I1, WS-L4) · **Phase:** 3 · **Related:** ADR-0021 (lowering loss report; loss classes), ADR-0026/0027 (durable-before-visible; `seq`; `surface_ids`), ADR-0030/0032 (open effects on cancel; `unknown → probe`; `abandoned`), ADR-0042/0044 (views; exporters as subscribers; sinks), ADR-0068 (retention floors), ADR-0070 (durable `pending`; async `defer`; `input_required` as target-side `defer`), ADR-0097 (`input_required` as a paused effect; `isError` vs protocol error; tasks extension C2), ADR-0098 (ACP as the session boundary; `StopReason` projection), ADR-0106 (`StopReason` sum; outcome-class projection), ADR-0131 (`lifecycle.run.suspended`; wakeups), ADR-0173, ADR-0174; CF-363, CF-364; OQ-241, OQ-396, OQ-397; R-2.11.3, R-2.11.4

## Context

OQ-241 asks which edge exposes a *run* of HarnessHarness to an external client: K3's MCP server via the tasks extension, or the ACP agent surface (K4). The callers K3 serves — agents, schedulers, CI, and model providers acting as MCP clients (S-136 `tool/_mcp/server.py` `execution = "remote"`; S-555 client credentials) — speak MCP and not ACP. MCP 2026-07-28 offers three shapes for long-running work: explicit handles returned by a creation tool and polled (S-153 `server/tools.mdx` L683–737), resources with `subscriptions/listen` and `notifications/resources/updated` (S-153 `server/resources.mdx` L244–268; Codex serves an event catalogue this way — S-107 `codex-mcp/src/resource_client.rs` L46–80, `event_stream.rs` L30–80), and the official tasks extension with a durable `taskId`, `input_required` + `tasks/update`, cooperative `tasks/cancel` and `notifications/tasks` (S-554). The extension's invariants are the ledger's: the server "MUST NOT return `CreateTaskResult` until the task is durably created" (L300) ⇔ durable-before-visible (ADR-0026); `failed` only for JSON-RPC faults, `completed` for results including `isError: true` (L837–892) ⇔ ADR-0097 decision 4; cancellation "MAY ultimately reach a terminal status other than `cancelled`" (L404) ⇔ ADR-0030's close-open-effects-then-terminal; `input_required` ⇔ `security.permission.pending` (ADR-0070); a task "is not a higher-trust channel" (L905) ⇔ ADR-0174 decision 3. The Codex app server's verb inventory (`thread/start`, `turn/start`, `turn/interrupt`, `thread/read`, `thread/tokenUsage/updated`, `turn/completed`, `item/*/requestApproval` — S-107 `app-server-protocol/src/protocol/common.rs`) is the richest audited run-exposure surface and is what the MCP carriers must lower. No audited server or client implements the tasks extension at the pinned commits.

## Options considered

1. **ACP only** (K4 is the sole run edge; MCP callers must embed an ACP client). *Rejected:* excludes the caller population K3 exists for; the tasks extension exists for exactly this case.
2. **Tasks extension only, at C1.** *Rejected:* unimplemented in the audited population; blocks the C1 surface on an extension; polling handles need no capability and are the spec's baseline.
3. **Blocking `tools/call` until the run finishes.** *Rejected:* the extension's own rationale (connection timeouts; no crash resilience); a paused run awaiting a human would hold a connection for hours; `time.human_wait_ms` budgets would be unenforceable at the edge.
4. **Chosen:** three carriers by tier — handle tools (C1), ledger resources + subscriptions and the tasks extension (C2) — each an explicit lowering of the run envelope with a loss report; ACP remains primary for interactive hosts.

## Decision

1. **Handle carrier (C1 / Stage 4).** `launch_run{definition_ref, profile_ref, environment_ref, budget: BudgetSpec (required), task, idempotency_key}` returns `run_handle` **only after** `lifecycle.run.created` (seq 0) is durable; `run_status{run_handle} → RunStatusView{status ∈ {created, running, suspended{reason}, finished{outcome_class, stop_reason}}, pending_approvals[permission_id], account: ResourceAccount view, head_seq}`; `read_ledger{run_handle, from_seq, content_classes} → LedgerPage{events[], next_seq, withheld[], watermark}` (inclusive cursors, ADR-0027; policy per ADR-0174 decision 8); `submit_input{run_handle, content, idempotency_key}` (content at the caller's authority, ADR-0174 decision 3); `cancel_run{run_handle}` → `control.decision{kind: cancel}` then open effects close per ADR-0030 before `finished{stop_reason: cancelled}`; `get_trace{run_handle, view}` over the ADR-0042 projections; `get_bundle{run_handle}`; `list_pending_approvals`; `respond_approval` (principals only). Loss: `exact` for status and ledger pages; `no_slot` for push (the caller polls).
2. **Resource carrier (C2 / Stage 5).** `ResourceTemplate`s `hh://run/{run_handle}/ledger` (`resources/read` with `from_seq`), `hh://run/{run_handle}/status`, `hh://results/{configuration_id}` (scheme per OQ-394 / OQ-068); `notifications/resources/updated` only after the underlying event is durable; a subscription is bound to the caller's binding and is cancelled when the binding changes or expires (Codex event-stream precedent); the subscription is a declared sink (`SinkPolicy`; OQ-396). Loss: `exact` content; `narrowed` (the update notification carries no payload).
3. **Task carrier (C2 / Stage 5).** For a request whose `_meta` declares `io.modelcontextprotocol/tasks`, `launch_run` (and `open_experiment`) return `CreateTaskResult{resultType: "task", taskId, status: working, pollIntervalMs, ttl}` after seq 0 is durable — never to a client without the capability (`-32021`, S-554 L61–63); `taskId` is a `surface_ids` alias of the run handle (whether the same alias or a distinct one is OQ-397) and `ttl ≥` the run's retention floor (ADR-0068). Mapping (exhaustive over run status, `StopReason` and outcome classes — ADR-0106): `working ← created | running | suspended{reason ≠ awaiting_approval}`; `input_required ← suspended{awaiting_approval} | security.permission.pending` **only for `human_principal` bindings** (`inputRequests` keyed by `permission_id`, unique per task — L350); for `delegate`/`service`/`provider_client` bindings the task stays `working` with `statusMessage = awaiting_principal_approval` and the approval routes through H7 (ADR-0174 decision 3); `completed ← lifecycle.run.finished` with the `RunStatusView` as `result` for **every** outcome class including `refused`, `budget_exhausted`, `infrastructure_failure`, `oracle_failure` (results, not faults — L837–892); `failed` only for a JSON-RPC fault of the server itself; `cancelled ← finished{stop_reason: cancelled}` (cooperative; a run that finished before the cancel took effect reports its real terminal — L404). `tasks/update{inputResponses}` → `respond_approval` under ADR-0174 decision 3; `tasks/cancel` → `cancel_run`; `notifications/tasks` after durability; on Streamable HTTP `Mcp-Name = taskId` (L511). Loss: `narrowed` (six outcome classes and suspension reasons → five statuses; the typed reason travels in `statusMessage` and `result`), `no_slot` for turn structure, budgets and `causes[]`.
4. **Experiments** are exposed identically (`experiment_handle`; `experiment_status` = the WS-J3 scheduler projection; `pause/resume/close`), with the experiment run as the task subject; subject runs remain reachable through their own handles (`causes[]`).
5. **ACP remains the primary interactive run edge** (ADR-0098; WS-K4): it carries turn-structured updates, typed permission options and configuration coordinates natively. K3's carriers exist for callers who speak only MCP; both are lowerings of one run envelope; the exposure definition's `LoweringLossReport` lists every carrier's loss classes and the two edges are never re-implementations of each other (CF-363).
6. **Reflexive debt.** The tasks carrier and the resource carrier each carry an assumption-debt record (hypothesis: MCP-only callers need durable handles / push; evidence: S-554, S-136, S-555; removal test: no binding of kind `agent | service | provider_client` used them in the last N releases; expiry: the extension's own deprecation clock) — T-LCD-05 applied reflexively (AC-K3-12).

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: durable-before-respond, polymorphic results, `-32021` gating, status semantics, `failed`/`completed` split, cooperative cancel, unique input-request keys, auth binding and routing header (S-554 `specification/2026-07-28/tasks.md` L61–63, L102, L151–160, L300–302, L326–338, L346–381, L383–410, L507, L511, L837–892, L900–905); handles as ordinary strings with per-call authorization (S-153 `server/tools.mdx` L683–737); resource subscriptions and list-changed (S-153 `server/resources.mdx` L232–268); durable-before-visible and inclusive cursors (ADR-0026/0027); `pending` durable, `defer` asynchronous, `input_required` as target-side `defer` (ADR-0070 decisions 2, 4); open effects close before a terminal (ADR-0030); `StopReason`/outcome-class projection (ADR-0106; ADR-0098 table); ACP as the session boundary (ADR-0096/0098).
- (b) Source-code precedent: codex `codex-rs/app-server-protocol/src/protocol/common.rs` L559–751, L1023–1046, L1741–1777, L1894–1934 @0735c51 (run handles, turn control, approval requests to the client, usage and completion notifications — the verb inventory lowered here); codex `codex-rs/codex-mcp/src/resource_client.rs` L46–80 and `event_stream.rs` L30–80 @0735c51 (event catalogue as resources; per-subscription clients cancelled on access change); gemini-cli `packages/a2a-server/src/agent/task.ts` L279–325 @ed2ac40 (via WS-E4: tool confirmations lowered to `input-required` on a task-shaped protocol — the same mapping shape); inspect_ai `src/inspect_ai/tool/_mcp/server.py` L14–110 @75f4891 (a provider as MCP client of a harness server). Exposing a run through MCP tasks with an exhaustive outcome-class mapping and principal-gated `input_required` is `no-precedent / novel`.
- (c) Disconfirming evidence considered: (i) ACP already carries the run envelope; a second edge doubles the tables — answered: the caller population differs (MCP-only agents, CI, providers), the projections are shared (`StopReason`, outcome classes) and only the carrier differs; the loss reports make the choice honest. (ii) The tasks extension is unimplemented in the audited population — answered: it is C2 with a debt record; the C1 handle carrier needs no extension. (iii) Push over resources duplicates the ledger's `subscribe` — answered: the resource carrier *is* `subscribe` lowered to MCP for callers that cannot reach the internal boundary; it is a sink, not a store. None overturns.
- (d) Conditionality: independent of model tier; assumes MCP 2026-07-28 and the tasks extension's 2026-07-28 stable revision through Stage 5 (pins in the derivation key; a bump is a recompile plus loss-report diff); assumes `human_principal` bindings exist (ADR-0174) for in-band approval; assumes WS-B3's `suspended{reason}` vocabulary includes `awaiting_approval` (ADR-0070 decision 4); no `provisional` result is load-bearing.
- (e) Build-stage assignment: **C1 / Stage 4** decision 1 (handle carrier) and decision 4 for experiments; **C2 / Stage 5** decisions 2–3 (resources, tasks) and 6; decision 5 is a standing rule from Stage 4.

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-11 (every carrier declares its loss classes; unknown `_meta` preserved; AC-K3-10 exhaustiveness), T-LCD-05 (reflexive debt on the C2 carriers), T-LCD-06 (carriers are lowerings; no run-envelope class gains a field for MCP), T-LCD-07 (client capabilities per request are claims that gate result shapes only), T-LCD-12 (records over a process boundary), T-LCD-14 (`launch_run` requires a budget), T-LCD-15 (`withheld[]`/`n/a` typed). Does not by itself satisfy T-LCD-03/-04/-13. **ADR-0024 rung:** the carrier mappings, durability gating and subscription binding are MUST-code (projection tables versioned with the spec pins); `pollIntervalMs`, `ttl` policy and which carriers an exposure definition enables are MUST-data.

## Consequences

- OQ-241 is answered: K3 exposes runs through handle tools at C1 and through resources/tasks at C2; ACP (K4) is the primary interactive edge; WS-E4's proposal stands with the C1/C2 split confirmed.
- WS-B1/L4 answer OQ-397 (`taskId` alias; TTL vs retention floors); WS-I1/H6 answer OQ-396 (subscriptions as sinks); WS-H7 routes a `delegate`-launched run's `ask` to its principal and confirms `suspended{awaiting_approval}`; WS-L6 allocates the `hh://` scheme with the `_meta` prefix (OQ-068).
- WS-K4 must not define a second run-exposure verb set over MCP; its generated SDK client and K3 share the operation records (CF-363).

## Reversibility

**High** for the C2 carriers (each is a lowering behind a debt record; dropping one deletes a projection table and its loss report); **medium** for the handle carrier's tool shapes (changing them re-keys `hh-lab/1` and every stored surface-session turn's catalogue hash); **low** for durable-before-respond and the `failed`/`completed` split (shared with ADR-0026 and ADR-0097 decision 4).
