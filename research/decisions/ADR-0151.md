# ADR-0151 — One registry, many kinds: the `registry/1` record model, envelope, operations and the C0 minimal slice

**Status:** ratified, amended (Phase 3 synthesis)
**Owner workstream(s):** WS-J2 (consumers WS-J1, WS-J3, WS-J5, WS-K1, WS-K2, WS-L5, WS-H5, WS-I3, WS-E1, WS-C3, WS-I2) · **Phase:** 3 · **Related:** ADR-0023, ADR-0025 (base shapes; `resolve` caller), ADR-0036, ADR-0037, ADR-0038 (identity, names, snapshot), ADR-0063/0064 (extension records), ADR-0087/0088 (capability record envelope; `tool_registry_policy`), ADR-0045 (metrics as registry objects), ADR-0019/0093/0094 (closed-world; the tool catalog is the model-facing registry), ADR-0024 (MUST-code/MUST-data), ADR-0048 stage note on R-2.10.2, ADR-0050 §8; CF-324, CF-327, CF-329; OQ-114, OQ-353; R-2.10.2, R-2.12.1, R-2.12.2

## Context

Phase 1 fixed the shapes a registry stores (`ClassRecord`/`VariantRecord`, ADR-0023; name histories, supersession and `registry_snapshot_id`, ADR-0036/0037/0038) and Phase 2 added a dozen registry-shaped record kinds (capability records with their own envelope, ADR-0087; extension records, ADR-0063; profiles and test reports, ADR-0124/0125; wire dialects, role tables, procedure profiles, surface families, metric declarations, validators, environment records) each with its own status words and events. phase-2 §6.5 makes WS-J2 the owner of the *service* that holds them all. The audit (WS-J2 dossier §4) shows that registries which survived production are a closed set of record kinds over open, namespaced names (Inspect `RegistryType`, Harbor `AgentName` + `AgentCapabilities`, Omnigent `HarnessContribution`, the MCP and ACP registries), that the two open-kind precedents fail late (OpenHands `DiscriminatedUnionMixin`, Agent Spec), that no audited registry content-addresses its entries or records which snapshot a run resolved against, and that a model-queryable registry is attacked through descriptions (S-301, S-310). A registry with three unreconciled status vocabularies, kind-specific envelopes and implicit `@latest` resolution would be the LCD trap turned inward.

## Options considered

1. **Per-kind registries** (a tool registry, a variant registry, a profile registry … each with its own store, envelope and events). *Rejected:* one identity model and one snapshot id already span them (ADR-0036/0038); N stores mean N snapshot rules and N status vocabularies — the failure the audit found in Omnigent's pre-registry enumerations.
2. **An open, schema-validated record store** (any `kind` string with a registered schema, like `ext`). *Rejected:* late failure on unknown kinds (S-110/S-139 counter-examples); admission and authority would be decidable by a slot the kernel does not own (T-LCD-01 reflexive).
3. **A registry the model can query** (expose `query`/`catalog` as a `ToolCapability`, so an agent can pick its own compaction strategy). *Rejected:* description-only attacks on selection (S-301, `provisional` but corroborated by S-310 tool poisoning and the ClawHub compromise); ADR-0002 (iii) keeps the editable surface outside the model's reach; the tool catalog (ADR-0094) already is the model-facing registry with its own retrieval suite.
4. **One store, closed `RecordKind` per registry dialect, one envelope generalising ADR-0087's, names over immutable records, snapshot-deterministic operations, not model-facing (chosen).**

## Decision

1. **One store, one identity model.** The registry is a typed record store under ADR-0036 (`version_id` per record with a kind-specific domain tag), ADR-0037 (immutability, name histories, supersession, `StaleIndex`) and ADR-0038 (`registry_snapshot_id` over the referenced closure). Records reference HIR nodes by `VersionedRef`; the registry is never a HIR document.
2. **Closed `RecordKind` per `registry/1`:** `class, variant, conformance_suite, conformance_report, namespace, name_history_entry, registry_snapshot, foreign_import, sealed_definition, capability, extension, model_profile, profile_test_report, wire_dialect, model_role_table, procedure_profile, surface_family, metric_declaration, validator, environment_record, environment_family, trust_root_policy, identity_profile`. Growth is a registry dialect bump, never `ext`. `UnknownRecordKind` is an error. Adding a *component class* is a `ClassRecord` registration (ADR-0023 decision 2), not a new kind.
3. **`RegistryEnvelope{kind, version_id, semantic_id?, registered_at, registrar: ProvenanceRecord, admission ∈ {resolved, sealed, quarantined, revoked}, name_history_ref?, trust_record_ref? (mandatory when registrar.origin ∉ {kernel, definition}), dialect_range, registry_dialect, ext}`** wraps every record; ADR-0087's capability-record envelope is the instance of this shape (`status` read as `admission`; CF-329).
4. **Three orthogonal status axes, one vocabulary each (R5):** *admission* per record (ADR-0063's four values), *publication* per name-history entry (ADR-0037's `active | deprecated | yanked`), *conformance* per declaration field (derived; Ontology v1 verdicts — ADR-0152). A fourth status vocabulary anywhere in the registry is a schema error.
5. **`ClassRecord` and `VariantRecord` keep their ADR-0023 shapes and gain additive fields:** `ClassRecord{…, contract_version, home, declaration_schema, conformance_suite_ref, decision_points, metrics_declared, slot_key}`; `VariantRecord{…, contract_range, version_label? (a claim), param_schema: map<name, ParamDecl{type, domain, default?, unit?, sweepable, budget_relevant, affects[]}>, implementation{… host_requirements}, applies_to{participant_classes = {native}, families?}, declared_costs? (advisory, ADR-0089), summary: Text}`. A contract change is a new `ClassRecord` version; variants declare the `contract_range` they implement.
6. **Operations** (records in, records out; deterministic given a `registry_snapshot_id`; implementable out-of-process — T-LCD-12): `register` (schema + class-declaration + debt-record + pinned-implementation + trust/locality checks; idempotent on equal bytes; typed failures `UnknownRecordKind, SchemaViolation, UnknownClass, ContractIncompatible, ConditionedRuleIncomplete, UnpinnedImplementation, TrustRecordRequired, LocalityInadmissible, DialectIncompatible`); `publish` (ADR-0037 verbatim + namespace policy + cross-kind `NameCollision` + `ConformanceRequired`/`SuiteStale`); `resolve` (ADR-0037 S3 and ADR-0088 decision 1 verbatim, composed with the class-contract check and a conformance floor: `… | ContractIncompatible | ConformanceBelowFloor`); `query` (a closed, quantifier-free predicate over envelope/record fields; ordering by declared fields with `version_id` tie-break; never relevance over free text); `catalog` (K1/K2/J1 projection); `slot_choices`/`substitutable` (WS-J3); `snapshot` (ADR-0038); `record_conformance` (ADR-0152); `deprecate`/`yank`/`revoke` (ADR-0037/0064 verbatim under namespace authority); `lineage`/`sameness` (ADR-0037 §6.4; snapshots authoritative, diffs cached); `import`/`export` (ADR-0153); `verify` (ADR-0036).
7. **Invariants R1–R10:** immutable records, mutable names only; closed kinds; **no load on read** (no registry operation executes or imports an implementation — only ADR-0025 `instantiate` or the WS-L5 host does); declared ≠ probed; three status axes; **not model-facing** (no registry operation is a `ToolCapability`; registry text never enters a model context; a definition binding one fails `validate_assembly`); pinned or refused (sealed forms reference records only by `version_id`; unpinned selectors resolve only inside ADR-0025 `resolve`, with the snapshot recorded); snapshot determinism; authority never widens by registration/publication/import; failures are records (`RegistryDiagnostic` + event), never instrument start-up failures.
8. **`RegistryPolicy` is MUST-data** (a `HarnessRule`-class record layered per ADR-0024 with `authority_cap`): `{require_conformance ∈ {none, declared, probed} (default declared), admissible_report_producers, require_trust_record_for_origins, require_signature_for_kinds (from TrustRootPolicy), max_age?, collision_policy = refuse, foreign_import_default_admission = quarantined, allowed_localities_by_origin, allowed_foreign_systems[]}`. The store, envelope, operations, conformance drivers and namespace enforcement are MUST-code.
9. **Events** (proposed to WS-B1, ADR-0088 OQ-225 shape; each declares durability and observability level): `lifecycle.registry.{registered, published, conformance_recorded, deprecated, yanked, revoked, imported, snapshot}` carrying `kind`; kind-specific classes (`lifecycle.capability.*`, `security.extension.*`, profile status transitions) remain and are not duplicated (CF-327).
10. **C0 minimal slice vs C1 service.** C0/Stage 1: file/ledger-backed store, `registry/1` kinds, namespaces `hh/` and `local/`, `ClassRecord`s for the two Stage-1 classes, first-party variants, `register/publish/resolve/snapshot/verify/lineage`, `require_conformance = declared`, events. C0/Stage 2–3: remaining Phase 2 classes and kinds, `record_conformance/query/slot_choices/catalog`, `exp/<id>/` namespaces, snapshot id in every bundle and `Design`. C1/Stage 4 (R-2.10.2 proper): multi-namespace service with signer ownership, third-party publish, foreign import, revocation propagation, the registry over the ADR-0050 surface boundary via generated client. C1/Stage 5: profile/dialect/role-table/surface-family kinds. C2/C4: federation, evolution lineages.

**T-LCD statement:** satisfies T-LCD-01 (reflexive: closed kinds, no `ext` escape for admission/authority), T-LCD-05 (`register` refuses incomplete debt records), T-LCD-06 (hosted participants never become variants), T-LCD-07 (reflexive declared/probed split, via ADR-0152), T-LCD-08 (`required_inputs` enforced at `register`), T-LCD-09/-14 (`slot_choices` with `budget_relevant` domains), T-LCD-10 (identity by `version_id`; names as histories), T-LCD-11 (import/export with loss reports), T-LCD-12 (operations; out-of-process), T-LCD-15 (`applies_to.participant_classes`). Not applicable: T-02/-03/-04/-13 (no model-facing surface). **ADR-0024 rung:** store/operations MUST-code; records and `RegistryPolicy` MUST-data under the pointer rule.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: closed kind sets over open names — Inspect `RegistryType` (S-136), Harbor `AgentName` (S-132), Omnigent `HarnessContribution` (S-118), MCP registry `registryType`/`status` (S-502), ACP manifest `distribution` (S-503); late failure of open kinds — OpenHands `DiscriminatedUnionMixin` (S-110), Agent Spec `component_type` (S-139); identity/behaviour/declaration as separable rows with lazy behaviour — Omnigent proposal (S-118); staged resolution with typed failures — opencode loader (S-111); collision refusal — Omnigent (S-118), goose (S-112); load identity vs origin — opencode (S-111), pi (S-113); registry attacked through descriptions — S-301 (`provisional`), S-310, S-311/S-312 (production reports); names as metadata — Unison (S-171); immutability — SemVer (S-227), OCI (S-187).
- (b) Source-code precedent: `inspect_ai/src/inspect_ai/_util/registry.py` L40–82, L250–330, L613–660 @75f4891; `harbor/src/harbor/agents/factory.py` L38–170, `agents/capabilities.py`, `models/agent/name.py` @7d5285b; `omnigent/omnigent/harness_plugins.py` L55–140, L932–1070, L1170–1200 @6a069da; `opencode/packages/opencode/src/plugin/loader.ts` L15–135, `config/plugin.ts` L62–70 @9f8db11; `pi-mono/packages/coding-agent/src/core/package-manager.ts` L1682–1700 @400d690; `goose/crates/goose/src/plugins/{mod.rs, discovery.rs}` @fae91d0; `software-agent-sdk/openhands-sdk/openhands/sdk/utils/models.py` L75–150 @3fc7b22. The integrated design (one content-addressed store for every registry-shaped kind, three status axes, no-load-on-read, not-model-facing as a validation invariant) is `no-precedent / novel` as an integration.
- (c) Disconfirming evidence considered: "a research instrument needs no registry" (doc 2 §7 — no framework imports; HAL import-path agents, S-134) — answered by the C0 slice being the Inspect shape plus identity fields that exist anyway; "content-addressed entries explode lineages" — answered by name histories, the sameness ladder and `local/`; "per-kind registries are simpler" — answered by the single snapshot/identity model already ratified; "the model should pick its components" — answered by ADR-0002 (iii) and S-301/S-310, which are the reason for R-NM, not against it. None overturns.
- (d) Conditionality: model- and task-independent; assumes ADR-0036/0037/0038 identity and name histories at Stage 1, ADR-0023/0025 `resolve` as the only unpinned-selector consumer, and that every Phase 2 class ships a `ConformanceSuite` (ADR-0152) before `require_conformance` is raised above `declared`; multi-namespace ownership assumes H5's C1 signer machinery.
- (e) Build-stage assignment: **C0 / Stage 1** (decisions 1–5, 7; operations `register/publish/resolve/snapshot/verify/lineage`; namespaces `hh/`, `local/`; events); **C0 / Stage 2–3** (`record_conformance/query/slot_choices/catalog`; remaining kinds; snapshot in bundles/`Design`); **C1 / Stage 4** (service, third-party publish, import/export, revocation propagation; R-2.10.2 proper); **C1 / Stage 5** (profile-plane kinds); **C2/C4** (federation, evolution lineages).

## Consequences

- WS-J1's `resolve` takes a `registry_view` = one snapshot; WS-J3 pins one snapshot per `Design`; WS-J5 rows carry `registry_snapshot_id` and conformance/revocation annotations; WS-K1/K2 render `catalog` and `RegistryDiagnostic`s; WS-L5's plugin record must be `register`-able as a `VariantRecord` with the envelope's trust fields; WS-E1's envelope is read as this envelope; WS-B1 gains the `lifecycle.registry.*` classes; WS-I3's bundle member list is refined (CF-328).
- No subsystem may add a status word, an envelope field or a model-facing registry operation outside a registry dialect bump.

## Reversibility

**Low** for closed kinds, the envelope, no-load-on-read and not-model-facing (bundles, results rows and the LCD invariants depend on them); **medium** for the operation set (additive operations are cheap; removing `query` fields is a dialect bump); **high** for the C0/C1 stage split and storage form (internal to the registry).
