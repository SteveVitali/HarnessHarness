# ADR-0078 — The memory hierarchy is five addressing classes over three ratified substrates; one `MemoryStore` contract; derived memories are immutable provenance-bearing records distinct from materialized views; verbatim history stays addressable beside distilled memories

**Status:** **ratified** (Phase 2 synthesis, 2026-09-10)
**Owner workstream(s):** WS-D3 (consumers: WS-D1, WS-D2, WS-D4, WS-D5, WS-B3, WS-E3, WS-H1, WS-I5, WS-I1, WS-J3) · **Phase:** 2 · **Related:** ADR-0026 (authoritative record; materialized views), ADR-0027/0029 (`seq`, content addresses, offload), ADR-0036 (five identity kinds), ADR-0037 (immutability I1–I5, supersession S1–S8, name histories, `StaleIndex`), ADR-0016 (`Memory`, `Artifact`, `Procedure` entities; `EffectDomain.memory_write`), ADR-0033/0034 (provenance record; P1 derivation), ADR-0014 (`validity()`), ADR-0007 (T-LCD-02/-08/-10/-12/-13/-15); CF-008, OQ-020 (retrieval half), OQ-049; R-2.4.3, R-2.4.4, R-2.2.1, R-2.9.3

## Context

Doc 2 §5.1 names five layers — working context, artifact memory, episodic memory, procedural memory, durable session state — and its second-pass synthesis adds that "a practical general-purpose memory substrate should therefore separate immutable event history from mutable derived memories; attach source, timestamp, version, confidence, scope, and revocation state; support conflict sets and supersession edges". Phase 1 ratified the substrates: the run ledger plus content-addressed blobs as the sole authoritative record with deterministic, rebuildable materialized views (ADR-0026), five identity kinds with names as append-only histories over immutable versions (ADR-0036/0037), and the `Memory`/`Artifact`/`Procedure` entities with validity and provenance (ADR-0016). The WS-D3 audit (dossier §4a F1, F3, F6, F8) found that every production coding harness read in source has exactly two physical stores — an append-only transcript and a directory of files with a small index — and that the memories in the directory are produced by a background pipeline from the transcript (Codex Phase 1/2 with leases, watermarks and a git-baselined memories directory; Claude Code auto memory; OpenHands `MEMORY.md`), never by editing the transcript. It also found the counter-lineage (A-MEM "memory evolution", Letta `core_memory_replace`, Mem0 UPDATE/DELETE) mutates records in place, and one `provisional` study (S-349) reporting that extracted memories lose 16–22 points against verbatim chunks in an identical pipeline.

## Options considered

1. **Five physical stores, one per layer** (a vector DB for episodic, a skill registry for procedural, a KV store for session state…). *Rejected:* no audited system does this; it multiplies write paths the monitor must guard and views the ledger must rebuild (Kiehl's projection cost, S-195 via WS-B1); it invites the AIOS shape where the memory store has its own trust model.
2. **One store — everything is a ledger event** (memories as `context.memory.written` payloads only). *Rejected:* a memory is a model-authored, versioned, supersedable record with a lifecycle (ADR-0037 S5); an event is immutable history. Conflating them either forbids supersession or forces history rewriting (ADR-0026 rule 4).
3. **MemGPT-style tiers (main/recall/archival) with LLM-directed paging.** *Rejected as the model:* the tiers are a *delivery* policy (D1 `handle_only`/`expanded`, D2 compaction) and an embedding archive; they carry no validity, authority or version (dossier F4). Retained as an expressible policy variant.
4. **Five addressing classes over three ratified substrates, one `MemoryStore` contract for derived records and manifests, deterministic views for indexes, derived memories as immutable versions with `derived_from` ranges that stay addressable (chosen).**

## Decision

1. **Layers are addressing classes, not stores.** `W` (working context) is the `ContextPlan` projection and is never a retrieval source; `A` (artifact memory) is the blob store and the environment tree, identity `ContentAddress`, names via `NameHistoryEntry`; `E` (episodic memory) has two forms — *verbatim* (ledger `EventRef` ranges and offloaded observations by `ContentAddress`) and *distilled* (`Memory{kind: episodic}` versions in the `MemoryStore` with `source_trajectories` and `derived_from` ranges); `P` (procedural memory) is `Procedure`/skill versions in the registry or `MemoryStore` with an **index form** `{name, description, triggers, location}`; `S` (durable session state) is the ledger and its views plus **named session artifacts** (progress notes, feature/task list, goal state, bootstrap script) — `Artifact` versions behind logical names with `supersedes` histories. Every item in every layer is addressable by an ADR-0036 identity or it is not retrievable (D1 closed world).
2. **One `MemoryStore` contract** (component class; in-process or out-of-process, T-LCD-12): `put(record, writer_ctx, scope) → version_id` (an effect of domain `memory_write`), `bind(name, version_id, supersedes?, reason)`, `revoke(version_id, reason, authority) → RevocationRecord`, `resolve(name | version_id, mode ∈ {execute, audit})` (ADR-0037 S3 verbatim), `manifest(scope, at) → MemoryManifest`, `enumerate(layer, query, at) → [RawHit]`, `stale_candidates(scope, policy)`. Every operation appends its ledger event; `put` carries the memory scope's `lease_generation`.
3. **`MemoryManifest{scope, entries[{name, version_id, kind, one_line: Text}], version, provenance}`** is the typed form of every index/entrypoint file (`MEMORY.md`, `memory_summary.md`): a versioned record bound to `(namespace = memory/<scope>, name = index)`, rebuilt by consolidation, delivered eagerly under a profile rule `memory_index_budget{max_lines, max_bytes}` with an assumption-debt record, while bodies are `handle_only` candidates.
4. **Derived-vs-authoritative boundary (with ADR-0026).** *Authoritative:* ledger, blobs, run manifest — unchanged. *Materialized views* (deterministic, `deriver = kernel`, rebuildable to equal `view_hash`): `lexical_index` (over ledger ranges, memory bodies, manifests), `structural_index` (symbols and reference graph over a tree address), `memory_usage` (from `context.memory.read` events — never a model-editable counter), `stale_candidates`, `resume_set` (layer-S heads by name). *Derived memories* (`deriver = delegate`; not rebuildable to equal bytes): first-class immutable versions in `MemoryStore`, never ledger events, never replacing their sources. Separation test: `project()` twice ⇒ equal hash; `extract()` twice ⇒ two versions joined by `supersedes{reason: consolidation}` (proposed `reason` value, CF-175) with identical `derived_from`.
5. **Verbatim stays addressable.** A distilled `Memory` carries `derived_from: [EventRef | ContentAddress]` and the ranges remain retrievable by `by_run`/`by_address`/`lexical`; consolidation prunes *manifest entries*, never ledger ranges (ADR-0026 rule 4; Codex keeps `raw_memories.md` + `rollout_summaries/` beside `memory_summary.md`).
6. **`MemoryKind = {episodic, procedural_note, preference, reference, decision}`** (closed per dialect, registered `ext`; OpenHarness/Claude Code `type` generalized) is a ranker feature and a manifest attribute; it never decides authority, validity or readers (ADR-0015 `ext` rule applied to a kernel field).
7. **Layer-S session artifacts** are written as `fs_write`/`memory_write` effects; a closed-schema field that a `Validator` references (a feature list's `passes`) is endorsed to `environment` by the `validator` basis (ADR-0035); free-text progress notes are `≤ external` (R-TEXT). B3's resume reads `resume_set` heads by name; a head whose validator has no verdict is delivered with `validity = unknown`.

**T-LCD statement.** Satisfies T-LCD-02 (memory bodies are `Text`/`StructuredValue`; manifests are typed; each delivered memory is ablatable), T-LCD-10 (identity = `version_id`/`semantic_id`; manifest names and one-liners are surfaces), T-LCD-12 (operations; out-of-process store is the goose MCP precedent), T-LCD-13 (bodies `handle_only` ⇒ deterministic activation on expansion; OQ-049 input), T-LCD-15 (hosted participants have no store events ⇒ `n/a`), T-LCD-05 (index budgets are conditioned rules). Not applicable: T-LCD-01/-03/-04/-06/-07/-08 (ranker contract is ADR-2)/-09/-11/-14.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** immutable history → background-derived memories with leases and watermarks — Codex memories pipeline (S-107, read in source); index eager + bodies on demand under a byte/line budget — OpenHands (S-110), Claude Code docs (S-351), OpenHarness (S-117), Codex; progress files / feature lists / goal state as the resume set — S-041 (Tier B), prime-agent `goals.ts` (S-116); memory tiers as paging policy — MemGPT (S-016); reflections as episodic records written after feedback — Reflexion (S-010); extracted memories are lossy, keep verbatim — S-349 (`provisional`), Codex/Cursor practice (S-050); in-place mutation as the counter-lineage — A-MEM (S-347), Letta (S-352), Mem0 (S-348); "separate immutable event history from mutable derived memories" — doc 2 §5.1 second pass (Tier-B synthesis); views vs records — ADR-0026 (ratified).
- **(b) Source-code precedent:** `codex/codex-rs/memories/README.md`, `state/memory_migrations/0001_memories.sql` (`stage1_outputs`, `jobs` with `lease_until`, `input_watermark`), `memories/write/src/{phase1,phase2,rollout_input}.rs`, `ext/memories/src/backend.rs` (`MemoriesBackend` trait — the store contract shape) @0735c51; `software-agent-sdk/openhands-sdk/openhands/sdk/context/memory.py` @3fc7b22 (two-tier manifest, logs on demand); `OpenHarness/src/openharness/memory/{types,schema,usage,memdir}.py` @9b2efd7 (lifecycle fields, `usage_index.json`, entrypoint caps); `goose/crates/goose-mcp/src/memory/mod.rs` @fae91d0 (out-of-process store); `prime-agent/packages/coding-agent/src/core/goals.ts` @427ea4c (durable goal state); `AIOS/aios/memory/note.py` @292d98f (the model-editable `retrieval_count`/`evolution_history` counter-example). **`no-precedent / novel`** for: the five layers as addressing classes with per-layer validity checks; `MemoryManifest` as a versioned name-bound record; `memory_usage` as a ledger-derived view; the extract-twice supersession test.
- **(c) Disconfirming evidence considered:** "five layers are two stores wearing five hats" — accepted at the store level, which is why layers are addressing classes; in-place mutation is simpler and what A-MEM/Letta/Mem0 ship — rejected by ratified ADR-0037 I1 and by S-106's failure signature; keeping verbatim ranges costs index space — the ledger already stores them (ADR-0029) and Codex/Cursor ship it; S-349/-04 are single-team preprints — used only to keep verbatim addressable and to type the mutation plane, never as a C0 basis. None overturns.
- **(d) Conditionality:** model- and task-independent for the structure; the *value* of distilled vs verbatim retrieval and of index budgets is model-conditioned and a Lab measurement (AC-D3-9/-10); assumes WS-D5's Procedure IR exposes the index form; assumes B5 exposes a tree address for the workspace (OQ-203).
- **(e) Build-stage assignment:** **C0 / Stage 1** — `MemoryStore` operations, `Memory`/`Artifact` records, `lexical_index`, `resume_set`; **C0 / Stage 2** — manifests, episodic extraction and consolidation Procedures, `memory_usage`, `stale_candidates`, layer-S validators; **C0 / Stage 3** — `structural_index` + T-LCD-13 memory chain; **C1 / Stage 5** — store variants (out-of-process), `MemoryKind` uses in rankers; **C2** — lifecycle richness (D4).

## Consequences

- WS-D1 admits retrieved items as `Candidate`s with `kind ∈ {memory, artifact_excerpt, procedure_index, procedure_body, transcript_item}`; a `memory_index` kind/priority may be needed (CF-176).
- WS-D2's compaction summaries become layer-A artifacts and layer-E inputs with `derived_from = forgotten ids` (ADR-0034 P1 already requires the label join).
- WS-D4 filters on ADR-0037 records and consumes `stale_candidates`/`memory_usage`; retirement is `supersedes{reason: expiry}`.
- WS-B1 gains `context.retrieval.completed` and payload extensions (ADR-2; CF-173); WS-A3/L4 decide the `consolidation` reason value (CF-175).
- WS-B3 reads `resume_set`; WS-I5 draws harness-edit hypotheses from the episodic layer with `derived_from` ranges as evidence.

## Reversibility

**High** for the layer partition and `MemoryKind` (dialect bump; stores unchanged); **medium** for the `MemoryStore` contract (consumers D1/D4/D5/B3 bind to it at Stage 1–2); **low** for the derived-vs-authoritative boundary — reverting to in-place memory mutation after Stage 2 would break ADR-0037 I1, the S-106 regression test and every `derived_from` chain the Lab uses for attribution.
