# ADR-0124 — The profile rule inventory `ProfileRuleInventory/1`, the capability/constraint split, additive `ModelProfile/1` fields, the Profile Compiler as a boundary component class, chain resolution with a closed selector grammar and no silent default, per-role profile binding, and the `profile_prose` opacity bucket

**Status:** **ratified, amended** (Phase 2 synthesis, 2026-09-10)
**Owner workstream(s):** WS-C3 (consumers: WS-A4, WS-C1, WS-C2, WS-D1, WS-D2, WS-E2, WS-E3, WS-A5, WS-J2, WS-J3, WS-I2, WS-I6) · **Phase:** 2 · **Related:** ADR-0007 (T-LCD-01/-02/-05/-08/-09/-10/-12), ADR-0008/ADR-0012/ADR-0048 (vocabulary; boundary component), ADR-0016 (`AgentProcess.native.profile`, surface record, `HarnessRule`), ADR-0019 (stage 3, closed-world rule, `relower`), **ADR-0020 (the contract this ADR designs inside — not superseded)**, ADR-0022 (E1–E7), ADR-0024 (per-field merge policy), ADR-0033/0034 (role-placement invariant), ADR-0036 (`configuration_id`), ADR-0039/0043 (`usage_mapping`, `normalizer_ref`), ADR-0045 (roles in result keys), ADR-0050 §8; CF-044, CF-046, CF-049, CF-106, CF-199, CF-166, CF-266…CF-269; OQ-064, OQ-104, OQ-122, OQ-294; R-2.3.3, R-2.3.1, R-2.3.2, R-2.4.1, R-2.5.2

## Context

ADR-0020 ratified the Model Profile as a five-part data document with a closed enum of twelve rule kinds and delegated to WS-C3 the rule inventory, the probes and the Profile Compiler. The source audit (WS-C3 dossier §4) found the same per-model knowledge in three maturity forms: codex keeps it as per-slug rows (`models.json`, 48 keys) but still has a literal `match slug` in `models-manager/src/model_info.rs` L188; gemini-cli keeps per-family full tool manifests as data and resolves the family by a regex in code while a flag-gated path already reads `family` from a data record (`config/models.ts` L440–447); OpenHands keeps selectors as ordered substring lists (`model_features.py` `apply_ordered_model_rules`, "last matching rule wins"); opencode keeps everything as branches (`session/system.ts` L28–50; 83 `includes(…)` tests in `provider/transform.ts`). pi-mono's typed `compat` flags (`types.ts` L568–760) show that a large share of "per-model transcript rules" are *constraints of the model/API* (`requiresAssistantAfterToolResult`, `requiresToolResultName`, `allowEmptySignature`) rather than harness choices. Tier-A evidence (S-459 ICLR 2024: format performance "only weakly correlates between models"; S-177 ACL 2026) shows rules are non-monotone across models. Runs bind more than one model (D2 summariser, G3 judges, F3 subagents, C2 fallback) and ADR-0045 keys results by "model snapshot(s) with roles", but ADR-0016 carries a single `profile`. Every audited system *defaults* on an unknown model; codex at least flags it (`used_fallback_model_metadata: true`).

## Options considered

1. **Open rule kinds with an "other" params blob** (pi/opencode growth pattern). *Rejected:* recreates the untyped escape hatch T-LCD-01 forbids; ADR-0020 fixed the enum as closed per schema version.
2. **One rule per pi-style flag** (~45 kinds, each with a debt record). *Rejected:* most flags are constraints, not hypotheses; a debt record per constraint is bureaucracy with no removal test (the §5 R1 objection made real).
3. **Selector as regex/substring evaluated in code** (gemini, OpenHands, opencode). *Rejected:* the T-LCD-01 failure signature; unbounded growth; no refusal on ambiguity ("last wins").
4. **Silent default profile for unknown models** (all audited systems). *Rejected:* attributes a run to a profile the model never had; `configuration_id` would lie.
5. **Twelve typed kinds with per-kind `params` schemas that *point at* neighbour-owned records (E2 families, D1 layouts, `Text` leaves); constraints live in `capabilities` and are kernel-derived without debt records; a closed selector `Pattern` grammar with declared precedence and refusal; explicit `fallback_profile` only; per-role binding in the manifest; `profile_prose` bucket (chosen).**

## Decision

1. **`ProfileRuleInventory/1`** fixes, for each ADR-0020 kind, the typed `params`, the `owned_fields`, the application point and the admissible compliance detector class exactly as the WS-C3 dossier §6.2 table: `interaction_mode{mode, fallback?, shim?, code_mode?}` (C0: `native_fc` only) · `tool_shape{capability_class → SurfaceFamilyRef}` (an E2 variant *by id*, never an inline surface — CF-199) · `naming{charset, max_length, case, namespace{scheme, separator}, reserved_names[], recovery_table?}` · `schema_dialect{dialect_id, strict ∈ {prefer, require}, transform: SchemaDialectTransformRef}` · `description_template{scope, template: Text, examples_policy}` · `error_format: ErrorFormatSpecRef` · `result_render: ResultRenderSpecRef` · `prompt_layout{layout: Layout, section_templates, role_map, demotion_wrappers?, reminder_placement, cache_tiers}` (houses everything D1 lists as profile-owned; no new kinds — CF-267) · `transcript_render{stale_signature ∈ {drop, placeholder}, placeholder_text: Text, image_downgrade, tool_result_naming_template, reasoning_summary}` (OQ-067 profile default: `placeholder`) · `compaction_reminder{threshold, template: Text, placement, guidance?, fallback{prompt, buffer_tokens}?}` · `sampling_defaults{temperature?, top_p?, reasoning{default_level, admissible[]}, max_output_default}` · `caching_markers{convention, positions[], retention_ttl_class}`. Rules apply in this order, then by `rule_id`. `ProfileRule` gains `scope?`, `supersedes?` and `compliance{detector_class ∈ {deterministic, judged, none}, followed_predicate_ref?}`. Nothing outside the twelve kinds; growth is `ProfileRuleInventory/2` by ADR, informed by the metered `ext` block (`profile.ext_field_count`).
2. **Capability/constraint split.** Provider *requirements* (`assistant_required_after_tool_result`, `tool_result_name_required`, `thinking_as_text_required`, `empty_signature_allowed`, `tool_name_charset`, `tool_call_id_charset`, `system_role_count`, `max_cache_breakpoints`, …) are `capabilities` fields (tri-state, declared → probed); the compiler derives the mandatory renderer/serialisation steps from them with `deriver = kernel` and **no debt record** — a constraint is not a hypothesis. Rules carry only *choices*. Additive `ModelProfile/1` capability fields: `seed_honoured`, `substitution_allowed`, `usage_mapping` (CF-106 custody), `compatibility_token?{value, provenance: reported}` (codex `comp_hash` precedent; CF-268), `tool_result_role`, `developer_role`, `reasoning_levels[]`.
3. **Envelope additions (additive, same schema version):** `Selector{provider_api_family, model_family, version_pattern: Pattern, precedence, successor_ref?, retirement_at?, roles_admitted ⊆ ModelRole}` with `Pattern ∈ {exact(id) | prefix(id) | range(family, lo?, hi?) | any}` — a closed grammar, never a regex or substring; `compatibility{inventory_version, min_compiler_version}`; `tests{validity_ref?, golden_ref?, probe_spec_refs[], compliance_design_refs[]}`. `successor_ref`/`retirement_at` are the data form of codex `upgrade{model, retirement_at}` (OQ-294: reroute `reason = policy` after `retirement_at`, `operator` before).
4. **Profile Compiler = boundary component class** (`home = model_boundary`, receives `(ModelProfile, ResourceAccount)`, pure, locality-neutral, own debt record) with operations `resolve_profile`, `link_profile`, `lower_profile` (ADR-0019 stage 3), `diff_profiles`, `test_profile`, `probe_profile` (executed by the C1 gateway `probe`), `evaluate_expiry`, `retire_rule` — contracts as in dossier §6.1; invariants: write-set ⊆ surface records; `diff(lower(P1), lower(P2)) ⊆ owned(P1) ∪ owned(P2)`; every surface element stamped `rule_ids[]`.
5. **Chain resolution.** Matches ordered by `(precedence, specificity exact > range > prefix > any)`; ties ⇒ `AmbiguousSelector` (refusal); chain = `extends` path leaf → base; per-field merge policy `override | append | forbid_override` (ADR-0024 pattern); `NoProfile` at `link` is an error unless the definition binds an explicit `fallback_profile` whose debt hypothesis is "unprofiled model" and whose status can never be `active` past a `date` expiry; the manifest records `fallback_used`.
6. **Per-role binding.** The run manifest carries `profile_binding: map<ModelRole ∈ {primary, summarizer, judge, subagent(class), shim_interpreter}, ProfileRef>`; ADR-0016's `AgentProcess.native.profile` is the `primary` entry; every `model.call.requested` stamps its role's `profile_ref`; `configuration_id` takes the primary profile's `semantic_id`, other roles are recorded coordinates (final tuple rule OQ-303 with A5/J3/L4).
7. **Opacity.** `OpacityReport.profile_prose` = tokens of every `Text` leaf owned by the bound chain rendered into the surface (templates, wrappers, placeholders, reminders); harness `opacity_ratio` excludes it; `profile_opacity_ratio` reported per profile hash (OQ-064).

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: rules are model-conditioned and non-monotone (S-459 Tier A; S-177 Tier A; S-037 Tier B; S-049 Tier B); constraints vs choices are distinguishable in typed form (S-113 `compat` flags); the same content exists as data in production (S-107 `models.json`; S-119 `model-family-sets`), as data-in-migration (S-119 `config/models.ts` flag path) and as branches (S-111); multi-role binding is already practice (S-119 `chat-compression-*` aliases; S-107 `auto_review_model_override`; WS-D2 `summarizer_profile`; ADR-0047 judge `ProfileRef`); unknown-model defaulting is flagged but not refused (S-107 `used_fallback_model_metadata`).
- (b) Source-code precedent: rule inventory cross-checked field-by-field against `codex-rs/models-manager/models.json` (S-107 @0735c51; 48 keys → 12 kinds + capabilities + selector + out-of-scope presentation keys) and `gemini-cli/packages/core/src/tools/definitions/model-family-sets/{default-legacy,gemini-3}.ts` (S-119 @ed2ac40); selector-as-data — `openhands-sdk/.../model_prompt_spec.py` L12–107 (S-110 @3fc7b22), gemini `modelFamilyService.ts` L20–30; override merge — gemini `tools/definitions/resolver.ts` L17–35; interaction-mode fallback at link — `codex-rs/core/src/tools/mod.rs` L80–90 `effective_tool_mode`; successor/retirement as data — `models.json` `upgrade`; compatibility token — `models.json` `comp_hash`, `codex-rs/core/src/session/turn.rs` L1233–1300; negative — `opencode/packages/opencode/src/session/system.ts` L28–50, `tool/registry.ts` L293–300, `codex-rs/models-manager/src/model_info.rs` L188. The closed `Pattern` grammar with refusal, the capability/constraint split with kernel derivation, per-role binding in the manifest and the `profile_prose` bucket are `no-precedent / novel`.
- (c) Disconfirming evidence considered: (i) the widest-coverage systems keep growing flag sets and branch files (pi ~45 flags; opencode 83 tests) — answered by the constraint/choice split (most growth is capabilities, which are tri-state fields not rules) and the metered `ext` block (ADR-0020 §5); (ii) every audited selector is regex/substring and works in production — answered: they also require a code edit per release (OpenHands variant lists) and cannot refuse ambiguity; the grammar is evaluated by data, and `range` covers version families; (iii) refusing unknown models hurts day-one usability — answered by the explicit, expiring `fallback_profile`; (iv) a 21k-character template makes a faithful profile look opaque — answered: reported in its own bucket, never gated. None overturns.
- (d) Conditionality: assumes ≥ 2 provider families with materially different tool/transcript conventions remain in use (true through 2026-09: patch vs string-replace, strict-schema subsets, eleven reasoning-replay formats); a single-family deployment (OpenHarness snapshot, no branches found) needs only the null profile — the component's own removal test. C0 slices rest on ratified ADR-0020 plus Tier-A/B evidence; no `provisional` claim is load-bearing.
- (e) Build-stage assignment: **C0 / Stage 1** (inventory enum + per-kind `params` schemas, `Pattern` grammar, capability additions, null profile, `profile_binding` manifest field); **C0 / Stage 3** (two minimal profiles compiled through `resolve_profile`/`link_profile`/`lower_profile`; `profile_prose`; refusal semantics; out-of-process run); **C1 / Stage 5** (full rule family, chains > 2, per-field merge, `successor_ref` reroute with C2, per-role binding executable); **C2** (`shim`/`code_mode`/`freeform`).

**T-LCD statement (ADR-0007 decision 5).** Satisfies: T-LCD-01 (twelve typed kinds, write-set ⊆ surface records, selector grammar replaces branches; AC-C3-1), T-LCD-02 (every template is a `Text` leaf; `profile_prose` bucket), T-LCD-05 (every rule carries a record; constraints explicitly do not need one and cannot be rules), T-LCD-08 (boundary component receiving profile + account; the profile is an input to D1/D2/E2/E3 through typed refs), T-LCD-09 (per-role binding makes model × rule a representable factor), T-LCD-10 (`naming`/`description_template` edits are `ProfileDiff` surface ops), T-LCD-12 (operations; AC-C3-12). Does not by itself satisfy T-LCD-04 (executable at Stage 3 under ADR-0019/0020 AC-7) or T-LCD-13 (ADR-2 of this workstream supplies the compliance suite). Rung on the ADR-0024 ladder: rules are *parameters/entities* (MUST-data); the compiler is MUST-code.

## Consequences

- WS-E2's `SurfaceFamily`/`VariantSelector` are the referents of `tool_shape`; WS-E3 reads `naming.recovery_table`; WS-D1 executes `prompt_layout`/`transcript_render`; WS-D2 consumes `compaction_reminder`.
- WS-C1 adds a compatibility token to discovery claims where a dialect exposes one; WS-C2's guard reads `successor_ref`/`retirement_at`.
- WS-A5/WS-J3/WS-L4 decide the `configuration_id` treatment of non-primary roles (OQ-303); WS-B1 adds `profile_binding` to the manifest and `profile_ref` per call (already present on `model_ref`).
- WS-I2 registers `profile_opacity_ratio` and `profile.ext_field_count`.

## Reversibility

**Medium.** Adding a kind or a capability field is an inventory/schema bump with migration. Reverting the constraint/choice split (debt records on constraints) is cheap but pointless; reverting the closed selector grammar to regex after Stage 3 would re-admit branch growth and invalidate AC-C3-1/-2 — the costly direction, hence decided now. The `fallback_profile` rule can be relaxed by ADR if day-one usability proves decisive.
