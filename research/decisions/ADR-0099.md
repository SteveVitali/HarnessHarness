# ADR-0099 — Protocol version and capability negotiation, and trust at every edge: the `ProtocolBinding` record, probe-first pinning, typed `ProtocolVersionMismatch`, omitted → `unknown`, unknown preservation, expiring eras; peers `unverified` until attested, claims never decide, approvals per `effect_id`

**Status:** **ratified** (Phase 2 synthesis, 2026-09-10)
**Owner workstream(s):** WS-E4 (consumers: WS-K3, WS-K4, WS-J6, WS-E1, WS-H1, WS-H3, WS-H5, WS-H6, WS-B1, WS-L6) · **Phase:** 2 · **Related:** ADR-0013 (capability vector; DRIFT), ADR-0015 (`ext` preserved), ADR-0018 (tri-state record), ADR-0021 (pins in the derivation key; CI drift checks), ADR-0026/0027 (run manifest), ADR-0031 (`projected(declared)` raises only), ADR-0033/0034/0035 (labels; endorsement; `pin`), ADR-0036 (content addresses), ADR-0038 (bundle as lock manifest), ADR-0050 §8(b); ADR-0007 (T-LCD-05/-07/-11); CF-027, CF-082, CF-087; CF-209; OQ-034, OQ-068, OQ-107, OQ-242, -03, -04, -06; R-2.5.4, R-2.12 (versioning/extensibility)

## Context

All three protocols negotiate versions and capabilities, each differently: MCP 2026-07-28 carries version and client capabilities per request in `_meta`, mandates `server/discover`, returns `UnsupportedProtocolVersionError{supported, requested}` (−32022) and `MissingRequiredClientCapabilityError` (−32021), and documents a compatibility matrix in which era mismatches "fail" unless probed (S-153); ACP negotiates one integer major on `initialize` ("only bumped for breaking changes; non-breaking changes via capabilities"), treats omitted capabilities as UNSUPPORTED, reserves `_`-prefixed methods/values and requires unknown values to be preserved (S-035); A2A declares `protocol_version` per `AgentInterface`, `AgentExtension{uri, required}` per card, and requires a new URI for a breaking extension change (S-180; `extensions.md` L240–244). No audited implementation records the negotiated version or the peer's declared capabilities durably; OpenHands pins provider binaries and runs a CI drift check (S-110); Omnigent keeps a declared-vs-probed capability table (WS-A1 F3). Trust posture diverges across hosts (WS-E4 F5) while the program already has one scheme (ADR-0033/0034/0035) and one extension-trust record (WS-H5).

## Options considered

1. **Latest-version-wins with silent fallback** (the default of most SDKs). *Rejected:* silent downgrade is the T-LCD-11 failure signature for wire versions; results become incomparable across runs.
2. **Single pinned version per protocol, no legacy.** *Rejected:* the audited population lags every spec by a major (WS-E4 F6).
3. **Trust derived from the peer's own declarations** (annotations, `clientInfo`, `required`, scopes). *Rejected:* forbidden by the specs themselves and by ADR-0035 (the model never endorses; claims are not grants); the counter-examples in the audit are the failure modes.
4. **Chosen:** a per-edge `ProtocolBinding` runtime record with pinned support sets and probe-first negotiation, typed mismatch, `unknown` at analysis, byte-preserved unknowns, expiring eras; trust by attestation only, with claims feeding risk upward and approvals per `effect_id`.

## Decision

1. **`ProtocolBinding`** (runtime record, run-manifest member, referenced by `lifecycle.run.created`; not an IR entity): `{protocol ∈ {mcp, acp, a2a}, role ∈ {client, server, agent, peer}, spec_pin{version_label, schema_content_hash}, era ∈ {modern, legacy}, negotiated_version, peer_info: Implementation (claim), capabilities_declared: TypedValue (wire form, preserved), capabilities_observed: map<field, {supported, unsupported, unknown}>, extensions: [prefixed id], transport ∈ {stdio, streamable_http, jsonrpc_http, grpc, custom(uri)}, negotiated_at: EventRef}`. `spec_pin.schema_content_hash` enters the bundle derivation key (ADR-0021 (d)); bindings are generated from the three schema sources with CI drift checks (ADR-0021 decision 1).
2. **Negotiation rules.** (N1) Probe first, then pin: MCP `server/discover` before any other request on stdio; ACP `initialize` with the latest pinned version, accepting a lower version only if pinned; A2A first `supported_interfaces` entry whose `protocol_version` is pinned. (N2) A version or required extension outside the pinned set raises `ProtocolVersionMismatch{requested, supported}` / `RequiredExtensionUnsupported{uri}` — errors, never warnings or silent fallback. (N3) Wire "omitted = unsupported" is re-mapped to `unknown` at analysis for all three protocols (CF-027 generalised); the capability vector is `reconcile(capabilities_declared, probes)` (ADR-0013); DRIFT is symmetric and recorded as a fact about the peer version (OQ-034). (N4) Unknown `_meta` keys, `_`-prefixed values, unknown extension ids and unknown A2A metadata survive lower → lift byte-for-byte in `ext` (ADR-0015); this is the opposite default from the internal ecosystem boundary, which rejects unknown fields (WS-L1 §6.5 I2) — both correct at their layer (CF-209). (N5) Every legacy era, compatibility profile and vendor-extension shim carries an assumption-debt record whose removal test is keyed to the spec's deprecation window (T-LCD-05, reflexive).
3. **Trust rules** (application of ADR-0033/0034/0035 and WS-H5; no second scheme). (T1) Every peer is `unverified` until an attestation verifies under `TrustRootPolicy`: a foreign MCP server is an `ExtensionRecord{kind: mcp_server}` with a pinned, reviewed surface; an A2A card's JWS `signatures[]` is `Attestation{kind: signature}` with `subject = card content address`; an ACP agent binary is `pin`ned by content (OpenHands pinned-binary precedent); attestation failure ⇒ `quarantined`, never coerced to `external`. (T2) `ToolAnnotations`, ACP `PermissionOptionKind`, A2A `AgentExtension.required`, OAuth scopes, `clientInfo`/`serverInfo`/`info` and `peer_info` are `declared_claims`; the reference monitor never reads them; ADR-0031's `projected(declared)` may only raise risk. (T3) Peer text (`instructions`, descriptions, plan entries, agent/task messages) is `external` at best, rendered only under `role_map(external)`; per-item origin `tool(server_ref, inner_source)` is recorded on every lifted item (codex `ResourceOrigin` shape). (T4) Approval endorses one `effect_id` (ADR-0035); an `allow_always` selection or a client allowlist is a ledgered policy amendment with basis `approval`, scoped ≤ run unless a principal seals it (OQ-246); adapter-level auto-approval is inadmissible. (T5) Secrets never cross an edge in payloads: OAuth tokens are H3-mediated and keyed by issuer; MRTR `requestState` is an opaque blob; `x-mcp-header` mirroring and A2A push credentials are disabled unless sealed. (T6) Everything a peer contributes carries `taint ∋ extension_id`; a delegated child's outputs re-enter at `≤ delegate`.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: per-request version/capability carriage and typed mismatch errors (S-153 `schema.ts` L63–118, L440–530; `versioning.mdx` L50–167); ACP integer major + capability-only evolution and `_` reservation (S-035 `schema.json` `ProtocolVersion`; `initialization.mdx` L71–88; `extensibility.mdx`); A2A per-interface versioning and extension URI rule (S-180 `a2a.proto` L336–360, L424–435; `extensions.md` L240–244); dual-era clients (S-112, S-107); CI drift check (S-110 `check-acp-drift.py`); declared-vs-probed reconciliation (WS-A1 F3, S-118); hints untrusted by spec (S-153 L1912–1920); attestation-not-manifest rule (WS-H5 §6.3; in-toto/SLSA lineage); location-trust and auto-approve counter-examples (S-119 `mcp-tool.ts` L207–216; S-110 `acp_agent.py` L1579–1596); requestState as attacker-controlled (S-153 `mrtr.mdx` L232–242).
- (b) Source-code precedent: codex `codex-rs/rmcp-client/src/protocol_mode.rs` L9–47 @0735c51; goose `crates/goose/src/agents/mcp_client.rs` L700–735 @fae91d0 (lifecycle modes), `agents/extension_manager.rs` L349–392 (foreign `_meta` stripped); software-agent-sdk `openhands-sdk/openhands/sdk/settings/acp_providers.py` L166–310 (pinned binaries, `agent_name_patterns` as claims) and `clients/typescript/scripts/check-acp-drift.py` @3fc7b22; omnigent `omnigent/harness_capabilities.py` + `tests/harness_bench/verdict.py` (via ADR-0013); codex `codex-rs/codex-mcp/src/resource_origin.rs` L24–99 (per-item origin). The durable `ProtocolBinding` record and the unified negotiation/trust rule set across three protocols are `no-precedent / novel`.
- (c) Disconfirming evidence considered: (i) probe-first adds a round trip per connection — answered: `server/discover` results are cacheable for the server's lifetime (S-153 `versioning.mdx` L149) and ACP/A2A already negotiate once. (ii) Refusing silent fallback will reject peers other tools accept — answered: rejection is typed and actionable; a legacy pin can be added by editing the support set, which is data (MUST-data) and re-keys the bundle. (iii) Signature verification for A2A cards and MCP servers is rare in practice — answered: T1 degrades to hash `pin` + `unverified` class, which is exactly what the audited hosts effectively have, now made explicit and stratifiable (T-LCD-07). None overturns.
- (d) Conditionality: assumes WS-H5's `TrustRootPolicy`/`ExtensionRecord` and WS-H3 credential mediation exist at the tier where each transport is enabled; assumes WS-B1 accepts `protocol_bindings[]` in the run manifest (amendment-log entry); independent of model tier; no `provisional` result is load-bearing.
- (e) Build-stage assignment: **C0 / Stage 3** the `ProtocolBinding` schema, N1–N4 for MCP stdio, T1–T3 and T6 for MCP servers; **C1 / Stage 4** ACP negotiation, T4/T5 with H3/H7; **C2** A2A card signatures and `RequiredExtensionUnsupported`.

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-05 (reflexive debt on eras/shims), T-LCD-07 (declare/verify/stratify; `unknown` never coerced; DRIFT recorded), T-LCD-11 (typed mismatch; byte-preserved unknowns), T-LCD-06 (record is instrument-level; no IR field), T-LCD-15 (capability vector feeds admissible granularities). Does not address T-LCD-03/-04 directly. **ADR-0024 rung:** negotiation, attestation verification and mismatch typing are MUST-code; support sets, era pins, `TrustRootPolicy` rows and approval-persistence policy are MUST-data with `authority_cap` (widening a support set or a trust root by model/evolution edit is `AuthorityWidening`).

## Consequences

- WS-B1 adds `protocol_bindings: [ProtocolBinding]` to the run manifest; WS-I3 includes the pins in the bundle lock manifest (ADR-0038); WS-H6 attests binding records with chain heads.
- WS-J6's capability vector consumes `capabilities_declared/observed` directly; WS-J4 stratifies on `era` and `negotiated_version` where they differ across rows.
- WS-L6 must allocate the `_meta` prefix, the A2A extension URI and the `_hh/` method namespace together (OQ-068), since all three follow the same reverse-DNS grammar.
- WS-H3 owns OAuth issuer keying, PKCE/`iss` validation and token storage; WS-H7 owns approval persistence (OQ-246).

## Reversibility

**High** for support sets and eras (data); **medium** for the record shape (adding fields is a schema bump; removing the record orphans stratification of stored rows); **low** for "claims never decide" and "approval per `effect_id`" (shared with ADR-0031/0035).
