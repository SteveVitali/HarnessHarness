# ADR-0132 — Self-healing environments by declared policy, and the kill-point failure-injection battery as the one shared durability acceptance suite

**Status:** **ratified** (Phase 2 synthesis, 2026-09-10)
**Owner workstream(s):** WS-B3 (with WS-B5, WS-E5, WS-B2, WS-F2, WS-G2, WS-L2, WS-I2) · **Phase:** 2 · **Related:** ADR-0028 (AC-B1-2), ADR-0030, ADR-0031, ADR-0032, ADR-0040 (AC-L2-4), ADR-0045, ADR-0047 (veto invariants), ADR-0033, ADR-0016 (`EffectDomain`), ADR-0130, ADR-0131, WS-E5 ADR-1/-3, WS-H7 ADR-2; CF-280, CF-284; OQ-045 (final, WS-E5), OQ-090, OQ-095, OQ-252, OQ-315, OQ-317; R-2.2.3, R-2.2.5, R-2.5.5, R-2.9.x (evaluation plan)

## Context

Doc 2 §5.5 lists "self-healing environments" among the cloud-agent mechanisms and §11 Stage 3 demands "long-horizon failure injection". Managed Agents treats container death as a tool error and reprovisions from a recipe (S-047); Anthropic's long-running harness has the initializer write `init.sh` and re-run an end-to-end test (S-041); Symphony reuses preserved workspaces and cleans terminal ones at startup (S-108 §8.6/§14.3); Cursor checkpoints/forks VM images and names self-healing ("report when secrets are missing … autoinstall") as future work (S-052); Kubernetes controllers re-examine current state on restart rather than replaying events (S-426). Six Phase 1/2 dossiers each sketched a piece of the failure battery — WS-B1 AC-B1-2 (four kill points + mid-batch), WS-B2 AC-B2-01 (per-class duplicates), WS-F2 AC-F2-08 (re-arm), WS-E5 AC-E5-02(c)/-06/-09 (helper death, detached, dedup/probe), WS-G2 AC-G2-4 (completion gate over `unknown`), WS-L2 AC-L2-4 (exhaustion mid-effect) — and the program needs one matrix so `decompose-spec` gets one ticket and the Lab one instrument-charged suite. Environment loss must never be healed silently: reprovisioning can destroy uncommitted work and can loop.

## Options considered

1. **Environment healing as model behaviour only (prompted "re-run init if the environment is broken"), no kernel verification.** Rejected: the kernel cannot know whether the environment the model is acting on is the one the run's manifest names; the model-facing rule is kept, as a `HarnessRule` with a debt record.
2. **Automatic reprovision on any resume failure, unbounded.** Rejected: silent loss of uncommitted work; heal loops; violates "the model always sees what happened" (ADR-0030 inv. 4 spirit).
3. **Per-dossier batteries left separate.** Rejected: duplicated fixtures, inconsistent kill points, no single veto metric; the Decompose-Readiness Gate wants one acceptance suite per obligation.
4. **Kernel `verify_environment` on every resume; healing only under a declared `HealingPolicy` as a ledgered `reversible`/`workspace_local` effect with attendance-dependent defaults and a heal bound; one kill-point matrix × four risk classes with a duplicate-effect veto and class-scoped recovery metrics** — chosen.

## Decision

1. **Verification on resume is mandatory and read-only.** `verify_environment(run, lease, handle) → attached{helper_session, containment_report} | reattachable{helper_session} | lost{cause ∈ {helper_gone, image_missing, workspace_missing, lease_expired, containment_changed}}` runs for every environment handle in the checkpoint view before `Cue.resumed` is delivered; it compares the current state (WS-E5 `hello(resume_session_id)`, WS-B5 handle inspection, WS-H4 `ContainmentReport`) with the manifest's content-addressed `environment_ref` and the last `action.world_state.snapshot/patch`; it appends `action.environment.verified{handle, verdict, spec_ref, world_state_ref?}` (level-triggered; never trusts a stale in-memory handle).
2. **Healing is policy-bound and ledgered.** `HealingPolicy{on_lost ∈ {reprovision, snapshot_restore_then_reprovision, ask, fail}, max_heals, verify_after?: Ref<Validator>, preserve_detached: bool}` is MUST-data of the Harness Definition; defaults by manifest `attendance` (WS-H7): `interactive → ask`, `async | unattended → reprovision` (with `snapshot_restore_then_reprovision` when WS-B4/B5 snapshots exist). `heal(run, lease, handle, policy) → healed{new_handle, restored ∈ {full, snapshot{ref}, none}, lost_items_ref} | refused | ask{permission_id}`: reprovision is an ordinary effect `{domain: spawn_process | exec, reversibility: reversible, repeat_safety: idempotent, scope: workspace_local}` through the ADR-0030 lifecycle (Π-authorized; `committed` before dispatch), built from `environment_ref` and the definition's init procedure, followed by `action.environment.attached{handle, image_ref}` and `action.environment.healed{from_handle, to_handle, cause, restored, heal_no, verification_verdict}`; `lost_items_ref` (uncommitted files, unsnapshotted state, terminated detached children) is delivered to the model as an observation with `authority = environment` (ADR-0033) — never silently. `heal_no > max_heals` ⇒ `MaxHealsExceeded` ⇒ WS-F2 `stop{environment_lost}`. The model-side behaviour ("read progress file, re-run init, report missing secrets/blocked network") is a `HarnessRule` with an assumption-debt record (T-LCD-05) whose delivery/activation/following is measured (T-LCD-13).
3. **Detached children across kernel loss.** `preserve_until(ttl)` (WS-E5) requires `ttl ≥ writer_lease.ttl + recovery_grace` (OQ-252); on resume every `detached_effect_ids[]` entry in `committed` is reconciled by the resuming writer to `observed | unknown | terminated` via `list_detached`; `preserve_detached = false` in the healing policy terminates them before reprovision and lists them in `lost_items_ref`. Hibernation (OQ-095) is `env.reserved_ms` with `state = hibernated` on `action.environment.detached/attached`; no third counter.
4. **The kill-point matrix is the one shared battery.** Injected runtime death at KP-1 (after `intended`, before `decided`), KP-2 (after `decided{allow}`, before `prepared`), KP-3 (after `prepared`, before `committed`), KP-4 (after `committed` durable, before dispatch), KP-5 (during execution), KP-6 (after execution, before `observed` durable), KP-7 (after `observed` durable, before visible/charged), KP-8 (after visible, before the next `control.decision`), KP-9 (mid-batch append, torn tail), KP-10 (after `suspended`, before `lease.released`), KP-11 (after `occurred`, before `fired`), KP-12 (during `heal`, between the reprovision `committed` and `attached`), KP-13 (during `restore`, after `lifecycle.run.resumed`), KP-14 (in a child run while the parent is active), KP-15 (helper/executor death with the runtime alive) — each crossed with four probe tools: `read_only` counter read, `reversible` file edit with baseline, `compensable` external counter (`dedup_support ∈ {executor, none}`), `irreversible` external counter. Plus: stale-worker (pause past ttl, takeover, resume), duplicate-occurrence (N ≥ 3 deliveries through two racing wakeup services), and budget-exhaustion-mid-effect (AC-L2-4) cases. Oracle: the ADR-0130 recovery table and ADR-0031's per-class table. **Veto:** `duplicate_effect_count` (ADR-0047 "duplicate effect" veto invariant) must be 0 across the matrix; any `applied` twice for a compensable-with-dedup or irreversible tool fails the suite. Recovery metrics `recovery_latency_ms`, `wasted_calls`, `unknown_effects_per_resume`, `heal_count`, `wakeups_skipped{reason}` are `MetricDeclaration`s (ADR-0045) with `requires_observability ⊇ {events}`, `applies_to_classes = {native}` (hosted `n/a{observability}` unless `resume` is declared — T-LCD-07/-15), `charged_to = instrument` for the probe tools and the fault injector.
5. **Placement and ownership.** The battery runs in the Stage 3 evaluation suite with `search_budget`/`eval_budget` recorded (T-LCD-14) and is the single acceptance suite discharging AC-B1-2, AC-B2-01/-02/-06/-08, AC-F2-08, AC-E5-02(c)/-06/-09, AC-G2-4, AC-L2-4/-6 and AC-B3-01/-03/-04/-07/-09; each of those criteria names its (KP, class) cells; the fixture set (probe tools, fault injector, external counters) is one Lab component with `charged_to = instrument`.
6. **Contract surface:** `verify_environment, heal, reconcile_detached`; battery operations `inject(kill_point, target)`, `probe_counter(tool) → int`; failure modes `MaxHealsExceeded, ImageUnresolvable, PolicyDenied, HelperUnreachable`.

**T-LCD statement.** Satisfies T-LCD-05 (the model-side recovery rule carries a debt record and a removal test — "delete the init-rerun rule and re-run the matrix"), T-LCD-08 (`HealingPolicy` is a definition parameter; environment classes implement `verify` through the executor contract), T-LCD-12 (verification and healing use WS-E5's out-of-process helper protocol), T-LCD-13 (rule delivery/activation/following measured), T-LCD-14 (the battery is budgeted and instrument-charged), T-LCD-15 (recovery metrics class-scoped). Not applicable: T-01/-02/-03/-04/-06/-07/-09/-10/-11 (no model-facing surface, lowering or hosting change; the hosted `resume` declaration is ADR-0130's). ADR-0024 ladder: `HealingPolicy`, ttl/grace constants and the fixture catalogue are MUST-data; verification, the heal effect path and the injector are MUST-code.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** S-047 (container death as tool error; `provision({resources})` recipe), S-041 (`init.sh`, progress file, commit-as-clean-state, e2e test), S-052 (VM checkpoint/restore/fork; hibernate; self-healing as future work — negative for automatic healing), S-108 (workspace reuse; startup terminal cleanup; §9.5 workspace invariants), S-426 (level-triggered reconciliation), S-073 (`provisional`: four kill points, zero repeated actions — battery shape), S-197/S-198 (sagas coordinator checkpointing; leases — via ADR-0030/0032), S-201 (timeouts force retry; idempotent activities), S-116 (`orphan-process-journal.ts`; orphan reaping), ADR-0031 class table, ADR-0047 veto invariants.
- **(b) Source-code precedent:** symphony @e0ccc837 `SPEC.md` §8.6, §9.5, §14.3 and `orchestrator.ex` L1138–1177 (`cleanup_issue_workspace`, `run_terminal_workspace_cleanup`); prime-agent @427ea4c `packages/coding-agent/src/core/orphan-process-journal.ts` L1–50 (fsync'd child journal with start-id); codex @0735c519 `codex-rs/core/src/unified_exec/process_manager.rs` L560–600 (background processes owned and terminable — via WS-E5), `exec-server` `hello(resume_session_id)` (via WS-E5 F10); OpenHands @3fc7b221 `agent_server/event_service.py` L1161–1190 (restart backfill — via WS-B2); Logos kill-point protocol (paper, no source). Healing under a declared policy with a ledgered reprovision effect and a `lost_items_ref` observation is `no-precedent / novel`; the unified matrix is `no-precedent / novel` as an instrument.
- **(c) Disconfirming evidence considered:** Cursor calls self-healing future work and Managed Agents leaves retry to the model — automatic healing is therefore bounded (`max_heals`), attendance-gated (`ask` for interactive) and always observable; reprovision can destroy uncommitted work — `lost_items_ref` and snapshot-first restore address it and the model is told; a 15 × 4 matrix is expensive — it is instrument-charged, runs at Stage 3 on the reference harness only, and each cell is a fixture-level test not a benchmark run; Logos' numbers are `provisional` and used only for the shape. None overturns.
- **(d) Conditionality:** assumes WS-E5's helper protocol (`hello(resume_session_id)`, `list_detached`, `NotCommitted`) and WS-B5's content-addressed `environment_ref`; healing defaults depend on `attendance` (WS-H7); snapshot restore depends on WS-B4/B5 (C2) — without it `restored ∈ {full, none}` only; the matrix assumes ADR-0030/0031 semantics and a probe tool per class implemented as Lab fixtures; no model-tier dependence; task classes without an environment skip rows 12/15.
- **(e) Build-stage assignment:** C0 / Stage 2 (`verify_environment` on resume; detached reconciliation; `preserve_until` ttl rule) → C0 / Stage 3 (the kill-point matrix KP-1…9/13/15 × four classes, veto metric, recovery metrics — the shared battery) → C1 / Stage 2 (`HealingPolicy`, `heal` with reprovision, `lost_items_ref` observation, AC-B3-09; KP-10/11/12/14 as suspension/wakeup/goal features land) → C2 (snapshot-first restore with B4/B5; hibernation-aware leases).

## Consequences

- WS-B5 exposes handle inspection sufficient for `verify_environment` and a content-addressed `environment_ref` + init procedure reference in the manifest; WS-E5 honours the preserve-ttl rule.
- WS-B1 adds `action.environment.verified/healed` (CF-280); WS-H6 marks `healed` audit-grade; WS-I2 registers the recovery metrics and the veto.
- WS-G2's completion gate consumes `unknown_effects_per_resume` and `lost_items_ref` (a claim of completion over lost items is `hold`).
- WS-I3 may include the fixture catalogue (probe tools, injector) in the reproducible bundle as instrument members.
- `decompose-spec` receives one ticket for the battery with the cross-dossier AC list of decision 5.

## Reversibility

**high** for the battery (it is a test suite; cells can be added or removed without schema change) · **medium** for healing (a definition parameter and two event classes; removing automatic healing leaves `verify_environment` + `ask`/`fail`, which is the interactive default anyway).
