# ADR-0035 — Endorsement and declassification points (closed basis list; the model never endorses), provenance recording in the run ledger, and the seven-check minimal reference-monitor set

**Status:** **ratified, amended** (Phase 2 synthesis, 2026-09-10); previously: **ratified, amended** (Phase 1 synthesis, 2026-09-10)
**Owner workstream(s):** WS-L3 (consumers: WS-H1, WS-H2, WS-H5, WS-H6, WS-H7, WS-B1, WS-D1, WS-D4, WS-G1) · **Phase:** 1 · **Related:** ADR-0033/ADR-0034, ADR-0026/ADR-0029 (envelope, chain), ADR-0016 (`Permission`, `Validator`), ADR-0014, ADR-0002 (iii: no self-widening), ADR-0007 (T-LCD-12/-13/-14); CF-077; OQ-021, OQ-022, OQ-101/-06/-07; R-2.1.5, R-2.8.1, R-2.8.2, R-2.8.5, R-2.8.6, R-2.8.7

## Context

Doc 2 §5.6 fixes the principle — "the model can reason about permission, but it cannot grant itself permission … only the runtime can confer authority" — and lists what a reference monitor must know: provenance, capability scope, current policy, target effect, and declassification/approval points; it must *not* need task semantics. DLM's rule that only an owner can declassify its own policy, Flume's endpoint declassification by trusted processes, CaMeL's per-tool `Allowed/Denied` policies with a default deny, and Fides' explicit declassification policy over the labeled trace all put label increases behind a small, enumerated set of trusted operations. The escalation studies show what happens without one: content acquires authority by being copied into a memory file, a skill directory or a config file (S-103 X-CPE), and permission review keyed on risk alone did not stop 13/13 objectives (S-104). Anthropic's containment telemetry (S-053, ~93% approvals) bounds what a human approval may be taken to mean. WS-B1's envelope already carries `provenance?` and a hash chain; it lacks the rule for which classes must carry it and has two event-class names that collide with this scheme's vocabulary.

## Options considered

1. **Any principal with a higher class may relabel freely (implicit endorsement).** *Rejected:* unauditable; S-103's mechanisms are all implicit relabelings.
2. **Approval raises the authority of the content that motivated the action.** *Rejected:* approval fatigue (S-053) would launder injected instructions into `principal`-class memory; CaMeL/CapScope scope approval to one call.
3. **Open, pluggable endorsement bases (hooks may endorse).** *Rejected:* hooks and extensions are supply-chain dependencies (doc 2 §5.6; WS-H5) and would become the escape hatch; T-LCD-01's "no escape hatch" applies to authority.
4. **Monitor reads the model-facing text (provenance banners) to decide.** *Rejected:* "authority is not a string" (S-105, `provisional`) restates what capability security has held for decades; the monitor reads records only.
5. **Closed basis list with an endorser-class rule, every endorsement a ledger event, persistence-scope ceilings, mandatory provenance on content-bearing events, and a seven-check monitor (chosen).**

## Decision

1. **Endorsement events.** The only label increases are `security.label.endorsed{subject_ref, from: Label, to: Label, endorser: ProvenanceRecord, basis, basis_ref}` and `security.label.declassified{…}` (readers only). Validity condition: `authority(endorser) ≥ to.authority` **and** `basis` ∈ the closed list below; otherwise the append fails with `IllegitimateEndorsement`. An endorser with `origin ∈ {model, evolution, participant}` (class `delegate`) is never valid.
2. **Closed basis list.** `seal` (harness author at `seal` → `definition`; imported instructions/skills only with a `pin` attestation); `approval` (human principal endorses **one Effect intent** `(effect_id, args_canonical_hash)` — never content, never a class); `validator` (a deterministic `kernel` Validator endorses an `external` value validated against a **closed schema** declared in the sealed definition → `environment`; free text never — `BasisNotAllowed`); `promotion` (a human reviewer promotes a memory/procedure → `principal`/`definition`, WS-D4); `pin` (WS-H5 verified signature/hash → `definition` or `principal` per policy); `policy_rule` (the kernel executing a `HarnessRule` issued at `definition` declassifies readers to a named recipient set). Adding a basis is a dialect bump.
3. **Persistence-scope ceilings.** Writing to `scope = user` requires effective authority ≥ `principal` and an `approval`; `project` ≥ `principal`; `session`/`run` ≥ `delegate`; `definition` only via `seal`. The persisted label is `⊔(context_label, label(writer))`. Violations: `ScopeCeilingExceeded`.
4. **Ledger recording.** Provenance is **mandatory** on: `context.assembled` (per item, plus `context_label`), `context.artefact.delivered/activated/followed`, `context.memory.read/written/invalidated`, `context.observation.recorded`, `context.compaction.completed` (summary record with `derived_from`), `model.call.requested/completed`, `action.tool.proposed`, `action.effect.*`, `security.permission.*`, `security.label.*`, `security.extension.loaded` (pin attestation), `measurement.harness_edit.proposed` (`evolution`/`delegate`), `lifecycle.hosted.native_record` (`participant`/`unverified`), `lifecycle.ledger.redacted` (endorser). Optional elsewhere. Renames requested of WS-B1 (CF-077): `security.taint.applied/declassified` → `security.label.applied/endorsed/declassified`; `security.authority.granted/revoked` → `security.permission.granted/revoked` (they are authority-*handle* events). The ledger's per-run hash chain (ADR-0029) is the `hash_chain` attestation anchor for every stamped record; WS-H6's attestation over chain heads therefore attests provenance without a second mechanism.
5. **Minimal reference-monitor check set** for a proposal `p` from AgentProcess `A` in model call `c` (WS-H1 implements 1, 2, 4, 5, 6, 7 at C0; WS-H2 adds 3 and the taint component of 4 at C2):
   1. *Authority of proposal* — `eff = min(authority(A), context_label(c).authority)`; `A` at `delegate` may only propose; conferral requires a valid `Permission` with `issuer.authority ≥ principal`.
   2. *Grant coverage and permission validity* — `EffectClass(p)` covered by `grants(Permission(A))` by domain + scope (attributes only narrow); the Permission is `valid` at `c`.
   3. *Flow (C2)* — for `world = open` effects and domains `net_egress`, `message_human`, `spend`: `readers(args) ⊇ destination principals` unless declassified by `policy_rule`/`principal`.
   4. *Taint gate* — if `eff ≤ external` or `taint(p) ≠ ∅`, and `EffectClass(p)` is not (`read_only ∧ closed`): decide by the policy table `Π(EffectClass, eff) → allow | ask | deny` (owned by WS-H1/H7, OQ-101); `ask` resolves only through an `approval` endorsement of this `effect_id`.
   5. *Endorsement legitimacy* — as in (1) above; checked at append.
   6. *Persistence ceiling* — as in (3) above.
   7. *Delegation attenuation* — at spawn: child ceiling ≤ `eff`, child `Permission ⊆` parent's, child `Budget ≤` parent's.
   The monitor reads records only; model-authored `risk_assessment` (WS-A3) and judge verdicts may feed Π as inputs but never change a class.

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-12 (checks are operations over records; implementable out-of-process, as Flume's user-level monitor), T-LCD-13 (delivered events carry provenance; endorsement events are separately observable), T-LCD-14 (approvals are a counted, budgeted resource so policies compare under matched budgets), T-LCD-06/-15 (hosted rows carry `participant` provenance; per-item checks on hosted content render `n/a` where observability lacks them). Not applicable: T-LCD-01/-02/-03/-04/-05/-07/-08/-09/-10/-11.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** "only the owner can declassify its own policy" — DLM (S-218, Tier A); declassification at trusted endpoints, untrusted processes compute, user-level reference monitor — Flume (S-219, Tier A); deterministic per-tool policies with default deny; state-changing tools denied when depending on non-public values; `send_email` allowed only if recipients are trusted or readers cover body/subject/attachments — CaMeL (S-099); explicit declassification policy over the labeled trace; product with an output-type lattice for quarantined outputs — Fides (S-101); "the model may propose … only the runtime can confer authority"; monitor needs provenance, capability scope, policy, target effect, approval points — doc 2 §5.6 (S-130) with CapScope (S-105, `provisional`) as fresh corroboration; ~93% approvals bound the meaning of approval — S-053 (Tier B); cross-scope persistence as attack — S-103 (`provisional (mech)`), corroborated in source (Claude SDK scope destinations; Codex/OpenHands memory loading); revocation must be enforced in the retrieval/control layer — S-106 (`provisional (mech)`); authority anchored on verified signer — in-toto/SLSA (S-222/-08); MCP annotations are hints (S-153); permission elicitation as a protocol verb — ACP (S-035).
- **(b) Source-code precedent:** `camel-prompt-injection/src/camel/security_policy.py` L44–96 (`SecurityPolicyEngine.check_policy`: no-side-effect exemption, deny-on-private-dependencies, ordered policies, default deny), `src/camel/pipeline_elements/security_policies/workspace.py` L70–130 (`send_email_policy`, `delete_email_policy`), `src/camel/quarantined_llm.py` L37–103 (schema-forced extraction with refusal); `fides/Tutorial.ipynb` cells 33–34 (`policy_no_untrusted_url`, `policy_no_untrusted_declassification`); `software-agent-sdk/openhands-sdk/openhands/sdk/security/confirmation_policy.py` (`ConfirmRisky` — the risk-only counter-example that S-104 defeats); `codex/codex-rs/protocol/src/protocol.rs` L988–1000 (`AskForApproval::UnlessTrusted` — scope trust switching approval policy); `agent-client-protocol/schema/v2/schema.json` (`RequestPermissionRequest/Subject/Option`); `claude-agent-sdk-python/src/claude_agent_sdk/types.py` L109–140 (`PermissionUpdate` writable to `userSettings/projectSettings/localSettings/session` — the write targets the ceilings govern). The closed basis list with an endorser-class rule recorded as ledger events, and the seven-check set as a contract, are `no-precedent / novel` as an integrated design.
- **(c) Disconfirming evidence considered:** approval fatigue makes approval a weak endorsement (S-053) — accepted; approval endorses one effect only and is a budgeted resource; per-tool policies are burdensome (S-099) — absorbed by keying Π on `EffectClass` rather than tool names; a closed basis list may be too rigid for WS-H5/H7 — absorbed by dialect-bump extension rather than an open hook; the risk-based confirmation pattern is what production ships (OpenHands, Codex) — S-104 shows it insufficient alone, and risk remains an input to Π; the monitor's checks add latency per proposal — the checks are record comparisons over small sets (CaMeL notes constant-time policy evaluation to avoid side channels). None overturns.
- **(d) Conditionality:** independent of model tier and task class. Assumes a human principal is reachable for `ask` (unattended runs must configure Π without `ask`, i.e. deny or pre-approved grants — S-104's scheduled-task vector); assumes `EffectClass` declarations on capabilities (WS-A3); the cost/benefit of the taint gate is a Stage 3 measurement.
- **(e) Build-stage assignment:** C0 / Stage 1 (ledger stamping rule; checks 1, 2, 5, 7 in WS-H1's kernel; `seal` basis); C0 / Stage 2 (`approval`, `promotion`, ceilings, check 6; audit chain anchor with WS-H6); C2 (check 3, taint component of 4, `validator` shape endorsement, `pin` via WS-H5, `policy_rule` declassification via WS-H2).

## Consequences

- WS-H1's kernel exposes `authorize(p) → allow | ask(effect_id) | deny(reason)` built from checks 1–7 and treats Π as configuration with an assumption-debt record if it is model-conditioned (T-LCD-05).
- WS-H7 owns the cadence and UX of `ask` and reports approval counts per configuration (T-LCD-14).
- WS-H5 supplies `pin` attestations; WS-H6 attests chain heads; WS-B1 applies the mandatory-provenance table and the renames; WS-D4 implements `promotion`; WS-G1 supplies `validator` endorsement for closed schemas; WS-D1 refuses to render items above their slot ceiling and records `context_label`.
- Every "trusted" configuration directory, memory file or skill in a later dossier must name its endorsement basis or be `external`.

## Reversibility

**Low-to-medium.** The basis list can grow by dialect bump; removing the endorser-class rule or the model-never-endorses rule after Stage 2 would silently reopen X-CPE and the evolution self-widening path (ADR-0002 iii), so those two rules are load-bearing and should be treated as constitutional.
