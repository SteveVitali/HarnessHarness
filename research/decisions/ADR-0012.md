# ADR-0012 — Ontology v1: two levels, planes as a partition with a home-plane rule, two boundaries, control boundary β, compatibility surface as a derived view

**Status:** **ratified, amended** (Phase 1 synthesis, 2026-09-10)
**Owner workstream(s):** WS-A2 (with WS-A3 for typed forms, WS-B1 for event stamps) · **Phase:** 1 · **Related:** ADR-0001, ADR-0004, ADR-0006 (novelty claim a), ADR-0007 (T-LCD-05/-06/-07/-09/-14/-15), ADR-0008 (vocabulary), ADR-0011 (name); CF-005, CF-020, CF-021, CF-026/-05/-06/-07/-08, CF-034/-04, CF-059; OQ-018, OQ-019, OQ-048/-03/-04/-05; R-2.1.1 (constrains R-2.1.2, R-2.9.2, R-2.10.4)

## Context

Spec §2 needs one vocabulary and one formal model that every other section can resolve symbols against. Ontology v0/v0.1 supplied definitions and names but left four things informal: what a "plane" *is* (doc 2 §4 calls the seven planes "a synthesis rather than a claim that the field has standardized"); where the doc 3 §2.3 "Model plane" fits; what object the "moving boundary of control" (doc 2 §9) names; and whether π_system, the compatibility surface, and the capability vector are stored entities or derived views. Concurrent Phase 1 dossiers now make these decisions urgent: WS-B1 stamps an eight-value `plane` on every event, WS-A3 asks for two register amendments, WS-A5 keys slots by component class, and WS-J-track work will key results by whatever "configuration" and "granularity" mean.

## Options considered

1. **Planes as architectural layers with a dependency direction (P1 → … → P7).** Rejected: the same mechanism recurs in different layers of different systems (memory is P1 for AIOS's `ContextInjector` and P5 for OpenHands' event log; compaction is a P1 policy with a P5 event), so a layering forces arbitrary placements; the build DAG is already by tier.
2. **Eight planes (add a Model plane per doc 3 §2.3).** Rejected: in every audited runtime the corresponding objects sit *at the boundary* between harness and model (AIOS `LLMAdapter` behind a syscall queue; Omnigent `Executor.run_turn`; Cloudflare "model execution" inside the harness); a plane answers a responsibility question, and "how do we call the model" is not one — it is the crossing point of `propose`. An Environment plane would follow by the same logic, and the count would never stabilize.
3. **Collapse planes into WS-A5's component classes (no plane concept).** Rejected: the novelty claim (a) in ADR-0006 ("first IR spanning all seven planes") and the LCD battery need a classification independent of the current class list; classes are the *implementation* of plane responsibilities.
4. **One flat ontology (harness and lab in one namespace).** Rejected: this is how the "meta-harness" name collision (CF-013) arose; Harbor `JobConfig` and HAL's runner live entirely at the instrument level and know nothing of planes, while the AIOS kernel knows nothing of experiments — the levels exist in every precedent implicitly.
5. **Store the compatibility surface as a first-class entity.** Rejected: the factor space is mostly categorical and model snapshots churn faster than a surface can be fitted (S-047, S-096); a stored surface would be stale truth. It is a derived view whose only persisted form is a fitted-surface report with expiry.
6. **Chosen:** two levels; planes as a partition with a total home-plane rule; two first-class boundaries with boundary components; the control boundary β as a typed element of θ; compatibility surface as a derived response surface; an explicit first-class/derived/report split; the CF-020/CF-021 dispositions and the WS-A3/WS-B1 amendments.

## Decision

1. **Two levels.** Every ontology term belongs to exactly one of *object level* (a harness: planes, boundaries, entities, artifacts, component classes/variants, θ, harness step, π_system) or *instrument level* (the Harness Lab: participants, descriptors, configurations, arms, runs and the run envelope, metrics/MetricDeclarations, conformance records, fitted-surface reports, Hosting ABI). The evolution service is an object-level P7 component that calls the instrument (ADR-0002).
2. **Planes are a partition with a home-plane rule.** P1–P7 keep their v0 names, core questions, mechanisms and failures. Every IR entity kind (`typed-by: WS-A3`), component class (WS-A5), plane operator and event family (WS-B1) declares exactly one `home ∈ {P1..P7} ∪ {model_boundary, environment_boundary} ∪ {run_lifecycle}`; `classify_home` is total over registered kinds and `UnclassifiedKind` is a schema error. Planes carry no dependency direction. Adding a plane or boundary requires an ADR (OQ-052).
3. **Two boundaries, not an eighth plane.** The **model boundary** (M | H) and **environment boundary** (H | E) are first-class; boundary components (model gateway, router, Profile Compiler, cache, interposition; environment/sandbox handle, effect capture, egress mediation) have a home *boundary*. Doc 3 §2.3 "Model plane" is a scope-catalogue grouping (CF-026). WS-B1's event `plane` values map `model → model_boundary`, `lifecycle → run_lifecycle` (CF-030); identifiers unchanged.
4. **Cross-cutting properties are mandatory attributes**, never planes: `resource` (dims WS-L2), `provenance{origin, version, authority_class}` (scheme WS-L3/CF-006), `conditioning{semantic_id, surface_owner}` (WS-A3 surface record).
5. **Formal model for Spec §2.3.** M is a *model snapshot* (amends v0 "frozen model", CF-033); a configuration names a *model set* with roles (OQ-048). θ = (h, p, β, π_pol). The harness step is the composition of plane operators `render, propose, interpret, authorize, execute, verify, persist, decide` with `observe` recording every step; π_system = H_{θ,E,B}[π_M] is the induced closed loop; J is the v0 objective; the **harness effect** Δ is always paired at matched B (T-LCD-14). The formalism fixes what is held constant and what is varied; the runtime never computes it.
6. **Control boundary β ∈ θ.** Decision points Δ = HIR/1 `DecisionPoint = {plan, act, retrieve, compact, verify, delegate, authorize, retry, stop, escalate}` (the union of WS-A2's and WS-A3's initial sets; closed, extended only by dialect bump — CF-107, OQ-062); β : Δ → {code, model, human} with guards; a `component-level` factor; observable in trajectories (code-owned steps have no model call). The v0 design principle is β's *default*, and CF-005 remains a Lab comparison target. Representation in HIR is OQ-051 (WS-A3).
7. **Compatibility surface = derived view.** Ψ_θ : F → Dist(Δ) over a mixed, mostly categorical factor space; estimated by designed experiment; persisted only as `FittedSurfaceReport{…, configuration_ids[], expiry_condition}`; `fit_surface` refuses `UnknownLevel`; model form is WS-J4's (OQ-050). Portability = sign-stability along the model axis; conditionality = the region where Δ > 0 with stated confidence.
8. **First-class vs derived vs report** per `ontology-v1-proposal.md` §4g. Derived views (π_system, Ψ_θ, capability vector, scorecard values, compliance rates, opacity ratio) are never stored as truth.
9. **Vocabulary dispositions.** CF-020: *capability declaration* and *capability vector* stay distinct with `vector = reconcile(declaration, probes)`. CF-021: enum values renamed `{component-level, configuration-level, product-level}`. CF-034: *surface vs semantic identity* reworded to "identity over the semantic projection". CF-037: no bare *capability* in spec prose. CF-059: `ledger ∈ observability_level ⇔ class = native` (derived, never declared). CF-032: prose *artifact*, identifiers *artefact*. **Added at synthesis:** CF-054 — the *Harness Definition* row reads "names component variants, parameters and policies, and *may constrain* profiles" (profile is a configuration coordinate); CF-084 — *capability declaration* is "a versioned record; the run manifest pins one `version_id`"; CF-049 — conditioned rules have two homes (`HarnessRule.conditioned_on` in the definition, `ProfileRule` in the profile) and one `AssumptionDebtRecord`; CF-094 — the ADR-0045 `MetricDeclaration` is the single full form and `applies_to` is retired; CF-100 — *opacity ratio* names the pair `opacity_ratio` (static) / `opacity_dynamic`; CF-095 — κ's `seed` coordinate is read as the replicate axis; CF-101 — the compliance-chain identifiers are `context.artefact.delivered/activated` (P1) and `verification.artefact.followed` (P4).

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-06 (no HIR→ABI edge; boundaries and levels make it checkable), T-LCD-07 (declaration/vector relation; `unknown` never coerced), T-LCD-09 (β and the factor tuple are explicit factors), T-LCD-14 (harness effect is defined only at matched B), T-LCD-15 (levels + admissible granularities), T-LCD-05 reflexively (fitted-surface reports expire). Does not itself satisfy T-LCD-01/-02/-03/-04/-10/-11 (WS-A3/A4) or T-LCD-13 (ADR-0014). No "does not" without a mitigating owner.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: every industrial decomposition is a strict subset of the seven planes and all omit P4 (verification) and treat P7 as telemetry — AIOS S-030/S-031, LangChain S-045, Cloudflare S-056, Harness-Bench S-062 (WS-A2 F1); the model call sits at a boundary in source (F2); decision-point ownership is already marked in trajectories (Harbor ATIF `llm_call_count == 0`, Omnigent `handles_tools_internally`, OpenHands `ActionEvent.security_risk` — F3); response-surface methodology is the Tier-A lineage for interaction effects over designed factors (S-167), and the field's own demand is "interaction effects, not single-axis leaderboards" (doc 2 §1); effects are model- and window-conditioned (S-072, S-062, S-088 — `provisional`, corroborating only); the two-level split is implicit in Harbor `JobConfig` vs the AIOS kernel (F7).
- (b) Source-code precedent: `AIOS/aios/scheduler/fifo_scheduler.py`, `aios/syscall/syscall.py`, `aios/memory/context_injector.py` (planes present/absent; model boundary as a syscall); `omnigent/omnigent/inner/executor.py` (`Executor.run_turn`, `handles_tools_internally`); `harbor/src/harbor/models/trajectories/step.py` (`llm_call_count == 0` ⇒ deterministic dispatch); `software-agent-sdk/openhands-sdk/openhands/sdk/event/llm_convertible/action.py` (`security_risk`, `critic_result`); `harbor/src/harbor/agents/base.py` + Harbor job config (instrument level). Precedent status: seven planes as a total classification — `novel as a classification` (partial precedent: every decomposition is a subset); β as a typed factor — `novel` (trajectory-level precedents only); two-level split — `no-precedent / novel` as an explicit statement; surface — `renamed` (RSM applied to configurations).
- (c) Disconfirming evidence considered: no source uses exactly seven planes and several mechanisms straddle two (memory, compaction, permissions) — absorbed by the home-plane rule and typed cross-plane edges; π_M is nonstationary and multi-model (S-047; S-096) — absorbed by *model snapshot* + *model set* and by never computing π_system; RSM assumes continuous factors — absorbed by the mixed factor space, `UnknownLevel`, and expiry; S-147 argues the instrument *is* the harness (against two levels) — `provisional` and contradicted at matched budget by S-083/S-075/S-091 (CF-004); the categorical-architecture formalism (S-169, `provisional`) is an adjacent competitor that types composition but not provenance, budget, validity or the instrument level — not adopted, not contradicted.
- (d) Conditionality: independent of model tier and task class (it is a classification and a factor tuple, not a performance claim); assumes model snapshot identity is at least *declarable* per configuration (drift is then detectable, not assumed absent); assumes the Lab can vary β only for native participants (hosted participants expose β only through the ABI's settable coordinates).
- (e) Build-stage assignment: C0 / Stage 1 — Spec §2 text, the `home` classification table, the configuration tuple, β *representable*; C0 / Stage 3 — β *variable* (WS-F1), harness effect with the matched-budget precondition; C2 / Stage 3–4 — fitted-surface reports (WS-J4).

## Consequences

- Spec §2 carries the two-level statement, the plane table, the boundary table, the attribute table, the formal model and the first-class/derived split; every symbol used elsewhere (κ, B, β, Δ, Ψ) resolves to §2 (AC-A2-1/-2).
- WS-A3 adds `home` to every entity kind and decides β's representation (OQ-051); WS-A5 adds `home` to every component class; WS-B1 registers the `plane` mapping and derives the `ledger` stamp; WS-J3/J4 use `{component-level, configuration-level, product-level}` and `fit_surface`; WS-C1 documents gateway/router/Profile Compiler as boundary components.
- `ontology.md` §1–§4 is replaced by `ontology-v1-proposal.md`; §5–§6 receive the amendments in its §4h.
- A future mechanism with no home plane triggers an ADR, not a "misc" column.

## Reversibility

**Medium.** Renaming granularity values and adding `home` fields are cheap schema edits. Reversing the two-level split or the boundary decision after Spec §2 is written would ripple through every section's vocabulary (a Phase 5 rewrite), and reversing "surface = derived view" would require a storage design and a staleness policy that do not exist. β can be demoted to a derived view at low cost if WS-A3 finds per-step ownership fields sufficient (OQ-051).
