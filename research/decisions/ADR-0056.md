# ADR-0056 — The flow-policy language: a closed, quantifier-free, non-recursive, total predicate language over labels × canonical arguments × effect projection; evaluation order; exact policy-edit classification; model-drafted policies narrowing-only

**Status:** **ratified** (Phase 2 synthesis, 2026-09-10)
**Owner workstream(s):** WS-H2 (consumers: WS-H1, WS-H7, WS-A3, WS-A5, WS-I5, WS-I6, WS-G1, WS-J3) · **Phase:** 2 · **Related:** ADR-0016 (`HarnessRule.action` closed sum — extension requested, CF-123), ADR-0017 (`HirDiff.classification.authority_delta`), ADR-0022 (`SurfaceArgMap`), ADR-0024 (policy-leaf interpreters are MUST-code; rules MUST-data), ADR-0026 (`project()` views), ADR-0035 (Π; check ordering), ADR-0002 (iii), ADR-0007 (T-LCD-01/-05/-10/-12); CF-123/-06; OQ-101 (Π default rows remain H1/H7's), OQ-141; R-2.8.2, R-2.8.1

## Context

The brief asks for "policy language expressiveness vs decidability". The audit found that every flow policy shipped in source is one of four predicate shapes (trusted parameter, reader coverage, public-only, ambient-dependency denial — CaMeL `security_policy.py`, `slack.py`, `banking.py`) plus a content predicate and a history predicate (Fides cells 29/33), and that the 2025–2026 systems add argument conditions with a fallback (Progent), history predicates over committed effects (APPA) and per-argument roles (PACT). None needs recursion, unbounded quantification or task semantics. CaMeL's policies are arbitrary code ("users needing to codify and specify security policies and maintain them"); Progent's are JSON-Schema rules whose *edits* an SMT solver classifies as narrowing (auto-applied) or expansion (approval). Cedar shows that a language restricted to no recursion, no unbounded loops, no user functions, bounded set operations and total semantics keeps constant-time operators, linear evaluation and a sound and complete SMT encoding — "the first of its kind for a non-trivial policy language" precisely because of those controls. Datalog/Rego terminates but does not yield exact edit classification. HarnessHarness needs the classification: ADR-0002 (iii) and ADR-0017 already say a widening diff is unacceptable in evolution contexts, which is only checkable if the policy language is analyzable.

## Options considered

1. **Arbitrary code policies (CaMeL).** *Rejected:* non-total, unanalyzable, an escape hatch on authority (T-LCD-01 in policy form); code enters a definition only as `CompiledPayload` behind a declared interface (ADR-0024), and a policy's "interface" is exactly the language below.
2. **Datalog/Rego-class recursive rules.** *Rejected:* recursion is unnecessary — the transitive relation IFC needs ("who influenced this value") is materialized in the label by the join; recursion forfeits exact narrowing/widening classification; transitive ledger queries belong to Lab analyses over `project()` views.
3. **Natural-language policies evaluated by a model.** *Rejected as enforcement:* `delegate` authority, non-deterministic; admissible only as an advisory `Validator{kind: judge}` row.
4. **Progent-style LLM-generated policies with SMT-classified updates, including approved expansions.** *Adopted in its narrowing half only*: an expansion is a `HirDiff` with `authority_delta = widening` and follows ADR-0017 (human origin; rejected in evolution contexts) — never an in-run approval.
5. **A closed, quantifier-free, non-recursive, total predicate language over three finite domains with a fixed evaluation order and an exact edit classifier (chosen).**

## Decision

1. **Where policies live.** A flow policy is a `HarnessRule` with action `flow_policy(FlowPolicy)` issued at authority ≥ `definition` (CF-123: dialect bump adding `flow_policy`, `declassify`, `sanitize` action kinds — `ext` may not decide authority). `FlowPolicy{policy_id, issuer, scope, rules: [FlowRule]}`; `FlowRule{selector{effect_class?, capability?, params?}, condition, decision ∈ {deny, allow, declassify(readers_to), sanitize(sanitizer_ref, param)}, remedies_hint?}`.
2. **Domains (finite, per proposal `p` in run `r`):** (i) labels — `L(p)`, `L⁺(p)`, `L(param)` for each capability parameter (through `SurfaceArgMap`, never surface fields); (ii) canonical arguments by parameter; (iii) the effect projection `project(r, effects, until_seq)` = the finite set of committed `(EffectClass, args_canonical_hash, phase)`.
3. **Atoms:** `authority(x) ≥ c`; `taint(x) ⊆ T`; `taint(x) = ∅`; `readers(x) ⊇ recipients(p)`; `readers(x) = Public`; `arg(param) {=, ∈, like, <, ≤} literal`; `EffectClass(p) matches pattern`; `committed(EffectClassPattern, arg-pattern)`; `count(committed(…)) ≤ n`; `detector(validator_ref, param)` for a deterministic kernel `Validator` (URL/secret-pattern detectors). **Connectives:** `∧ ∨ ¬`. **Iteration:** only the built-in `∀ param ∈ params(p)` and `∀ e ∈ effects(r)` (finite, linear). **No** variables beyond `p`, no user functions, no recursion, no string concatenation, no arithmetic beyond comparison and bounded counts.
4. **Semantics:** total — any evaluation error (undeclared parameter, missing field, detector failure) makes the rule evaluate to `deny(EvaluationError)`; **order:** all `deny` rules, then `allow`/`declassify`/`sanitize` rules, then Π's default row for `(EffectClass, effective_authority, taint ≠ ∅)`; first match wins within a tier; no match ⇒ Π default; **complexity:** linear in `|params| + |rules| + |effects(r)|`, constant time per atom over small sets; evaluators must be constant-time per atom (no early exit on secret-dependent data) to avoid a policy-timing channel; implementable out-of-process over the canonical encoding.
5. **Analyzability and edits.** `classify_policy_edit(P, P′) → narrowing | widening | incomparable` is exact (`narrowing ⇔ ∀p. allowed(P′, p) ⇒ allowed(P, p)`), computed by a sound and complete encoding into a decidable logic or by an equivalent syntactic subsumption procedure (OQ-141); it feeds `HirDiff.classification.authority_delta` for `flow_policy` ops. A `delegate`-origin edit (model, evolution, hosted) applies iff `narrowing`; otherwise it is a widening diff under ADR-0017. Two policies with `incomparable` edits are treated as widening.
6. **Expressiveness ceiling stated:** the language must express every policy in the audited corpus (AC-H2-8 round-trip: CaMeL suite policies, Fides notebook policies, Progent rule shapes, APPA history predicates, PACT argument roles); anything beyond it is either a Lab analysis or a kernel `Validator` referenced by `detector(...)` with its own declared interface.

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-01 (no escape hatch: no code in a rule; detectors are declared Validators), T-LCD-05 (a rule with `conditioned_on` needs a debt record; Π rows conditioned on a profile likewise), T-LCD-10 (rules bind to capability parameters and `EffectClass`, never to surface names — renaming a tool changes no rule), T-LCD-12 (the evaluator and classifier are operations over records; out-of-process), T-LCD-14 (policy variants are compared under `MatchSpec` in AC-H2-10). Not applicable: T-LCD-02/-03/-04/-06/-07/-08/-09/-11/-13/-15. ADR-0024 rung: rules are MUST-data (conditioned rules, parameters); the evaluator and classifier are MUST-code policy-leaf interpreters.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** restricted expressiveness ⇒ linear evaluation + sound and complete SMT encoding enabling equivalence/subsumption/vacuity analysis; default deny; forbid overrides permit — Cedar (S-269, Tier A); Datalog terminates but recursion is not needed and costs analyzability — OPA/Rego (S-270, Tier B); JSON-Schema rules with SMT-classified narrowing vs expansion, "every security decision is deterministic" — Progent (S-262, 2025, single team); ordered per-tool policies with default deny and a no-side-effect exemption — CaMeL (S-099/S-100); policy as a predicate over the labeled trace — Fides (S-101/S-102); history predicates over committed effects and finite recovery — APPA (S-258, `provisional`); argument roles — PACT (S-261, `provisional`); constant-time policy evaluation to avoid side channels — CaMeL (S-099); widening diffs unacceptable in evolution contexts — ADR-0002 (iii), ADR-0017.
- **(b) Source-code precedent:** `camel-prompt-injection/src/camel/security_policy.py` L77–96 (evaluation order, default deny), `pipeline_elements/security_policies/{slack.py L35–99, banking.py L37–120, agentdojo_security_policies.py L47–54}` (the four rule shapes), `capabilities/utils.py` L15–37; `fides/Tutorial.ipynb` cells 29, 33–36 (`Policy = f(trace)`, content predicate, declassification predicate). The closed language, its totality rule and the edit classifier as a kernel operation: `no-precedent / novel` in the agent-security corpus (Cedar is the precedent outside it).
- **(c) Disconfirming evidence considered:** a closed language cannot express transitive relations — unnecessary (labels materialize provenance) and available as Lab analysis; policy authoring burden remains (S-099) — bounded by keying rules on `EffectClass` and capability parameters with Π defaults, and by admitting model-*drafted* narrowing rules; exact classification may need an SMT backend at Stage 3 — the contract admits a syntactic subsumption implementation for the fragment actually used (OQ-141); the adaptive-evaluation study warns that symbolic privilege rules can be evaded by "policy-disguise" attacks (S-259) — its one experiment showed the Progent gate held, and rules here bind to canonical parameters and labels, not to surface text. None overturns.
- **(d) Conditionality:** independent of model tier; assumes capability parameters are declared (E1) and `SurfaceArgMap` exists (ADR-0022); assumes reader/taint universes and the effect projection are finite per run (true for native participants; hosted participants supply `n/a`).
- **(e) Build-stage assignment:** **C2 / Stage 3** (evaluator, classifier, corpus round-trip AC-H2-8/-9); the `HarnessRule.action` dialect bump is a **C0 / Stage 1** schema change owned by WS-A3 (CF-123) that costs nothing until C2 uses it.

## Consequences

- WS-A3 bumps the HIR dialect to add the three action kinds; WS-A5 validates `flow_policy` rules at `seal` (rejecting recursion/code); WS-H1 evaluates Π after the rule tiers; WS-I5/I6 treat policy edits as `HirDiff` ops with `authority_delta` from the classifier; WS-G1 registers content detectors as deterministic Validators; WS-J3 varies policy sets as arms under `MatchSpec`.
- Any future "richer" policy need is met by a declared Validator (`detector`) or by a dialect bump that must preserve totality and analyzability — never by opening the language.

## Reversibility

**Medium.** Rules are data; the language can grow by dialect bump (adding atoms preserves analyzability if each atom is decidable over a finite domain). Opening it to recursion or code after Stage 3 loses exact edit classification and therefore the evolution-safety guarantee of ADR-0002 (iii) — that is the load-bearing restriction.
