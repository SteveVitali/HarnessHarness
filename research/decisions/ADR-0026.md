# ADR-0026 — The run ledger is the sole authoritative record; views are derived; event sourcing is selective; one fenced writer per run (resolves OQ-003, OQ-042 parts 1–2)

**Status:** **ratified, amended** (Phase 1 synthesis, 2026-09-10)
**Owner workstream(s):** WS-B1 (with WS-B2 for lease semantics, WS-B3 for recovery, WS-D1 for the context view, WS-H6 for audit) · **Phase:** 1 · **Related:** ADR-0001, ADR-0003, ADR-0004, ADR-0005, ADR-0007 (T-LCD-13/-15), ADR-0009 (WS-L1 inputs); OQ-003, OQ-042, OQ-080, OQ-085; CF-057, CF-059; R-2.2.1, R-2.8.6, R-2.9.1, R-2.10.5; ADR-0027/ADR-0028/ADR-0029, ADR-0030

## Context

Doc 2 §11 instructs "use event sourcing selectively, not dogmatically: the append-only event log should be the authoritative record of decisions and effects, while compact materialized views serve fast context/retrieval; do not force every large artifact into the event stream; store content-addressed artifact references instead." Doc 3 §8 registers the boundary as OQ-003 and WS-L1 needs the answer (OQ-042) before any ecosystem can be ratified. HarnessHarness's purpose is instrument validity (ADR-0003): ablation, attribution, audit (R-2.8.6 "deep audit trails at all levels", C0/Must) and results (R-2.9.1) all need a fine-grained, non-rewritable record of what each component decided and did. Five audited harnesses converge on an append-only record but differ on unit, persistence policy and whether history may be rewritten (WS-B1 §4a F1–F4).

## Options considered

1. **Mutable session state + history table** (goose `sessions/messages`, opencode `session/message/part` rows; Kiehl's "history table gets 80% of the value"). *Rejected:* both audited systems needed destructive paths (`DELETE FROM messages`, `removeMessage`) that lose the audit record; a message table cannot carry effect phases, permission decisions, or artifact delivery/activation — T-LCD-13 and H6 become unimplementable.
2. **Snapshot-per-step with history** (LangGraph checkpoints, S-143). *Rejected:* snapshots record states, not decisions; component-level attribution needs the transitions; snapshot size grows with state, not with information.
3. **Dogmatic event sourcing** (every fact including environment state, deltas and payloads in the stream). *Rejected:* the transcript becomes the database (Kiehl S-195; Fowler's external-gateway problem); Codex's persistence policy and Logos's projection pruning show mature systems exclude exactly these.
4. **Authoritative typed append-only ledger + content-addressed blobs, with fixed derived views and explicit exclusions; single fenced writer per run (chosen).**

## Decision

1. **Authoritative record** of a run = (a) the typed append-only event log, (b) the content-addressed blob store it references, (c) the immutable run manifest (payload of `lifecycle.run.created`, seq 0). Nothing else is authoritative.
2. **Materialized views** — context view (WS-D1), run summary, HEAD, indexes, effect ledger (WS-B2), audit chain heads (WS-H6), results rows (WS-J5), cost totals (WS-L2) — are pure functions of the durable prefix, stamped with the `(run_id, seq)` watermark and a view-policy version they were derived from, rebuildable at any time, and never written except by projection. `project(run, view_kind, until_seq)` is deterministic: two rebuilds yield equal `view_hash`.
3. **Selective exclusions (what is *not* event-sourced):** environment state (recorded as handles, snapshot references, world-state patches); secret values (references only); streaming deltas (ephemeral; final message persisted); payloads above a class-declared size threshold (offloaded to blobs and referenced — ADR-0029); UI-only presentation facts. Every event class declares `durability ∈ {ledger, ephemeral}` in one persistence-policy table (Codex `rollout/src/policy.rs` precedent), never ad hoc in producers.
4. **History is never rewritten.** Rollback, navigation, compaction, redaction and fork are *appended events* (`lifecycle.run.rolled_back`, `lifecycle.head.moved`, `context.compaction.completed`, `lifecycle.ledger.redacted`, `lifecycle.run.forked`) that projections interpret; no operation mutates or removes a durable event; redaction deletes blob bytes only.
5. **Write path:** exactly one writer per run holds a lease whose `lease_generation` (WS-B2 §6.3) is the fencing token; every event carries the generation; the ledger refuses a stale generation (`Fenced`). Appends are atomic multi-event units assigned dense, strictly increasing per-run `seq`. An event is visible (to views, streams, subagents, the reference monitor) only after it is durable (**durable-before-visible**); readers stop at the last complete record.
6. **Storage class at Stage 0–1** (properties, no technology): a local ordered append-only record store with atomic multi-record append and acknowledged durable flush; a local exclusive-writer primitive with stale-holder detection usable across processes on one host; forward/reverse scan; a local content-addressed blob store with dedup and delete-by-address. WS-B1 §6.6 lists the full property set for WS-L1.
7. Every event carries `participant_class` and `observability_level` (phase-0 §5.5); the ledger is native and typed, never interchange-shaped; imported hosted runs are `open_run` + one append batch with `provenance = imported{format, source}`.

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-06 (hosted rows enter through the same native envelope; no native contract changes for them), T-LCD-12 (contract is operations/invariants; implementable out-of-process), T-LCD-13 (artifact delivered/activated/followed classes are in the taxonomy — executable test at Stage 3), T-LCD-15 (events stamp `observability_level` so metric registries can resolve `requires_observability`). Not applicable: T-LCD-01/-03/-04/-05/-07/-08/-09/-10/-11/-14 (no model-facing surface or lowering is introduced by this ADR; T-LCD-10 is addressed by ADR-0027).

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** doc 2 §11 (S-doc2) rule quoted above; Managed Agents S-047 ("the session log sits outside the harness, nothing in the harness needs to survive a crash"; `getEvents()` positional slices transformed before entering context); Cursor S-052 (append-only conversation store; durable loop "one 9 → two 9s"); Fowler S-194 (complete rebuild, temporal query, snapshots as caches); Logos S-073 (`provisional`, mechanism only: transcript "owned by no process"; invariants I1–I4; durable-before-visible; zero repeated actions across four kill points) — corroborated by the Tier-B source precedents in (b), so no provisional claim is load-bearing.
- **(b) Source-code precedent:** OpenHands S-110 @3fc7b22 `openhands-sdk/openhands/sdk/conversation/event_store.py` (`EventLog.append` under lock, duplicate-id and parent checks, `_advance_length_marker`), `conversation/state.py` (`View.from_events(path_to_root(leaf))`, "append replays only the new tail — O(k)"), `context/view/properties/{tool_call_matching,tool_loop_atomicity,batch_atomicity,observation_uniqueness}.py`; `openhands-agent-server/openhands/agent_server/conversation_lease.py` (generation-fenced ownership lease). Codex S-107 @0735c51 `codex-rs/rollout/src/policy.rs` (`is_persisted_rollout_item`, `should_persist_event_msg` — deltas and approval requests not persisted), `rollout/src/writer_lock.rs` (`WouldBlock` for an active writer), `rollout/src/recorder.rs` (`pending_items` removed "only after it is written successfully"), `core/src/session/rollout_reconstruction.rs` (rollback interpreted at reconstruction, "skip the next N user-turn segments"), `rollout/src/state_db.rs` (derived index with backfill lease). Pi S-113 @400d690 `packages/agent/src/harness/session/commit.ts` (`validateCommittedWrites`: "Non-monotonic storage sequence"), `session/jsonl/io.ts` (`serializeJsonlTransaction`, `publishFileAtomically`), `session/jsonl/fork.ts` (`highestCompleteSeq`, torn-tail tolerance). Destructive counter-examples rejected: opencode S-111 @9f8db11 `packages/opencode/src/session/revert.ts` (`removeMessage`/`removePart`); goose S-112 @fae91d0 `crates/goose/src/session/session_manager.rs` (`replace_conversation` → `DELETE FROM messages`).
- **(c) Disconfirming evidence considered:** Kiehl S-195 ("that first extra projection you add doubles the amount of code that touches your event stream"; schema-evolution fidelity loss; eventual-consistency anomalies; "a history table gets you 80% of the value of a ledger with essentially none of the cost"); Fowler S-194 (external-gateway and code-versioning problems); LangGraph S-143 (a widely used runtime chose snapshots). *Why it does not overturn:* the projections are few and contract-fixed (not an open subscriber ecosystem); the remaining 20% — effect phases, permission decisions, delivered/activated/followed, tamper evidence — is precisely what a research instrument exists to measure; the "selective" clause removes the payload/state bloat the critique targets; and the two history-table systems audited had to add destructive rewrites. The costs are carried as consequences (schema-evolution discipline, rebuild acceptance tests).
- **(d) Conditionality:** independent of model tier and task class. Assumes one host and one writer per run at Stage 0–1 (multi-host leases are WS-B3's Phase 2 extension); assumes payload sizes at coding-agent scale (event ≤ 64 KiB after offload; blobs up to environment-snapshot scale). Hosted participants supply only the classes their `observability_level` permits; missing classes are `n/a`, never errors.
- **(e) Build-stage assignment:** C0 / Stage 1 (envelope, append/read/head/subscribe, blob store, persistence-policy table, context_view + run_summary projections); C0 / Stage 2 (fork/navigate/rolled_back, compaction, derived index, audit checkpoints with WS-H6); C0 / Stage 3 (artifact.* chain, results_row projection, interchange identifiability); C1 / Stage 4 (subagent and hosted ingestion).

## Consequences

- WS-D1's context view, WS-B2's effect ledger, WS-J5's results rows and WS-H6's chain heads are all specified as `project(...)` view kinds with `derived_from` watermarks; each owner writes the rebuild-equality acceptance test (AC-B1-3).
- WS-B3's recovery reads the last durable effect phase from the ledger and appends `lifecycle.run.resumed{recovery_decision}`; it never edits history.
- WS-L1 receives the storage-property list (WS-B1 §6.6) as ratification input; a candidate ecosystem must satisfy all ten properties without an exotic dependency.
- Schema evolution is a hard compatibility contract: `schema_version` on every event, golden fixtures per prior version, deprecation handlers rather than field removal (OpenHands `sdk/AGENTS.md` policy; AC-B1-8).
- Every producer must be able to run with the ledger out-of-process (T-LCD-12); the append contract is the only way in.

## Reversibility

**Low.** Downgrading to a history table after Stage 1 forfeits audit chains, effect-phase accounting and compliance events, and every consumer contract (B2, B3, B4, D1, H6, I1, J5) is written against the ledger. Upgrading the storage class (local → remote, single-host → multi-host leases) is *medium* because the contract names only properties.
