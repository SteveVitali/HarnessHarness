# ADR-0001 — Positioning: native-primary, hosting-as-participant (two participant classes)

**Status:** ratified (pre-ratified by sponsor; seeded at Preflight 2026-09-09 per doc 3 §4, §11.2 step 6)
**Owner workstreams:** WS-A1 (positioning audit), WS-J6 (external-harness hosting / thin observational ABI), WS-A2 (participant classes in the ontology)
**Supersedes:** —
**Related:** ADR-0002; CF-003; OQ-004; R-2.10.6

## Context

The sponsor's brief asks for "the most sophisticated, generic, modular, extensible meta-harness framework on the market" *and* the ability to "compare everyone's" harness. Doc 2 warns twice (§5.11 Harness ABI, §12 Harness IR) that maximally generic abstractions hide exactly the model-conditioned features that drive real performance — the lowest-common-denominator (LCD) trap. Third-party harnesses (Codex, Claude Code, OpenHands, Cursor CLI, Gemini CLI) are black boxes we do not control; they cannot be component-decomposed, ablated, or causally attributed. A single ABI that pretends they can would be an LCD interface.

Doc 2 §5.11 and §7 also document that a harness-hosting layer is emerging in industry (Omnigent, ACP-style hosting, Cloudflare/AWS/Microsoft runtimes) — so hosting external harnesses has real value for factorial model × harness × environment science, provided it does not dictate the internal representation.

## Options considered

1. **ABI-first / host-everything.** One universal Harness ABI; MetaHarness's own runtime is just another ABI participant. *Rejected:* forces the LCD trap into the core; loses component decomposition, ablation, attribution, evolution.
2. **Native-only.** Only IR-native harnesses; no external hosting. *Rejected:* forfeits "compare everyone's" and the cheap factorial evaluation the hosting layer enables (doc 2 §5.11).
3. **Native-primary, hosting-as-participant (chosen).** The white-box IR-native path is the core; external harnesses join as black-box participants through a deliberately thin *observational* ABI, sharing the comparison plane but never pretending to be decomposable.

## Decision

- The **white-box path is the core**: harnesses expressed in our IR and run on our native runtime, whose components can be swapped, ablated, causally attributed, and evolved.
- **External harnesses join as hosted participants** through a **thin observational ABI**: start/resume/cancel · stream events · supply context/tools/skills · request permission · account cost. They share the same environments, evals, scorecards, cost/latency/audit as IR-native harnesses.
- **One comparison plane, two participant classes:** `IR-native (white-box)` and `hosted-external (black-box)`. The comparison/analysis engine (WS-J4) spans both; component-level analyses apply only to white-box participants.
- External hosting is **first-class but strictly secondary** to the native instrument. Deep interop lives on the white-box path where we own the internals.

## Evidence (per doc 3 §3.3 synthesis contract)

- **(a) Mechanism evidence:** the LCD risk is a mechanism argument from doc 2 §5.11/§12 and from the model-conditioning cross-cutting property (doc 2 §4; Cursor model-specific tools S-049; Managed Agents stale-guardrail report S-047). Harness hosting as a distinct role is documented by the 11-system source-code study (S-074, tier C, mechanism) and by Omnigent (S-118, S-060), ACP (S-035), Cloudflare harness/runtime split (S-056/S-057).
- **(b) Source-code precedent:** Omnigent (S-118) hosts multiple existing harnesses behind common sessions/policies/sandboxes; ACP (S-035) standardizes session create/resume, updates, permissions, cancellation — the exact verbs of the thin ABI. Codex App Server (S-055) exposes a hosting boundary. *Precedent exists; not novel.* The **two-participant-class comparison plane** is `novel` in combination (no precedent found at Preflight; WS-A1 to confirm or refute).
- **(c) Disconfirming evidence considered:** (i) doc 2 §7 finds none of eleven mature coding harnesses uses a general framework for its core loop — suggesting that a "framework" others adopt is unlikely; this ADR is consistent with that finding because MetaHarness positions itself as a research instrument + reference runtime, not a framework for others' core loops. (ii) A thin ABI may still be too thin to compare fairly (e.g. cannot hold context policy fixed across black-box participants) — accepted: black-box comparisons are labeled as configuration-level, not component-level, and the ABI depth is an open question (OQ-004, WS-J6).
- **(d) Conditionality:** assumes external harnesses continue to expose ACP-like session/permission/event interfaces; if the ecosystem converges on richer standardized internals, the ABI may deepen (revisit at Phase 3).
- **(e) Build-stage assignment:** white-box core = C0 (Stages 0–3); hosting/ABI = C2, Phase 3 design, later build stage (after the eval backbone exists so hosted participants have something to join).

## Consequences

- WS-A2 must formalize the two participant classes in the ontology; WS-J4 must make every metric declare which class(es) it applies to.
- WS-J6 owns the ABI depth decision (OQ-004) and must guard against ABI growth that re-imports the LCD trap.
- The Canonical Spec §6 (laboratory) carries a hosting subsection marked *secondary*; readiness does not require any specific external harness to be integrated.

## Conditionality summary

Holds for: any model tier, any task class. Assumes black-box participants can at minimum start/stream/cancel and account cost; participants that cannot are excluded from the comparison plane rather than accommodated by loosening the native path.

## Build-stage

C0 (native core) / C2 (hosting). Hosting is not on the critical path of Stages 0–3.

## Reversibility

Medium. Adding depth to the ABI later is cheap; retrofitting component decomposition onto black-box participants is impossible by construction, which is why the native path is primary.
