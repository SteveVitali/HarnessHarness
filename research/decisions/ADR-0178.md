# ADR-0178 — API stability and versioning policy for the embedding contract: one schema source with generated bindings and CI drift checks, contract identity `(contract_major, schema_hash, kernel version_id)`, additive-only evolution within a major (AIP-180 rules), stability tiers with experimental opt-in and assumption-debt records, deprecation with removal tests, exact pinning with floors, and a compatibility-matrix fixture set

**Status:** ratified
**Owner workstream(s):** WS-K4 (with WS-L4 for identity, WS-L6 for packaging/changelog; consumers WS-K1, WS-K2, WS-K3, WS-J1…J5, WS-I3, WS-L5, WS-B1) · **Phase:** 3 · **Related:** ADR-0176, ADR-0050 (D3 I1/I3; §5 per-layer reversibility; §8), ADR-0036 (content identity; `VersionedRef`), ADR-0037 (immutability I1–I5; supersession; name histories; sameness ladder; `RevocationRecord`), ADR-0038 (`InstrumentRecord.component_versions`), ADR-0026 (AC-B1-8 schema evolution; "old events must always load"), ADR-0099 (probe-first pinning; typed `ProtocolVersionMismatch`; expiring eras with debt records), ADR-0007 (T-LCD-05 reflexive; T-LCD-07), ADR-0024 (MUST-code/data); CF-375; OQ-403; R-2.11.4, R-2.12.1, R-2.12.2

## Context

The doc 3 §5 row makes "stability/versioning of the API (L4)" a WS-K4 deliverable. ADR-0050 D3 already requires a single source of truth for types with generated, CI-checked bindings (I1), version negotiation on `hello` (I2) and exact pinning by the consuming side (I3); ADR-0036/0037 give every authored record a content identity, immutability, append-only name histories with SemVer-class labels and a sameness ladder; ADR-0099 fixed, for protocol edges, probe-first pinning, typed mismatch errors, no silent fallback and assumption-debt records on every legacy era. What is missing is the policy for the *public* contract: what "stable" means for a research instrument whose kernel contracts are versioned records, how additive change is bounded, how experimental features enter and leave without an escape hatch, and what evidence the readiness report needs.

The audit found the mechanisms and their absence side by side. Codex marks experimental methods *and fields* in the protocol source, refuses them with a typed `"{reason} requires experimentalApi capability"` unless the connection opted in at `initialize`, filters them from default generated bindings, keeps `v1`/`v2` namespaces behind an allowlist, and lets clients opt out of notification methods (S-107 `experimental_api.rs`, `export.rs`, `protocol/v1.rs`, `message_processor.rs`). ACP negotiates a single integer major and defines capabilities as additive ("The introduction of new capabilities is not considered a breaking change") with `_meta`/`_`-prefix reserved space (S-035). OpenHands generates its client from the exact pinned server image's OpenAPI and fails CI on drift while shipping under an "ALPHA … Breaking changes may occur in any release" banner (S-110 `clients/typescript`). The Claude SDK bundles an exact CLI version and probes a minimum at spawn — but only *warns* — and exposes its `Transport` with a "may change or [be] remove[d]" notice (S-109). Pi's protocol has a handshake and strict envelopes but "no compatibility guarantees" (S-113). Cloudflare marks its composition surface "Experimental … may change between releases" (S-557). Google's AIP-180 states the rule set mature APIs converge on (S-559).

## Options considered

1. **SemVer on the SDK package only, kernel API unversioned** (most audited SDKs). *Rejected:* the SDK is a generated client; the contract is the kernel's; a package label says nothing about the schema the kernel actually serves (ADR-0036 N7: labels are claims).
2. **Perpetual experimental status with exact pinning** (OpenHands/Pi posture). *Rejected:* an instrument whose results are keyed by `configuration_version_id` and bundled for reproduction (ADR-0038) needs old clients to keep reading old bundles and new kernels to keep accepting old definitions; "breaking changes in any release" would make every stored experiment's tooling rot.
3. **Full tolerant-reader evolution** (ignore unknown fields everywhere, as ACP/MCP/OpenHands envelopes do). *Rejected:* CF-209 — the ecosystem boundary carries canonical, hash-equal events and rejects unknowns; tolerance would let two sides disagree on bytes they both hash.
4. **Chosen:** contract identity + AIP-180 additive rules within a major + per-item stability tiers with experimental opt-in, typed refusal and debt records + deprecation by removal test + exact pinning with floors + a compatibility-matrix fixture set, all as applications of ADR-0036/0037/0099.

## Decision

1. **Single schema source; generated bindings; CI drift check (I1).** The kernel exports one machine-readable schema set: HIR/1, ledger event schemas, `MetricDeclaration`, and every `hh-embed` message, frame and error type. Every binding in every ecosystem is generated from it; CI regenerates and fails on any difference (S-110 `check-agent-server-api.mjs` shape; S-107 `GENERATED_TS_HEADER`). Hand-written client code sits *above* the generated layer and is type-checked against it; nothing hand-written defines a wire type.
2. **Contract identity.** `ContractIdentity{contract_major: int, schema_hash: ContentAddress over the canonical schema export (ADR-0036 `idp/1`), kernel_version_id}`; `kernel.version` is a SemVer-class *label* in an ADR-0037 name history bound to the `version_id`. `hello` exchanges the identity; a generated client asserts `(contract_major, schema_hash)`; mismatch is typed — `ContractMajorUnsupported{requested, supported[]}` or `SchemaMismatch{direction ∈ {client_newer, kernel_newer}}` — never silent fallback (ADR-0099 N2 applied inward).
3. **Additive evolution within a major (AIP-180, adopted as normative).** Within one `contract_major`: methods, frame kinds, optional fields, request-position enum values and error variants *may* be added; existing components *must not* be removed or renamed; types *must not* change even if wire-compatible; defaults *must not* change; a new client-populated field *must* default to the prior behaviour when absent; visible semantics *must not* change. Response-position closed sums (`StopReason`, `decider`, `EffectDomain`, error codes) grow only by **dialect bump** (phase-2 §6.8 rule 3); the dialect is announced at `hello` and carried in every durable frame's `schema_version`; a client receiving an unknown dialect refuses loudly (`SchemaMismatch`) — the reverse of ADR-0026 AC-B1-8 (CF-375). A `contract_major` bump is required for anything AIP-180 classes as breaking and is an ADR.
4. **Stability tiers per method and per field.** `stable` — governed by rule 3; removed only at a major after a deprecation window. `experimental` — callable only on a connection whose `hello.capabilities.experimental = true`; otherwise refused with `ExperimentalRequired{reason: "<method>" | "<method>.<field>"}`; excluded from default generated bindings and from the `stable` conformance suite; may change or vanish in a minor; **must** carry an `AssumptionDebtRecord{hypothesis, evidence_refs, owner, expiry_condition, removal_test}` whose removal test is "promoted to `stable` or deleted, and no first-party surface references it" (T-LCD-05 reflexive). `internal` — reachable only from first-party in-process clients; absent from the exported schema (the Claude `Transport` warning made structural). Experimental payload fields inside *durable events* are not gated per connection (that would break I4); they live in `ext` until promoted (OQ-403). Promotion `experimental → stable` closes the debt record and enters the contract changelog.
5. **Deprecation.** A `stable` item marked `deprecated{since, removal_major, replacement}` stays callable for the rest of its major and is listed in `hello.stability`; each use appends `lifecycle.contract.deprecated_use{method, client}`; removal at the next major requires the readiness report to show zero uses across the participant/surface registry (ADR-0037 "removal test"; Codex `v1` allowlist precedent). Deprecation of a whole `contract_major` follows ADR-0099 N5 (an era with a debt record keyed to the window).
6. **Per-connection variability is capability-only.** A client may decline event classes (`opt_out_notifications`) and ephemeral frames, and may enable `experimental`; it may not request a narrower durable schema — the ledger is never sampled (ADR-0044).
7. **Exact pinning and floors (I3).** A client package pins one exact kernel build (S-107 `python-runtime`; S-110 `agentServerImage`) and declares `kernel_floor`; `hello` refuses a kernel below the floor (`KernelBelowFloor`) rather than warning (the S-109 warning is an untyped escape hatch); the pinned build's `schema_hash` enters the client's own version identity, and WS-I3 records the client's `ContractIdentity` in `InstrumentRecord.component_versions` (ADR-0038) so a bundle names the tooling that ran it.
8. **Compatibility matrix as a test artifact.** Golden fixtures per `(contract_major, schema_hash)` are kept; the suite runs newer-client × older-kernel (expects `SchemaMismatch{kernel_newer = false}`), older-client × newer-kernel within a major (expects success with defaults), and cross-major (expects `ContractMajorUnsupported`); the readiness report cites it for R-2.11.4.
9. **What the policy does not promise.** No behavioural interchangeability across kernel builds (ADR-0006 N6): two builds with the same `contract_major` may produce different runs; reproducibility claims come from the bundle (ADR-0038), not from the API version.

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-05 reflexively (every experimental item and every deprecation carries a debt record with a removal test; eras expire), T-LCD-07 (client capabilities declared; `unknown` never coerced; experimental never implied), T-LCD-10 (contract identity is content-addressed; labels are name-history entries), T-LCD-11 (typed mismatch; no silent downgrade; `ext` preserved), T-LCD-12 (policy is over records and schemas). Does not address T-LCD-01/-02/-03/-04/-06/-08/-09/-13/-14/-15. **ADR-0024 rung:** schema export, negotiation, refusal typing and the drift check are MUST-code; tiers, deprecation windows, floors and the stability map are MUST-data.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** experimental gating per method and field with typed refusal, export filtering and notification opt-out (S-107 `app-server-protocol/src/experimental_api.rs`, `export.rs` L45–70, `protocol/v1.rs` L43–66, `app-server/src/message_processor.rs` L960–975); single integer major with additive capabilities and reserved extension space (S-035 `initialization.mdx`, `extensibility.mdx`); generated client from a pinned server with CI drift failure and an explicit alpha posture (S-110 `clients/typescript/README.md`, `package.json`, `scripts/check-agent-server-api.mjs`); exact pin + minimum-version probe that only warns (S-109 `_cli_version.py`, `subprocess_cli.py` L36, L1144–1180) and a disclosed-unstable abstraction (S-109 `transport/__init__.py`); "no compatibility guarantees" with strict envelopes (S-113 `protocol/README.md`); an experimental composition surface (S-557 `lifecycle.md`); the backwards-compatibility rule set (S-559 AIP-180); immutable released contents (S-227 SemVer via ADR-0037); typed mismatch and expiring eras (ADR-0099).
- **(b) Source-code precedent:** codex `codex-rs/app-server-protocol/src/experimental_api.rs` (`ExperimentalApi` trait; inventory of `ExperimentalField{type_name, field_name, reason}`), `export.rs` (`JSON_V1_ALLOWLIST`, `GenerateTsOptions{experimental_api}`), `app-server/src/transport.rs` L40–60 (`outbound_experimental_api_enabled`, `outbound_opted_out_notification_methods`) @0735c51; software-agent-sdk `clients/typescript/scripts/{check-agent-server-api.mjs, generate-agent-server-api.mjs}` and `package.json` `config.agentServerImage` @3fc7b22; claude-agent-sdk-python `_cli_version.py`, `_internal/transport/subprocess_cli.py` L1144–1180 @ad77094; agent-client-protocol `docs/protocol/v2/initialization.mdx` @9b00c27. The combination — content-addressed contract identity, AIP-180 rules bound to dialect bumps, tiers with debt records and removal tests, floors instead of warnings, and a compatibility matrix in the readiness report — is `no-precedent / novel` as a policy; each mechanism is precedented.
- **(c) Disconfirming evidence considered:** (i) Strictness on unknown fields makes every additive change a coordinated upgrade (OpenHands' tolerant envelope; ACP/MCP preserve rules) — answered by CF-209 (hash-equal events need strictness), `schema_hash` at `hello` (mismatch known before any payload), I1 (both sides generated from one source) and rule 3 (older clients stay valid to newer kernels). (ii) Experimental gating adds a capability flag every host must learn — answered: the flag is one boolean, and the alternative (Pi/OpenHands "no guarantees") makes stored experiments' tooling rot. (iii) Refusing below a floor is harsher than warning — answered: a warning is an untyped path into undefined behaviour; a refusal is actionable and the floor is data. (iv) AIP-180 was written for long-lived cloud APIs, not a research instrument — answered: the instrument's *results* are long-lived (bundles, R-levels), which is precisely the property that needs the rules; rule 9 disclaims what AIP-180 would over-promise. None overturns.
- **(d) Conditionality:** independent of model tier and task class; assumes ADR-0036 canonical form and `idp/1` for `schema_hash`; assumes ADR-0037 name histories for kernel labels; deprecation windows and which Stage-1 items ship `experimental` are MUST-data set at Stage 1 and the first minor after Stage 5; the policy applies to the embedding contract and, by WS-L5's adoption, to the variant-host boundary — not to the Hosting ABI, which has its own `hh-hosting/N` (WS-J6 §6.4).
- **(e) Build-stage assignment:** **C0 / Stage 0** schema export, `ContractIdentity`, generated bindings, CI drift check. **C0 / Stage 1** `hello` negotiation with typed refusals, stability map in the export, experimental opt-in and refusal, floors (AC-K4-8), first compatibility fixtures. **C0 / Stage 3** WS-I3 records `ContractIdentity` in bundles. **C1 / Stage ≥ 5** deprecation machinery (`deprecated_use` counting) at the first minor with a deprecation; readiness-report matrix.

## Consequences

- WS-L6 maintains the contract changelog and the stability map release-by-release, and packages generated clients pinned to exact kernel builds; WS-L4 supplies the `schema_hash` derivation and the kernel label's name history.
- WS-B1 adds `lifecycle.contract.deprecated_use`; WS-I3 adds the client's `ContractIdentity` to `InstrumentRecord.component_versions`.
- WS-K1 may ship on `experimental` items (first-party opt-in); WS-K2 and third-party SDKs may not without declaring `experimental`; WS-K3's Lab tools inherit tiers from the operations they wrap.
- WS-L5 applies rules 1–5 and 7–8 to the variant-host boundary; WS-J6 keeps `hh-hosting/N` separate but may reuse the same tier vocabulary.
- The Decompose-Readiness Gate gains a checkable item for R-2.11.4: the compatibility-matrix fixture set exists and passes for the Stage-1 contract.

## Reversibility

**High** for tiers, windows and floors (data); **medium** for AIP-180 rules (loosening them after Stage 3 would orphan stored bundles' tooling — the cost the rules exist to avoid); **low** for I1/I2 and content-addressed contract identity (shared with ADR-0050 D3 and ADR-0036).
