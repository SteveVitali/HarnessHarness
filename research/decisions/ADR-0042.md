# ADR-0042 — The trace/span model is a projection of the run ledger; export is lowering; the ledger is never sampled

**Status:** **ratified, amended** (Phase 1 synthesis, 2026-09-10)
**Owner workstream(s):** WS-I1 (with WS-B1, WS-H6, WS-K2, WS-J6) · **Phase:** 1 · **Related:** ADR-0026/ADR-0027/ADR-0029 (ledger authoritative; ID model; canonical form), ADR-0030 (effect phases), ADR-0004/0005 (observability levels, class-scoped metrics), ADR-0007 (T-LCD-06, -11, -13, -15), CF-088, CF-089, CF-092, OQ-115, OQ-119, R-2.9.1, R-2.8.6

## Context

The sponsor requires "deep audit at all levels" with per-call cost and latency (doc 3 §2.9, R-2.9.1) and a scorecard built from process metrics over heavy-tailed runs (doc 2 §8). WS-B1 has fixed the run ledger as the sole authoritative record with derived views. Every mature harness audited in source (Codex, goose, OpenHands, opencode) instruments telemetry at the same call sites that emit its session events, exports spans through an in-process pipeline, and keeps at most a derived accounting table; where a second book exists it needed reconciliation paths (goose `carried_forward` rows; opencode signed projection). OpenTelemetry's SDK decides sampling at span start, caps events/links per span at 128 by default, and leaves tail-based sampling to a collector — properties that disqualify an SDK span store as the audit record of a research instrument whose informative runs are the tail. Industry attribute schemas (`gen_ai.*`, OpenInference, backend-specific span types) are converging but are Development-stability, lack cost/effect/permission/compaction semantics, and are normalized between each other by backends.

## Options considered

1. **Instrument call sites directly with an in-process span pipeline; keep the ledger separate** (what every audited harness does). *Rejected:* two books that drift; spans die with the process on crash while the ledger keeps the opening event; sampling and span limits make the trace incomplete precisely for the runs that matter; component attribution needs ledger-level provenance that spans do not carry.
2. **Make the OTel-style span the ledger's native unit** (span = event). *Rejected:* spans have a fixed identity model (one parent, 16/8-byte ids) and no notion of effect phases, provenance, authority, durability policy or hash chain; it would re-introduce the LCD trap on the measurement plane (T-LCD-11 in reverse).
3. **Trace/span model as a deterministic projection over the ledger; exporters as subscribers; export as lowering with a loss report; sampling only at sinks (chosen).**

## Decision

1. **Spans are scopes.** A span is `(scope-opening event, scope-terminal event | open)` for one ledger scope id; `scope_kind ∈ {run, turn, model_call, model_attempt, context_assembly, compaction, tool_call, tool_attempt, effect, permission, validation, subagent, environment_op, memory_op, wakeup}`. Span identity *is* the opening event's `EventRef`; the parent is the nearest enclosing scope by the envelope's `scope{}` nesting; non-tree causality (subagent spawn → child run, MCP transport, retries) is `causes[]`. Trace identity is the root run of a run tree.
2. **No telemetry store.** `trace_view`, `cost_view`, `metric_view`, `turn_phase_profile`, `open_scopes`, `audit_view` are WS-B1 materialized views (`project`), pure in the durable prefix, stamped `derived_from` and `view_hash`. Exporters consume `subscribe` and render views incrementally; they never append to the ledger except `measurement.export.delivered` (what left the system, with content classes and loss report).
3. **Export is lowering.** Rendering `trace_view`/`metric_view` to any external convention is a target lowering with a *telemetry loss report* `{dropped_fields, truncated_fields, unit_conversions, unmappable_scopes}` (T-LCD-11 applied to telemetry). Lifting an external span (MCP server, subprocess, hosted participant) recovers a `causes[]` link via the propagation context (`traceparent` + a `tracestate` member carrying `(run_id, event_id)`), never a new identity. External trace/span ids are `surface_ids` aliases.
4. **The ledger is never sampled.** Every `durability = ledger` event is recorded for every run; sampling, rate limiting and previews apply to export sinks and `ephemeral` diagnostics only. No scorecard metric may be computed from an exported sample.
5. **Scope closure is audited.** A scope-opening event without its terminal event past a deadline is an `open_scopes` entry and sets `audit_completeness = false` for the run (deadline policy: OQ-119).
6. **Requests to WS-B1** (not contradictions): `model.call.attempt.started/completed/failed` classes under the logical `model_call_id`; `assembly_ms{measured_at}` on `context.assembled` (chosen at synthesis, CF-092; WS-D1 may add `context.assembly.started` in Phase 2 if open-scope auditing of assembly is needed); `measurement.export.delivered`; `measurement.metric.emitted` restricted to non-derivable observations (CF-088/-02/-05).

**T-LCD statement (ADR-0007 decision 5):** satisfies T-LCD-06 (no IR entity gains a field; propagation rides existing `_meta`/env slots), T-LCD-11 (loss report on export; lifting recovers links), T-LCD-13 (compliance computed from the ledger chain), T-LCD-15 (views render `n/a` by class/observability). Does not address T-LCD-07 (hosted capability probing — WS-J6). No unmitigated "does not".

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: WS-B1 F1/F2 (ledger + enforced projections in five codebases); this dossier F1 (telemetry derived from loop events in Codex `otel/src/events/session_telemetry.rs`, goose `agents/agent.rs`, OpenHands `llm/utils/telemetry.py`, opencode `session/projector.ts`; second-book reconciliation in goose `session_manager.rs: record_usage_metrics`), F2 (convention convergence yet insufficiency: S-228 `gen_ai.*` Development stability, no cost attribute, content-reference `TODO`; S-232 GenAI↔OpenInference normalization), F7 (propagation through `_meta`/env: S-230 SEP-414, S-107 `otel/src/trace_context.rs`), F10 (no audited harness samples its own log; S-229 sampling at span start, span limits). Managed Agents (S-047) reads telemetry from the session log (`getEvents()`). Harness-Bench (S-062, `provisional (mech)`) shows the scorecard needs traces + usage + validator outputs per run.
- (b) Source-code precedent: OpenHands `openhands-sdk/openhands/sdk/agent/acp_tracing.py` (`ACPTurnTrace` — spans synthesized *from events it does not own*, "shaped like the native ones so a trace consumer needs no ACP-specific branch"); Codex `codex-rs/protocol/src/protocol.rs: W3cTraceContext` + `otel/src/trace_context.rs` (trace context as protocol data and env); OTel MCP conventions `docs/gen-ai/mcp.md` (context in `params._meta`, transport as link); WS-B1 `project`/`subscribe`. The *projection-only* trace model and the telemetry loss report are `no-precedent / novel` as an integrated contract.
- (c) Disconfirming evidence considered: in-process span pipelines are universal (S-107/S-110/S-111/S-112) and give in-flight visibility; Kiehl (S-195) on projection cost; OTel's own guidance assumes spans are born at the call site. Not overturning because exporters can subscribe to the durable tail and open spans at scope-opening events (OpenHands' ACP tracer already does this for foreign events), open scopes are a first-class view state that survives crashes, and the projections are few, fixed and hash-checked (AC-B1-3/AC-I1-1). Residual cost (exporters written as subscribers; a few-hundred-millisecond visibility lag equal to durable-append latency) is accepted.
- (d) Conditionality: independent of model tier and task class. Assumes WS-B1's durable-before-visible append is fast enough that projection lag is tolerable for live viewers (Stage 1 target: tens of events/s per run — WS-B1 §6.6). For hosted participants, span fidelity is bounded by `observability_level`; views report the level rather than inventing spans.
- (e) Build-stage assignment: C0 · Stage 0 (minimal `trace_view`/`cost_view` over the single-file trace) → Stage 1 (scope kinds M1–M12, `SinkPolicy`, propagation at the subprocess seam) → Stage 2 (MCP/ACP propagation via lowering slots; `audit_view`) → Stage 3 (loss-report export to two convention-shaped sinks; AC-I1-1…13 in the suite).

## Consequences

- WS-K2's trace/time-travel viewer, WS-H6's attestation, WS-J4/J5's scorecards and WS-I7's counterfactuals all read the same views; no consumer talks to an exporter.
- WS-B1 adds the requested classes/fields; WS-A4/E4 carry the propagation context through lowering slots and list it in the lowering loss report when a target cannot carry it.
- Every exporter is a component variant implementing `export(view, SinkPolicy) → Delivery{loss_report}`; convention mapping tables are declared data, versioned in the bundle (WS-I3).
- Hosted-participant adapters (WS-J6) append events; they never emit spans directly.

## Reversibility

Medium. Adding a direct-instrumentation shortcut later is cheap but reintroduces two books; removing the projection model after consumers depend on `view_hash` audit would invalidate H6 attestation and Stage 3 acceptance tests.
