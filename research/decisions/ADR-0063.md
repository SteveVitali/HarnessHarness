# ADR-0063 — The extension trust model: three-leg trust record, provenance class on injection, location neutrality, attestation → `pin`, and execution isolation for skills, hooks, plugins, MCP servers and instruction files

**Status:** **ratified** (Phase 2 synthesis, 2026-09-10)
**Owner workstream(s):** WS-H5 (consumers: WS-H1, WS-H2, WS-H3, WS-H4, WS-B5/E5, WS-D1, WS-D5, WS-E2, WS-E4, WS-F1, WS-L5, WS-J2, WS-H6) · **Phase:** 2 · **Related:** ADR-0002 (iii), ADR-0007 (T-LCD-02/-06/-10/-11/-12/-13), ADR-0016/0017, ADR-0019 (closed-world rule), ADR-0024 (pointer rule, MUST-code, `authority_cap`), ADR-0025, ADR-0033/0034/0035, ADR-0036/0037/0038, ADR-0050 §8; CF-055 (confirmed), CF-140…CF-142, CF-144; OQ-022, OQ-107, OQ-162/-03/-04/-07; R-2.8.5, R-2.12.2, R-2.5.4

## Context

Doc 2 §5.6 requires that "tool plugins, hooks, MCP servers, skills, and fetched instructions … be treated like supply-chain dependencies with version/pinning and provenance, not automatically elevated because they appear in a configuration directory." ADR-0024's pointer rule already says a definition names executables only by content address plus a **trust record** and asked WS-H5/L5 to confirm its shape (CF-055). The audit of seven harnesses at pinned commits (dossier §4) found the negation of every part of that sentence in source: MCP server `instructions` and discovered skills are rendered into the system prompt (goose `agents/prompt_manager.rs` L109–127, `skills/client.rs` L246–266; opencode `skill/index.ts` L307–330); third-party plugin code is dynamically imported into the harness process (opencode `plugin/loader.ts` L128–137; pi-mono `core/extensions/loader.ts`); extension processes inherit the full environment and keyring secrets (opencode `mcp/index.ts` L352–355; goose `extension_manager.rs` L1609–1650); hooks run as host shell commands; bare names resolve to `@latest`; and the only integrity store found (gemini-cli `integrity.ts`) is a machine-local HMAC over install metadata. The attack literature attacks each of the three things an extension is — text the model reads (tool poisoning, S-310; semantic registry attacks, S-301), code a machine runs (ClawHavoc, S-311/16), and self-declared claims (MCP annotations, `allowed-tools`) — and the maturing harnesses' remedies (trusted-folder prompts, admin source allowlists, extension policies that may only narrow) are scope and policy facts, not authority. ADR-0033 fixed the minting rules and ADR-0035 fixed `pin` as an endorsement basis owned by WS-H5; this ADR applies them kind-by-kind.

## Options considered

1. **Location-based trust** (user dir > project dir > session; "trust this folder" prompts; Codex/pi/gemini). *Rejected:* location is the S-103/S-104 escalation vector; a scope fact cannot mint authority under ADR-0033 rule 6.
2. **Scanner-based trust** (malware/injection scanners decide what loads; goose OSV, ClawHub VirusTotal/ClawScan). *Rejected as a trust basis:* evadable by construction (padding, droppers, post-publication payload swaps — S-311; governance evasion 36.5–100% — S-301); fail-open in source; kept as advisory validators that may deny.
3. **One trust level per extension** (trusted/untrusted plugin; gemini `mcpServers[].trust`, codex project `TrustLevel`). *Rejected:* a single bit cannot say that a signed script is trustworthy code while its SKILL.md is `external` text, nor that a claim is not a grant; every audited compromise crossed between legs.
4. **Mandatory signatures for everything** (TUF/SLSA-complete supply chain). *Rejected for now:* no skill ecosystem signs (S-309, S-313); unusable at C1; retained as the *optional* path that alone can raise text authority.
5. **Three-leg trust record (text authority / code identity + isolation / grants) with location-neutral defaults derived from ADR-0033, attestation verified against a definition-plane trust-root policy as the only route to `definition`, claims never grants, third-party code always out of process (chosen).**

## Decision

1. **Kinds and record.** `ExtensionKind ∈ {skill, hook, plugin, mcp_server, instruction_file, fetched_instruction, component_variant, other(ext)}` (closed per dialect). An `ExtensionRecord{extension_id (version_id), kind, name, content: ContentAddress (tree rule), manifest, contributes: [VersionedRef], locator: SourceLocator{scheme, credential_free_uri, selector?, resolved, fetched_at}, trust: ExtensionTrustRecord, provenance, ext}` is a registry-layer versioned record (new `RecordKind` + domain tag under ADR-0036) that references the HIR nodes it contributes; it is not a new HIR entity. `ExtensionTrustRecord{text_authority, code_identity[], isolation, grants: VersionedRef<Permission>, declared_claims, attestations[], attestation_status, scans[], text_hygiene, installed_by, installed_at, scope, status ∈ {resolved, sealed, quarantined, revoked}, review_ref?}` — this is the CF-055 trust-record shape.
2. **Invariants (validation/append errors, never warnings).** **L1 location neutrality:** `text_authority ≤ default_text_authority(kind, origin, attestation_status)`, a total function that does not read `locator`, `scope`, directory, marketplace, settings layer or any "trusted folder" fact — `LocationElevation`. **L2 leg independence:** no leg raises another; a verified signature raises text authority only through a `pin` endorsement event; grants are conferred only by a `Permission` with `issuer.authority ≥ principal` (ADR-0035 check 1) — `LegCrossing`. **L3 claims ≠ grants:** `declared_claims` (`allowed-tools`, MCP `ToolAnnotations`, plugin permission manifests) never reach the monitor (S-153 L1903–1910 rule). **L4 pinned in sealed form:** sealed definitions/run manifests/bundles reference extensions only with pinned `content` and `locator.resolved` — `UnpinnedInSealedForm` (ADR-0036 N5). **L5 out of process:** `isolation ≠ in_process` for every extension with `origin ≠ kernel`. **L6 taint:** every item an extension contributes or emits carries `taint ∋ extension_id` unless sealed/pinned at `definition` and closed-world.
3. **Default provenance class on injection** (ADR-0033 minting rule applied): author-placed skill/plugin text at `seal` → `definition`; signature-verified under `TrustRootPolicy` → `definition` via `pin` (or `principal` where the policy says); hash-pinned unsigned text (marketplace, directory scan, git ref) → `external` (rule R-TEXT); attestation required and failed/missing → `unverified`, code refused (`AttestationRequired`); MCP `instructions`/descriptions/prompt text → lifted at `unverified` (server outside the sealed definition) or `external` (sealed, open-world), rendered only as tool surface or through a slot with `min_authority ≤ external`; tool results, hook and script output → `external` (or `environment` only via closed-schema `validator` endorsement); repository instruction files discovered by a declared source → `external`, `definition` only when the author sealed the content hash, `principal` only via `promotion`; fetched web instructions → `external` with taint; model-installed extensions → ≤ `external` with taint `{model, source}` (ADR-0065). Role placement follows ADR-0034 RP: none of the `external`/`unverified` rows may render into a role above `role_map(external)`.
4. **Attestation and `pin`.** `Attestation.kind ∈ {pin, signature, hash_chain, seal}` (ADR-0033 shape; `verified_by = kernel`). `TrustRootPolicy{allowed_sources, accepted_signers, required_predicates, require_signature_for, hash_only_ceiling = external, max_age?, drift_policy, scanner_policy, model_install, archive_policy}` is a `definition`-plane `HarnessRule` artifact layered with `authority_cap` (ADR-0024: organisation > user > project may only narrow). The `pin` endorsement (ADR-0035 basis) is emitted only for `attestation_status = verified` under the current policy; a hash-only pin yields integrity and at most `hash_only_ceiling`. Verification anchors on the signer/trust root and never on the extension's own manifest (in-toto/SLSA signer–builder rule). Signer revocation is a supersession of the policy record that marks vouched-for extensions `stale-by-dependency` (ADR-0037 `StaleIndex`).
5. **Execution isolation.** `IsolationClass ∈ {in_process (kernel only), subprocess_confined, container, remote, host_unconfined}`; defaults: hooks and skill scripts `subprocess_confined`; local MCP servers `subprocess_confined` with declared `net_egress` destinations; remote MCP `remote` (no token passthrough); plugins inherit the max of their members; `host_unconfined` only under `authority_cap` and always reviewed. Confined processes receive a cleared environment plus *declared env keys*, no ambient credentials (WS-H3 handles), fs allowlists and resource limits; every start is a `spawn_process`/`exec` effect whose grant source is the extension's `Permission`. Extension stdout/stderr is `external` tool output with the extension's taint tag and passes WS-H3 redaction before delivery.
6. **Advisory scans and hygiene.** Malware advisories, secret patterns, invisible-Unicode/bidi detection (`TextHygieneReport`) and description–code mismatch are `Validator{kind: advisory}` results recorded on the trust record with `status ∈ {clean, flagged, unavailable}`; `scanner_policy` may deny or quarantine; no scan result ever raises a class.

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-02 (extension text only as `Text` leaves with class), T-LCD-06 (nothing here exists for hosted participants; their extensions are `n/a`), T-LCD-10 (identity = `content`/`extension_id`; names, marketplace entries and descriptions are surfaces), T-LCD-11 (lifted MCP surfaces at `unverified`; claims carried as typed claims, never dropped), T-LCD-12 (records-in/records-out; helper boundary), T-LCD-13 (skill load emits the artefact chain with the extension's `delivery_id`). Not applicable: T-LCD-01/-03/-04/-05/-07/-08/-09/-14/-15. **ADR-0024 rung:** verification, isolation and endorsement are MUST-code; extension records, declared sources and `TrustRootPolicy` are MUST-data under the pointer rule.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** location-based elevation as the harness bug — S-103, S-104 (`provisional (mech)`, corroborated in source: goose/opencode system-prompt injection, codex developer-role AGENTS.md via WS-L3); tool poisoning, cross-server shadowing, rug pulls — S-310 (Tier B), MCP hints rule S-153; registry-scale compromise through SKILL.md instructions and "no isolation between skill logic and agent authority" — S-311/16 (Tier B reports), S-299/03 (`provisional`); semantic selection/governance evasion — S-301 (`provisional`); credential leakage via stdout into context — S-279 (`provisional (mech)`, ASE 2026); authority anchored on verified signer, never predicate — S-222/S-223 (Tier B), TUF S-306 (Tier A); consent transparency — SEP-1024 S-307, MCP best practices S-308; extension policies narrow only — gemini-cli `policy/config.ts` L244–252 (Tier B); the scheme this applies — ADR-0033/0034/0035.
- **(b) Source-code precedent:** goose `crates/goose/src/agents/extension.rs` L161–265 (`available_tools`, `env_keys`), `agents/extension_manager.rs` L1562–1650 (container placement; env merge counter-example), `agents/extension_malware_check.rs` L44–70/L425 (advisory OSV, fail-open counter-example), `recipe/mod.rs` L273–289 (Unicode-tag check) @fae91d0; opencode `packages/opencode/src/plugin/loader.ts` L128–137, `config/plugin.ts` L20–31, `mcp/index.ts` L352–355, `skill/index.ts` L307–330 @9f8db11 (counter-examples); gemini-cli `packages/core/src/policy/config.ts` L133, L224–278, L564–616, `core/src/config/extensions/integrity.ts` L190–320, `core/src/hooks/trustedHooks.ts`, `cli/src/config/extensions/consent.ts` L20–30 @ed2ac40; codex `codex-rs/core/src/agents_md.rs` L55–62, `core/src/hook_runtime.rs` L983–995, `core-plugins/src/marketplace_policy.rs` L35–80, `core-plugins/src/plugin_bundle_archive.rs` L127–235 @0735c51; pi-mono `packages/coding-agent/src/core/project-trust.ts`, `core/package-manager.ts` L139–144 @400d690; claude-agent-sdk-python `src/claude_agent_sdk/types.py` L850–927 (sandbox settings shape) @ad77094; software-agent-sdk `openhands-sdk/openhands/sdk/extensions/fetch.py` L170–284 @3fc7b22; MCP `schema/2026-07-28/schema.ts` L1903–1910, `docs/seps/1024-…mdx` @aa8ce04. **`no-precedent / novel`** for the three-leg record, location neutrality as a validation error, and the per-kind default table as one contract.
- **(c) Disconfirming evidence considered:** no ecosystem signs skills and marketplaces document "no built-in signing" (S-309/17) — absorbed by mandatory hash pins + optional signatures (the design is usable unsigned); confined defaults break tools people install extensions for (gemini `excludedCommands`; ~93% approvals, S-053) — absorbed by per-extension declared isolation and grants reviewed at seal, with `host_unconfined` admissible under `authority_cap`, cost measured (AC-H5-9); `external` skill text lowers the context label and may make skills a liability — author-sealed and signed skills are `definition`, only discovered unsigned third-party text is `external`, which is the population that was compromised; a single trust level is simpler (gemini/codex) — every audited compromise crossed legs. None overturns.
- **(d) Conditionality:** model- and task-independent. Assumes the helper binary can enforce fs/network/env confinement (ADR-0049/OQ-045 provisional answer; WS-B5/E5 final); assumes ADR-0033's R-TEXT rule (free text ≤ `external`) stands — if WS-D5 introduces typed skill interfaces, structured parts may reach `environment` via `validator`; signature-based elevation assumes a trust-root custody answer (OQ-162). Utility cost of `external` extension text and confinement is a Stage-4 measurement, not an assumption.
- **(e) Build-stage assignment:** **C0 / Stage 1** (records, domain tags, pins at `resolve`, `default_text_authority`, invariants L1–L4 in `validate_assembly`, `TextHygieneReport`, event classes); **C0 / Stage 2** (isolation classes enforced by the helper, env/secret defaults, taint tags on output, instruction-file and MCP `instructions` placement); **C1 / Stage 4** (`TrustRootPolicy`, signature verification, `pin` endorsement, source allowlists, advisory validators); **C2** (cross-extension flow with WS-H2). Stage note on R-2.8.5 requested (CF-144).

## Consequences

- WS-L5 carries `ExtensionTrustRecord` on every plugin/variant record and may not admit in-process third-party code; WS-J2 stores extension records with name histories.
- WS-H1 consumes `pin` endorsements, extension taint tags and extension `Permission`s; `declared_claims` never enter Π. WS-H2 uses `taint ∋ extension_id` for cross-server flow checks at C2.
- WS-D1 gives MCP `instructions` and discovered instruction files slots with `min_authority ≤ external`; WS-D5 lifts `allowed-tools` as a claim the author may accept at `seal`.
- WS-E2/E4 lift MCP surfaces at `unverified` and produce the surface document (ADR-0064).
- WS-H3/H4/B5/E5 implement the confinement defaults; WS-H6 stores trust records in the bundle and attests them.
- The ADR-0035 `pin` row is read with the refinement: signature-verified only (CF-142).

## Reversibility

**Low** for L1–L5 (the rules that close M-CPE/X-CPE for extensions and keep the model from conferring authority; reverting reopens the audited failure modes) · **medium** for the default table rows (`external` vs `environment` for particular kinds can be re-cut by dialect note) · **high** for `TrustRootPolicy` fields and isolation-class defaults (policy data, amendable by ADR without touching stored records).
