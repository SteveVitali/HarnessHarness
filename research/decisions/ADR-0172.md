# ADR-0172 — Local web surface security posture P1–P13: loopback default, capability token on every request, exact Host/Origin allow-lists, fetch-metadata checks on mutations, tokens never in URLs, no advertisement, the surface as a sink, no far-side decisions, ledgered human provenance, same-origin UI

**Status:** ratified
**Owner workstream(s):** WS-K2 (with WS-K4 for the transport profile; WS-H3/H6/H7/I1 for sink, audit and approval obligations; WS-L6 for packaging) · **Phase:** 3 · **Related:** ADR-0050 D1 row 4, D2, D3, §8; ADR-0044 (`SinkPolicy`, content classes); ADR-0034 (`readers` labels); ADR-0057/0059 (`SecretRef`, LT-01…12); ADR-0052/0053 (monitor, pre-authorization); ADR-0066/0068 (audit, `sink_deliveries`, redaction authority); ADR-0070 (`respond`, `responder_provenance`, leases); ADR-0098 (ACP edge); CF-361/05; OQ-389/05; R-2.11.2, R-2.8.3, R-2.8.6; T-LCD-12

## Context

A local web dev-tool is a browser-reachable process next to a kernel that can execute effects, spend money, and — through the approval inbox — carry a human's endorsement. The failure class is documented and exploited: CVE-2025-49596 (MCP Inspector, CVSS 9.4) — "lack of authentication between the Inspector client and proxy, allowing unauthenticated requests to launch MCP commands over stdio", exploitable from the LAN when bound to 0.0.0.0 and from any web page even when bound to 127.0.0.1 via "DNS rebinding, malicious ads, phishing pages"; fixed by "per-run session tokens … Origin and Host checks (strict CORS). Safer defaults (127.0.0.1 binding)" (S-539). The MCP transport specification now states the `Origin` MUST and the loopback SHOULD (S-153 @aa8ce04). Jupyter — the oldest such tool — requires a token even on loopback because "access to the Jupyter Server means access to running arbitrary code" (S-541). Chrome 142 ships Local Network Access, gating public-site → loopback requests behind a permission (S-540). The audited surfaces each implement part of the defence and none implements all of it (WS-K2 §4a F5); two counter-examples ship the CVE shape (an unauthenticated loopback POST; a client-side auto-accept of permissions). The decision is the floor every HarnessHarness local surface must meet, stated as testable rules.

## Options considered

1. **A layered floor P1–P13 — loopback default; per-launch capability token on every request including loopback; exact Host and Origin allow-lists; fetch-metadata and custom-header checks on mutations; off-loopback only with auth + explicit origins; no advertisement; response hardening; the surface as a `SinkPolicy` sink with reader-scoped content; tokens never in URLs; no far-side decisions or ambient credentials; shell cert pinning / SSH for remote; every write ledgered with human provenance; same-origin UI** — chosen.
2. *Loopback binding alone* (gemini devtools, pre-fix MCP Inspector) — rejected: the CVE demonstrates browser-side reachability of loopback; the MCP spec's MUST exists because of it.
3. *Loopback without a token but with Origin/Host checks* (Inspect View's default) — rejected for this surface: Inspect's viewer is read-only over log files; ours can `respond`, `fork`, `register`, `apply`; Jupyter and the MCP Inspector fix require the token on loopback; a same-host-different-port page is a distinct origin that Origin checks alone must be configured to reject, and misconfiguration (opencode's any-port loopback rule) is the common failure — the token is the layer that survives it.
4. *Exclude browsers from the kernel transport entirely* (Codex: any `Origin` request is 403) — adopted for the **kernel's raw transport**, but a *web* surface must accept browser origins; so the surface's own server terminates the browser session and speaks to the kernel as a generated client (ADR-0050 D1 row 4).
5. *Password from environment, optional* (opencode) — rejected: optional auth with a startup warning is the pre-CVE posture.
6. *Full multi-user identity and RBAC at C2* — rejected as premature: the local surface is single-principal; reviewers under `ApproverGrant` and rotations are WS-L8's; a hosted mode is out of scope for R-2.11.2.

## Decision

The following rules bind every HarnessHarness local web surface at every stage at which it exists (the battery AC-K2-6 is part of the C1/Stage-4 slice, not deferrable):

- **P1 Loopback by default.** Bind a loopback address and an ephemeral or configured port; an off-loopback bind is an explicit, logged choice subject to P5.
- **P2 Capability token on every request, including loopback.** A per-launch random token (≥ 128 bits of entropy) minted by the launcher and delivered out of band (launch-URL fragment, spawning-shell environment, or an owner-only file); constant-time comparison; missing/invalid → 401 without detail. A host-local socket with owner-only permissions is an admissible alternative for non-browser clients. Token delivery and rotation details are OQ-389.
- **P3 Exact Host and Origin allow-lists.** The `Host` authority must equal the bound authority (host **and** port); browser requests must carry an `Origin` exactly in the allow-list — the served UI's own origin by default, desktop-shell origins only when registered at launch; `null`/opaque origins and wildcards refused; requests with `Sec-Fetch-Site ∈ {cross-site, same-site}` refused.
- **P4 Mutations require fetch-metadata and a script-only header.** Every operation that writes (`respond`, `fork`, `rollback`, `apply`, `register`, `redact`, `submit`, `publish`, …) requires `Sec-Fetch-Dest: empty` (when sent) and a custom request header; simple-form submissions are refused.
- **P5 Off-loopback requires both authentication and explicit trusted origins;** a wildcard bind without them refuses to start; a single explicit `unsafe` acknowledgement is the only override and warns on every start.
- **P6 No discovery advertisement by default** (mDNS/LAN announcement is off; enabling it implies P5).
- **P7 Response hardening:** `frame-ancestors 'none'`/deny framing; a content-security policy forbidding inline script and third-party origins for the served UI; no caching of API responses; no referrer leakage of tokens.
- **P8 The surface is a sink.** It declares a `SinkPolicy{content_classes, redaction, max_field_bytes, requires_consent}` (ADR-0044); `content`-class items are delivered only when the session's reader set covers the item's `readers` label (ADR-0034); `SecretRef` values never appear (ADR-0057, SV-1…10); exports pass through the J5/H6 lowering with redaction and a loss report; every delivery to the surface is `measurement.export.delivered` so `audit_view.sink_deliveries` records what the human saw (ADR-0066 rule 5). Default content classes per session kind are OQ-392.
- **P9 Tokens never in URLs or logs.** Authorization header or first-message websocket auth; query-string tokens refused; authorization headers redacted from server logs.
- **P10 No far-side decisions, no ambient credentials.** The surface carries a human's `ApprovalResponse` to `respond` under an authenticated session; the kernel records `decider.kind = human` with `responder_provenance{surface_session_ref}` and evaluates authority (`IllegitimateEndorsement` below `principal` without an `ApproverGrant`); "always" is an `ApprovalLease` (ledgered, scoped, expiring, fingerprint-invalidated); the surface holds no provider credential, mints no permission, caches no decision, and offers only the `options[]` the kernel supplied; `irreversible` items are never batched; never-auto items show no lease option.
- **P11 Desktop shells and remote access.** A packaged shell embedding the surface pins the local server's certificate fingerprint or uses a host-local socket; remote access is by SSH port-forwarding to loopback, never by opening the bind.
- **P12 Every surface-initiated write is ledgered** with `provenance.origin = human(author_ref, role)`, the surface session reference and a request id; the audit view lists what the surface changed.
- **P13 Same-origin UI.** The UI is served by the same local origin as the API it calls; a public-origin UI reaching a local kernel is not the design (Chrome LNA blocks exactly that pattern; a same-origin local UI needs no local-network permission).

**Boundary placement (ADR-0050 §8 clause 4).** The surface's server is a process on the surfaces side of the kernel↔surfaces boundary; it terminates the browser session (P2–P9) and speaks the §6.5 verbs plus the surface verb group to the kernel/Lab as a generated client over the local transport; the kernel's raw transport keeps the strict profile (browser origins rejected outright).

**Acceptance battery AC-K2-6** (WS-K2 §6.5): foreign `Host` → 400; disallowed/`null`/cross-site `Origin` → 403; missing token → 401 on loopback; query-string token refused; simple-form POST → 403; off-loopback without auth+origins refuses to start; LT-01…12 fixtures leak nothing through any response or export; framing headers present; DNS-rebinding simulation (right IP, wrong `Host`) fails; plus AC-K2-7 (approval round trip: only kernel options, N endorsements per batch, `IllegitimateEndorsement` path, exhaustion prompt, `AlreadyDecided` from another surface).

**T-LCD statement.** T-LCD-12 (the surface is an out-of-process client; the posture is stated as operations/invariants/failure modes); T-LCD-06 (no native contract changes; hosted participants are unaffected); T-LCD-11 (exports from the surface carry loss reports). Not addressed: the rest (not an abstraction over models, targets or participants). **ADR-0024 rung:** allow-lists, `SinkPolicy` and bind configuration are MUST-data of the surface process; token minting, Host/Origin/fetch-metadata enforcement and log redaction are MUST-code; no `HarnessRule`, no IR entity.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** CVE-2025-49596 mechanism and fix (S-539: advisories from Oligo/Tenable/Qualys/SentinelOne); MCP transport §Security Warning — `Origin` MUST, loopback SHOULD, DNS-rebinding rationale (S-153 `docs/specification/2025-06-18/basic/transports.mdx` @aa8ce04); Jupyter token-by-default and "NOT RECOMMENDED" to disable (S-541); Chrome Local Network Access and its CSRF rationale (S-540); gemini devtools' own statement that cross-origin access "would let arbitrary websites exfiltrate logs (which may contain API keys/headers)" (S-119); OpenHands' rationale for first-message auth — tokens "out of URLs and therefore out of reverse-proxy / load-balancer access logs" (S-110); Cursor's async, non-blocking approval stance for long-running agents (S-052) motivating the inbox being a channel, not an authority; the ratified authority scheme forbidding far-side widening (ADR-0035 rule 1; CF-119).
- **(b) Source-code precedent:** inspect_ai `src/inspect_ai/_view/network.py` (`ViewerNetworkPolicy`, `HostValidationMiddleware`, `BrowserOriginMiddleware`, `SecurityHeadersMiddleware`) and `fastapi_server.py` (`_validate_mutating_request`, `authorization_middleware`, `standalone_view_app`) @75f4891 — P1, P3, P4, P5, P7; codex `codex-rs/app-server-transport/src/transport/{auth.rs, websocket.rs, unix_socket.rs}` @0735c51 (capability token / signed bearer with constant-time compare; loopback listener rejecting `Origin`; control socket 0600) — P2, P5, P11; goose `crates/goose-cli/src/cli.rs` L1810–1820, `crates/goose/src/acp/transport/mod.rs` (`AcpOriginPolicy`), `ui/desktop/src/{gooseServe.ts, backendCertificateVerifier.ts}` @fae91d0 (secret required to start; exact non-wildcard origins; cert pinning) — P2, P3, P11; software-agent-sdk `openhands-agent-server/openhands/agent_server/{sockets.py, middleware.py, _secret_redaction.py}` @3fc7b22 (first-message auth; loopback CORS; export redaction) — P8, P9; gemini-cli `packages/devtools/src/index.ts` @ed2ac40 (same-origin only) — P3. Counter-examples cited as such: opencode `packages/opencode/src/server/{auth.ts, mdns.ts}`, `packages/server/src/cors.ts`, `packages/app/src/context/permission-auto-respond.ts` @9f8db11 (optional password; mDNS; any-port loopback origin; client-side auto-accept); goose `gooseServe.ts` `buildLocalServeUrls` (token in URL); gemini devtools `/api/trigger-debugger` (unauthenticated loopback POST). The union as one floor is `no-precedent` (no audited surface implements all thirteen).
- **(c) Disconfirming evidence considered:** (i) Inspect allows unauthenticated loopback and Codex's loopback listener needs no token — both are read-only or browser-excluded designs; ours writes and must accept browsers (CF-361); (ii) Host validation alone defeats rebinding — true, but not same-host-different-port CSRF, and Chrome LNA is one browser behind a user permission; layered checks are cheap (Inspect implements all); (iii) a token on loopback is friction — one paste per launch, the Jupyter norm for a decade; (iv) fetch-metadata headers are absent in some clients — hence the *custom header* requirement as the client-independent layer; (v) desktop shells need `file://`/`null` origins — admitted only as *registered* origins at launch (goose's packaged-shell rule), never as defaults. None overturns.
- **(d) Conditionality:** single-principal local use at C1/C2; browsers that send fetch-metadata headers strengthen P3/P4 but the token and custom header do not depend on them; hosted participants and remote kernels are unaffected (the posture governs the surface process only); independent of model tier, task class and budget.
- **(e) Build-stage assignment:** C1/Stage 4 with the first surface slice (not deferrable — the battery ships with the read-only viewer because the inbox ships with it); the kernel-transport strict profile is WS-K4's C0/Stage-1 item; packaging of the token handoff is WS-L6 (OQ-389).

## Consequences

- Every local surface launch prints/handoffs a token; automation that drives the surface must obtain it from the launcher, never from a fixed value.
- WS-K4's transport profile for the kernel's raw listener rejects browser origins outright; the web surface is always a separate process.
- WS-H7 stamps `responder_provenance{surface_session_ref}`; WS-H6's `sink_deliveries` includes surface reads; WS-I1's `SinkPolicy` gains a `surface` sink kind with the OQ-392 defaults.
- The leak battery LT-01…12 (ADR-0059) gains a surface fixture set.
- Hosting the surface for multiple users, or advertising it on a LAN, requires a new ADR (P5/P6 make it an explicit, warned choice, not a configuration knob).

## Reversibility

**Medium.** Each rule is a configuration or middleware on the surface side and can be relaxed by ADR; reversing P2 (token on loopback) or P10 (no far-side decisions) would re-open the CVE-2025-49596 and CF-119 failure classes respectively, which is why they are stated as constitutional for the surface rather than as defaults.
