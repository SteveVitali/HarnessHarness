# ADR-0088 — The tool registry contract: immutable content-addressed capability versions, source-kind lifting with `unverified` provenance, refresh-as-supersession (rug-pull defence), snapshots, binding and catalog/search projections

**Status:** **ratified, amended** (Phase 2 synthesis, 2026-09-10)
**Owner workstream(s):** WS-E1 (consumers: WS-E3, WS-E4, WS-E5, WS-B5, WS-H1, WS-H5, WS-H6, WS-J2, WS-I3, WS-A4, WS-A5, WS-B1, WS-K1) · **Phase:** 2 · **Related:** ADR-0019 (stage 1 `link`; tool table), ADR-0021 (MCP lowering/lifting C0/Stage 3), ADR-0023/0024/0025 (`VariantRecord`; MUST-code; `verify_resume`; `registry_snapshot_id`), ADR-0026/0027 (events; allocated ids), ADR-0031 (idempotency key uses `capability_version`), ADR-0033/0034/0035 (`import` origin; P7; `pin`), ADR-0036 (identity kinds), ADR-0037 (I-rules, S-rules, name history, `resolve` modes), ADR-0038 (bundle `tools[]`; snapshot = closure), ADR-0048 (R-2.5.4 stage note), ADR-0050 §8 (SDK availability reference only); CF-195, CF-196; OQ-220, OQ-224, OQ-225; R-2.5.1, R-2.5.3, R-2.5.4

## Context

Doc 2 §11 asks for a registry of "typed capabilities, schemas, cost/risk metadata, MCP bridge, dynamic discovery". The audit (dossier §4 F1, F7, F8) finds that production registries are in-memory maps keyed by model-facing name, that tools arrive from at least five source kinds with different trust and lifecycles, that MCP listings are re-fetched per session/turn under `ttlMs` and `list_changed` with descriptions the client cannot authenticate, and that no audited registry versions a listing — which is exactly the "rug pull" class the MCP security literature names (S-310/-05/-06). Phase 1 already fixed the identity and lifecycle rules a registry must obey (ADR-0036/0037/0038) and the MCP lowering/lifting slice as C0/Stage 3 (ADR-0021, ADR-0048). This ADR instantiates those rules for capability records and fixes the operations the compiler, kernel, executors, Lab and WS-E3 call.

## Options considered

1. **In-memory name-keyed registry rebuilt per session (Codex, goose, opencode, OpenHands shape).** *Rejected:* no immutable version for the run manifest to pin (ADR-0038 N5); rename changes identity; a mutated listing is indistinguishable from the approved one.
2. **Registry as a plain document store of provider schemas with a hash per document.** *Rejected:* hashes the surface (name/description) into identity (T-LCD-10 failure) and carries no lifted-provenance rule.
3. **A separate "MCP bridge" registry beside the native one.** *Rejected:* two record kinds for one entity; the compiler's tool table and the kernel would need two code paths; MCP is one *source* of the same record (doc 3 §5 row; ADR-0021).
4. **One registry of immutable capability versions under ADR-0036/0037 identity and name history, a closed `CapabilitySource` sum with per-source provenance defaults, `refresh` as supersession, snapshots as closures, `bind` at link/environment creation, and surface-independent catalog/search projections (chosen).**
5. **Option 4 with a pluggable store.** *Rejected:* the store is MUST-code (ADR-0024: loader/registry semantics); only the *policy* (admission, trust, collision, refresh cadence) is a component class.

## Decision

1. **Store and identity.** The registry stores capability records immutably by `version_id` with `semantic_id` and a name history per `(namespace, name)` (ADR-0037 I1–I5, S1–S8). `resolve(selector, registry_snapshot_id?, mode)` follows ADR-0037 S3; `mode = execute` never returns yanked/revoked/stale heads. A publish whose diff vs `supersedes` has `authority_delta = widening` (effects grew, `world` opened, `mutability` rose, scope bindings dropped) requires `provenance.origin = human` + attestation.
2. **Sources.** `CapabilitySource = native_variant | procedure | mcp_listing{server_ref, listing_hash, tool_name_on_server, listing_ttl_ms?, imported_at} | provider_hosted | participant_supplied` (closed). Default declaration authority: `definition` (native, at `seal`; provider-hosted effects authored by the harness author), `unverified` (mcp_listing, participant_supplied). `import_listing` lifts an MCP `Tool` per ADR-0021/ADR-0034 P7: description → `external` `Text`; annotations → `EffectAttributes` with `unknown_domain` unless a pinned HarnessHarness `_meta` export supplies the `EffectClass` set; every declaration `unverified`; `listing_hash = H(canonical(Tool))`.
3. **Refresh is supersession.** On `notifications/tools/list_changed`, `ttlMs` expiry or session start, `refresh` re-imports; an unchanged `listing_hash` is a no-op; a change creates a new version with `supersedes{reason: edit}` and a `HirDiff.classification` (surface-only vs semantic; `authority_delta`). Definitions and runs that pinned the old version stay pinned; `verify_resume` (ADR-0025) reports `capability_changed_under_run{old, new, classification}`; a `pin` attestation names one `listing_hash` and never transfers. The kernel keeps the pinned declarations; behaviour of the changed tool is `unknown` until re-authorised. No new mechanism is introduced — this is ADR-0037 applied to listings.
4. **Snapshot.** `snapshot(refs) → registry_snapshot_id` over the referenced closure (ADR-0038); recorded in the sealed definition and bundle (`tools[] = {semantic_id, version_id, surface_hash per profile}`); `catalog`, `resolve` and `search_projection` are deterministic given a snapshot.
5. **Binding.** `bind(version_id, environment, executors) → ExecutorBinding | BindFailure` checks `execution_requirement` (environment class, isolation, interrupt, `dedup_support_required`, `env_requires` preconditions) against executor declarations (WS-E5/B5); called by the compiler's `link` to fill the Runtime Plan tool table (ADR-0019 stage 2) and by the runtime on environment (re)creation; ledgered as `lifecycle.component.bound{class_id = tool_executor}`. A capability record with no successful binding in an environment is `usability = unusable` in that environment's catalog view (OpenHands `is_usable` precedent), never silently dropped from the model surface — the compiler records it in the lowering loss report.
6. **Projections for neighbours.** `search_projection(version_id)` (surface-independent: `purpose`, parameter names/descriptions, effect domains, namespace) is what WS-E3 indexes; `catalog(filter, snapshot, page)` is the Lab/K1 view; `required_grants` and `project_risk` are derived views for `validate` and the kernel; `estimate` is the advisory cost view (ADR-3 of this workstream). None is stored primary (ADR-0026 rule).
7. **Policy is a component class.** `tool_registry_policy` (admission by source kind and trust record, collision policy, refresh cadence, exposure defaults) receives `(ModelProfile, ResourceAccount)` (T-LCD-08) and is MUST-data-parameterised; the store, `validate`, `register`, `resolve`, `snapshot`, `bind`, `import_listing`, `refresh` are MUST-code.
8. **Events.** `lifecycle.capability.registered/refreshed/revoked` are proposed to WS-B1 (OQ-225) with `{version_id, semantic_id, source_kind, registrar, supersedes?, classification?}`; every event class declares durability and observability level per ADR-0026.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: name-keyed registries with collision policy and exposure metadata — S-107 (`registry.rs` L287–330 `IndexMap<ToolName, RegisteredTool>`, `first_collision`; `tool_executor.rs` L51–130 `ToolExposure`, `search_info`); resolver-based registration with usability checks and duplicate-name warnings — S-110 (`registry.py` L95–205); prefixed MCP names with owner recovery, trusted-update meta key, cached listings — S-112 (`extension_manager.rs` L190, L299–321, L1754–1800); MCP listing lifecycle — S-153 (`CacheableResult.ttlMs` L1081–1096; `ToolListChangedNotification` L1895–1899; `tools.mdx` L59–73, L238–271) and client obligations (log usage, validate results, L787–815); rug-pull/tool-poisoning class — S-310 (Invariant Labs; mechanism follows from unauthenticated re-fetched descriptions), S-370/-06 (`provisional`, corroborating); content-addressed immutability and name histories — ADR-0036/0037 (S-224 git objects, S-225 Nix, S-227 SemVer via WS-L4); snapshot-as-closure — ADR-0038; multi-target export from one record — S-110 (`tool.py` L660–800 `to_mcp_tool/to_openai_tool/to_responses_tool`).
- (b) Source-code precedent: `openai/codex` `codex-rs/core/src/tools/registry.rs L280–330`, `codex-rs/tools/src/tool_executor.rs L51–130`, `tool_search.rs L18–32`; `OpenHands/software-agent-sdk` `openhands-sdk/openhands/sdk/tool/registry.py L95–205`, `tool/spec.py`; `aaif-goose/goose` `crates/goose/src/agents/extension_manager.rs L190–420, L1754–1800`; `anomalyco/opencode` `packages/opencode/src/tool/registry.ts L1–455`; `modelcontextprotocol` `schema/2026-07-28/schema.ts L1081–1096, L1779–1793, L1895–1899`. **`no-precedent / novel`** for: content-addressed capability versions with surface-excluded identity; versioned MCP listings with refresh-as-supersession and pinned-run protection; a closed `CapabilitySource` sum with per-source provenance defaults.
- (c) Disconfirming evidence considered: versioning ephemeral listings bloats the registry and pins the Lab to unreproducible server states — does not overturn because versions are hashes of small documents, GC follows ADR-0037 S8 (only executed/published versions retained), and an unpinned MCP tool is precisely the `unpinned[]` claim ADR-0038 requires; goose's `TRUSTED_TOOL_UPDATE_META_KEY` shows a legitimate need for in-place tool updates — accommodated as `refresh` producing a new version whose classification is surface-only and whose trust record inherits via WS-H5 policy (OQ-224), never as mutation; a pluggable store would let hosts reuse their own catalog services — rejected because the store's semantics (immutability, resolve modes, snapshot) are kernel guarantees, while a host catalog can still be a *source* through `import_listing`. Retrieval-quality claims (S-368) and catalog-scale claims (S-076, `provisional`) do not bear on this contract beyond motivating a surface-independent search projection.
- (d) Conditionality: independent of model tier and task class; assumes ADR-0036 `idp/1` hashing and a JCS-class canonical form for MCP `Tool` documents (ADR-0029/0015); MCP SDK availability for the ADR-0050 kernel ecosystem (S-155) is referenced only as protocol-SDK availability per ADR-0050 §8(b).
- (e) Build-stage assignment: **C0 / Stage 1** (store, `register`, `publish`, `resolve`, `lookup`, `snapshot`, `required_grants`, `project_risk`; native source; `bind` for kernel-internal and sandbox-helper executors); Stage 2 (`bind` to environment handles; usability probes); **C0 / Stage 3** (`import_listing`/`refresh` for `mcp_listing` — the ADR-0021/ADR-0048 C0 slice; AC-E1-5/-6); C1/Stage 3–4 (`search_projection`, `catalog` for WS-E3; `provider_hosted`); C2 (`procedure`, `participant_supplied`).

**T-LCD statement.** Satisfies T-LCD-04 (MCP is the second target; export/import round trip AC-E1-5), T-LCD-06 (`participant_supplied` is defined here; no dependency on the Hosting ABI), T-LCD-07 (lifted declarations `unverified`; `unknown_domain` never coerced), T-LCD-10 (versions keyed by content; names are histories; AC-E1-2), T-LCD-11 (lift recovers everything the `_meta` carried set holds; loss report otherwise), T-LCD-12 (every operation out-of-process over the canonical encoding; AC-E1-11), T-LCD-08 (`tool_registry_policy` receives the profile and accounting). Not applicable: T-LCD-01/-02/-03/-05/-09/-13/-14/-15 (no surface, rule, comparison or metric is introduced; the record's own T-LCD-01/-02 obligations are in ADR-1). ADR-0024 rung: store and operations MUST-code; policy parameters and source declarations MUST-data.

## Consequences

- The Runtime Plan tool table (ADR-0019) is populated from `bind` results keyed by `version_id`; WS-E5 executors accept `(effect_id, attempt_no, idempotency_key)` whose key already embeds `capability_version` (ADR-0031).
- WS-E4's MCP client is a transport for `import_listing`/`refresh`; its server side lowers registry records (ADR-0021). WS-E3 indexes `search_projection` and selects exposure per turn among compiled identities (closed-world rule).
- WS-H5 defines `pin` over `listing_hash`; WS-H6 audits `lifecycle.capability.*`; WS-J2 reads `catalog`; WS-I3 bundles `tools[]` and `registry_snapshot_id` as already specified in ADR-0038.
- `verify_resume` (ADR-0025) gains the `capability_changed_under_run` reason.

## Reversibility

**Medium-low.** Reverting to a session-scoped name-keyed registry would break R1+ reproducibility (ADR-0038), the rug-pull defence and the idempotency-key derivation; adding source kinds or projections is a dialect/contract bump (cheap).

## Amendment log (Phase 2 synthesis, 2026-09-10)

- Registry records carry `status ∈ {quarantined, sealed, revoked}`: capabilities lifted with `effects = unknown` or absent `preconditions` register as `unverified` + `quarantined`, are not model-visible until `seal`, where E1–E3/E7 run (ADR-0097; CF-210).
