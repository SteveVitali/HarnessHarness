# ADR-0084 — The Procedure/1 profile: HIR/1 `Procedure` extended only through a registered `ext` block; checkable preconditions vs applicability notes; tests through `validates` edges; model-free procedure validity; composition by resolve-time inlining; the HIR/2 promotion list

**Status:** **ratified** (Phase 2 synthesis, 2026-09-10)
**Owner workstream(s):** WS-D5 (consumers: WS-D1, WS-D3, WS-D4, WS-A3, WS-A4, WS-F1, WS-F3, WS-G1, WS-H1, WS-H5, WS-I5, WS-C3, WS-E2) · **Phase:** 2 · **Related:** ADR-0014 (three-valued validity), ADR-0015 (`ext` never decides authority/budget/validity; closed `ProcedureStepKind`), ADR-0016 (entity 5; V-EFF; `validates` edge), ADR-0017 (`derived-from`), ADR-0024 (ladder), ADR-0025 (`resolve`), ADR-0033/0034/0035 (authority; retrieval order; `promotion`/`validator` bases), ADR-0037 (supersession, `StaleIndex`); CF-038 (resolved here), CF-187/-05; OQ-023, OQ-049 (procedure kind), OQ-168, OQ-213/-05; R-2.4.5, R-2.4.3

## Context

Doc 2 §5.12 asks for a procedure that "can carry preconditions, expected evidence, allowed capabilities, failure handlers, provenance, version, and validation tests" and be "retrieved like a skill, compiled into model-facing instructions or deterministic workflow nodes"; OQ-023 asks whether a representation between prose and code supports "typed preconditions/effects, composition, retrieval, validation, migration, and repair". ADR-0016 fixed the HIR/1 `Procedure` (closed `ProcedureStep = Instruction | Invoke | Delegate | Branch | Loop | Verify | Opaque`, `preconditions`, `expected_evidence`, `allowed_capabilities`, `failure_handlers`, derived `effects`, surface `compile_hint`) and ruled (CF-038) that WS-D5 "extends only through `ext` slots or an HIR/2 dialect with migration; never by making `ProcedureStep` an open union". The audit of nine harnesses (dossier §4) found production skills already carry typed fields HIR/1 lacks — parameters (goose `skills/arguments.rs`; OpenHands `inputs`; MCP `PromptArgument`), dependencies and invocation policy (codex `skills/src/model.rs`), checkable path triggers (OpenHands `PathTrigger`) — and that unconditional procedures mislead (S-362, `provisional`: retrieving skills "paradoxically increases the model's confidence in wrong tool calls"). No audited system carries a test, an expiry or a provenance record on a skill.

## Options considered

1. **Bump to HIR/2 now** with a richer kernel Procedure (parameters, outputs, index, invocation policy, `Call` step, relation edges). *Rejected:* forces a dialect migration on every Phase 1 consumer before any procedure has been lifted or tested; the evidence for relation vocabularies is `provisional`; CF-038 asks for `ext` first.
2. **Keep procedures as `Text` leaves plus an index; no typing beyond the Agent Skills frontmatter** (the industry state). *Rejected:* no V-EFF coverage for scripts, no checkable preconditions, no tests, no model-free validity; fails T-LCD-02's ablation purpose and doc 2 §5.12.
3. **Open `ProcedureStepKind` through a registered step kind in `ext`.** *Rejected:* explicitly forbidden by ADR-0016/CF-038; compilers and diff classifiers would lose exhaustiveness.
4. **A registered `ProcedureProfile/1` `ext` block that carries only retrieval/parameter/policy metadata; fix the D5 semantics of the existing kernel fields; tests through the existing `validates` edge; composition by resolve-time inlining; file a HIR/2 promotion list (chosen).**

## Decision

1. **Extension block.** `ext["<hh-prefix>/procedure"] : ProcedureProfile/1 = {index{description: Text, retrieval_hints[Text], examples[Text], tags[Text]}, parameters[{name, type: TypedValueKind, required, description: Text, default?}], outputs?{schema_ref: Ref<Artifact>}, applicability_notes[Text], invocation_policy{model = true, principal = true, implicit = true}, failure_classes[FailureClass], target_override?{compile_hint, reason: Text}, composition[{callee: Ref<Procedure>, binding: ArgBinding, inline_at_resolve = true}], relations[{kind: registered, to: Ref<Procedure>}], source{extension_ref?, tree_path?}}` — closed schema, registered with WS-L6's prefix (OQ-068). Invariant (ADR-0015 preserved): nothing in the block decides authority, budget or validity.
2. **Kernel field semantics fixed.** `preconditions` admit a closed `Predicate = path_glob | capability_present | artifact_present | env_requires | validator_passed(ref, within) | parameter_bound | budget_remaining` — **checkable by the kernel from records** — or a `Ref<Validator>`; every other applicability condition is an `applicability_notes` `Text` leaf (BASM-class boundary prose) rendered to the model and never evaluated by the kernel. `failure_handlers[].on ∈ FailureClass = {precondition_failed, step_failed(step), validator_failed(ref), budget_exhausted, permission_denied, effect_unknown, timeout, delegate_failed}`, `then ∈ Handler = retry(bound: Ref<Budget>) | fallback(Ref<Procedure>) | compensate(Ref<Procedure>) | escalate | abort`; handlers total over `failure_classes` (`HandlerIncomplete`). `allowed_capabilities` is the closed set every `Invoke` references; for lifted skills it is populated only at `seal` (ADR-0086). Effectful procedures (`effects ⊄ read_only`) require `expected_evidence ≠ ∅` when their risk class contains `irreversible` or `scope = external` (`ProcedureUnverifiable`, error) and otherwise carry validity `unknown` until tests exist.
3. **Tests without a new field.** `ProcedureTestSuite(P) = {v : Validator | validates(v → P)}`; each such validator `depends-on` its fixture `Artifact`s (environment image digest, task text) and records the profile scope of its last run. `validity(P, at) = valid` iff every suite member has a `kernel`-recorded pass on its pinned fixture inside `P.validity` and no `depends-on` target is revoked/stale (ADR-0037 `StaleIndex`); `invalid` iff any recorded fail; `unknown` otherwise. Validity is model-free (ADR-0014); compliance (`activated`/`followed`) is measured per profile and target (ADR-0085).
4. **Retrieval and delivery.** Retrieval applies ADR-0034 P5 (validity → authority → readers → relevance) before any selector; a procedure whose checkable precondition is false at delivery is a D1 `Omission{reason: precondition}`; at `workflow_node` entry it is `PreconditionFailed` routed to handlers. `ProcedureSelector` is a registered component class (`select(view, catalog, profile, accounting, k) → Selection{method, ranked[], truncated}`; deterministic; reads index surfaces and records only; emits `context.procedure.selected`).
5. **Composition.** At HIR/1, `composition[]` is expanded at `resolve` (ADR-0025) by inlining the callee's steps with the binding applied, recorded as `derived_from{kind: projection}`; the call graph must be acyclic (`CompositionCycle`) and recursion is impossible by construction. `Call(Ref<Procedure>, ArgBinding)` is filed for HIR/2.
6. **Render purity.** A body may not contain a render-time execution marker or an `Opaque` step in its index; `validate` raises `RenderTimeExecution`. Dynamic content is a declared `filling` slot bound to a `ToolCapability` invocation with its own effect record (ADR-0019 closed-world rule).
7. **HIR/2 promotion list (filed):** `parameters`, `outputs`, `index`, `invocation_policy`, `FailureClass`/`Handler` sums, `Call` step kind, `ProcedureRelation` edge kind. Criterion for promotion: a kernel invariant or a Lab metric comes to depend on the field.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- (a) Mechanism evidence: typed skill fields exist in production and are absent from HIR/1 — parameters (S-112 goose `skills/arguments.rs`; S-110 OpenHands `inputs`; S-153 MCP `PromptArgument`), dependencies/policy (S-107 codex `skills/src/model.rs`), checkable path triggers (S-110 `PathTrigger`); unconditional procedures mislead and boundary fields repair them (S-362, `provisional`, mechanism only); contract-bearing procedural units with "verifier reachability" and "dependency closure" (S-363, `provisional`); procedures with typed relations and gated edits (S-095, `provisional`); executable skill libraries with self-verification (S-011, Tier A); doc 2 §5.12/§11 (Tier B synthesis); the three-valued validity and retrieval order are ratified (ADR-0014, ADR-0034).
- (b) Source-code precedent: `codex-rs/skills/src/model.rs` L8–95 and `core/src/mcp_skill_dependencies.rs` L1–80 (S-107 @0735c51); `openhands-sdk/openhands/sdk/skills/skill.py` L178–300, L732–800 and `skills/trigger.py` (S-110 @3fc7b22); `crates/goose/src/skills/arguments.rs` L1–60 (S-112 @fae91d0); `modelcontextprotocol/schema/2026-07-28/schema.ts` L1659–1687 (S-153 @aa8ce04); `AFlow/scripts/optimizer.py` L26–30 (S-025 @3f45721). The `Predicate` sum, `validates`-based test suite, model-free procedure validity and resolve-time inlining are `no-precedent / novel` as an integrated contract.
- (c) Disconfirming evidence considered: (i) the ecosystem converged on untyped bodies and reports value from them (S-039) — answered: the body stays a `Text` leaf; typing beyond the index is a ladder promotion gated by experiment; (ii) most applicability conditions are semantic, not predicates — answered: they remain notes with validity `unknown`; the design only insists checkable ones are checked and the two are labelled; (iii) `ext` is an escape hatch — answered: nothing in the block decides authority/budget/validity; every load-bearing element is a kernel field or edge; the block's size is reported. None overturns.
- (d) Conditionality: independent of model tier; assumes WS-L6 allocates the prefix; assumes coding/computer-use environments for the initial `Predicate` list (extended by dialect for other domains); the `provisional` papers motivate only the precondition split and the transfer gate.
- (e) Build-stage assignment: **C0 / Stage 2** (`ProcedureProfile/1` schema, `Predicate`, `validate_procedure`, `RenderTimeExecution`, C0 index-all selector, validity via `validates`); **C1 / Stage 3** (parameters/outputs in compilation, `test_procedure`, lexical selectors); **C2 / Stage 4–6** (`relations`, section-level bodies, HIR/2 promotion).

**T-LCD statement (ADR-0007 decision 5).** Satisfies T-LCD-02 (bodies and notes are `Text` leaves; `procedure_instruction` opacity bucket), T-LCD-08 (`ProcedureSelector` receives profile and accounting), T-LCD-10 (index description is a surface; identity excludes it), T-LCD-12 (operations only), T-LCD-13 (procedure validity is separable from per-profile compliance), T-LCD-14 (`test_procedure` refuses unbudgeted arms). Does not by itself satisfy T-LCD-01/-04/-11 (ADR-0085/-3 cover them) nor T-LCD-03 (Stage 3 executable). **ADR-0024 rung:** entity (rung 3) with the prose body at rung 2.

## Consequences

- WS-A3: `Predicate`, `FailureClass`, `Handler` are closed sums registered with the `ext` schema; `validate` gains `validate_procedure`; the HIR/2 promotion list enters the dialect backlog.
- WS-D1/D3: `procedure_index`/`procedure_body` candidates carry the block's `index`; admission evaluates checkable preconditions; the `procedures` slot has a `budget_share`.
- WS-G1: the `trace_predicate` validator family gains the procedure `followed` detector (ADR-0085).
- WS-H5: OQ-168 answered — `parameters`/`outputs` let structured results reach `environment` through `validator` endorsement while prose stays `external`.
- WS-I5: `induce` returns a Procedure version with `derived-from`, `origin = evolution`, validity `unknown`.
- Scope register: stage note on R-2.4.5 (CF-188).

## Reversibility

**High** for the block's contents (a schema version bump; no kernel change). **Medium** for the validity definition (consumers of retrieval order would need re-specification). **Low** for "tests via `validates`": moving tests into a dedicated field would be a dialect change touching every validator consumer — hence decided now.
