# ADR-0041 — Matched-budget comparison definitions (matched-cap, iso-cost, matched-total), engine refusal, and provenance-stratified capability-cost Pareto reporting

**Status:** **ratified** (Phase 1 synthesis, 2026-09-10)
**Owner workstream(s):** WS-L2 (with WS-J3 as enforcer, WS-J4/I2 as reporters, WS-I5 as consumer of matched-total, WS-I3/L4 for pricing-table pinning) · **Phase:** 1 (contract) / 3 (engine) · **Related:** ADR-0002 (matched-budget conditionality on C4), ADR-0004/0005 (class-scoped metrics, observability levels), ADR-0007 (T-LCD-09, -14, -15); WS-A2 (harness effect Δ at matched budget; factor space); WS-A1 F1 (cost-controlled planes: HAL, Harbor); CF-004; OQ-016, OQ-025, OQ-033, OQ-093, OQ-094, OQ-097; R-2.9.2, R-2.10.3, R-2.10.4

## Context

Doc 2 §8 makes budget accounting "non-negotiable" for adaptive methods: the relevant comparison is not "evolved harness after N expensive attempts against a static baseline with one attempt" but against alternatives with comparable inference, feedback and evaluation resources; *Rethinking Harness Evolution* (S-083, `provisional (counter)`) shows this can reverse conclusions. T-LCD-14 (ADR-0007) requires the experiment engine to refuse any comparison whose arms lack an explicit, matched budget, with `search_budget` and `eval_budget` per arm in the results schema. WS-A2 defines the only reportable effect quantity as the paired difference at matched budget. Cost-controlled comparison planes exist (HAL, Tier A; Harbor; Kapoor's accuracy–cost Pareto), but none defines *what "matched" means across budget dimensions, models and cost provenances*, and the audit shows tokens are not a common unit across models or even across metering conventions (Codex weighted tokens vs Anthropic "novel tokens seen" vs billed tokens).

## Options considered

1. **Single "budget" scalar (dollars) matched across arms.** *Rejected as sole mode:* prices drift and differ by serving route; provider-reported costs are unauditable; S-083 matches feedback and inference budgets, not dollars.
2. **Token-matched only.** *Rejected:* tokens are model- and tokenizer-specific and provider metering differs; cross-model token matching is ill-defined.
3. **Leave matching to the experimenter (warn, don't refuse).** *Rejected:* T-LCD-14 requires refusal; CF-004's resolution makes matched budgets mandatory for C4 claims.
4. **Three declared modes over a declared dimension set, with a pinned pricing table for spend, engine refusal on ill-typed matches, and provenance-stratified reporting (chosen).**

## Decision

1. **`MatchSpec{dimensions: [DimensionId], mode ∈ {matched_cap, iso_cost, matched_total}, tolerance, pricing_table_ref?, model_scope ∈ {same_snapshot, cross_model}}`** is mandatory on every experiment arm alongside `search_budget: BudgetSpec` and `eval_budget: BudgetSpec`.
2. **M1 matched-cap:** identical hard ceilings on the declared dimensions across arms; per-arm consumption distributions and `budget_utilization = consumed / hard` are always reported (an under-utilising arm is not "cheaper"). Admissible on any kernel dimension under `same_snapshot`; under `cross_model` only on `spend`, `time.*`, `model_calls`, `tool_calls`, `approvals.*`.
3. **M2 iso-cost (cost-controlled frontier):** arms compared at equal *realized* consumption via `P(success | consumed ≤ c)` curves and the capability–cost Pareto frontier; rows whose spend `confidence = estimate` or `coverage < 1` are stratified out of the exact frontier and shown as a band.
4. **M3 matched-total (adaptive/evolving methods):** `total = search_budget + eval_budget + inference_budget` equal across arms; the search-produced artifact is frozen and evaluated under `eval_budget` only (artifact benefit), search-time benefit reported separately; the baseline arm receives the same total as test-time compute. Required for every C4 (WS-I5) claim (ADR-0002 (d)).
5. **Common rules:** matched dimensions use the same `MeteringFormula` across arms; spend matching requires one pinned pricing table version and reports `provenance_mix` per arm; heavy tails (exhaustion rate, p95/p99 consumption) are reported, never only means; the frontier is computed per `charged_to = subject` with `instrument` cost reported beside it.
6. **Refusal semantics:** the engine refuses to run or report with typed errors — `UnbudgetedArm`, `IncommensurableMatch` (e.g. cross-model token match, differing metering formulas), `MissingPricingTable`, `MissingMatchSpec` — never warns (T-LCD-14 engine precondition).
7. **Cache warmth** is recorded on every model call (`warm | cold | unknown`) and is either controlled (cold start per run) or a stratification factor; an experiment must declare which (OQ-097).
8. **T-LCD statement.** Satisfies T-LCD-14 (refusal; `search_budget`/`eval_budget` fields), T-LCD-09 (budget is an explicit factor with distributions), T-LCD-15 (efficiency metrics declare observability and class; `n/a` for hosted rows lacking usage). Does not decide cross-model token normalisation — recorded as OQ-094 with spend as the only admitted common unit meanwhile.

## Evidence (doc 3 §3.3 synthesis contract — all five mandatory)

- **(a) Mechanism evidence:** unmatched search budgets reverse conclusions (S-083, `provisional (counter)`; doc 2 §8 standard); accuracy-only benchmarking yields costly agents and joint accuracy–cost optimisation is necessary (S-207, 2024); cost is non-monotone in effort (S-135, Tier A); token metering conventions differ (Codex `sampling_token_weight/prefill_token_weight`, S-107; Anthropic novel-token countdown, S-214; Inspect formula metering, S-136); cache warmth changes spend for identical prompts (S-213 TTL semantics); evaluation budget itself can be allocated adaptively (S-082, `provisional`).
- **(b) Source-code precedent:** hal-harness `hal/agent_runner.py` + `hal/utils/weave_utils.py` (cost-controlled runs; cost reconstruction per task; judge cost excluded); harbor `models/job/config.py JobConfig{agents[], tasks[], n_attempts}` + `models/trial/result.py compute_token_cost_totals` (agents × tasks × attempts with per-trial cost); inspect_ai `util/_limit.py apply_limits/sample_limits` (uniform per-sample limits across solvers) and `agent/_run.py` (limits per agent run); codex `core/tests/suite/rollout_budget.rs` (weighted-token budget under test). The `MatchSpec` with three modes and refusal semantics is `novel as integrated` (no audited plane distinguishes matched-cap from iso-cost from matched-total, nor stratifies by cost provenance).
- **(c) Disconfirming evidence considered:** dollar matching is fragile (prices, routes, unauditable reports) — mitigated by pinned tables and provenance stratification, and by admitting raw-resource matching within one snapshot; token matching is ill-defined across models — accepted, refused by the engine; strict refusal may block exploratory runs — accepted: exploratory runs may be *executed* with a `MatchSpec{mode: none}` but never *reported as a comparison* (the refusal is on reporting Δ, matching T-LCD-14's wording "run or report a comparison"). None overturns.
- **(d) Conditionality:** M1/M2 hold for any model tier; M3 is required only for adaptive/search-based methods (C4); cross-model matching assumes a pricing table covering every arm's models; cache-warmth control assumes providers expose cache state (else `unknown` and stratified).
- **(e) Build-stage assignment:** schema (`MatchSpec`, `search_budget`, `eval_budget`, results fields) C0 / Stage 1; engine refusal and M1/M2 reporting C0 / Stage 3 (evaluation-first, before profiles and evolution); M3 gates used by WS-I5 at C4 / Stage 6; cross-model exchange rates (if any) C1 pending OQ-094.

## Consequences

- WS-J3 implements refusal preconditions and per-arm root budget allocation from `eval_budget`; WS-J4/I2 implement frontiers, utilisation, exhaustion rate and provenance bands; WS-J5's results row carries the T-LCD-14 fields.
- WS-I5's evolution pipeline must express every gate as M3; ADR-0002's "matched-budget acceptance criteria, never absolute" becomes concrete.
- WS-I3 pins the pricing-table version in the bundle; WS-L4 content-addresses it; WS-C4 exposes cache state.
- WS-A2's `harness effect Δ` gains a `MatchSpec` reference; the readiness matrix row for T-LCD-14 can be encoded.

## Reversibility

**High** for the mode set (adding a mode is additive) and **medium** for refusal semantics (relaxing refusal to warning is a one-line policy change but would re-open CF-004). Results recorded without `MatchSpec` cannot be retroactively made comparable — which is why the schema lands at Stage 1.
