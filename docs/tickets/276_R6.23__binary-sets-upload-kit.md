## Goal

Make true, offline, the two controller-side artifact paths that ride on `hh-receipt-index/1`'s pass-level `artifacts` section: (1) spec §5.2's "build once, carry by digest" rule (REQ-XC-330) — the infrastructure and H binary sets, bundles and layers are built at most once per pass, exported with sha256 into the harvested run root and the index, loaded in later windows over the IAP path and verified by image ID, with slot-identity digests and a typed refusal for any mismatch or ungated rebuild; and (2) spec §4.10's per-window upload kit (REQ-XH-102…104, REQ-XH-107) — the admitted upload tool, the pre-upload secret + live-credential scan, read-back verification and the ordered post-upload remediation procedure. Nothing is built, uploaded or loaded for real here; the window skeletons (R6.32, R6.40, R6.44, R6.45, R6.47) execute these paths after their gates.

## In scope — deliverables

**Stage 1 — BINARY-SETS** (commit checkpoint at the end of the stage)
1. Pinned-container build recipe for the infrastructure set (runner, helper, relay, `hh-model-proxy`, egress mediator) and the H set (`hh-kernel` participant build plus HIR and compiled artifacts, the phase-4 level's included), each producing one set digest (REQ-XC-330).
2. Export path for layers, bundles and binary sets (`podman save`, or harness-specific blobs plus the image config with base blobs re-pulled by digest) into the harvested run root with sha256, written as `artifacts` entries through R6.12's codec; the export size feeds the exporting window's egress quote line as a labelled quantity (REQ-XC-330, REQ-XH-118 input).
3. Load path from the controller (IAP copy via R6.13's recipe, `podman load`, base-blob re-pull by digest), timed, then image-ID (config digest) verification; a RepoDigest is never the identity (REQ-XC-330).
4. Slot-identity digests: the slot record carries the image ID, the infrastructure-set digest and, on HH-native and V5 slots, the H-set digest frozen at G-L1 (REQ-XC-330).
5. Refusals: a mismatched image ID → `withheld{admission:harness_layer_mismatch}`; a rebuilt carried artifact without a gate record refuses (new participant / runner version) (REQ-XC-330).
6. Proprietary-bundle rule: a bundle or layer containing Claude Code is a `digest_only` index entry, its bytes stay on the controller, unless an operator redistribution record exists (REQ-XC-330).

**Stage 2 — ARCHIVE (b): upload kit** (commit checkpoint)
7. Upload-tool admission record (AR-20 completion) and a controller-only upload command: refuses unless the window's harvest manifest verifies; HF token read at use from `HH_OPERATOR_ENV_FILE`, passed per invocation, never printed or persisted, no `login`; private dataset only; an upload receipt citing the tool admission with a `provided` block (REQ-XH-102, REQ-XH-023).
8. Pre-upload scan: the repository detector set plus the live-credential mask set (Ollama key, HF write token, controller GCP credentials) via `hh-secret-scan` (CC1); a live hit refuses the file and stops the row; a slot token passes in raw files only with its `security.credential.revoked` row and is tombstoned in every derived file; an unrevoked token is a live hit (REQ-XH-103).
9. Read-back verification of every file's sha256 against the index → `archive_verified` | `inconclusive{readback_unavailable}`; append-only revisions; a re-upload supersedes by reference (REQ-XH-104).
10. Remediation procedure and its machinery: the HUMAN rotation row (`provided: yes/no`), the operator-recorded purge record, then the tombstone/supersede index entry, in that order, with no secret value (REQ-XH-107).
