# ADR-0391: R5.12 whole-vector Account reserve — landing decisions

- **Status:** Accepted
- **Date:** 2026-11-02
- **Ticket:** R5.12
- **Requirement ids:** REQ-E-207, REQ-D-006 (contributing; primary owner of both is R5.19 AC-3 — no full-target claim)
- **Spec:** docs/evidence-and-adoption-spec.md §2.4 + AC-2-3; PADR-R5-2 (admitted GATE-G9, packet B — B.1 item 3, B.3, B.5, B.9 items 3–4); decomposition row 28 (whole-vector reserve, budget owner); ticket docs/tickets/181_R5.12__reserve.md
- **Rung (ADR-0024 obligation):** implementation landing record — the admitted whole-vector `reserve` admission's concrete shape inside `hh-budget`; no RPC, no wire/schema/class change, no new dependency

## Context

PADR-R5-2 B.1 item 3 admits: "Account `reserve` checks **projected
derived totals** on every ancestor — consumed usage, outstanding and
new primary holds, and slice holds … Admitted primary token categories
only are charged; `tokens.input/output.total` stay derived
(REQ-E-207)." B.3 fixes "no new primary dimension" and keeps
usage/dedup facts under the existing `control.budget.*` +
`measurement.cost.attributed` families. The landed baseline checked
only the *primary* bound keys named in the request vector — a
`tokens.input.total` ceiling never bound anything. The landing choices
below are this ticket's owned decisions inside the admitted semantics.

## Decision

1. **Every bounded key on every ancestor is projected, primary or
   derived.** `Account::reserve` iterates `path(budget_id)` (leaf→root)
   and, per node, every `spec.dimensions` entry carrying `hard`, in
   `DimensionKey` canonical order. The violation reports the first
   failing (node, key) in that order as
   `InsufficientBudget{dimension: key, requested, available}` — the
   admitted refusal member, unchanged.
2. **The projection reuses the owning fold — no parallel total.**
   `projected = BudgetTree::level(node, key) + quantity.key_total(key)`;
   `level` is `consumed + reserved + slice_held` and `key_total`
   evaluates derived names over stored primaries
   (`DerivedDimension::components`). `tokens.*.total` are never
   chargeable (`ResourceQuantity.dimension` is `DimensionId`, primary
   only) and never stored in any vector.
3. **`>` preserves the exact boundary.** `level + requested == hard`
   admits; only a strict overshoot refuses. A hard key the request does
   not touch contributes `requested = 0`, so it refuses only when
   conservation is already breached there (`level > hard`) — a node at
   its cap on an unrelated key still admits.
4. **Gauge hard keys are skipped exactly as `BudgetTree::check` skips
   them.** Gauges cap the next increment via E5 (`gauge_reserve` /
   `GaugeCapExceeded`), never reserve — a slice child's affine gauge
   hold in `slice_held` cannot turn a vector reservation into a gauge
   admission. Gauge dims *in the request* still refuse
   `DimensionNotBudgetable` before any row is minted.
5. **The refused row is the durable fact; refusal holds nothing.**
   `control.budget.reserved{outcome:"refused"}` is ledgered (the AC-4
   convention — refusals are facts) and folds to no claim; only
   `outcome:"held"` enters `reservations` and `reserved` aggregation.
6. **`requested`/`available` report the request's key contribution and
   the pre-request remaining.** For a derived key `requested` is the
   `key_total` component sum of the request (e.g. 110 = uncached 60 +
   cache_read 50) and `available` is `hard − level` — the refusal names
   the bound that failed, never a component of it.

## Consequences

- The whole-vector admission is enforced at the one authority
  (`Account::reserve`); every existing caller (router G-4 candidate
  selection, env dispatch, subagent spawn, fleet engine) gains the
  derived-cap check without a call-site change.
- An ancestor already over any bounded key (e.g. after a tighten
  amendment or an `over_reservation` charge) refuses all new holds —
  the conservative reading of atomic admission; at-capacity untouched
  keys admit.
- A slice child's derived ceiling over-holds component-wise at the
  parent (the existing affine `slice_held` fold); the projected check
  inherits that conservatism — recorded, not relaxed, here.
- Consumer wiring (the fixed order's earlier/later legs) stays owed to
  R5.19; the deduplicated incurred-use fold to R5.13 — decomposition
  row 28's sibling operation.

## Alternatives considered

- The baseline per-request-dim primary-key scan — rejected: derived
  bound keys never bound, so `tokens.input/output.total` ceilings were
  dead letters (the admitted defect this ticket fixes).
- Root-first reporting (mirroring `check`'s outermost convention) —
  rejected: leaf→root preserves `reserve`'s established iteration order
  and names the innermost violated bound; the refusal *set* is
  identical either way (atomicity is unchanged).
- Refusing only the keys the request touches — rejected: the admitted
  text is "checking every ancestor hard key"; admitting new holds on a
  node whose conservation is already breached would weaken the
  pre-dispatch guarantee.
- Persisting a projected-total row or a new derived-dimension counter —
  rejected: derived totals are views evaluated by the fixed
  `MeteringFormula`, never stored primaries (§8.2; REQ-E-207 tail).

## Revisit triggers

- If R5.19's prepared-call ordering requires reservations to admit on a
  node that is already over an *unrelated* bounded key (dispatch under
  an acknowledged breach rather than refusal), revisit the
  untouched-key clause (Decision 3).
- If gauge admission semantics move from E5 increment checks into the
  vector path (e.g. gauge-aware reservations), revisit the gauge skip
  (Decision 4).
- If the affine `slice_held` fold is relaxed for derived keys
  (component-wise worst-case hold → whole-vector hold), revisit the
  expected `level` arithmetic in `tests/r5_12.rs`'s slice legs.
