# ADR-0361: R3.8 blob-pool AEAD — the `HHBE` frame, the `BlobCipher` custody seam, and the plaintext-address rule

- **Status:** Accepted
- **Date:** 2026-10-16
- **Ticket:** R3.8
- **Requirement ids:** BL-45 · DF-S1.15-3 · R-2.8.6 · ADR-0345 (revisit
  trigger (a) — **fired and answered** by ADR-0359's reservation +
  this construction) · ADR-0359 (D2 reserved scope — **consumed**;
  no sibling dep ADR needed) · OQ-170 · CC1 · CC3 · CC10
- **Spec:** §5g.6 §9's C2 row ("blob encryption with per-event keys",
  consumed from R-2.8.3's custody vocabulary) and I-A8 ("hashes are
  over plaintext bytes at `put_blob`; a decryption failure reports
  `missing{reason = key_unavailable}`, never `tampered`").
- **Rung (ADR-0024 obligation):** C2 — the §5g.6 §9 row assigns blob
  encryption to C2/Stage 4+; the mechanism lands now because the H5
  ruling made a conforming primitive available, and every surface it
  adds is fixture-verified inside the offline ceiling.

## Context

BL-45 carried the last DF-S1.15-3 cell — per-event blob encryption —
blocked since minting on the pure-std contract: no conforming AEAD
construction exists in the standard library, and inventing one would
fabricate cryptography (CC3). The operator's HUMAN-H5 ruling
(2026-10-14) admitted a vetted external crypto crate, and ADR-0359 D2
pinned `ring =0.17.14` with `ring::aead` and `ring::rand::SystemRandom`
explicitly **reserved for R3.8 under the same ADR** — R3.8 consumes the
pin if its design stays inside that scope, else authors a sibling ADR.

Two design questions the reservation does not answer:

1. *Where does the producer live?* ADR-0359 scopes `ring` to
   `hh-secrets` ("the only workspace member that may name `ring`"), but
   §5g.6's seam is the blob pool in `hh-ledger` (CC10: no second store,
   and dependencies point downward — `hh-secrets` already depends on
   `hh-ledger`, never the reverse).
2. *What does the content address cover, and how do reads type their
   failures?* I-A8 fixes the plaintext-hash rule and the
   `key_unavailable` typing, but the frame format, the per-event key
   schedule, and the residency↔declaration accounting are the ticket's
   own decisions.

## Decision

- **D1 — the `BlobCipher` seam keeps `ring` inside `hh-secrets`; the
  trait and frame codec live in `hh-ledger`.** `hh-ledger::cipher`
  declares `trait BlobCipher { algorithm, key_id, seal, open }` plus
  the `HHBE` frame codec; `hh-secrets::aead::RingBlobCipher` is the
  one admitted impl (CC1) over `ring::aead::AES_256_GCM`. The ledger
  depends on nothing new; `Cargo.toml` gains **zero** dependency
  lines — ADR-0359's reserved scope is consumed as written, and no
  sibling dep ADR is needed. Custody mirrors the signer seam
  (`AuditSigner`/`AuditKeyResolver`): `Store::set_blob_cipher` is the
  install point, the ledger sees `seal`/`open` and the content-free
  `algorithm`/`key_id` coordinates only, and no key bytes ever enter
  ledger state (OQ-170 — `n/a{custody}`; the live
  `CredentialBroker::kernel_use` resolution leg rides BL-30).
- **D2 — the `HHBE` v1 frame.** Stored bytes are
  `"HHBE" ‖ ver:u8 ‖ len-prefixed {alg, key_id, nonce} ‖ ciphertext‖tag`.
  The header is readable without key material so `blob_status` /
  `audit_view` report sealed residency honestly; the whole encoded
  header is the AEAD's associated data, so a tampered `key_id`/`alg`
  refuses at `open` exactly like a body tamper.
- **D3 — per-event keys without `ring::hkdf`.** The cipher holds one
  resolved 32-byte master key; each blob seals under
  `HMAC-SHA256(master, "hh-ledger/blob/v1" ␟ address)` — the
  HKDF-expand-shaped single-block derivation over the workspace's
  admitted HMAC (`hh_wire::sha256::hmac_sha256`, CC1). `ring::hkdf`
  would exceed ADR-0359's named scope; the admitted-HMAC expand stays
  inside it. Fresh 96-bit nonces come from `ring::rand::SystemRandom`
  (the ADR's reserved nonce-generation scope). A frame replayed under
  a different address refuses — the per-event binding §5g.6's C2 row
  names.
- **D4 — content addressing and the residency codecs.** The file is
  still `blobs/<digest>` where the digest covers the **plaintext**
  (I-A8); `put_blob` computes the address before sealing, so identical
  plaintext deduplicates to one sealed file (first-write wins on the
  fresh nonce). A sealed frame is not an `HHZ1` residency-codec
  subject — ciphertext does not compress — so `set_blob_compressed`
  returns `false` honestly on `HHBE` bytes while the durable
  `lifecycle.ledger.tier_transition` row still records (ADR-0333's
  accounting is unaffected). GC and redact compose unchanged: the
  tombstone names the plaintext address before the bytes retire.
- **D5 — typed failure classes (I-A8, binding).** A malformed `HHBE`
  frame is `BlobCorrupt` (structural corruption — the undecodable-
  `HHZ1` class); a well-formed frame that cannot be opened — no
  cipher installed, foreign `key_id`, wrong key bytes, or an AEAD tag
  failure — is `Missing{reason: key_unavailable}`, **never
  `Tampered`** (ADR-0068 R3); a `seal` failure is the new typed
  `LedgerError::CipherFault`, never a silent plaintext write under a
  declared seam (CC3); and the post-open digest re-check still runs —
  a non-authenticating cipher's output that does not hash back is
  `BlobCorrupt` (the defense-in-depth half the fixture battery
  exercises).
- **D6 — the audit surface: declaration + coverage, honestly folded.**
  `RunManifest.blob_encryption{alg, key_id}` carries the durable
  declaration from seq 0 (the ADR-0345 D2 manifest-declaration
  precedent; a spawned child inherits it — `hh-subagent`'s spawn
  manifest). `BlobStatus::Sealed{key_id}` reports sealed residency
  from the frame header alone — no key material needed. `audit_view`
  gains the `encryption` member: `{declared, installed, refs_sealed[],
  refs_unsealed[], status}` with `status ∈ {enforced, unenforced,
  undeclared, n/a{no blob_encryption declared}}` — declared +
  every resident ref sealed under the declared `key_id` is `enforced`;
  resident plaintext or foreign-`key_id` frames are `unenforced`;
  sealed residency without a declaration is `undeclared`. The member
  joins `completeness.encryption_ok` and the headline veto — never a
  fabricated `enforced`, never a `false` by absence. These three
  pieces — the durable declaration, the residency status, the
  coverage fold — **are** the non-custody R-2.8.6 emission legs
  re-homed from BL-21/BL-45: the custody-riding legs (live
  `kernel_use` key introduction, custody-backed policy) stay on
  DF-S2.5-1/BL-30 + DF-S1.15-1/BL-05 and are not pulled in.

## Consequences

- `Store::put_blob` seals every write while a cipher is installed;
  `Store::get_blob` opens `HHBE` frames, decompresses `HHZ1`, and
  verifies the plaintext digest either way — the file layout is a
  three-way self-describing frame set (`HHBE` / `HHZ1` / raw).
- `LedgerError::CipherFault` joins the typed refusal set (documented
  per ADR-0233's convention).
- `BlobStatus` gains `Sealed{key_id}` and drops `Copy`; consumers
  (`hh-results` citation/leaderboard checks, `hh-ledger`'s replay
  coupling) treat sealed residency as present — bytes are held; an
  unopenable frame fails at read time, not at residency accounting.
- `audit_view` gains a `cipher` parameter and the `encryption` member;
  the schema's view payload shape grows honestly (the member is part
  of the signed view preimage like every other component).
- The workspace still fetches nothing new: `Cargo.lock` is unchanged
  (`ring`'s graph was already pinned at R3.7).
- Key custody is unchanged — `n/a{custody}`: the batteries install
  fixture constructions only; a custody-resolved install is a BL-30
  leg.

## Alternatives considered

- **Encrypt under a content key store / second pool** — rejected:
  CC10 says the encryption/decryption seam lives in the one blob
  pool; a second store would fork the residency accounting and the
  tombstone machinery.
- **Address over ciphertext** — rejected: I-A8 fixes hashes over
  plaintext at `put_blob`; ciphertext addressing would also break
  dedup (fresh nonces) and force every citation to know the nonce.
- **Deterministic (nonce-misuse-resistant) construction** — rejected:
  `ring::aead` offers no SIV mode inside the admitted scope, and
  deterministic sealing would leak plaintext equality anyway (dedup
  already does); fresh random nonces are the honest construction.
- **`ring::hkdf` for the per-event keys** — rejected: outside
  ADR-0359's admitted scope; the admitted `hh-wire` HMAC expand covers
  the derivation with zero scope growth.
- **A `lifecycle.ledger.blob_sealed` audit row per put** — rejected:
  the frame header *is* the durable residency evidence, the manifest
  declaration carries the claim from seq 0, and a per-blob row would
  duplicate both while scaling the WAL by pool size; `audit_view`'s
  `encryption` member is the coverage fold, matching how `gc`/
  `redacted` rows compose with tombstones rather than duplicate them.

## Revisit trigger

Reopen when (a) key custody lands (ADR-0213/OQ-170 resolution —
BL-30): the seam becomes a live `kernel_use` resolution and the
`n/a{custody}` bounds lift; (b) a custody coordinate rotation needs
multi-`key_id` frames or re-sealing semantics; (c) ADR-0359's scope
needs widening (e.g. `ring::hkdf`, a second construction, or a
second crate) — a sibling dep ADR then owns the amendment.
