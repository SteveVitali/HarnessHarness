# ADR-0411: R5.33 offered-answer respond gate and O4/O5 permission cells — landing decisions

- **Status:** Accepted
- **Date:** 2026-11-03
- **Ticket:** R5.33 (Real permission wait, answer and resume matrix)
- **Requirement ids:** none primary — contributing-only slice: REQ-B-105,
  REQ-C-006, REQ-D-203, REQ-D-204, REQ-D-205, REQ-D-206, REQ-D-207,
  REQ-E-012, REQ-E-110, REQ-E-205 (full-target R/P and actual-execution
  predicates stay owed to primary owner R5.44 AC-1 per the coverage
  register)
- **Spec:** docs/evidence-and-adoption-spec.md §5 (s5 O1–O8 cells, counts
  and limits); docs/tickets/203_R5.33__permission.md; design D3 O4/O5;
  O2 partition packet (env dispatcher + monitor responder + apparatus

- **Rung (ADR-0024 obligation):** implementation landing record — the
  fold-level offered-answer authority (a semantic tightening of the
  shared respond contract), the O4/O5 evidence-cell vocabulary and
  folds; no RPC, no schema, no new dependency, no new event class,
  no store/dispatch authority

## Context

§5.2 and D3-O4/O5 require the permission cells to exercise a **real
dispatch-produced wait**: `security.permission.pending` → suspend → a
host answer checked against the *durable offer* and the endorser's
authority → `permission_decided` wakeup → resume on the same effect
with exactly one mutation — and the negative matrix where deny,
unoffered, unauthorized and conflicting answers can neither grant nor
mutate. The respond contract's definitional clause is "reject unoffered
answer". Before this ticket the durable row had written
`request.options` since ADR-0343 D4, but `ApprovalState::fold`'s
pending arm **dropped** them (`options: Vec::new()`), and
`respond_inner` had no membership check — the folded pending could not
say what had been offered, so an offerless conferring answer
(`allow_lease` when only `allow_once`/`deny` were offered, `modify`
never offered) would decide and mint. The embed layer's
`OptionNotOffered` is session/surface-side only; the monitor — the
authority the durable record answers to — enforced nothing. The env
cells also had no `PermissionFailure`/`o4_outcome`/`o5_outcome`
vocabulary to evidence the cells. This is an existing-contract repair
inside the ticket's own deliverable — the same class as R5.24's R0
fold repair and R5.28's K-2 fix — not a new contract: ADR-0343 D4
already owns the durable `request.options` member; this ADR owns the
fold/respond semantics that make the written member load-bearing.

## Decision

1. **`ApprovalState::fold` folds the durable offer.** The
   `security.permission.pending` arm parses `request.options[]` ids
   into `ApprovalPending.request.options` (each id → `ApprovalOption`
   with `label = id.as_str()` — the label is informational; the id is
   the authority). An unparseable id **drops, never widens**; an absent
   `options` member folds empty, so pre-R2.11 durable rows stay
   ungated (backward compatibility over the recorded format).
2. **`respond_inner` gains the offered-membership gate.** When the
   folded offer is non-empty, a conferring or option-consuming answer
   must be a member: `allow_once`, `allow_lease`, `modify` and
   `more_info` are checked against `request.options`; `remedy` is
   checked against `request.remedies`. An answer outside the durable
   offer **restores the pending** and refuses with the typed
   `ApprovalError::UnofferedOption{option_id}` — it never decides,
   never mints a `decided`/grant, never mutates.
3. **Decide-against answers are exempt.** `deny`/`cancelled` confer
   nothing — a refusal grants nothing — and the wire's deny spellings
   (`deny_once`/`deny_lease`, `abort_run`) predate the closed option-id
   set, so gating them would break admitted compatibility. The gate
   runs **before** the legitimacy gate: an unoffered answer from even
   a legitimate endorser restores the pending unanswered.
4. **The env cells name every way the wait can fail.**
   `crates/hh-env/src/ops.rs` (read-only, ADR-0410 confinement
   unchanged) gains the closed `PermissionFailure` set
   (missing_pending, mutation_during_wait, missing_wait_interval,
   lost_pending, missing_wakeup, missing_decision, second_mutation,
   digest_mismatch, non_idempotent_answer, conflicting_grant,
   unoffered_admitted, unauthorized_admitted, deny_mutated,
   sentinel_mutation) and the pure folds `o4_outcome`
   (`PermissionWaitCell`: durable pending carrying the offered set,
   ≥2 clean no-mutation intervals, restart-preserved pending,
   `occurred`→`fired` wakeup, durable `decided`, exactly one marker
   with matching digest, idempotent identical re-answer, conflicting
   new-key refusal, intact sentinel) and `o5_outcome`
   (`PermissionDenyCell`: pending → offered `deny` → `decided{deny}`
   → refused resume with zero mutation; a conflicting later answer
   authorizes nothing). `PermissionOutcome` is `Pass` or
   `Failed(PermissionFailure)` — no member launders a negative into
   a pass.
5. **The battery drives the real seams.** `tests/r5_33.rs` runs the
   real `Store`/WAL, the real Π `Monitor`, the `Dispatcher`'s
   irreversible `PermissionRequest` ask, `MarkerSink`/`OpsObserver`/
   `Sentinel` from R5.32's apparatus; answers go through the real
   `ApprovalState::respond_with_ctx` + `decided` mint under the fenced
   writer, `store.deliver_wakeup` (occurred→fired) and same-input
   re-dispatch (the resume leg via `decision_for_effect`).
6. **`input_required` is not mediation.** The paused-`input_required`
   leg proves the label cannot stand in for the O4 wait — that effect
   may already be `committed`; only the pending→answer→wakeup chain
   evidences permission mediation.
7. **Recorded finding — the session-side scan.** `service.rs:1967`
   (hh-embed) hardcodes the four-option presentation in its session
   scan; it predates the closed option-id set and is contained by the
   fold-level gate (the monitor refuses what the surface might
   optimistically offer). Recorded for a later owner's session-scan
   repair; not this ticket's deliverable, no runtime consequence while
   the gate holds.

## Consequences

- The monitor's respond authority is now honest over the durable
  record: what the `pending` row offered is what the answer may name;
  an offerless conferring answer restores the pending instead of
  deciding.
- Pre-R2.11 durable rows (no `options` member) keep working — the
  gate engages only when a non-empty offer is folded.
- The O4/O5 cells have labelled, falsifiable folds: every negative in
  the matrix maps to a `PermissionFailure` member and none can pass.
- `UnofferedOption` joins `IllegitimateEndorsement`/`UnknownPermission`
  in the typed refusal surface — callers see *why* an answer was
  refused; the pending survives every refusal.
- The `service.rs:1967` session scan remains a hardcoded presentation
  surface contained by the gate; a later ticket owns aligning it with
  the closed option vocabulary.
- `pub mod ops` stays a read-only internal instrument — no RPC,
  schema, dependency or event-class admission. Actual backend/live
  trials remain gated to R5.44.

## Alternatives considered

- **Gate at the embed/session layer only** — rejected: `service.rs`'s
  `OptionNotOffered` is surface-side; the monitor is the authority the
  durable record answers to, and a session bypass (repair tooling, a
  second binding) would decide unoffered. The fold-level gate is the
  only place that reads the durable offer.
- **Gate `deny`/`cancelled` against the offer too** — rejected: a
  refusal confers nothing (it cannot launder a grant), and the wire's
  deny spellings predate the closed id set — gating them would refuse
  admitted spellings and break compatibility without buying safety.
- **Drop unparseable option ids vs refuse the pending** — the fold
  drops them: a typo'd id narrows the offer (the answer side still
  must match a parsed member), never widens it; refusing the whole
  pending would brick older rows with no safety gain.
- **A second `input_required`-as-wait path** — rejected: the paused
  label carries no pending/offer/wakeup semantics; the battery proves
  it cannot substitute (the paused effect may already be committed).
- **Splitting the monitor gate from the env cells (the ruled-on
  crate-seam proposal)** — rejected by the 2026-11-03 scoped review
  (`planning/2026-11-03_R5.33-split-review.md`): the gate is the O4
  cell's own precondition (the `UnofferedAdmitted` cell member cannot
  evidence without it), the O2 packet binds the unit to one owner
  working set with no written contingency, and leg (b) alone ~1,348
  lines still crosses the ≤600 trigger — a non-curative
  impl-vs-battery cut.

## Revisit triggers

- If `request.options` gains a wire member (a new option id, a
  structured remedy object, a deny-spelling refresh), re-read the
  gate's member mapping and the deny/`cancelled` exemption — the
  exemption stands on the spellings predating the closed set.
- If the fold's empty-offer path changes (options required, a
  default offer), re-read the pre-R2.11 back-compat clause — gating
  empty offers would refuse legacy pendings.
- If `service.rs`'s session scan is repaired to the closed option
  vocabulary (the recorded finding), re-read whether the fold-level
  gate's option-id domain still matches what surfaces present.
- If `PermissionFailure` grows members or the O4/O5 evidence spec
  changes (interval count, marker cardinality), re-read the folds —
  the closed set and the battery must move together.
- If `ops` ever gains write/dispatch authority, re-read ADR-0410's
  read-only confinement — the permission folds inherit it unchanged.
