# ADR-0229: S1.2 migrates `ContractIdentity.schema_hash` to the one `idp/1` `ContentAddress` scheme (closes DF-S0.1-2)

- **Status:** Accepted
- **Date:** 2026-09-15
- **Ticket:** S1.2
- **Requirement ids:** R-2.12.1 (anchors CC1); discharges DF-S0.1-2 (§7.4; ADR-0036)
- **Spec:** §7.4 (`ContractIdentity{contract_major, schema_hash, kernel_version_id}`); §8.3
  (`idp/1`, `ContentAddress`, `address`/`identify`/`verify` over one canonicalizer); §8.5 (schema
  ownership); ADR-0036, ADR-0219 (the Stage-0 interim), ADR-0212 (Stage 0–1 inheritance), ADR-0227 D2

## Context
Stage 0 needed a `schema_hash` for `ContractIdentity` before the `idp/1` identity model existed.
ADR-0219 recorded an **interim**: a raw `sha256:<hex>` over the sorted-key compact-JSON canonical
schema export, known-answer tested in `hh-wire::sha256`. DF-S0.1-2 made the migration a debt row
scoped to S1.2 — the ticket that lands `idp/1` and `ContentAddress`. S1.2 also introduces κ's two
configuration ids (`configuration_id`, `configuration_version_id`), which are themselves content
addresses and so face the same "which canonicalizer computes them" question. CC1 ("one scheme per
concern") anchors at this ticket: two coexisting content-addressing schemes (the Stage-0 raw
`sha256` and `idp/1`) would be exactly the second canonicalization CC1 forbids.

## Decision
`schema_hash` is computed by `hh_identity::address(canonical_schema_bytes(), "application/schema+json")`
— an `idp/1` `ContentAddress` rendered `sha256:<hex>` (§7.4; ADR-0036). The Stage-0 raw-`sha256`
scheme is **superseded, not coexisting**: `hh-embed-schema` and `hh-ontology` take a dependency on
`hh-identity` so the *one* canonicalizer computes every content address in the tree (`schema_hash`,
both configuration ids, `VersionedRef`/`StaleIndex` addresses, the golden corpus). The pinned
`EXPECTED_SCHEMA_HASH` in `hh-embed-client-generated` is regenerated to the `idp/1` value
(`sha256:c6f41391…`) via `check-drift`. DF-S0.1-2 is closed `DONE` with this as its evidence.

## Consequences
- Good: a single content-addressing scheme (CC1) — no second canonicalizer survives; `schema_hash`,
  κ's configuration ids, and the artifact-identity model all derive from the same `idp/1` rule, so
  `verify`/`identify` semantics are uniform; the deferral's compensating proxy (the interim raw
  `sha256`) is retired; the generated client's pinned hash now asserts the `idp/1` form, so a
  drifted schema fails negotiation deterministically.
- Cost: `hh-embed-schema`/`hh-ontology` grow an `hh-identity` dependency (hermetic, pure-std, no
  external deps — within the E1 hermetic budget). Any external party pinning the *old* Stage-0
  `sha256` value must re-pin to the `idp/1` form (acceptable: Stage 0/1, pre-release, ADR-0219
  explicitly flagged the interim as superseded).

## Alternatives considered
- **Keep the Stage-0 raw `sha256` as the `schema_hash` and use `idp/1` only for new ids.** Rejected:
  leaves two coexisting content-addressing schemes (CC1 violation) and a permanent "which scheme is
  this hash" ambiguity on the wire.
- **Re-pin to `idp/1` but keep a raw-`sha256` fallback for back-compat.** Rejected: a fallback is a
  second live scheme and a silent-widening risk (CC2/CC8); the interim was never a shipped contract.

## Revisit trigger
Only if the `idp/1` canonical form itself is revised (a new `idp/2` profile) — at which point a new
ADR records the re-pin and `EXPECTED_SCHEMA_HASH` is regenerated; never by reintroducing a parallel
scheme.
