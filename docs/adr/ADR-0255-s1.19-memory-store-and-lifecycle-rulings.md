# ADR-0255: S1.19 memory-slice rulings — the `put` op order, the endorsed supersession path, honest `unknown`, the `resolve` serving set, and the `Memory`/`MemoryManifest`/`ViewKind` registrations

- **Status:** Accepted
- **Date:** 2026-09-17
- **Ticket:** S1.19
- **Requirement ids:** R-2.4.3⁰, R-2.4.4⁰
- **Spec:** §5c.3 · §5c.4 · ADR-0078…0083 · ADR-0033…0037 · ADR-0066
- **Rung (ADR-0024 obligation):** **C0** — MUST-code: the `MemoryStore`
  contract ops (`put`/`bind`/`revoke`/`resolve`/`manifest`/`enumerate`/
  `stale_candidates`), `Memory`/`Artifact` records, scope leases with
  generation fencing, `lexical_index`, deterministic `retrieve` over the
  fixed filter order, the E1–E4 lifecycle pure functions, deterministic
  conflict sets, `promote`/`revalidate`/`resolve_conflict`, and the
  `MemoryStaleIndex`/`MemoryUsage`/`LexicalIndex` views. Consolidation,
  non-lexical indexes, hosted/memory-proxy halves and `resume_set`
  consumers stay at their spec'd stages.

## Context
The C0 memory slice must satisfy §5c.3's store contract and §5c.4's
lifecycle algebra while staying honest about what C0 cannot evaluate
(unevaluatable conditions, environment-dependent stamps). The open seams:
the exact ordering of `put`'s checks (the spec names the order, the
record needed pinning), how `promote`'s endorsed write relates to the
supersession authority rule, what `unknown` means when nothing is
checkable, which states `resolve(mode=execute)` may serve, and where the
new record/view kinds register.

## Decision
1. **`put`'s check order is: provenance → scope → contract → label →
   lease → supersession → conflict → store** (§5c.3's write order).
   Provenance first (a write with no provenance is refused before any
   store state is read); scope capability next; `contract` completeness
   for `session`/`project`/`user` scopes (`MissingContract`); label join
   `join(context_label, writer_label)` then the per-kind
   `min_authority_for_storage` floor and the delegate/text ceilings;
   lease-generation fencing (`Fenced{scope, expected, got}` — the write
   must hold the scope's current generation); supersession checks
   (target exists, kind matches, `authority(new) ≥ authority(old)`);
   deterministic conflict-set detection (`same subject_key + overlapping
   readers + neither supersedes the other`); then the version is stored
   and `context.memory.written` emitted (audit-grade, `MEMORY_FIELDS`).
2. **The endorsement basis substitutes for the supersession authority
   check on the `promote` path.** `promote`'s own guards (human/kernel
   reviewer, non-model source, `to_authority ≤ reviewer.authority`, no
   `no_store` basis) authorize the raise; `put_inner(…, endorsed=true)`
   waives the in-store `authority(new) ≥ authority(old)` comparison so a
   principal-endorsed promotion of an external write is not refused. The
   waiver is reachable only from `promote` (`pub(crate)`), and every
   promotion appends `security.label.endorsed{basis: promotion}`
   (ADR-0035 endorsement bases).
3. **`unknown` is the honest state when nothing is checkable.** A version
   whose `contract` is empty AND whose `validity` carries no `until`/`fired`
   member is `unknown` — never silently `valid`. A `validity` carrying an
   unevaluatable `condition` is likewise `unknown` (C0 evaluates only the
   `superseded`/`refreshed`/`ttl` conditions internally; everything else
   defers to `LifecycleEnv::condition_fired`, and an absent probe is
   `unknown`, not `false`). The precedence chain is
   `revoked > superseded > expired > stale_by_dependency > {valid |
   unknown}` — explicit, total, tested (`lifecycle_precedence_and_expiry`).
4. **`resolve(mode=execute)` serves `{valid, stale_by_dependency,
   unknown}` and refuses `{revoked, superseded, expired}`.** §5c.3's
   never-serve set is the revoked/stale/superseded head — but `stale` in
   the lifecycle algebra is `stale_by_dependency`, which §5c.4's slot
   filter admits or withholds per `ValidityPolicy` (the slot decides
   delivery; `resolve` decides servability). `expired` joins the
   never-serve set; `unknown` remains servable (it is *unverified*, not
   *refuted* — the slot's `admitted_states` is the gate). `audit`/
   `reproduce` always return the annotated record.
5. **Stale-by-dependency propagates transitively through
   `justifications`.** `lifecycle_state` walks the version's
   `justifications[]`; a justification ref whose own state is
   `revoked`/`superseded`/`expired`/`stale_by_dependency` poisons the
   dependent — recursively, so a three-deep chain stales end to end
   (AC-R-2.4.3-5). `MemoryStaleIndex` (the new `ViewKind`) is the derived
   projection over it; `stale_candidates` enumerates the frontier.
6. **`RecordKind::{Memory, MemoryManifest}` and
   `ViewKind::{LexicalIndex, MemoryStaleIndex, MemoryUsage}` register in
   their owning crates' closed sums.** Memory records are first-class
   versioned records (I1–I5) so `VersionedRef::pinned(RecordKind::Memory,
   …)` is the justification/name-binding spelling; `MemoryManifest` is the
   per-`manifest()` snapshot record. The three view kinds are
   owner-projected (`hh-context` owns the fold; `Store::project` refuses
   them in-crate, per the existing owner-view seam).
7. **`retrieve` is one deterministic pipeline**: `enumerate` (the
   `RetrievalQuery` closed sum — `by_address`/`by_name`/`by_path_glob`/
   `by_run`/`lexical` over `lexical_index`) → lifecycle filter in the
   attested order `validity → authority → readers → relevance` →
   `deterministic_default` ranking (relevance, then
   `(authority desc, created_at, version_id)` tie-break) → budget cut
   (`RetrievalBudget{tokens, k}` — `estimate_tokens` is the declared
   estimator, no hidden truncation) → the `context.memory.read` audit row
   (`delivered[]`, `withheld[]{version_id, state, reason}`,
   `filter_order_attestation`) + `context.retrieval.completed` report.
   A `stale` request watermark (`at > store.applied_seq`) is
   `StaleStore`, never silently served.

## Consequences
- `put`'s fixed order makes the earliest failing check the reported one —
  tests pin the order (`ac_r_2_4_3_2_put_caps_fencing_and_read_your_writes`)
  and downstream writers get a stable refusal surface.
- `endorsed` writes exist only through `promote`, keeping the in-store
  authority rule the default and the endorsement audited.
- `unknown` never collapses into `valid`: an empty-contract memory is
  honestly unverified, and the execute path serves it only when the slot
  admits `unknown` — the AC-R-2.4.3-5 filter test pins both halves.
- The conflict detector is deterministic (same inputs ⇒ same
  `conflict_set_id`), so `resolve_conflict` replays and the
  `conflict_set_ref` content ref stays stable.

## Alternatives considered
- **`resolve(execute)` serving only `valid`.** Rejected: §5c.3's
  never-serve set is `{revoked, stale, superseded}` and §5c.4 admits
  `stale_by_dependency`/`unknown` through `ValidityPolicy` — over-refusing
  at `resolve` would double-gate what the slot policy owns.
- **Promote via a public "skip authority check" flag on `WriteContext`.**
  Rejected: the waiver must be unreachable outside the endorsement path —
  a ctx flag would let any caller self-waive. `pub(crate) put_inner`
  scopes it to `lifecycle.rs`.
- **Conflict detection as an opt-in check.** Rejected: §5c.4 makes the
  conflict set a `put`-time obligation; skipping it would silently lose a
  `conflict_set_ref` the audit partition declares.
- **Lexical index over raw `Text` only.** Kept, but the index also folds
  `Structured` canonical bytes — both arms feed `lexical_index` so a
  structured fact is retrievable by term.

## Revisit trigger
The consolidation/`resume_set` tickets (R-2.4.3¹/R-2.4.4¹) and the Stage-3
executable battery re-read decisions 3–5 when non-lexical indexes, judge
probes and hosted memory proxies land. Reopen decision 2 if a second
endorsed-write basis (e.g. `revalidation`-conferred authority) needs the
same waiver.
