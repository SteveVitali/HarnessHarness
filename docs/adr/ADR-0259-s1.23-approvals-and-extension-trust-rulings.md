# ADR-0259: S1.23 approvals and extension-trust rulings — `security.permission.requested` goes fully ephemeral, the C0 owed-decision trail, `pending` fold semantics, extension records in `hh-registry`, and mediation as a replayable fold

- **Status:** Accepted
- **Date:** 2026-09-17
- **Ticket:** S1.23
- **Requirement ids:** R-2.8.7⁰, R-2.8.5⁰
- **Spec:** §5g.7 · §5g.5 · ADR-0063…0065 · ADR-0069…0071 · CF-152 · I-P5/I-P6
- **Rung (ADR-0024 obligation):** **C0** — MUST-code: the `ApprovalRequest`/
  `ApprovalResponse`/`PermissionRequest`/`ApprovalLease`/`EscalationInput`/
  `EscalationDecision` records, the durable `security.permission.pending`
  owed-decision row, the ephemeral `requested` prompt rendering, the
  never-auto set and `UnattendedPolicy = deny` floors, the exact-hash lease
  record at `scope = run`, the mediation fold, `ExtensionRecord`/
  `ExtensionTrustRecord`, `DeclaredSource`/`SourceLocator`/`ExtensionRef`,
  resolve-time pins, `UnpinnedInSealedForm`, `default_text_authority`, and
  `TextHygieneReport`. The human ask loop, `hook`/`auto_reviewer` live
  stages, `ApproverGrant`, the lease-cache `decider`, the
  `security.extension.*` emitters and the declared-source scanners stay at
  their spec'd stages (DF-S1.23-1/-2).

## Context
§5g.7 defines the approvals and escalation machinery; §5g.5 the extension
supply-chain trust records. At this ticket's start the Π table, Π-12's
unattended transform and `floor_verdict`'s never-auto set were landed
(S1.11), `security.permission.requested` was registered `Ledger`-durable
with an ephemeral `rendering` member under ADR-0234's *interim* ruling —
made only because no durable `pending` row existed — and the recovery/
checkpoint/stop projections derived owed decisions from `requested`. The
registry had no extension record kind; the Assembly grammar had no
`extensions` member; sealing had no extension pin rule. Separately, a
latent scope-chain bug existed in `hh-env::dispatch`: the arg-map-eval
refusal minted `action.tool.rejected` carrying a `tool_call_id` scope that
`action.tool.proposed` had never opened (`rejected` is a `tool_call`
closer — the append refused `ScopeNotOpen`).

## Decision
1. **`security.permission.requested` is `Durability::Ephemeral`; `pending`
   is the durable owed-decision row** (§5g.7 §3; CF-152). This supersedes
   the ADR-0234 interim durable+stripped-member ruling for `requested`:
   that ruling existed *only* because no durable `pending` row existed.
   `pending` is audit-grade (`row_audit`, `PENDING_FIELDS`) carrying
   `{permission_id, effect_id|effect_ids, request{subject_ref,
   capability_ref, args_canonical_hash, reason}, requested_at, mode,
   timeout}`; `requested` rides subscribe only, carrying the same
   `permission_id` plus the prompt surface (`options_presented`,
   `explanation`, `rendering`). The `ephemeral_fields` strip+fragment
   machinery stays in the schema (no landed class uses it now — it is
   generic machinery, like the dormant `head.moved` frame).
2. **The C0 owed-decision trail is `decided{ask} → pending → requested →
   refused/cancelled`, one `permission_id` threading all of it.** The
   dispatcher mints the id deterministically —
   `H(capability_ref.version_id ∥ args_canonical_hash ∥ salt)` where the
   salt is the `effect_id` exactly when `never_auto(risk)` (irreversible
   or `UNKNOWN`) — so identical pending `(capability_ref, args)` asks
   coalesce to one `permission_id` and `irreversible`/`unknown` never
   coalesce (the identical-request / never-batched rules). Stage 1 has no
   mid-dispatch human round-trip (the control envelope owns the ask loop —
   DF-S1.23-1), so the pending resolves `cancelled` by
   `action.effect.refused{ask_required}` — never `unknown` (AC-R-2.8.7-6).
3. **`pending` folds resolve on *final* verdicts and terminated effects
   only.** In the `checkpoint` view, recovery (`restore`), and
   `hh-control::stop::pending_permissions`: a `pending{permission_id}`
   opens the owed decision; a `decided{permission_id}` closes it only when
   `decision ∈ {allow, deny}` — a `decision = ask` row is the verdict that
   *opened* the pending, not its resolution; a refusal/`unknown` terminal
   on every attached `effect_id` resolves it `cancelled`. Coalesced
   pendings merge on `permission_id` across `effect_ids[]`.
4. **`security.permission.decided{ask}` carries `permission_id` +
   `requested_at`.** The monitor's ask verdict is recorded in the same
   owed-decision coordinate as the `pending` it creates — the trail reads
   `decided{ask, pid} → pending{pid} → requested{pid} → refused` without
   joins.
5. **Exact-hash `ApprovalLease`s are run-scoped and content-keyed.**
   `lease_key = H(capability_ref ∥ args_canonical_hash ∥ scope ∥
   policy_fingerprint)` — any policy change revokes by construction (a new
   fingerprint is a new key); `irreversible` requires `max_uses` and
   `scope ≤ run`; `uses` counts served hits. The
   `security.permission.lease.{granted,used,expired,revoked}` +
   `security.permission.escalated` classes are declared audit-grade now;
   their emitters are the Stage-2 escalation machinery's (DF-S1.23-1).
6. **The mediation invariant is a pure fold, `check_mediation`, replayed
   by the test battery** (AC-R-2.8.7-1's property-check form):
   `prepared`/`observed` need a preceding `decided{allow}` or Π allow
   (`action.effect.authorized`) for the same `(effect_id, attempt)`;
   `committed` needs `decided{allow}` specifically (I-H7 — the same
   verdict the strict append gate raises, so the offline check and the
   append rule report one verdict, CC1). Gating `authorized` itself on
   `decided{allow}` is a landed-contract change deferred to S2.6 review
   (DF-S1.23-1).
7. **`ExtensionRecord`/`ExtensionTrustRecord` live in `hh-registry` as a
   `RecordKind::Extension` versioned record** — never a HIR entity (CC10:
   §5g.5 fixes the records, the registry stores them). Authority,
   attestation, claim, grant and provenance are separate legs;
   `default_text_authority(kind, origin, attestation_status)` delegates
   the origin half to `hh_provenance::default_text_authority` — the one
   minting table (CC1) — and `validate_extension_record` refuses both
   over- and under-minted `text_authority` (L1 `LocationElevation`;
   AC-R-2.8.5-2). `TextHygieneReport` is advisory — it scans for
   bidirectional/invisible/tag code points and preserves bytes
   (AC-R-2.8.5-11).
8. **`Assembly.extensions{sources, refs, merge_policy}` is the only
   extension enumeration** — `DeclaredSource` declares where extensions
   may come from (no implicit scanning creates authority);
   `resolve_extensions` pins each ref through `RegistryStore::resolve`
   (resolved locator coordinates + `fetched_at` + `content`, no surviving
   `selector`); `exact_only` refuses duplicate `(name, kind)` refs;
   `seal`/`check_completeness` refuse any unpinned ref with
   `HirError::UnpinnedInSealedForm` (L4; AC-R-2.8.5-1). The
   `security.extension.*` event family is declared audit-grade with
   Stage-4 emitters (DF-S1.23-2).
9. **`action.tool.proposed` mints before the arg-map eval** so a
   `resolve`-stage refusal closes the scope it opens — `action.tool.
   rejected` is a `tool_call` closer and the ledger refuses a close of an
   unopened scope. The `args`-refusal trail is now `proposed → rejected`
   anchored at `turn ⊃ model_call ⊃ tool_call` (no effect coordinate
   exists yet — it derives from the canonical args). This repairs a latent
   scope-chain bug the Ask-path acceptance test surfaced.

## Consequences
- Every owed-decision projection — `checkpoint` view, recovery
  `pending_permissions`, `hh-control` drain report, the
  `approval_requests` telemetry count — reads the durable `pending`
  class; `requested` can no longer be mistaken for the owed-decision
  source (it never lands in `state.events` at all).
- A `decided{ask}` row no longer masquerades as a pending's resolution:
  the folds only treat `allow`/`deny` as final, so a pending stays owed
  until a real verdict or its effects terminate.
- `hh-env` arg-map refusals now append a balanced `proposed → rejected`
  pair instead of crashing on `ScopeNotOpen` — the tool_call scope opens
  and closes atomically in one batch.
- `approval_requests` counts durable facts (`pending`), never ephemeral
  renderings — the count is replay-stable (I-P5).
- Sealed assemblies carry only pinned extension refs; resolution is the
  sole pinning point and the registry is the sole resolver (CC7/CC1).

## Alternatives considered
- **Keep `requested` `Ledger`-durable with the ephemeral `rendering`
  member** (ADR-0234's interim form): rejected — it duplicates `pending`'s
  durable request record, contradicts the §5g.7 partition (`requested` is
  the ephemeral prompt *rendering*), and leaves every fold free to read
  the wrong source. The interim ruling's stated precondition (no durable
  `pending`) is gone.
- **Emit `decided` without `permission_id`:** rejected — the trail would
  need effect-coordinate joins to connect the ask verdict to its pending;
  one coordinate threads them (the test asserts it).
- **Anchor the args-eval `rejected` at `turn/model_call` only** (the dedup
  precedent): rejected — the dedup path anchors low because the tool_call
  scope was *already closed* by the first dispatch; here it was never
  opened, and `proposed → rejected` preserves the `tool_call` linkage the
  record exists to carry.
- **Fold `decided{ask}` as a pending resolution:** rejected — the ask
  verdict is what *opened* the pending; treating it as a decision would
  make the owed-decision views lie in any flow where a pending outlives
  its ask.

## Revisit trigger
