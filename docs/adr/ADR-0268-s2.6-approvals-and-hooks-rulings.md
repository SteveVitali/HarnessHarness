# ADR-0268: S2.6 approvals/hooks rulings — the out-of-process `authorize` boundary, the `batch_id` mint, hook attestation admission, the pre-authorization ceiling, the approval-mint cap binding, and the defer/wakeup wiring

- **Date:** 2026-09-19
- **Ticket:** S2.6
- **Requirement ids:** R-2.8.1 (AC-R-2.8.1-{7,16}; DF-S1.11-{1,3}),
  R-2.8.7 (AC-R-2.8.7-{2,4,5,9,11,14}; DF-S1.23-1, DF-S2.3-1, DF-S2.4-1)
- **Spec:** §5g.1 (the reference monitor — steps 5/7–8, H-7 lifetimes,

  `request_approval`/`respond`, batching, `defer`, leases) ·

- **Rung (ADR-0024 obligation):** **C0/Stage-2** — the §5g.1 §9 Stage-2

## Context

S2.6 lands the Stage-2 half of the reference monitor and the §5g.7
approvals/hooks slice. The spec fixes the *what*; the mechanism choices
below were left to the ticket:

1. **The independent `authorize`.** AC-R-2.8.1-16 (T-LCD-12) wants a
   second `authorize` — out of process, over canonical bytes — producing
   byte-identical `KernelDecision`s and profile-invariant decisions. The
   wire shape, the input completeness set, and what "canonical" means at
   the process boundary were unspecified.
2. **Where `batch_id` is minted.** §5g.7 §5 groups requests by
   `(effective_risk_class, requested_of, scope)` but does not name the
   key derivation.
3. **Hook attestation as an admission rule.** `HookReport` carries
   `attestation_ref` (R-2.8.5); whether an *unattested* report may still
   move the chain needed a ruling.
4. **The pre-authorization handle's ceiling.** §5g.1 §9 says "issued at
   `definition`; bounded by `authority_cap`" — the interim mint
   hardcoded `Delegate` and applied no caps.
5. **What `authority_cap.of` binds in the approval path.** The cap names
   a sealed entity; a `permission_id` is minted at runtime and can never
   appear in a sealed constraint.
6. **The `defer` round-trip.** Which subscription/resume pair carries an
   `async`/Π-12-defer ask back into `authorize` without a re-ask loop.

## Decisions

**D1 — `hh-authorize` is a second binary over the one canonical codec,
never a second implementation.** `crates/hh-monitor/src/bin/hh-authorize.rs`
reads `hh-monitor/authorize-input/1` canonical JSON (stdin or a file
argument), rejects noncanonical bytes at the boundary, decodes the full
monitor state (handles, Π, proposers, capabilities, the approval fold)
plus the `Proposal`, runs the *same* `Monitor::authorize`, and writes the
canonical `KernelDecision` to stdout; malformed or unresolvable input is a
nonzero exit. The codec lives in `hh_monitor::wire` over
`hh_wire::json::Json` (`BTreeMap`-ordered object keys) and thin
`hh_hir::wire`/`hh_compiler::schema` wrappers — no duplicated encoders.
Byte-equality and profile invariance are conformance-tested in-process vs
the spawned binary (`crates/hh-monitor/tests/authorize_oop.rs`); approval
state crosses the boundary in the input, so a lease hit decides identically
out-of-process.

**D2 — `batch_id` is the deterministic `idp` id over `(risk_class,
requested_of, scope_ref)`.** `approval::mint_batch_id` canonicalizes the
risk class through `RiskClass::to_json` (the `intended`/`decided` spelling)
and keys on the reviewer coordinate plus the run scope — every batchable
ask in a run lands under the same batch id, so one prompt may render N
pendings while each `permission_id` still decides independently (a batch
allow records N `label.endorsed`-equivalent endorsements —
`endorsement_count` per attached effect, AC-R-2.8.7-14). The mint is gated
on `EscalationInput.batchable`: `irreversible` (per-effect salted
`permission_id`) and `permission_request` asks never carry a batch.

**D3 — an unattested `HookReport` is never consulted.** `run_chain`'s hook
stage admits only reports carrying a non-empty `attestation_ref` (R-2.8.5 /
ADR-0063…0065 — the hook runner is outside the TCB; the *recorded*,
*admitted* report is what moves the chain). An unattested report is
skipped: its `deny` cannot resolve, its `allow` cannot mark, its `defer`
cannot suspend. Removal-sensitive test:
`chain_unattested_hook_report_never_admitted`.

**D4 — a `pre_authorize` handle mints at `min(definition, issuer.authority,
authority_cap)`.** §5g.1 §9's row reads "issued at `definition`; bounded by
`authority_cap`" (ADR-0053 D5) — the seal endorsement confers `definition`
authority on the rule; the recorded issuer and the caps can only lower it.
This corrects the interim hardcoded `Delegate` (which ignored both the
`authority_cap` rows and the issued-at class). `cap_ceiling` now takes the
authority class directly so root, pre-authorization and approval mints
share one clamp.

**D5 — `authority_cap.of` binds the capability semantic id in the approval
path.** The cap's `of` member names a *sealed* entity (ADR-0240); a
`permission_id` is minted at runtime and can never appear in a sealed
constraint, so the approval mint applies caps whose `of` is absent/`"*"`
(global) or equals the pending's `capability_ref.semantic_id`. The ceiling
folds `min(responder grant_authority, caps)` — caps lower, never raise.

**D6 — `defer`/`async` suspends on a `permission_decided` wakeup bound to
the durable `pending`.** The dispatch ask path mints
`security.permission.pending` + `security.permission.requested`, calls
`wakeup_subscribe(Trigger::PermissionDecided{permission_id})` against the
pending event ref, then `suspend(AwaitingApproval{permission_id})` (§5a.3;
ADR-0130/0131). On the resume half, `authorize` consults
`ApprovalState::decision_for_effect` *before* the lease stage: the recorded
`decided` row is the truth — `allow` serves with `decider = human` and the
`origin_permission_id` back-reference, `deny` reproduces the verdict — so a
re-dispatched effect never re-asks and never trips the exactly-one-decided
gate.

## Consequences

- AC-R-2.8.1-16 is executable: `tests/authorize_oop.rs` spawns the binary
  and asserts byte-identical allow/deny output, canonical-input rejection,
  malformed/unresolvable-input nonzero exits, profile invariance and the
  approval-state carry.
- A noncanonical or foreign-profile input can never silently decide — the
  boundary fails closed.
- Batched asks share a durable `batch_id` on the pending row; the fold
  recovers it, and a batch allow's endorsement count is derivable.
- An unadmitted hook report is indistinguishable from no report — hooks
  stay raise-only *and* attestation-gated.
- Pre-authorization handles now obey `authority_cap` — a definition can
  bound its own pre-authorizations; they still never exceed `definition`.
- The defer slice is end-to-end: `ChainDecision::Defer` → durable pending
  → suspend + subscription → `respond` → `decision_for_effect` resume.
- `label.endorsed{basis: approval}` emission and `ApproverGrant` records
  remain C1 (DF-S1.23-1 keeps them); `ApprovalOption.modify` stays C2.

## Alternatives considered

- **A hand-rolled second `authorize` implementation** for AC-16 — refused:
  a divergent re-implementation could never prove byte-equality; the spec's
  intent is independence of *process* over the one canonical contract.
- **Batch key over `(permission_id)` or a random group id** — refused: a
  random id can't group deterministically and a per-request id groups
  nothing; the spec names the three members.
- **Skipping the attestation gate at the offline stage** ("no hook sources
  exist yet") — refused: the gate is load-bearing the moment any report
  arrives; wiring it later would silently admit unattested reports in the
  interim.
- **`of` bound to `permission_id`** (as first patched) — wrong: the cap is
  a sealed-time declaration and cannot name a runtime-minted id; the
  capability semantic id is the entity the ask is over.
- **`issuer.authority` alone as the pre-auth ceiling** — refused: the
  recorded issuer (kernel, at `open_session`) would mint `kernel`-class
  pre-authorizations; the spec's issued-at class is `definition`.

## Revisit trigger

Reopen D1 when the authorization input grows members the codec doesn't
carry (a `AuthorizeInput/2` bump is additive per CC8); D2 if the spec
gains a batch *policy* leaf (`pending_batch_id` on `EscalationInput`) that
must override the deterministic key; D3 when a real hook runner lands and
the admission rule must verify the attestation's *content*, not only its
presence; D4/D5 if ADR-0240's `of` grammar is extended to non-entity
targets; D6 if `defer` gains cross-process resume (the current slice is
in-process, matching §5a.3's Stage-2 posture).
