## Context

S6.1a landed the evolution pipeline; S6.1b
lands its sibling 6a service — the
assumption-debt *manager*: the standing
monitor that keeps the no-conditioned-
assumption-without-a-removal-test
discipline true over time. The run had to
rule on where the service lives, what its
book of record is, how the probation
trigger becomes a *ledgered* fact (the
S5.4 residual), how `no_dead_weight_found`
evaluates, and how the proposal/deployment
split stays structural.

## Decision

- **D1 — `hh-debt` is a new projection
  crate, edge-free upward, consumed only by
  `hh-embed` under `tier-c4`.** Like
  `hh-evolution`/`hh-fleet`: the manager is
  a projection/consumer layer over the one
  Store — no second store, no second
  authority path (CC3/CC6). Every
  manager-minted row goes through
  `Store::commit_kernel_row_for` with
  producer `hh-debt`.
- **D2 — The registry audit run is the
  book of record.** The manager binds one
  run (the S5.4 `ensure_registry_run`
  convention when the caller passes none)
  and folds its `lifecycle.debt.*` prefix
  into `ManagerView`: the probation book,
  the open/settled removal-test map, the
  per-debt status fold, the
  model-version-change tick clock, and the
  sweep count. `open` *is* the restart
  path — the fold is a pure function of
  the prefix, so rebuild equality is
  structural (CC10).
- **D3 — `lifecycle.debt.probation.opened`
  is the book of record for hypothesized
  probation (DF-S5.4-1).** The sweep opens
  an entry for every `hypothesized` record
  lacking one (`due_at = now +
  hypothesized_max_age`); `evaluate_debt`
  reads the ledgered entry through
  `DebtObservables.probation`, fires
  `probation_overrun` on `due_at ≤ now`,
  and cites the ledgered row's event ref
  as the transition's `evidence_ref` — the
  §5h.7 consumed-by gate resolves a durable
  record, not a caller assertion. The
  record-derived bound remains the fallback
  when no ledgered entry exists (and a
  mismatched `debt_ref` entry falls through
  to it — a foreign row is not this debt's
  book).
- **D4 — `schedule_removal_test` is a
  records-in function under `DebtPolicy`.**
  The `expiry_urgency` priority classes —
  `expired`+used > `expiring`+used >
  `hypothesized` past probation > scheduled
  cadence — order the sweep; the
  `max_open_removal_tests` bound and the
  instrument-budget reservation answer
  `Deferred{reason}` (never a silent drop,
  never a refusal). Executable tests
  instantiate as `ExperimentSpec{kind:
  retirement}` with `ext.charged_to =
  instrument`, `ext.debt_ref`/`debt_rule_id`
  lineage, and `predicted_effect.metric_ref`
  as the primary metric; the caller
  registers the spec through §06 — the
  manager never opens a run (D-2).
- **D5 — `retirement_batch` is a fold of
  caller-resolved 2-arm templates.** k ≥ 2
  debts whose resolved templates share one
  base arm, design, suite and budgets fold
  into one `ExperimentSpec{kind:
  retirement_batch}` (base + k removal
  arms; `ext.debt_refs[]`/`debt_rule_ids[]`
  parallel the arms); anything else is
  `BatchIncompatible`. A batch counts as
  one open test per *debt* — the bound is
  on open obligations, not experiments.
- **D6 — `no_dead_weight_found{window}`
  measures the folded window in
  commit-order, not wall-clock.** The
  window closes when ≥ N
  `model_version_change`-cause
  `status.changed` rows exist (the §05b
  cause-spelling family — one closed set);
  the verdict reads the settled pass set
  inside the window (`inconclusive{
  window_open}` while open; `fail` when a
  pass exists — the manager is doing work;
  `pass` when none ever did — the manager
  is dead weight). The reflexive verdict
  mints `removal_test.settled` like any
  static test; `retired` still requires
  the human-sealed gate — the honest end
  state is proposed, never automatic.
- **D7 — Proposal and deployment are
  structurally separated.** `propose_retirement`
  admits only a `pass` verdict on the debt
  plus a diff projection that removes
  *exactly* the debt's rule and widens
  nothing (`NotARetirementDiff` on
  authority-widening, budget-loosening, or
  over-removal) — and returns a
  `RetirementProposal{state: proposed}`.
  `retire` delegates to
  `hh_lab::debt::retire` — the human-sealed
  `RetirementRecord` gate — and mints
  `status.changed{to: retired,
  supersedes_reason: expiry}`. The manager
  holds no authority handle over subject
  runs and applies no diffs.
- **D8 — New event classes:
  `lifecycle.debt.{probation.opened,
  service.registered, sweep.completed}`** —
  audit-grade kernel-origin rows
  (registered in `hh-ledger::classes`
  alongside the S5.4 `lifecycle.debt.*`
  family; `OPEN_AUDIT` posture, one
  `payload` shape per class, folded by
  `ManagerView`).

## Consequences

- The probation trigger is now a ledgered
  fact end-to-end: append (`sweep` opens
  the entry) → consume (`evaluate_debt`'s
  probation leg) → evidence (the
  transition cites the event ref the §5h.7
  gate can resolve). DF-S5.4-1 closes.
- `hh-embed` grows six
  `lab.debt.{manager_open,register,sweep,
  settle,retire,propose}` ops, all
  `experimental` + `serves_measurement`-
  gated; a `--no-default-features` build
  answers `Unsupported{by: "tier-c4"}`.
- The sweep is *the* standing monitor —
  callers drive it on whatever cadence the
  deployment wants; `DebtPolicy.schedule`
  is carried on the service record for the
  deployment's scheduler to honor
  (AC-R-2.9.6-12's cadence declaration).
- The reflexive record is a normal
  `AssumptionDebtRecord` on home 16 — the
  same fold, the same settle path, the
  same gate. The only manager-special code
  is its constructor and the window
  evaluation.

## Revisit trigger

Reopen if a new `DebtPolicy.priority`
ordering lands (the `PRIORITY_SPELLINGS`
set is closed — a new order is a new
spelling + class function, never a silent
reinterpretation); if the probation book
must carry *renewal* semantics (a lapsed-
and-extended probation currently mints no
second entry — first write wins); if
`no_dead_weight_found` needs a window
denominated in something other than
model-version changes (e.g. wall-clock —
the tick clock would need a second
cause-set); or if `lab.debt.sweep` must
run inside a serving process's hot path
(the service is deliberately batch-shaped
— a hot-path variant would need its own
budget story).
