# ADR-0318: S5.7 C2 web-surface and MCP write/analysis-group rulings

- **Status:** Accepted
- **Date:** 2026-10-02
- **Ticket:** S5.7
- **Requirement ids:** R-2.11.2, R-2.11.3
  (C2 halves; AC-R-2.11.2-{9,11},
  AC-R-2.11.3-10); CC1/CC2/CC3/CC5/CC6/CC7/CC9/CC10.
- **Spec:** §7.2 (R-2.11.2 C2 — the web
  editing surface), §7.3 (R-2.11.3 C2 — the
  MCP write/analysis/resource/task groups);
  owning rulings ADR-0170…0179, ADR-0131,
  ADR-0132, ADR-0136, ADR-0137.
- **Rung (ADR-0024 obligation):** **C2** — the C2 web surface + MCP write groups — the C2 rung.

## Context

S5.7 lands the C2 depth of both surface
families on top of S4.10's `hh-web` skeleton
and S4.11's `hh-mcp-lab` C1 catalogue. The web
surface gains the editing/launcher/operations/
frontier/experiment/console views (V3–V6,
V11, V12) and the C2 write ops; the MCP Lab
server gains the analysis/write/hosting tool
groups, the tasks carrier, resources +
subscriptions, `serve_bundle`, and the
`service`/`provider_client` binding kinds.
Both surfaces had to stay projections over the
same canonical kernel/Lab operations — the
run had to rule on the points below.

## Decision

- **D1 — The web surface is a pure
  projection client; the browser never
  supplies authority fields.** Every C2 write
  rides `hh-embed/1` through the closed
  operation catalogue; the session layer mints
  `idempotency_key`, `invocation`,
  `session_id`, the responder identity and the
  `registrar` record on the surface run.
  Browser-supplied `idempotency_key`/
  `invocation`/`attestation` members are
  stripped before dispatch — forgery in those
  fields is a no-op, never a grant
  (`ops_c2::c2_write_opens_writer_and_strips_forgery`).
- **D2 — The human's attest act is a surface
  mint, not a field.** AC-R-2.11.2-9:
  `assembly_apply` lands the surface-minted
  `registrar` row with an `attestation` member
  only when the human's own act sets it; a
  widening `authority_delta` without it fails
  at the registry's own gate, never at the
  surface (the surface never decides
  admissibility).
- **D3 — One serving path stays one serving
  path.** The MCP C2 groups are data in the
  `ExposureDefinition` (`hh-lab/1`) lowered
  into the same catalogue: every new tool maps
  to exactly one canonical operation (or the
  declared `respond_approval →
  respond_permission` control lowering);
  `tools/list` is catalogue-derived and
  stable; stdio and Streamable HTTP dispatch
  identically. No far-side MCP state is
  authoritative.
- **D4 — `subject_kind = client` binds only
  `service` / `provider_client`.** An OAuth
  client-grant subject has no human principal;
  a `user` subject may bind any kind, a
  `client` subject refuses to parse onto
  `human_principal`/`agent`. Identity is never
  inferred from request payloads.
- **D5 — The delegate write gate is
  permission coverage, not caller kind.**
  Write-class tools (`apply`, `publish`,
  `register`) refuse `DelegateWriteForbidden`
  for a delegate whose binding lacks a
  declared `entities.permissions` row covering
  the tool's namespace; a covered delegate
  passes to the kernel's own authority.
  `serve_bundle` is launch-class (it wraps
  `lab.serve`), not memory-write — it is not
  delegate-gated.
- **D6 — Tasks and resources are carriers,
  not authority.** `tasks/*` maps onto durable
  surface-run handles + run-ledger status with
  an exhaustive status fold (and `-32021` when
  the client never negotiated the
  capability); `tasks/update` approval input
  routes to `respond_permission` under the
  `human_principal` gate; `tasks/cancel` to
  `cancel`. `resources/*` reads are
  ledger-backed and binding-scoped; the
  subscription set is a transport/session
  projection that dies with the binding —
  never durable authority. Both carriers are
  declared assumption-debt records
  (`tasks_carrier`, `resource_carrier`)
  required at exposure link.
- **D7 — Notifications drain through the
  response envelope.** Subscription/task
  notifications are minted only after the
  durable row exists and ride the
  `notifications` member of the POST response;
  the `GET /mcp` SSE arm remains DF-S4.11-1
  (progress recorded). The surface-run-scoped
  `respond_approval{permission_id}` reply path
  remains DF-S4.11-3 (progress recorded —
  task `inputResponses[]` now reaches
  `respond_permission`).
- **D8 — Fork incoherence resolves to
  nearest coherent points.** The web views
  surface incoherent-fork positions by
  resolving to the nearest coherent fork
  points; the surface never fabricates merged
  state
  (`ops_c2::ac11_incoherent_fork_offers_nearest_coherent`).

## Consequences

- Both surfaces gain full C2 reach with zero
  new authority: every write is an
  `hh-embed/1` operation under caller
  authority ceilings, matched budgets, the
  effect lifecycle, and typed refusals.
- `hh-mcp-lab` grows two modules
  (`tasks.rs`, `resources.rs`) that are pure
  projections — removing them removes the
  carriers without touching kernel state.
- OAuth client-subject bindings are now
  admissible but only for the two
  non-human kinds; a `client`-subjected
  `human_principal` binding fails at parse.
- DF-S4.11-1 (SSE) and DF-S4.11-3
  (surface-run-scoped permission reply) stay
  OPEN with progress notes; no other deferral
  moved.

## Alternatives considered

- **Push notifications over SSE now** —
  rejected: the wire ruling for server-initiated
  traffic over Streamable HTTP is DF-S4.11-1's
  owned surface; draining through the response
  envelope keeps one exchange shape.
- **A far-side task store** — rejected: a
  second authority over run state would break
  the single-serving-path rule; the carrier
  projects durable handles instead.
- **Letting the browser pass
  idempotency/attestation fields through** —
  rejected: CC2 — authority is conferred by
  the surface mint, never read from request
  content.

## Revisit trigger

Reopen if the tasks/resources carriers need
durable state of their own (a spec change
naming a far-side authority), if DF-S4.11-1's
SSE ruling lands and the drain-through-response
shape must coexist with push delivery, or if a
new caller kind breaks the
`subject_kind = client` restriction.
