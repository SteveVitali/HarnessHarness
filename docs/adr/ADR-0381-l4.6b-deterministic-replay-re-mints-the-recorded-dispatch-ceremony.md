# ADR-0381: L4.6b deterministic replay re-mints the recorded dispatch ceremony (the shared-allocator contract)

- **Status:** Accepted
- **Date:** 2026-10-24
- **Ticket:** L4.6b
- **Requirement ids:** `R-2.2.4⁰ᵇ` (deterministic replay) · the L4.6 AC
  "replay of each live run is byte-identical offline" re-tested here on
  the capstone evidence.
- **Spec:** §5a.2 (the effect write-ahead ceremony) · §5a.4 (replay
  validity — a real divergence still answers `invalid{replay_diverged}`).
- **Rung (ADR-0024 obligation):** C0 — the replay driver's recorded-input
  contract; no wire/schema/behaviour surface changes. The live path is
  untouched — only what the re-drive re-mints changed.

## Context

The L4.6 capstone surfaced a live defect: every effect-dispatching run
(3/3 on the anthropic lane, `hh.submit` completion included) answered
`replay{driver_mode: deterministic}` with `invalid{replay_diverged}` —
expected `model_call mc-15`, got `mc-11`, a ~4-id skew per dispatch.

The mechanism: the live drive and the deterministic re-drive share one
monotone `Driver::next_id` allocator for `mc-N`/`tc-N`/`ef-N`/`d-N`/`e-N`
ids. A live dispatch mints the §5a.2 ceremony —
`security.permission.decided`/`pending`, `action.effect.{authorized,
prepared, committed}` — through `append_producer` on that allocator
before the terminal lands. The pre-fix `ReplayGate` served only the
recorded *terminal* outcome (`emitted: []`), so the re-drive minted no
ceremony rows, the shared allocator fell ~4 ids behind per dispatch, and
the model port's recorded-call-id check correctly — but spuriously —
reported `replay_diverged`. The verdict was honest and useless at once:
the effect outcome *was* being replayed faithfully; the contract that
broke was the allocator's.

## Decision

**Leg (a): the replay re-mints the recorded ceremony through the normal
driver append path — never weakens the id matching.**

- `extract_recorded` classifies the gate-emitted rows inside each
  driver-minted `action.effect.intended` … terminal window: a non-driver
  row naming the effect (its scope `effect_id`, or the payload
  `effect_id` the chain carries) is reclassified into the replay lattice
  (`driver_seqs`) and stored verbatim per `effect_id`
  (`RecordedInputs.effect_lifecycle`). The recorded gate producer is
  captured (`gate_component`).
- Two rows name the effect yet never re-serve: the `decider: human`
  permission row (the principal's record — an external row and an
  `Approval` cue) and a *service*-minted terminal (`report_host_effect`
  settling a `Pending` dispatch — the live gate answered `Pending`, so
  the replayed gate serves `Pending` and the recorded terminal folds the
  effect settled off the external lane; a driver re-mint would spend a
  `next_id` the live drive never allocated).
- `ReplayGate::dispatch` returns the recorded rows via
  `GateOutcome.emitted`; no executor ever runs. The driver re-appends
  them exactly as live did — the same classes, the same allocator, the
  same `e-N` mints — so every later `mc-N`/`d-N`/`e-N` matches the
  record byte-for-byte.
- `EffectGate::producer_component` widens `&'static str → &str`; the
  replay gate serves the *recorded* component so the re-minted ceremony
  attributes to the boundary that produced it (INV-7), never to the
  replay's own name.
- Divergence stays honest: the change re-serves recorded facts, it adds
  no tolerance. A dropped ceremony row still skews the allocator and the
  port reports the divergence; a tampered decision payload still answers
  `invalid{replay_diverged}` — both are committed tests
  (`dropped_ceremony_row_diverges`, `ceremony_tampered_decision_diverges`,
  `l46b_effect_dispatch_replay_byte_identical`'s WAL-mutation arm).

## Consequences

- Deterministic replay of an effect-dispatching run is byte-identical
  offline — proven in `hh-control` (`ceremony_dispatch_run_replays_
  byte_identical`) and end-to-end over bindings (a)+(c) in
  `crates/hh-embed/tests/l4_6b.rs`, including the read-only attach arm
  the capstone diverged on.
- The replay mints zero provider/host rows — only the replay lifecycle
  markers land on the target ledger.
- The replay contract's surface area grows by one input class: recorded
  gate-`emitted` rows are now part of what `extract_recorded` feeds the
  re-drive. A new class of gate-emitted row joins the ceremony by the
  same naming rule (`scope.effect_id` or payload `effect_id` inside the
  window) — no code change, but it must be non-driver-produced to
  re-serve.
- L4.6's `blockedOn` is discharged by this fix on evidence (the
  `l4-6b-replay` live leg replays a recorded dispatching ledger over
  binding (c), USD 0 — the scripted lane, no provider dial).

## Alternatives considered

- **Leg (b) — match recorded terminals positionally/by content instead
  of by minted id.** Rejected: it papers over the allocator skew rather
  than reproducing the record. A run whose live path genuinely minted
  fewer ceremony rows would silently "replay" — the divergence report
  would stop naming the broken contract, exactly the silent-pass the
  replay validity rules exist to forbid (§5a.4). The fix belongs at the
  mint, not the match.
- **Re-mint the ceremony with synthetic payloads** (structural stand-ins
  for the recorded rows). Rejected: only the recorded rows reproduce the
  record byte-identically; a synthetic row diverges on payload compare
  and fabricates a Π-floor record the gate never made.
- **Skip the re-serve for `Pending` terminals** (service-minted
  `observed`/`unknown` rows). Partially taken: the ceremony re-serves
  (the live gate emitted it), the terminal stays external (the live
  drive never minted it) — a hybrid that is the record's exact shape,
  not a tolerance.

## Revisit trigger

Reopen when: the `EffectGate` contract grows a new emitted-row class the
window rule misclassifies (a driver-minted non-`intended` row inside a
dispatch window, or a gate-emitted row naming its effect some other
way); the id allocator leaves `Driver` (the ceremony re-serve's binding
to the shared `next_id` is the contract being kept — moving the
allocator moves the contract); or deterministic replay is asked to
re-execute effects (the recorded-terminal design is `executor calls = 0`
by construction — re-execution is a different driver mode, not a change
to this leg).
