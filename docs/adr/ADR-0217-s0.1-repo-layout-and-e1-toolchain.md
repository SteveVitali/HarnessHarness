# ADR-0217: S0.1 repository layout and the E1 toolchain binding

- **Status:** Accepted
- **Date:** 2026-09-15
- **Ticket:** S0.1
- **Requirement ids:** R-2.12.3 (program), R-2.11.4⁰ᵃ
- **Spec:** §11.5, §7.4, §10.6; ADR-0050 (e) (research), ADR-0176/0178/0179 (research)

## Context
ADR-0050 (research, ratified) chose the polyglot split E5a with a late-bound surface layer and
assigned the language binding to build stages: its clause (e) **binds Stage 0** — "toolchain,
repo layout, CI for the E1 kernel and the schema-export → codegen pipeline". E1 is the
"compiled, memory-safe systems ecosystem" (Rust). CC4 keeps the spec/contracts language-neutral
(ecosystems appear only by candidate id E1/E2/E3); ADR-0050, and now this build ADR, are the only
places the concrete ecosystem is named. S0.1 must realize that binding: a repository layout, CI,
and the durable schema-export→codegen pipeline — with no framework code beyond the toolchain, the
pipeline, the drift check and throwaway spike trees.

## Decision
Stand up a **Cargo workspace** (E1 = Rust) with these crates, all **pure standard library** (no
external crates):
- `hh-wire` — transport primitives (canonical JSON, SHA-256 content addressing, newline-delimited
  JSON-RPC 2.0 framing). No verbs/fields.
- `hh-embed-schema` — the single schema source (CC7) for the `hh-embed/1` Stage-0 message set.
- `hh-kernel` — the reference kernel binary; `serve` is the stdio boundary skeleton.
- `hh-codegen` — the schema-export→codegen tool.
- `hh-embed-client-generated` — the generated, drift-checked client (ADR-0179).

The toolchain channel is pinned (`rust-toolchain.toml`, 1.94 + rustfmt). The E1 **helper**
ecosystem is bound here too (same ecosystem as the kernel), but its binary is not built until
S2.1 (ADR-0050 (e): helper is Stage 1–2). Throwaway spike trees live in `spikes/`, excluded from
the workspace.

**Hermetic pure-std** was chosen deliberately: the toolchain, CI and the boundary spike then
build and run offline and reproducibly, and the content address (schema hash) has no external
dependency in its input. This is a Stage-0 skeleton; later stages may introduce vetted crates
under the supply-chain policy (ADR-0050 C11; out of scope for S0.1).

## Consequences
- Good: offline, reproducible builds; a byte-stable schema hash; no supply-chain surface at
  Stage 0; the whole pipeline is inspectable in one language.
- Good: the workspace is ready for the S1.x kernel crates and the S2.1 helper binary to land as
  additional members without restructuring.
- Cost: `hh-wire` hand-rolls a minimal JSON codec and SHA-256 rather than using `serde`/`sha2`.
  These are small, test-covered (NIST known-answer vectors; canonical round-trip tests) and
  scoped to the Stage-0 message set; they will be revisited when the real HIR/1 and ledger
  schemas land (S1.2/S1.4) and a schema-derive story (schemars-class) is chosen.

## Alternatives considered
- **`serde` + `schemars` (the codex `export.rs` precedent).** Rejected for Stage 0: it adds a
  network/registry dependency to CI and the content address, for a message set of three types.
  Revisit when the schema surface grows (S1.2+).
- **A single crate.** Rejected: the single-schema-source (CC7) and generated-client (ADR-0179)
  boundaries are clearer as separate crates, and the drift check needs the generated client to be
  a real, compiled artifact distinct from the source.

## Revisit trigger
When the real HIR/1 / ledger / measurement schemas land (S1.2/S1.4) and the message surface
outgrows a hand-written codec, or when the supply-chain policy (ADR-0050 C11, WS-L6) admits vetted
crates — re-evaluate `serde`/`schemars`-class derivation for the single schema source.
