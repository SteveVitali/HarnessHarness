# ADR-0221: S0.2 throwaway baseline lives in a workspace-member crate, deleted at the Stage-0 boundary

- **Status:** Accepted
- **Date:** 2026-09-15
- **Ticket:** S0.2
- **Requirement ids:** R-2.1.2, R-2.1.5, R-2.1.6, R-2.2.5, R-2.3.1, R-2.3.2⁰, R-2.4.1, R-2.5.5, R-2.6.1, R-2.6.2, R-2.8.3, R-2.9.1, R-2.11.1⁰ᵃ, R-2.11.4⁰ᵃ
- **Spec:** §9.1 (the Stage-0 hand-authored baseline slices); §9.8 (the Stage-0 closure — a throwaway subset); doc 3 §11.0 (throwaway baseline)

## Context
§9.1 requires a hand-authored `react/minimal` definition to run one headless coding task
end-to-end through a deliberately minimal C0 subset, and §9.8/doc 3 §11.0 state the code is a
**throwaway** de-risking baseline, deleted at the Stage-0 boundary — the durable subsystems
(ledger, reference monitor, credential broker, budget accounting, HIR compiler, gateway/router)
are later tickets (S1.x+). Two competing placements existed: (a) a member crate of the S0.1
workspace, or (b) an out-of-workspace tree under `spikes/` (like the S2 boundary spike). The
baseline's acceptance criteria (AC-R-2.1.6-1, AC-R-2.3.2-1, AC-R-2.5.5-14, AC-R-2.8.3-1,
AC-R-2.11.1-3/6) must be **executable and CI-verified**, and CI runs `cargo test --workspace`.

## Decision
The baseline is one crate, `crates/hh-baseline`, added as a **workspace member** but **not a
dependency of the persistent kernel** (`hh-kernel` does not reference it). It reuses S0.1's
persistent transport (`hh-wire`) and the single schema source (`hh-embed-schema`) for
`hello`/`ContractIdentity` — never re-establishing them (CC7). Its crate doc and the workspace
`members` comment both state it is throwaway and deleted at the Stage-0 boundary. The `spikes/`
tree stays reserved for the R1–R6 *measurement* spikes (which produce numbers, not retained
code); the baseline is retained-but-throwaway code with its own tests, which is why it is a
member crate rather than an excluded tree.

## Consequences
- Good: the baseline's six gated ACs run under `cargo test --workspace` in the existing CI with
  no new job; the crate is self-contained (pure std beyond `hh-wire`/`hh-embed-schema`), offline
  and hermetic; deleting `crates/hh-baseline` and its `members` line at the Stage-0 boundary
  breaks nothing persistent (the kernel never depends on it).
- Cost: the workspace carries one throwaway crate until the Stage-0 boundary; a Stage-1 ticket
  must remember to delete it (tracked by the "deleted at the boundary" note in the crate doc,
  the workspace comment, and §9.8's closure rule).

## Alternatives considered
- **`spikes/hh-baseline` (out of workspace).** Rejected: excluded trees are not covered by
  `cargo test --workspace`, so the baseline's acceptance tests would not run in CI without a new
  job, and the ACs demand executable verification.
- **Fold the baseline into `hh-kernel`.** Rejected: the kernel is the *persistent* boundary
  skeleton; mixing a throwaway end-to-end runtime into it would make the "delete at the
  boundary" step a surgical edit of persistent code rather than a whole-crate removal, and would
  risk a persistent dependency on throwaway logic.

## Revisit trigger
At the Stage-0 boundary (GATE-G1 / the first Stage-1 ticket that supersedes a baseline
subsystem): delete `crates/hh-baseline` and its workspace `members` entry, and confirm the
persistent build, CI and drift check are unaffected (they must be, since nothing depends on it).
