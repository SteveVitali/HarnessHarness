# ADR-0332: R2.1 doctor-identity ruling — `KernelDescriptor.version` is the SemVer-class label; `kernel_version_id` keeps the `<name>/<label>` spelling

- **Status:** Accepted
- **Date:** 2026-10-06
- **Ticket:** R2.1
- **Requirement ids:** R-2.12.1 · R-2.11.4 · DF-DOC.1-1
- **Spec:** §7.4 (contract identity + `hello` negotiation; the row-2 identity rule) · §7.1 (row 7, exact pinning and floors) · §5a (R-2.2.1 identity compare)
- **Rung (ADR-0024 obligation):** MUST-data — the ruling fixes the spelling of an existing wire member's value domain; no contract migrates.

## Context

`hh-kernel doctor` exited 1 (`identity mismatch`) on every clean build
(DF-DOC.1-1, found at DOC.1): the binary self-check compared the hello
result's `kernel.version` member against `ContractIdentity.
kernel_version_id`, but the two sides are spelled differently —
`EmbedService` stores only the `rsplit('/')` semver tail (`"0.0.1"`) as
`kernel_version`, so `negotiate` reports `version: "0.0.1"` while the
identity field carries `hh-kernel/0.0.1`. The compare could never pass.
The ticket assigns the ruling: which side is canonical.

The §7.4 row-2 rule names `kernel.version` "a SemVer-class label in an
ADR-0037 name history"; §7.1 row 7's `kernel_floor` compare
(`version_lt`) is defined over bare `x.y.z` semver triples, and
`KernelBelowFloor.version` answers in the same domain. Every consumer of
the wire member already speaks the bare label.

## Decision

**D1 — The stored field's contract wins: `KernelDescriptor.version` is
the SemVer-class label — the semver tail of `kernel_version_id`.** The
`hh-kernel/<semver>` `<name>/<label>` spelling stays on
`ContractIdentity.kernel_version_id` (the name-history id); it never
appears on the wire `version` member. `hh-kernel doctor` derives the
expected label from the identity and compares in the label domain —
fixing the compare, not the reported value.

**D2 — One spelling of the extraction (CC1).**
`hh_embed_schema::kernel_version_label(kernel_version_id)` is the single
canonical tail-extraction; `EmbedService::build` and the binary's
`doctor_identity_ok` both derive through it (the defect was exactly two
spellings disagreeing). `negotiate`'s parameter is renamed
`kernel_version` — it always received the label; the signature now says
so honestly.

## Consequences

- `hh-kernel doctor` exits 0 on a clean build and still fails loudly on
  a genuine identity mismatch (full-id `version`, foreign label, wrong
  `schema_hash`, wrong `contract_major`, missing descriptor — all
  pinned by `doctor_identity_check_accepts_the_label_and_refuses_mismatch`
  + `tests/doctor.rs`).
- The `kernel_floor` floor keeps its semver domain unchanged — no
  negotiation behaviour moves; `hh doctor`'s boundary answer is
  byte-identical to before.
- DF-DOC.1-1 discharges (flip recorded in `DEFERRALS.md`).

## Alternatives considered

- **Report the full `hh-kernel/<ver>` id on `kernel.version`.**
  Rejected: `version_lt` parses bare `x.y.z` triples — a
  `<name>/<label>` operand fails the parse and `version_lt` returns
  `false`, so `kernel_floor` would silently never refuse (an
  honest-refusal violation), and the wire member's value changes for no
  consumer need.
- **Keep per-consumer `rsplit('/')` extractions.** Rejected: a second
  spelling of the same contract (CC1) — that duplication is what let the
  defect in.
- **Compare the reported label against `env!("CARGO_PKG_VERSION")`
  directly in doctor.** Rejected as the *primary* compare: it hard-wires
  the binary's package version rather than the identity's
  `kernel_version_id` — the two coincide today only because
  `KERNEL_VERSION_ID` is built from it; deriving through the one helper
  keeps the compare on the contract field, not the build constant.

## Revisit trigger

Reopen if a `hh-embed/2` dialect declares `KernelDescriptor.version` to
carry the name-history id — the label helper, the `kernel_floor`
compare domain and the doctor check move together (CC1).
