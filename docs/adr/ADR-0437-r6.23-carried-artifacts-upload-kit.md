## Context

§5.2 (O2 RA-1/RD-13) makes cross-window layer identity a carry-by-digest
obligation: layers, bundles and the two HH binary sets are built at most
once per pass, exported with sha256 into the harvested run root and the
pass-level `artifacts[]` section, loaded in later windows over the
REQ-XB-203 IAP path and verified by image ID. §4.10 (AR-20; Q-X35) fixes
the per-window upload outline — admitted operator tool, live-credential
scan, read-back, remediation — but names no tool (H1 F7). AR-20's record
(ADR-0430) lands the index/condenser; this row completes its upload-tool
admission the way AR-15/ADR-0431 records `gcloud`. Nothing here executes:
W1/W3/W4 skeletons (R6.32, R6.40, R6.44, R6.45, R6.47) run the host acts.

## Decision

1. **Two carried binary sets, one set digest each (`hh-binary-set/1`).**
   `INFRA_SET_MEMBERS` = `{runner: hh-runner, helper: hh-helper,
   relay: hh-cell-relay, model_proxy: hh-model-proxy,
   egress_mediator: hh-egress-mediator}` (built in W1); `H_SET_MEMBERS` =
   `{hh_kernel: hh-kernel participant build, hir, compiled_artifacts}`
   (built at W3 start, frozen at G-L1; the phase-4 level's artifacts are
   members, never separate). `set_digest` is `sha256:` over the canonical
   member map — one identity per set (CC1 canonicalizer).
   `BinarySetRecipe.render()` emits one pinned Containerfile: `FROM` a
   digest-pinned toolchain base, `ARG HH_WORKSPACE_COMMIT=<40-hex>`,
   `cargo build --release --locked -p …`, member copies into the set dir
   plus a `sha256sum` manifest. A member outside the closed set refuses.
2. **Export = one `artifacts[]` entry per role through R6.12's codec.**
   `ExportPlan` renders the pinned argv — `podman save --format
   oci-archive` for images, `podman save --format oci-dir` +
   `base_blobs[]` (re-pulled by digest at load) for the small-transfer
   variant, `tar -cf` for binary sets — then records
   `hh-carried-export/1` `{argv, sha256, bytes, elapsed_ms}` and feeds
   the byte count to the exporting window's egress line (REQ-XH-118
   input, labelled `artifact_export:<role>:<name>`). `podman`/`gcloud`
   shims pin argv offline; the identity member is `image_id` or `digest`
   only — a `name@sha256:<d>` RepoDigest refuses at plan construction.
3. **Load = controller scp over IAP + VM-side `podman load`/`tar -xf`
   + base-blob re-pull + image-ID verify, timed.** `LoadPlan` renders
   `gcloud compute scp --tunnel-through-iap` (the R6.13 idiom) and one
   `gcloud compute ssh --command` per VM act; `hh-carried-load/1` records
   argv, observed image ID and `elapsed_ms` (the window-overhead input).
   `verify_image_id` compares the config digest only; a mismatch is
   `AdmissionReason::HarnessLayerMismatch` → `withheld{admission:
   harness_layer_mismatch}` through R6.8's `map_slot_facts`. A RepoDigest
   is never an identity — a load drops it by construction.
4. **Slot identity: `identity.infrastructure.set_digest` +
   `identity.h_set`.** The existing optional `infrastructure` member
   gains the `set_digest` scalar beside the per-binary digests (§3.3);
   `h_set{digest, frozen_at, hh_kernel, hir, compiled_artifacts}` is
   admitted and member-checked in `slot_record::from_json`. W4 slots
   carry one infrastructure-set digest; HH-native and V5 (`rsn-drop`)
   slots carry the H-set digest frozen at G-L1. `check_slot_identity`
   refuses a missing/different digest and an `h_set` on a hosted lane.
5. **Build-once at pass level.** `carried_rebuild_guard(index, role,
   name, gate)` refuses when `artifacts[]` already carries the
   (role, name) member and no gate record `{gate, new_version}` is
   presented — a rebuild is a new participant or a new runner version
   (PROV-Wc's recorded scope), never a silent overwrite.
6. **Proprietary rule, redistribution-aware.** `artifact_upload_decision`
   extends R6.22's `artifact_upload`: `proprietary`/`source_available`
   stays `digest_only` (bytes on the controller) *unless* an operator
   redistribution record is named — Q-X26's terms do not grant one.
7. **AR-20 tool admission: `hf` — the `huggingface_hub` CLI at `2.4.0`.**
   One external operator tool, admitted the way AR-15 admits `gcloud`:
   name (`hf`, the `huggingface_hub` 2.x entry point), exact version
   (`2.4.0`, released 2026-10-29), scope (one private dataset repository),
   token handling (`HF_TOKEN` per invocation, no `login`). No library or
   workspace dependency enters the tree (§4.10's cap).
8. **`scripts/hf-upload.sh` — the controller-only upload command.**
   `upload` refuses an unverified harvest manifest (re-runs the
   REQ-XB-220 sha256 check), a non-private dataset target, and any
   `login`/`auth` invocation (REQ-XH-023). The token is read at use
   from `HH_OPERATOR_ENV_FILE`'s `HF_WRITE_TOKEN` member, passed per
   invocation as `HF_TOKEN`, never printed/persisted; the receipt says
   `provided: yes/no`. `hh-archive-upload/1` receipts cite the tool
   admission (ADR-0437) and are leak-scanned before write (exit 5).
   `verify` reads back every file (`hf download`, sha256 vs index) →
   `archive_verified` | `inconclusive{readback_unavailable}`; a sha
   mismatch fails the row. `remediate` writes the REQ-XH-107 records in
   order — the HUMAN rotation row, the operator purge record, the
   tombstone index entry — and never a secret value (Q-X59 pending: the
   purge is *recorded*, never executed by this row).
9. **Pre-upload scan = one `hh-secret-scan` seam, three tiers**
   (REQ-XH-103, CC1): the repository detector set plus the
   live-credential mask set (Ollama key, HF write token, controller GCP
   credentials via the operator env file) — a live hit refuses the file
   and stops the row. Slot tokens ride a second mask set built from the
   operator-local token file: each hit is verified against its
   `security.credential.revoked` row — revoked tokens stay in the raw
   roles (`raw_receipts`, `egress_log`, `native_log`, `store_segment`)
   and are tombstoned in the derived roles (`transcript`, `atif`) by
   R6.12's condenser hook; an unrevoked token is a live hit.
10. **Append-only archive.** `verify_readback` marks `archive_verified`
    only when every `archived` member hashes back equal; a re-upload
    mints a new revision whose index entry `supersedes[{ref}]` the prior
    one (REQ-XH-104). `remediation_records` returns
    `[rotation, purge, tombstone]` in that order, `provided: yes/no`
    only — the incident is reported at round closure.

## Consequences

- REQ-XC-330's acceptance is deterministic: stub-shim argv pins, the
  mismatched-image-ID `withheld` spelling, the rebuild gate, the
  `digest_only` Claude Code fixture. The live legs (W1 export, W4 load,
  per-window upload) stay `skipped(executes-in-W*)` — `carried-artifacts`
  and `archive-upload` are registered for the skeletons' live evidence.
- `identity.h_set` is additive: earlier windows' records carry no H set;
  `from_json` member-checks it when present and never requires it.
- The owed predicate "each paid window's gate readout cites the previous
  window's `archive_verified` index" is rowed as DF-R6.23-1 (owners
  R6.40, R6.44, R6.45, R6.47) — the kit supports the order; it does not
  decide it (SR-18's W1-uploads-in-W2 deviation stays the windows' own).
- No new dependency, no committed secret: `HF_WRITE_TOKEN` is only ever
  `provided: yes/no` in a record; the purge is operator-recorded under
  Q-X59's pending default.

## Alternatives considered

- **`huggingface-cli` (legacy entry point) or raw API calls** — refused:
  `hf` is the `huggingface_hub` 2.x supported surface with `upload`/
  `download` verbs and `HF_TOKEN` env; a raw API re-implements auth and
  retry semantics the admitted tool already owns.
- **RepoDigest or tag as the carried identity** — refused: `podman load`
  drops the RepoDigest; the image ID (config digest) is the only identity
  that survives the load and the only one the slot may record.
- **A second scan implementation** — refused (CC1): `hh-secret-scan`'s
  `DetectorSet::standard` + `leak_scan`/`redact` are the one detector set;
  the slot-token tier is a mask set over the same machinery, not a new
  detector family.

## Revisit trigger

Re-open if (a) a second upload tool or a public dataset is admitted
(the single-tool admission and `private`-only refusal must be re-cut);
(b) `hf`'s argv surface changes such that `upload`/`download` or
`HF_TOKEN` semantics diverge from the pinned version; (c) Q-X59 resolves
against pre-authorized purge — the remediation order or its record
shape may then tighten; or (d) a W-skeleton measures a load path that
cannot carry base-blob re-pull by digest (RD-13's UNVERIFIED terms).
