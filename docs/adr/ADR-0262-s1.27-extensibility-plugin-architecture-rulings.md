# ADR-0262: S1.27 extensibility/plugin rulings — `hh-plugin` owns the contract surface, the manifest rides `ExtensionRecord{kind:plugin}.manifest`, policies ride `RegistryPolicy`, layered-first precedence, and the range-grammar consolidation

- **Status:** Accepted
- **Date:** 2026-09-18
- **Ticket:** S1.27
- **Requirement ids:** R-2.12.2
- **Spec:** §8.4 · §8.5 · §4.4 · ADR-0180/0181/0182 · ADR-0184 D2
- **Rung (ADR-0024 obligation):** **C0** — MUST-data/MUST-code: `PluginManifest/1`,
  `ContractRef`, `ContractVersionPolicy`, `check_compatibility` inside
  `resolve`, `tier`/`depends_on`, the spec-DAG check, the module-graph lint,
  `plugin_abi/1` in the kernel schema export, `placement` on registrations,
  the golden manifest corpus.

## Context

S1.27 lands the C0/Stage-1 slice of §8.4 (the extensibility/plugin
architecture). Several placements were underdetermined by the spec's field
lists and needed a ruling consistent with the ratified ADRs:

1. **Crate homes.** `ContractRef`/`ContractVersionPolicy`/`check_compatibility`
   are consumed by the registry *and* by the spec-DAG/module-lint tooling —
   putting them in `hh-registry` would force tooling crates to depend on the
   store; putting them in `hh-embed-schema` would mix the schema plane with
   resolution semantics.
2. **`ContractVersionPolicy` storage.** §8.4 §3 calls it "a `hh/`-namespace
   registry record (MUST-data)" — but `registry/1`'s `RecordKind` sum is
   closed (R2/AC-2 of §6.2: growth is `registry/2`, never `ext`).
3. **`PluginManifest/1` storage.** The spec makes a plugin "an
   `ExtensionRecord{kind: plugin}`" — the manifest is the `manifest` member's
   canonical content, not a new record kind.
4. **`tier`/`depends_on` on a manifest.** §8.4 §3's declaration row puts
   `depends_on` on "every `ClassRecord` and every plugin manifest" but the
   `PluginManifest/1` field list does not name the members.
5. **Range grammar.** `hh-registry::store` carried a private
   `range_covers`/`version_cmp`; `ContractRef.version_range` needs the same
   grammar (CC1 — one scheme).
6. **Policy precedence.** With a kernel table plus operator-layered policies,
   `check_compatibility`'s first-match lookup needs a defined precedence so a
   layered sunset can actually narrow the kernel table.
7. **`path_or_locator` / `code_pointer`.** AC-1's fault list (inline body,
   serialized closure, path outside the package root, unpinned) needs concrete
   member-level rules.

## Decision

1. **New `hh-plugin` crate** owns the §8.4 contract surface:
   `contract` (`ContractRef`, `ContractRefKind`, `VersionRange`,
   `ContractVersionPolicy`, `SunsetBound`, `EvalPoint`, `ContractIncompatible`,
   `check_compatibility`, `negotiate_version`, `kernel_contract_policies`,
   `contract_defining_tier`), `dag` (`parse_spec_tables` +
   `spec_dag_check` over the §4.4 tables as data, extended by
   `ClassDagInput`/`PluginDagInput`), `lint` (the module-graph lint for
   first-party in-process variants — `use`-root allowlist, sibling-`variants`
   reach, `mod` declarations, `unsafe`), `corpus` (the golden-corpus driver —
   checker-agnostic so the *naive* second implementation and the registry
   codec can be compared), and the `hh-plugin-check` readiness binary
   (`spec-dag`, `module-lint` subcommands). Depends on `hh-wire`,
   `hh-identity`, `hh-provenance`, `hh-ontology` only — never on
   `hh-registry` (the dependency direction is registry → plugin, not the
   reverse).
2. **`RegistryPolicy.contract_version_policies: Vec<ContractVersionPolicy>`**
   carries the operator/layered policies. A dedicated `RecordKind` would be a
   `registry/2` dialect bump; the kernel's own table is
   `hh_plugin::kernel_contract_policies()` and the admission set is
   **layered-first** (`contract_version_policies` then kernel table then one
   `record_kind:<kind>` row generated per `RecordKind::ALL` member —
   supported `["1"]`), so an operator sunset narrows the kernel table while
   the built-ins supply the contract universe. The field encodes only when
   non-empty — pre-S1.27 canonical policy bytes are unchanged (CC8).
3. **`PluginManifest/1` is `ExtensionRecord{kind: plugin}.manifest`** —
   decoded/encoded by `hh_registry::extension::plugin`
   (`manifest_from_json`/`manifest_to_json`/`manifest_from_bytes`), admitted
   by `admit_plugin` inside `register`'s `Extension` arm, and re-checked by
   `execute_mode_compat_check` inside `resolve(mode = execute)` — a sunset
   that passed between admission and execute refuses there, dated (AC-2).
4. **Manifest `tier` + `depends_on` are top-level members** (mirroring
   `ClassRecord.tier`), decoded strictly alongside the spec-listed members;
   `depends_on` is a `[ContractRef]` array, defaulting to `[]` only where the
   member is absent is NOT permitted — the member is required (a manifest
   with no declared dependencies still declares `[]` — CC3).
5. **The range grammar consolidates into `hh_plugin::contract`**:
   `RegistryStore`'s private `range_covers`/`version_cmp` are delegates to
   `hh_plugin::contract::{range_covers, version_cmp}` with byte-identical
   semantics (`*`/empty, `>=v`, `<=v`, `lo-hi`, exact; `v`-prefix tolerated;
   unparseable segments compare as 0). `VersionRange::parse` is the strict
   boundary grammar for manifest/policy decode.
6. **Member-level pin rules** (`path_or_locator`, `code_pointer`,
   `requires.records[]`): a string `path_or_locator` is a package-relative
   path — absolute, `..`-containing, `:`-carrying or empty spellings are
   `SchemaViolation`; an object form is a `SourceLocator` that must be
   `is_pinned()` and credential-free else `UnpinnedInSealedForm`/
   `SchemaViolation`; `executable.code_pointer` is a `ContentAddress` object
   — anything else (bare selector, missing digest/size, non-`sha256`
   algorithm) is `UnpinnedInSealedForm`; `requires.records[]` members are
   `{version_id, kind?}` pins (no selector/name forms). `declaration` members
   named `body`/`content`/`closure`/`code` are refused — declarations name
   records, they never carry them (AC-1).
7. **Admission check order**: namespace → locality (per-`executable`
   isolation/`placement_preference` vs first-party = registrar authority ∧
   `hh/` namespace) → tier (`depends_on` defining-tier ≤ manifest tier;
   unnameable ref → `ContractIncompatible`) → `check_compatibility` (the
   `hir_dialect`/`registry_dialect`/`plugin_abi` ranges materialised as
   `ContractRef`s on the `…/1` contract ids + `requires.contracts` + each
   contribution `contract_range` — `variant` contributions resolve their
   class via `declaration.class_id`, other kinds via `record_kind:<kind>`)
   → `requests ⊆ requests_cap` when supplied. All checks are pure — no fetch,
   no spawn exists at Stage 1; refusal precedes any launchable artifact.
8. **`in_process` admissibility**: `placement_preference = in_process`
   requires *both* the registrar's conferred first-party authority
   (`kernel`/`definition`) *and* `identity.namespace ⊆ hh/` — reading either
   alone would let a `hh/`-named third-party manifest or a first-party
   `local/` manifest slip the CF-141 vector.
9. **`hh-hosting/1` appears nowhere** — not in `kernel_contract_policies`,
   not in the schema, not in `depends_on` admissible tiers (its defining
   tier is C2, so a C0/C1 `depends_on` on it is `TierViolation`; a `requires`
   on it is `ContractIncompatible` with empty `supported_range`) — AC-12 by
   construction *and* by check.

## Consequences

- AC-R-2.12.2-1 (manifest is inventory): strict decode refuses unknown
  non-`ext` members, inline bodies, escaping paths, unpinned pointers —
  the 14-case golden corpus (`tests/fixtures/plugin-manifests/`) pins the
  failure kinds (`UnknownRecordKind`, `ContractIncompatible`,
  `UnpinnedInSealedForm`, `RequestsExceedCap`, `SchemaViolation`,
  `LocalityInadmissible`, `TierViolation`).
- AC-R-2.12.2-2 (compatibility before load): `register` of a plugin
  extension runs `admit_plugin`; `resolve(mode = execute)` re-runs
  `check_compatibility`; a past-sunset refusal carries the dated bound.
- AC-R-2.12.2-8 (extension DAG): `hh-plugin-check spec-dag` parses the
  §4.4 tables — `nodes=164 edges=741 ks_edges=59 tier_violations=[]
  cycles=[]` — and `module-lint` walks `crates/*/src/variants/**`
  (vacuously clean at Stage 1; the walker and the negative fixtures are
  tested).
- AC-R-2.12.2-12 (T-LCD-06): no `PluginManifest/1` member, `plugin_abi/1`
  member or `ContractRef` policy references the Hosting ABI or
  `OpaqueProcess`.
- `ClassRecord.depends_on` encodes absent-when-empty, so every pre-S1.27
  class record's canonical bytes — and therefore its `version_id` — are
  unchanged (CC8; the corpus's pinned digests still verify).
- The naive-checker seam: `hh_plugin::corpus::run_corpus` takes any
  `bytes → Result<id, kind>` closure; the registry test wires the real
  codec; a foreign implementation runs the same `.expect` pins (the
  cross-candidate half is DF-S1.27-1).

## Alternatives considered

- **A dedicated `contract_version_policy` `RecordKind`** — rejected: grows
  the closed `registry/1` sum, which is a `registry/2` dialect bump; the
  policy member is additive and carries the same data.
- **A `plugin` `RecordKind`** — rejected: the spec makes a plugin an
  `ExtensionRecord{kind: plugin}`; a parallel record kind would fork the
  extension lifecycle (L1–L3, locator pins, trust legs).
- **`ContractRef` in `hh-registry`** — rejected: the spec-DAG tool and the
  module lint must not depend on the store; `hh-plugin` is the leaf the
  registry consumes (CC10 layering).
- **Manifest `requires.dialects` as one map** — rejected: the spec names
  `hir_dialect`/`registry_dialect`/`plugin_abi` members; materialising them
  as `ContractRef`s inside `check_compatibility` keeps one dependency form
  (X1) without re-spelling the wire shape.

## Revisit trigger

A `registry/2` dialect bump (which would promote `ContractVersionPolicy` to
a record kind and could move `PluginManifest` onto its own kind), a C1
`remote`/`container` execution slice needing per-contribution
`placement_preference` semantics beyond Stage-1 admission, or the Stage-2
variant host needing `requests` → `Permission`/`ContainmentPolicy` lowering
inside `admit_plugin` (the `requests_cap` seam is already the shape).
