# ADR-0434: The comparative-protocol support gate for stochastic hosted participants (AR-12)

- **Status:** accepted (lands with manifest 271/R6.18)
- **Date:** 2026-11-07
- **Ticket:** R6.18 (SELECT + D1-a)
- **Amendment register item:** AR-12 (experiments spec §10.5)
- **Requirement ids:** REQ-XC-010, REQ-XD-020

## Context

Experiments spec §4.6 gives `central_protocol` a hard support gate:
`materialize_protocol` refuses any protocol whose `support_seed`,
`support_fingerprint` or `support_cache` declarations are false. For the
two-arm compaction study those supports were honest — the participants
were pinned artifacts whose seed, cache-bypass and fingerprint behavior
were verifiable properties of the arm.

Phase 2's participants are stochastic hosted models — glm-5.3-flash on
Ollama. REQ-XC-010 fixes their honest declarations:

- `support_fingerprint = false` — the `hh.fingerprint/v1` probe
  (temperature 0, 128 tokens) misleads on an always-thinking model and
  is never an identity gate.
- `support_cache = false` — provider-side cache state is a typed
  unknown; the harness cannot assert a bypass.
- `support_seed = unverified` — treated as false until a recorded
  replay test passes.

Invoking the existing gate on these participants either refuses the
phase-2 design outright or invites falsified declarations — flipping
the booleans to satisfy the gate. REQ-XC-010 forbids both: "A protocol
gate requiring these supports SHALL be amended by ADR (AR-12) or
replaced, never satisfied by flipping booleans." REQ-XD-020 then gives
the comparative protocol ownership of "the declared-unsupported support
members … admitted only under the weaker claim class of AR-12."

## Decision

- `central_protocol`'s support gate is **byte-unchanged** — it still
  refuses false support declarations for the two-arm study it was
  written for. `comparative_protocol/1` is a sibling materializer
  (D1 F2, C-11), never an edit to that gate and never a call into it
  with adjusted declarations.
- `comparative_protocol/1` admits per-arm support declarations of
  `fingerprint`, `cache` and `seed ∈ {verified, unverified}` as
  **recorded facts, not gate predicates**. An arm whose every support
  verifies carries claim class `admitted_support`; an arm with any
  declared-unsupported member carries `declared_unsupported` — the
  weaker claim class this ADR admits.
- Under `declared_unsupported`, claims are restricted: participant
  identity is `catalog_declared` (REQ-XC-120 — the Ollama catalog
  tuple, effort pin and `gen_param_policy` hash, with what it does not
  establish stated), never determinism, seed-replay or
  fingerprint-equality claims. `hh.fingerprint/v1` byte-equality is
  never an identity gate; a declaration asserting it as one refuses
  typed.
- `support_seed = unverified` is treated as false until a recorded
  replay test passes; upgrading to `verified` requires that replay
  record, not a declaration edit.

## Consequences

- The glm-5.3-flash arms materialize with their honest declarations
  (`false / false / unverified`) and the record marks the weaker claim
  class instead of pretending support.
- Nothing in `central_protocol` loosens: its AC surface is unchanged,
  and a test asserts the comparative path never invokes its
  materializer with falsified support.
- A participant later gaining verified seed/cache support upgrades its
  claim class by a new declaration plus the replay record — the class
  is derived, never asserted.

## Alternatives considered

- **Flip the booleans** — REQ-XC-010's named failure mode; rejected.
- **Widen `central_protocol`'s gate with a flag** — a second gate
  semantics in one materializer (C-11, D1 F2); rejected.
- **Drop the support members entirely** — hides the typed unknowns;
  the record would claim more than was declared. Rejected.

## Revisit trigger

Revisit when a recorded replay test verifies seed honouring or cache
bypass for a hosted participant (the `unverified` declaration and the
`declared_unsupported` claim class then upgrade by new declaration, not
edit), when a phase-2 arm needs a fourth support member (a new member
is a new declaration, not an extension of this ADR), or when any claim
under `declared_unsupported` needs wording the class does not carry —
that is a new AR item, not a widening of this gate.
