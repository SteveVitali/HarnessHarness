# ADR-0424: The GitHub Pages lane — separate `pages.yml`, SHA-pinned actions, `hh-site-publication/1` records (AR-28)

- **Status:** Accepted
- **Date:** 2026-11-07
- **Ticket:** R6.6 (manifest row 259; experiments supplement §9.6)
- **Requirement ids:** REQ-XF-128, REQ-XF-129, REQ-XF-130, REQ-XF-140, REQ-XH-018
- **Spec:** experiments supplement §9.2, §9.4, §9.6; design/39 F10
- **Rung (ADR-0024 obligation):** docs/CI surface — no runtime contract moves rung

## Context

Round 6 must ship the public results-site profile with three hard
guarantees: nothing is public until an explicit operator gate
(REQ-XF-128); only the phases a committed publication record pins reach
the public tree (REQ-XF-129); and publication is an append-only,
operator-gated act — an agent can never flip it (REQ-XF-130,
REQ-XH-018). AR-28 requires this ADR to land before the workflow file,
carrying the exact pinned action SHAs.

Design/39 F10 already fixes the shape: the site has two profiles —
`internal` (renders every phase its inputs carry, designed absent
states elsewhere) and `public` (renders a phase only where a committed
`hh-site-publication/1` record pins that phase's *exact* input set —
everything else is `not yet published — publication gate pending` with
no numbers). A record whose pins no longer match the current named
inputs refuses the public build; republishing drifted inputs is a new
record and a new operator gate, never a silent re-pin.

## Decision

1. **`.github/workflows/pages.yml` is separate from `ci.yml`.** It
   triggers on `push` to `main` and `workflow_dispatch` only — never
   `pull_request`, so an untrusted head can never reach a deploy step.
   Permissions are minimal and explicit: `contents: read`,
   `pages: write`, `id-token: write`. A `concurrency` group serializes
   deploys; `cancel-in-progress: false` keeps a running deploy atomic.
2. **Every `uses:` is pinned by a 40-hex commit SHA** with a `# v…`
   comment naming the tracked version:
   - `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1` — v7.0.1
   - `actions/configure-pages@45bfe0192ca1faeb007ade9deae92b16b8254a0d` — v6.0.0
   - `actions/upload-pages-artifact@fc324d3547104276b827a68afc52ff2a11cc49c9` — v5.0.0
   - `actions/deploy-pages@368f82528645a54fb793d4d04e342629a3f51346` — v5.0.1
   `scripts/ci/check-pages-workflow.sh` statically lints the file for
   these pins, the permissions, the triggers, the concurrency group,
   and the publication gate — a self-test mutates each element.
3. **The record gate precedes every deploy step.** The job builds the
   public profile (`build.py --out _site --profile public`) and checks
   it (`check-site.sh --profile public _site`) unconditionally — the
   green build is the honest "nothing published" state. The
   `configure-pages`/`upload-pages-artifact`/`deploy-pages` steps each
   carry `if: steps.pub.outputs.published == 'yes'`, where `pub` globs
   `docs/results/publication/*.json`. Zero committed records → the job
   exits green and deploys nothing. The *record* is the switch, not a
   variable, secret, or environment.
4. **`hh-site-publication/1` is append-only and pins inputs.** One
   `docs/results/publication/<phase>-<YYYY-MM-DD>.json` per decision;
   it names the manifest gate row (`GATE-G22`/`GATE-G31`), references —
   never copies — the operator's readout, pins `{path, sha256}` per
   input plus the canonical `inputs_digest`, carries
   `labels.outside_verified: false`, and supersedes only by a
   `supersedes` path. Validation lives in `hhsite/publication.py`;
   `check-publication.sh` runs it plus the manifest-row checks.
   Changelog entries and `/archive/<version>/` markers derive
   deterministically from the record set (REQ-XF-140).
5. **Human rows the agent never performs** (REQ-XF-130): HUMAN-H12
   (Pages enablement), GATE-G22 / GATE-G31 (per-phase publication
   decisions), and HUMAN-H17 (dataset-visibility flip — a *separate*
   human act requiring fresh secret + contamination scans and a pinned
   revision). The validator fails closed if the manifest lacks these
   rows or the checklist `docs/results/publication/CHECKLIST.md` is
   absent.

## Consequences

- With zero records the public profile renders the
  publication-gate-pending absent state on every phase surface — a
  page that can be checked end-to-end before anything is deployed.
- A record pins *bytes*: editing a named packet afterwards refuses the
  build rather than silently publishing drift. The cost is that every
  republish is a new record; the benefit is the public tree is always
  byte-consistent with what was decided.
- `pages.yml` does not weaken `ci.yml`'s path-mode guarantees — it is
  not part of the ADR-0362 step-mode graph.
- A malformed record fails closed at both seams: `check-publication.sh`
  (committed-tree lint) and the public build itself (validator inside
  `run_out`).

## Alternatives considered

- **Deploy gating on a repository variable or environment secret.**
  Rejected: the switch would be invisible in-tree and could be flipped
  without a commit. The committed record makes publication an
  auditable, append-only act.
- **A `pages:` job inside `ci.yml`.** Rejected: Pages deploys need
  `pages: write`/`id-token: write`, which would widen CI's permission
  surface; and the deploy must never run on pull_request heads, which
  is easier to guarantee in a file with no `pull_request` trigger at
  all.
- **Copying the operator's gate decision into the record.** Rejected
  (ADR-0362's verbatim-decision-in-readout rule generalizes): the
  record references the readout path; the decision stays verbatim in
  one place.

## Revisit trigger

Any change to the Pages surface — a new action version, an added deploy
step, a widened permission, a changed trigger, or a second publication
record — re-arms this ADR: update `check-pages-workflow.sh`, the
`hhsite/publication.py` validator and this record's pinned SHAs in the
same commit.
