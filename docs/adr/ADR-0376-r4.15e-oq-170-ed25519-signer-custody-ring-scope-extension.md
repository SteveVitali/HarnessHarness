## Context

OQ-170 — *which process holds the audit-signer key, and how does custody
reach the `AuditSigner`/`AuditKeyResolver` seam?* — was reserved by
ADR-0213 (WS-H3/H6/L4) and held open by ADR-0331 D3 ("custody stays
external; the landed seam is the conformant interim"). The round-4
re-charter moved the ratification to the operator: the BL-30 brief
(`docs/build/planning/round4-bl30-adjudication-briefs.md` §OQ-170)
drafted a concrete custody proposal with a recommended option and three
costed alternatives, dispositioned `needs-code-leg(R4.15e)`. At GATE-G7
(2026-10-22, "Adopt all" — LEDGER GATE DECISIONS ### Round 4) the
operator adopted the proposal as written: **the kernel holds the key;
`hh-secrets` is the custody home; the algorithm is Ed25519 via
`ring::signature`.**

The blocker this ADR resolves: ADR-0359 D2 admitted `ring =0.17.14` for
**verification plus test-time fixture signing** (the DPoP proof-of-
possession verifier) and reserved `ring::aead`/`ring::rand` for R3.8's
blob-pool AEAD (ADR-0361). *Production* signing with a persistent key —
generating, persisting, and signing with `ring::signature`'s
`Ed25519KeyPair` — exceeds that admitted scope. D2's own revisit rule is
that a sibling-scope act needs its own ADR; this is that act. The crate,
the pin (`=0.17.14`), and the dependency count are unchanged — only the
admitted API surface grows.

## Decision

- **D1 — custody owner and location (the adopted proposal verbatim).**
  `hh-secrets` holds the kernel's ledger-signing key: the only
  `ring`-admitted crate keeps key material under one owner. The kernel
  holds the signer in-process; `hh-ledger` sees the landed
  `AuditSigner`/`AuditKeyResolver` seam only (`key_id` +
  `sign(preimage)` + public verify bytes — key material never crosses).
- **D2 — the admitted `ring` surface extends to Ed25519 production
  signing.** ADR-0359 D2's admitted scope is amended to add, same crate
  and same pin:
  - `ring::signature::Ed25519KeyPair::{generate_pkcs8, from_pkcs8}` —
    per-installation key generation and document parsing;
  - `ring::signature::KeyPair`/`Ed25519KeyPair::sign` — production
    checkpoint signing;
  - `ring::signature::UnparsedPublicKey` over `&ED25519` — public-half
    verification inside the `AuditKeyResolver` implementation;
  - `ring::rand::SystemRandom` — the generation source (already
    admitted for R3.8's AEAD nonces; now also the key-mint source).
  No other `ring` module is admitted; every previous exclusion stands.
- **D3 — the file-backed custody layout.** The install/provisioning act
  writes `<HH_STORE_ROOT>/secrets/ledger-signer.<key_id>.pkcs8`, mode
  `0600`, owner-only — minted on the host (`generate_pkcs8` +
  `SystemRandom`) or operator-placed. `key_id` is
  `ed25519-<hex(sha256(public_key))[..16]>` — content-derived, so the
  file name can never lie about which key it holds. `ledger-signer.active`
  names the live key; retired `.pkcs8` files stay so historical
  checkpoints keep verifying. No key bytes enter ledger state, manifests,
  child environments, logs, or projections — the seam's `key_id`/`sig`
  fields only (`provided: yes/no`).
- **D4 — the honest postures.** An absent custody is the unprovisioned
  posture (`Ok(None)`): `signer_key_ids` stays empty and `audit_view`
  keeps reporting `n/a{no signer_key_ids declared}` — never a fabricated
  signer. A present-but-defective custody — a missing named key, a file
  whose mode is not `0600`, a document that does not parse or whose
  derived `key_id` does not match its file name, an ambiguous or
  dangling active pointer — is a typed `CustodyError` refusal at boot,
  never a warning, a placeholder, or a silent half-load.
- **D5 — provisioning through `kernel_use`, not a side channel.** The
  signer materialises through
  `CredentialBroker::kernel_use(KernelPurpose::LedgerSigning)` over a
  `kernel_only`, `bindable: false` `CredentialKind::SigningKey` channel:
  the `security.credential.used{destination = kernel:ledger_signing}`
  row is durable before the value returns (§5g.6 (a)). The `AuditSigner`
  is built from the delivered PKCS#8 document, never from a file read
  that bypassed the seam.
- **D6 — the checkpoint signature contract extends additively (CC8).**
  `signatures[].alg_ref` extends `{hmac-sha256}` → `{hmac-sha256,
  ed25519}`; `sig` spells `<alg>:<hex>` under one codec
  (`render_sig_alg`/`parse_sig_alg`, 32-byte HMAC / 64-byte Ed25519
  lengths). The resolver holds **public** bytes only — a verifier
  (including a foreign cross-implementation replay) cannot forge, which
  is the asymmetric point the brief names. The C0 `FixedSigner`/`KeyTable`
  HMAC construction stays admitted and verifiable — existing signed
  runs do not break.
- **D7 — co-signed custody rotation.** `CheckpointKind::Rotation` gains
  the `key_rotation{from_key_id, to_key_id}` claim member (inside the
  signed preimage): incumbent and successor co-sign the same unsigned
  claim, the incumbent must already be admitted on the run, and a
  verified claim folds `to_key_id` into the effective signer set while
  retired ids stay resolvable. A rotation claim lacking the incumbent's
  co-signature is a defect (`BadRotation` → `BadSignature` at verify) —
  rotation is itself an auditable ledger event (CC3). Signer-key
  rotation is distinct from `idp`-profile rotation (ADR-0036): a `key_id`
  is a custody coordinate, never an identity; neither rotation forces
  the other.
- **D8 — `signer_key_ids` accumulation.** Every manifest the kernel
  opens carries the custody's full key-id set (current + retired); the
  kernel confers the set — a caller or surface can never subtract it.
  The `kind = final` checkpoint lands after `lifecycle.run.finished`
  signed by the kernel-held key.

## Consequences

- Signed audit checkpoints are asymmetric for real: exported runs verify
  against public bytes; a holder of the `KeyTable` cannot mint claims.
- The kernel boot loads custody honestly — provisioned installs sign
  immediately (the sign-on-boot `on_demand` checkpoint is the boot's own
  proof); unprovisioned installs keep the unchanged honest unsigned
  posture.
- `subagent_anchor` and `producer_resolution` checkpoints now ride real
  custody — their claims verify against public keys, not fixture HMACs.
- `hh-secrets`'s `ring` surface grows; the workspace stays otherwise
  hermetic. `Cargo.lock`, toolchain, and CI fetch behaviour are
  unchanged (no new package).
- A mis-permissioned or corrupt key file now *refuses the boot* — an
  operator-visible act; recovery is fixing the file, not a fallback.
- Retired-key retention is a disk-costs-bytes trade for verifiable
  history — the adopted ruling's own trade, recorded.

## Alternatives considered

All four options below are the BL-30 brief's costed table — adopted
verbatim at GATE-G7; recorded here for the record.

- **Kernel-held `hmac-sha256`** (zero scope growth — the landed
  `CHECKPOINT_ALG` + `FixedSigner` shape) — rejected: symmetric custody
  means every resolver holds sign power; an exported audit trail cannot
  distinguish verifier from signer. The asymmetric upgrade is the point
  of the adopted ruling.
- **Helper-held key** (process isolation) — rejected: the helper is
  per-spawn ephemeral; custody continuity and per-run availability
  couple wrongly. WS-H3 reserves the helper model.
- **External key store** (OS keychain / HSM / KMS — the strongest
  custody boundary) — rejected: unprovisionable under the hermetic
  build; a platform dependency. A future admission, not this ticket.
- **Deferring the code leg** — rejected by the GATE-G7 "Adopt all" act
  itself: the brief dispositioned OQ-170 `needs-code-leg(R4.15e)` and
  the operator adopted it.

## Revisit trigger

- A future custody ruling (e.g. operator-adopted OS-keychain/HSM/KMS
  storage, or a hardware-attested signer) reopens D3/D5 — the seam
  already isolates the change.
- Witness-signature custody (`WitnessDecl`) adopts the same
  per-installation file convention when witness declarations land —
  the revisit vehicle for extending this custody to the witness seam.
- Any additional `ring` module, a second crypto crate, or a non-Ed25519
  signing algorithm requires its own sibling-scope ADR — D2's closed
  list is the boundary.
