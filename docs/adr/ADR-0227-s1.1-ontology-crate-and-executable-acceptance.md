# ADR-0227: S1.1 lands the ontology and formal model as the persistent `hh-ontology` crate, with §2.9.2 acceptance made executable

- **Status:** Accepted
- **Date:** 2026-09-15
- **Ticket:** S1.1
- **Requirement ids:** R-2.1.1
- **Spec:** §2 (all subsections); §2.9.1 interface contracts; §2.9.2 acceptance criteria; §2.9.3 build stage; §2.9.4 data model; §2.9.8 test-matrix hooks; ADR-0012, ADR-0013, ADR-0014

## Context
§2 (R-2.1.1, C0/Stage 1, Must) fixes the ontology and formal model: the seven planes and the
home-plane rule (CC10 originates here), the two boundaries, the three cross-cutting attributes,
the formal-model symbols (θ, M, E, D, B, κ, β, Δ, Ψ, J, π_M, π_system), configuration κ with
both configuration ids, the two participant classes with `admissible_granularities`, validity vs
compliance with the three chain events, the compatibility surface Ψ_θ, and the control boundary
β. §2.9.2 makes AC-A2-1/-2/-7 deterministic and AC-A2-3…-6 carry a *static half* landed at
Stage 1 (the executable halves land at Stage 3, §2.9.3). §2.9.8 names the fixtures and checks
(classify_home totality, symbol resolution, the spec-DAG check, the glossary check). The
existing workspace is a hermetic pure-std Rust binding of the E1 candidate (ADR-0050 (e),
ADR-0217); the contracts name no language (CC4) — the crate is the *build binding* only.

## Decision
Land §2 as a new **persistent** workspace member `crates/hh-ontology` (contrast the throwaway
`hh-baseline`, ADR-0221): the home table + `classify_home`, the formal-model symbol registry,
κ + both configuration ids, the participant classes, the compliance chain schema, the
compatibility-surface shape, the control boundary, plus the executable §2.9.2 checks. Specific
owned choices:

1. **`classify_home` totality by construction, plus a runtime identifier path.** The classifiable
   domain §2 fixes directly (event families, plane operators, §2-named component classes,
   boundary components, `run_lifecycle`) is a closed `Kind` enum, so `classify_home(&Kind) → Home`
   is total by exhaustiveness — the compiler forbids an unclassified kind. The IR-validation
   runtime path is `classify_home_identifier(&str) → Result<Home, UnclassifiedKind>`, which meets
   an unregistered identifier (a `state.*` prefix, a `misc` plane, an unknown operator) and raises
   `UnclassifiedKind` (§2.9.6; §2.10 "a `misc` plane" escape hatch refused). Both forms of the
   §2.9.1 contract are present.
2. **Configuration ids reuse the one Stage-0 content-address scheme (CC1).** `configuration_id`
   (seedless semantic coordinate) and `configuration_version_id` (seeded exact-bytes manifest key)
   are `sha256` content addresses over a canonical, order-fixed rendering, reusing
   `hh-wire::sha256` — no second hashing scheme. (These are Stage-1 semantic/version coordinates;
   the `idp/1` canonical-form migration is DF-S0.1-2 / S1.2, unchanged here.)
3. **CC7 single source without a codegen edge yet.** The §2 records (home table, descriptor,
   metric declaration, chain events, β, surface report) are defined **once** in `hh-ontology` —
   the single source. No JSON-Schema export / generated-client edge is added at Stage 1 because no
   §7 surface binding consumes these records yet; the schema-export→codegen pipeline (S0.1) stays
   scoped to the `hh-embed/1` wire contract. When a surface first consumes an ontology record, that
   ticket adds the export+drift edge (CC7 obligation deferred to its first consumer, not skipped).
4. **Static-half scope.** Behaviours §2.9.3 reserves for later stages (β *variable*, emitted
   `delivered`/`activated`/`followed`, `paired_effect`, judged detectors, fitting Ψ_θ from real
   rows) are landed as *shapes and preconditions* only (record types, the no-interpolation rule as
   `UnknownLevel`, the envelope-reserved-code rule as `IncompatibleBoundary`), never executed.

## Consequences
- Good: AC-A2-1/-2/-7 and the static halves of AC-A2-3…-6 are executable under the existing CI
  (`cargo test --workspace`, no new job); 56 new tests (48 unit + 8 integration) each fail if the
  behaviour they guard is removed; the spec-DAG check reports `tier_violations=[]`, `cycles=[]`,
  `hosting_edges=[]`, `proj_abi_total=true`. The crate is pure-std, offline, hermetic; downstream
  Stage-1 tickets (S1.2 identity, S1.4 HIR, S1.6 budgets, …) `cite` these constructs.
- Cost: the ontology records are typed Rust with no cross-language schema export until their first
  surface consumer (item 3); that consumer must add the CC7 export/drift edge. The `classify_home`
  split means two entry points instead of one (documented at both).

## Alternatives considered
- **Fold §2 into `hh-kernel`.** Rejected: §2 is the shared vocabulary every later subsystem
  resolves against; a standalone crate keeps the dependency direction clean (kernel and later
  crates depend on the ontology, not vice-versa) and matches the one-crate-per-concern layout.
- **A single fallible `classify_home(&str)` only.** Rejected: it discards the compile-time
  totality guarantee the closed `Kind` enum gives (the strongest possible form of "total over
  registered kinds"); the runtime path is retained *in addition* for the IR-validation case.
- **Add the JSON-Schema export/codegen edge for every ontology record now.** Rejected as premature
  (CC8/simplicity): no surface binding consumes them at Stage 1, so the generated artifacts would
  have no consumer and no drift signal of value; deferred to the first real consumer.

## Revisit trigger
When the first §7 surface/plugin binding consumes an ontology record (descriptor, metric
declaration, chain event, β, surface report): add that record to the single-schema-source export
and the CI drift check (CC7), and reconcile the Rust type with the generated binding. Also revisit
if §2 is amended (spec amendment protocol) or a later ticket needs a second content-address scheme
(it must not — CC1).
