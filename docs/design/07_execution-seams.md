**Q-2 finding:** this is more than runner glue. Three prerequisites precede an informative compaction pilot: (1) the chosen strategy must change the request actually sent to the provider, (2) all four matched budget dimensions must be enforced on that path, and (3) one integration must own the launched subject, real task execution, independent grading and terminal/result settlement. Existing native mechanisms supply substantial pieces, but the inspected default service path does not establish that chain. A configured variant, successful lifecycle or supplied reward is insufficient evidence.

## Minimal route options and ownership

The [facade](../../crates/hharness/src/lib.rs) reexports the owning layers. Keep authoritative events in the fenced run ledger, identity/canonicalization in existing owners, projections in ResultsStore and reports in Lab. `hh-bench` has control/gateway/context as test dependencies rather than a production runtime owner ([manifest](../../crates/hh-bench/Cargo.toml)); do not reverse that layering to make the adapter drive the kernel. Any dependency expansion or contract/schema change needs its normal ADR/generated-client process.

Using the original runner is an option to reuse existing apparatus, not permission to change the benchmark version, oracle, network policy or subject accounting silently.

## Answer and completion assessment

E1 is complete as source-backed feasibility research. Implemented producers include experiment subject allocation, lower-level driver/context/environment mechanisms, grading parsers, budget Account, results projections/overlays, analysis and native export. Missing selected-path integration includes launched-subject adoption, actual task/effect/verifier execution, treatment binding and request consumption, canonical budget enforcement, detector/rate mapping, grade/terminal/settlement ordering and receipt closure. Some may be small compositions; others require owning-layer fixes. Their runtime feasibility and engineering size remain open.
