## Review entry — recommendation for Q-2

**Approve the connected portfolio for further design, with a tightly bounded offline feasibility tranche before selecting the implementation route.** Serve the technical harness evaluator who wants to compare a policy on useful tasks and inspect the evidence. Lead with one actual independently checked task, then explain its native trace, replay and receipt; add a small honest offline Lab lesson, the central real two-arm compaction study, and a few recovery/deny/pause/budget cases using the same apparatus. A report/verification path belongs in the foundation. One packaged-component exercise and at most one foreign receipt consumer remain optional. All 22 capability families and nine later groups retain C1's explicit dispositions (F2).

The audits change feasibility. The setup fixture works but does not produce the promised useful artifact. Selected Lab CLI requests are incomplete, and a newly exported successful fixture reports R0 lifecycle drift. Current live receipts preserve useful bounded evidence, but date/leg filenames overwrite earlier attempts and do not distribute native replay closure. E1 adds deeper gaps: experiment launch and ordinary session opening create different subjects; real task tools and an executable upstream verifier still need an owner; grading accepts supplied verifier output; terminal execution and later grade/settlement need a coherent order. This requires integration and behavior work alongside documentation (F1).

Keep **useful-task readiness separate from study readiness**. The useful-task route needs real effects, an independent correctness check, honest outcomes and a retained native receipt. It need not first solve every compaction metric or complete a statistically informative study. The study additionally needs proof that the selected native policy changes the actual serialized provider input: the inspected default ladder only falls back to eviction, while the gateway reconstructs the full transcript independently of assembled input. It also needs actual enforcement of input tokens, output tokens, model calls and real elapsed time. Fixed remaining-token fields, logical guard ticks and a `full` stamp do not establish those caps. Detector counts need valid rate definitions and denominators. These are admission gates, not details to discover during paid confirmation (F1/F4).

Investigate a restricted native scenario runner first. It should compose existing owners and give a technical reader one documented, versioned recipe; it must not copy private runtime code or author success rows. Where suitable, reuse the pinned original task runner for environment setup and the unchanged oracle. That does not repair native treatment or accounting. A generalized supported embed/API route adds compatibility, negotiation and lifecycle obligations; choose it only if the restricted composition cannot meet the selected user job, or Q-2 explicitly values broader integration enough to fund it. E2 may establish the minimum owning-layer extraction by source-backed design without implementing it (F3/F5).

The minimum useful release still includes an actual checked task, its trace and tested native verification/replay/R0 procedures, the offline Lab lesson and a precise bug/report path. If the study is blocked, publish its unmet gates and seek an explicit scope decision; do not describe that release as completion of the comparison objective. If even the task bridge fails, a fixture-only teaching/diagnostic package is available, but it fails both the useful-task and real-study objectives and requires a conscious rescope. Conversely, a sound null, negative or inconclusive study can complete the scientific deliverable. A favorable effect is neither an implementation acceptance test nor automatic authority to change a product default (F2/F4).

For sizing, identify **eight core work packages: five shared useful-task/teaching/operational packages and three study-specific packages**. **8–16 implementation/review slices** is a nonbinding illustration of one or two slices per package under F3’s assumptions. Exact slicing may change within approved behavior and ownership; counts are neither measured effort nor approval triggers. Material scope additions receive separate review. Calendar and agent effort remain unestimated until feasibility/decomposition supplies evidence. The immediate proposal is three offline investigations with a combined ten-hour wall-time maximum, scratch-only writes, no installations/network and **$0 additional task-provider/cloud-runtime spend**, excluding ordinary Codex planning usage. It is a ceiling, not expected expenditure (F5).

Study cost cannot responsibly be priced yet. For two arms, `N_subject = 2 × T_selected × R`, with `R ≥ 5`, so the floor is `10 × T_selected` subject runs. The TB2 catalogue's 89 tasks are not an automatic selection of `T_selected`; the held-out manifest and contract interpretation remain D2/Q-3 work. The floor is not a power calculation. Parity, exploratory pilots, retries, independent verification, retention and any fresh replication add resources. Preserve Terminal-Bench 2.0 and all frozen evaluation constraints; if a feasible design needs another version or a reduced contractual obligation, present an amendment. Q-4 later chooses actual model/rate pins and ceilings; old spending authorizes nothing (F4).

After an affirmative recorded decision, D1, G1 and the selected E2 scope can begin; subsequent D2/D3/F1 and integration/receipt work follow the ledger.
