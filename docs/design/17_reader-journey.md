## Reader route and scope

Serve the technical harness evaluator: **README → prerequisites → one real task and independent check → annotated run → one supported edit → offline Lab lesson → real comparison and evidence**. Every stage offers a failure/report exit. Skeptical readers can enter at a receipt. Doctor, scripted completion and inspecting someone else's accepted receipt are separate milestones; none is a newly completed useful task.

The runtime executes/records runs; the Lab plans comparisons and analyzes observations. Explain this beside the first output and Lab handoff. Version commands, definitions and receipts together. Inventory/history are optional depth; retain all [C1 dispositions](06_demo-and-study-portfolio.md#f7--full-family-coverage-does-not-require-a-separate-experiment-per-family).

This conditional design follows Q-2's [recorded approval](../research-ledger.md#checkpoints-and-resource-boundaries); older “Q-2 unanswered” notes remain historical. Q-3–Q-6 own pins, resources, access and participation. Prefer the restricted native runner with one build/invocation recipe; needing a general API returns to E3/Q-2. No provider defaults or unimplemented commands are invented. **Q-/REQ-/ticket gates are internal authoring/release coordination, never reader approval steps.** Public guides explain supported modes, prerequisites, readers' own resource choices and semantic outcomes plainly; an open-source reader using their own provider does not await this program's Q-4.
